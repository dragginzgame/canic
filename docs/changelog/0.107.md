# Canic 0.107 Changelog

## 0.107.0 - 2026-08-20

This is a maintainer-requested checkpoint release. It publishes the coherent
B2-B4 and B6 outcomes plus the B7 evidence independent of B5. It does not
close the 0.107 minor.

### Fleet Planning And Effect Boundary

- Direct `canic deploy plan` receives the selected top-level environment and
  rejects hidden or canonical target disagreement before Fleet-catalog work.
- Direct planning now requires `--fleet-input`, uses the same `--profile` and
  optional `--release-build` spelling as install, and no longer accepts its old
  `--config` or `--build-profile` options.
- Plan and install call one pure host preflight for canonical Fleet identity,
  Coordinator/root placement, Component admissions, initial group assignments,
  limits and positive creation funding. Its structured result records that no
  build, workspace mutation or IC mutation has begun.
- Fresh install loads target authority, Fleet input and its read-only release
  source before any release-build allocation. Invalid Fleet schema or topology
  fails in Planning without creating release-build state.
- Mainnet preflight consumes existing validated cache authority without a
  network call or cache publication. B5 retains ownership of final structured
  live catalog collection and provenance.

### Canonical Decision And Recovery

- One compact canonical decision includes exact workspace or finalized release
  authority, expected artifacts, placement, derived Canister counts,
  per-category funding, maximum operator debit and strictly bounded operator-
  balance evidence. Its domain-separated SHA-256 digest excludes report output
  paths and generated delivery files.
- Direct planning renders the complete decision in text and JSON. Install
  recompiles it before release-build allocation and can require an exact
  expected digest; changed source or balance evidence fails before an effect.
- Same-release install recovery preserves the original decision source and
  digest. Persisted Fleet plans, deployment truth, completion receipts, known
  replica rejection receipts and resume comparisons bind the same digest and
  reject conflicting authority.

### Durable Runtime Whitelist

- Managed application roles now bootstrap memory ID 61 from the validated
  compiled whitelist exactly once. The stable schema owns at most 256 sorted
  principals, one revision and digest, and one retained exact-operation result;
  post-upgrade validates that authority without reseeding or merging config.
- Existing managed `canic_command` and `canic_status` methods gain bounded
  `RuntimeWhitelist` variants under controller-first or exact stable-Root
  authorization. Root, Coordinator, Store and standalone-local specialized
  surfaces do not gain the variants, and `caller::is_whitelisted()` no longer
  reads compiled configuration after bootstrap.

### Validation

- Focused CLI coverage freezes the new grammar, removed spellings, required
  Fleet input, exact finalized release source, structured no-effect output and
  invalid-input behavior.
- Focused host coverage proves canonical root ordering, effect-boundary
  rejection, incomplete placement rejection, install source ordering and
  no-allocation failure for invalid schema and admissions.
- Focused B4 coverage proves complete counts/funding, stale and insufficient
  balance rejection, workspace-source exclusions, plan/install digest parity,
  exact retry, changed-authority conflict, receipt binding and resume mismatch
  rejection. Warning-denied host/CLI Clippy passes.
- Focused runtime-whitelist policy, storage conversion, stable-schema,
  allocation, macro-surface and Candid checks pass. The real maximum schema
  encodes to 8,417 bytes, the status page to 4,072 bytes and one mutation to
  101 bytes.
- One bounded managed-role PocketIC journey proves compiled seeding,
  independent controller and stable-Root administration, unrelated-caller
  denial, response-loss exact retry, conflict rejection, immediate removal,
  same-release restoration, re-addition without a rebuild and zero implicit
  0.105 application sessions.
- Targeted policy-purity, passive-DTO, lifecycle, stable-memory, changelog and
  current-document guards pass, as do formatting and diff checks.

- Locked `ic-query 0.40.1` and the inspected upstream source cannot retain the
  accepted failed-load cache/version context or represent unknown
  retryability. B5 remains blocked without a fork, error-string parser or
  guessed retry classification.
- The read-only Toko checkout contains no Canic integration or
  CANIC-011/012/013 evidence. B7 records that exact downstream blocker instead
  of modifying Toko.
- Once the upstream typed API exists, B5 propagation and final B7

  human-requested 0.107 closeout audit before 0.108 production work begins.
