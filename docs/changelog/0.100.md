# Canic 0.100 Changelog

## [0.100.9] - 2026-07-27 - Multi-Level Component Trees

### ⚠️ Breaking

- Replaces Component Spec and Component Topology schema/domain version 2 with
  version 3. There is no v1/v2 decoder or mixed topology path under the
  reinstall-only release boundary.
- Removes `initial_instances` and renames the Component aggregate
  `maximum_children` limit to `maximum_descendants`.
- Removes child-role `maximum_instances` and replaces implicit parent/child
  authority with explicit
  `[component_specs.<spec>.spawn_grants.<parent>.<child>]`
  `maximum_instances_per_parent` capabilities.
- Hard-cuts keyed placement from `binding`/`PlacementBinding*` to
  `index`/`PlacementIndex*`, including configuration, public APIs, DTOs,
  workflows, metrics and stable-state contracts. Protected identity
  `*Binding` types remain distinct.

### 🔧 Changed

- Treats each Component Spec child-role map as the flat catalog of every
  potential descendant role and Wasm in that Component tree, rather than a
  declaration of fixed direct-child edges.
- Compiles a bounded flat role-to-role spawn-capability graph. Each exact
  registered parent may create only a granted child role and only up to that
  grant's per-parent ceiling, while `maximum_descendants` bounds the whole
  dynamic tree.
- Allows role-graph recursion without encoding static parentage; every
  concrete child still points to a pre-existing parent and the root-owned
  Registry remains a finite acyclic tree.
- Allows any exact registered node to request an admitted direct child from
  its own Fleet Subnet Root; the root remains sole controller, Registry owner,
  funding authority and lifecycle executor at every depth.
- Adds the exact immediate parent to every protected child binding while
  retaining the owning top-level Component identity.
- Permits a top-level Component role to also appear in another Spec's
  potential-descendant catalog and derives each root's release-set/Store
  closure from the complete flat catalog.
- Aligns role attachment with that rule, so an existing Component role may be
  attached as a potential descendant of another existing Spec together with
  an explicit spawn grant from that Spec's Component role.
- Allows a potential-descendant role to own scaling, sharding or Placement
  Index pools, provided each pool target has an exact matching spawn grant and
  does not exceed its grant ceiling.
- Raises the default per-Component aggregate limit to 20,000 descendants and
  the default Component Registry allowance to 16 MiB.
- Specifies normalized indexed Component Registry storage, compact
  revision-bound paginated Directories, durable post-order subtree removal
  and per-Component concurrency so large trees do not require whole-tree
  snapshots or serialize unrelated Components.
- Reserves `Directory` for read-only discovery derived from Registry state and
  `Placement Index` for application-owned domain-key-to-instance placement.
- Extends the proposed 0.101 composition contract with reduction-only
  deployment-member limits, allowing separate deployments to reuse one group
  while safely narrowing aggregate or spawn-grant ceilings beneath the shared
  Component Spec envelope.
- Corrects the Toko topology so every project-data cell contains a Project Hub
  that creates local Project Instance children, which may create their own
  Ledger and Machine children.

### 🧪 Testing

- Freezes canonical v3 Component Spec, Component Topology, application-union,
  root release-set and Fleet Registry digests.
- Covers multi-level Project Hub, Project Instance and Ledger bindings,
  immediate-parent conflicts, spawn-grant completeness and ceilings,
  descendant-owned placement pools, flat role-catalog projection, Placement
  Index state and the absence of removed initial-child fields.

## [0.100.8] - 2026-07-27 - Canonical Fleet Registry Snapshots

### ➕ Added

- Adds passive Candid contracts for the complete Fleet Registry, immutable
  Component Spec entries, Fleet Subnet Root entries and lifecycle status,
  current-head manifests and compact Registry versions.
- Compiles epoch-one, revision-one genesis from the exact Component Topology
  with every immutable Fleet Component Spec and no root rows.

### 🔧 Changed

- Freezes a bounded, domain-separated Fleet Registry canonical encoding and
  derives its byte length, SHA-256 content identity and mirror/journal version
  from the exact complete snapshot.
- Validates the configured App and Coordinator authority, exact Component Spec
  set, canonical physical-Subnet root order, unique non-authority root
  principals, one common active release build, each root’s
  topology/admissions/limits and aggregate Fleet admission ceilings.
- Allows zero-root genesis and partial `Joining` admission while roots are
  registered incrementally, without permitting any admitted total to exceed
  its Component Spec’s immutable Fleet maximum.

### 🧪 Testing

- Freezes the canonical multi-root Registry digest and covers Candid
  round-trips, genesis App/epoch/revision, Spec drift, noncanonical roots,
  protected-authority drift, duplicate principals, Coordinator collisions,
  release-build drift, partial joining and aggregate admission excess.

## [0.100.7] - 2026-07-26 - Component Topology v2 and Root Structural Cycles Funding

### ⚠️ Breaking

- Replaces the intermediate Component Spec and Component Topology v1 canonical
  encodings with schema/domain version 2. There is no v1 decoder or mixed
  topology path under the reinstall-only release boundary.

### ➕ Added

- Adds explicit `initial_instances` policy to every direct Component Child;
  omission resolves to zero, required children cannot exceed their role or
  Component limit, and each admitted root must fit one Component’s complete
  required initial footprint.
- Adds bounded `[component_specs.<requester>.provisions.<target>]` declarations
  and a separate canonical `ComponentProvisioningGrant` collection with exact
  requester/target identity and positive per-requester/root ceilings.
- Rejects missing targets, self grants, grant cycles, excessive outbound
  grants, noncanonical compiled order and malformed initial cardinality before
  topology bytes or digests can become authority.

### 🔧 Changed

- Includes initial child cardinality in reusable Component Spec hashes and
  includes grants only in topology-level digests, so grant policy never
  changes either endpoint Spec’s content hash.
- Projects every grant incoming to a root-admitted target Spec while leaving
  the requester Spec unadmitted; release-set projection therefore retains the
  target’s complete child artifact closure without importing requester
  artifacts or capacity.

### 🩹 Fixed

- Resolves direct Fleet Subnet Root child funding policy from the unique
  topology role without requiring a current Component Spec on root
  infrastructure.
- Keeps Component Child funding lookup qualified by the parent Component Spec,
  preserving exact policy selection when child roles repeat across Specs.

### 🧪 Testing

- Corrects the root request-handler fixture to preserve the real
  no-Component-Spec invariant and covers structural cycles funding through
  focused core and PocketIC paths.
- Freezes v2 Spec, topology, application-union and root-manifest digests and
  covers default/required/optional child counts, invalid grant graphs,
  canonical Candid round trips, target-only incoming-grant projection and
  requester-artifact exclusion.

## [0.100.6] - 2026-07-26 - Immutable Multi-Root Fleet Install Plans

### ➕ Added

- Adds a canonical pre-creation Fleet install plan containing the exact Fleet
  and release-build identity, application-union digest, Coordinator
  subnet/funding, and every root’s subnet, admissions, topology digest,
  release set, limits and funding.
- Adds `FleetSubnetRootReleaseSet` as the protected release-build plus
  root-manifest digest identity shared by host planning and later Registry
  authority.
- Adds pre-creation topology planning that derives canonical Spec hashes and
  root-local topology digests without fabricating Coordinator or root
  principals.
- Persists the plan at
  `.canic/recovery/fleet-install-plans/<canonical-network-id>/<fleet-id>/<release-build-id>/plan.json`
  with exact per-Subnet manifests in its `root-release-sets/` directory.

### 🔧 Changed

- Projects and immutably publishes every planned root manifest from the
  finalized `.5` application union before publishing the plan itself under
  its Fleet, network and release-build path identity.
- Serializes exact cycle amounts as canonical decimal strings in durable JSON,
  avoiding precision loss while retaining typed `u128` values in memory.
- Makes exact retry and interrupted manifest-first publication recoverable,
  while rejecting conflicting plans/manifests, noncanonical documents,
  identity or topology drift, zero funding and symlinked authority files.
- Keeps root uniqueness Fleet-scoped: one Fleet cannot repeat a physical
  Subnet, while different Fleets can independently plan roots on that Subnet.

### 🧪 Testing

- Focused core and host tests cover pre-creation topology derivation, exact
  multi-root persistence and loading, partial retry, immutable conflict,
  cross-Fleet Subnet reuse, path identity and no-follow admission.

## [0.100.5] - 2026-07-26 - Durable Application Artifact Union

### ➕ Added

- Derives the exact application build targets from the validated complete
  install snapshot, including each topology role's resolved Cargo package and
  raw/gzip artifact paths.
- Immutably publishes canonical application-union bytes at
  `.canic/release-builds/<release-build-id>/application-artifact-union.json`
  and reloads them only under the same release-build and topology identity.
- Adds the persisted application-union path to successful manifest-phase
  evidence for normal current installs.

### 🔧 Changed

- Qualifies the exact current build outputs against the snapshot targets and
  persists the complete application union before release-build finalization;
  any union failure leaves the durable build planned.
- Shares strict project-root containment and regular no-follow artifact reads
  with infrastructure evidence, rejecting escaped, non-UTF-8 or symlinked
  artifact paths.
- Makes exact same-release publication idempotent, including recovery after
  finalization, while rejecting conflicting bytes, noncanonical documents,
  cross-build identities, topology drift and first publication after
  finalization.

### 🧪 Testing

- Focused host coverage proves durable canonical publication and loading,
  exact retry, finalized recovery, build/topology identity, unsafe artifact
  rejection and installer publication ordering.

## [0.100.4] - 2026-07-26 - Qualified Application Release Sets

### ➕ Added

- Adds pre-build target and qualified build-output contracts for every
  topology-admitted Component and Component Child role.
- Adds one canonical application artifact union bound to the exact
  `ReleaseBuildId` and Fleet-wide Component Topology digest, with resolved
  Cargo package, raw/gzip path, size and SHA-256 evidence per deduplicated
  role.
- Adds canonical Fleet Subnet Root release-set manifests that bind every
  projected entry to its exact Component Spec, structural Component/child
  use, root-local topology digest and qualified artifact.
- Adds the facade-exported, boundary-safe `ReleaseSetDigest` identity for the
  SHA-256 digest of one validated canonical root release-set manifest.

### 🔧 Changed

- Rejects incomplete, duplicate or orphan target/output role sets,
  target/output package or path disagreement, cross-build evidence,
  representation mismatch and cross-topology projection before a root
  manifest can be accepted.
- Preserves a shared child artifact under every exact Component Spec edge
  while accounting for byte-identical Store payloads only once; byte
  deduplication does not erase or broaden authorization.
- Requires topology-aware validation before canonical application-union bytes
  or digests can be produced, preventing a structurally valid but incomplete
  deserialized union from self-authorizing.

### 🧪 Testing

- Focused host tests freeze canonical union and root-manifest digests and
  cover qualification, topology completeness, split root admissions,
  shared-child edges, content-addressed Store limits and tamper rejection.

## [0.100.2] - 2026-07-26 - Infrastructure Artifact Manifest

### ➕ Added

- Adds the exact `CanicInfrastructureRole` set for the Fleet Coordinator,
  Fleet Subnet Root and Wasm Store.
- Adds a separate canonical `CanicInfrastructureArtifactManifest` that binds
  exactly one entry per infrastructure role to one `ReleaseBuildId`, Cargo
  package, raw/gzip path, byte length and SHA-256 digest.

### 🔧 Changed

- Derives artifact lengths and hashes from matching raw and gzip Wasm bytes
  rather than accepting digest authority from a caller.
- Canonicalizes infrastructure role order and rejects missing, duplicate,
  cross-build, unsafe-path, invalid-package, corrupt, representation-mismatched
  or noncanonical manifest input before installation wiring can consume it.
- Keeps infrastructure entries structurally separate from Component and
  Component Child release-set entries.

### 📚 Documentation

- Proposes bounded Fleet-scoped Coordinator Workers outside Component topology
  for partitioning high-cardinality operational work while the Coordinator
  remains the sole Fleet policy and assignment authority.
- Uses push-first root cycles coordination as the motivating example but
  deliberately leaves Worker terminology, kinds, identity, artifact carriage,
  placement, funding, replacement and recovery unfrozen. No Worker
  implementation is approved or included in 0.100 or 0.101.

### 🧪 Testing

  set, build binding, artifact representations, paths, packages, sizes and

## [0.100.1] - 2026-07-25 - Component Topology and Fleet Subnet Root Contracts

### ⚠️ Breaking

- Hard-cuts staged `[tree_specs.*]`/`[tree_groups.*]`, `TreeSpecId`,
  `TreeGroupId` and `TreeId` from maintained source, generated bootstrap,
  public exports, host/CLI projections, scaffolding, fixtures and active
  guidance. No alias, decoder or retained Tree identity remains.
- Replaces `canic app role attach --tree-spec` with exact
  `--component-spec <component-spec>` selection; the removed flag has no
  compatibility alias.
- Keeps the current Component Spec environment selector explicitly
  transitional. It is not a protected binding and is removed once root-local
  allocation supplies the concrete Component identity.

### ➕ Added

- Defines `ComponentSpecId` for one non-recursive Component blueprint and
  canonical 32-byte `ComponentInstanceId` for one concrete Component. Durable
  root allocation remains in the Component lifecycle slice.
- Applies the existing 4,096 Fleet declaration ceiling to concrete Component
  instances rather than empty Tree allocations.
- Defines immutable root-local `ComponentSpecAdmission` ceilings whose sum
  cannot exceed each Spec's Fleet-wide maximum.
- Defines root-owned Component Registry and Component Directory partitions
  keyed by concrete Component identity.
- Adds the bounded canonical Component Topology compiler, frozen
  domain-separated per-Spec hashes and root-local topology digests.
- Adds strong physical `SubnetId`, immutable Coordinator/root authority,
  positive Component admissions, root limits and protected Component/child
  binding contracts.
- Defines one exact Canic Infrastructure Artifact Manifest for the
  Coordinator, Fleet Subnet Root and Wasm Store, kept separate from
  application release sets.

### 🔧 Changed

- Source config now declares exactly one Component role and zero or more
  direct children per `[component_specs.*]`; root and the implicit Wasm Store
  sit outside Specs. Positive Component/child ceilings, singleton exactness,
  same-Spec pool targets and the 4,096 Fleet Component ceiling fail closed.
- Bootstrap, control-plane and host projections consume all flat Component
  Specs. Root startup unions Component and direct-child bootstrap/release-role
  inputs without a sole-Spec restriction; maintained root bootstrap consumes
  the compiled topology rather than raw Spec configuration.
- Component Specs compile finite aggregate child, Registry-byte and
  cycles-funding limits. The host topology planner derives canonical
  admission hashes and root-local digests, enforces complete Fleet coverage
  and one root per Fleet/Subnet pair, and never accepts caller-provided hash
  authority.
- `canic app role attach` creates the Component when its selected Spec does
  not exist and otherwise adds a direct child. Reusing one globally declared
  child artifact across several Specs is supported, while role-only lookup
  fails on ambiguity rather than choosing an owner.
- Scaffolding, checked-in configs, package/ICP fixtures, active configuration
  guidance and topology-sensitive repository tests use the flat Component
  shape.
- Component identity is allocated only when a Fleet Subnet Root creates a
  concrete Component; installation creates no empty logical workload
  partitions.
- Root bootstrap now resolves the root and implicit Wasm Store outside
  Component Specs, binds each direct Component payload to its unique admitted
  Spec and projects the root-local Subnet Directory across all admitted
  Specs. Managed fixture Wasms compile against that same canonical Fleet
  topology instead of package-local Spec namespaces.
- Revises the proposed 0.101 service contract so a Fleet service Spec may be
  admitted on several roots. One exact planned occurrence is the Authority;
  additional same-Spec occurrences may be cross-Subnet Replicas.
- Replaces the proposed singleton-Spec/sole-admission placement inference with
  an exact protected Authority group occurrence and root placement.

### 📚 Documentation

- Freezes exactly one Fleet Subnet Root per occupied
  `(FleetKey, SubnetId)`. Different Fleets may each own an independent root on
  the same physical Subnet.
- Makes one Component Spec declare one direct Component role and its direct
  children. `root`, `service` and `component` kinds, `owner_component`,
  recursive Specs and nested Components are excluded.
- Separates immutable Component Topology, root-local admissions, active
  release set and observed Wasm Store Catalog. One qualified artifact union is
  built per `ReleaseBuildId`, then exact root release-set manifests are
  projected.
- Makes installation ownership explicit: the host directly installs the
  Coordinator and roots from qualified infrastructure entries, while each
  root alone bootstraps its exact verified local Wasm Store.
- Defers Coordinator-created operational helper Canisters and distributed
  cycles management to the proposed 0.104 design.
- Makes Fleet Subnet Roots the required lifecycle controllers, gives each
  Component instance independent Registry and Directory authority, and
  distributes Directories directly from roots.
- Adds proposed bounded `ComponentGroupSpec` deployment composition in 0.101.
  Groups may include groups in configuration but flatten completely to direct
  root-owned Components before planning, with no Group Canister, runtime
  parent or delegated lifecycle authority.
- Makes flattening occurrence-preserving: inclusion does not execute a
  separate deployment or deduplicate equal Specs, while an independently
  deployed included group creates additional Components. The protected
  configuration digest covers groups, flattened deployments and service
  targets.
- Separates typed Ordinary, Fleet-service Authority and Fleet-service Replica
  purpose from inert free-form labels. One service-bearing Component Group can
  be reused with an Authority assignment at one deployment and a Replica
  assignment where another group includes it. Fleet Registry and Fleet
  Directory publish one exact Authority plus configured Replica bindings;
  Replica presence does not assert application-data readiness. A
  service-sensitive direct child resolves the same fence through its exact
  owning Component without becoming a group member or service endpoint.
- Adds proposed explicit monotonic group scale-out across exact additional
  already-installed roots within immutable admissions. It does not add
  scale-in, admission expansion, Replica promotion or database
  synchronization. Configured placement maxima such as Toko's ten are
  installation-specific rather than protocol constants; grouped Components
  and roots cannot bypass the absence of scale-in through ordinary removal.
- Freezes Directory confirmation for fresh install and scale-out separately:
  every initial root confirms fresh publication, while new placement roots
  and affected Authority roots confirm Replica additions before activation.
- Aligns 0.103 route evidence with selection of an exact published Authority
  or Replica endpoint while leaving the application-data protocol for a later
  design.
- Further generalizes 0.101 without adding runtime depth:
  `ComponentGroupPlacementId` identifies each concrete copy, several copies of
  one deployment may share a root, and protected density, minimum-spread and
  aggregate root limits bound packing and distribution. Placement identity is
  never a Tree, Canister, parent or lifecycle authority.
- Separates bounded `FleetServiceId` from Component role and adds explicit
  `AuthorityReplica` and `ActivePool` modes. The former retains one
  same-Spec Authority plus Replicas; the latter publishes a same-Spec
  configured endpoint pool without claiming leadership, health, load
  balancing, readiness or consistency. Service-wide member density/spread
  makes anti-affinity or intentional co-location explicit instead of deriving
  placement from purpose. Typed member purpose may be assigned at the
  deployment, inclusion or leaf edge, allowing both reusable uniform groups
  and mixed-purpose cells without wrapper groups.
- Records the generic scaling composition rule: co-scaled Components share a
  deployment, independently scaled tiers use separate deployments, and
  dynamic high-cardinality local shards remain direct Component Children.
  Scale-out now reserves stable placement IDs and exact placement-to-root
  assignments, which may repeat roots within policy.

### 🧪 Testing

- Focused Component schema/identity tests cover structural depth, ceilings,
  aggregate limits, pool targets, repeated child artifacts and ambiguous
  role-only lookup.
- Golden canonical-topology tests cover deterministic Spec/topology hashes,
  bounded encoding, exact admission projection, Fleet-wide sums, protected
  binding validation and Candid round trips.
- Host topology-planner tests cover derived hashes/digests, canonical
  admissions, App/Fleet binding, duplicate root/Subnet rejection and
  independent same-Subnet use by different Fleets.
- Focused host, install-root, CLI app/scaffold/build/deploy/medic/status and
  public configuration/reference tests cover multi-Spec projection, mutation,
  artifact selection and active examples.
- The prepared-root PocketIC upgrade baseline covers complete root-managed
  Wasm Store and multi-Spec Component bootstrap before Fleet activation.

## [0.100.0] - 2026-07-25 - Tree Identity Contracts

### ⚠️ Breaking

- Begins the reinstall-only 0.100 implementation line. No 0.99 installation,
  stable state, topology identity or compatibility decoder is an input to a
  0.100 Fleet.

### ➕ Added

- Added distinct `TreeSpecId` and `TreeGroupId` types for App-declared Tree
  topology and independent scaling groups. Both reject empty, noncanonical or
  over-40-byte names at Serde and Candid boundaries.
- Added generated 32-byte `TreeId` for one concrete Fleet-scoped Canister
  Tree. Its text, Serde and Candid representations are exact 64-character
  lowercase hexadecimal.
- Re-exported the three Tree identity types through the public Canic facade.

### 📚 Documentation

- Opened the 0.100 implementation tracker against immutable `v0.99.34` and
  recorded the staged hard-cut boundary: these foundational contracts do not
  make the remaining 0.99 Subnet Slot or Fleet Root runtime releasable as
  0.100.

### 🧪 Testing

- Focused core tests cover declared-name bounds, invalid Serde input, Candid
  round trips and canonical concrete Tree identity encoding.
