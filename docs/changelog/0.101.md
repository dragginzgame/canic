# Canic 0.101 Changelog

## [0.101.52] - 2026-08-12 - Toko Qualification And Semantic Cleanup

### 🔧 Changed

- Current installation and operator guides now describe terminal
  Coordinator/Registry/Directory/Component activation without embedding a
  stale release-specific implementation stop. Removed CLI and Project-identity
  examples are replaced with the maintained App, Fleet, and workspace surface.
- The session handoff is compact again, with its historical narrative archived
  and the active Q5 decision, remaining work, and focused evidence kept in one
  current page.
- Architecture guidance now shows workflow calling pure policy and stateful ops
  as independent branches, and release version ownership has one authoritative
  human-owned rule.
- Recovery and release-validation guidance now distinguishes same-release
  retry from reinstall-only cross-release transitions, single-root local install
  evidence from multi-root PocketIC qualification, and dated release verdicts
  from evergreen checklists.
- A current-document semantics guard derives the workspace version, keeps the
  handoff compact, and rejects superseded installation, CLI, identity,
  layering, and version-authority claims. Recovery and release-validation
  guards reject stale no-blocker and gate-classification claims. The release-
  integrity guard protects required outcomes
  without freezing job counts, step adjacency, exact validation order, or exact
  primitive Make recipes, and the checks workflow drops an unreachable tag
  condition.

### 🩹 Fixed

- Exact Coordinator replay after the first Component runtime-activation
  response now recognizes only that recorded first-progress cursor. Arbitrary
  current-cursor mismatches still conflict.
- The Toko qualification now owns a dedicated root configuration and Wasm
  build fixture. Its larger initial topology no longer changes the canonical
  placement, role or release-set contract used by existing grouped,
  cross-root and restart journeys.

### 🧪 Testing

- Current-document, release-validation, package/install, recovery-runbook,
  layering, and release-integrity guards pass with the maintained claims; the
  documentation guards now reject the superseded wording they replaced.
- `actionlint`, targeted ShellCheck, documentation-example `rustfmt --check`,
  changelog governance, reference-surface tests, and `git diff --check` pass.
- A three-application-Subnet PocketIC Fleet provisions database A/B/C
  Authorities on one root and same-Spec Replicas plus Project Hub PoolMembers
  on two application roots. Reused Project Hub deployments retain distinct
  protected 10,000- and 2,000-child policies.
- Packed and spread ActivePool placements survive two scale-outs with the
  Coordinator restarted after every durable advance. Three Project Instances,
  three Ledgers and one optional Machine retain exact parentage and remain on
  their owning root's Subnet.
- A second Fleet keeps its own Coordinator, root, Store, pool and Registry
  while sharing one physical Subnet. The qualification report freezes the
  executed topology, canonical plan/Registry/Directory sizes and representative
  Wasm footprints without claiming live-mainnet or application-replication
  behavior.

## [0.101.49] - 2026-08-11 - Scale-Out Recovery and ActivePool Qualification

### 🩹 Fixed

- Coordinator provisioning status and advance commands now carry the current
  scale-out synchronization cursor independently from the selected-root
  publication cursor. Exact retry after either durable response commit returns
  the committed status; a skipped or substituted root/count still conflicts.
- Root Directory synchronization accepts an intent timestamp equal to the
  operation's planned timestamp. IC time is constant within one update, so
  requiring a strictly later value incorrectly rejected a valid first step.
- The two-root Fleet fixture now builds every required Wasm before starting
  PocketIC, avoiding an idle server while independent Cargo builds run.

### 🧪 Testing

- A complete durable Coordinator journey publishes two initial same-Spec
  PoolMembers on distinct roots, then adds ordinal 2 to the first root. The
  resulting three-member ActivePool spans both roots while retaining two
  stable placements on the selected root.
- Scale-out synchronizes both affected roots in canonical order, publishes the
  selected root's Directory, advances the Fleet Registry exactly one revision,
  activates the new runtime and commits the placement ledger. Restarted exact
  status replay returns the original terminal result without another mutation.
- The nearest invalid continuation is also qualified: attempting to place a
  third member on the already-full root violates the frozen deployment and
  service density boundary and leaves durable Coordinator state unchanged.
- Scale-out recovery now reloads durable Coordinator state while the affected-
  root synchronization, selected-root publication and runtime-activation
  intents are each in flight. Every restart returns the exact typed reconcile
  call without rewriting intent or skipping the response commit.
- Fleet Registry and Fleet Directory service DTOs now state and exhaustively
  test their topology-only contract. ActivePool membership carries no runtime
  health, readiness, consistency or load-balancer eligibility claim.
- A real two-application-Subnet PocketIC journey scales `grouped_projects`
  from one Project Hub to two, restarts the Coordinator after every durable
  advance and replays the same command without duplicate placement or
  membership. The new Hub creates a Project Instance, which creates its
  Ledger; all three Canisters are observed on the selected root's Subnet and
  both Hubs discover the exact two-member service.
