# Canic 0.101 Design: Fleet-Authoritative Service Provisioning and Publication

Date: 2026-07-25

## Status

- Status: proposed.
- Release boundary: reinstall only.
- Dependency: the
  [0.100 Fleet Coordinator design](../0.100-multi-subnet-fleet-coordinator-and-registry-synchronization/0.100-design.md)
  defines the Tree, Fleet Registry and Tree Registry architecture used here.
- Scope: fresh provisioning of declared singleton Fleet services inside
  ordinary Trees, followed by atomic Fleet publication.
- Compatibility posture: none. A 0.101 Fleet starts from empty 0.101 state.

0.101 does not inspect or preserve a 0.100 installation. It has no candidate
discovery, service adoption, ownership transfer, cross-release plan, prior
service inventory or mixed-version mode. Existing Fleets are reinstalled.

## Thesis

A fresh 0.101 installation creates the Coordinator and Trees described by
0.100, then provisions each declared Fleet-authoritative service through the
selected Tree Root. Only after every service is durably ready does the
Coordinator publish the complete service set in one Fleet Registry revision.

For each `[services.fleet.targets]` role:

1. resolve its singleton Tree Group;
2. resolve the one active Tree in that group;
3. prove the exact Tree Spec permits the role;
4. ask that Tree Root to provision the service through its ordinary local
   lifecycle;
5. verify the exact Tree Registry result; and
6. include the resulting `(role, TreeId, canister_id)` in the one complete
   Fleet publication.

The Coordinator owns Fleet-wide publication. The Tree Root owns local service
lifecycle. The service Canister owns application data.

## Release Boundary

| Release | Fresh-install responsibility |
| --- | --- |
| 0.99 | App/Fleet identity and one-Tree activation |
| 0.100 | Coordinator, Tree topology and Fleet Registry synchronization |
| 0.101 | Same topology plus service provisioning and atomic publication |
| Later | Replication, relocation, replacement, failover and data movement |

The table describes architectural dependency, not an in-place release path.
Installing 0.101 creates all required 0.101 state directly.

### Fresh Installation Barrier

Fresh 0.101 installation executes the 0.100 Coordinator, Fleet Registry and
Tree join protocols but extends their final runtime-activation barrier:

1. install the Coordinator and every required initial Tree Root;
2. commit and synchronize the all-active Tree topology while the roots remain
   runtime `Prepared`;
3. resolve and persist the complete service provisioning plan;
4. provision every service Canister behind its runtime `Prepared` fence and
   commit the complete Tree-local evidence;
5. publish the complete Fleet service binding set once;
6. synchronize that exact Fleet Registry Mirror and Fleet Directory to every
   required initial Tree Root, derive each selected Tree's exact Tree
   Directory from its Tree Registry and cascade both Directories to every
   provisioned service;
7. activate the provisioned service Canisters and then their Tree Roots;
8. verify exact runtime `Active`, Fleet Registry Mirror and Fleet Directory
   evidence; and
9. publish the Fleet catalog row only after that complete installation
   evidence, then record terminal host authority after the catalog is durable.

The 0.101 Tree Root Prepared fence additionally admits only the exact
Coordinator-authenticated plan-acceptance, provisioning, status,
publication-confirmation and runtime-activation operations required by this
sequence. No ordinary application endpoint or timer starts early.

Fleet Registry publication may temporarily precede runtime activation during
recovery, but no ordinary managed consumer is active and no Fleet catalog row
exists in that state. Exact retry resumes activation; it never republishes a
different binding set.

## Terminology

### Fleet-authoritative service

One singleton role published as the Fleet's canonical service endpoint.
“Authoritative” describes Fleet-wide lookup, not Coordinator ownership of the
Canister.

### Service target

The protected mapping from one role to one singleton `TreeGroupId`.

### Service Tree

The ordinary active Tree selected by that target. Its Tree Root remains the
Tree Registry owner and lifecycle authority.

### Provisioning

Fresh creation and installation through the selected Tree Root's canonical
Tree-local lifecycle.

### Publication

One Fleet Registry revision containing the complete declared service set.
Publication does not transfer controllers or local ownership.

### Runtime activation

The exact Canister lifecycle transition from runtime `Prepared` to runtime
`Active`. “Activation” is reserved for that transition; the larger
Coordinator operation is service provisioning and publication.

## Goals

0.101 must:

1. provision only protected declared targets;
2. resolve the complete target plan before external mutation;
3. provision only through each selected Tree Root;
4. retain exact Tree and Tree Registry ownership;
5. reject any unexpected pre-existing service row or role conflict;
6. publish no partial service set;
7. bind every published role to exact `TreeId` and principal;
8. make interruption and exact retry deterministic;
9. return completed results without duplicate provisioning; and
10. keep ordinary Canisters out of Coordinator workflows.

## Non-Goals

0.101 does not implement:

- any prior-release transition;
- discovery or adoption of existing services;
- relocation, replacement or principal rotation;
- writable-primary replication, promotion or failover;
- application-data migration or synchronization;
- automatic Tree scaling or application routing;
- Coordinator relocation or replacement;
- controller transfer to the Coordinator;
- distributed transactions between Tree Roots; or
- compatibility aliases, readers or fallback behavior.

## Configuration

The App declares services in their Tree Spec and maps each Fleet role to one
Tree Group:

~~~toml
[tree_specs.primary_data]

[tree_specs.primary_data.canisters.root]
kind = "root"

[tree_specs.primary_data.canisters.users_db]
kind = "service"

[tree_specs.primary_data.canisters.projects_db]
kind = "service"

[tree_groups.primary_data]
tree_spec = "primary_data"
initial_trees = 1
maximum_trees = 1

[services.fleet.targets]
users_db = "primary_data"
projects_db = "primary_data"
~~~

The target declaration is:

- complete and non-empty when service publication is requested;
- sorted by raw role bytes;
- bound to the exact Fleet;
- bounded by count and encoded size;
- protected with the fresh Coordinator installation;
- immutable for that installation; and
- resolved only against the committed current Fleet Registry.

A target group must have exactly one active Tree and maximum size one. The
role must occur exactly once in that group's exact Tree Spec.

Configuration supplies declarations, not concrete service principals.

## Authority Map

| Concern | Sole owner |
| --- | --- |
| fresh installation progress | host installation journal |
| service target declaration | protected Coordinator installation state |
| Tree/group/spec truth | Fleet Registry |
| service provisioning/publication sub-operation | Coordinator service-provisioning journal |
| local service lifecycle | selected Tree Root |
| concrete Tree-local service row | selected Tree Root's Tree Registry |
| Fleet service binding | Coordinator Fleet Registry |
| consumer service projection | Fleet Directory derived from that Fleet Registry |

A source-config reread, host report, Tree mirror or service response cannot
replace these owners.

The host journal records the exact Coordinator operation identity and terminal
evidence but does not duplicate its plan or invent service bindings. The
Coordinator journal owns the service sub-operation; the host journal owns the
complete fresh-install sequence and final Fleet catalog publication.

## Fleet Registry and Fleet Directory Schema Hard Cut

0.101 directly installs the current service-aware Fleet Registry:

~~~rust
pub struct FleetRegistry {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub tree_groups: Vec<FleetTreeGroup>,
    pub trees: Vec<FleetTreeEntry>,
    pub services: Vec<FleetServiceBinding>,
}
~~~

The matching Fleet Directory adds the complete consumer-shaped service
projection. There is no reader for the 0.100 Fleet Registry or Fleet Directory
shape and no empty placeholder field in 0.100.

~~~rust
pub struct FleetDirectory {
    pub provenance: FleetDirectoryProvenance,
    pub groups: Vec<FleetDirectoryGroup>,
    pub services: Vec<FleetDirectoryService>,
    pub trees: Vec<FleetDirectoryTree>,
}

pub struct FleetDirectoryService {
    pub role: CanisterRole,
    pub tree: TreeId,
    pub canister_id: Principal,
}
~~~

`FleetDirectoryProvenance`, group projections and Tree projections retain
their exact 0.100 meanings. `services` is derived only from the complete
committed Fleet Registry service set. `TreeDirectoryProvenance` remains the
separate Tree Registry-derived contract and gains no Fleet service field.

The fresh genesis Fleet Registry starts with the service field empty while
Trees are installed. The service provisioning/publication protocol fills it
once with the complete declared set before the Fleet becomes terminally
installed.

## Provisioning Plan

Before provisioning, the Coordinator resolves a complete plan:

~~~rust
pub struct FleetServiceProvisioningPlan {
    pub fleet: FleetBinding,
    pub fleet_registry: FleetRegistryVersion,
    pub target_declaration_hash: [u8; 32],
    pub entries: Vec<FleetServicePlanEntry>,
}

pub struct FleetServicePlanEntry {
    pub role: CanisterRole,
    pub tree: TreeBinding,
}
~~~

Plan entries are sorted by role. The plan contains no optional candidate,
preserved principal or branch between provisioning modes.

Planning fails before mutation unless:

- every protected target appears exactly once;
- the Fleet Registry version is current and exact;
- every target group is singleton;
- every group has exactly one active Tree;
- every Tree uses the expected Spec hash;
- every role is permitted by that Spec;
- no target role already has a Tree Registry row;
- no service role is already Fleet-published; and
- all count and byte bounds hold.

The complete plan and its canonical hash are durable before the first
provisioning request.

## Tree-Local Provisioning Contract

The Coordinator sends each selected Tree Root one authenticated batch request
binding:

- Fleet;
- authority epoch;
- Fleet Registry version;
- provisioning operation ID;
- plan hash;
- the complete sorted roles assigned to that Tree;
- exact Tree Binding; and
- expected absence of every planned Tree Registry role row.

The Tree Root:

1. authenticates the exact Coordinator;
2. checks its protected Tree Binding and current Fleet Registry Mirror;
3. proves every role is permitted by its Tree Spec;
4. checks every planned role is absent from its Tree Registry;
5. durably records provisioning intent before creation;
6. creates and installs each service in deterministic role order through the
   existing Tree-local lifecycle, leaving it runtime `Prepared`;
7. reconciles every uncertain external outcome before retry;
8. commits the complete exact Tree Registry result;
9. stores one aggregate durable result receipt; and
10. returns that receipt idempotently.

The request does not grant the Coordinator direct management-canister access
to the service.

## Local Provisioning State

Each selected Tree Root stores one bounded aggregate state for the
provisioning and publication operation:

~~~rust
pub struct TreeProvisionedService {
    pub role: CanisterRole,
    pub canister_id: Principal,
}

pub enum TreeServiceProvisioningState {
    Accepted {
        operation_id: [u8; 32],
        plan_hash: [u8; 32],
        roles: Vec<CanisterRole>,
    },
    Provisioned {
        operation_id: [u8; 32],
        plan_hash: [u8; 32],
        services: Vec<TreeProvisionedService>,
        tree_registry_content_hash: [u8; 32],
    },
    Published {
        operation_id: [u8; 32],
        plan_hash: [u8; 32],
        services: Vec<TreeProvisionedService>,
        tree_registry_content_hash: [u8; 32],
        fleet_registry: FleetRegistryVersion,
        tree_directory_content_hash: [u8; 32],
        fleet_directory_content_hash: [u8; 32],
    },
    RuntimesActive {
        operation_id: [u8; 32],
        plan_hash: [u8; 32],
        services: Vec<TreeProvisionedService>,
        tree_registry_content_hash: [u8; 32],
        fleet_registry: FleetRegistryVersion,
        tree_directory_content_hash: [u8; 32],
        fleet_directory_content_hash: [u8; 32],
    },
}
~~~

Roles and services use canonical raw-role order. The final Tree Registry
content hash is measured after every planned role has been committed, so a
later role cannot make an earlier per-role receipt stale. Every state after
`Accepted` retains the operation and plan identity required for exact retry.

`Provisioned` does not make a service Fleet-authoritative. It records that the
complete Tree-local lifecycle is ready, with runtime endpoints still fenced,
and supplies evidence for the later atomic Fleet publication.

## Provisioning and Publication Protocol

### 1. Persist planned

The Coordinator stores the complete exact plan before calling any Tree Root.

### 2. Selected Tree Roots accept the plan

Each selected Tree Root durably accepts the exact operation and plan. A Tree
Root with mismatched active work or contradictory Tree-local state rejects.

### 3. Provision services

The Coordinator asks each selected Tree Root to provision its complete role
batch. Aggregate Tree Root results are projected to the planned roles without
losing the final Tree Registry identity. Exact retry resumes the existing
Tree Root operation and never chooses another Tree or principal.

### 4. Verify complete readiness

Before publication, the Coordinator verifies for every role:

- the expected Tree and Tree Root;
- one exact aggregate Tree Root receipt covering every role assigned to that
  Tree;
- exact Tree Registry identity;
- role and principal uniqueness;
- current active Tree status;
- unchanged target declaration; and
- unchanged plan/Fleet Registry relationship.

Any missing or contradictory evidence stops before Fleet Registry mutation.

### 5. Publish once

The Coordinator constructs the complete sorted service binding set and commits
one next Fleet Registry snapshot. It never appends roles one at a time.

~~~rust
pub struct FleetServiceBinding {
    pub role: CanisterRole,
    pub tree: TreeId,
    pub canister_id: Principal,
}
~~~

### 6. Confirm locally

After Fleet Registry publication, every required initial Tree Root
synchronizes the exact new Fleet Registry Mirror and Fleet Directory. Each
selected service Tree verifies its bindings, derives the exact Tree Directory
from its Tree Registry, cascades both Directories to every prepared service in
the operation and verifies matching service-side provenance before marking
the operation `Published`. That state records the exact Fleet Registry
version and both Directory content hashes. Confirmation may be retried; it
cannot change the committed set.

Publication is committed once its Fleet Registry snapshot is durable. The
overall service provisioning/publication operation becomes complete only
after required Fleet and Tree Directory confirmation and exact service runtime
activation. Delayed confirmation or activation remains observable recovery
work, not a reason to publish again.

### 7. Activate runtimes

After every required initial Tree Root confirms the exact published Fleet
Registry and Fleet Directory, and every selected Tree Root confirms its exact
Tree Directory, the Coordinator asks each selected Tree Root to activate the
complete prepared service batch for its exact operation, plan and Fleet
Registry version. The Tree Root activates services in canonical role order,
reconciles uncertain outcomes through the ordinary Tree-local lifecycle,
verifies exact runtime `Active` evidence and atomically records the aggregate
state as `RuntimesActive`.

Once the Coordinator records every selected Tree's exact service evidence and
completes the service provisioning/publication sub-operation, the host
installation journal
activates every initial Tree Root through the 0.100 runtime activation path.
The Coordinator never activates a Tree Root or becomes its local lifecycle
owner. Exact retry observes recorded service and Tree Root runtime state
before reissuing any activation.

## Fleet and Tree Directory Projections

The Fleet Directory projects the complete Fleet Registry service set with
exact:

- role;
- Tree identity;
- Canister principal;
- Fleet Registry authority;
- revision; and
- content hash.

Each Tree Directory remains the separate Tree Registry-derived local Canister
lookup defined by 0.100. Ordinary Canisters consume both projections through
the Tree-local cascade. They do not query the Coordinator during normal
service lookup.

A missing role, duplicate role, duplicate principal, inactive Tree, unknown
Tree, Fleet Registry/Fleet Directory mismatch or Tree Registry/Tree Directory
mismatch fails closed.

## Failure and Recovery

The Coordinator journal is monotonic:

~~~text
Planned
  → RootsAccepted
  → ServicesProvisioned
  → RegistryPublished
  → DirectoriesConfirmed
  → RuntimesActivated
  → Complete
~~~

For each external effect:

- durable intent precedes invocation;
- uncertain outcomes are observed before replay;
- exact result receipts are durable before journal advancement;
- retries retain the same operation, role, Tree and expected identity; and
- completed work returns its recorded result.

The operation may be cancelled only before any Tree Root accepts provisioning
intent. After the first accepted provisioning intent it is forward-only:
recovery finishes provisioning, publication, Tree Root confirmation and Fleet
and Tree Directory synchronization. It never deletes a provisioned service,
rewinds the Fleet Registry or constructs another service set.

Contradictory or unknowable non-idempotent outcomes halt with a typed recovery
disposition. Operators resume only by exact retry of
`canic install <app> <fleet>` and inspect recovery through maintained passive
status or `deploy inspect resume-report` surfaces. They may not edit journals,
synthesize receipts or mark work complete.

## Bounds and Encoding

The design uses explicit bounds for:

- target count;
- target declaration bytes;
- provisioning-plan bytes;
- roles per Tree;
- receipt bytes;
- journal bytes; and
- final service bindings.

Canonical arrays use the documented field order and sorted role order. Hashes
are domain-separated and length-prefixed. Hash metadata is not embedded
inside the bytes it hashes.

Overflow, duplicate keys, noncanonical ordering, unknown tags and oversized
input fail before mutation.

## Authorization

Only the protected Fleet Coordinator may ask a Tree Root to accept a
provisioning plan, provision services, confirm publication or activate the
planned runtimes. Every request binds exact Fleet, authority epoch, Fleet
Registry version, operation, plan, Tree and role.

Tree Roots do not accept:

- controller status as Coordinator identity;
- a caller from another Fleet;
- a stale or future epoch;
- an unrecorded Tree;
- a role absent from the Spec; or
- a second active operation with different identity.

Service Canisters gain no Fleet Registry mutation authority.

## Stable State and Backup

0.101 installs only the current state shape.

Backup and restore must preserve:

- host fresh-install journal and its exact Coordinator operation binding;
- Coordinator Fleet Registry and service-provisioning journal;
- protected target declaration;
- Tree Root-local provisioning intents and receipts;
- Tree Registry service rows;
- Tree Root publication confirmation state; and
- exact Fleet Registry snapshot/manifest evidence.

Restore validates cross-document identity before resuming. Candidate or
partial files cannot be interpreted as committed state. An ambiguous restored
Coordinator authority remains fenced under the 0.100 authority-epoch rule.

No 0.100 decoder, migration routine or cross-release restoration path exists.

## Role Boundary

| Owner | Responsibility |
| --- | --- |
| Host/CLI | compile protected targets and drive fresh installation |
| Coordinator | plan, orchestrate and atomically publish |
| Tree Root | provision locally and retain exact receipts |
| Service Canister | own application data and service behavior |
| Ordinary Canister | consume Fleet Directory service bindings and Tree Directory local bindings |

Coordinator code must not be linked into ordinary Canisters. Tree-local
creation code must not be duplicated in the Coordinator.

## Typed Failures

At minimum, typed failures distinguish:

- target declaration mismatch;
- unknown or nonsingleton group;
- missing or inactive Tree;
- Tree Spec mismatch;
- role not permitted;
- unexpected existing local role;
- duplicate role or principal;
- stale Fleet Registry version;
- Coordinator or authority mismatch;
- competing operation;
- provisioning outcome unknown;
- local receipt mismatch;
- incomplete ready set;
- Fleet Registry publication conflict;
- Fleet or Tree Directory confirmation pending; and
- corrupt or oversized durable state.

Recovery logic must not depend on display strings.

## Implementation Slices

### Slice 1 — Contracts and planning

- freeze target, plan, binding and error shapes;
- compile protected targets during fresh install; and
- reject any existing-service branch.

### Slice 2 — Tree Root provisioning

- accept exact provisioning operations;
- use the canonical local creation lifecycle;
- keep new service runtimes `Prepared`;
- reconcile interruption and retain one aggregate receipt per Tree; and
- expose exact idempotent results.

### Slice 3 — Coordinator orchestration

- resolve complete plans;
- drive every selected Tree Root;
- verify complete readiness; and
- retain monotonic recovery state.

### Slice 4 — Atomic publication

- commit the complete service set once;
- synchronize every required Fleet Registry Mirror and Fleet Directory,
  cascade to every prepared service and confirm selected Tree publication;
- activate prepared services and Tree Roots; and
- publish the terminal Fleet catalog only after complete evidence.

### Slice 5 — Operational qualification

- exercise crash points and retry;
- prove backup/restore consistency;
- prove role-package boundaries; and
- remove stale adoption or transition language.

## Required Validation

Tests must prove:

- fresh install provisions every declared service;
- no prior installation or service candidate is read;
- target resolution is deterministic and complete;
- wrong group, Tree, Spec, role, Fleet or epoch rejects before mutation;
- unexpected existing local roles reject rather than being reused;
- a Tree Root, not the Coordinator, creates the service;
- creation/install uncertainty reconciles before replay;
- completed local provisioning is idempotent;
- several planned roles in one Tree produce one aggregate receipt with the
  final Tree Registry content hash;
- partial readiness publishes nothing;
- duplicate role/principal evidence rejects;
- the complete set appears in one Fleet Registry revision;
- provisioned services remain runtime `Prepared` before Fleet publication;
- Tree Root confirmation, service Fleet and Tree Directory cascade and
  runtime activation resume after interruption without republishing;
- no Fleet catalog row appears before every required service and Tree Root has
  exact runtime `Active`, Fleet Registry Mirror, Fleet Directory and Tree
  Directory evidence;
- completed Coordinator operations perform no duplicate work;
- backup/restore preserves one consistent authority;
- corrupt, incomplete, stale and mismatched state fails closed; and
- ordinary Canister Wasms contain no orchestration authority.

A realistic disposable-environment journey must install a Coordinator, at
least one service Tree and multiple services, mutate service data, restart
recovery at a high-risk effect/receipt boundary and prove the final Fleet and
Tree Directories resolve the restored service principals and Tree-local
Canister identities.

## Completion Criteria

0.101 is complete when:

1. every declared service is freshly provisioned in its exact selected Tree;
2. every local service has one Tree Root lifecycle owner;
3. one Coordinator journal owns the service provisioning/publication
   sub-operation;
4. the Fleet Registry publishes the complete set atomically;
5. Fleet Directory consumers observe exactly that committed service set while
   Tree Directory consumers retain the distinct Tree-local projection;
6. every selected Tree retains one aggregate operation/plan-bound receipt and
   final Tree Registry content hash;
7. the Fleet catalog is published only after required runtime activation and
   Fleet/Tree Directory confirmation;
8. interruption and exact retry cannot duplicate or skip provisioning;
9. no existing-service discovery, adoption, ownership transfer or
   cross-release path remains; and
10. code, tests, schemas, examples and documentation describe only this model.

## Expected Follow-On

Replication, relocation, replacement, promotion, failover and application-data
movement require separate designs. They must not reinterpret this release's
singleton binding or add a second service authority.
