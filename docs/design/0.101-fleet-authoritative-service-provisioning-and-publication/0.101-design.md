# Canic 0.101 Design: Composable Component Deployment and Fleet Service Publication

Date: 2026-07-27

## Status

- Status: proposed.
- Release boundary: reinstall only.
- Dependency: the
  [0.100 Fleet Subnet Root design](../0.100-multi-subnet-fleet-coordinator-and-registry-synchronization/0.100-design.md)
  defines the Coordinator, roots, qualified infrastructure manifest, flat
  Component Specs, root-local Component identity, topology-admitted Wasm
  Stores, multi-level dynamic Component trees, Component Provisioning Grants,
  Fleet Registry and Component Registries used here.
- Scope: compile-time Component Group composition, typed Component deployment
  purpose, repeatable root-local placements, bounded spread/density policy,
  reduction-only deployment-member limits, fresh provisioning, mode-aware
  Fleet service publication and explicit same-release group scale-out within
  installed admissions.
- Compatibility posture: none. A 0.101 Fleet starts from empty current state.

0.101 does not inspect or preserve a 0.100 installation. It has no candidate
discovery, service adoption, ownership transfer, cross-release plan, prior
service inventory or mixed-version mode. Existing Fleets are reinstalled.

## Thesis

One `ComponentSpec` is the reusable blueprint for one top-level Component role
and the flat catalog of potential descendant roles and Wasms in its dynamic
tree. The same Spec may be admitted to several Fleet Subnet Roots and
materialized as several independent Component instances. Each root stores the
same exact qualified artifact closure for that Spec, while each concrete
instance receives its own `ComponentInstanceId`, principal, state and root
binding.

Deployment purpose and Fleet service membership belong to the concrete
planned occurrence, not to the Component Spec:

- one occurrence may be an `Authority` member of an Authority/Replica service;
- other occurrences of the same Spec may be `Replica` members of that service
  and must remain write-fenced by that Component package;
- several occurrences may be `PoolMember`s in a stateless or
  application-coordinated `ActivePool` service; and
- an unrelated occurrence is `Ordinary`.

“Authority” and “Replica” are the maintained terms for the single-writer
profile. They correspond to the traditional master/slave deployment shape
without encoding that terminology in schemas or configuration. `PoolMember`
has different semantics: Canic publishes several configured endpoints but
grants none of them implicit consistency, readiness or single-writer
authority.

Reusable `ComponentGroupSpec` declarations compose Component occurrences and
may include other Component Groups. Group inclusion is configuration-only.
The compiler rejects cycles and flattens every selected group to direct
Component occurrences before any deployment plan or runtime state is created.

The Component Spec remains the immutable upper envelope for every occurrence.
Two deployments may reference the same group while applying different
reduction-only limits to the same flattened member path. This permits, for
example, one Project Hub deployment with a 10,000-instance
`project_hub -> project_instance` grant and another with a 2,000-instance
effective grant without duplicating the group, Spec, role or Wasm. The
protected plan may assign those deployments to roots on different physical
Subnets.

~~~text
Configuration composition

project_data_cell
  +-- databases Component Group [Replica assignment]
          +-- database_a Component Spec [Replica of database_a]
          +-- database_b Component Spec [Replica of database_b]
          +-- database_c Component Spec [Replica of database_c]
  +-- project_hub Component Spec [PoolMember of project_hubs]

Compiled runtime placement

Fleet Subnet Root @ Project-workload Subnet
  +-- database_a Component [Replica of database_a]
  +-- database_b Component [Replica of database_b]
  +-- database_c Component [Replica of database_c]
  +-- project_hub Component [PoolMember of project_hubs]
          +-- project_instance Component Child [created later]
                  +-- project_ledger Component Child [created later]
                  +-- project_machine Component Child [optional]
~~~

There is no Group Canister, Group controller, nested Component declaration,
group-local Wasm Store or delegated lifecycle manager. Every group member
materializes as a top-level Component directly below the Fleet Subnet Root on
its physical Subnet. Below it, registered descendants may create children to
any depth through that same root. The root owns all platform effects; each
node owns only its own direct-child relationship.

A Toko-style Fleet can therefore have:

~~~text
Authoritative database Subnet
  Fleet Subnet Root
    +-- database_a [Authority]
    +-- database_b [Authority]
    +-- database_c [Authority]

Project Subnet 1
  Fleet Subnet Root
    +-- database_a [Replica]
    +-- database_b [Replica]
    +-- database_c [Replica]
    +-- project_hub [PoolMember]
          +-- project_instance
          |     +-- project_ledger
          +-- project_instance
                +-- project_ledger
                +-- project_machine

...

Project Subnet 10
  Fleet Subnet Root
    +-- database_a [Replica]
    +-- database_b [Replica]
    +-- database_c [Replica]
    +-- project_hub [PoolMember]
          +-- many dynamic project_instance child trees
~~~

Each project-data placement is one flattened database-plus-Project-Hub batch
on one root. The deployment may scale monotonically from its initial placement
count to its configured maximum as exact additional placements are assigned to
roots. Each local Project Hub asks its own Fleet Subnet Root to create
Project Instances as its direct children. A Project Instance may then ask that
same root to create its Ledger and optional Machine as direct children. Canic
does not predeclare those concrete edges or automatically create them.

Toko chooses one project-data placement per root. That is policy, not a topology
restriction: another deployment may place several distinct copies of the same
flattened group on one root, within its per-root density cap and the root's
aggregate group-placement limit. Each copy receives a durable placement
identity but creates no Group Canister or runtime parent.

The Coordinator owns composition planning, group-placement orchestration and
Fleet-wide service publication. Each Fleet Subnet Root owns Component identity
allocation, platform effects, exact artifact selection, Component Registry
commitment and root-local group receipts. It never becomes an application-data
proxy. A Project Hub child request does not route through the Coordinator; its
protected binding records the Hub as the Project Instance's immediate parent,
while the root remains the sole lifecycle authority.

## Runtime Topology Boundary

Every Component Group member provisioned by 0.101 remains a top-level
Component directly below one Fleet Subnet Root. Its descendants form a
dynamic root-owned tree:

~~~text
Fleet Subnet Root -> Component -> child -> child -> ...
~~~

A Component Group is not part of that topology. A group may include another
group only in checked-in configuration. Compilation produces bounded leaf
paths and then a flat canonical list of direct Component plan entries. It
preserves every distinct leaf occurrence; flattening is not global
Component-Spec deduplication.

No protected binding, Component Registry row or Component Directory can
encode:

- a Component parented by another Component;
- a Component Group as a runtime parent;
- a Component Group Canister or controller;
- a Component Child as a group member;
- a nested child-role declaration; or
- lifecycle authority delegated below the Fleet Subnet Root.

Protected child bindings do encode each concrete immediate parent. A child may
itself request another admitted child, so runtime depth is bounded by aggregate
root/Component-tree limits rather than a fixed level count.

Group membership is orchestration and discovery metadata. It grants no
controller, child-management, service-authority or application-data authority.

### Fresh Installation Barrier

Fresh 0.101 installation executes the 0.100 Coordinator/root join protocol but
extends its final runtime-activation barrier:

1. compile the complete Component Topology and bounded Component Group graph;
2. flatten every initial group placement, resolve reduction-only member
   limits and validate all Authority, Replica, PoolMember, capacity, density
   and spread invariants;
3. build the exact Canic Infrastructure Artifact Manifest and separate
   qualified Component/Component-Child artifact union once, then project every
   root's exact release-set manifest;
4. host-install the Coordinator and every required initial Fleet Subnet Root
   from the exact infrastructure entries, with each root alone bootstrapping
   its local Wasm Store;
5. commit and synchronize the all-active root topology while roots remain
   runtime `Prepared`;
6. resolve and persist the complete initial Component provisioning plan,
   grouped first by root and then by group placement;
7. provision every planned top-level Component behind its runtime `Prepared`
   fence and commit every Component Registry partition;
8. derive the exact mode and complete configured member set for every declared
   Fleet service;
9. publish that complete Fleet service set in one Fleet Registry revision;
10. synchronize the exact Fleet Registry Mirror and Fleet Directory, derive
    every affected Component and Component Group Directory, and send the
    required projections directly to every provisioned Component;
11. activate every provisioned Component runtime only under its exact
    prepared Directory authority;
12. promote every corresponding Component Registry partition to `Active`,
    derive and synchronize its new revision-bound Component Directory and
    independently verify target convergence;
13. activate the Fleet Subnet Roots and verify exact runtime, Wasm Store,
    Fleet Registry Mirror, Component Registry and Directory evidence; and
14. publish the Fleet catalog row only after that complete evidence, then
    record terminal host authority after the catalog is durable.

The 0.101 Fleet Subnet Root `Prepared` fence additionally admits only the exact
Coordinator-authenticated plan acceptance, provisioning, status, publication
confirmation and runtime-activation operations required by this sequence. No
ordinary application endpoint or timer starts early.

Fleet Registry publication may temporarily precede runtime activation during
recovery, but no ordinary managed consumer is active and no Fleet catalog row
exists in that state. Exact retry resumes activation; it never substitutes a
different Component, root, group placement, member occurrence or service
membership.

## Terminology

### Component Spec

The flat 0.100 blueprint for one top-level Component role, every potential
descendant role and qualified Wasm in its dynamic Component tree, plus
Fleet-wide and per-tree ceilings. The declaration does not encode concrete
runtime parentage. Purpose and physical placement are not properties of a
Component Spec.

### Component Group Spec

A bounded reusable deployment-composition declaration. Its members are direct
Component Spec occurrences or references to other Component Group Specs. It is
fully flattened before planning and has no runtime authority.

The maintained name is Component Group, not Canister Group, because each leaf
materializes a top-level Component whose flat Spec catalog may admit dynamic
descendants at multiple levels. The group plan still names only that top-level
Component; descendants are never flattened group members.

`ComponentGroupSpecId` identifies the checked-in declaration. It is not a
replacement for `TreeGroupId`: it identifies no workload partition, root,
Canister, Registry or concrete group instance.

### Component Group deployment

A named declaration selecting one Component Group Spec plus initial and
maximum placement counts. One placement materializes the complete flattened
group on one Fleet Subnet Root. Several placements of the same deployment may
share one root when its density policy and every root limit permit it.

### Deployment member limits

The protected reduction-only aggregate and spawn-grant ceilings applied by one
deployment to one exact flattened Component member path. They are derived
under the Component Spec's immutable envelope and apply identically to every
placement of that deployment. They are neither Component Spec mutation nor
physical Subnet configuration.

### Component Group placement identity

`ComponentGroupPlacementId` is the durable Fleet-scoped identity of one
materialized deployment copy:

~~~rust
pub struct ComponentGroupPlacementId {
    pub deployment: ComponentGroupDeploymentId,
    pub ordinal: u32,
}
~~~

Initial placements receive canonical contiguous ordinals starting at zero.
Scale-out durably reserves the next monotonically increasing ordinals before
contacting a root. An ordinal is stable across exact retry and is never reused,
including by a later design that may add scale-in. `maximum_placements` bounds
simultaneously committed placements, not the lifetime ordinal value; checked
ordinal exhaustion fails before mutation.

This identity exists because several homogeneous placements may share one
root. It is not a Tree ID, Canister, controller, Registry partition, runtime
parent or lifecycle delegation boundary. The placement identifies one
orchestration batch and Component Group Directory; every leaf still receives
its own root-allocated `ComponentInstanceId`.

### Component Group member path

The bounded sequence of member names produced while flattening nested group
inclusions. It distinguishes leaf occurrences, including repeated use of the
same Component Spec, without creating runtime parentage.

### Group inclusion and materialization

A Component Group Spec declaration and a group inclusion are inert until a
Component Group deployment selects an outer group. Flattening walks each
reachable inclusion path once and emits one Component occurrence for each leaf
path. It does not execute a separate deployment merely because that deployment
selects an included group, and it does not deduplicate equal Component Specs.

For example:

~~~text
group_two = [C]
group_one = [A, B, include group_two]

one placement of group_one = [A, B, group_two/C]
~~~

That placement creates exactly A, B and C. A separate deployment of
`group_two` creates an additional C; deploying both therefore creates A, B,
C and C as distinct Component instances. Two inclusion paths to the same
Component Spec likewise produce two occurrences with different member paths.

An included group inherits the outer deployment's selected root and placement
count. Deployment, inclusion-edge and leaf-edge purpose assignments
participate in the effective path, but any independent deployment declaration
that also selects an included group does not. Before concrete Component
identity allocation, one planned occurrence is uniquely identified by
`(group_placement, member_path)`. The placement record separately binds its
exact Fleet Subnet Root.

### Component deployment purpose

The typed semantic purpose of one flattened Component occurrence:
`Ordinary` or `FleetServiceMember { service, member_purpose }`.
`member_purpose` is `Authority`, `Replica` or `PoolMember`. Purpose is
protected plan and runtime-binding data. It is never inferred from a label,
root, Subnet, creation order or Component Spec count.

### Deployment label

Bounded canonical key/value metadata attached to a Component occurrence for
passive operator filtering and observability. Labels grant no placement,
authority or routing decision and cannot replace typed purpose.

### Fleet service identity

`FleetServiceId` is a bounded App-declared logical endpoint-set identity,
separate from `CanisterRole`. A target binds the ID to one Component role,
Component Spec and service mode. Several service IDs may intentionally use the
same role and Spec, allowing an App to publish bounded named partitions,
tenants or API pools without inventing new Canister roles. Domain-key routing
to a service ID remains application policy.

### Fleet service mode

`AuthorityReplica` publishes exactly one Authority and zero or more same-Spec
Replicas. `ActivePool` publishes one or more same-Spec PoolMembers. The mode
validates member purposes; it does not implement application consensus, load
balancing, health or readiness.

### Fleet service Authority

The one Component instance published as the Fleet's canonical writable
endpoint for one `AuthorityReplica` service. “Authority” describes the service
binding, not Coordinator ownership or IC controller status.

### Fleet service Replica

A Component instance of the same exact Component Spec as its service
Authority and assigned the protected Replica purpose for that service ID.
The Component package must use that purpose to remain write-fenced. Its
binding identifies topology intent and discovery; it does not by itself block
unknown application writes or prove that application data is current.

This purpose is distinct from 0.100's `ComponentChildKind::Replica`, which
classifies one potential descendant role within a same-root Component tree. A
Fleet service Replica is itself a top-level Component instance, normally on
another root.

### Fleet service Pool member

One configured `PoolMember` endpoint in an `ActivePool` service. Multiple Pool
members may share a root or span roots according to placement policy. Canic
grants a Pool member no implicit write leadership or readiness; the
application owns request distribution and any shared-state consistency.

### Group scale-out

An authenticated same-release operation that monotonically adds complete
group placements assigned to exact active roots within the installed
deployment maximum, per-root density, root aggregate placement limit and
immutable Component admissions. It is not automatic metric-driven scaling and
does not add roots or enlarge admissions.

### Dynamic Component descendants

Any exact registered Component-tree node may ask its own Fleet Subnet Root to
create a direct child whose role is present in the owning Component Spec's flat
potential-descendant catalog and covered by an exact spawn grant from the
requester's registered role. The root records the immediate parent, applies
the per-parent grant, Component-tree and root limits, and remains sole
controller. For Toko, a Project Hub creates Project Instances and each Project
Instance creates its own Ledger and optional Machine. Their creation timing
and required/optional status are application policy; Canic enforces the
catalog, spawn grants and aggregate protected limits.

## Goals

0.101 must:

1. reuse one Component Spec across Ordinary, Authority, Replica and PoolMember
   instances on one or several Fleet Subnet Roots;
2. compile bounded acyclic Component Groups and flatten all nested inclusion
   before planning;
3. preserve flat group-member composition while admitting multi-level dynamic
   Component descendants;
4. give every materialized group copy one stable placement identity without
   making it a runtime parent;
5. support bounded placement packing and spreading across exact Fleet-owned
   roots;
6. let separate deployments reuse one group with different reduction-only
   member limits beneath the shared Component Spec envelope;
7. provision only protected Component-Spec occurrences through those roots;
8. attach typed service ID, mode and member purpose independently of
   free-form labels;
9. resolve exactly one Authority and zero or more Replicas for every
   `AuthorityReplica` service;
10. resolve one or more Pool members for every `ActivePool` service;
11. require every service member to use its target's exact Component Spec and
    satisfy the target's service-wide member density and spread policy;
12. group provisioning into one aggregate operation per selected Fleet Subnet
    Root while retaining each placement boundary;
13. select Wasm only from each root's exact active release set;
14. retain exact root and Component Registry ownership;
15. publish no partial Fleet service member set;
16. support explicit monotonic group scale-out within configured deployment,
    per-root and root-aggregate limits;
17. make interruption and exact retry deterministic;
18. provide root-local group-member discovery without granting group
    lifecycle authority;
19. keep Component descendants out of Coordinator group workflows; and
20. keep the Coordinator off every dynamic descendant-creation path.

## Non-Goals

0.101 does not implement:

- any prior-release transition;
- discovery or adoption of existing Components;
- runtime Group Canisters or nested Component declarations;
- provisioning a Component Child as a group member or Fleet service;
- cross-root descendant creation;
- letting a child or Component perform IC management lifecycle effects
  directly;
- arbitrary Wasm upload, artifact override or Store-catalog expansion;
- arbitrary per-deployment application init arguments or Component Spec
  replacement;
- automatic metric-driven placement or scaling;
- automatic selection of a root for a domain key;
- automatic service load balancing, health selection or readiness;
- group scale-in, relocation, replacement or principal rotation;
- database snapshot, log, cursor or change-stream synchronization;
- Replica freshness, lag, read-routing or readiness guarantees;
- Replica promotion, failover or a second writable Authority;
- application consistency or conflict resolution between Pool members;
- automatic domain-key routing or dynamic data repartitioning between named
  services;
- application-data migration;
- live root creation or admission expansion for a group scale operation;
- Coordinator or Fleet Subnet Root relocation or replacement;
- controller transfer to the Coordinator;
- distributed transactions between roots;
- cross-Fleet service authority merely because roots share a Subnet; or
- compatibility aliases, readers or fallback behavior.

## Configuration

The Toko shape uses one Component Spec per logical database. One Authority plus
up to ten Replicas requires a Fleet maximum of eleven for each database Spec.
Ten is this deployment's chosen example maximum, not a Canic-wide constant:

[component_specs.project_hub.limits]
maximum_descendants = 20_000
maximum_registry_bytes = 16_777_216

[component_specs.project_hub.index.pools.projects]

The `databases` group is declared once. A component member's `service` field
references a `FleetServiceId`; the target then binds that ID to the Spec's
top-level Component role and exact Component Spec. It does not choose member
purpose. The `authoritative_databases` deployment applies the Authority
assignment to those three slots. The nested `databases` inclusion inside
`project_data_cell` applies the Replica assignment to the same three slots.
Each project-data cell also contains one Project Hub PoolMember. Application
routing selects the correct Hub, and that Hub creates Project Instances only
through its local root.

The Project Hub Spec's `children` table is a flat potential-Wasm catalog, not
a static hierarchy. Its separate flat spawn-grant graph authorizes
`project_hub -> project_instance`,
`project_instance -> project_ledger` and
`project_instance -> project_machine` without declaring concrete instances or
nested configuration. A protected binding records
`ProjectHub -> ProjectInstance`, then another records
`ProjectInstance -> ProjectLedger` or
`ProjectInstance -> ProjectMachine`. The Project Hub grant permits up to ten
thousand direct Project Instances for one Hub; the Ledger and Machine grants
permit each Project Instance at most one of each. The 20,000-descendant
aggregate remains the final bound across the whole concrete Component tree.
“Every project has one Ledger” and “one project in one hundred needs a
Machine” remain creation policy enforced by Project Hub/Project Instance state
and idempotent operation identities. Catalog membership selects a permitted
artifact; only the exact role-to-role spawn grant authorizes creation.

The `projects` placement is deliberately an **Index**, not a Directory.
Canic Directories are root-derived read-only discovery projections of
authoritative Registry state. The Project Placement Index is application-owned
keyed state mapping `project_id -> ProjectInstance`; it may drive
resolve-or-create but cannot prove membership or grant lifecycle authority.
Scaling, sharding and indexing are the three composable placement strategies.

The canonical target declaration is:

~~~rust
pub struct FleetServiceTarget {
    pub service: FleetServiceId,
    pub role: CanisterRole,
    pub component_spec: ComponentSpecId,
    pub mode: FleetServiceTargetMode,
    pub placement: FleetServicePlacementPolicy,
}

pub enum FleetServiceTargetMode {
    AuthorityReplica {
        authority_deployment: ComponentGroupDeploymentId,
        authority_member: ComponentGroupMemberPath,
    },
    ActivePool,
}

pub struct FleetServicePlacementPolicy {
    pub maximum_members_per_root: u32,
    pub minimum_distinct_roots: u32,
}
~~~

Targets use canonical raw `FleetServiceId` order. An `AuthorityReplica`
declaration binds the service to an exact Authority occurrence. An
`ActivePool` declaration instead admits every exact PoolMember occurrence for
that service. Neither contains a root principal, physical Subnet, Component
identity, Canister principal or artifact selector.

The service placement policy applies across every deployment contributing
members to that service. Toko's `maximum_members_per_root = 1` ensures an
Authority and its Replicas occupy distinct roots. Another application may
choose a larger value to co-locate read replicas for throughput; Replica
purpose alone does not imply anti-affinity.

The host's protected placement plan assigns `authoritative_databases` to one
exact Fleet Subnet Root and assigns each materialized
`project_data_cells` placement to a different exact Fleet Subnet Root.
Physical Subnet IDs and root principals do not appear in App configuration.

Every selected root must already admit every Component Spec required by its
flattened group. In the maximum Toko shape:

- the Authority root admits one instance each of database A, B and C;
- each of ten project roots admits one instance each of databases A, B and C
  plus one Project Hub and up to its 20,000-descendant aggregate tree limit;
- each project root's Store contains the Project Hub, Project Instance, Ledger
  and optional Machine Wasms once, irrespective of concrete descendant count;
- each relevant root's Wasm Store contains only the exact admitted Spec
  closure required by its release set.

`initial_placements = 1` creates the first project-data cell during fresh
installation. An administrator may later scale `project_data_cells`
monotonically to ten by selecting additional already-installed eligible roots.

Another installation may configure a different positive
`maximum_placements`, subject to the Fleet's Component-instance ceiling,
available root placement capacity, immutable Spec admissions and root-local
limits. The configured maximum becomes protected immutable state for that
installation; 0.101 does not raise it live.

The old scalar target form and the old singleton-Spec rule do not parse.
Targets declare an exact service ID, role, Spec, mode and service-wide
placement policy; an `AuthorityReplica` target additionally names its exact
Authority occurrence.

An independently scaled active API pool uses the same primitives without an
Authority:

~~~toml
[component_specs.public_api]
component_role = "public_api"
maximum_instances = 20

[component_groups.public_api.components.api]
component_spec = "public_api"
service = "public_api"

[component_group_deployments.public_api]
component_group = "public_api"
service_purpose = "pool_member"
initial_placements = 3
maximum_placements = 20
placement.maximum_per_root = 4
placement.minimum_distinct_roots = 2

[services.fleet.targets.public_api]
role = "public_api"
component_spec = "public_api"
mode = "active_pool"
placement.maximum_members_per_root = 4
placement.minimum_distinct_roots = 2
~~~

The initial three placements must occupy at least two roots and no root may
host more than four placements of that deployment. Later scale-out may add
several placements to an existing root or use another pre-admitted root.
Fleet Directory publishes their protected configured membership; application
health, load balancing and state consistency remain outside this design.

## Scaling Composition Model

The deployment is the scaling unit and the placement is one concrete copy of
that unit. Configuration should group only Components that must be created,
published and scaled together. Components with independent cardinality use
separate deployments even when their placements are assigned to the same
root.

The primitives compose into the common scaling shapes:

| Application requirement | Maintained representation |
| --- | --- |
| co-scaled cell or shard bundle | one Component Group deployment |
| independently scaled tiers | separate Component Group deployments |
| several homogeneous copies on one root | several placements under `maximum_per_root` |
| Subnet/root anti-affinity | `maximum_per_root = 1` plus the required minimum spread |
| service-member availability across several deployments | target-level member density and spread |
| single-writer service with read copies | `AuthorityReplica` service |
| stateless or application-coordinated endpoint pool | `ActivePool` service |
| bounded named partitions or tenants | one `FleetServiceId` per declared partition |
| dynamic high-cardinality local trees | multi-level Component Children under each placement's Component |
| fixed multiple copies inside one scale unit | repeated leaf paths in the Component Group |
| same group with different safe capacities | separate deployments with reduction-only member limits |

## Deployment-Scoped Member Limits

A Component Spec defines the absolute maximum policy admitted by topology. A
Component Group deployment may narrow that policy for one exact flattened
member path. It cannot raise a limit, add a role or grant, replace a package or
Wasm, or change any placement belonging to another deployment.

Source configuration uses one bounded member-path entry per reduction:

~~~toml
[component_groups.project_hubs.components.project_hub]
component_spec = "project_hub"

[component_group_deployments.project_hubs_large]
component_group = "project_hubs"
initial_placements = 1
maximum_placements = 1
placement.maximum_per_root = 1
placement.minimum_distinct_roots = 1

[[component_group_deployments.project_hubs_large.member_limits]]
member = ["project_hub"]
spawn_grants = [
  { parent_role = "project_hub", child_role = "project_instance", maximum_instances_per_parent = 10_000 },
]

[component_group_deployments.project_hubs_small]
component_group = "project_hubs"
initial_placements = 1
maximum_placements = 1
placement.maximum_per_root = 1
placement.minimum_distinct_roots = 1

[[component_group_deployments.project_hubs_small.member_limits]]
member = ["project_hub"]
spawn_grants = [
  { parent_role = "project_hub", child_role = "project_instance", maximum_instances_per_parent = 2_000 },
]
~~~

The protected plan may assign `project_hubs_large` and `project_hubs_small`
to roots on different physical Subnets. Physical root or Subnet identity
remains plan input and never enters the reusable group or deployment source
configuration.

A member-limit entry may narrow:

- the Component tree's aggregate `maximum_descendants`;
- its `maximum_registry_bytes`; and
- one or more exact role-to-role `maximum_instances_per_parent` spawn-grant
  ceilings.

Omitted fields inherit the Component Spec. Every configured value is positive
and no greater than the matching Spec value. A spawn-grant reduction must
reference an exact grant already present in that Spec; Singleton grants remain
exactly one. The compiler resolves the flattened member path, removes
redundant equal-to-Spec reductions and emits one canonical effective member
policy.

Every placement of one deployment receives the same effective policy. To use
different limits, configuration declares two deployment IDs referencing the
same group and the protected plan assigns their placements independently.
Scale-out always inherits its deployment's frozen effective policy; it cannot
raise or replace limits.

These limits are control-plane quotas, not arbitrary application init
arguments. Different Wasms, role configuration or application behavior still
requires a different Component Spec, while runtime Authority/Replica behavior
continues to use typed deployment purpose.

Nested group inclusion is solely a way to reuse configuration. An included
group has no independent placement count inside its outer deployment. If its
cardinality must change independently, it is selected by a separate deployment
instead.

This split intentionally keeps bounded Fleet-wide composition in the
Coordinator and high-cardinality dynamic allocation under each top-level
Component tree. For example, a user-hub deployment can scale hub Components
across or within roots while each hub creates its own admitted user shards
through that root. A descendant can itself create descendants without becoming
a top-level Component Group member.

The model does not prescribe the signal that chooses a desired count. A later
operator or autoscaler may drive the same authenticated desired-count
scale-out protocol without changing placement identity or runtime topology.
Safe scale-in still requires its own drain, routing, data-movement and
publication protocol; it must retire placement IDs rather than reusing them.

## Application-Triggered Descendant Provisioning

0.101 reuses the 0.100 same-root descendant lifecycle without adding a
Coordinator operation or cross-root child protocol. The Toko flow is:

1. application routing selects the Project Hub PoolMember on the project-data
   cell that should own the project;
2. that exact Project Hub accepts an application request with one durable
   domain operation identity;
3. the Hub calls its own Fleet Subnet Root for a `project_instance` direct
   child;
4. the root authenticates the Hub, resolves its exact Component binding and
   registered role, verifies the exact
   `project_hub -> project_instance` spawn grant and flat
   potential-descendant catalog entry, and enforces the per-parent grant,
   tree, root, release-set and Store limits;
5. the root creates and installs the Project Instance, records
   `parent_canister_id = project_hub`, and returns the idempotent child
   receipt;
6. the Hub commits `project_id -> ComponentChildBinding` in application
   state;
7. the Project Instance later calls the same root for its Ledger and,
   according to application policy, an optional Machine; and
8. the root authenticates the Instance's registered role, checks the exact
   Instance-to-Ledger or Instance-to-Machine spawn grant and records the
   Project Instance as the immediate parent of each.

The Project Instance, Ledger and Machine receive no
`ComponentGroupPlacementId`, do not become Fleet-service members and do not
mutate the Fleet Registry. They remain descendants of the Project Hub's
top-level Component binding. The Coordinator does not approve, journal or
forward these high-cardinality operations.

Exact retry with the same parent, role and operation identity returns the same
child and receipt. Changing the parent, role or intent conflicts. The
Project Hub's Placement Index does not authorize it to create a Ledger or
Machine beneath a Project Instance: the root accepts those requests only from
the exact registered Project Instance parent. All four Wasms were already
included in the root's flat Spec closure even when most optional descendants
are never created.

The canonical declaration model is:

Member names are unique within one group. Component Group Specs and
deployments use canonical ID order. Source-table order is irrelevant;
canonical compilation orders every member by raw member ID and records its
variant explicitly.

The compiler:

1. resolves every Component Spec and included Component Group;
2. rejects missing references and inclusion cycles;
3. enforces bounded group count, inclusion depth, member count, flattened leaf
   count, path length, label count and encoded bytes;
4. flattens each deployment to canonical `ComponentGroupMemberPath` leaves;
5. resolves every `FleetService` leaf through exactly one Authority, Replica
   or PoolMember assignment on its deployment, inclusion or leaf path;
6. emits each leaf's exact Component Spec, Spec hash, concrete purpose and
   effective labels;
7. resolves each deployment-member limit against one exact flattened path,
   rejects any increase or unknown grant and emits canonical effective
   `ComponentDeploymentLimits`;
8. validates service target mode and member-purpose compatibility;
9. proves each selected placement and distribution fits root-local admissions,
   per-deployment and per-service density/spread policy, and aggregate limits;
   and
10. derives one `ComponentDeploymentConfigurationDigest` from
   domain-separated canonical group-graph, flattened-deployment and
   Fleet-service-target sections.

The configuration digest is semantic, not a raw source-file hash. Whitespace,
comments and source-table order do not affect it. Any member reference,
Component Spec or Spec hash, effective path, purpose, label, placement count,
placement policy, effective member limit or service target change does.
Explicit limits equal to the Spec envelope canonicalize to omission, so they
do not create a second semantic digest for the same effective policy.

An `Ordinary` leaf always compiles to `ComponentDeploymentPurpose::Ordinary`.
A `FleetService` leaf must encounter exactly one
`FleetServiceMemberPurpose` assignment at its deployment, an inclusion edge or
its own leaf edge. No assignment or more than one assignment rejects; there is
no implicit inheritance override. This permits one reusable `databases` group
to be deployed once as Authorities and included elsewhere as Replicas without
duplicating its A/B/C membership. It also permits a deliberately mixed cell to
assign different purposes on separate leaves without wrapper groups.

An assignment applies only to the `FleetService` leaf on that edge or to
service-bearing descendants and must be consumed by at least one such leaf. An
assignment on a path with no applicable service-bearing leaf rejects as
inapplicable rather than acting as metadata.

Service IDs are unique; roles need not be. Every `FleetService` leaf
occurrence must resolve to exactly one declared target whose Component Spec
matches that leaf. The target role must equal the Spec's direct Component
role. An `AuthorityReplica` target must resolve to exactly one Authority, zero
or more Replicas and no PoolMembers. An `ActivePool` target must have at least
one initially materialized PoolMember and no Authority or Replica members. An
orphan member, duplicate service ID, mode mismatch or
service-bearing occurrence outside that relationship rejects.

For each target, the compiler also computes maximum concurrent service members
from every matching occurrence and deployment maximum. Both service placement
bounds are positive and no greater than that maximum. At configured member
count `n`, the assignment must use at least
`min(n, minimum_distinct_roots)` roots and no root may host more than
`maximum_members_per_root` members of that service. Purpose never silently
adds a placement rule.

Deployment, included-group and leaf labels form one canonical effective label
set. A duplicate label key anywhere on one path rejects instead of silently
overriding another value.

The same Component Spec may occur more than once in one flattened group when
the paths differ and capacity permits it. Each occurrence becomes a distinct
Component instance. No group path is copied into `ComponentBinding` as a
parent; it appears only in deployment-purpose and group-discovery projections.

Unknown leaf kinds or purpose assignments reject. Labels may be extended
independently because they have no authorization meaning. A label named
`authority`, `master`, `replica`, `slave`, `writer` or similar remains inert
metadata and cannot override the typed purpose.

### Protected Component deployment context

Every 0.101 runtime receives one current protected deployment context:

~~~rust

    GroupMember {

        group_placement: ComponentGroupPlacementId,

~~~

The root constructs and persists this value from its accepted plan and exact
allocated `ComponentBinding`; the Component cannot supply or mutate it.
`UngroupedOrdinary` covers Components later created through the ordinary 0.100
lifecycle outside a group. Fleet service member purpose is valid only in the
`GroupMember` variant. Its effective deployment limits are resolved from the
immutable Component Spec plus the deployment's reduction-only member entry.
The root persists and enforces those limits for that concrete Component tree;
the Component cannot select or raise them.

This context does not replace `ComponentBinding` as lifecycle identity and
contains no generic parent pointer. The runtime exposes the protected purpose
to application authorization policy. Before activation, a grouped Component
must also verify that its applicable Component Group Directory contains the
same binding, group placement, member path, purpose and labels, while the
root's accepted plan and protected context bind the effective limits.

A later-created Component Child does not become a group member or receive an
independent Fleet service purpose. Its exact `ComponentChildBinding` retains
the owning top-level `ComponentBinding` and exact immediate parent, and the
root sends it the current Fleet and Component Directories through the 0.100
lifecycle. This remains true for grandchildren and deeper descendants. If a
descendant participates in an `AuthorityReplica` service's canonical data
path, its application authorization must verify that exact owning Component is
the service Authority, or accept only an authenticated parent call that has
already enforced that condition. A descendant under a Replica owner must
remain write-fenced. A descendant under a Pool member follows the
application-defined ActivePool protocol and gains no Canic write leadership.
Its role kind, parent depth, label, controller or co-location cannot alter
member purpose.

## Capacity and Placement

Component Spec Fleet ceilings count all Component instances regardless of
purpose. For every Spec, configuration validation computes maximum concurrent
grouped demand:

~~~text
sum over deployments(
  maximum_placements
  × flattened occurrences of this Component Spec per placement
)
~~~

The sum counts every member path in every deployment. An included group that
is also deployed independently contributes both occurrences; equal Component
Specs never coalesce for capacity accounting.

That demand must not exceed `maximum_fleet_instances`. Root admission and
aggregate root-limit validation remains independent:

- `maximum_placements`, `maximum_per_root` and
  `minimum_distinct_roots` are positive;
- `initial_placements <= maximum_placements`,
  `maximum_per_root <= maximum_placements` and
  `minimum_distinct_roots <= maximum_placements`;
- at desired count `n`, the assignment uses at least
  `min(n, minimum_distinct_roots)` roots and no root receives more than
  `maximum_per_root` placements of that deployment;
- a deployment without an Authority occurrence may start with zero placements
  and scale out later, while a deployment containing any Authority must start
  and remain at exactly one;
- one group placement is entirely on one Fleet Subnet Root;
- the root must admit every flattened Component Spec occurrence;
- repeated occurrences consume repeated admission slots;
- each occurrence's deployment-member limits are positive, canonical and no
  greater than its immutable Component Spec envelope;
- every placement must fit `maximum_component_instances`,
  `maximum_managed_canisters`, Store, Registry and cycles limits;
- accepted reservations plus committed placements must fit the root's
  `maximum_group_placements`;
- every service member assignment must also fit its target's service-wide
  member density and spread policy; and
- roots belonging to another Fleet are never eligible.

Because 0.100 permits only one root for a Fleet on a physical Subnet, distinct
Fleet roots also mean distinct physical Subnets for that Fleet. Several
placements may use one root when the deployment density and all root limits
permit it. Assigning one placement per Subnet is therefore expressed by
`maximum_per_root = 1`, not by a separate placement mode.

Deployment placement policy counts complete group copies from one deployment.
Service placement policy independently counts matching members across every
deployment contributing to that service. The two policies may differ: a
multi-member group can be packed as one placement while its separate services
apply their own distribution limits, and several independently scaled
deployments cannot evade a service-wide cap. Toko uses a one-member-per-root
service cap; same-root Authority/Replica placement is valid only when another
installation explicitly chooses a larger cap and the complete assignment
satisfies its policy.

Fresh 0.101 installation extends the protected root-limit value with the
aggregate group-placement ceiling:

~~~rust
pub struct FleetSubnetRootLimits {
    pub maximum_component_instances: u32,
    pub maximum_managed_canisters: u32,
    pub maximum_group_placements: u32,
}
~~~

`maximum_group_placements` counts placements from every deployment on that
root. A root counts accepted but uncommitted placement reservations as well as
committed receipts, while an exact retry of the same reservation is counted
once. Ordinary ungrouped Components do not consume this placement ceiling but
still consume Component, managed-Canister, Registry, Store and cycles limits.
The bounded field may be zero to make a root ineligible for Component Group
placements. It is immutable protected installation input; there is no 0.100
state decoder.

The maximum-demand calculation covers grouped occurrences only. If a Spec is
also intended for ungrouped ordinary creation, its Fleet ceiling and
root-local admissions must include that additional headroom. Spec, admission
and root maxima are ceilings rather than reservations: an already-created
ordinary Component may consume otherwise eligible capacity and cause a later
group scale-out to fail before mutation.

For dynamic descendants, each admitted Project Hub Spec and root-local
admission includes the complete potential-Wasm catalog and aggregate
descendant headroom. Toko sizes each project root's managed-Canister limit for
the Project Hub, Project Instances, Ledgers and possible Machines. Concrete
parent-child edges consume capacity only when created; the Store closure is
complete before any descendant request.

The Spec envelope controls admission and artifact closure; the deployment
member limits control the concrete Component tree. A Project Hub with an
effective 2,000-instance spawn grant cannot consume the unused difference from
the Spec's 10,000-instance grant, even when its root has spare aggregate
capacity. Conversely, a 10,000-instance effective grant does not reserve root
capacity and remains subject to aggregate descendant, Registry, cycles and
managed-Canister limits.

The maximum deployment count is a logical ceiling, not a reservation of
physical Subnet capacity. A root must be installed, Registry-`Active`,
runtime-`Active` and sufficiently admitted before a group scale-out starts. It
may be an initial root or may have completed the ordinary 0.100 root
registration lifecycle in an earlier same-release operation. 0.101 never
combines root creation, admission expansion and placement scale-out into one
operation. This separation permits a Fleet to add Subnet capacity over time
without making a partially joined root eligible or weakening exact retry.

Root selection is explicit protected deployment input. It is never inferred
from labels, current latency, apparent Subnet headroom or root iteration
order. A placement-to-root assignment may repeat a root principal, but every
placement identity in the assignment is distinct.

## Fleet Service Resolution

Every Fleet service target identifies one bounded service ID, direct Component
role, exact Component Spec and mode. The target role must equal the Spec's
direct `component_role`. Every materialized member occurrence must name that
service, use that exact Spec and Spec hash, and carry a purpose admitted by the
target mode.

For `AuthorityReplica`, the Coordinator additionally requires:

- the target's exact deployment and member path resolve to an Authority
  occurrence;
- that deployment has
  `initial_placements == maximum_placements == 1`;
- no other occurrence declares Authority for the service ID;
- zero or more Replica occurrences use the same exact Spec and Spec hash;
- no occurrence for that service has PoolMember purpose.

For `ActivePool`, the Coordinator requires:

- at least one PoolMember occurrence is materialized by the initial
  placements;
- every occurrence for the service has PoolMember purpose;
- all members use the same exact Spec and Spec hash; and
- there is no Authority or Replica occurrence.

In both modes, every member's root must be active, Fleet-owned and admitting
the Spec; every artifact must appear in that root's exact active release set
and Wasm Store Catalog; the complete assignment must satisfy both deployment
and service density/spread policy; and all Spec and aggregate root capacity
must remain available. An orphan member, an unmaterialized Authority selector
or a target with no valid initial member set rejects before mutation.

The target Spec may have `maximum_fleet_instances > 1` and may be admitted by
many roots. An Authority's exact root comes from its protected singleton group
placement, not from a sole Spec admission. Pool members and Replicas come from
their exact placement-to-root assignments. Member purpose never selects a root:
an Authority and Replica may share one only when the target policy explicitly
permits it.

Purpose does not change the artifact. All members of one service use the same
exact Component Spec and qualified Component artifact. Before activation, a
service runtime must find its own exact Component, placement, member path and
purpose in that service's Fleet Directory member set. An Authority or Replica
must additionally resolve exactly one matching Authority from the same
`AuthorityReplica` entry. A Pool member must resolve the `ActivePool` mode but
no leader. A mismatch leaves the runtime `Prepared`.

Authority and Replica purpose form a protected write-role fence and discovery
relationship. Canic cannot infer which application endpoint mutates canonical
state; the service package must bind those write operations to the matching
service ID and protected Authority purpose. A Replica must reject that write
authority. PoolMember purpose says only that the Component is a configured
member of an application-coordinated pool. It grants neither write leadership
nor readiness. An Ordinary occurrence cannot claim either service membership.
IC controller status, group membership, co-location or apparent data freshness
cannot change purpose.

Each root principal joins to one exact active

one or more PoolMembers and no Authority or Replica.

Replica entry does not certify a completed snapshot, current cursor, bounded
lag or eligibility for an application read. A PoolMember entry does not
certify health, load-balancer eligibility or consistency with another member.
Application protocols own that evidence. Consumers derive the one Authority
by requiring exactly one member with Authority purpose; no redundant
`authority` field can disagree with the member set.

Components are installed. Fresh installation fills every target's complete
declared initial member set once before the Fleet becomes terminally installed.
Later successful group scale-out may append the exact newly materialized
Replica or PoolMember bindings in one Fleet Registry revision; it never
changes an Authority or removes a member in 0.101.

There is no reader for the 0.100 Fleet Registry or Fleet Directory shape and
no placeholder service field in 0.100.

`batches` is the sole canonical entry representation. Batches are sorted by

plan hash. For fresh installation it contains every initial Fleet Subnet Root.
For scale-out it contains every selected root plus every existing root that

AuthorityReplica service therefore includes its Authority root; an ActivePool
includes all of its existing member roots. A scale-out containing only
Ordinary occurrences confirms only its selected roots. Existing unrelated
roots receive the new Fleet Registry revision through normal 0.100 mirror
synchronization.

The plan deliberately contains no `ComponentInstanceId` or Canister principal.
Each selected root allocates both under its durable aggregate operation. Exact
retry uses the same operation and plan hash and therefore returns the same
resulting identities.

Planning fails before mutation unless:

- the exact protected Component deployment configuration digest matches;
- every group expansion is acyclic, canonical and within bounds;
- every service-bearing occurrence belongs to the complete target bijection;
- every fresh service target has the exact mode-compatible initial member set;
- every service member resolves to its target's exact Component Spec;
- every placement has one exact unused ID and names one eligible Fleet-owned
  root;
- every Spec appears in that root's exact Component Topology and admissions;
- every entry's effective limits rederive exactly from that Spec and the
  deployment's canonical reduction-only member policy;
- every deployment assignment satisfies its density and minimum-spread policy;
- every service member assignment satisfies its target's density and
  minimum-spread policy;
- every root retains sufficient Spec, group-placement and aggregate capacity;
- every artifact appears in the root's active release set and matching Wasm
  Store Catalog;
- every deployment and Fleet-wide Component maximum remains satisfied;
- no group placement ID is committed or reserved;
- no service ID or Component occurrence conflicts with active work; and
- all count, path and byte bounds hold.

Any existing Component is distinct ordinary state unless an exact committed
receipt proves it belongs to the same operation. It is never adopted into a
group or service binding.

The complete canonical plan and hash are durable before the first provisioning
request.

Application-triggered descendant provisioning does not use
`FleetComponentProvisioningPlan`. It creates one child under one exact
registered parent and root-local operation, so it has no group placement,
member path, independent deployment purpose or Coordinator journal. It reuses
the 0.100 root-local child lifecycle.

## Root-Local Provisioning Contract

The Coordinator sends each selected Fleet Subnet Root one authenticated batch
request binding:

- Fleet and authority epoch;
- Fleet Registry version;
- operation ID and complete plan hash;
- exact Fleet Subnet Root binding and active release set;
- complete sorted group placements and flattened entries for that root; and
- expected absence of each placement and member reservation.

The root:

1. authenticates the exact Coordinator;
2. checks its protected root binding and current Fleet Registry Mirror;
3. verifies every Component Spec admission, exact reduction-only member
   limits, placement density and available Component, managed-Canister and
   group-placement capacity;
4. verifies every exact Component artifact in its active release set and Wasm
   Store Catalog;
5. resumes an exact existing reservation idempotently and rejects a placement,
   member or reservation bound to different intent;
6. durably records one aggregate root-batch intent;
7. allocates each `ComponentInstanceId` and performs Component creation in
   canonical placement/member order;
8. installs every Component runtime `Prepared` with its exact protected
   Component deployment context and effective limits;
9. reconciles every uncertain external outcome before retry;
10. commits each exact Component Registry partition;
11. stores one durable result containing every Component binding and Registry
    identity, partitioned by group placement; and
12. returns that result idempotently.

The request does not grant the Coordinator direct management-Canister access
to a Component. It cannot supply Component identity, Canister principal, Wasm
bytes or a replacement artifact.

The call reuses the ordinary 0.100 Component creation machinery behind an
exact protected publication barrier. It does not duplicate a second creation
implementation.

## Provisioning and Publication Protocol

### 1. Persist planned

The Coordinator stores the complete exact canonical batch plan before calling
any Fleet Subnet Root.

### 2. Selected roots accept the plan

Each selected root durably accepts its exact batch. A root with mismatched
active work, Component Topology, admission, active release set, Wasm Store
Catalog, group placement or contradictory local state rejects.

### 3. Provision Components

The Coordinator asks each selected root to provision its complete batch.
Aggregate root results are projected back to exact group member paths without
losing any Component Registry identity. Exact retry resumes the existing root
operation and never chooses another root, Component Spec, group path,
Component identity, principal, purpose or artifact.

### 4. Verify complete readiness

Before publication, the Coordinator verifies:

- every planned group placement and member is present exactly once;
- every result has the expected Component Spec, effective member limits,
  purpose and root;
- every root receipt covers its complete assigned batch;
- every Component binding and Component Registry identity is exact;
- Component Topology, admission, active-release-set and Wasm Store Catalog
  evidence still agree;
- service ID, Component binding and principal uniqueness;
- every service has the exact mode-compatible member set;
- every AuthorityReplica service has exactly one Authority and every Replica
  uses its exact Spec;
- every ActivePool has at least one same-Spec PoolMember;
- every complete service assignment satisfies its target's member density and
  spread policy;
- all selected roots and every existing member root of an affected service
  remain active; and
- the configuration digest, plan and Fleet Registry relationship remain
  unchanged.

Any missing or contradictory evidence stops before Fleet Registry mutation.

### 5. Publish service topology

For fresh installation, the Coordinator constructs the complete sorted service
set from exact root receipts and commits one next Fleet Registry snapshot.

For scale-out, it adds all new Replica or PoolMember bindings produced by the
exact operation in one Fleet Registry revision. It does not append one member
at a time, replace an Authority or republish unchanged bindings.

An operation whose new group placements contain no Fleet service occurrence
does not invent a Fleet Registry service mutation.

### 6. Confirm Directories

Every root in the plan's exact `directory_confirmation_roots` synchronizes the
published Fleet Registry version and activates its matching Fleet Directory.
This ensures every new Component sees the published topology and every
existing member of an affected service sees the complete new configured member
set before the new Components activate. Each selected root additionally
derives:

- every affected Component Directory from its Component Registries; and
- every affected Component Group Directory from the exact placement receipt
  and those same Registry rows.

The root sends the Fleet, Component and applicable Component Group Directories
directly to each prepared Component and verifies matching provenance before
marking its provisioning batch `Published`.

The service member list remains topology intent. Components must not treat it
as health, application-data readiness or load-balancer eligibility evidence.

Atomic publication means one complete Fleet Registry snapshot commit; it is
not a distributed transaction that forces every unrelated active root to
acknowledge a later scale-out revision synchronously. Those roots converge
through the bounded 0.100 mirror protocol. Fresh installation still requires
every initial root because no Fleet runtime or catalog row is released until
all initial Directories agree.

### 7. Activate runtimes

After every `directory_confirmation_roots` member confirms exact publication
and each selected root confirms all affected Directories, the Coordinator asks
roots to activate their complete prepared batches for the exact operation,
plan and Fleet Registry version.

Roots activate Authority Components first during fresh installation, followed
by the remaining group placements in canonical order. Runtime `Active` permits
application service coordination or replication work to begin; it does not
claim that a Replica has finished synchronizing or that a Pool member is
healthy.

Each root reconciles uncertain outcomes through its ordinary platform
lifecycle, verifies exact runtime `Active` evidence and atomically records its
aggregate state as `RuntimesActive`.

After the fresh operation completes, the host activates every initial Fleet
Subnet Root through the 0.100 path and publishes the Fleet catalog. For later
scale-out, the already-active roots remain active while the new prepared
Components cross the same publication and Directory barrier.

## Explicit Group Scale-Out

After terminal fresh installation, an authenticated Fleet administrator may
request a higher desired placement count for one deployment. The request
binds:

- exact Fleet and authority epoch;
- current Fleet Registry version;
- Component Group deployment and protected configuration digest;
- current and requested placement counts;
- exact newly reserved Component Group placement IDs;
- exact placement-to-active-root assignments;
- expected absence of every reserved placement ID; and
- a unique operation identity.

The requested count must be greater than the current count and no greater than
`maximum_placements`. The assignment list is canonical, has exactly
`requested - current` distinct placement IDs and may repeat a root. Combined
with existing placements, it must satisfy `maximum_per_root` and
`minimum_distinct_roots`. Every selected root must satisfy immutable Component
admissions, the active release set, `maximum_group_placements` and all other
aggregate limits. Every service membership addition, combined with the
published members, must also satisfy that target's
`maximum_members_per_root` and `minimum_distinct_roots`.

The Coordinator expands only the new placements, runs the same root-batch
protocol, publishes their complete Replica and PoolMember additions atomically
when present, distributes Directories and activates the complete new
placements.
Existing placements are neither reprovisioned nor included as mutable work.
Every new placement receives the deployment's already-protected effective
member limits; desired-count scale-out cannot alter them.

Scale-out is forward-only after the first root accepts intent. Exact retry
uses the same placement IDs and root assignments and returns the same
Components and receipts. 0.101 has no scale-down, replacement, relocation or
automatic threshold trigger.

A deployment containing any Authority occurrence must remain exactly one
placement and cannot use scale-out. A scalable deployment may contain Replica,
PoolMember and Ordinary occurrences.

## Grouped Lifecycle Fence

A committed or in-progress group placement is not an ordinary collection of
independently removable Components. While a
`ProtectedComponentDeployment::GroupMember` remains referenced by a
placement record, operation journal or Fleet service binding:

- the ordinary 0.100 Component drain/removal path rejects it;
- its root cannot drain or remove that Component's membership;
- its root cannot enter `Draining` or `Removed`; and
- no administrator may delete, adopt, replace, relocate or reclassify the
  Component through another lifecycle surface.

0.101 defines no operation that decrements a deployment's committed placement
records. Root-owned same-identity start/stop recovery and the Component's
admitted direct-child lifecycle remain available where the existing lifecycle
contract permits them; neither may change deployment, member path, purpose or
effective member limits or service binding.

If a grouped Component or its Subnet disappears outside the protocol, Canic
retains the exact placement, service binding and failure evidence and fails
closed. It does not reinterpret disappearance as scale-in, publish a smaller
member set, reuse the placement ID or choose a replacement. Repair, replacement
and qualified group removal require a later design.

## Fleet, Component and Group Directory Projections

The Fleet Directory projects each service ID, role, exact Component Spec, mode
and complete configured member set. Every member includes purpose, Component
identity, principal, owning Fleet Subnet Root, group placement and member path.

Each Component Directory remains the separate Component Registry-derived
parent/child lookup defined by 0.100, including its compact head, indexed
filters and revision-bound pagination. Each Component Group Directory is a
separate bounded sibling lookup for one flattened placement. Managed
Components receive only the projections applicable to their exact bindings
and never query the Coordinator during normal lookup. No Project Placement
Index is published through any of these Directories.

A grouped data-cell member identifies its sibling database through the exact
member binding in its Component Group Directory, then verifies that same
binding appears in the Fleet Directory service's `members` with Replica
purpose. Equal `fleet_subnet_root` proves co-location but is not sufficient
sibling identity when another placement on the same root contains the same
service Spec. An ActivePool consumer uses the same exact-member join when
placement-local association matters. These joins are deterministic topology
lookup, not automatic routing, health or freshness decisions.

A missing service ID or role, mode-incompatible member, duplicate Authority,
duplicate service member, duplicate Component identity, duplicate principal,
inactive or wrong-Fleet root, unknown Component, purpose mismatch, Fleet
Registry/Fleet Directory mismatch, Component Registry/Component Directory
mismatch or group receipt/Group Directory mismatch fails closed.

## Failure and Recovery

The Coordinator journal is monotonic:

~~~text
Planned
  -> RootsAccepted
  -> ComponentsProvisioned
  -> ServiceTopologyPublished
  -> DirectoriesConfirmed
  -> RuntimesActivated
  -> Complete
~~~

For each external effect:

- durable intent precedes invocation;
- uncertain outcomes are observed before replay;
- exact result receipts are durable before journal advancement;
- retries retain the same configuration digest, operation, group placement,
  root, member path, Component Spec, effective member limits, purpose, active
  release set and expected Component identity; and
- completed work returns its recorded result.

An operation may be cancelled only before any root accepts provisioning
intent. After the first acceptance it is forward-only: recovery finishes
provisioning, publication where required, Directory synchronization and
runtime activation. It never deletes a provisioned Component, rewinds the
Fleet Registry, substitutes another root or constructs another service set.

A failure for one entry remains isolated in that root's aggregate journal and
does not erase completed Component Registry evidence. It still blocks
publication and activation for the complete affected operation.

Contradictory or unknowable non-idempotent outcomes halt with a typed recovery
disposition. Operators resume only by exact retry of the initiating install or
scale-out command and inspect recovery through maintained passive status
surfaces. They may not edit journals, synthesize receipts or mark work
complete.

## Bounds and Encoding

The design uses explicit bounds for:

- Component Group Spec and deployment counts;
- inclusion depth and edges;
- members and flattened leaves per group;
- group member path components and encoded bytes;
- labels per leaf plus label key/value bytes;
- deployment member-limit entries and spawn-grant reductions;
- placement IDs, initial and maximum placement counts, deployment and service
  per-root density, minimum spread and root aggregate placement count;
- configuration-digest sections and Directory-confirmation root count;
- provisioning-plan and root-batch bytes;
- Components, placements and receipts per root;
- descendant role/tree counts, immediate-parent bindings and operation
  receipts;
- Component and group Directory bytes;
- Coordinator/root journal bytes; and
- Fleet service IDs, modes and member bindings.

Canonical arrays use documented field order. Hashes are domain-separated and
length-prefixed. Hash metadata is not embedded inside the bytes it hashes.

Overflow, inclusion cycles, duplicate keys, duplicate paths, noncanonical
ordering, unknown purpose variants and oversized input fail before mutation.

## Authorization

Only the protected Fleet Coordinator may ask a Fleet Subnet Root to accept a
Component group plan, provision planned Components, confirm publication or
activate planned runtimes. Every request binds exact Fleet, authority epoch,
Fleet Registry version, operation, plan, group placement, root, group member
path, Component Spec, effective member limits, purpose, Component Topology,
admission and active release set.

Separately, any exact registered node may ask its own active root to create an
admitted direct child. The request binds the caller as immediate parent, the
owning top-level Component and Spec, child role, authority epoch, operation
identity, current Component Topology/admission and active-release-set identity.

Roots do not accept:

- controller status as Coordinator identity;
- a caller or root from another Fleet, including one on the same Subnet;
- a stale or future epoch;
- an unrecorded, inactive or unselected root;
- a Component Spec absent from the root's topology or admissions;
- a Component Child role as a group member;
- an artifact absent from the exact active release set or Wasm Store Catalog;
- a purpose inferred from a label or caller-supplied override;
- a descendant request from an unknown, foreign-root or cross-tree parent;
- a descendant role absent from the owning Spec's flat catalog;
- a descendant request without an exact parent-role/child-role spawn grant or
  exceeding that grant, Component-tree or aggregate root capacity;
- a committed or reserved placement ID outside exact retry;
- an assignment exceeding deployment density or root aggregate placement
  capacity; or
- a second active operation with different identity.

Component Group membership grants no sibling call permission. Application
endpoints independently authenticate exact callers and operations. Endpoints
that mutate an `AuthorityReplica` service's canonical state must additionally
require the matching service ID and protected Authority purpose; Replica,
PoolMember and Ordinary purpose fail that check. An ActivePool package defines
its own operation policy and must not interpret PoolMember purpose as
Canic-granted leadership. A service-sensitive descendant must bind the same
decision to its exact owning top-level Component and cannot use
`ComponentChildKind`, parent depth, a label or caller assertion as purpose.

Logical parentage grants only the right to request an admitted direct child
from the root. It does not let the parent perform IC management calls or
directly start, stop, fund, upgrade or remove the child.

Ordinary Component/root removal authorization must also prove that no
protected group placement, in-progress operation or Fleet service binding
references the target. Controller status, a missing Canister observation or an
administrator label cannot bypass that fence.

Service Components gain no Fleet Registry or Wasm Store publication authority.

## Stable State and Backup

0.101 installs only the current state shape.

Backup and restore must preserve:

- the host fresh-install journal and exact Coordinator operation binding;
- Coordinator Fleet Registry and provisioning/scale-out journals;
- protected Component Group graph, deployment declarations and service
  targets plus their exact configuration digest;
- every Component runtime's exact protected deployment context and effective
  reduction-only member limits;
- every placement ID, exact root assignment, current deployment count,
  next-placement ordinal and placement policy;
- each root's immutable Component Topology digest, Component admissions,
  aggregate group-placement limit, active release set and Wasm Store Catalog
  evidence;
- each root's latest durable Component allocation sequence;
- root-local aggregate provisioning intents and group-placement receipts;
- descendant-provisioning intents, causal origins, aggregate accounting and
  exact parent/child receipts;
- per-Component Registry rows;
- grouped Component and root lifecycle fences;
- root publication and Directory confirmation state; and
- exact Fleet Registry service-mode/member snapshot and manifest evidence.

Restore validates cross-document identity before resuming. Candidate or
partial files cannot be interpreted as committed state. An ambiguous restored
Coordinator authority remains fenced under the 0.100 authority-epoch rule.

No 0.100 decoder, migration routine or cross-release restoration path exists.

## Role Boundary

| Owner | Responsibility |
| --- | --- |
| Host/CLI | compile and flatten groups, resolve reduction-only member limits, validate maximum capacity, select exact initial roots, build the artifact union, project root release sets and drive fresh installation |
| Coordinator | protect declarations and effective member limits, plan root batches, orchestrate group placements, retain placement counts and publish service topology |
| Fleet Subnet Root | validate and enforce effective member limits, allocate Component and descendant identities, provision top-level Components and every child depth, own platform effects, Component Registries and group-placement receipts |
| Service Authority Component | own canonical writable application data and enforce application write policy |

Coordinator code must not be linked into roots or managed application
Canisters. Generic platform creation code must not be duplicated in
Components. Wasm Store publication code remains root-only.

## Implementation Slices

### Slice 1 — Composition and purpose contracts

- add bounded Component Group, deployment, placement and Fleet-service
  identities;
- compile and flatten acyclic nested groups to canonical member paths;
- distinguish inclusion from independent deployment and preserve every leaf
  occurrence without implicit deduplication;
- resolve reusable service-bearing groups through exact
  deployment/include/leaf purpose assignments;
- add typed Ordinary, Authority, Replica and PoolMember purpose plus inert
  inherited labels;
- compile bounded reduction-only member limits against exact flattened paths
  and Component Spec envelopes;
- validate AuthorityReplica and ActivePool target/member invariants;
- derive the one protected Component deployment configuration digest;
- remove singleton-Spec and sole-admission service assumptions; and
- validate worst-case Spec, deployment, service-member density/spread and root
  capacity.

### Slice 2 — Plans and root provisioning

- freeze the single canonical root/placement/member plan shape;
- carry each entry's canonical effective member limits into root acceptance,
  protected runtime context and durable receipts;
- reserve stable never-reused placement ordinals before root calls;
- accept exact aggregate operations per selected root;
- enforce immutable root aggregate group-placement limits;
- reuse root-local `ComponentInstanceId` allocation and platform lifecycle;
- accept exact same-root descendant requests from any registered
  Component-tree node without a Coordinator operation;
- bind every descendant to its exact immediate parent while retaining the
  top-level Component binding;
- retain group-partitioned Component Registry evidence and receipts; and
- keep every new Component runtime `Prepared`.

### Slice 3 — Service topology and Directories

- derive each target's exact mode-compatible configured member set from
  receipts;
- publish the complete initial service topology atomically;
- add Fleet Directory service mode and member projections;
- derive root-local Component Group Directories; and
- freeze and confirm the exact required Fleet, Component and Group Directory
  recipients before activation.

### Slice 4 — Explicit group scale-out

- persist deployment placement IDs, counts and exact root assignments;
- accept monotonic desired-count increases within immutable maxima;
- pack or spread only new placements within protected deployment and service
  policy;
- atomically append complete Replica and PoolMember additions when present;
- fence grouped Components and their roots from ordinary removal; and
- resume interruption without duplicate placements or Components.

### Slice 5 — Operational qualification

- exercise crash points and exact retry;
- prove backup/restore consistency;
- prove topology, admission, active-release-set, purpose, label and authority
  boundaries;
- prove each Project Hub provisions Project Instance children only through its
  local root while the Coordinator remains off the per-instance path;
- prove a Project Instance can provision its own Ledger and optional Machine

- prove same-Spec cross-Subnet Authority/Replica placement and packed

- remove stale singleton, Tree, runtime-group, adoption or transition language.

## Required Validation

Tests must prove:

- a Component Group may include another group and compiles to flat direct
  Component entries;

## Completion Criteria

0.101 is complete when:

1. Component Groups include other groups acyclically in configuration and
   flatten occurrence-by-occurrence before runtime;
2. every materialized member is a direct Component under one exact Fleet
   Subnet Root;
3. every materialized group copy has a stable placement ID without becoming a
   runtime parent;
4. one Component Spec may back one service Authority and multiple
   cross-Subnet Replicas or a multi-member ActivePool;
5. service ID, mode and member purpose are typed, protected and independent of
   labels;
6. deployment policy can pack several placements on one root or spread them
   across roots, while service policy independently controls member
   distribution across deployments;
7. separate deployments may reuse one group with different reduction-only
   member limits, and every placement of one deployment receives its same
   protected effective policy;
8. every Component identity, platform effect and Component Registry row is
   owned by its root;
9. any exact registered Component-tree node may request an admitted direct
   child through its own root without a Coordinator hot path;
10. every descendant binding records its exact immediate parent while the
   Fleet Subnet Root remains sole lifecycle authority;
11. every provisioned Wasm comes from the exact active release set and matching
   Wasm Store Catalog;
12. the Fleet Registry publishes the complete mode-compatible configured member
   set for each service;
13. Fleet, Component and Component Group Directories remain distinct
   projections with distinct authority;
14. explicit group scale-out is monotonic, bounded, placement-identifiable,
    density/spread constrained and idempotent;
15. grouped Components and their roots cannot bypass the absence of scale-in
    through ordinary removal;
16. another Fleet on the same Subnet remains a separate authority;
17. no Tree identity, runtime Group Canister, nested Component declaration,
    Component Child group/service target, delegated lifecycle authority,
    adoption, ownership transfer or cross-release path remains; and
18. code, tests, schemas, examples and documentation describe only this model.

## Expected Follow-On

0.101 establishes generic co-scaled composition, independent deployment
cardinality, packed or spread placement, stable placement identity and
mode-aware same-Spec service discovery. It reuses root-local multi-level
Component trees for dynamic application instances without adding those
descendants to group composition. It deliberately does not claim that a
configured member is healthy or that application state has moved or converged.

A later scale-in design may drain and retire placements while preserving their
IDs as tombstoned history. A later autoscaler may choose desired counts. Neither
requires a new runtime topology model or a new identity for surviving
placements.

0.103 measures the cross-Subnet call substrate. A later database transport
design must separately define snapshot/log format, revision or cursor
authority, bootstrap, incremental synchronization, backpressure, freshness,
read eligibility, backup/restore interaction and any promotion/failover
protocol. That later design may consume the exact 0.101 service and Replica
bindings but must not add a second writable Authority or reinterpret a label
as authority.
