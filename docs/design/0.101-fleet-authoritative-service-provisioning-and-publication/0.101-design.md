# Canic 0.101 Design: Fleet-Authoritative Service Provisioning and Publication

Date: 2026-07-25

## Status

- Status: proposed.
- Release boundary: reinstall only.
- Dependency: the
  [0.100 Fleet Coordinator design](../0.100-multi-subnet-fleet-coordinator-and-registry-synchronization/0.100-design.md)
  defines the Tree and Registry architecture used here.
- Scope: fresh provisioning of declared singleton Fleet services inside
  ordinary Trees, followed by atomic Fleet publication.
- Compatibility posture: none. A 0.101 Fleet starts from empty 0.101 state.

0.101 does not inspect or preserve a 0.100 installation. It has no candidate
discovery, service adoption, ownership transfer, cross-release plan, prior
service inventory or mixed-version mode. Existing Fleets are reinstalled.

## Thesis

A fresh 0.101 installation creates the Coordinator and Trees described by
0.100, then provisions each declared Fleet-authoritative service through the
selected Tree Root. Only after every service is durably ready does the
Coordinator publish the complete service set in one Registry revision.

For each `[services.fleet.targets]` role:

1. resolve its singleton Tree Group;
2. resolve the one active Tree in that group;
3. prove the exact Tree Spec permits the role;
4. ask that Tree Root to provision the service through its ordinary local
   lifecycle;
5. verify the exact local Registry result; and
6. include the resulting `(role, TreeId, canister_id)` in the one complete
   Fleet publication.

The Coordinator owns Fleet-wide publication. The Tree Root owns local service
lifecycle. The service Canister owns application data.

## Release Boundary

| Release | Fresh-install responsibility |
| --- | --- |
| 0.99 | App/Fleet identity and one-Tree activation |
| 0.100 | Coordinator, Tree topology and Registry synchronization |
| 0.101 | Same topology plus service provisioning and atomic publication |
| Later | Replication, relocation, replacement, failover and data movement |

The table describes architectural dependency, not an in-place release path.
Installing 0.101 creates all required 0.101 state directly.

## Terminology

### Fleet-authoritative service

One singleton role published as the Fleet's canonical service endpoint.
“Authoritative” describes Fleet-wide lookup, not Coordinator ownership of the
Canister.

### Service target

The protected mapping from one role to one singleton `TreeGroupId`.

### Service Tree

The ordinary active Tree selected by that target. Its Tree Root remains local
Registry owner and lifecycle authority.

### Provisioning

Fresh creation and installation through the selected Tree Root's canonical
Tree-local lifecycle.

### Publication

One Registry revision containing the complete declared service set.
Publication does not transfer controllers or local ownership.

## Goals

0.101 must:

1. provision only protected declared targets;
2. resolve the complete target plan before external mutation;
3. provision only through each selected Tree Root;
4. retain exact Tree and local Registry ownership;
5. reject any unexpected pre-existing service row or role conflict;
6. publish no partial service set;
7. bind every published role to exact `TreeId` and principal;
8. make interruption and exact retry deterministic;
9. return completed results without duplicate provisioning; and
10. keep ordinary Canisters out of Coordinator workflows.

## Non-Goals

0.101 does not implement:

- any prior-release transition;
- discovery or adoption of existing services;
- relocation, replacement or principal rotation;
- writable-primary replication, promotion or failover;
- application-data migration or synchronization;
- automatic Tree scaling or application routing;
- Coordinator relocation or replacement;
- controller transfer to the Coordinator;
- distributed transactions between Tree Roots; or
- compatibility aliases, readers or fallback behavior.

## Configuration

The App declares services in their Tree Spec and maps each Fleet role to one
Tree Group:

~~~toml
[tree_specs.primary_data]

[tree_specs.primary_data.canisters.root]
kind = "root"

[tree_specs.primary_data.canisters.users_db]
kind = "service"

[tree_specs.primary_data.canisters.projects_db]
kind = "service"

[tree_groups.primary_data]
tree_spec = "primary_data"
initial_trees = 1
maximum_trees = 1

[services.fleet.targets]
users_db = "primary_data"
projects_db = "primary_data"
~~~

The target declaration is:

- complete and non-empty when service publication is requested;
- sorted by raw role bytes;
- bound to the exact Fleet;
- bounded by count and encoded size;
- protected with the fresh Coordinator installation;
- immutable for that installation; and
- resolved only against the committed current Registry.

A target group must have exactly one active Tree and maximum size one. The
role must occur exactly once in that group's exact Tree Spec.

Configuration supplies declarations, not concrete service principals.

## Authority Map

| Concern | Sole owner |
| --- | --- |
| service target declaration | protected Coordinator installation state |
| Tree/group/spec truth | Fleet Registry |
| provisioning plan and progress | Coordinator service-activation journal |
| local service lifecycle | selected Tree Root |
| concrete local service row | selected Tree Root's local Registry |
| Fleet service binding | Coordinator Fleet Registry |
| consumer projection | Fleet Directory derived from that Registry |

A source-config reread, host report, Tree mirror or service response cannot
replace these owners.

## Registry and Directory Schema Hard Cut

0.101 directly installs the current service-aware Registry:

~~~rust
pub struct FleetRegistry {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub tree_groups: Vec<FleetTreeGroup>,
    pub trees: Vec<FleetTreeEntry>,
    pub authority_services: Vec<FleetAuthorityServiceBinding>,
}
~~~

The matching Fleet Directory adds the complete consumer-shaped service
projection. There is no reader for the 0.100 Registry or Directory shape and
no empty placeholder field in 0.100.

The fresh genesis Registry starts with the service field empty while Trees are
installed. The service activation protocol fills it once with the complete
declared set before the Fleet becomes terminally installed.

## Activation Plan

Before provisioning, the Coordinator resolves a complete plan:

~~~rust
pub struct FleetServiceActivationPlan {
    pub fleet: FleetBinding,
    pub registry: FleetRegistryVersion,
    pub target_declaration_hash: [u8; 32],
    pub entries: Vec<FleetServicePlanEntry>,
}

pub struct FleetServicePlanEntry {
    pub role: CanisterRole,
    pub group: TreeGroupId,
    pub tree: TreeId,
    pub tree_root: Principal,
    pub spec_hash: [u8; 32],
}
~~~

Plan entries are sorted by role. The plan contains no optional candidate,
preserved principal or branch between provisioning modes.

Planning fails before mutation unless:

- every protected target appears exactly once;
- the Registry version is current and exact;
- every target group is singleton;
- every group has exactly one active Tree;
- every Tree uses the expected Spec hash;
- every role is permitted by that Spec;
- no target role already has a local Registry row;
- no service role is already Fleet-published; and
- all count and byte bounds hold.

The complete plan and its canonical hash are durable before the first
provisioning request.

## Tree-Local Provisioning Contract

The Coordinator sends the selected Tree Root an authenticated request binding:

- Fleet;
- authority epoch;
- Registry version;
- activation operation ID;
- plan hash;
- role;
- Tree, group and Spec hash; and
- expected absence of a local role row.

The Tree Root:

1. authenticates the exact Coordinator;
2. checks its protected Tree identity and current mirror;
3. proves the role is permitted by its Tree Spec;
4. checks the role is absent locally;
5. durably records provisioning intent before creation;
6. creates and installs the service through the existing local lifecycle;
7. reconciles uncertain external outcomes before retry;
8. commits the exact local Registry row;
9. stores one durable result receipt; and
10. returns that receipt idempotently.

The request does not grant the Coordinator direct management-canister access
to the service.

## Local Publication State

Each selected Tree Root stores one bounded state for the activation operation:

~~~rust
pub enum TreeServicePublicationState {
    Prepared {
        operation_id: [u8; 32],
        plan_hash: [u8; 32],
    },
    Provisioned {
        role: CanisterRole,
        canister_id: Principal,
        local_registry_hash: [u8; 32],
    },
    Published {
        registry: FleetRegistryVersion,
    },
}
~~~

The exact durable representation may group several roles for one Tree, but it
must retain one canonical operation, plan and transition direction.

`Provisioned` does not make a service Fleet-authoritative. It records that the
Tree-local lifecycle is complete and supplies evidence for the later atomic
Fleet publication.

## Activation Protocol

### 1. Persist planned

The Coordinator stores the complete exact plan before calling any Tree Root.

### 2. Prepare target roots

Each selected Tree Root durably accepts the exact operation and plan. A root
with mismatched active work or contradictory local state rejects.

### 3. Provision services

The Coordinator asks each root to provision its roles. Results are retained
per role. Exact retry resumes the existing root operation and never chooses
another Tree or principal.

### 4. Verify complete readiness

Before publication, the Coordinator verifies for every role:

- the expected Tree and root;
- an exact root receipt;
- exact local Registry identity;
- role and principal uniqueness;
- current active Tree status;
- unchanged target declaration; and
- unchanged plan/Registry relationship.

Any missing or contradictory evidence stops before Registry mutation.

### 5. Publish once

The Coordinator constructs the complete sorted service binding set and commits
one next Fleet Registry snapshot. It never appends roles one at a time.

~~~rust
pub struct FleetAuthorityServiceBinding {
    pub role: CanisterRole,
    pub tree: TreeId,
    pub canister_id: Principal,
}
~~~

### 6. Confirm locally

After Registry publication, every selected Tree Root synchronizes the exact
new version, verifies its service bindings and marks the operation
`Published`. Confirmation may be retried; it cannot change the committed set.

The Coordinator operation is complete only after publication is durable.
Delayed root confirmation remains observable recovery work, not a reason to
publish again.

## Directory Projection

The Fleet Directory projects the complete Registry service set with exact:

- role;
- Tree identity;
- Canister principal;
- Registry authority;
- revision; and
- content hash.

Ordinary Canisters consume the Tree-local cascade. They do not query the
Coordinator during normal service lookup.

A missing role, duplicate role, duplicate principal, inactive Tree, unknown
Tree or Registry/Directory mismatch fails closed.

## Failure and Recovery

The Coordinator journal is monotonic:

~~~text
Planned
  → RootsPrepared
  → ServicesProvisioned
  → RegistryPublished
  → Complete
~~~

For each external effect:

- durable intent precedes invocation;
- uncertain outcomes are observed before replay;
- exact result receipts are durable before journal advancement;
- retries retain the same operation, role, Tree and expected identity; and
- completed work returns its recorded result.

The operation may be cancelled only before any Tree Root accepts provisioning
intent. After the first accepted provisioning intent it is forward-only:
recovery finishes provisioning, publication, root confirmation and Directory
synchronization. It never deletes a provisioned service, rewinds the Registry
or constructs another service set.

Contradictory or unknowable non-idempotent outcomes halt with a typed recovery
disposition. Operators may use maintained Canic recovery commands; they may
not edit journals, synthesize receipts or mark work complete.

## Bounds and Encoding

The design uses explicit bounds for:

- target count;
- target declaration bytes;
- activation-plan bytes;
- roles per Tree;
- receipt bytes;
- journal bytes; and
- final service bindings.

Canonical arrays use the documented field order and sorted role order. Hashes
are domain-separated and length-prefixed. Hash metadata is not embedded
inside the bytes it hashes.

Overflow, duplicate keys, noncanonical ordering, unknown tags and oversized
input fail before mutation.

## Authorization

Only the protected Fleet Coordinator may prepare or provision services at a
Tree Root. Every request binds exact Fleet, authority epoch, Registry version,
operation, plan, Tree and role.

Tree Roots do not accept:

- controller status as Coordinator identity;
- a caller from another Fleet;
- a stale or future epoch;
- an unrecorded Tree;
- a role absent from the Spec; or
- a second active operation with different identity.

Service Canisters gain no Fleet Registry mutation authority.

## Stable State and Backup

0.101 installs only the current state shape.

Backup and restore must preserve:

- Coordinator Registry and service-activation journal;
- protected target declaration;
- root-local provisioning intents and receipts;
- local Registry service rows;
- root publication confirmation state; and
- exact Registry snapshot/manifest evidence.

Restore validates cross-document identity before resuming. Candidate or
partial files cannot be interpreted as committed state. An ambiguous restored
Coordinator authority remains fenced under the 0.100 authority-epoch rule.

No 0.100 decoder, migration routine or cross-release restoration path exists.

## Role Boundary

| Owner | Responsibility |
| --- | --- |
| Host/CLI | compile protected targets and drive fresh installation |
| Coordinator | plan, orchestrate and atomically publish |
| Tree Root | provision locally and retain exact receipts |
| Service Canister | own application data and service behavior |
| Ordinary Canister | consume published Directory bindings |

Coordinator code must not be linked into ordinary Canisters. Tree-local
creation code must not be duplicated in the Coordinator.

## Typed Failures

At minimum, typed failures distinguish:

- target declaration mismatch;
- unknown or nonsingleton group;
- missing or inactive Tree;
- Tree Spec mismatch;
- role not permitted;
- unexpected existing local role;
- duplicate role or principal;
- stale Registry version;
- Coordinator or authority mismatch;
- competing operation;
- provisioning outcome unknown;
- local receipt mismatch;
- incomplete ready set;
- Registry publication conflict;
- Directory confirmation pending; and
- corrupt or oversized durable state.

Recovery logic must not depend on display strings.

## Implementation Slices

### Slice 1 — Contracts and planning

- freeze target, plan, binding and error shapes;
- compile protected targets during fresh install; and
- reject any existing-service branch.

### Slice 2 — Tree Root provisioning

- prepare exact activation operations;
- use the canonical local creation lifecycle;
- reconcile interruption and retain receipts; and
- expose exact idempotent results.

### Slice 3 — Coordinator orchestration

- resolve complete plans;
- drive every root;
- verify complete readiness; and
- retain monotonic recovery state.

### Slice 4 — Atomic publication

- commit the complete service set once;
- synchronize mirrors and Directory; and
- confirm selected roots.

### Slice 5 — Operational qualification

- exercise crash points and retry;
- prove backup/restore consistency;
- prove role-package boundaries; and
- remove stale adoption or transition language.

## Required Validation

Tests must prove:

- fresh install provisions every declared service;
- no prior installation or service candidate is read;
- target resolution is deterministic and complete;
- wrong group, Tree, Spec, role, Fleet or epoch rejects before mutation;
- unexpected existing local roles reject rather than being reused;
- a Tree Root, not the Coordinator, creates the service;
- creation/install uncertainty reconciles before replay;
- completed local provisioning is idempotent;
- partial readiness publishes nothing;
- duplicate role/principal evidence rejects;
- the complete set appears in one Registry revision;
- root confirmation and Directory synchronization resume after interruption;
- completed Coordinator operations perform no duplicate work;
- backup/restore preserves one consistent authority;
- corrupt, incomplete, stale and mismatched state fails closed; and
- ordinary Canister Wasms contain no orchestration authority.

A realistic disposable-environment journey must install a Coordinator, at
least one service Tree and multiple services, mutate service data, restart
recovery at a high-risk effect/receipt boundary and prove the final Directory
resolves the restored service principals and data.

## Completion Criteria

0.101 is complete when:

1. every declared service is freshly provisioned in its exact selected Tree;
2. every local service has one Tree Root lifecycle owner;
3. one Coordinator journal owns activation progress;
4. the Fleet Registry publishes the complete set atomically;
5. Directory consumers observe exactly that committed set;
6. interruption and exact retry cannot duplicate or skip provisioning;
7. no existing-service discovery, adoption, ownership transfer or
   cross-release path remains; and
8. code, tests, schemas, examples and documentation describe only this model.

## Expected Follow-On

Replication, relocation, replacement, promotion, failover and application-data
movement require separate designs. They must not reinterpret this release's
singleton binding or add a second service authority.
