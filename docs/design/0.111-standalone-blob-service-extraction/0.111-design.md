# Canic 0.111 Design: Standalone Blob Service Extraction

Roadmap promotion accepted: 2026-09-25

## Status

- Scheduled next after the amended 0.110 closeout. The maintainer accepted
  blob extraction as the next major slice on 2026-09-25, replacing bounded
  multi-Fleet estates in the 0.111 roadmap position.
- Planning is authorized; implementation remains behind the requested and
  accepted human 0.110 closeout and the ownership/evidence dependencies below.
- Retained need: separate application blob-storage semantics from Canic's
  infrastructure lifecycle responsibilities.
- Canic owners: runtime/facade, host/CLI and testing owners for the eventual
  removal and generic Component integration.
- External owner: unassigned. A standalone service needs its own maintainer,
  exact repository path, package names and release plan before external work
  or a Canic dependency on its publication can begin.
- Repository scope: Canic only. This note authorizes no external repository
  creation or mutation. Existing external repositories remain read-only.

Implementation tracker: [status.md](status.md).

## Intended Outcome And Dependencies

The concrete need is the maintainer's prioritized move of application blob
storage out of Canic. Canic runtime/facade, host/CLI and testing owners own
the in-repository design and extraction. The consuming application and exact
first integration must be named during B1; this plan does not infer authority
to modify that application.

The service must support two deployments through the same implementation:

- An independently deployed service canister that builds and operates without
  Canic, exercised by a concrete consumer.
- An ordinary Canic-managed Component that embeds the same service library
  through thin endpoint and lifecycle adapters.

A non-Canic client calling only the managed deployment does not establish
independence. Both deployments must expose the same blob API and enforce the
same tenant authorization rules. The managed deployment additionally exposes
Canic's required lifecycle endpoints. Multi-Fleet
estate indexing, a reserve Fleet and the proposed cycle-disposition capsule
are not prerequisites. Their design is now a
[deferred idea](../ideas/bounded-multi-fleet-estates/design.md).

## Current Boundary

Canic still has the `blob-storage` and `blob-storage-billing` features,
`canic blob-storage` commands, provider adapters and stable allocations.
Extraction has not shipped. Current allocations are recorded in
[the allocation owner](../../../crates/canic-core/src/role_contract/allocation.rs).

The [Caffeine inventory](../../contracts/BLOB_STORAGE_INVENTORY.md) and
[Cashier inventory](../../contracts/BLOB_STORAGE_CASHIER_INVENTORY.md)
retain earlier protocol evidence. A future extraction must refresh that
evidence against exact provider source or deployed interfaces before selecting
a backend or promising its behavior.

## Retained Direction

A standalone service should own content identities, tenant references,
quotas, provider access, billing, retention and deletion. Canic would manage it
as an ordinary application Component with exact artifact and lifecycle
authority. Blob-specific types and policy would leave Canic's production
dependency graph; no fourth infrastructure role would be introduced.

The proposed external boundaries are:

| Boundary | Responsibility |
| --- | --- |
| Protocol library | Passive identities, requests, responses, errors and canonical Candid |
| Client library | Checkpointable hashing, upload/download and byte verification |
| Service library | Tenant authority, storage invariants, provider policy and workflows |
| Canister entrypoints | External service owner maintains both the standalone entrypoint and Canic adapter; thin endpoint/lifecycle adapters delegate to the service |

Package names and optional shared provider code are decisions for the external
owner. Linking a library must not silently export endpoints. A composed
Canic application must delegate to the same service handlers and satisfy
Canic's maintained managed-role contract. An opaque standalone Wasm is not
automatically a managed Component.

The external service owner owns the Canic adapter's package, release and
maintenance; Canic's runtime/testing owners qualify its generic managed-role
integration. The service core must remain buildable without Canic. Neither
adapter may contain a second storage workflow or independent tenant policy.

Caffeine remains the first backend candidate. Its suitability must be proved;
a generic backend plugin framework is outside this line.

## Contracts Worth Preserving

- Distinguish a portable raw-content digest from a provider-specific object
  identity. Persist service, tenant, reference and immutable content identity
  together; keep gateway URLs and credentials out of durable references.
- Authorize reference release by exact tenant and actor authority. Possession
  of a digest or Canic controller status grants no tenant authority.
- Bound objects, references, bytes, sessions, receipts and global capacity.
  Define counter ownership and atomic reference/accounting transitions.
- Persist upload and deletion intent before paid effects. Reconcile uncertain
  completion through exact provider evidence; HTTP success or caller assertion
  alone must not prove durable storage or deletion.
- Bind upload recovery to its originating actor and epoch. Define finite
  receipt horizons and durable sequence bounds so expired receipts cannot
  authorize duplicate effects or reference-identity reuse.
- Separate logical reference release, provider deletion and billing stop.
  Consumers need a durable release outbox when deleting application records.
- Qualify MIME handling, active-content isolation and public-serving policy.
  Public-by-reference storage does not provide confidentiality.
- Keep provider request types and callback authority in one external owner;
  client and service adapters must not independently recreate that contract.

## B1 Service Contract And B2 Entry Conditions

B1 must freeze a short service contract alongside the complete removal
inventory before B2 begins. Resolve the decisions below, name accountable
maintainers for each owner role, and bind every guarantee to an acceptance
test or authoritative evidence source. Missing evidence remains an open gate;
this design does not claim provider suitability or completed qualification.
B1 closes contract decisions and provider suitability evidence, and assigns
executable service acceptance cases to B2/B3. It does not require an unbuilt
service's tests to have passed before implementation starts.

### Bounded Consumer Target

B1 must name the first consuming application and its owner. The acceptance
journey is one authorized tenant uploading a bounded object, resuming after
interruption, reading and verifying its bytes, then releasing its reference
through confirmed deletion and billing cessation. Exercise the same journey
in both deployments, including unauthorized access, exhausted quota and the
supported restore boundary. Freeze object/session bounds and the consumer's
actual serving needs in B1.

Classify every proposed behavior as existing behavior being preserved, a
correction required for safe extraction, or a new capability that can be
deferred. Bind preserved behavior to current source/evidence and each required
correction to a safety gap and acceptance proof. B2 delivers only the preserved
behavior and necessary corrections for this journey. New capabilities require
a separate scope decision and must not silently become Canic extraction gates.

### Retirement Of Existing Installations

Removing allocation ownership from Canic source and safely retiring an
installation that used those allocations are separate obligations. B1 must
inventory external objects, outstanding uploads, uncertain paid effects,
provider/Cashier balances, ongoing billing and the local records needed to
identify or settle them. Record the exact installation/provider namespace,
authority, accountable operator and evidence for each obligation.

Before an affected installation is reset or its only obligation records are
erased, require evidence that no obligations exist or a completed decommission
procedure owned by its named operator. The procedure must stop new work,
reconcile in-flight effects, establish deletion and billing cessation
separately, and settle balances. Unresolved paid effects remain fenced against
repeat execution and retain durable evidence and an accountable owner; neither
a timeout nor reset clears them. The contract must define controlled return or
explicitly reviewed terminal disposition of residual balances, bounded debits
and any residual liability. An unresolved or continuing obligation blocks reset
unless an explicitly reviewed disposition preserves its records, authority and
funded ownership independently of the state being erased.

Retirement evidence is an operator prerequisite to destructive installation
work, not a migration engine or an old-state reader in the extracted Canic
release. B3 closes source-removal ownership; affected operators separately
close their installation retirement records before reset.

### Recovery Identity And Restore Boundary

Same-release restore alone is insufficient: a backup at upload sequence 40
can be restored after sequence 41 completed and incurred a provider charge.
B1 must specify the recovery identity and its service, provider namespace,
tenant, actor, epoch and operation bindings, including which authority prevents
identity reuse when local counters and completed-session records move backward.
A counter or epoch restored from that same backup is insufficient on its own.

Every supported restore path must fence paid/destructive work and admission
based on stale accounting until reconciliation establishes outstanding effects,
references, reservations, balances and safe operation-identity allocation.
Define fence entry, the evidence needed to lift it, and enforcement against
concurrent or stale instances. The identity authority or provider evidence must
survive the supported restore boundary; choosing a new epoch alone cannot erase
unaccounted effects from the old one.

If the provider cannot supply sufficient evidence, explicitly restrict the
supported backup/restore boundary to a provable one and reject other restores
before effects. Do not advertise arbitrary older-backup recovery. Every
supported path must preserve paid-effect recovery guarantees, including lost
responses and expired local receipts. Same-release backup/restore remains
required within this explicit boundary.

### Provider Suitability And Failure Criteria

For each paid or destructive operation, B1 must record:

- The exact identity binding a retry to its original operation and authority.
- Authoritative completion evidence, how it is queried, and its retention
  horizon relative to retry, receipt and supported restore horizons.
- The typed uncertain outcome, durable fence, bounded reconciliation and
  escalation/disposition when completion cannot be established.
- Separate evidence for object deletion and billing cessation, including
  outstanding charges and balance settlement where applicable.

Missing exact retry binding, authoritative completion evidence, evidence
retention sufficient for the supported recovery boundary, or a safe unresolved
outcome disqualifies Caffeine for that operation and thus this journey if the
operation is required. Inability to establish deletion or billing cessation
also disqualifies it for the stated journey. B1 must record a supported narrower
contract or another provider decision before proceeding; it must not assume
that local retry logic supplies missing provider guarantees. Expiry of a local
receipt or provider evidence never grants permission to repeat an uncertain
paid effect. Such effects retain non-reuse protection and cost accounting.

Separate evidence from exact provider source/deployed interfaces and observed
provider behavior from evidence produced by test substitutes. PocketIC tests
against a substitute qualify service behavior under the modeled contract;
they do not prove that the deployed provider implements that contract. Record
provider identity/version, evidence provenance and limitations explicitly.

### Quota, References And Cost Accounting

B1 must choose absent, tenant-local or shared deduplication, and specify whether
quota measures logical referenced bytes, physical stored bytes or both. Shared
cross-tenant deduplication is not required; introducing it requires a concrete
consumer need and decisions on information exposure, charging and deletion
ownership.

Freeze reservation timing before upload effects, release conditions after
success/abort/uncertain completion, counter ownership and atomic transitions
for upload/release races. Define who pays after logical release until confirmed
deletion and billing cessation. Releasing tenant quota must never remove
still-stored provider bytes from global capacity or cost accounting. In-flight
and uncertain effects retain conservative reservations or equivalent bounded
liability until authoritative reconciliation; race proofs must preserve live
references, prevent premature deletion and avoid lost or double-counted charges.

### Guarantee Ownership And Acceptance Map

The frozen contract must replace these role assignments with named accountable
owners and exact evidence/test references, including any supported exclusions.

| Guarantee | Accountable owner | Required acceptance test or evidence |
| --- | --- | --- |
| Bounded journey and behavior classification | Consumer and external service owners | Named application, preserved-source inventory, necessary corrections and deferred capability list |
| Independent and managed deployments; shared API/authority | External service owner; Canic runtime/testing owners qualify managed integration | Core build without Canic, exact shared implementation/artifact/Candid provenance, both journey runs and identical tenant rejection cases |
| Retirement before destructive reset | Affected installation operator; Canic extraction owner inventories affected allocations | Absence evidence or completed decommission/disposition record, including uncertain effects, residual balances and billing cessation |
| Restore fencing and non-reused operation identities | External service owner | Older-backup-after-paid-completion, stale/concurrent instance, lost-response and expired-receipt cases; supported restore evidence |
| Provider guarantees and suitability | External service owner | Per-operation evidence matrix from the actual provider, retention bounds and explicit suitability verdict; substitutes identified separately |
| Quota, reservations, references and costs | External service owner | Upload/release race, exhausted-capacity, uncertain completion and delayed deletion/billing cases with conserved counters and liabilities |
| Complete removal and surviving generic coverage | Canic runtime/facade, host/CLI and testing owners | Removal inventory and replacement coverage mapping for generic behavior previously exercised by the blob fixture |

## Required Evidence

1. Establish a concrete consumer and an external owner willing to maintain
   the service independently of Canic.
2. Refresh provider hashing, completion, deletion, gateway and Cashier evidence,
   including bounds, namespace exclusivity and uncertain-response behavior.
3. Qualify an independently deployed non-Canic service canister and one ordinary
   Canic Component embedding the same service implementation, with the same
   blob API and tenant rules, exact Candid/artifact evidence and no duplicate
   endpoint exports. Exercise the named consumer journey against both.
4. Prove tenant isolation, quota enforcement, resumable upload/read/release,
   corrupt-byte rejection and same-release restart/restore in PocketIC within
   the frozen recovery boundary, including older-backup fencing and identity
   non-reuse. Qualify actual-provider guarantees separately from substitutes.
5. Inventory the complete Canic feature, runtime, allocation, macro, CLI,
   Medic, fixture, package and documentation removal.
6. Complete B3 as one Canic extraction batch containing the hard cut, its direct
   evidence, propagation and changelog work. External service publication must
   be available before the integration relies on it.

The eventual Canic cut removes old surfaces completely, including their
stable allocation ownership. It provides no aliases, old-state readers,
cross-release migration or mixed-version recovery. Downstream application
adoption remains separately owned.

## Completion And Safety Boundary

Canic extraction is complete only when the external service is independently
available, both deployments use its same handlers, and the Canic removal
inventory is closed with no aliases or compatibility readers. Canic must not
retain a blob-specific production dependency merely to re-export the service.
Generic managed-role authentication, synchronous lifecycle restoration,
artifact authority and same-release recovery remain qualified. Endpoint
adapters authenticate; workflow orchestrates; model/ops own state and effects.

The accepted 0.110 absolute byte/function reserves remain the baseline for
changed canonical artifacts and fixtures. Report measured changes without
claiming unmeasured size or build-time savings. The blob fixture's removal must
account for its surviving generic capability coverage in replacement consumer
evidence; shrinking coverage cannot manufacture a passing budget result.

This is a reinstall-only boundary. There is no cross-release blob-state
migration, installation adoption, preserved identity, mixed-version operation
or rollback promise. Cycle conservation, exact authority, bounded paid effects,
intent-before-effect records, lost-response reconciliation and immediate
effect-free replay remain required. Same-release backup and restore remain
required under the service owner's frozen restore/fencing contract. Every
affected installation reset must satisfy the B1 retirement contract before
erasing obligation records. Blob reference release, provider deletion and
billing stop remain separate qualified outcomes.
