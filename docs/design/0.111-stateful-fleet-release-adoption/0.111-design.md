# Canic 0.111 Design: Stateful Fleet Release Adoption

Date: 2026-08-18
Reoriented: 2026-08-30

  exception. This planning amendment authorizes no evidence or mutation.
- Purpose: qualify one whole-Fleet, stop-the-world transition from one exact
  released 0.110 predecessor to one exact 0.111 successor while preserving
  Canister Principals, application stable memory and Fleet identity.
- Predecessor gate: 0.110 must close with its runtime, build, operator and
  validation budgets satisfied and its stateful-retirement contract published.
- Promotion gate: B1 requires that exact released predecessor plus explicit

- Downstream steering: Toko Miner is the primary read-only real-application

- Exception boundary: no rolling upgrades, mixed versions, predecessor ranges,

## Why This Line Remains Separate

0.109 demonstrated that adding recovery exceptions while an operator journey
is still changing multiplies artifact, journal, status and validation paths.
0.110 therefore contracts the system and freezes budgets first. 0.111 then
owns exactly one transition protocol against one immutable predecessor.

The line does not absorb estate transfer or observability. Transition safety
is independently reviewable only when the Fleet has no uncertain paid,
controller-changing, retirement or provisioning operation.

## Decision

The supported transition is:

```text
one exact released 0.110 predecessor
  -> complete verified backup
  -> read-only copied-state dry run
  -> whole-Fleet admission/effect fence
  -> stop every affected Canister in frozen order
  -> upgrade each role under one transition manifest
  -> restore Canic and application lifecycle participants synchronously
  -> verify every role and the complete release set
  -> reopen the Fleet
```

The successor carries no ordinary old-state fallback. Transition code is
reachable only from the exact admitted manifest and is removed or deliberately
replaced when a later exact transition is designed.

## Goals

0.111 must:

1. preserve every participating Coordinator, Root, Store, managed Component
   and descendant Principal;
2. preserve Fleet, App, Root, Component, parent/child and physical-placement
   identity unless preflight rejects before mutation;
3. preserve application stable memory and invoke the synchronous application
   lifecycle participant after Canic restore and before deferred work;
4. convert each Canic-owned stable record through one exact bounded
   predecessor-to-successor function;
5. fence new external effects and reject admission while any existing paid,
   controller-changing, retirement or provisioning result is uncertain;
6. require verified backup and copied-state dry-run success before the first
   stop or Wasm change;
7. persist host intent and role-local terminal evidence so response loss resumes
   the same transition;
8. recover forward after the first successor state commits;
9. prove release-set convergence across a representative multi-Subnet Fleet
   before ingress reopens; and
10. remain inside the 0.110 Wasm, build and validation budgets.

## Non-Goals

0.111 does not:

- operate two active Canic releases in one Fleet;
- implement rolling, canary, blue/green or partial-Fleet service;
- accept an unnamed predecessor or a version range;
- downgrade after successor state commits;
- translate application business data inside Canic;
- infer conversion success from installed module hash alone;
- bypass 0.110 stateful retirement for removal or recycling;
- preserve uncertain external effects by abandoning them;
- add a product protocol v2, migration registry or compatibility alias;
- implement cross-Fleet transfer or reserve-Fleet operation; or
- modify Toko Miner, IcyDB, Prequel Wars or another sibling repository.

## Steering And Qualification Boundary

Toko Miner supplies requirements from a real endpoint-heavy, IcyDB-composed
managed application and its staging/release process. Canic qualification must
represent that shape with repository-owned fixtures:

- one stateful managed Component with application rows;
- the synchronous application lifecycle participant;
- current Fleet admission and local application authorization;
- stateful-retirement evidence;
- one Fleet with at least two Roots on distinct physical Subnets; and
- the exact public backup, dry-run, transition and verification surfaces.

Read-only downstream confirmation may close an evidence question or expose a
Canic-owned blocker. Mutable downstream code is never release authority.

## Authority And Evidence

| Concern | Sole authority |
| --- | --- |
| predecessor and successor | immutable transition manifest bound to released Git, package, artifact and protocol identities |
| Fleet membership and order | terminal Coordinator Registry plus verified live role bindings |
| Canic stable conversion | role-owned successor conversion over the exact predecessor record |
| application stable conversion | application-owned synchronous lifecycle participant |
| backup sufficiency | canonical backup verifier and complete manifest digest |
| dry-run result | copied-snapshot decode, conversion and invariant evidence |
| effectful progress | one host transition journal plus role-local terminal receipts |
| final convergence | installed module, protocol and release-set evidence for every member |

Caller-supplied version strings, identity labels, prose, file locations and
module-hash equality alone are never transition authority.

## Transition Admission

Before effects, preflight proves:

- the exact 0.110 predecessor and 0.111 successor release/package/artifact set;
- complete Fleet membership with no unknown installed Canister;
- current management Principal, Subnet, controller, module and runtime evidence;
- complete protected role authority after any prerequisite Start has already
  converged through its separately reviewed plan;
- verified backup snapshots and one complete manifest digest;
- successful copied-state decode, conversion and invariant validation;
- no uncertain external result or active retirement, transfer, funding,
  creation, reset, controller or provisioning operation;
- bounded cycle and instruction headroom;
- the inherited 0.110 code/build/validation budgets; and
- one explicit operator confirmation naming network, Fleet, releases,
  Canister count and backup digest.

Incomplete or contradictory evidence blocks before stopping a Canister. No
forced transition exists.

## Stop-The-World Ordering

The Fleet first enters durable `TransitionFenced`. Status remains available;
commands that could create effects reject.

B1 freezes the exact dependency order. The default is:

1. fence Coordinator and Roots against new work;
2. stop managed descendants and Components in post-order;
3. stop Stores and Roots after local work is terminal;
4. stop the Coordinator last;
5. upgrade Coordinator, Roots, Stores and managed roles in the accepted
   recovery order;
6. run Canic restore and application participants synchronously per role;
7. verify each local invariant while the Fleet remains fenced;
8. converge exact protocol and release-set identity across every Root; and
9. reopen only after terminal Coordinator convergence.

No partial transition may serve ordinary application ingress or issue a new
external effect.

## Stable-State Conversion

Each role owns one conversion from the exact predecessor record to the current
record. It:

- checks exact predecessor identity and encoded bounds;
- validates semantic invariants before commit;
- preserves terminal operations, replay receipts, Fleet bindings and
  stateful-retirement evidence;
- rejects unknown fields, corrupt indexes, count drift and uncertainty;
- performs no async work or inter-canister call; and
- commits atomically inside the role upgrade lifecycle message.

The maintained product contract remains version 1. The immutable transition
manifest names historical release identities without creating a general v2
product lane.

Application stable memory remains application-owned. A participant trap aborts
that Canister's upgrade and leaves the Fleet fenced. Correction retries the
same transition; it does not select another successor.

## Failure And Recovery

Qualification covers interruption:

1. before and after the Fleet fence;
2. after each stop;
3. before and after each upgrade, including response loss;
4. during Canic conversion;
5. during the application participant;
6. after local verification but before host receipt;
7. during multi-Root release-set convergence; and
8. after convergence but before reopen.

Before any successor commit, the frozen B1 procedure may retry or restore the
predecessor from verified backup. After the first successor commit, recovery is
forward-only through the same journal and successor. No downgrade reader is
retained.

## Size And Validation Discipline

The transition must not erase 0.110 contraction gains. Each added conversion,
manifest, fence and status variant is attributed to a capability and measured
for canonical roles and the endpoint-heavy fixture.

Pure copied-state conversion and host state-machine tests own the interruption
matrix. PocketIC retains only representative external behavior:

- one multi-role transition with response-loss recovery;
- one participant-trap retry; and
- one two-Root release-set convergence journey.

The final inventory must remain inside the accepted 0.110 case/time/RSS/process
ceiling. Expanding the ceiling requires a separate accepted design amendment,
not an incidental test addition.

## Completion Criteria

0.111 is complete only when:

1. one exact released predecessor and successor are frozen;
2. every participating role has one exact bounded conversion;
3. verified backup and copied-state dry run are mandatory;
4. uncertain external effects block transition admission;
5. the whole multi-Subnet Fleet remains fenced during partial transition;
6. Principals, topology identity, application data and terminal receipts are
   preserved;
7. response loss and restart resume the same journal;
8. successor commits recover forward without a downgrade reader;
9. unsupported predecessors and contradictory evidence fail before mutation;
10. complete release-set convergence precedes ingress reopen;
11. the downstream-shaped stateful fixture passes without a production
    downstream dependency;
12. 0.110 size, build and validation budgets remain satisfied; and
13. a human-requested closeout audit is accepted before 0.112 begins.
