# Canic 0.111 Design: Bounded Multi-Fleet Estates

Date: 2026-08-18
Promoted from former 0.112: 2026-08-31
Cycle-only hard cut: 2026-08-31
Cycle-disposition primitive hold: 2026-08-31

## Status

- Status: held at Q0 platform qualification. This amendment authorizes no
  0.111 implementation, and B1 cannot be promoted from the current design.
- Purpose: add indexed Root-local estates, one ordinary reserve Fleet and one
  bounded same-Subnet source-disposition/destination-credit operation.
- Predecessor: accepted 0.110 contraction closeout and explicit Q0 promotion.
  B1 additionally requires accepted Q0 evidence. Cancelled stateful-adoption
  work is not a prerequisite.
- Hard cut: no cross-release upgrade, migration, backup transition,

- Scope: high-throughput lanes, multi-asset batches, broad automatic funding
  and 1,000-canister qualification remain unscheduled.
- Runtime impact: none from this design amendment.

Implementation status: [status.md](status.md)

## Why This Line Changed

The former 0.111 stateful-retirement and release-adoption design conflicted
with the complete pre-1.0 hard cut. It required backup transitions, stable
conversion and preservation of Principals and application state across
releases. That proposal is cancelled and archived without active authority.

The former 0.112 bounded-estates design is promoted to 0.111, but its physical
Principal controller-transfer path is also removed. The maintained operation
conserves controlled cycles while disposing one empty source asset. It does not
move or preserve that Canister. A later destination asset is fresh.

The first promoted draft also required a stopped, module-free source to issue
its own controlled credit. That is not executable: the
[management canister specification](https://docs.internetcomputer.org/references/ic-interface-spec/management-canister/)
defines `deposit_cycles` over cycles attached by its caller and says deletion
discards the stopped source's balance. The
[canister System API](https://docs.internetcomputer.org/references/ic-interface-spec/canister-interface/)
requires the source to run trusted code and attach its own cycles with
`ic0.call_cycles_add128`. Q0 therefore owns the physical primitive before
estate storage or workflow implementation begins.

## Decision

0.111 makes these decisions:

1. Every Fleet Subnet Root owns one bounded indexed ledger of physical assets
   under its current authority.
2. Total estate, Ready reserve, draining, credit-pending and terminal-deletion
   counts are distinct and atomically coupled to authoritative rows.
3. A reserve Fleet is ordinary infrastructure with explicit Roots and empty
   application topology. It gains no special identity or authority.
4. The only eligible source class is `DisposableOrdinaryComponent`; broad
   `Asset` or controller-only eligibility is forbidden.
5. The first cross-Fleet operation binds exactly one source asset, source Root,
   destination Root, finalized capsule and controlled destination credit on one
   observed physical Subnet.
6. Before capsule installation, the source is stopped, module-free, unbound and
   funding-fenced. Canic decodes, exports and preserves no application data.
7. Both Roots prepare and activate the same immutable plan digest before credit
   becomes permissible.
8. The finalized one-shot capsule temporarily runs in the source and attaches
   the exact controlled credit to the destination Root call. The operation
   transfers controlled cycle value, not a Principal.
9. The destination's atomic operation receipt is credit authority. A raw Root
   balance delta is corroborating evidence only.
10. Source deletion is forbidden until exact accepted destination credit,
    bounded observed protocol debit and bounded terminal residual discard
    reconcile under one operation.
11. Response loss and restart resume that same source, destination and amount.
12. A later destination creation uses ordinary creation authority and receives
    a fresh Principal.
13. Root operating reserve, estate credits, protocol debit, residual discard
    and operator debit remain separate quantities.
14. Every later runtime batch that consumes 0.110 headroom inherits its
    canonical/endpoint-heavy measurement and stop/continue/retarget gate.

## Non-Goals

0.111 does not:

- upgrade, migrate, adopt or preserve an installation across releases;
- preserve or transfer application data, stable memory, Wasm, logical identity
  or a Principal;
- add application retirement receipts or data-disposition tombstones;
- move a live or stateful application Canister between Fleets;
- infer authority or cycle settlement from controller status alone;
- create or transfer a Root, Coordinator or Wasm Store;
- perform a cross-Subnet operation;
- batch assets or add automatic high-throughput creation/reset;
- promise 1,000-canister scale;
- add an on-canister Observatory or renderer; or
- make a downstream application a production dependency.

## Authority Map

| Concern | Sole authority |
| --- | --- |
| Fleet identity and membership | exact Coordinator Registry authority |
| Root identity and physical placement | Registry plus live effective-ID-routed management evidence |
| source asset and balance | source Root estate row plus exact live management/balance observation |
| destination reservation | destination Root capacity and credit record |
| operation intent | matching source/destination records under one operation and plan digest |
| finalized capsule | immutable descriptor binding an audited code hash, invoker, source, destination, amount, operation and plan digest that match both Root records |
| controlled credit | exact atomic destination receipt; live Root balance is corroborating accounting evidence, never standalone proof |
| bounded source debit | exact source pre-balance, accepted credit and final pre-delete residual under one reviewed protocol-debit ceiling |
| deletion eligibility | reconciled credit/debit/residual proof plus stopped, module-free, unbound and funding-fenced source observation |
| terminal result | source deletion observation and matching terminal receipts at both Roots |

The host composes evidence but is not an authority cache. Semantic versions,
prose, identity labels and matching controllers never substitute for the exact
records and observations above.

## Eligible Source Class

The maintained source type is the closed class
`DisposableOrdinaryComponent`. It excludes:

- Coordinator, Root and Wasm Store Canisters;
- issuer, verifier, control-plane or other authority-bearing Canisters;
- every topology-bound Component; and
- every Canister with pending funding, installation, recovery, release,
  admission, removal or other workflow work.

`unbound` is not a label. It is the conjunction of exact negative Registry,
Directory, application-topology, funding-reservation, recovery-journal and
workflow observations. The funding fence rejects new top-ups, debits,
reservations and ownership changes from preparation through terminal deletion.
Resource reservations and reserved-cycle balance must both be zero before
preparation. Any missing, stale or contradictory observation rejects before
effect.

## Q0: Cycle-Disposition Platform Qualification

Q0 precedes indexed-estate storage work. It uses disposable canisters and
retains an immutable platform report proving:

1. a stopped, uninstalled and otherwise empty source accepts only the finalized
   per-operation capsule hash;
2. the finalized descriptor binds the audited code hash and exact authorized
   invoker, source, destination, operation ID, plan digest and credit amount;
3. after start and authorized invocation, the source attaches exactly that
   credit to the named destination call;
4. the destination accepts exactly the first matching credit and atomically
   commits its operation receipt and internal credit allocation;
5. a duplicate matching call accepts zero cycles so the unaccepted attachment
   is refunded, while any mismatched call also accepts zero and fails closed;
6. response-loss recovery resolves through the destination receipt and the
   same immutable operation rather than a blind alternative transfer;
7. the source retains reviewed execution slack instead of attaching its entire
   liquid balance;
8. the source can be stopped and the capsule uninstalled after settlement;
9. the source's residual balance is observed immediately before deletion; and
10. deletion succeeds, the source is absent and the observed residual is
    recorded as deliberately discarded.

The capsule has no stable-memory decoder, export or preservation path. Q0 must
prove that it neither reads nor interprets predecessor stable memory. Its code
hash and initialized bindings are immutable after finalization; no endpoint,
install retry or mutable source state can retarget it.

Q0 is a physical-operation qualification, not authority to add estate product
state. If the exact-credit, duplicate-refund, response-loss, slack or deletion
path fails, the design returns for revision before B1.

## Indexed Estate Contract

Each Root maintains bounded counters and keyed indexes for total owned assets,
Ready assets, claimed/installed assets, draining assets, destination-credit
reservations, deletion-ready assets, uncertain operations and terminal
deletion records.

Hot decisions use counters and indexes rather than full stable-memory scans.
Every counter change commits atomically with its authoritative row. Duplicate
ownership, corrupt counts, impossible phases, missing reverse indexes or
repeated operation bindings fail closed.

The initial policy distinguishes `owned_target`, `owned_maximum`,
`ready_reserve`, `standby_cycles` and `claim_top_up_cycles`. Changing a target
never destroys an asset, cancels an issued effect or creates work above the
reviewed maximum.

## Ordinary Reserve Fleet

A reserve Fleet contains one Coordinator, one Root per selected physical
Subnet, one sibling Store per Root and zero application Components. Registry,
funding, admission and Root authority remain ordinary Fleet contracts. Empty
topology grants no application release, membership or preservation authority.

## Cycle-Safe Disposition Eligibility

Before intent, evidence proves:

- exact source/destination network, Fleet, Root and physical Subnet identity;
- one `DisposableOrdinaryComponent` under exact source authority;
- source stopped, module-free, concretely unbound and free of nonterminal work;
- an active funding fence covering the source;
- zero source resource reservations and reserved-cycle balance;
- exact source controlled-cycle balance and accepted residual ceiling;
- exact destination controlled account, capacity, operating reserve and
  pre-credit accounting state;
- no existing reservation for the source or destination credit;
- exact credit, reviewed protocol-debit maximum, residual-discard maximum and
  operator-debit maximum;
- finalized capsule hash and its immutable bindings; and
- same-operation retry evidence for every prior effect.

The operator explicitly accepts that source data and Principal are destroyed,
not preserved. No application acknowledgement or data decoder is involved.
Wrong, stale, missing or contradictory evidence rejects before effect.

## One-Asset Cycle Transfer And Deletion

One operation proceeds:

1. eligibility proves the empty source, concrete unbound state and funding
   fence;
2. destination Root durably enters `DestinationPrepared` with capacity and the
   exact credit reservation;
3. source Root durably enters `SourcePrepared` with the source pre-balance,
   deletion intent, capsule hash and all exact amounts and maxima;
4. host freezes one content-addressed plan digest over both records;
5. destination Root verifies the digest and enters `DestinationActivated`;
6. source Root verifies the matching destination activation and enters
   `SourceActivated`;
7. both exact activations establish `CreditPermitted`; only then may the source
   Root install and start the finalized capsule in the empty source;
8. the source Root invokes the capsule's bound operation, and the capsule calls
   `accept_estate_credit(operation_id, plan_digest, source_asset)` on the
   destination Root while attaching the exact credit;
9. destination Root verifies caller, source, operation, digest, reservation and
   exact attached amount, accepts the cycles and atomically commits the receipt
   plus internal credit allocation;
10. response loss re-observes the authoritative destination receipt and source
    balance before permitting only same-operation recovery;
11. after accepted credit is proved, the source is stopped, the capsule is
    uninstalled and the source is revalidated as stopped, module-free,
    concretely unbound and funding-fenced;
12. the last source balance immediately before deletion becomes
    `terminal_residual_discard`; both Roots reconcile the conservation equation;
13. only after reconciliation succeeds may the source Canister be deleted;
14. both Roots commit terminal receipts and immediate replay performs no
    transfer, deletion or operator debit; and
15. any later destination asset creation is a separate ordinary creation with
    a fresh Principal.

The prepare/activate order is fixed:

```text
DestinationPrepared
    -> SourcePrepared
    -> DestinationActivated
    -> SourceActivated
    -> CreditPermitted
```

Prepare and activate acknowledgements are direct Root-to-Root update evidence
bound to the exact peer caller. The host may trigger and retry those calls, but
cannot manufacture an acknowledgement. Before `CreditPermitted`, both Roots
store the matching peer evidence, including the source activation receipt.

Before the credit effect, cancellation may release both reservations. After an
effect may have issued, only observation or exact same-operation retry is
allowed. Uncertainty cannot select another source, destination or amount.

For a first matching call, the destination verifies the complete binding,
requires the exact attached amount, accepts exactly that amount and creates one
receipt atomically. The receipt records exact caller, operation ID, plan
digest, source asset, cycles offered, cycles accepted and resulting internal
credit allocation. A matching terminal duplicate accepts zero and returns the
existing receipt, causing all newly attached cycles to be refunded. A mismatch
accepts zero and returns no success authority.

The destination Root maintains an internal accounting invariant over its one
native balance:

```text
root_native_balance >=
    root_operating_reserve
    + sum(outstanding_estate_credits)
    + other_bound_cycle_liabilities
```

Native cycle balances have no subaccounts. The atomic receipt and internal
allocation therefore prove this operation's credit; before/after Root balance
deltas alone cannot distinguish it from Root burn or unrelated top-ups.

## Conservation Rule

For exact observed values bound to one operation:

```text
source_pre_cycles =
    controlled_destination_credit
    + observed_protocol_debit
    + terminal_residual_discard

0 <= observed_protocol_debit <= reviewed_protocol_debit_max
0 <= terminal_residual_discard <= reviewed_residual_max
```

`controlled_destination_credit` is the exact amount accepted in the atomic
destination receipt. `terminal_residual_discard` is the last observed source
balance immediately before deletion. `observed_protocol_debit` is the exact
residual arithmetic term after subtracting those two amounts; it is not a
claim that the platform supplied an itemized execution invoice. The source
retains enough slack for capsule execution and response handling and never
attaches its entire liquid balance.

Every term is nonnegative and bound to the same immutable plan. A protocol
debit or terminal residual above its reviewed maximum, an accounting
underflow, a changed source balance after the final observation or any other
unexplained loss blocks deletion and terminalization. Operator debit defaults
to zero and is never a plug for failed conservation.

## Failure And Recovery

Qualification covers interruption before either preparation, at every
prepare/activate boundary, after capsule installation/start, after credit
issuance with response loss, after either observation, before capsule
uninstall, before deletion, after deletion with response loss and after one
terminal receipt. Each phase has one permitted next action. Restart reads both
Root records, the destination receipt and live evidence; terminal replay is
effect-free.

Same-release retry and idempotency are mandatory. They are not cross-release
compatibility and preserve neither application state nor Principal identity.

## Size And Validation Discipline

Roles without estate ownership compile none of this workflow. Every B1-B6
batch that changes a runtime artifact remeasures all canonical roles and the
endpoint-heavy fixture, records validator-counted/defined functions, byte and
instruction deltas plus fresh marginal attribution, and makes an explicit
stop, continue or retarget decision. The artifacts retain 0.110's absolute
code-section and replica-validator function reserves. A batch that changes
generic/type-instantiation fanout also refreshes the named post-`-Oz`
monomorphization report and records the new per-instantiation marginal deltas.

Pure transition tables and host fixtures own the interruption matrix;
PocketIC retains Q0's physical capsule proof and only representative
credit-response-loss/deletion and two-Fleet isolation journeys.

## Completion Criteria

0.111 is complete only when:

1. estate decisions use bounded indexes/counters without full scans;
2. owned target, maximum and Ready reserve remain distinct;
3. a reserve Fleet is ordinary infrastructure with empty topology;
4. Q0 proves the finalized capsule's exact credit, duplicate refund,
   response-loss, execution-slack, uninstall, residual-observation and deletion
   behavior before B1;
5. only `DisposableOrdinaryComponent` is eligible, under complete negative
   binding/workflow evidence and an active funding fence;
6. one operation binds one source asset, both Roots, one finalized capsule and
   one controlled destination credit;
7. both Roots durably prepare and activate the same digest before credit;
8. the atomic destination receipt, not a raw balance delta, proves exact caller,
   operation, offered/accepted cycles and internal allocation;
9. deletion is impossible before accepted credit, bounded observed protocol
   debit and bounded terminal residual discard reconcile;
10. response loss resumes the same operation without blind retry or alternate
    selection;
11. unexplained loss and any debit/residual above its reviewed maximum fail
    closed;
12. terminal replay performs no transfer, deletion or operator debit;
13. no contract promises data, stable-memory, Wasm, logical-identity or
   Principal preservation;
14. later destination creation receives a fresh Principal;
15. two Fleets across two Subnets remain authority-isolated;
16. every runtime batch retains 0.110 artifact/build/validation budgets and its
    fresh measurement decision; and
17. a human-requested closeout audit is accepted before another minor begins.
