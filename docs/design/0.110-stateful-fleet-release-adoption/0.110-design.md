# Canic 0.110 Design: Stateful Fleet Release Adoption

Date: 2026-08-18

## Status

- Status: accepted and scheduled as the first explicit pre-1.0 cross-release
  exception. This planning cut authorizes no evidence or runtime mutation.
- Purpose: qualify one whole-Fleet, stop-the-world transition from one exact
  released predecessor to one exact successor while preserving Canister
  Principals, application stable memory and current Fleet identity.
- Predecessors: completed 0.104 lifecycle composition, 0.105 local
  authorization, 0.107 runtime admission and 0.109 stateful
  retirement/estate contracts. B1 begins only
  after the exact predecessor release and every Canic-owned stable/Candid
  surface are immutable.
- Successor: 0.111 may use the adopted Prequel Wars Fleet as a durable
  observatory qualification target. Until 0.110 closes, every stateful demo
  Fleet remains disposable.
- Repository scope: Canic only. Prequel Wars and IcyDB remain read-only
  requirements/evidence sources and are not modified by this line.
- Exception boundary: this design does not approve rolling upgrades, mixed
  versions, arbitrary historical migration, downgrade or a permanent
  compatibility layer.

## Decision

Canic will support the smallest production-credible release transition:

```text
one exact released predecessor
  -> verified backup and dry run
  -> whole-Fleet admission fence
  -> stop all affected Canisters
  -> upgrade each role under one frozen transition manifest
  -> run Canic and application lifecycle participants synchronously
  -> verify every role and exact release-set convergence
  -> reopen the Fleet
```

The first supported transition is selected in B1 only after the predecessor is
released. The successor is this maintained 0.110 contract. Every role used by
the qualification has one exact predecessor schema, successor schema,
conversion owner, invariant set and terminal receipt. Unsupported predecessor
identity fails before the first upgrade.

This is adoption, not fallback decoding. The successor does not carry a
general old-state reader in ordinary runtime paths. Transition code is
reachable only through the exact admitted predecessor manifest and is removed
or replaced deliberately when the next supported transition is designed.

## Goals

0.110 must:

1. preserve every participating Coordinator, root, Store and managed
   application Canister Principal;
2. preserve Fleet, App, root, Component, parent/child and physical-estate
   identity unless the frozen transition explicitly rejects before mutation;
3. preserve application stable memory and invoke the 0.104 synchronous
   lifecycle participant before deferred application work;
4. migrate each Canic-owned stable record through one exact predecessor-to-
   successor conversion with checked bounds and no heuristic decoding;
5. fence nonterminal paid, controller-changing, retirement, transfer,
   provisioning, funding and application operations before transition;
6. require a verified backup and a read-only dry run before the effectful
   transition;
7. persist host-side intent and per-Canister terminal evidence so response loss
   resumes the same transition rather than starting another;
8. define exact failure and forward-recovery behavior for every interruption
   point;
9. prove final whole-Fleet release-set convergence before ingress reopens; and
10. qualify one representative stateful Canic+IcyDB Prequel Wars fixture
    without adding a production dependency on either downstream project.

## Non-Goals

0.110 does not:

- permit two active Canic releases to serve one Fleet concurrently;
- provide rolling, canary, blue/green or partial-Fleet operation;
- adopt an unnamed or unbounded predecessor range;
- support downgrade, rollback after successor state commits or arbitrary
  restoration of an old binary over new state;
- translate application business data inside Canic;
- infer migration success from Wasm installation alone;
- bypass 0.109 application retirement for removal/recycling;
- preserve nonterminal external effects by silently abandoning them;
- add `v2` product protocols, compatibility aliases or generic migration
  registries; or
- authorize modification of Prequel Wars, IcyDB or another sibling repository.

## Authority And Evidence

| Concern | Sole authority |
| --- | --- |
| admitted predecessor and successor | immutable transition manifest bound to released Git/package/artifact identities |
| Fleet membership and ordering | terminal Coordinator catalog plus verified live role bindings |
| Canic stable conversion | role-owned successor migration function over the exact predecessor record |
| application stable conversion | application-owned synchronous lifecycle participant |
| backup sufficiency | canonical backup verifier and immutable pre-transition evidence digest |
| dry-run result | read-only decoder/conversion against copied snapshots; never live mutation |
| effectful progress | host transition journal plus role-local terminal evidence |
| final convergence | verified installed module/protocol/release-set identity for every participating Canister |

Caller-supplied version strings, local identity names and file paths are never
authority. The host resolves the exact Fleet from its terminal catalog,
verifies live Canister metadata and binds every transition input before asking
for confirmation.

## Transition Admission

Before the first stop or Wasm change, preflight must prove:

- exact predecessor package, release-set, protocol-profile and module hashes;
- complete role membership with no unknown installed Canister;
- verified backups for every stable owner and one manifest digest covering the
  complete set;
- successful dry-run decode, conversion and invariant validation for every
  copied snapshot;
- no nonterminal operation whose external result remains uncertain;
- no active retirement, estate transfer, controller transition or paid
  funding/creation lane;
- bounded cycle headroom and management-call authority for the complete plan;
- exact successor artifacts and transition functions; and
- one explicit operator confirmation naming network, Fleet, predecessor,
  successor, Canister count and backup digest.

Any incomplete or contradictory evidence blocks before effects. A forced
upgrade path is outside this design.

## Stop-The-World Ordering

The Fleet enters a durable `TransitionFenced` state before stopping workload
Canisters. New commands that could create external effects reject; bounded
status and transition inspection remain available.

The frozen B1 order must respect authority dependencies. The default proposal
is:

1. fence Coordinator and every root against new work;
2. stop managed application Components and descendants in post-order;
3. stop Stores and roots after their local work is terminal;
4. stop the Coordinator last;
5. upgrade Coordinator, roots, Stores and managed Components in the exact
   accepted recovery order;
6. run each role's Canic restore and any application participant synchronously;
7. verify every local invariant while ingress remains fenced;
8. converge release-set and protocol identity across the complete Fleet; and
9. reopen only after the Coordinator commits terminal convergence.

B1 may change the middle ordering only with an explicit dependency proof. It
may not permit application ingress or new external effects during a partial
transition.

## Stable-State Conversion

Each Canic-owned role keeps one transition function from the exact predecessor
record to the current record. Conversion:

- accepts only the frozen predecessor identity and exact encoded bounds;
- checks every semantic invariant before committing successor state;
- preserves terminal operation and replay receipts;
- rejects unknown fields, corrupt indexes, count mismatches and nonterminal
  uncertainty;
- performs no inter-Canister call or asynchronous work; and
- commits atomically inside the role's upgrade lifecycle message.

The current product schema remains version 1. The transition manifest names
the predecessor release; it does not create a product `v2` lane. Ordinary
fresh installs continue to accept only current state.

Application stable memory remains application-owned. The 0.104 participant is
invoked after Canic synchronous restoration and before deferred work. A
participant trap aborts that Canister's upgrade and preserves its prior Wasm
and state. The Fleet remains fenced while the exact same transition is retried
after correcting the cause.

## Failure And Recovery

The qualification covers interruption:

1. before the Fleet fence;
2. after the fence and before any stop;
3. after each stop;
4. before and after each upgrade call with response loss;
5. during Canic stable conversion;
6. during the application lifecycle participant;
7. after local verification but before host receipt;
8. during final release-set convergence; and
9. after convergence but before ingress reopen.

Before any successor commit, the exact plan may safely retry or restore the
predecessor from verified backup according to the frozen B1 procedure. After a
Canister commits successor state, recovery is forward-only: retry that same
successor transition until every role converges. A general downgrade reader is
not retained.

The journal records no secret key material. It stores immutable Fleet and
transition identity, ordered Canister entries, prior observations, exact
request/receipt hashes and terminal verification.

## Prequel Wars Qualification

Canic owns a bounded test fixture representing a stateful managed planet role;
it does not vendor the game. An exact test/dev IcyDB revision may be used to
prove:

- unchanged Canister Principal and application stable rows;
- Canic Component/Fleet identity preservation;
- synchronous IcyDB recovery through the 0.104 participant;
- terminal operation and application-retirement receipt preservation;
- local 0.105 authorization state either migrates exactly or is deliberately
  invalidated by the frozen transition policy; and
- post-transition reads and updates satisfy both Canic and application
  invariants.

The external Prequel Wars repository adopts the released surface separately.
Its own integration evidence is not a Canic mutation gate.

## Completion Criteria

0.110 is complete only when:

1. one exact released predecessor and successor are frozen;
2. every participating role has one exact bounded stable conversion;
3. verified backup and dry run are mandatory before effects;
4. nonterminal external effects block admission;
5. the whole Fleet remains fenced throughout partial transition;
6. Principals, Fleet/application topology identity and terminal receipts are
   preserved;
7. application stable memory and the synchronous lifecycle participant pass;
8. response loss and restart resume the same journaled transition;
9. successor commits recover forward without a generic downgrade reader;
10. unsupported predecessor, corrupt state and contradictory live evidence
    fail before mutation;
11. final release-set convergence covers every participating Canister before
    ingress reopens;
12. the stateful Canic+IcyDB fixture upgrades without data loss; and
13. active docs describe this exact exception without implying rolling or
    arbitrary compatibility.

## Next Authorized Action

exact predecessor release is available, explicit maintainer promotion may
authorize B1 inventory only. Every mutating batch remains blocked on accepted
B1 and its named predecessor.
