# Canic 0.113 Design Reservoir: Skynet Fleet Observatory

Date: 2026-08-11

## Purpose

Skynet should make the capabilities and boundaries of a real Canic Fleet easy
to see. An operator or visitor should be able to move through a themed network
and understand:

- which physical Subnets and Fleet Subnet Roots exist;
- which application Components run on each root;
- which service member is Authority, Replica or PoolMember;
- which descendants were created through scaling or sharding policy;
- which configuration, placement, limits and authority apply;
- which endpoints and metrics each role exposes;
- which facts are observed, configured, derived or merely proposed; and
- where Canic deliberately stops short of replication, routing, failover,
  automation or external authority.

The demo should become richer as Canic gains real capabilities, without
inventing those capabilities inside application presentation code.

## Current Baseline

The 0.101.43 application already provides:

- one Skynet Authority and seven Replicas on eight distinct configured roots;
- a maximum of one Skynet service member on each of up to 32 pre-installed,
  pre-admitted roots;
- one initial T-800 scaling child and one initial memory-cell sharding child
  per service node, with independent policy ceilings of four;
- shared code-native HTML and JSON rendering across root, service-node,
  worker and shard roles;
- live Canister identity, cycles, readiness, environment, protected deployment
  context, Directory, service membership, descendants, metrics and endpoint
  highlights; and
- navigable raw-gateway links between published members and direct relatives.

Those facts define the truthful starting point. In particular:

- a configured Replica is not a synchronized or read-ready data replica;
- a green root card is not a load-balancer health decision;
- placement scale-out reaches only roots installed with the same fresh Fleet;
- Skynet does not add roots to a live Fleet;
- descendant creation remains explicitly authorized and bounded; and
- the console does not make controller-only state public.

## Non-Negotiable Principles

### 1. Ordinary application composition

Skynet exercises ordinary Canic configuration, Components, Fleet services,
scaling, sharding, metrics, endpoints and operator workflows. No Skynet-only
runtime hook, Registry field, lifecycle bypass or infrastructure role is
permitted.

### 2. Evidence-labelled presentation

Every visible value belongs to exactly one evidence class:

| Class | Meaning |
| --- | --- |
| Observed | Read from current Canister, runtime, Directory or metric state. |
| Configured | Compiled from checked-in application or protected Fleet input. |
| Derived | Deterministically calculated from identified observed/configured inputs. |
| Planned | Accepted policy or operation which has not committed its effect. |
| Simulated | Explicitly inert fictional or failure-injection presentation. |
| Unavailable | Not exposed, not authorized, not implemented or not currently reachable. |

The UI must not present Configured as Observed, Replica as read-ready,
Simulated as live, or Unavailable as healthy. JSON must preserve the same
distinction if the richer model is implemented.

### 3. One presentation owner

Shared presentation models, escaping, HTTP routing, JSON serialization and
HTML rendering stay centralized in `skynet_console`. Role Canisters supply
only bounded sanitized observations. A role must not fork the page template or
reimplement common projection logic.

### 4. Existing authorities remain authoritative

The Fleet Coordinator, Fleet Registry, Fleet Subnet Roots, Component
Registries, Component runtime status and application-owned state retain their
existing authority. A browser graph, cached observation or Skynet summary is a
view and never becomes another topology, lifecycle, funding or data authority.

### 5. Public observation is passive

The public console and JSON resource remain read-only. Any future mutation:

- uses an existing or separately approved authenticated Canic endpoint;
- shows the exact target, authority, cost and bounded effect before execution;
- never infers permission from possession of the console URL; and
- records and reuses the required durable operation identity.

### 6. Cost remains operator-bounded

Spanning additional Subnets creates real infrastructure, storage and cycles
cost. A dramatic visual is never authority to choose a network, create a root,
spend ICP, mint cycles, scale a Component or retain paid storage.

### 7. Fiction never becomes a harmful capability

T-800, neural net, swarm, Judgment Day and time-travel terminology may label
inert application nodes, graphs, simulations and recovery demonstrations.
They must not conceal or normalize code for real-world targeting, weapons,
injury, surveillance of people or physical autonomous attack.

### 8. Every Skynet Canister is eventually repurposed

Every Canister created for the Skynet Fleet must have a durable path to a
useful post-demo role in a real application such as Toko. No Canister is
permanently branded, reserved or abandoned merely because it once belonged to
Skynet.

Repurposing means:

- an application Canister is removed from every Skynet placement, service,
  Directory, descendant and operation authority, has its application state
  deliberately erased, and is freshly installed under the exact admitted role
  and authority of its new application;
- a prepaid Canister returns through qualified root-owned asset lifecycle and
  may be claimed for an ordinary admitted workload;
- a Coordinator, Fleet Subnet Root or Wasm Store continues as generic useful
  Fleet infrastructure where its maintained contract permits, or is freshly
  reprovisioned through a separately approved infrastructure lifecycle; and
- every retained cycle balance and Canister Principal is accounted for before
  Skynet teardown is terminal.

Changing a label, role string, Registry row or Wasm without completing those
authority and data-erasure boundaries is not repurposing. Skynet state must
never be adopted implicitly as Toko state, and this invariant grants no
cross-release migration or compatibility exception.

The current 0.101 grouped lifecycle cannot yet satisfy this invariant because
it has no qualified group-removal or application-reprovisioning operation.
Skynet deployment beyond a disposable environment therefore requires an
operator-owned eventual-reuse plan, while implementation waits for the
missing generic lifecycle designs. The proposed
[0.114 Canister-estate design](../0.114-fleet-subnet-canister-estates/0.114-design.md)
owns the physical empty-asset estate and same-Subnet cross-Fleet transfer; it
does not bypass the still-required qualified removal of live Skynet
application authority.

## Target Experience

### Fleet overview

The primary service-node console should eventually show:

- physical Subnet and Fleet-root topology;
- root lifecycle and Directory convergence state when safely observable;
- complete Fleet-service membership with purpose and placement;
- current versus configured placement counts and immutable maxima;
- the eventual post-demo disposition of every known Canister asset;
- root-local estate target, Ready reserve, creation/reset progress and exact
  transfer state when 0.114 exists;
- local descendant trees by scaling/sharding pool;
- cycle reserves, top-up state and relevant funding policy;
- bounded route, latency, byte and outcome observations when 0.106 exists;
- backup/archive posture without backup contents or credentials; and
- explicit unavailable cards for unimplemented replication, failover and
  load-balancing semantics.

### Canister detail

Every role should continue to have a mobile-friendly detail page containing:

- identity, package, Canic and Canister version;
- physical placement and exact parent/root relationships;
- readiness, activation and bootstrap state;
- protected deployment purpose, labels and effective limits;
- direct relatives with navigable links;
- bounded metric samples and representative endpoints; and
- an explanation of which system owns each displayed fact.

### Network activity

After route-aware transport is qualified, the presentation may animate real,
bounded observations such as:

- same-Subnet versus cross-Subnet calls;
- request and response byte classes;
- latency and outcome classes;
- required cycle reserve versus observed consumption; and
- caller, target role and service relationship when safe to disclose.

The demo must not synthesize traffic and label it live. Inert animation is
allowed only under an unmistakable Simulated mode.

### Operations

An authenticated operator view may eventually offer preview-first controls
for maintained operations such as placement scale-out, child creation,
sharding assignment, diagnostics and backup. Public visitors retain a
read-only view. Controller-only endpoints are listed as protected capabilities
rather than invoked from unauthenticated browser code.

## Role Presentation

| Role | Theme | Truthful responsibility |
| --- | --- | --- |
| Fleet Coordinator | Global command authority | Fleet policy, Registry and bounded orchestration authority. |
| Fleet Subnet Root | Defense Grid root | Root-local lifecycle, Registry, Store and pool authority. |
| Wasm Store | Artifact vault | Qualified Wasm availability on one root's Subnet. |
| Skynet node | Neural-net processor | Ordinary application service member and parent of local descendants. |
| T-800 | Infiltration unit | Ordinary bounded scaling child with diagnostics and a harmless ping. |
| Memory cell | Memory core | Ordinary bounded sharding child and partition demonstration. |

Theme names do not alter these roles or grant additional authority.

## Architectural Boundary

```text
authoritative Canic/application state
  Coordinator Registry + Directory + root/runtime state + metrics
                              |
                              | bounded read projections
                              v
                    role-owned snapshot builder
                              |
                              | sanitized presentation model
                              v
                  shared skynet_console renderer
                       |                 |
                       v                 v
                    HTML UI       /api/status.json

host/operator commands -- authenticated maintained APIs --> authorities above
browser public view ---- read-only; never an authority ----^
```

The design should prefer direct existing observations. It must not introduce a
central Skynet database merely to draw the graph. If later high-cardinality
Fleet observation requires aggregation, that capability belongs to an
approved generic Canic design such as Coordinator Workers, not to hidden demo
infrastructure.

## Relationship to Future Design Lines

### 0.101 — Component Groups and Fleet services

Provides the present multi-root topology, protected placements, service
membership, explicit scale-out and dynamic descendants. Skynet should not
claim a supported maximum beyond the finite envelope eventually qualified by
0.101.

### 0.102 — Compact diagnostics

Would let the console show stable compact diagnostic identities while the host
retains rich explanation and remediation. Skynet should consume the maintained
diagnostic view rather than create a second error catalogue.

### 0.106 — Cross-Subnet transport groundwork

Would provide route classification, bounds and measurements for real
Canister-to-Canister calls. It does not supply replication, read routing,
promotion or failover.

### 0.107 — Coordinator Workers

Could partition high-cardinality observation and maintenance work after a
measured need. Workers remain bounded infrastructure executors; they do not
become Skynet application nodes or application-data routers.

### 0.108 — Declarative authentication profiles

Could support provider-neutral login, token reuse and protected operator
actions. Authentication still does not confer resource ownership or
infrastructure authority.

### 0.109 — Standalone blob service

Could retain optional public demo artifacts or exported presentation assets as
an ordinary application service. Skynet does not make blob storage Canic
infrastructure.

### 0.110 — Coordinator-backed root funding

Would make root endurance visible and provide bounded replay-safe routine
funding. The external operator treasury, immutable limits and kill switches
remain authoritative.

### 0.111 — Optional encrypted snapshot archives

Could support a disaster-recovery demonstration in which encrypted remote
archives reconstruct the canonical local restore input. Live Canisters never
gain filesystem, repository or key authority.

### 0.112 — Language-neutral managed guests

Skynet does not depend on Motoko. Canic, IcyDB, infrastructure and the current
Skynet application remain Rust. A future mixed-language guest could appear
only after its own approved production design.

### 0.114 — Fleet Subnet Canister Estates

Would provide the generic fixed-estate, high-throughput refill and same-Subnet
cross-Fleet transfer authority needed to preserve paid Skynet Canisters for a
later ordinary App. Skynet may display its target, state counts, funding,
progress and final transfer receipts. The observatory never becomes the asset
ledger, transfer coordinator or controller of those Canisters.

## Missing Generic Designs Before Autonomous Fleet Operation

The following are intentionally ideas, not 0.113 implementation scope:

1. **Live root expansion:** safely install, admit and activate another Fleet
   Subnet Root after the initial all-root barrier.
2. **Application-data replication:** transfer revisioned state, resume safely,
   expose lag and establish read eligibility.
3. **Health-based routing:** choose among eligible members using explicit
   freshness, health, load and consistency evidence.
4. **Autonomic placement scaling:** translate trusted metrics into bounded
   scale-out or scale-in decisions with budgets, cooldowns, hysteresis,
   approval policy and kill switches.
5. **Fenced promotion and failover:** stop or fence a writer, prove the
   replacement state, promote exactly once and republish authority.
6. **Service replacement and relocation:** drain or replace a failed member
   without reusing identity or confusing Directory authority.
7. **Qualified grouped removal:** reclaim application placements and assets
   only after references, service publication and retry journals are safe.
8. **Live workload-to-estate reclamation:** combine qualified grouped removal
   with 0.114 physical reset and transfer so complete authority detachment,
   state erasure, fresh admission and exact accounting precede installation
   of a former Skynet Canister for Toko or another ordinary application.

Each capability requires a separate bounded design and qualification journey.
Skynet may visualize its absence before then but cannot implement a private
version of it.

## Tentative Milestones

These milestones preserve ordering ideas. They are not approved work.

### M0 — Preserve and qualify the baseline

- complete the remaining 0.101 qualification relevant to the demo;
- measure the supported root/member/Directory envelope;
- keep the current shared renderer and role snapshots DRY; and
- record every live-versus-configured distinction.

### M1 — Observatory completeness

- improve topology navigation and current-node orientation;
- expose configured, observed and effective ceilings distinctly;
- make missing capabilities visible without implying failure;
- add clear data-source labels and freshness timestamps; and
- retain responsive, accessible, dependency-free HTML and bounded JSON.

### M2 — Route-aware network activity

- consume qualified 0.106 route and call measurements;
- present same-Subnet and cross-Subnet activity honestly;
- distinguish reserves, consumption, timeouts and outcomes; and
- keep synthetic animation in a separate Simulated view.

### M3 — Authenticated operator experience

- consume approved 0.108 profiles and client helpers;
- separate visitor, operator and controller-only surfaces;
- show preview, cost, target and authority before effects; and
- preserve durable operation identities and exact retry.

### M4 — Endurance and recovery

- visualize approved 0.110 funding policy, balance classes and kill switches;
- link host-owned backup and restore status without exposing secrets; and
- demonstrate 0.111 reconstruction only after its held implementation is
  approved and qualified.

### M5 — Elastic and resilient Fleet

- begin only after the missing live-root, replication, routing, scaling,
  failover and removal designs are independently accepted;
- exercise their maintained surfaces without Skynet-specific authority;
- use Coordinator Workers only after measured high-cardinality need;
- consume 0.114 estate and transfer receipts without copying their authority;
  and
- qualify a post-demo journey in which every surviving Canister is either
  useful generic Fleet infrastructure or freshly installed for a non-demo
  admitted workload, with no Skynet state or authority surviving.

### M6 — Fictional simulation and history

- allow bounded failure-injection or replay scenarios in explicitly Simulated
  mode;
- represent a decentralized "swarm" only as cooperating software Canisters;
- represent "Judgment Day" only as an inert load/failure scenario; and
- represent "time travel" only as a historical timeline, snapshot recovery or
  deterministic replay metaphor.

M6 never authorizes physical autonomy or harmful action.

## Security and Privacy

The public projection must not expose:

- bearer tokens, credentials, identity password material or key-provider data;
- controllers merely because a visitor can reach a Canister;
- raw protected runtime records or stable-memory contents;
- backup contents, archive keys, repository credentials or plaintext metadata;
- unbounded raw reject messages or provider responses;
- application user data, personal location or targeting data; or
- mutation endpoints disguised as browser navigation.

All observed strings remain escaped before HTML insertion. Every list, label,
metric page and JSON response remains positively bounded. External analytics,
trackers and third-party assets remain absent by default.

The current raw HTTP console is not described as a certified application-data
response. Any future integrity claim requires a maintained certification
design and browser verification path.

## Cost and Scale Presentation

The console should make cost drivers understandable without inventing a price:

- number of roots, Stores, pools, service members and descendants;
- 0.114 owned-estate target, immutable maximum, Ready reserve, state counts,
  creation rate and transfer disposition when available;
- accounted post-demo disposition for every created Canister;
- current cycle balances and configured funding thresholds;
- current versus maximum placement and descendant counts;
- cross-Subnet call reserve and observed usage when available;
- snapshot/archive byte counts and confirmation status when available; and
- disabled or unavailable automation when no enforceable spend authority
  exists.

No local counter can claim to enforce a global provider bill. Monetary and
treasury authority stays with the operator and the relevant approved design.

## UX and Accessibility

- The complete primary status remains useful on a phone without horizontal
  page scrolling.
- Graphs have a table or list equivalent and do not rely on colour alone.
- Authority, Replica, PoolMember, root and child relationships use both text
  and visual treatment.
- Long Principals and hashes wrap or abbreviate with an accessible complete
  value.
- Refresh does not trigger a mutation.
- Simulated mode is visually and textually unmistakable.
- Empty, unauthorized, unavailable and not-yet-observed states are distinct.

## Qualification Ideas

Future implementation should use focused evidence appropriate to each slice:

- native model/HTML/JSON tests for escaping, classification and bounded output;
- build checks for the four Skynet roles against canonical configuration;
- representative PocketIC journeys across at least two physical application
  Subnets rather than pretending a local graph proves 32-Subnet operation;
- exact tests that Replicas never claim readiness, promotion or failover;
- authentication tests for every operator mutation introduced later;
- interruption and exact-retry tests for every external effect; and
- manual mainnet demonstration only under explicit operator network, identity,
  funding and cost control.

No automated test or demo installation should deploy to mainnet implicitly.

## Open Questions

1. Which single public page should be the preferred Fleet entry point without
   making it a new topology authority?
2. Should a browser query several nodes directly, or should it navigate among
   bounded node-local observations?
3. Which protected root and Coordinator facts need a generic sanitized view
   before they can appear publicly?
4. How should observation freshness and partial reachability be represented?
5. What is the measured HTML and JSON response ceiling for the qualified Fleet
   envelope?
6. Which metrics are safe and useful to publish without revealing sensitive
   operational detail?
7. Should an authenticated operator UI remain embedded in each Canister or be
   a separate host/client application?
8. What certification, if any, is required for public observability responses?
9. Which simulations provide educational value without being mistaken for
   production behavior?
10. What independently approved designs and ethical review are required before
    any future use of the word autonomy?
11. Which qualified grouped-removal design feeds terminal empty assets into
    the 0.114 estate protocol without weakening the pre-1.0 reinstall-only and
    no-adoption boundaries?

## Promotion and Deferral Rule

0.113 is expected to be pushed forward while foundational work remains open.
An idea leaves this reservoir only when:

1. it has one concrete user or operator need;
2. its authoritative data and mutation boundaries are known;
3. prerequisite Canic designs are implemented and qualified;
4. its security, cost, failure and interruption semantics are bounded;
5. its creation plan includes a qualified post-demo destination for every
   Canister it may create;
6. its ethical and safety implications have been reviewed; and
7. the maintainer explicitly approves a bounded implementation slice.

Until then, this document preserves direction without creating release scope.
