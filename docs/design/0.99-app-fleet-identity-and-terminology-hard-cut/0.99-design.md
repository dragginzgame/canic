# Canic 0.99 Design: App/Fleet Identity and Terminology Hard Cut

Date: 2026-07-25

## Status

- Status: implemented.
- Release boundary: reinstall only.
- Baseline: `v0.98.24`.
- Scope: App/Fleet identity, canonical network identity, one-Tree runtime
  identity, fresh installation and terminology.
- Compatibility posture: none. A 0.99 Fleet is created from fresh state.

0.99 does not upgrade, import, translate or adopt a pre-0.99 installation.
There is no migration journal, mixed-version mode, legacy decoder, old-state
hash, rollback protocol or compatibility path. Existing deployments are
reinstalled.

## Decision

Canic uses one term for each surviving concept:

| Term | Meaning | Canonical owner |
| --- | --- | --- |
| App | Checked-in source and build identity | `[app].name` |
| Fleet | One installed instance of an App | canonical-network Fleet catalog |
| Environment profile | Operator configuration selecting trust and tooling | `icp.yaml` and CLI selection |
| Canonical network | Trust-derived IC network identity | enrolled root key |
| Subnet slot | App-local logical workload slot | App configuration |
| Subnet | Resolved physical IC Subnet | observed platform placement |
| Canister | Concrete principal inside one Fleet | protected runtime identity |
| Registry | Complete authoritative records within one scope | that scope's declared writer |
| Directory | Derived, read-only consumer projection | Registry projection |
| Placement binding | Keyed application placement | placement authority |

The one-Tree 0.99 Fleet has one Fleet Root. That root owns Fleet-wide facts
only because 0.99 has exactly one Tree. It is not a permanent multi-Tree
Coordinator abstraction.

## Hard-Cut Terminology

The following mappings are destructive replacements:

| Removed concept | Surviving concept |
| --- | --- |
| source `fleet` | App |
| installed `deployment` | Fleet |
| `Prime` configuration slot | `default` |
| current sole-member `prime` root | Fleet Root |
| public topology `Index` | Registry or Directory, according to ownership |
| keyed placement `Directory` | Placement Binding |
| ambient network identity | CanonicalNetworkId |

`default` means the default logical workload slot. It does not mean the
physical Subnet hosting a Fleet-wide authority, or a unique physical Subnet.

Removed names do not survive as aliases, deprecated APIs, duplicate fields,
fallback parsers or compatibility readers.

## Identity Model

### App identity

`AppId` is exactly the validated `[app].name`. Source discovery, packages,
roles, builds and checked-in configuration are App-scoped.

### Fleet identity

`FleetName` is the immutable operator-selected label. `FleetId` is the
generated durable 32-byte identity of one installed Fleet. Two canonical
networks may both contain a Fleet named `local`; complete runtime and
authorization identity is therefore:

~~~text
FleetKey {
    canonical_network_id: CanonicalNetworkId,
    fleet_id: FleetId,
}
~~~

The installed Fleet catalog maps `FleetName` to `FleetId` and stores the
explicit App binding. Equal App and Fleet display names imply nothing.

The spelling convention is:

| Serialized/member spelling | Domain type | Meaning |
| --- | --- | --- |
| `canonical_network_id` | `CanonicalNetworkId` | trust-derived canonical network identity |
| `fleet_name` | `FleetName` | operator-selected immutable label |
| `fleet_id` | `FleetId` | generated immutable identity of one Fleet |
| `fleet` where an exact key is required | `FleetKey` | canonical network plus `FleetId` |

Snake-case fields and PascalCase Rust types are two spellings of the same
concept, not additional identity kinds. Code must not use `fleet_name`,
`FleetId` and `FleetKey` interchangeably: a name selects a catalog entry, an
ID identifies the Fleet within its canonical network and the key carries the
complete network-qualified identity used by runtime and authorization.
`FleetKey` serializes exactly `canonical_network_id` and `fleet_id`; the
ambiguous member name `network` is removed without an alias or legacy decoder.

### Canonical network identity

An environment profile resolves trust material. The enrolled root key
determines `CanonicalNetworkId`; the profile name is not network identity.
Several profiles may resolve to the same canonical network and therefore the
same Fleet namespace.

Public-IC staging and production profiles may intentionally converge on one
canonical network. Non-public trust is explicitly enrolled before Fleet
creation. Root-key paths reject symlinks and special files and are revalidated
when read.

### Runtime identity

Every managed Canister stores one immutable protected binding containing:

- canonical network identity;
- Fleet identity;
- App identity;
- its principal and role;
- its logical subnet slot;
- the Fleet Root principal; and
- the release-build identity required by activation.

No operation infers these facts from ambient CLI state, a role name or a
display-name match.

Delegated-auth audiences bind to the exact `FleetKey`.

## Release Evidence

Release evidence has two non-circular identities:

1. `ReleaseBuildId` is fixed before Wasm compilation and embedded in every
   qualified Wasm.
2. The host calculates the release-set manifest digest afterward from the
   exact final artifact hashes.

A Canister verifies its embedded build identity against installation input.
The host verifies the complete final release set. No Wasm embeds a digest
whose own value depends on that Wasm's final bytes.

## Configuration

The minimum source contract is:

~~~toml
[app]
name = "example"

[services.fleet]
roles = ["root", "user_shard"]

[subnets.default]
root = "root"
~~~

Rules:

- `[app].name` is required.
- Fleet identity never appears in checked-in App configuration.
- `subnets.default` is a logical slot, not a physical-network selector.
- Fleet service roles are declarations only in 0.99; they do not establish a
  future Coordinator-owned service lifecycle.
- Removed keys and spellings fail parsing rather than being translated.

## Fresh Installation

The sole installation mutation is:

~~~text
canic install <app> <fleet>
~~~

The host:

1. resolves the App and selected environment profile;
2. resolves the profile to one canonical network;
3. builds and finalizes exact release evidence;
4. creates one Fleet-scoped activation journal before external mutation;
5. creates and installs the Fleet Root in `Prepared`;
6. prepares the exact bounded child inventory;
7. activates children before the root;
8. verifies complete `Active` evidence; and
9. publishes the Fleet catalog row only after activation is complete.

The journal is the single host recovery authority for this fresh installation.
Exact retries resume it. Identity conflicts, competing active journals,
contradictory observations and mismatched module evidence fail closed.

The catalog is not a progress log. An installed Fleet row appears only after
terminal activation and is the sole live host authority for Fleet resolution.

## Prepared Runtime Fence

Every managed Canister is installed in `Prepared`.

While prepared:

- ordinary managed query and update endpoints reject before access-policy
  evaluation;
- only the exact authenticated installation-control surfaces needed to accept
  protected cascade/credential evidence, report activation status and activate
  are available;
- timers, runtime services, bootstrap and application hooks do not start; and
- raw CDK query/update exports are forbidden in qualified managed packages.

The root activates every prepared child first and itself last. Activation
requires the exact protected identity, cascade evidence and Fleet credential
generation for the journalled operation.

The endpoint fence applies to Canic-managed endpoints. Qualification rejects
application endpoints that bypass the maintained endpoint macros.

## Subnet Registry, Directory and Cascade

The Fleet Root owns the complete Tree-local `SubnetRegistry`. 0.99 has no
multi-Tree `FleetRegistry`. Other Canisters receive consumer-shaped
`FleetDirectory` and `SubnetDirectory` projections carrying exact Fleet,
source-root and revision provenance.

Cascade rules:

- validate raw size before Candid decoding;
- validate complete structural and semantic state before mutation;
- accept one exact local state transition atomically;
- persist accepted local state before downstream fanout;
- retain that state if downstream transport fails; and
- make exact retry heal incomplete fanout even when the root command was
  already applied.

The raw ingress and inter-Canister cascade limit is 16,384 bytes. There is one
transport, one revision authority and no compatibility payload.

Placement Binding remains separate from Registry/Directory topology.

## Authority Map

| Concern | Sole owner |
| --- | --- |
| App source identity | App configuration |
| canonical network identity | enrolled trust/root key |
| installed Fleet identity | canonical-network Fleet catalog |
| release-set truth | finalized host manifest |
| fresh-install progress | Fleet activation journal |
| protected Canister identity | runtime activation record |
| one-Tree authoritative topology | Fleet Root's `SubnetRegistry` |
| consumer topology | provenance-bound Directory |
| keyed application placement | Placement Binding authority |
| delegated-auth audience | protected FleetKey |

No status document, CLI cache, role name, environment-profile name or
Directory projection competes with these owners.

## CLI and Host Boundary

The maintained command surface distinguishes source Apps from installed
Fleets:

- App commands discover, inspect, scaffold and build source.
- Fleet commands resolve through the canonical-network Fleet catalog.
- `install` is the only installation mutation.
- `deploy` retains passive plan/check/inspect evidence only.
- status reports Apps and Fleets in separate tables.
- runtime inspection and Medic select Fleets explicitly.

The semantic inventory records every retained, renamed, moved and deleted
command. Deleted command families have no parser, host API, report-only DTO or
active-document residue.

## Lifecycle Boundary

`canic::start!` remains thin. Lifecycle adapters synchronously restore Canic
invariants, then schedule asynchronous runtime and application work.
Application hooks run after activation through zero-delay timers and must be
idempotent.

## Scope

0.99 includes:

- App/Fleet terminology and identity;
- canonical network enrollment and lookup;
- non-circular release identity;
- minimum current configuration;
- fresh Fleet installation and recovery;
- immutable protected runtime identity;
- the Prepared activation fence;
- one-Tree `SubnetRegistry`/Directory propagation;
- Fleet-scoped delegated-auth identity; and
- recursive CLI authority cleanup.

0.99 excludes:

- importing or upgrading a 0.98 installation;
- host-path or stable-state migration;
- mixed-version operation;
- multi-Tree Fleet coordination;
- Fleet-wide service publication;
- service adoption;
- application routing and data replication; and
- compatibility aliases, shims or fallback readers.

## Implementation Sequence

1. Freeze the semantic and command inventories.
2. Hard-cut configuration and source identity to App.
3. Hard-cut live installed identity to Fleet.
4. Establish canonical network and release-build identity.
5. Implement one fresh-install journal and terminal Fleet catalog.
6. Establish protected Prepared/Active runtime identity.
7. Complete one-Tree Directory cascade and retry semantics.
8. Remove obsolete command and public report families.
9. Prove stale terminology and competing authority are absent.

## Required Validation

Validation must prove:

- removed configuration and command forms reject;
- App and Fleet names remain independent;
- profiles resolving to one trust root share one canonical network namespace;
- invalid, symlinked and special root-key inputs fail before enrollment writes;
- release-build identity is stable and non-circular;
- restart resumes one exact fresh-install journal;
- uncertain create/install/activate outcomes reconcile before replay;
- no Fleet catalog row appears before complete Active evidence;
- Prepared blocks every managed application endpoint and runtime service;
- children activate before the root;
- exact cascade retry repairs incomplete fanout;
- malformed, contradictory and oversized cascade input fails before mutation;
- delegated-auth material for another Fleet is rejected; and
- current CLI help, JSON, examples and documentation use one surviving term.

Focused PocketIC tests cover Canister creation, installation, activation,
inter-Canister calls and interruption. Host tests cover journal durability,
artifact identity, catalog publication and command behavior.

## Completion Criteria

0.99 is complete when:

1. every active surface uses App for source and Fleet for installed identity;
2. one canonical owner exists for network, Fleet, release, activation and
   topology truth;
3. fresh reinstall is the only cross-release path;
4. every managed Canister is immutably Fleet-bound before becoming Active;
5. no partial installation is published as an installed Fleet;
6. one-Tree cascade is bounded, fail-closed and convergent;
7. deleted terminology, commands, DTOs and report stacks are absent; and
8. no migration, compatibility or mixed-version path survives.

## Follow-On Releases

0.100 starts from a new installation. It creates a Fleet Coordinator and an
empty Fleet Registry, then installs fresh Fleet Subnet Roots with flat
root-owned Components. It does not extract, transfer or fence 0.99 authority.

0.101 also starts from a new installation. It flattens composable Component
Groups, provisions stable packed-or-spread placements through selected roots
and publishes each Fleet service's complete typed same-Spec member set:
Authority plus Replicas or an `ActivePool` of PoolMembers. It does not adopt
preserved service Canisters from 0.99 or 0.100.
