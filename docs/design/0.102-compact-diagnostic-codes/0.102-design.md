# Canic 0.102 Design: Compact Diagnostic Codes

Date: 2026-08-13

## Status

- Status: Register, Map and the atomic Cut are complete in the untagged
  `0.102.2` draft. The exhaustive B1 producer, dynamic-public-context,
  durable-state and Wasm evidence remains archived conversion evidence. The
  unreleased 991-row condition-plus-handling allocation was rejected and
  replaced by the reviewed 161-reason semantic register.
- Preservation posture: retain the distinct raw/registered types, host-only
  catalogue, CLI lookup and finite typed producer work. Existing numeric
  assignments are unreleased and may be replaced freely.
- Release boundary: reinstall only. A 0.102 installation starts from fresh
  current-schema state. 0.102 is not rolling-compatible with any pre-0.102
  Canic release.
- Scope: Canic public errors, internal diagnostic identity, host and CLI
  rendering, and diagnostic-derived durable state.
- Sequence: this is the 0.102 design line. It follows the
  [0.99 identity and terminology hard cut](../archive/0.99-app-fleet-identity-and-terminology-hard-cut/0.99-design.md) and
  [0.100 multi-subnet design](../0.100-multi-subnet-fleet-coordinator-and-registry-synchronization/0.100-design.md), but has no
  semantic dependency on multi-subnet synchronization. The intervening 0.101
  line is reserved for fresh Fleet-authoritative service provisioning and
  Directory publication.
- Compatibility posture: pre-1.0 hard cut. The current error contract is
  replaced atomically; there is no parallel error generation, alias, shim,
  fallback decoder or old message field.
- Protocol posture: there is one current diagnostic protocol. Types and fields
  must not use `V1`, `V2`, `version`, `schema_version` or equivalent
  generation names.
- Footprint posture: the wire carries only one `nat16` code. Host-only catalog
  data recovers origin and meaning; a masked failure retains a separate
  operator-visible numeric internal code.
- Composition posture: released codes identify shared canonical causes, not
  handling, exposure, remediation, producer sites, source lines, modules or
  message variants. Those orthogonal dimensions remain typed host or operation
  context and must not multiply the reason-code space.
- Repository scope: Canic only. Required downstream source changes are documented,
  not implemented in sibling repositories.
- Measurement posture: the design is motivated by a credible Wasm-retention
  problem, but implementation must establish a fresh Canic baseline before
  claiming a size win.

## Decision

Canic will hard-cut its public and internal error machinery to use compact,
numeric diagnostic identities in canister-reachable code. Rich labels,
messages and remediation text will live in host-only code.

Every Canic-owned canister participating in one Fleet installation must be
installed from one admitted release set before that Fleet is activated. The
existing release-set identity and activation machinery enforce this boundary;
0.102 adds no diagnostic protocol-version field. Host, CLI and Canic-owned
callers must use the matching source surface, and external callers must
regenerate bindings, before the Fleet becomes available. Mixed pre-0.102 and
0.102 canister operation is forbidden rather than decoded compatibly.

The public Candid error becomes:

~~~rust
pub struct Error {
    code: u16,
}
~~~

This directly replaces the current public shape:

~~~rust
pub struct Error {
    pub code: ErrorCode,
    pub message: String,
}
~~~

The current Candid `ErrorCode` variant and `message : text` field are removed.
Every maintained endpoint returns the new numeric record immediately. No
endpoint, decoder or release may support both shapes.

Canister code retains typed errors where policy or workflow decisions require
them, but a failure that needs a stable boundary or operator identity maps to
one compact numeric reason. The allocation unit is the canonical semantic
cause, not its producer site or the behavior a caller, machine or operator may
apply in one particular operation. Equivalent causes share one registered code
across modules, roles and handling contexts.

Formatting that identity inside a canister is compact and numeric. The host
catalog recovers the reason's label, semantic domain and general safe guidance.
Broad class, exact retry disposition, remediation, exposure, machine decision
and source owner remain host-only or typed operation context and are recovered
from the endpoint, operation, receipt or status that observed the reason. A
reason code alone never grants retry or mutation authority.

The goal is not to remove every string from Canic Wasm. It is to remove static
diagnostic prose, enum-label formatting and redundant failure text while
preserving strings that are part of a real protocol, cryptographic domain,
metric, application log or operator-owned data contract.

## Why 0.102

The current public error contract carries both a Candid variant label and an
owned message. Internally, `InternalError` carries another owned message,
supports appended string context and often receives errors through
`to_string()`. Separately, many canister-reachable error enums derive prose-rich
`thiserror::Error` and `Debug` implementations.

That shape has four costs:

1. Static error messages and formatting fragments can be retained in every
   Wasm role that reaches their constructors.
2. Variant names can be retained through derived `Debug`, Candid schema and
   formatting code.
3. The public `message` encourages callers and tests to depend on prose even
   though prose is not a stable machine contract.
4. Error context is flattened to strings, losing the typed identity needed for
   reliable automation and host-side rendering.

A sibling implementation, IcyDB, has shown that compact numeric public errors,
numeric debug formatting and host-owned rendering can remove meaningful Wasm
weight. Its individual cuts ranged from low single-digit KiB to roughly
20–27 KiB of raw Wasm per affected canister, with about 47.5 KiB cumulative in
one compacting sequence. Those measurements demonstrate feasibility, not an
expected Canic result: the linked code, profiles, error fan-out and baseline
are different.

The decision is therefore architectural first and size-sensitive second:

- numeric diagnostics are a better machine contract;
- host-owned prose prevents canister presentation concerns from spreading
  through runtime crates; and
- the implementation proceeds in measured slices so the actual Canic result
  is known.

## Goals

0.102 must:

1. Establish one stable numeric identity for every maintained diagnostic cause
   family that requires a public, operator-visible or durable identity, and
   exhaustively map all current producer sites onto that shared set.
2. Remove public diagnostic text and Candid error variant labels from canister
   error responses.
3. Make internal diagnostic propagation code-first rather than string-first.
4. Keep rich labels, summaries and remediation guidance in host-only code.
5. Preserve typed distinctions needed by policy, workflow and automation.
6. Keep unknown future codes observable as their lossless raw number without
   inventing fallback behavior.
7. Change diagnostic-derived durable strings only when this hard cut directly
   disturbs them and stable-state safety is proved.
8. Measure raw Wasm, gzip Wasm and retained sections before and after each
   material slice.
9. Leave no dual protocol or pre-1.0 compatibility layer.
10. Produce an explicit downstream source-change guide for the one current
    contract.

## Non-Goals

0.102 does not:

- strip all strings from Canic Wasm;
- replace application logs with numeric codes;
- remove IC method names, Candid field names, role names, metric labels or
  cryptographic domain-separation strings;
- define an application-wide localization framework;
- make a generic structured payload for arbitrary error details;
- add telemetry transport or a remote diagnostic catalog;
- preserve callers that match the current Candid `ErrorCode` variant;
- preserve callers that read or parse `Error.message`;
- recover codes by matching historical error text;
- redesign successful endpoint responses;
- change authentication boundaries; or
- modify downstream repositories.

## Naming and Versioning

The maintained runtime vocabulary is deliberately small:

- `DiagnosticCode`: any lossless numeric value observed by decoding;
- `RegisteredDiagnosticCode`: a Canic-owned semantic reason that runtime code
  may originate;
- `Error`: the public Rust/Candid record containing only the raw number; and
- `InternalError`: an exact registered reason plus its safe public reason.

The host catalogue maps a registered number to name, origin, summary and
optional universally safe guidance. Existing typed domain and operation state
continues to own retry, reconciliation and policy decisions. 0.102 introduces
no generic diagnostic class, disposition or handling framework.

There is no `DiagnosticV1`, `ErrorV2`, `LegacyError`, `schema_version` or
versioned endpoint. The 0.102 number identifies this Canic design line; it is
not part of the runtime protocol.

Code numbers are identities, not protocol generations. Unreleased allocations
may be changed freely. Once a reason appears in a released Canic version, its
`code + name` pair is its immutable semantic identity: neither member may be
rebound to another cause. Summary and guidance may change, origin may change
after review, and `retired` may move from `false` to `true`. Removing a released
reason leaves one minimal `retired = true` row in `reasons.toml`; retirement is
not a separate runtime subsystem.

The unreleased 991-row candidate never crossed that release boundary.
Recompression replaces or deletes it without creating retired history.

No range is reserved speculatively. Allocate codes only for reason families
with a current qualifying producer or for a reason introduced in the same
coherent implementation slice. Adding another producer or handling context for
an existing reason reuses its registered code and does not allocate another
number.

## Public Error Contract

The Candid wire shape is exactly:

~~~candid
type Error = record {
  code : nat16;
};
~~~

The corresponding Rust field remains a plain numeric wire value, but the Rust
field is private. Public decoding exposes a lossless raw identity without
granting producer authority.

### Field Semantics

`code` is the complete public reason identity. It must be specific enough for
the host catalog to recover:

- the canonical cause family and semantic domain;
- the symbolic label;
- the operator summary; and
- optional general guidance that is safe in every context represented by the
  reason.

The code does not carry a broad class, exact retry disposition, remediation
recipe, security exposure, producer role or machine decision. Those properties
may vary without changing what failed. A host combines the reason catalogue
with the endpoint, operation, receipt or status context. If an exact handling
decision must cross a boundary, its owner is an endpoint-specific typed result,
view, receipt or status field rather than another diagnostic code.

The raw code does not promise to identify one physical source function. A
shared code may have several current producer owners. Exact source attribution,
when needed, comes from the command, endpoint, operation, receipt or status
context rather than another wire field or another code.

Origin is not duplicated on the wire because a known code recovers it from the
reason catalog. Class is omitted for a different reason: it is consumer-owned
context, not a property recovered from a raw reason. Handling is not bit-packed
into the code. If a later reviewed contract truly requires independent reason
and handling values on the wire, it must use explicit named fields; that is
outside 0.102 and cannot be smuggled into the numeric allocation.

An unknown code remains observable as its raw `u16`, but its origin cannot be
guessed. Diagnosis requires a host catalog from the same maintained Canic
surface. Canic does not add version negotiation, reserved numeric ranges or
fallback metadata to make an unknown code self-describing.

### Public Rust Surface

`canic::Error` remains the facade return type so endpoints do not acquire a
replacement-generation name. The private field changes in place. Runtime
producers construct it only through `Error::from_registered(...)`. There is no
public `Error::from_raw(...)` or conversion from `DiagnosticCode` to `Error` or
`RegisteredDiagnosticCode`.

Raw initialization is private to the one `Error` decoding implementation used
at Candid and host boundaries. Transparent forwarding passes that already
decoded value unchanged; it does not reconstruct an error from its raw code.
Observation paths may inspect the lossless raw identity through:

~~~rust
impl Error {
    pub const fn code(&self) -> DiagnosticCode;
    pub const fn raw_code(&self) -> u16;
}
~~~

There is no accessor or conversion that presents an arbitrary decoded `u16` as
a registered producer identity. `DiagnosticCode::from_raw(...)` is an
observation and lookup operation only; calling it cannot acquire authority to
originate a diagnostic.

The canister-side `Display` and `Debug` forms, if retained, are compact numeric
forms:

~~~text
E123
~~~

The exact punctuation is chosen once and tested. It must not include the Rust
constant name, class label, origin label, summary or remediation prose.

## Diagnostic Registry

`canic-core` owns only the prose-free runtime identity:

- `DiagnosticCode`, a lossless raw numeric identity whose tuple field is
  private and whose `from_raw(u16)` path does not imply registration;
- `RegisteredDiagnosticCode`, a distinct registered reason identity with a private
  field and no public numeric constructor;
- explicit numeric code constants typed as `RegisteredDiagnosticCode`; and
- compact numeric formatting.

One registered constant may be referenced by any number of semantically
equivalent causes observed by different producers or handling contexts. The
central declaration module owns constants, not a parallel constant per
producer or context row.

The declaration owner may be a directory module tree split by canonical
semantic domain; it is one construction authority, not necessarily one large
source file. Every code still has exactly one canonical constant path.
Producer modules import that constant directly and must not introduce local
numeric declarations, renamed aliases or physical-subsystem copies. The split
follows shared cause families, never the current list of producer crates,
roles, endpoints or handling contexts.

Only that central declaration tree may construct a
`RegisteredDiagnosticCode`. Runtime error constructors accept that type, never
raw `u16` or arbitrary `DiagnosticCode`. `Error::from_registered(...)` is the
sole diagnostic-originating boundary and always stores the registered value's
raw number. Only the decoder boundary may initialize an `Error` from untrusted
raw bytes. Observation may construct a `DiagnosticCode`; transparent
forwarding preserves an already decoded `Error` unchanged. Neither path may
construct a registered identity or originate a new `Error` from raw input.

`InternalError` keeps both exact and public identities private. Its public
conversion always reads `public_code`; no conversion may expose `code`
directly. Direct `Error { code: ... }` construction outside the one public-error
boundary module is a compile error. `RegisteredDiagnosticCode(...)` and
numeric producer construction outside the central declaration module are also
compile errors. Rust privacy is the enforcement mechanism.

Production Wasm must not contain:

- a complete iterable code list;
- the exhaustive producer-coverage frontier or a producer-to-code table;
- code-to-class, code-to-origin or code-to-prose metadata tables;
- public exposure tables;
- human-readable labels;
- complete English messages;
- remediation hints;
- formatted invariant prose;
- documentation copied into compiled string constants; or
- a feature-gated rich renderer.

Feature-gating prose inside `canic-core` is rejected because Cargo feature
unification can make host-selected features reachable in canister builds. The
physical crate boundary is the enforcement mechanism.

An illustrative source shape is:

~~~rust
pub const INPUT_CANISTER_ID_MALFORMED: RegisteredDiagnosticCode =
    registered(101);
~~~

The generator may use a local macro to declare numeric constants once. It does
not emit a separate native inventory. A focused drift test compares both
generated outputs directly with `reasons.toml`. The resulting Wasm contains
only constants reached by that role.

### Reason Ledger

`canic-host` owns one checked-in, machine-readable reason ledger at
`crates/canic-host/diagnostics/reasons.toml`. It is the sole accepted source for
numeric allocation and host prose and is absent from canister dependencies and
release Wasm. A small generator produces checked-in runtime constants and the
host catalogue from it. There is no language-neutral registry in 0.102.

Each row contains only what the maintained lookup needs:

- `code`;
- `name`;
- `origin`;
- `summary`;
- optional universally safe `guidance`; and
- `retired`, defaulting to `false`.

Unreleased rows may be regenerated or renumbered. Release validation compares
the ledger with the latest released Canic version and rejects any change to a
released `code + name` identity or any reuse of either member for another
cause. Summary and guidance may change, origin may change after review, and
`retired` may move only from `false` to `true`. Removing a released reason keeps
its row with `retired = true`; removing an unreleased candidate leaves no
history. The generator and a focused drift test keep runtime constants and
host entries in sync. There is no extra canonical-meaning field, fingerprint,
history database, producer frontier or handling table in this ledger.

### Registry Invariants

The registry must prove only the maintained contract:

1. Every active or retired number is nonzero and unique.
2. Every released `code + name` pair is immutable; neither member is rebound
   to another cause.
3. Every qualifying boundary maps its typed failure to one registered reason;
   purely local typed control flow has no global code.
4. Every active reason has one runtime constant and one host catalogue entry.
5. Every public-capable failure has an explicit safe public reason, including a
   local typed failure that maps directly to that reason without registering
   its exact internal identity.
6. Unknown raw numbers remain lossless and printable.
7. No classification depends on strings.
8. The ledger and host prose are absent from release Wasm.

Rust privacy is the primary enforcement: numeric construction of
`RegisteredDiagnosticCode` stays inside its declaration owner and the private
`Error.code` field is initialized only by registered construction or decoding.
Focused tests cover generated drift and boundaries Rust cannot express; 0.102
does not maintain duplicate grep and compile-fail systems for ordinary privacy.

Codes are nonzero and unique. Numbers encode no semantics and no ranges are
reserved. Sequential allocation is a convenience, not an invariant.

## Reason Identity and Orthogonal Handling Composition

The current 20 public `ErrorCode` leaves are too broad to reconstruct useful
operator guidance on their own. `InvalidInput`, `Conflict`, `Unavailable` and
`Internal` are broad classes, not sufficient reason identities. The opposite
extreme is also wrong: a unique number for every combination of cause, class,
disposition, exposure, remediation and projection turns a small reason
vocabulary into a compound policy matrix.

The rejected 991-row candidate demonstrates that multiplication directly:

| Candidate grouping | Distinct rows |
| --- | ---: |
| Canonical condition | 166 |
| Origin plus condition | 167 |
| Origin, condition and class | 348 |
| Origin, condition, class and disposition | 572 |
| Origin, condition, class and public projection | 664 |
| Full proposed tuple | 991 |

The same proposal needed 503 singleton rationales. Those numbers are review
evidence that handling dimensions were encoded into identity; they are not
evidence of 991 irreducible causes.

### Allocation Key

The default allocation key is the canonical cause family. Semantic origin may
qualify it only when the same condition wording would otherwise combine
genuinely different causes. The following properties do not normally split a
reason:

- broad class;
- caller or operator action;
- host disposition or runtime retry behavior;
- security exposure;
- operational remediation;
- public projection;
- machine decision; or
- producer, subsystem, role, endpoint, phase, function or source location.

A proposed split must prove that the meaning of what failed differs, not merely
that one operation handles the same failure differently. Merely preferring a
different summary, action or retry instruction is not a split rationale.
Wrappers, context appenders, transparent conversions and repeated invariant
checks never receive another code.

The host model is one boring catalogue keyed by code: name, origin, summary and
optional universally safe guidance. Existing typed callers continue making
retry, reconciliation and policy decisions from their own domain state. 0.102
defines no generic handling taxonomy. A command that already needs a local
typed retry result may keep it, but it is not registry metadata and does not
allocate another code.

### Qualification Boundary

Not every Rust error variant is entitled to a global permanent number. A typed
local variant receives a registered reason only when at least one of these is
true:

- it crosses the public error boundary;
- it is emitted through a retrievable operator diagnostic;
- it is stored in a durable receipt, status or evidence record; or
- another process is authorized to make a machine decision from that stable
  identity.

Purely local validation and invariant variants may remain finite and typed,
then map to a shared reason at their owning boundary. This preserves code-first
logic without turning every implementation branch into a public-style
vocabulary entry.

### Public Projection

An unsafe exact reason maps at its boundary to a reviewed safe public reason.
Exposure is a projection function, not part of the exact reason key. Several
internal reasons may share one public reason, and one internal reason may be
public as itself. Public projection is explicit at the typed mapping or
`InternalError` construction boundary and exhaustively tested. There is no
central public-projection table.

A sensitive exact failure receives its own `RegisteredDiagnosticCode` only
when that exact identity independently crosses the public, retrievable
operator, durable-evidence or machine-decision qualification boundary. An
existing appropriate operator log, status or receipt may own a masked exact
registered reason. 0.102 does not create a status schema, receipt system,
correlation-ID scheme or lifecycle record solely to make that identity qualify.
Where no suitable owner exists, the exact condition remains local typed state
and maps directly to the reviewed safe public registered reason. The review may
record the missing operator convenience for the owning feature, but it does not
allocate an exact code in anticipation of a future consumer.

### Review Gate

The accepted B1 audit owns an exhaustive host-only producer-coverage frontier;
the Register phase owns a reviewed many-to-one map from those observations to
qualifying cause families.
Every coverage row maps to one reason or to an explicit non-diagnostic
disposition such as transparent propagation, unreachable sediment, local typed
state or owned operational text. The frontier, labels, review-only handling
columns and mapping table never enter release Wasm.

The 166 canonical-condition buckets and 167 origin-qualified buckets are a
mechanical lexical starting partition, not evidence that each bucket is one
cause. Review may accept, rename, merge, split or exclude every bucket. A
bucket must split whenever one cause meaning, one truthful semantic
origin and one summary cannot describe every qualifying producer. Optional
guidance is admitted only when it is safe for every occurrence. Differences in
class, handling, projection, producer or endpoint alone do not justify a split.

The generated first pass currently marks 157 buckets as possible global
reasons and ten as possible local typed groups. Those counts are not an
allocation recommendation. In particular, high-fan-in buckets require
producer-by-producer semantic review and may split into several causes even if
that raises the total. Conversely, equivalent buckets may merge and an
observation with no qualifying boundary receives no global identity.

Count is review evidence, not a correctness mechanism. The complete register
always requires explicit maintainer review; no numeric threshold approves or
rejects it. No cause may be collapsed to meet a target and no cause may survive
merely because it was one of the mechanical buckets.

Conversely, a generic string slot must not be used to avoid allocating a leaf.
The following is intentionally excluded:

~~~rust
pub struct Error {
    pub code: u16,
    pub detail: String,
}
~~~

When a meaningful value such as an operation ID, principal, limit or retry
time must cross a boundary, it belongs in an endpoint-specific typed response,
view, receipt or status record. It is not appended to a generic error message,
and the public cut cannot silently discard it merely because no owner exists
yet.

## Internal Error Model

`InternalError` becomes code-first. Its authoritative state is diagnostic
identity and exposure policy, not a formatted message.

The ordinary registered-projection case is equivalent to this illustrative
shape:

~~~rust
pub struct InternalError {
    code: RegisteredDiagnosticCode,
public_code: RegisteredDiagnosticCode,
}
~~~

The implementation may privately represent the projection as an enum so an
already-decoded remote `Error` can be forwarded unchanged. That forwarding
variant carries the decoded public value itself, is not a registered public
identity and grants no authority to originate a diagnostic from its raw code.
Its local transport failure still has an independently registered exact code.

This pair is used only for public-capable failures whose exact identity already
qualifies for a registered reason: an ordinary public diagnostic stores the
same code in both fields, while a masked registered diagnostic stores its exact
operator code plus a safe public code. A true operator-only diagnostic uses an
operator-owned type with no public conversion and no `public_code`. A local
typed variant has no global exact code; when it reaches a public boundary, its
typed mapping constructs the safe public reason directly without first
creating an `InternalError` for an unregistered exact identity. This keeps
public projection total where it applies without registering local detail.

The final names may follow existing model conventions, but the invariants are
fixed:

- there is no owned `message: String`;
- there is no optional complete public `Error`;
- public projection is deterministic and typed;
- conversion to public `Error` always reads `public_code`, never `code`;
- sensitive internal identities can map to a safe public leaf;
- the internal code remains available for numeric operator diagnostics when a
  public projection masks it;
- class and origin are not stored in the runtime error; and
- formatting is never used to recover identity.

### Conversion Rules

Conversions from typed internal errors must match typed variants or fields.
They must not call `to_string()` and then classify the result.

`with_diagnostic_context` is removed. A caller that currently appends prose
must do one of the following:

1. preserve the primary diagnostic unchanged;
2. map it to a more specific registered leaf;
3. retain a typed secondary cause for internal control flow; or
4. write dynamic context to an approved structured status or log owner.

There is no generic vector of causes on the public wire and no recursively
nested diagnostic tree. Those shapes would add protocol and allocation cost
without a demonstrated consumer.

### Retained Typed Errors

This design does not flatten every internal error enum into `u16`.

Typed variants remain appropriate where code makes a decision such as:

- retry versus stop;
- absent versus forbidden;
- stale versus expired;
- conflict versus invariant failure; or
- recoverable platform rejection versus corrupt state.

At the layer boundary, those variants map exhaustively to compact diagnostics.
Derived `thiserror::Error` or `Debug` prose is removed when it remains
canister-reachable solely for formatting. Manual numeric formatting is used
where a formatting trait is actually required.

## Public Exposure and Security

Not every internal diagnostic is safe to expose.

Every failure belongs to exactly one exposure category at its owning boundary:

1. **Public as-is.** The exact registered reason is also the public reason.
2. **Masked internal.** The exact registered reason is operator-visible and
   the public-capable error stores a deterministic safe public reason.
3. **Operator-only.** The reason has stable numeric operator evidence but its
   type is mechanically non-convertible to public `Error`. If a later boundary
   needs public conversion, that occurrence must become an explicitly reviewed
   masked-internal mapping.
4. **Local typed failure.** Finite typed control-flow state has no global exact
   reason code. It may map directly to a safe public registered reason at a
   public boundary; its exact identity is registered only if that identity
   independently gains a qualifying consumer.

Projection must not leak:

- secret or authentication material;
- cryptographic intermediate values;
- private topology;
- stable-state contents;
- raw platform reject text;
- file or build paths; or
- implementation details that weaken authorization boundaries.

Authentication remains enforced at endpoints. Workflow and ops continue to
assume authenticated input. Compact diagnostics do not replace those
boundaries.

A mapped public diagnostic exposes only the safe public code. The host catalog
reports the safe code's public origin and does not reveal the sensitive
internal origin by accident.

When a registered internal reason and its public reason differ, the
implementation uses an existing appropriate operator log, status or receipt
for the exact number. It must not invent a new status schema, operation record,
correlation protocol or durable observation store solely for diagnostics. If
no suitable exact owner exists, the exact failure remains local typed state and
the caller receives the reviewed safe public registered reason directly.

The internal observability value is the numeric code, not diagnostic prose.

## Host-Owned Rendering

`canic-host` owns the rich diagnostic catalog. This crate is already shared by
host/operator surfaces and is not linked into canister Wasm.

Every current registered code maps to:

- a stable symbolic label for logs and presentation;
- a concise operator-facing summary;
- optional general guidance that is safe for every occurrence of the reason;
- its semantic origin;
- optional documentation metadata.

Runtime policy still uses its owning typed error and operation state; it does
not perform a canister-side catalog lookup or recover behavior from a reason
number. Labels are presentation-only and must never be matched for automation.
0.102 adds no generic class, disposition, action or remediation model.

This includes internal codes written to approved operator diagnostics, not only
codes returned publicly. An origin names the narrowest stable semantic domain
that makes the failure actionable, such as delegated authentication or Wasm
publication. It is not automatically the module that produced the failure.
Normal command rendering uses its own endpoint or operation context when it
already has one. A raw-code lookup renders only catalogue metadata and
universally safe guidance.

An illustrative entry is:

~~~rust
DiagnosticEntry {
    code: INPUT_CANISTER_ID_MALFORMED,
    label: "INPUT_CANISTER_ID_MALFORMED",
    summary: "The canister ID is malformed.",
    guidance: Some("Check the principal supplied by the caller."),
}
~~~

The concrete wording is written during the inventory slice. The example does
not allocate that code or mandate that message.

The central host response decoder renders known codes automatically. A normal
CLI command therefore remains useful to a human even though the canister sent
only one numeric field.

Retired and unknown codes render losslessly and distinctly:

~~~text
E1199 (retired diagnostic: FORMER_SYMBOLIC_IDENTITY)
E65000 (unknown diagnostic)
~~~

The host must not fail decoding, relabel an unknown code as a known error or
infer its origin or retry behavior.

### CLI Lookup

0.102 adds one current lookup surface:

~~~text
canic diagnostic E123
canic diagnostic 123
~~~

It prints the numeric identity, name, origin, summary and any universally safe
guidance. A raw lookup never invents retry or mutation advice. Released retired
rows and unknown numbers remain distinguishable using existing CLI output
conventions.

### Deferred Non-Rust Registry

0.102 does not generate a checked-in JSON or Markdown registry. A
language-neutral projection may be added later when a concrete maintained
non-Rust consumer requires symbolic diagnostic constants.

## Dynamic and External Text

Static diagnostic prose and dynamic operational data are different ownership
classes.

### Static Prose

Static summaries, labels and hints move to the host catalog. They must not be
duplicated in runtime crates for convenience.

### Dynamic Context

Dynamic context remains only when an explicit owner needs it:

- typed IDs and values remain in typed response or status fields;
- application and operator logs may retain bounded messages;
- external platform rejection text may be retained in an approved diagnostic
  log or status record when it is operationally necessary; and
- no decision may depend on parsing that text.

Raw reject text must not be copied into the compact public `Error`. A public
caller receives only the registered code.

The accepted B1 audit identifies every dynamic value currently interpolated
into a public `Error.message`, including operation IDs, generations, limits,
retry times, principals and conflicting authority. Before removing a message,
the owning conversion must establish whether each value is caller-derivable,
sensitive operator data or already owned by a typed response, view, receipt or
status.

Correctness-, recovery- or caller-required data must not disappear. If the
removed message is its only owner, the cut first adds the smallest
endpoint-specific typed response, view, receipt or status field needed to carry
it. This does not authorize a generic diagnostics or operation-status
subsystem.

Operator convenience or context that does not affect correctness, recovery or
caller continuation may be intentionally dropped when retaining it would
require new infrastructure. The conversion audit records that decision. An
independently meaningful existing owner remains unchanged.

### Strings Explicitly Outside This Cut

The following do not become numeric diagnostics merely because they are
strings:

- user and application log messages;
- Candid method and record-field names;
- metric names and label values;
- role, App, Fleet and Subnet identities;
- cryptographic suite names and domain-separation constants;
- configuration paths and user-provided configuration values;
- HTTP content and headers;
- certified data inputs; and
- protocol strings required by the IC or another current external contract.

Any later proposal to compact one of these owners needs its own evidence and
contract analysis.

## Durable-State Boundary

Only durable fields directly disturbed by removal of the existing diagnostic
string representation are in scope. If a field such as `last_error: String`
has independent operator, recovery or lifecycle meaning, 0.102 leaves it
unchanged. General logs and historical durable-error cleanup are not part of
this release.

A directly affected field loses its prose only when a typed reason is already
authoritative and current behavior remains unchanged. Otherwise the bounded
text stays with its existing owner and any broader redesign is recorded for a
later design line. 0.102 does not introduce a new durable error taxonomy or
lifecycle state machine.

### Current Stable-State Boundary

0.102 installs only the current stable shape. No pre-0.102 stable bytes are
decoded, translated or migrated.

For every stable record actually changed, implementation proves its current
encoding and lifecycle behavior and that no decision depends on matching
diagnostic text.

There is no old reader, dual-written field, fallback parser, one-time
migration or text-to-code conversion.

## Candid and Generated Surface Cut

The public cut must update every owned schema and generated surface in one
coherent slice:

- canonical `.did` files;
- generated facade endpoint signatures;
- checked-in test and example declarations;
- host response decoding;
- CLI rendering;
- canic-testing helpers; and
- Canic-owned downstream fixtures.

The old `ErrorCode` Candid variant is deleted, not deprecated. The old
`message` field is deleted, not left empty.

An intermediate local commit may introduce registry plumbing before the
contract cut, but no supported release state may expose dual public shapes or
two diagnostic protocols.

### Fleet-Atomic Activation Boundary

The source and Candid cut is repository-atomic; safe operation is Fleet-atomic.
0.102 is not rolling-compatible with pre-0.102. Before activation, deployment
must prove that the Coordinator, every Fleet Subnet Root, every root-local Wasm
Store and every Canic-owned application canister admitted to that installation
come from one exact release set. The matching host and CLI surface must be in
use, Canic-owned callers must be rebuilt, and external bindings must be
regenerated. Existing release-set identity, installation receipts and
activation gates enforce the boundary. A partially installed Fleet remains
unavailable; it does not make mixed-version calls. No dual decoder, migration
reader or diagnostic protocol-version field is introduced.

## Interaction With 0.99, 0.100 and 0.101

This design uses App, Fleet, canonical-network and Canister identity from
0.99, plus Component Spec, Component instance, Fleet Subnet Root, Component
Registry, Component Directory, Fleet Coordinator and physical-Subnet
placement vocabulary from 0.100. Its diagnostic origins must not reintroduce
0.99 Subnet Slot, Fleet Root, Tree identity or local Subnet
Registry/Directory terms into a 0.100-or-later surface.

0.100 may add new multi-subnet errors. If implemented first, those producers
join the 0.102 coverage inventory and participate in the reviewed many-to-one
map. If 0.102 is implemented first, later 0.100 work reuses every applicable
canonical code and allocates only genuinely new cause families.

0.101 may add Component Group compilation, stable placement identity,
density/spread policy, root provisioning, explicit scale-out and
mode-compatible Fleet-service publication errors. Those producers follow the
same ordering rule: if present before 0.102, they join its inventory; if
implemented later, they reuse applicable canonical codes and allocate only
genuinely new cause families.

No diagnostic schema generation, negotiation or compatibility field is added
for this sequencing. Both designs target the one maintained pre-1.0 surface.

## Implementation Phases

These four phases are the complete conceptual plan. Existing B1/B2 labels may
remain in historical evidence, but they do not introduce more architecture.

### 1. Register

1. Retain the accepted B1 coverage, dynamic-value and Wasm baseline material as
   temporary conversion evidence.
2. Review the 167 mechanical buckets producer by producer and accept, rename,
   merge, split or exclude each one according to semantic cause.
3. Create `reasons.toml`, then generate only the registered runtime constants
   and host catalogue from it.
4. Replace the unreleased 991-row candidate directly. Unreleased allocations
   may change freely and create no retirement history.

### 2. Map

1. Map existing finite typed failures to registered reasons at qualifying
   boundaries.
2. Keep local failures local and transparent wrappers transparent.
3. Select exact and safe public reasons explicitly; never infer identity from
   rendered text.
4. Register a masked exact reason only when an existing operator, durable or
   machine consumer independently qualifies it. Otherwise keep the exact
   failure local and map it directly to the safe public reason; do not add a
   subsystem solely for diagnostics.

### 3. Cut

1. Make `InternalError` code-first.
2. Replace `ErrorCode + message` with `Error { code: u16 }`.
3. Update Rust, Candid, facade, host, CLI and maintained tests atomically.
4. Remove the old types, formatters and string conversions completely.
5. Require one admitted release set and matching callers before Fleet
   activation.

### 4. Clean and Measure

1. Remove dead diagnostic prose and conversions while preserving owned logs,
   protocol text and application data.
2. Change only durable fields directly disturbed by removal of the diagnostic
   string representation. Leave independently meaningful operational or
   recovery text unchanged.
3. Remove the temporary B1 tooling and its allocation authority at closeout;
   archive useful inventory and review evidence as conversion history.
4. Measure representative release Wasm, record the deltas and update the
   active documentation and downstream source-change guidance.

## Measurement Contract

Raw canonical release Wasm is the primary size metric. Builder-produced gzip is
secondary because compression can hide duplicated prose or amplify unrelated
layout changes.

For every measured role and slice, record:

- immutable source identity;
- canonical builder and profile identity;
- raw release Wasm bytes;
- builder-produced gzip bytes;
- data-section bytes;
- function count;
- exported-method count; and
- bounded retained-size evidence for changed hotspots.

The closeout records the final reason count and may retain the B1 tuple counts
as evidence of the rejected allocation mistake. Neither compression ratio nor a
target reason count is an acceptance metric. Semantic cohesion takes priority
over making the registry artificially small.

At minimum, the roster must include:

- one representative leaf role;
- root;
- Wasm store; and
- any role found to have substantially different diagnostic reachability.

The preferred full closeout is a compatible run of
`CANIC-WASM-001`. Role-scoped development measurements may guide a slice but
must not be presented as the retained audit.

### Decision Thresholds

The architecture and public-contract benefits stand independently of size, but
the measured result determines how strongly Wasm savings justify further
low-level compaction:

| Raw release delta | Interpretation |
| --- | --- |
| Less than 5 KiB per affected role | Not worthwhile for size alone; retain only cuts justified by the cleaner contract and ownership model |
| 5–10 KiB | Modest; continue only through low-risk, high-fan-out paths |
| 10–20 KiB per leaf or at least 25 KiB in root | Worthwhile |
| 30–50 KiB in a role | Strong result |

These are review thresholds, not acceptance promises. A slice that increases
Wasm must be explained and either corrected or accepted explicitly for its
contract value.

IcyDB measurements must never be inserted into Canic audit history as if they
were Canic results.

## Testing Strategy

### Registry Tests

- every code is nonzero and unique;
- every released `code + name` identity remains unchanged and neither member
  is rebound to another cause;
- generated runtime constants and the host catalogue match `reasons.toml`;
- retired released reasons have no active producer constant;
- Rust privacy prevents arbitrary decoded values from becoming registered
  producer reasons, with one focused boundary test for raw decoding and
  forwarding; and
- unknown raw values round-trip without panic or guessed metadata.

### Mapping Tests

- typed internal variants map to the intended diagnostic;
- transparent wrappers and context propagation retain the primary code rather
  than allocating another identity;
- masked registered codes project to the intended safe public code and have a
  proven existing exact operator, durable or machine consumer;
- operator-only typed failures have no public conversion, while local typed
  failures have no global exact code and may map directly to a safe public
  registered reason;
- every public conversion reads `public_code`, never the exact internal code;
- no mapping path parses or compares text;
- existing typed retry, reconcile and policy decisions remain typed; and
- dynamic values needed for correctness, recovery or caller continuation
  remain in an existing or smallest endpoint-specific typed owner rather than
  disappearing with the message.

Tests assert typed codes and observable state, not rendered error strings.

### Wire Tests

- Candid `Error` is exactly one `nat16` field;
- `message : text` is absent;
- the Candid `ErrorCode` variant is absent;
- every checked-in `.did` uses the current shape;
- representative facade endpoints decode both success and error results;
- host response and replica-query paths decode the compact record;
- a Fleet cannot activate until every Canic-owned participant belongs to one
  admitted release set; and
- no mixed pre-0.102/0.102 caller path is admitted.

### Host and CLI Tests

- known raw codes render the expected name, origin, summary and optional safe
  guidance;
- retired released codes remain identifiable without an active producer;
- unknown codes retain only their raw code and are not assigned guessed
  metadata;
- lookup accepts the canonical numeric forms; and
- normal command failures automatically use host rendering.

Human-facing host text may be snapshot-tested in the host/CLI owner. Runtime
and domain tests must not assert it.

### Stable-State Tests

For every changed stable record:

- encode the exact current state;
- restore it through the maintained current lifecycle;
- prove authoritative typed failure state and recovery behavior; and
- prove no string matching occurs.

Stable records whose error text has independent operational or recovery
semantics are outside this hard cut and do not require new tests.

### Wasm Tests

- search canonical release Wasm for a bounded set of removed diagnostic
  fragments;
- prove the host catalogue and temporary B1 evidence are not linked into each
  representative role;
- inspect retained sections and functions for the high-fan-out error paths;
- confirm strings intentionally retained by logs or protocols have documented
  owners; and
- record deltas using the measurement contract.

Source scans are discovery aids. Absence from source or presence in source is
not a substitute for artifact measurement.

## Performance and Resource Invariants

- Success paths must not allocate merely to prepare an unused diagnostic.
- Canister code performs no registry lookup to construct a public error.
- Release Wasm contains no reason ledger, host catalogue or temporary B1
  inventory.
- Public error construction allocates no message string.
- Host rendering may allocate because it is outside canister Wasm and occurs
  on error paths.
- No network call is made to resolve a diagnostic code.
- Diagnostic lookup does not read canister stable state.
- Unknown codes remain printable without a catalog search.

## Contract Impact

### Breaking Public Changes

- `canic::Error.code` changes from a Candid enum to `u16`.
- `canic::Error.message` is removed.
- the public Rust and Candid `ErrorCode` enum is removed.
- callers matching named Candid variants must match current numeric codes
  instead.
- callers parsing message text must stop.

### Preserved Behavior

- endpoints continue to return `Result<T, canic::Error>`;
- authentication and authorization remain endpoint-owned;
- host and CLI users continue to receive human-readable diagnostics for known
  codes;
- unknown diagnostics remain visible; and
- typed domain decisions remain typed inside Canic.

### Stable Changes

The public error cut does not itself change stable state. Individual durable
failure fields change only after the durable-state audit identifies their
current typed owner and recovery behavior.

## Downstream Hard-Cut Guide

Canister and Candid callers must:

1. regenerate bindings from the current `.did`;
2. replace named `ErrorCode` matches with numeric code constants;
3. stop reading or parsing `message`; and
4. retain the raw code when logging an unknown diagnostic.

Rust producers should import the current `RegisteredDiagnosticCode` constants;
decoders use `raw_code()` and preserve arbitrary `DiagnosticCode` values.
Non-Rust callers use the numeric values documented for the maintained public
surface. A generated language-neutral registry is deferred until a concrete
maintained consumer requires one. No caller duplicates the host message
catalog in canister code.

CLI users receive rendered prose automatically. A code copied from a canister
log can be resolved with `canic diagnostic`.

Canic-owned examples and fixtures are updated in the atomic public slice.
Downstream repositories receive a source-change report; automated work under this
design does not edit them.

There is no period in which both error shapes are accepted.

## Alternatives Rejected

### Keep `message` Beside a Numeric Code

This preserves the main Wasm-retention source and encourages prose-dependent
callers. It is not a hard cut.

### Carry More Metadata Beside the Code

Origin and handling metadata would be more self-describing under host/catalog
skew, but origin is redundant for a known globally unique code and handling is
not an intrinsic reason property. The extra fields also require canister-side
metadata or repeated constructor arguments. 0.102 chooses the smaller
`{ code }` contract; the host catalogue recovers the origin and existing typed
callers retain their own operational decisions.

### Feature-Gate Rich Messages in `canic-core`

Cargo feature unification makes this boundary fragile. Rich rendering belongs
in a crate that canister artifacts do not link.

### Shorten Existing Messages

Shorter prose may save some bytes but leaves the string-first architecture,
variant formatting and unstable machine contract intact.

### Reuse Only the Current 20 Error Codes

The broad variants cannot reconstruct useful action for many failures. They
are suitable class inputs, not a sufficient leaf taxonomy.

### Allocate One Code Per Inventory Label

The source frontier is intentionally exhaustive and may contain thousands of
  observations. Treating those rows as allocations would confuse coverage with
  runtime identity, retain unnecessary constants and create a permanent catalog
  that cannot be reviewed. Producer rows must first map many-to-one onto shared
  cause families, while handling remains orthogonal context. The 991-row
  candidate is an explicit failed composition result, not implementation
  authority.

### Add a Generic `detail: String`

This recreates the message field under a new name. Required details belong in
typed owner records.

### Add a Versioned Error Type

`ErrorV2`, dual endpoints and version fields are pre-1.0 compatibility
baggage. Canic maintains one current protocol.

### Strip Every Runtime String

Many strings are protocol constants, application data, metrics or logs.
Deleting them would conflate ownership and can break correctness.

### Rewrite Every Error Before Measuring

A blanket rewrite obscures attribution and risks removing operational context
without proving Wasm value. Measured coherent slices preserve evidence.

## Acceptance Criteria

0.102 is complete when:

1. The public Candid error is exactly `{ code : nat16 }`.
2. The old public `ErrorCode` enum and `message` field no longer exist.
3. No supported endpoint or host decoder accepts the old shape.
4. `InternalError` and boundary conversions are code-first and never recover
   identity by parsing text.
5. `DiagnosticCode` remains lossless for arbitrary observed values, while only
   `RegisteredDiagnosticCode` can originate a Canic diagnostic.
6. Every qualifying boundary maps an existing typed failure to one semantic
   reason. Local exact failures remain local and may map directly to a safe
   public registered reason; a masked exact identity is registered only when it
   has an independent qualifying owner.
7. `reasons.toml` generates the registered runtime constants and boring host
   catalogue: code, name, origin, summary and optional guidance.
8. A released `code + name` pair is immutable and neither member is rebound to
   another cause; unreleased allocations remain freely changeable.
9. The CLI renders and looks up known, retired and unknown raw codes without
   guessing operational handling.
10. No correctness-, recovery- or caller-required dynamic value is lost;
    deliberate removal of operator convenience is recorded, and no generic
    status or operation subsystem is added solely for diagnostics.
11. Only durable fields directly disturbed by this hard cut change, and every
    changed record has focused encoding and lifecycle evidence.
12. Release Wasm contains no host catalogue or temporary B1 audit machinery,
    and representative baseline/closeout measurements are recorded.
13. Every activated Fleet uses one admitted release set with matching callers;
    no aliases, compatibility decoders or message fallbacks remain.
