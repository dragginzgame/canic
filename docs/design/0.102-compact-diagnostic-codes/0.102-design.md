# Canic 0.102 Design: Compact Diagnostic Codes

Date: 2026-08-13

## Status

- Status: direction approved; evidence-only Slice A may continue, while
  mutating Slices B-F remain held until the complete Slice A producer-coverage
  frontier, mandatory semantic-compression map, dynamic-public-context and
  durable-state inventories plus the compressed initial allocation ledger,
  host catalog and projection table receive maintainer approval.
- Release boundary: reinstall only. A 0.102 installation starts from fresh
  current-schema state. 0.102 is not rolling-compatible with any pre-0.102
  Canic release.
- Scope: Canic public errors, internal diagnostic identity, host and CLI
  rendering, and diagnostic-derived durable state.
- Sequence: this is the 0.102 design line. It follows the
  [0.99 identity and terminology hard cut](../archive/0.99-app-fleet-identity-and-terminology-hard-cut/0.99-design.md) and
  [0.100 multi-subnet design](../0.100-multi-subnet-fleet-coordinator-and-registry-synchronization/0.100-design.md), but has no
  semantic dependency on multi-subnet synchronization. The intervening 0.101
  line is reserved for fresh Fleet-authoritative service provisioning and
  Directory publication.
- Compatibility posture: pre-1.0 hard cut. The current error contract is
  replaced atomically; there is no parallel error generation, alias, shim,
  fallback decoder or old message field.
- Protocol posture: there is one current diagnostic protocol. Types and fields
  must not use `V1`, `V2`, `version`, `schema_version` or equivalent
  generation names.
- Footprint posture: the wire carries only one `nat16` code. Host-only catalog
  data recovers origin and meaning; a masked failure retains a separate
  operator-visible numeric internal code.
- Composition posture: permanent codes identify shared canonical conditions
  and handling contracts, not producer sites, source lines, modules or message
  variants. Exhaustive producer evidence remains host/repository-only and maps
  many-to-one onto the compact code set.
- Repository scope: Canic only. Required downstream source changes are documented,
  not implemented in sibling repositories.
- Measurement posture: the design is motivated by a credible Wasm-retention
  problem, but implementation must establish a fresh Canic baseline before
  claiming a size win.

## Decision

Canic will hard-cut its public and internal error machinery to use compact,
numeric diagnostic identities in canister-reachable code. Rich labels,
messages and remediation text will live in host-only code.

Every Canic-owned canister participating in one Fleet installation must be
installed from one admitted release set before that Fleet is activated. The
existing release-set identity and activation machinery enforce this boundary;
0.102 adds no diagnostic protocol-version field. Host, CLI and Canic-owned
callers must use the matching source surface, and external callers must
regenerate bindings, before the Fleet becomes available. Mixed pre-0.102 and
0.102 canister operation is forbidden rather than decoded compatibly.

The public Candid error becomes:

~~~rust
pub struct Error {
    code: u16,
}
~~~

This directly replaces the current public shape:

~~~rust
pub struct Error {
    pub code: ErrorCode,
    pub message: String,
}
~~~

The current Candid `ErrorCode` variant and `message : text` field are removed.
Every maintained endpoint returns the new numeric record immediately. No
endpoint, decoder or release may support both shapes.

Canister code retains typed errors where policy or workflow decisions require
them, but every failure that crosses a layer boundary maps to one stable,
composable numeric handling identity. The allocation unit is one canonical
semantic condition plus the behavior a caller, machine or operator must apply,
not the producer site. Equivalent failures share one registered code across
modules and roles. Formatting that identity inside a canister is compact and
numeric. The code identifies its canonical condition, class, semantic domain
and handling contract in the host catalog; exact source
owners remain host-only metadata and, when operationally relevant, are
recovered from the endpoint, operation, receipt or status context.

The goal is not to remove every string from Canic Wasm. It is to remove static
diagnostic prose, enum-label formatting and redundant failure text while
preserving strings that are part of a real protocol, cryptographic domain,
metric, application log or operator-owned data contract.

## Why 0.102

The current public error contract carries both a Candid variant label and an
owned message. Internally, `InternalError` carries another owned message,
supports appended string context and often receives errors through
`to_string()`. Separately, many canister-reachable error enums derive prose-rich
`thiserror::Error` and `Debug` implementations.

That shape has four costs:

1. Static error messages and formatting fragments can be retained in every
   Wasm role that reaches their constructors.
2. Variant names can be retained through derived `Debug`, Candid schema and
   formatting code.
3. The public `message` encourages callers and tests to depend on prose even
   though prose is not a stable machine contract.
4. Error context is flattened to strings, losing the typed identity needed for
   reliable automation and host-side rendering.

A sibling implementation, IcyDB, has shown that compact numeric public errors,
numeric debug formatting and host-owned rendering can remove meaningful Wasm
weight. Its individual cuts ranged from low single-digit KiB to roughly
20–27 KiB of raw Wasm per affected canister, with about 47.5 KiB cumulative in
one compacting sequence. Those measurements demonstrate feasibility, not an
expected Canic result: the linked code, profiles, error fan-out and baseline
are different.

The decision is therefore architectural first and size-sensitive second:

- numeric diagnostics are a better machine contract;
- host-owned prose prevents canister presentation concerns from spreading
  through runtime crates; and
- the implementation proceeds in measured slices so the actual Canic result
  is known.

## Goals

0.102 must:

1. Establish one stable numeric identity for every maintained diagnostic
   canonical-condition and handling contract, and exhaustively map all current
   producer sites onto that shared set.
2. Remove public diagnostic text and Candid error variant labels from canister
   error responses.
3. Make internal diagnostic propagation code-first rather than string-first.
4. Keep rich labels, summaries and remediation guidance in host-only code.
5. Preserve typed distinctions needed by policy, workflow and automation.
6. Keep unknown future codes observable as their lossless raw number without
   inventing fallback behavior.
7. Audit diagnostic-derived durable strings and remove or type them only where
   stable-state safety is proved.
8. Measure raw Wasm, gzip Wasm and retained sections before and after each
   material slice.
9. Leave no dual protocol or pre-1.0 compatibility layer.
10. Produce an explicit downstream source-change guide for the one current
    contract.

## Non-Goals

0.102 does not:

- strip all strings from Canic Wasm;
- replace application logs with numeric codes;
- remove IC method names, Candid field names, role names, metric labels or
  cryptographic domain-separation strings;
- define an application-wide localization framework;
- make a generic structured payload for arbitrary error details;
- add telemetry transport or a remote diagnostic catalog;
- preserve callers that match the current Candid `ErrorCode` variant;
- preserve callers that read or parse `Error.message`;
- recover codes by matching historical error text;
- redesign successful endpoint responses;
- change authentication boundaries; or
- modify downstream repositories.

## Naming and Versioning

The maintained vocabulary is:

- `DiagnosticCode`: a lossless raw decoded numeric identity;
- `RegisteredDiagnosticCode`: a centrally allocated current producer identity;
- `DiagnosticClass`: a host-only broad failure classification;
- `DiagnosticOrigin`: a host-only semantic domain, not a physical-module
  discriminator that forces another code;
- `DiagnosticDisposition`: host-only typed retry/reconcile behavior; and
- `Error`: the public Candid error record.

`DiagnosticClass`, `DiagnosticOrigin` and `DiagnosticDisposition` are native
host catalog types. They are not Candid types, runtime error fields or
canister-side lookup tables.

There is no `DiagnosticV1`, `ErrorV2`, `LegacyError`, `schema_version` or
versioned endpoint. The 0.102 number identifies this Canic design line; it is
not part of the runtime protocol.

Code numbers are identities, not protocol generations. A retired number is
never reassigned to a different meaning. Its runtime constructor and active
catalog entry are removed, while its number, former symbolic identity,
retirement status and last summary remain permanently recorded in the
host/repository-only allocation ledger. A host lookup may render that identity
as retired; only a number that was never allocated is unknown. This is stable
numeric identity, not a decoder for the removed pre-0.102 Candid shape.

No range is reserved speculatively. Allocate codes only for handling contracts
with a current producer or for a contract introduced in the same coherent
implementation slice. Adding another producer of an existing contract reuses
its registered code and does not allocate another number.

## Public Error Contract

The Candid wire shape is exactly:

~~~candid
type Error = record {
  code : nat16;
};
~~~

The corresponding Rust field remains a plain numeric wire value, but the Rust
field is private. Public decoding exposes a lossless raw identity without
granting producer authority.

### Field Semantics

`code` is the complete public identity. It must be specific enough for the
host catalog to recover:

- the semantic domain and complete handling contract;
- the broad failure class;
- the symbolic label;
- the operator summary and action; and
- the intended machine behavior.

The raw code does not promise to identify one physical source function. A
shared code may have several current producer owners. Exact source attribution,
when needed, comes from the command, endpoint, operation, receipt or status
context rather than another wire field or another code.

Class and origin are not duplicated on the wire or in the canister-side error.
That redundancy would spend Wasm and payload bytes without adding information
for a known code.

An unknown code remains observable as its raw `u16`, but its origin cannot be
guessed. Diagnosis requires a host catalog from the same maintained Canic
surface. Canic does not add version negotiation, reserved numeric ranges or
fallback metadata to make an unknown code self-describing.

### Public Rust Surface

`canic::Error` remains the facade return type so endpoints do not acquire a
replacement-generation name. The private field changes in place. Runtime
producers construct it only through a registered-code boundary; decoders and
transparent forwarding paths may retain an arbitrary raw code through the
explicit raw API:

~~~rust
impl Error {
    pub const fn raw_code(&self) -> DiagnosticCode;
}
~~~

There is no accessor that presents an arbitrary decoded `u16` as a registered
producer identity.

The canister-side `Display` and `Debug` forms, if retained, are compact numeric
forms:

~~~text
E123
~~~

The exact punctuation is chosen once and tested. It must not include the Rust
constant name, class label, origin label, summary or remediation prose.

## Diagnostic Registry

`canic-core` owns only the prose-free runtime identity:

- `DiagnosticCode`, a lossless raw numeric identity whose tuple field is
  private and whose `from_raw(u16)` path does not imply registration;
- `RegisteredDiagnosticCode`, a distinct producer identity with a private
  field and no public numeric constructor;
- explicit numeric code constants typed as `RegisteredDiagnosticCode`; and
- compact numeric formatting.

One registered constant may be referenced by any number of semantically
equivalent producers. The central declaration module owns constants, not a
parallel constant per producer row.

The declaration owner may be a directory module tree split by canonical
semantic domain; it is one construction authority, not necessarily one large
source file. Every code still has exactly one canonical constant path.
Producer modules import that constant directly and must not introduce local
numeric declarations, renamed aliases or physical-subsystem copies. The split
follows shared conditions and handling contracts, never the current list of
producer crates, roles or endpoints.

Only that central declaration tree may construct a
`RegisteredDiagnosticCode`. Runtime error constructors accept that type, never
raw `u16` or arbitrary `DiagnosticCode`. `Error::from_registered(...)` is the
sole public producer boundary and always stores the registered value's raw
number. Raw construction is permitted only for decode, observation and
transparent forwarding paths that do not originate a Canic diagnostic.

`InternalError` keeps both exact and public identities private. Its public
conversion always reads `public_code`; no conversion may expose `code`
directly. Direct `Error { code: ... }` construction outside the one public-error
boundary module is a compile error. `RegisteredDiagnosticCode(...)` and
numeric producer construction outside the central declaration module are also
compile errors. Repository guards scan for both forms so future refactors
cannot bypass the typed boundary through conversion helpers.

Production Wasm must not contain:

- a complete iterable code list;
- the exhaustive producer-coverage frontier or a producer-to-code table;
- code-to-class, code-to-origin or code-to-prose metadata tables;
- public exposure tables;
- human-readable labels;
- complete English messages;
- remediation hints;
- formatted invariant prose;
- documentation copied into compiled string constants; or
- a feature-gated rich renderer.

Feature-gating prose inside `canic-core` is rejected because Cargo feature
unification can make host-selected features reachable in canister builds. The
physical crate boundary is the enforcement mechanism.

An illustrative source shape is:

~~~rust
pub const INPUT_CANISTER_ID_MALFORMED: RegisteredDiagnosticCode =
    registered(101);

#[cfg(not(target_arch = "wasm32"))]
pub const ALL_DIAGNOSTIC_CODES: &[RegisteredDiagnosticCode] = &[
    INPUT_CANISTER_ID_MALFORMED,
    // Every currently produced public or operator-visible code exactly once.
];
~~~

The implementation may use a local macro to declare numeric constants once and
emit a native-only complete list for coverage tests. The macro must not accept
prose, class or origin arguments. Target gating a numeric test inventory is
permitted; feature-gating a rich renderer in `canic-core` is not.

The resulting Wasm must contain only constants reached by that role. The host
catalog is checked against the native-only complete list so every current code,
including internal codes emitted to operator diagnostics, remains resolvable.

### Permanent Allocation Ledger

`canic-host` owns a checked-in, machine-readable allocation ledger that is
physically absent from every canister dependency and release Wasm. It contains
both current and retired allocations. Its frozen B1 ownership and transition
contract is recorded in
[code-allocation-ledger.md](code-allocation-ledger.md). Every row retains at
least:

- the nonzero numeric code;
- the current or former symbolic identity;
- `current` or `retired` status; and
- the current or last operator summary.

Current rows additionally identify their active catalog owner. Retiring a code
changes its ledger status in place; it never deletes or renumbers the row. The
active runtime constant, producer and rich current catalog entry are deleted.
Host lookup may use the ledger to explain that a raw number is a retired
identity, preserving historical log, receipt and operator-evidence diagnosis.
It does not decode the removed enum-plus-message Candid contract.

CI proves uniqueness across all current and retired rows, a bijection between
current ledger rows, native registered constants and current host catalog
entries, and the absence of a runtime producer or active catalog entry for
every retired row. The ledger is packaged only with host/operator tooling and
is explicitly inspected out of representative release Wasm.

### Registry Invariants

The registry must prove:

1. Every current or retired allocation is nonzero and globally unique.
2. Every current public producer maps to one registered code.
3. Every internal diagnostic emitted to operator logs is registered.
4. Every registered code has exactly one host class, origin, disposition and
   rendering entry.
5. Every internal-only code has an explicit public projection at its runtime
   constructor or boundary conversion.
6. No complete registry or metadata table is retained in release Wasm.
7. No string comparison participates in classification.
8. Unknown and retired raw codes remain round-trippable and distinguishable by
   host lookup.
9. Retired ledger rows remain permanent and their numbers are not reassigned.
10. There are no placeholder, reserved or padding leaves.
11. Direct numeric producer construction is mechanically rejected outside the
    central declaration module, and direct public-error struct construction is
    rejected outside its one boundary module.
12. Every current producer maps to exactly one registered internal code, while
    equivalent producers map many-to-one and do not allocate site-specific
    aliases.
13. Every initial singleton code has an explicit reason why it cannot compose
    with another maintained handling contract.
14. Every current code has exactly one canonical runtime constant path; a
    producer-local alias or duplicate declaration is rejected.

The initial approved set is densely numbered. Later retirement may create
gaps, but semantic and ownership-based numeric bands are forbidden: the number
does not encode a subsystem or reserve future leaves.

## Composable Diagnostic Identity and Granularity

The current 20 public `ErrorCode` leaves are too broad to reconstruct useful
operator guidance on their own. `InvalidInput`, `Conflict`, `Unavailable` and
`Internal` are classes in practice, not sufficient diagnostic leaves.

The exhaustive source inventory is deliberately broader than the permanent
code set. Its rows prove that every producer was considered; they are not
proposed allocations. A code identifies one canonical semantic condition and
its handling contract. One concise host label and summary must remain truthful
for every producer that shares it; neither a misleading union of unrelated
failures nor a generic loss of the actual condition is valid compression.

0.102 allocates another identity only when the canonical condition or one of
these contract properties differs:

- caller action;
- typed host disposition or runtime retry behavior;
- security exposure;
- operational remediation; or
- machine decision.

Physical subsystem, module, role, endpoint, function, source line, message
wording and interpolated value are not identity properties. `DiagnosticOrigin`
classifies the shared semantic domain in the host catalog; it does not prevent
composition across physical owners. Two producers with the same properties
above and the same canonical condition must share one code unless the
allocation row records a reviewed behavioral distinction. Merely preferring
different summaries is not a split rationale.

Wrappers, context appenders, transparent conversions and repeated invariant
checks never receive another code. Dependency variants collapse at the Canic
adapter boundary whenever Canic applies the same exposure, decision and
remediation. Internal invariant sites share the narrowest truthful identity
when their canonical condition and operator recovery are the same; exact
expected/observed values and operation state belong in typed receipts, views
or statuses.

There is no Cartesian product of primary cause with wrapper, phase, role,
endpoint or operation state. The primary canonical condition supplies the
code; typed operation context supplies those orthogonal dimensions. A boundary
may replace an unsafe internal code with its reviewed public projection, but it
does not stack or synthesize another compound diagnostic identity.

Slice A therefore owns two different artifacts:

1. an exhaustive host-only producer-coverage frontier, which may contain
   thousands of source observations; and
2. a reviewed many-to-one semantic-compression map from every maintained
   observation to one registered internal code and, when masked, one shared
   public projection.

Every coverage row must map to a compressed code or to an explicit
non-diagnostic disposition such as transparent propagation, unreachable
sediment or owned operational text. Every proposed code must list all mapped
producer owners. The coverage frontier, its labels and the mapping table never
enter release Wasm.

A four-digit initial allocation means semantic compression has failed and
blocks B2. This is a review gate, not a reserved range or permission to allocate
999 leaves. Allocation remains driven by distinct canonical-condition and
handling contracts, and the maintainer may require further composition at any
lower count.

Conversely, a generic string slot must not be used to avoid allocating a leaf.
The following is intentionally excluded:

~~~rust
pub struct Error {
    pub code: u16,
    pub detail: String,
}
~~~

When a meaningful value such as an operation ID, principal, limit or retry
time must cross a boundary, it belongs in an endpoint-specific typed response,
view, receipt or status record. It is not appended to a generic error message,
and the public cut cannot silently discard it merely because no owner exists
yet.

## Internal Error Model

`InternalError` becomes code-first. Its authoritative state is diagnostic
identity and exposure policy, not a formatted message.

An illustrative shape is:

~~~rust
pub struct InternalError {
    code: RegisteredDiagnosticCode,
    public_code: RegisteredDiagnosticCode,
}
~~~

An ordinary public diagnostic stores the same code in both fields. A sensitive
internal diagnostic stores its exact operator code plus a safe public code.
This small error-path value avoids a global runtime metadata or exposure table.

The final names may follow existing model conventions, but the invariants are
fixed:

- there is no owned `message: String`;
- there is no optional complete public `Error`;
- public projection is deterministic and typed;
- conversion to public `Error` always reads `public_code`, never `code`;
- sensitive internal identities can map to a safe public leaf;
- the internal code remains available for numeric operator diagnostics when a
  public projection masks it;
- class and origin are not stored in the runtime error; and
- formatting is never used to recover identity.

### Conversion Rules

Conversions from typed internal errors must match typed variants or fields.
They must not call `to_string()` and then classify the result.

`with_diagnostic_context` is removed. A caller that currently appends prose
must do one of the following:

1. preserve the primary diagnostic unchanged;
2. map it to a more specific registered leaf;
3. retain a typed secondary cause for internal control flow; or
4. write dynamic context to an approved structured status or log owner.

There is no generic vector of causes on the public wire and no recursively
nested diagnostic tree. Those shapes would add protocol and allocation cost
without a demonstrated consumer.

### Retained Typed Errors

This design does not flatten every internal error enum into `u16`.

Typed variants remain appropriate where code makes a decision such as:

- retry versus stop;
- absent versus forbidden;
- stale versus expired;
- conflict versus invariant failure; or
- recoverable platform rejection versus corrupt state.

At the layer boundary, those variants map exhaustively to compact diagnostics.
Derived `thiserror::Error` or `Debug` prose is removed when it remains
canister-reachable solely for formatting. Manual numeric formatting is used
where a formatting trait is actually required.

## Public Exposure and Security

Not every internal diagnostic is safe to expose.

Each runtime constructor or typed boundary mapping makes one explicit choice:

- public as-is;
- public through a less-specific safe code; or
- internal-only, with a deterministic safe public projection.

Projection must not leak:

- secret or authentication material;
- cryptographic intermediate values;
- private topology;
- stable-state contents;
- raw platform reject text;
- file or build paths; or
- implementation details that weaken authorization boundaries.

Authentication remains enforced at endpoints. Workflow and ops continue to
assume authenticated input. Compact diagnostics do not replace those
boundaries.

A mapped public diagnostic exposes only the safe public code. The host catalog
reports the safe code's public origin and does not reveal the sensitive
internal origin by accident.

When the internal and public codes differ, the owning workflow or ops path must
have an approved numeric observability owner for the internal code. The exact
internal number must be attached to the same operation/status record as the
masked failure or correlated through an existing operation ID that the caller
or operator can actually retrieve. An uncorrelated process log or global recent
failure is insufficient at an operation boundary. Read-only and pre-readiness
paths without an operation record may use a guarded bounded observation only
when the same status surface exposes it. If no such owner exists, the
implementation must allocate a sufficiently specific safe public code rather
than make the true origin permanently undiagnosable.

The internal observability value is the numeric code, not diagnostic prose.

## Host-Owned Rendering

`canic-host` owns the rich diagnostic catalog. This crate is already shared by
host/operator surfaces and is not linked into canister Wasm.

Every current registered code maps to:

- a stable symbolic label for logs and presentation;
- a concise operator-facing summary;
- an actionable hint when one exists;
- its host-only class and semantic origin;
- one typed host-only `DiagnosticDisposition`;
- every current Canic producer owner when that improves developer triage; and
- optional documentation metadata.

`DiagnosticDisposition` records machine-relevant host behavior without parsing
labels or prose. Its maintained variants cover `DoNotRetry`, `ExactRetry`,
`RetryAfterStateChange`, `BoundedRetry` and `Reconcile`. Runtime policy still
uses its owning typed state and exact numeric constants; it does not perform a
canister-side catalog lookup. Labels are presentation-only and must never be
matched for automation.

This includes internal codes written to approved operator diagnostics, not only
codes returned publicly. An origin names the narrowest stable semantic domain
that makes the failure actionable, such as delegated authentication or Wasm
publication. It is not automatically the module that produced the failure.
The catalog may list several producer owners for one shared entry, while normal
command rendering uses its endpoint or operation context for exact attribution.

An illustrative entry is:

~~~rust
DiagnosticEntry {
    code: INPUT_CANISTER_ID_MALFORMED,
    label: "INPUT_CANISTER_ID_MALFORMED",
    disposition: DiagnosticDisposition::DoNotRetry,
    summary: "The canister ID is malformed.",
    action: Some("Check the principal supplied by the caller."),
}
~~~

The concrete wording is written during the inventory slice. The example does
not allocate that code or mandate that message.

The central host response decoder renders known codes automatically. A normal
CLI command therefore remains useful to a human even though the canister sent
only one numeric field.

Retired and unknown codes render losslessly and distinctly:

~~~text
E1199 (retired diagnostic: FORMER_SYMBOLIC_IDENTITY)
E65000 (unknown diagnostic)
~~~

The host must not fail decoding, relabel an unknown code as a known error or
infer its origin, class or retry behavior.

### CLI Lookup

0.102 adds one current lookup surface:

~~~text
canic diagnostic E123
canic diagnostic 123
~~~

It prints the numeric identity, allocation status, symbolic label, class,
origin, disposition, summary and action when those fields are available. If
the CLI supports JSON for this command, the maintained current-code shape is:

~~~json
{
  "code": 123,
  "known": true,
  "status": "current",
  "label": "INPUT_CANISTER_ID_MALFORMED",
  "class": "invalid_input",
  "origin": "canister_input",
  "disposition": "do_not_retry",
  "summary": "The canister ID is malformed.",
  "action": "Check the principal supplied by the caller."
}
~~~

Retired lookup keeps `code`, `known: true`, `status: "retired"`, the former
label and last summary. Unknown lookup keeps `code` and `known: false` and
omits unavailable catalog fields. The implementation must use the repository's
current CLI output conventions rather than add a second envelope format.

### Language-Neutral Current Registry

The host catalog deterministically generates and checks in one current-code
JSON registry for Candid, Motoko and other non-Rust callers. It contains the
numeric code, label, class, origin, disposition, summary and action for every
current entry. It contains no runtime constructors and is packaged only with
host/operator artifacts. CI regenerates it and requires a byte-identical diff,
then proves its current rows are bijective with the current allocation ledger
and host catalog. A Markdown view may be generated for humans, but is not a
second authority.

## Dynamic and External Text

Static diagnostic prose and dynamic operational data are different ownership
classes.

### Static Prose

Static summaries, labels and hints move to the host catalog. They must not be
duplicated in runtime crates for convenience.

### Dynamic Context

Dynamic context remains only when an explicit owner needs it:

- typed IDs and values remain in typed response or status fields;
- application and operator logs may retain bounded messages;
- external platform rejection text may be retained in an approved diagnostic
  log or status record when it is operationally necessary; and
- no decision may depend on parsing that text.

Raw reject text must not be copied into the compact public `Error`. A public
caller receives only the registered code.

Slice A inventories every dynamic value currently interpolated into a public
`Error.message`, including operation IDs, expected/observed generations,
limits, retry times, principals and conflicting authority. Each interpolation
is assigned exactly one disposition:

1. **Caller-derivable.** The caller already owns the value and can safely
   derive it again; removal is explicit.
2. **Sensitive operator-only.** Public exposure is forbidden, and the value is
   retained only in a bounded, correlated operator owner when operationally
   required.
3. **Authoritatively typed.** An existing response, view, receipt or status
   field already owns the value; the inventory names that exact field and its
   retrieval path.
4. **Caller-required but unowned.** Correctness, recovery or remediation needs
   the value, but no typed owner currently exists. An endpoint-specific typed
   response, receipt, view or status owner must land before the public hard cut.

Category 4 cannot be waived by replacing the message with a broader code. No
recovery-, correctness- or remediation-significant dynamic public value may be
lost unintentionally. This inventory is distinct from the durable-string audit
below; a value may require both a public retrieval owner and durable recovery
classification.

### Strings Explicitly Outside This Cut

The following do not become numeric diagnostics merely because they are
strings:

- user and application log messages;
- Candid method and record-field names;
- metric names and label values;
- role, App, Fleet and Subnet identities;
- cryptographic suite names and domain-separation constants;
- configuration paths and user-provided configuration values;
- HTTP content and headers;
- certified data inputs; and
- protocol strings required by the IC or another current external contract.

Any later proposal to compact one of these owners needs its own evidence and
contract analysis.

## Durable-State Audit

Canic currently persists or projects several failure strings. Examples include:

- runtime bootstrap `last_error`;
- ICP refill `error_message`, alongside a typed refill error code;
- cycle top-up event `error`;
- authentication renewal or batch `failure`;
- pool and blob-operation reason strings; and
- runtime detail or validation strings.

The list is illustrative. Implementation must inventory every stable record,
snapshot, DTO projection and lifecycle restoration path before changing one.

General log text is not diagnostic baggage and remains outside this cut.
Diagnostic-derived durable text is evaluated field by field.

### Required Classification

Every durable failure string must be assigned to exactly one class:

1. **Redundant diagnostic prose.** A typed code is already authoritative.
   Remove the text from the current schema.
2. **Advisory transient context.** The value may be cleared and safely rebuilt,
   retried or re-observed during lifecycle restoration. The owner must document
   that behavior.
3. **Recovery-significant state.** The value affects recovery or decisions. It
   must become a typed state field before prose can be removed.
4. **Owned operational text.** A log or status consumer genuinely needs the
   dynamic text. Keep it bounded and prohibit string-based classification.

0.102 does not turn this inventory into a general recovery-state redesign.
Slice E removes redundant diagnostic prose, deterministically clears only
proven advisory state and retains bounded owned operational text. A
recovery-significant field may be replaced only when its existing behavior has
a direct bounded typed representation and no new lifecycle state machine is
required. If preserving the behavior needs a new state machine or broader
recovery protocol, retain the current owned text and record the redesign for a
later design line.

### Current Stable-State Boundary

0.102 installs only the current stable shape. No pre-0.102 stable bytes are
decoded, translated or migrated.

For every changed stable record, implementation must prove:

- the current record has one exact canonical encoding;
- any recovery-significant text removed by 0.102 is replaced by a direct typed
  field with the same current behavior;
- any retained recovery-significant text has a documented later-design owner
  and remains bounded without text-based classification;
- advisory state is rebuilt or cleared deterministically during current
  lifecycle restoration; and
- no decision depends on matching diagnostic text.

There is no old reader, dual-written field, fallback parser, one-time
migration or text-to-code conversion.

## Candid and Generated Surface Cut

The public cut must update every owned schema and generated surface in one
coherent slice:

- canonical `.did` files;
- generated facade endpoint signatures;
- checked-in test and example declarations;
- host response decoding;
- CLI rendering;
- canic-testing helpers; and
- Canic-owned downstream fixtures.

The old `ErrorCode` Candid variant is deleted, not deprecated. The old
`message` field is deleted, not left empty.

An intermediate local commit may introduce registry plumbing before the
contract cut, but no supported release state may expose dual public shapes or
two diagnostic protocols.

### Fleet-Atomic Activation Boundary

The source and Candid cut is repository-atomic; safe operation is Fleet-atomic.
0.102 is not rolling-compatible with pre-0.102. Before activation, deployment
must prove that the Coordinator, every Fleet Subnet Root, every root-local Wasm
Store and every Canic-owned application canister admitted to that installation
come from one exact release set. The matching host and CLI surface must be in
use, Canic-owned callers must be rebuilt, and external bindings must be
regenerated. Existing release-set identity, installation receipts and
activation gates enforce the boundary. A partially installed Fleet remains
unavailable; it does not make mixed-version calls. No dual decoder, migration
reader or diagnostic protocol-version field is introduced.

## Interaction With 0.99, 0.100 and 0.101

This design uses App, Fleet, canonical-network and Canister identity from
0.99, plus Component Spec, Component instance, Fleet Subnet Root, Component
Registry, Component Directory, Fleet Coordinator and physical-Subnet
placement vocabulary from 0.100. Its diagnostic origins must not reintroduce
0.99 Subnet Slot, Fleet Root, Tree identity or local Subnet
Registry/Directory terms into a 0.100-or-later surface.

0.100 may add new multi-subnet errors. If implemented first, those producers
join the 0.102 coverage inventory and participate in the reviewed many-to-one
map. If 0.102 is implemented first, later 0.100 work reuses every applicable
canonical code and allocates only genuinely new condition-and-handling
contracts.

0.101 may add Component Group compilation, stable placement identity,
density/spread policy, root provisioning, explicit scale-out and
mode-compatible Fleet-service publication errors. Those producers follow the
same ordering rule: if present before 0.102, they join its inventory; if
implemented later, they reuse applicable canonical codes and allocate only
genuinely new condition-and-handling contracts.

No diagnostic schema generation, negotiation or compatibility field is added
for this sequencing. Both designs target the one maintained pre-1.0 surface.

## Implementation Slices

Implementation should use the following coherent slices. These are work
boundaries, not patch versions or protocol generations.

### Slice A: Baseline and Registry Inventory

1. Build current canonical release artifacts for representative leaf, root and
   Wasm-store roles.
2. Record raw Wasm, gzip Wasm, data sections, function counts and bounded
   retained-size attribution.
3. Inventory every public constructor, internal conversion and host consumer
   as producer-coverage evidence, not as one allocation per row.
4. Inventory every dynamic public-message interpolation under the four required
   ownership categories and name each authoritative retrieval path.
5. Build a reviewed many-to-one compression map using canonical semantic
   condition, caller action, disposition, exposure, remediation and machine
   decision as the equivalence key; physical origin and prose do not split
   identities.
6. Define each compressed code's handling semantics, host class, semantic
   origin, disposition, producer set and public projection.
7. Assign a retrievable, operation-correlated observability owner to every
   masked internal code.
8. Inventory durable diagnostic strings and classify their ownership.
9. Produce the compressed current allocation rows, coverage-to-code map and
   permanent-ledger changes for maintainer approval without making them runtime
   authority.

This slice changes no public behavior.

### Slice B: Prose-Free Registry and Host Catalog

1. Add distinct raw `DiagnosticCode` and producer-only
   `RegisteredDiagnosticCode` identities plus one current constant per
   approved shared canonical-condition and handling contract to `canic-core`.
2. Add the permanent current/retired allocation ledger and exhaustive host
   rendering to `canic-host`.
3. Add typed host disposition, CLI lookup and the generated language-neutral
   current-code JSON registry.
4. Prove uniqueness across current and retired allocations, current native
   inventory/catalog/JSON bijection and direct-construction enforcement.
5. Prove the complete producer-coverage frontier, coverage-to-code map,
   allocation ledger and host metadata are absent from release Wasm.

Until the public cut lands, this is internal scaffolding only. It must not
become a second user-visible diagnostic protocol.

### Slice C: Atomic Public Contract Cut

1. Replace `ErrorCode` and `message` with the single `code` field.
2. Update canonical and generated Candid.
3. Update all facade endpoints, host decoders, CLI callers and test helpers.
4. Remove the old types and formatters completely.
5. Require one admitted release set and matching callers before Fleet
   activation.
6. Measure every representative role again.

The source cut is atomic at the supported repository boundary; availability is
atomic at the Fleet activation boundary defined above.

### Slice D: Internal Propagation Cut

1. Make `InternalError` code-first.
2. Remove message concatenation and optional complete public errors.
3. Carry explicit internal and public codes where security projection differs.
4. Give each masked internal code a numeric observability owner.
5. Replace string conversions with exhaustive typed mappings.
6. Compact or remove canister-reachable derived formatting.
7. Measure by subsystem so high-fan-out wins and regressions are attributable.

### Slice E: Durable and Observability Owners

1. Apply the durable-state classification field by field.
2. Remove redundant prose, deterministically clear proven advisory state and
   retain bounded owned operational or deferred recovery-significant text.
3. Add a direct typed replacement only where current recovery behavior remains
   unchanged without a new state machine; record broader redesigns for a later
   design line.
4. Keep general logs and required dynamic context.
5. Add exact stable decode and lifecycle evidence for every changed record.
6. Verify that metrics, traces and operator statuses still identify failures
   through typed numeric codes.

### Slice F: Closeout

1. Scan runtime crates and release Wasm for residual diagnostic prose.
2. Attribute retained strings rather than deleting by pattern.
3. Record final size deltas and method identity.
4. Update active documentation and downstream change notes.
5. Remove temporary inventory tooling unless it is admitted as a recurring
   audit owner.

## Measurement Contract

Raw canonical release Wasm is the primary size metric. Builder-produced gzip is
secondary because compression can hide duplicated prose or amplify unrelated
layout changes.

For every measured role and slice, record:

- immutable source identity;
- canonical builder and profile identity;
- raw release Wasm bytes;
- builder-produced gzip bytes;
- data-section bytes;
- function count;
- exported-method count; and
- bounded retained-size evidence for changed hotspots.

The B1 compression report separately records producer observations,
non-diagnostic dispositions, distinct internal codes, distinct public
projections, singleton codes, producers-per-code distribution, total
compression ratio and distinct codes reachable by each representative role.
These are host-side review metrics and are not compiled into Wasm.

At minimum, the roster must include:

- one representative leaf role;
- root;
- Wasm store; and
- any role found to have substantially different diagnostic reachability.

The preferred full closeout is a compatible run of
`CANIC-WASM-001`. Role-scoped development measurements may guide a slice but
must not be presented as the retained audit.

### Decision Thresholds

The architecture and public-contract benefits stand independently of size, but
the measured result determines how strongly Wasm savings justify further
low-level compaction:

| Raw release delta | Interpretation |
| --- | --- |
| Less than 5 KiB per affected role | Not worthwhile for size alone; retain only cuts justified by the cleaner contract and ownership model |
| 5–10 KiB | Modest; continue only through low-risk, high-fan-out paths |
| 10–20 KiB per leaf or at least 25 KiB in root | Worthwhile |
| 30–50 KiB in a role | Strong result |

These are review thresholds, not acceptance promises. A slice that increases
Wasm must be explained and either corrected or accepted explicitly for its
contract value.

IcyDB measurements must never be inserted into Canic audit history as if they
were Canic results.

## Testing Strategy

### Registry Tests

- every current or retired ledger code is unique and nonzero;
- every retired allocation remains lookup-visible but has no producer,
  registered constant or active catalog entry;
- every current public or operator-visible internal code appears in the
  native-only inventory;
- every current code has one host class, origin, disposition and rendering
  entry and one byte-identical language-neutral JSON row;
- every masked internal code has an explicit public projection and numeric
  retrievable, operation-correlated observability owner;
- compile-fail and repository guards reject numeric producer construction
  outside the central declaration module and direct public-error struct
  construction outside its boundary module;
- no unproduced placeholder code is allocated;
- every maintained producer-coverage row maps to exactly one current internal
  code or one explicit non-diagnostic disposition;
- producers with identical compression keys share one registered code, and
  every singleton allocation carries a reviewed split rationale;
- every current code has one canonical declaration path and no producer-local
  alias or duplicate constant;
- the initial allocation is not four digits and no producer-site alias table
  is linked into representative Wasm;
- compact `Display` and `Debug` contain no symbolic labels; and
- unknown raw values round-trip without panic.

### Mapping Tests

- typed internal variants map to the intended diagnostic;
- transparent wrappers and context propagation retain the primary code rather
  than allocating another identity;
- physical module, endpoint and role differences alone do not split codes;
- dependency variants with identical Canic handling collapse to one adapter
  identity;
- internal-only codes project to the intended safe public code;
- every public conversion reads `public_code`, never the exact internal code;
- host class and origin come only from the host catalog;
- runtime errors do not store or look up class and origin;
- no mapping path parses or compares text;
- removal of string context does not change retry or policy decisions; and
- every dynamic public-message interpolation has one approved ownership
  disposition and category-4 values have a typed retrieval owner before cut.

Tests assert typed codes and observable state, not rendered error strings.

### Wire Tests

- Candid `Error` is exactly one `nat16` field;
- `message : text` is absent;
- the Candid `ErrorCode` variant is absent;
- every checked-in `.did` uses the current shape;
- representative facade endpoints decode both success and error results;
- host response and replica-query paths decode the compact record;
- a Fleet cannot activate until every Canic-owned participant belongs to one
  admitted release set; and
- no mixed pre-0.102/0.102 caller path is admitted.

### Host and CLI Tests

- every current public or operator-visible internal code has one catalog entry;
- known codes render the expected origin, class, disposition, label, summary
  and action;
- retired codes render their permanent former identity without an active
  producer;
- unknown codes retain only their raw code and are not assigned guessed
  metadata;
- lookup accepts the canonical numeric forms;
- CLI JSON output follows existing conventions and the checked-in current-code
  JSON registry regenerates byte-identically; and
- normal command failures automatically use host rendering.

Human-facing host text may be snapshot-tested in the host/CLI owner. Runtime
and domain tests must not assert it.

### Stable-State Tests

For every changed stable record:

- encode the exact current state;
- restore it through the maintained current lifecycle;
- prove authoritative typed failure state and recovery behavior;
- retain recovery-significant text when removal would require a new state
  machine, with a recorded later-design owner;
- prove no string matching occurs; and
- exercise reinstall and restart behavior with PocketIC when a Canister
  lifecycle is involved.

### Wasm Tests

- search canonical release Wasm for a bounded set of removed diagnostic
  fragments;
- prove the producer frontier, coverage-to-code map and host registry are not
  linked into each representative role;
- inspect retained sections and functions for the high-fan-out error paths;
- confirm strings intentionally retained by logs or protocols have documented
  owners; and
- record deltas using the measurement contract.

Source scans are discovery aids. Absence from source or presence in source is
not a substitute for artifact measurement.

## Performance and Resource Invariants

- Success paths must not allocate merely to prepare an unused diagnostic.
- Canister code performs no registry lookup to construct a public error.
- Release Wasm contains no complete code inventory, allocation ledger,
  language-neutral registry or host metadata table.
- Release Wasm contains no producer-coverage labels, producer-to-code mapping
  table or per-site aliases; equivalent sites reference the same constant.
- Diagnostic metadata footprint is bounded by distinct codes reachable by that
  role. Ordinary producer control flow may contain the compact numeric value,
  but no registry, table, label or alias set scales with the repository-wide
  producer-observation count.
- Public error construction allocates no message string.
- Host rendering may allocate because it is outside canister Wasm and occurs
  on error paths.
- No network call is made to resolve a diagnostic code.
- Diagnostic lookup does not read canister stable state.
- Unknown codes remain printable without a catalog search.

## Contract Impact

### Breaking Public Changes

- `canic::Error.code` changes from a Candid enum to `u16`.
- `canic::Error.message` is removed.
- the public Rust and Candid `ErrorCode` enum is removed.
- callers matching named Candid variants must match current numeric codes
  instead.
- callers parsing message text must stop.

### Preserved Behavior

- endpoints continue to return `Result<T, canic::Error>`;
- authentication and authorization remain endpoint-owned;
- host and CLI users continue to receive human-readable diagnostics for known
  codes;
- unknown diagnostics remain visible; and
- typed domain decisions remain typed inside Canic.

### Stable Changes

The public error cut does not itself change stable state. Individual durable
failure fields change only after the durable-state audit identifies their
current typed owner and recovery behavior.

## Downstream Hard-Cut Guide

Canister and Candid callers must:

1. regenerate bindings from the current `.did`;
2. replace named `ErrorCode` matches with numeric code constants;
3. stop reading or parsing `message`; and
4. retain the raw code when logging an unknown diagnostic.

Rust producers should import the current `RegisteredDiagnosticCode` constants;
decoders use `raw_code()` and preserve arbitrary `DiagnosticCode` values.
Motoko and other language callers consume the generated current-code JSON
registry when they need named constants. No caller duplicates the host message
catalog in canister code.

CLI users receive rendered prose automatically. A code copied from a canister
log can be resolved with `canic diagnostic`.

Canic-owned examples and fixtures are updated in the atomic public slice.
Downstream repositories receive a source-change report; automated work under this
design does not edit them.

There is no period in which both error shapes are accepted.

## Alternatives Rejected

### Keep `message` Beside a Numeric Code

This preserves the main Wasm-retention source and encourages prose-dependent
callers. It is not a hard cut.

### Carry Class and Origin Beside the Code

`{ code, class, origin }` is more self-describing under host/catalog skew, but
class and origin are redundant for every known globally unique code.
The extra fields also require canister-side metadata or repeated constructor
arguments. 0.102 chooses the smaller `{ code }` contract; the current host
catalog recovers exact origin and class.

### Feature-Gate Rich Messages in `canic-core`

Cargo feature unification makes this boundary fragile. Rich rendering belongs
in a crate that canister artifacts do not link.

### Shorten Existing Messages

Shorter prose may save some bytes but leaves the string-first architecture,
variant formatting and unstable machine contract intact.

### Reuse Only the Current 20 Error Codes

The broad variants cannot reconstruct useful action for many failures. They
are suitable class inputs, not a sufficient leaf taxonomy.

### Allocate One Code Per Inventory Label

The source frontier is intentionally exhaustive and may contain thousands of
  observations. Treating those rows as allocations would confuse coverage with
  runtime identity, retain unnecessary constants and create a permanent catalog
  that cannot be reviewed. Producer rows must first map many-to-one onto shared
  canonical conditions and handling contracts. A four-digit initial allocation
  is an explicit failed compression result, not implementation authority.

### Add a Generic `detail: String`

This recreates the message field under a new name. Required details belong in
typed owner records.

### Add a Versioned Error Type

`ErrorV2`, dual endpoints and version fields are pre-1.0 compatibility
baggage. Canic maintains one current protocol.

### Strip Every Runtime String

Many strings are protocol constants, application data, metrics or logs.
Deleting them would conflate ownership and can break correctness.

### Rewrite Every Error Before Measuring

A blanket rewrite obscures attribution and risks removing operational context
without proving Wasm value. Measured coherent slices preserve evidence.

## Acceptance Criteria

0.102 is complete when:

1. The public Candid error is exactly `{ code : nat16 }`.
2. The old public `ErrorCode` enum and `message` field no longer exist.
3. No supported endpoint or host decoder accepts the old shape.
4. Release Wasm contains compact diagnostic identity but no complete
   inventory, allocation ledger, language-neutral registry, class, origin or
   rich rendering catalog.
5. Every current public producer has one registered code and explicit public
   projection.
6. Every maintained producer-coverage row maps to exactly one registered
   internal canonical-condition and handling identity or an explicit
   non-diagnostic disposition; equivalent producers share codes and the
   initial allocation is not four digits.
7. Every current public or operator-visible internal code has one host class,
   origin, disposition and rendering entry.
8. `InternalError` and boundary conversions are code-first and do not classify
   through strings; raw and registered identities are distinct and direct
   numeric producer construction is mechanically blocked.
9. Every masked internal code has an approved retrievable, operation-correlated
   numeric observability owner.
10. The CLI renders known failures, including their origin, and looks up raw
   codes, and the generated language-neutral current registry is exact.
11. Current, retired and never-allocated raw identities remain lossless,
    non-panicking and distinguishable without guessed metadata.
12. Every changed durable failure field has exact current encoding,
    restoration and lifecycle evidence.
13. Every current and retired allocation remains permanently unique in the
    host/repository ledger; retired numbers cannot be reassigned.
14. Every dynamic public-message interpolation has an approved ownership
    classification, and no recovery-, correctness- or remediation-significant
    value is unintentionally lost.
15. Every activated Fleet uses one admitted 0.102 release set and matching
    host/CLI/Canic-owned caller surfaces; mixed pre-0.102 operation is blocked.
16. General logs and required protocol strings remain owned and intact.
17. Canonical Wasm measurements exist for baseline, material slices and
    closeout.
18. The final report distinguishes Canic measurements from comparative IcyDB
    evidence.
19. Active docs, examples and downstream change guidance describe only the current
    numeric protocol.
20. No aliases, shims, legacy fields, fallback parsers, generation names or old
    protocol anti-resurrection tests remain. Permanent allocation-ledger and
    anti-reuse checks remain required.

## Implementation Readiness

The direction is approved. Slice A may continue as evidence-only inventory
work. Mutating implementation Slices B-F remain blocked until:

1. the fresh producer, consumer, dynamic-public-context and durable-state
   inventories are complete;
2. the first canonical Wasm baseline is reproducible;
3. the exhaustive coverage frontier has a reviewed many-to-one compression map
   and no four-digit initial allocation;
4. the compressed current/retired allocation ledger, host metadata and public

5. that complete Slice A authority receives maintainer approval.

No numeric assignments in examples in this document are authoritative. The
