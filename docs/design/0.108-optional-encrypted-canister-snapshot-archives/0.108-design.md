# Canic 0.108 Design: Optional Encrypted Canister Snapshot Archives

Date: 2026-08-09

## Status

- Status: accepted for M0 investigation; M1 through M7 are on HOLD.
- Implementation approval: evidence gathering, threat-model validation,
  protocol design and reproducibility proof in M0 only. No product code,
  provider mutation or external-repository implementation is approved.
- Release boundary: pre-0.108 backup layouts are unsupported. The accepted
  `SnapshotArchivePackageV1`, `SnapshotArchiveEnvelopeV1`,
  `SnapshotRecoveryCapsuleV1` and `ArchiveRepositoryProtocolV1` contracts are
  durable recovery formats across later Canic releases. This is an explicit,
  narrow exception to the ordinary pre-1.0 reinstall-only rule.
- Durable-reader rule: a later Canic release either reads V1 exactly or fails
  before any repository mutation. It must not guess, partially decode, migrate
  in place, fall back to another decoder or emit a mixed V1/V2 archive.
- Live-state boundary: Canic installation remains reinstall only. The durable
  V1 reader does not authorize cross-release Canister upgrade, state adoption
  or mixed-version operation.
- Sequence: this design follows the
  [0.106 standalone blob-service extraction](../0.106-standalone-blob-service-extraction/0.106-design.md)
  and the
  [0.107 Coordinator-backed root-funding design](../0.107-coordinator-backed-root-funding/0.107-design.md).
  Its approved M0 investigation may run alongside 0.106 M0 because the
  provider capability, retention and cost evidence overlap.
- Default: remote archival is absent and disabled. Existing local backup
  creation, verification, pruning and restore remain the baseline.
- Provider status: no blob repository is selected by this document. The
  standalone 0.106 service is one candidate behind an external repository
  adapter, not a Canic dependency or privileged infrastructure role.
- Version-1 scope: manual `list`, `pull`, `push` and `release`; one frozen
  package/encryption/capsule suite; one recoverable production key provider;
  disaster-recoverable repositories only; exact interruption recovery; one
  fake adapter and one qualified real adapter; reconstruction as the sole full
  verification journey.
- Cost status: unattended operations are outside version 1. A qualifying
  repository retains objects until explicit release under a provider-enforced
  prepaid or hard-capped authority. Manual commands display exact byte counts
  and require explicit confirmation.

## Summary

Canister snapshots should optionally be copied to blob storage, but only after
Canic has downloaded and verified the complete local backup and only as
client-side encrypted archive objects.

The local backup directory remains the canonical capture and restore format.
Remote storage is a second, off-machine durability tier. It is disabled by
default because it adds provider cost, credentials, key custody, retention and
recovery obligations. A failed, unaffordable or unavailable remote archive
must not invalidate an otherwise complete local backup.

The remote repository never receives raw snapshot files. Snapshot artifacts
can contain the complete Wasm module, heap, stable memory, certified variables
and chunk store of an application Canister. The first 0.106 blob service is
public by reference, so its ordinary integrity guarantees are insufficient for
private Canister state. Canic therefore packages a completed local backup,
encrypts it on the operator host, and gives only ciphertext plus a small
recovery capsule to a provider-neutral repository adapter.

One archive subsystem in `canic-backup` owns packaging, encryption, archive
journals, recovery capsules, manual confirmation policy and restore-input
materialization. Existing backup capture remains the sole source of a valid
local backup. Existing restore remains the sole authority that uploads
snapshot artifacts to the IC and loads them. The archive subsystem
reconstructs one canonical, byte-identical restore-input projection and then
delegates to those maintained paths; it does not duplicate snapshot or restore
logic.

~~~text
live Canisters
    |
    | existing canic backup create
    v
verified durable local backup directory       required baseline
    |
    | canonical package -> authenticated encryption
    v
ciphertext data object + recovery capsule     optional remote tier
    |
    | retrieve -> authenticate -> decrypt -> verify -> atomic publish
    v
verified durable local backup directory
    |
    | existing canic restore ...
    v
target Canisters
~~~

No live Canister writes a host file in this design. All local filesystem,
encryption-key and repository-credential work is performed by the native
operator process.

## Problem

Canic's maintained backup path already solves the hard part of snapshot
capture: topology binding, stop/create/start recovery, resumable download,
checksums, durable artifact publication, a manifest and a restart-safe
journal. That backup is still vulnerable when it exists on only one operator
machine or one mounted filesystem.

Keeping additional IC-resident snapshots is not a complete off-site backup
strategy:

- each snapshot retains the full Canister state and is billed as Canister
  storage;
- the platform permits only a bounded number of snapshots per Canister;
- deleting the Canister, exhausting its cycles or losing the relevant control
  path can also remove or strand the snapshot; and
- a Fleet backup can contain multiple Canisters whose snapshot set and restore
  order are represented by Canic's local manifest, not by one IC snapshot ID.

Copying the downloaded directories directly to a public-by-reference blob
service creates a worse problem: application secrets and user data become
available to anyone who learns a reference. Adding a provider directly to
backup capture would also couple backup correctness to a paid external
service, duplicate transfer/recovery policy and conflict with 0.106's
requirement that production Canic contain no blob protocol or package
dependency.

The missing boundary is an optional, encrypted, provider-neutral archive tier
that preserves the existing local backup and restore authorities.

## Decision

| Question | 0.108 decision |
| --- | --- |
| Should snapshots be archived remotely? | Optionally, after a complete local backup exists. |
| Is remote archival enabled by default? | No. It requires explicit operator policy and credentials. |
| Is the remote copy canonical? | No. The canonical operational format remains the verified local backup directory. |
| May raw snapshot bytes leave the host? | No. Remote objects are always client-side authenticated ciphertext. |
| Does Canic depend on 0.106 blob packages? | No. A generic external repository adapter isolates all provider protocol. |
| May the 0.106 service store the ciphertext? | Yes, through a separately shipped external adapter after its contract qualifies. |
| Does remote failure fail backup capture? | No by default. Strict operator policy may make archival required for a higher-level job result, but it cannot rewrite the local backup result. |
| Are unattended operations in version 1? | No. Version 1 is manual and requires exact-byte display plus explicit confirmation. |
| How long do version-1 objects remain retained? | Until explicit release; expiring or renewable retention is unsupported. |
| Can remote bytes alone claim disaster recovery? | No. A discoverable recovery capsule, accessible key provider and successful reconstruction proof are also required. |
| Does remote retrieval restore a Canister directly? | No. It reconstructs a verified local backup and delegates to the existing restore path. |
| Must later Canic releases read V1? | Yes. They read it exactly or reject it before repository mutation. |

## Goals

1. Preserve a complete Canic backup outside the operator's primary filesystem.
2. Make remote archival explicitly optional and disabled by default.
3. Keep plaintext snapshot bytes, encryption keys and provider credentials out
   of all Canisters and blob services.
4. Preserve the accepted V1 recovery contracts across later Canic releases.
5. Resume safely after process interruption or ambiguous provider responses
   without paying for or retaining duplicate objects.
6. Rediscover archived backups after loss of the primary local backup disk.
7. Reconstruct the canonical, byte-identical restore-input projection before
   using the existing restore planner and runner.
8. Keep provider integration outside Canic's production dependency graph and
   preserve the 0.106 blob hard cut.
9. Centralize archive model, policy, crypto, repository and journal behavior in
   one `canic-backup` subsystem.
10. Prove the entire recovery bootstrap from a blank second host using only an
    independently preserved recovery profile, credentials and key authority.

## Non-Goals

0.108 does not:

- replace IC snapshots, local backup creation or local restore;
- take snapshots from inside a live Canister;
- give a Canister host filesystem, repository credentials or encryption keys;
- add a Canic blob feature, blob protocol package, fourth infrastructure role
  or blob-aware Fleet Registry entry;
- make the 0.106 blob service private or add application metadata to that
  service;
- decode pre-0.108 backup layouts or migrate archives in place;
- infer application-level consistency beyond the accepted backup manifest;
- provide a general file-sync, object-storage or arbitrary-directory command;
- provide convergent encryption or plaintext-content deduplication;
- silently delete the local backup after remote publication;
- silently delete a remote archive when local backup pruning runs;
- claim multi-region or multi-provider redundancy from one repository;
- automate after-backup upload, retention, legal holds, scheduled verification
  or monetary policy in version 1;
- support renewable/expiring retention, receipt-required degraded
  repositories, key rewrap or multiple verification levels in version 1;
- place key escrow, monetary billing or provider funding policy in a
  Coordinator, root or application Canister;
- introduce a Canic background daemon; or
- implement provider work in the standalone 0.106 repository from this
  repository.

## Terminology

### IC snapshot

One management-canister snapshot retained on the source or target Canister's
Subnet. It has an IC snapshot ID and incurs IC Canister storage usage.

### Local backup

One complete Canic backup directory containing the deployment manifest,
backup plan, journals and checksum-verified downloaded snapshot artifacts.
This is the maintained input to restore.

### Restore-input projection

The canonical subset of one complete local backup required by current
integrity validation and restore. Its included files are byte-identical to the
source, but transient locks, reports, staging and archive state are excluded.
It is not described as an exact copy of the original directory.

### Backup source identity

`BackupSourceIdentityV1`, the canonical domain-separated SHA-256 identity of
the complete accepted restore-input projection. It is frozen before any remote
effect and revalidated after packaging.

### Archive package

A canonical byte stream derived only from one complete local backup. It
contains the exact required files and a package index; it is plaintext only
inside the trusted native process and protected staging boundary.

### Archive data object

The authenticated ciphertext of one archive package. The repository may
observe its size and ciphertext identity but not Fleet identity, Canister IDs,
snapshot IDs, timestamps, file names or file contents.

### Recovery capsule

A small, independently enumerable remote object that binds an `ArchiveId`,
the archive data object's identity, the encryption suite, the wrapped data key
and encrypted recovery metadata. It contains no raw data key and no plaintext
Fleet or Canister metadata.

### Recovery descriptor

The authenticated, encrypted metadata inside a recovery capsule. After the
configured key provider unwraps the data key, it identifies the backup,
package digest, required ciphertext object and repository receipt.

### Repository

An operator-configured remote durability target. A repository is addressed by
a stable local `RepositoryId`; provider identities remain opaque to core Canic
archive policy.

### Repository adapter

An explicitly configured external executable implementing the frozen 0.108
archive repository protocol. It translates provider-neutral requests into one
provider's upload, list, inspect, retrieve and release operations.

### Key provider

An operator-owned native security boundary that generates or unwraps one
archive data-encryption key through a bounded interface. Canic stores only a
provider identifier, key identifier and wrapped key material.

### Recovery profile

`ArchiveRecoveryProfileV1`, the independently preserved non-secret bootstrap
record that identifies the repository endpoint and namespace, repository
protocol, qualified adapter artifact, credential reacquisition method, key
provider configuration and required archive reader contract.

### Workflow and remote effect

One manual push, pull or release has one immutable `ArchiveWorkflowId`. Every
external adapter call inside that workflow has a distinct immutable
`RemoteEffectId` and an exact frozen request. A remote mutation uses its effect
ID as the provider idempotency key.

### Manual cost confirmation

One operator approval bound to the exact repository, operation, ciphertext
and capsule byte counts, provider-disclosed price evidence and hard-capped
account identity. It authorizes only that frozen manual workflow and is not an
unattended cost-control mechanism.

## Existing Baseline

The maintained backup layout already has four authority classes:

- `deployment-backup-manifest.json` binds the source, topology, members,
  snapshot provenance, artifact paths and checksums;
- `backup-plan.json` binds the accepted capture plan;
- `download-journal.json` binds each artifact's monotonic download and durable
  state; and
- `backup-execution-journal.json` binds the restart-safe live operations and
  receipts.

Artifact paths are rooted below the backup directory. Backup integrity checks
validate the manifest/journal agreement and recompute durable artifact
checksums. Restore planning reads that same manifest, verifies local artifacts
and uploads them before any snapshot load.

0.108 begins only after the existing backup integrity and terminal execution
checks pass. It does not accept a dry-run, partial, failed, locked, mutable or
checksum-invalid layout as archive source.

The current ICP snapshot documentation records that a snapshot captures the
Wasm module, heap, stable memory, certified variables and chunk store; up to
ten may be retained per Canister; snapshot storage is charged as Canister
storage; and download/upload is the supported offline transfer path. Those
platform facts motivate an off-Subnet archive but do not change Canic's
existing snapshot authority.

## Durable Recovery-Format Boundary

The hard cut occurs once, at entry to 0.108:

- Canic does not archive or recover pre-0.108 backup layouts;
- the first accepted writer emits only package, envelope and capsule V1;
- repository control messages use only protocol V1;
- exact version tags are authenticated before payload interpretation; and
- unknown or unsupported versions fail before any provider mutation.

After publication, V1 is a durable read contract. Later Canic releases retain
the exact V1 reader, golden vectors and reconstruction tests even if their
current writer emits a later format. A later writer never mixes versions
inside one archive. Reading V1 is recovery support, not live-Canister state
migration, upgrade adoption or a compatibility fallback.

The canonical repository protocol authority is a published specification in
this repository, accompanied by machine-readable schemas, positive finite
limits, golden messages and a conformance fixture. Canic and external adapters
must consume that authority; neither repository independently invents DTO
shapes or enum meanings. M0 must freeze the specification location and
release-signing process before M1 can leave HOLD.

Every qualifying real adapter publishes reproducible signed artifacts that
continue to implement repository protocol V1. A recovery profile pins the
adapter name, version, artifact digest, signature authority and acquisition
location. A current V1-compatible adapter may replace the originally pinned
binary only after its conformance evidence passes; format guessing is never
used to bridge adapter versions.

## Non-Negotiable Invariants

### 1. Local completion precedes remote effects

No package, encryption or repository mutation begins until the exact local
backup passes the maintained terminal and integrity checks. The archive
journal binds one fully defined `BackupSourceIdentityV1` before any remote
call.

### 2. Local and remote outcomes are separate

`BackupComplete` and `ArchiveComplete` are different facts. Remote failure,
cost rejection or provider unavailability cannot demote or corrupt a complete
local backup.

A later orchestration design may compose both terminal receipts. It must not
merge their state machines or rewrite either result.

### 3. Plaintext never reaches a repository

Every remote data byte is produced by an accepted authenticated-encryption
suite. Packaging and compression, when accepted, occur before encryption.
Repository adapters receive ciphertext paths or bounded ciphertext streams
only. There is no debug, retry or fallback path that uploads plaintext.

### 4. Keys and credentials remain host-owned

Raw data-encryption keys, key-provider credentials and repository credentials
never enter:

- command-line arguments;
- application or Fleet configuration;
- backup manifests or archive journals;
- logs, JSON reports or diagnostics;
- Canister init arguments or stable memory; or
- recovery capsules.

Wrapped key material is not a raw key and is bound to the exact archive and
encryption suite.

### 5. No-replace local publication

Remote reconstruction writes into private staging, validates every path and
byte, and durably publishes one new local backup directory with no-replace
semantics. An existing destination is never merged, replaced or partially
updated.

### 6. Workflow and effect identities are distinct

One push, pull or release has one durable `ArchiveWorkflowId`. Every external
call has a separate `RemoteEffectId`, exact effect kind and frozen request.
Retrying or inspecting one effect uses that exact identity. A later effect or
workflow must not adopt it.

### 7. Response loss is not failure or success

After an ambiguous put, get or release response, Canic records
`OutcomeUnknown` against the exact remote effect and reconciles through the
adapter. It neither issues a new identity, creates a second paid object nor
declares completion from local assumption.

### 8. Remote discovery survives primary-disk loss

The repository adapter must enumerate bounded recovery capsules from a blank
host using the independently recovered profile and repository credentials. A
local-only map from backup ID to provider reference is insufficient and cannot
qualify as disaster recovery.

### 9. Version 1 is manual and provider-capped

No version-1 remote operation is unattended. The repository credential or
account has a provider-enforced prepaid or hard maximum, objects remain
retained until explicit release, and the operator confirms the exact frozen
byte counts before each manual mutation. Local counters are observations, not
spend or quota authority.

### 10. Restore reuses the maintained path

Successful retrieval ends in a normal, verified local `BackupLayout`. All IC
snapshot upload, restore ordering, safety snapshots, lifecycle handling and
post-load verification remain owned by the existing restore subsystem.

### 11. Archive deletion is explicit

Local prune and remote release are independent commands and receipts. A policy
may select both, but each effect has its own preview, authorization, journal
and terminal evidence.

### 12. Provider types stop at the adapter

Provider URLs, digests, tenants, accounts, reference IDs, payment assets and
error payloads do not enter Canic archive model types. The adapter returns
bounded opaque handles and normalized capability and operation-status records.

### 13. V1 recovery remains readable

Package, envelope, capsule and repository protocol V1 remain exact recovery
contracts in later Canic releases. An unknown version or unavailable exact
reader fails before mutation; it never triggers a best-effort decoder.

### 14. The native adapter is trusted code

Version 1 treats an operator-installed adapter as trusted same-user native
code with ordinary host access. Control/data-plane separation limits accidental
exposure and protocol ambiguity; it is not an OS sandbox and does not defend
plaintext from a malicious adapter. Canic must not claim stronger process
isolation unless a later design implements and proves it on Linux and macOS.

## Relationship to 0.106

0.106 and 0.108 meet at a deliberately narrow external boundary.

0.106 owns a standalone public-by-reference immutable blob service, its
portable protocol/client, Caffeine/Cashier adaptation, tenant quotas,
retention and garbage collection. Canic may deploy that service as an ordinary
application Component but must not gain a blob package, feature, module, macro
or production dependency.

0.108 owns Canic backup eligibility, canonical packaging, client-side
encryption, recovery metadata, manual confirmation, archive journals and local
backup reconstruction. It speaks only the provider-neutral repository adapter
protocol.

An optional adapter may later be released from the standalone project:

~~~text
Canic repository                       standalone blob repository

canic-backup archive workflow          blob-archive-adapter executable
        |                                         |
        | ArchiveRepositoryProtocolV1             | blob-client/protocol
        +----------------------------------------> blob service
                                                   |
                                                   v
                                                Caffeine
~~~

That adapter is not `blob-service-canic`, does not execute in a Canister and
does not move blob semantics back into Canic. It is native operator tooling
that may depend on standalone blob packages. This Canic repository records the
required downstream work but does not implement it externally.

The first 0.106 service does not need private-object semantics for 0.108:
authenticated client-side ciphertext is safe to store through its ordinary
public-by-reference byte path, subject to qualified crypto, metadata-leakage
and key-custody evidence. The service must not learn Fleet, Canister, snapshot
or backup identities.

The following questions are shared M0 evidence:

1. Can one tenant enumerate retained references with enough bounded metadata
   to rediscover recovery capsules after local loss?
2. Can an exact operation be inspected after response loss without allocating
   another retained reference?
3. Can the provider expose an independently enforced prepaid or hard-capped
   account/credential boundary across concurrent processes and hosts?
4. Can the client retrieve a small capsule without downloading unrelated
   archive data?
5. Do provider deletion and billing semantics distinguish reference release,
   physical garbage collection and the time at which cost stops?

If 0.106 evidence cannot satisfy these requirements, the external blob adapter
does not qualify for version-1 0.108 use. The generic 0.108 design may still
qualify against another repository adapter without changing 0.106.

## Component Boundaries and DRY Ownership

The proposed source shape is one directory module under `canic-backup`:

~~~text
canic-backup/src/archive/
  mod.rs                 public archive workflow boundary
  model/                 passive bounded archive contracts
  package/               canonical source inventory and streaming package
  crypto/                suite framing, encryption and authentication
  key_provider/          host key-provider boundary
  journal/               durable monotonic push/pull/release operations
  policy/                pure eligibility and manual-confirmation decisions
  repository/            provider-neutral adapter protocol and process client
  recovery/              capsule discovery and local reconstruction
  tests/                  boundary and interruption matrices
~~~

This is a logical proposal; normal Rust directory modules with `mod.rs` are
required if implementation is approved.

Ownership rules:

- `canic-backup::archive` is the sole owner of archive state machines,
  package/envelope formats and repository normalization.
- Existing backup integrity functions are called, not copied.
- Existing artifact path and checksum validation is reused, not redefined.
- Existing durable regular-file and directory publication helpers are reused
  or generalized at their current owner; archive code must not grow private
  rename/link/fsync variants.
- `canic-cli` owns only lexicographically ordered command declaration,
  argument parsing, confirmation and human/JSON rendering.
- `canic-host` gains no blob-aware path. A generic process boundary may live
  there only if M0 proves it is shared by another host subsystem; otherwise it
  remains private to `canic-backup::archive::repository`.
- `canic-core`, `canic`, `canic-macros`, `canic-control-plane` and every
  Canister package remain unchanged by the archive data path.
- The external adapter is the sole owner of provider DTO conversion.

There is exactly one core operation per intent:

~~~text
archive_list(repository, recovery_profile)
archive_pull(archive_id, repository, destination, policy)
archive_push(local_backup, repository, policy)
archive_release(archive_id, repository, policy)
~~~

Interactive commands call only these operations. Version 1 has no second
automation, upload, encryption, retention or monetary-policy path.

## Source Eligibility and Package Format

### Eligibility

An archive source is accepted only when:

1. the path resolves through the existing secure backup-layout boundary;
2. Canic acquires one source lease that excludes every cooperating backup
   mutation and prune operation until package completion;
3. the backup and execution journals are not owned by another command;
4. the execution journal is terminal and successful;
5. the manifest, plan and journals validate under their current schemas;
6. every required artifact is durable and its checksum recomputes exactly;
7. descriptor-relative, no-follow metadata proves every included entry is a
   regular file with link count one, rejecting hard links as well as symlinks,
   devices, sockets, FIFOs and out-of-root paths;
8. no serialized restore-input field contains an absolute, temporary or
   host-specific path; M0 must inventory every packaged journal field and
   prove reconstruction on another host;
9. the complete source inventory fits explicit entry, path, individual-file
   and total-byte limits; and
10. descriptor-relative metadata and bytes remain identical across inventory,
    package read and final identity revalidation.

The source lease protects against other Canic commands; it is not authority
over arbitrary same-user filesystem mutation. For that reason every file is
opened beneath the held root descriptor, metadata is checked before and after
its streaming read, and the complete source identity is recomputed before the
first remote effect. Any change fails the workflow without reusing its frozen
identity.

### `BackupSourceIdentityV1`

The canonical identity is:

~~~text
SHA-256(
  "canic:backup-source-identity:v1" ||
  package_format_version ||
  entry_count ||
  for each entry in canonical relative-path byte order:
    path_length || path_bytes || file_length || SHA-256(exact_file_bytes)
)
~~~

Every integer encoding, path encoding, ordering rule and domain byte is frozen
by M0 golden vectors. The identity includes the exact manifest, plan, terminal
journals and every artifact file in the restore-input projection. It excludes
locks, reports, temporary files and archive state by construction. The archive
journal persists the complete canonical inventory plus this root identity
before encryption or adapter invocation.

### Canonical entry set

The package includes only restore-relevant, integrity-bound backup files:

- the exact deployment backup manifest bytes;
- the exact backup plan bytes;
- the exact terminal download journal bytes;
- the exact terminal backup execution journal bytes; and
- every regular file reachable through a manifest-approved artifact path.

Archive journals, locks, repository receipts, temporary files, reports and
previous ciphertext staging are excluded. This prevents self-inclusion and
defines the canonical, byte-identical restore-input projection. The projection
is deliberately not an exact copy of the original backup directory.

### Canonical stream

M0 must freeze one platform-independent `SnapshotArchivePackageV1` framing
with:

- a domain-separated magic and version;
- an exact lexicographically ordered relative-path encoding;
- explicit entry count, path length, byte length and total length;
- one SHA-256 digest per file and one digest for the complete package;
- regular files only, with directories derived from paths;
- no host uid, gid, mode, xattr, ACL, timestamp or inode metadata;
- exact rejection of duplicate, absolute, parent, empty, non-canonical or
  normalization-ambiguous paths; and
- streaming creation and extraction with bounded memory.

The format need not be a general archive standard. If M0 selects an existing
container, its canonicalization and safe-extraction rules must meet every
requirement above. Re-serializing JSON is forbidden; exact accepted file bytes
are packaged.

Compression is optional inside the versioned suite. If accepted, its
algorithm, parameters and decompression limits are exact. Compression occurs
before encryption and may not cause an archive with an unbounded decompression
ratio or output size to be accepted.

### Reconstructed-layout publication

Pull preflight creates a private sibling staging directory below the exact
destination parent and proves that staging and destination are on the same
filesystem before any paid data retrieval. Extraction uses descriptor-relative
no-follow creation and owner-only permissions.

Before publication, Canic:

1. authenticates the complete envelope and package;
2. verifies every entry against `BackupSourceIdentityV1`;
3. runs the maintained `BackupLayout` integrity checks against staging;
4. syncs every regular file;
5. syncs nested directories in post-order and then the staging root;
6. executes the shared atomic no-replace directory-publication primitive; and
7. syncs the destination parent before recording publication complete.

An existing destination, cross-filesystem staging, unsupported atomic
no-replace primitive or failed file/directory/parent sync is terminal before
publication. M0 must freeze the exact Linux and macOS primitives, filesystem
capability preflight and crash tests. Archive code may not add its own
rename/link/fsync implementation beside the maintained durable-I/O owner.

## Encryption and Key Custody

### Envelope

`SnapshotArchiveEnvelopeV1` uses chunked authenticated encryption so package
creation, upload, download and reconstruction do not require the entire
backup in memory. Its minimal public header contains only:

- envelope magic and version;
- encryption-suite identifier;
- random `ArchiveId`;
- ciphertext chunk size and count; and
- fields required to authenticate and frame the ciphertext.

Fleet name, Canister principals, snapshot IDs, topology, timestamps, file
paths, plaintext sizes and package digests remain encrypted. Ciphertext total
size is inherently observable by the repository.

Each archive receives a cryptographically random data-encryption key and
nonce material. The suite binds the public header, ordered chunk number,
ciphertext length and terminal package digest as authenticated data. Truncated,
reordered, duplicated, substituted or appended chunks fail authentication.

M0 must choose an audited, maintained AEAD construction suitable for streaming
large files on supported Linux and macOS hosts. It must freeze nonce derivation,
chunk limits, algorithm agility and test vectors. No implementation starts
with a placeholder cipher, home-grown construction or unauthenticated mode.

### Key provider

The key provider:

1. creates or accepts one random archive data key;
2. wraps it under an operator-selected key-encryption key;
3. returns bounded opaque provider/key identifiers and wrapped bytes;
4. unwraps only after explicit archive/repository context is authenticated;
   and
5. supports non-interactive use without putting secret material in arguments,
   config files or ordinary environment variables.

An initial implementation must qualify at least one recoverable production key
provider and one isolated test provider. OS keychain, hardware token, KMS and
offline recovery-key choices remain M0 decisions. A key provider that exists
only on the lost primary disk does not satisfy the disaster-recovery claim.

Version 1 has no generic key-provider plugin system and no key-rewrap
operation. M0 selects exactly one production integration and freezes whether
it is in-process or external. If it is external, M0 must publish one
`ArchiveKeyProviderProtocolV1` authority with bounded control records and
dedicated inherited descriptors for secret bytes; repository protocol DTOs or
ad hoc command conventions must not be reused. The external key provider is
trusted native code under the same honest same-user trust model as the
repository adapter unless an actual OS sandbox is separately implemented and
proved.

### No convergent encryption

Data keys and nonces are random per archive. Equal plaintext backups do not
produce equal ciphertext identity. This deliberately gives up cross-backup
deduplication to avoid equality leakage and unsafe key/nonce reuse.

## Recovery Capsule and Discovery

One archive is remotely complete only when both of these immutable objects are
retained:

1. the large archive data object; and
2. a small recovery capsule that names and authenticates the data object.

The capsule's public portion contains only the format version, random
`ArchiveId`, key-provider identifier, non-secret key identifier, wrapped data
key, encrypted descriptor length and authenticated encrypted descriptor. The
encrypted descriptor contains:

- local backup ID and creation metadata;
- package digest and exact plaintext limits;
- ciphertext digest, size and chunk framing;
- opaque repository data handle;
- source Canic release identity;
- repository identity and publication operation;
- repository protocol V1 identity; and
- capsule generation fixed to version-1 generation zero.

The adapter must be able to enumerate capsule handles without a local catalog,
then retrieve an exact selected capsule. Canic decrypts capsule descriptors
locally and filters them only after successful authentication. This can make
listing slower than a plaintext provider catalog, but avoids leaking Fleet and
backup metadata.

A terminal local `ArchiveReceiptV1` records both opaque handles, their
ciphertext identities, the frozen manual confirmation and the archive journal
digest. It is useful evidence and should be exported with ordinary operator
state, but it is not the sole discovery authority.

Version 1 accepts only disaster-recoverable repositories. Receipt-required
repositories are deferred rather than represented by a degraded enum variant.

### Blank-host bootstrap

Capsule discovery solves remote catalog loss, not configuration bootstrap.
Before the first push, the operator must export one bounded
`ArchiveRecoveryProfileV1` to an independently protected location. It contains
no repository credential or raw key, but it identifies:

- exact repository endpoint, namespace and repository ID;
- repository protocol V1 and capsule media/type selector;
- qualified adapter artifact, digest, signature authority and acquisition
  instructions;
- credential provider and documented reacquisition procedure;
- selected key-provider kind, non-secret configuration and key identifier;
- package, envelope and capsule reader versions; and
- the minimum Canic recovery-runner release capable of exact V1 reading.

M7 starts on a blank supported second host with only this recovery profile,
independently reacquired credentials and independently recovered key
authority. No workspace, backup directory, receipt, archive journal, cached
capability record, adapter binary or local catalog may survive from the source
host.

## Repository Adapter Protocol

### Canonical authority

`ArchiveRepositoryProtocolV1` is owned by one published protocol specification,
machine-readable schemas, bounds, golden records and conformance fixture in
this repository. It is not separately handwritten as an authority in the
standalone adapter repository. The external project may implement generated or
schema-validated provider DTOs, but the published specification decides field,
enum, limit and error meaning.

### Trusted-process boundary

The version-1 adapter is trusted operator-installed native code running with
the operator's ordinary user authority. Canic does not claim to prevent it
from opening unrelated same-user files, inspecting the process or abusing
repository credentials. Pinning, signatures, a scrubbed environment and
restricted inherited descriptors reduce supply-chain and accidental-exposure
risk; they are not a security sandbox.

Canic executes one configured absolute program path directly with a fixed
argument vector, controlled working directory, scrubbed environment, bounded
stderr, explicit timeout and no shell interpolation. M0 must test the exact
process behavior on Linux and macOS. A later real sandbox requires its own
accepted cross-platform design and threat model.

Repository credentials never enter command arguments, ordinary environment
variables or control records. M0 freezes exactly one credential transport for
the real adapter, using either an OS credential-provider handle or a dedicated
inherited descriptor. That transport is part of repository protocol
conformance and may not become an adapter-specific command convention.

### Control plane

One adapter invocation exchanges one bounded, versioned control request and
response through stdin/stdout. Control records never contain bulk object bytes,
filesystem paths to data, raw credentials or raw encryption keys.

Protocol V1 defines exact records for:

- `capabilities`;
- `inspect-effect`;
- `list-capsules`;
- `put-data`;
- `put-capsule`;
- `get-capsule`;
- `get-data`;
- `release-capsule`;
- `release-data`; and
- `status`.

Every effect request carries the workflow ID, distinct remote effect ID,
repository/configuration digest, effect kind, exact byte/digest expectations
and effect-specific immutable fields. Unsupported versions, duplicate IDs,
unknown fields and over-bound values fail closed. Stdout is protocol-only;
stderr is bounded diagnostics and must redact credentials, authority-bearing
URLs and protected metadata.

### Bulk data plane

Large archive bytes never use stdin/stdout and are never addressed to the
adapter by path.

- `put-data` receives one dedicated inherited read-only descriptor positioned
  at the exact ciphertext range named by the control request.
- `get-data` receives one dedicated inherited write-only descriptor for a
  private no-follow, create-new ciphertext staging file owned by Canic.
- exact descriptor numbers, close-on-exec rules, seek/resume behavior, byte
  limits, short-read/write handling and digest verification are frozen by M0;
- repeated `get-data` under one exact effect ID must replay the same bytes until
  Canic durably records ciphertext completion, and must not become a separately
  charged mutation identity;
- Canic retains ownership of staging names and never gives the adapter a
  plaintext source or reconstruction path; and
- capsules remain below a small positive finite bound and may use the control
  plane, or one separately frozen bounded descriptor if M0 evidence requires
  it.

The descriptor split is a large-data protocol contract, not sandbox evidence.
A malicious same-user adapter remains capable of opening other paths and is
outside the version-1 confidentiality threat model.

### Normalized inspection outcomes

`inspect-effect` returns exactly one bounded outcome:

- `Absent` — the exact effect has no provider evidence;
- `Pending` — the provider accepted the exact effect but it is non-terminal;
- `Committed` — the exact put/get effect completed with a matching receipt;
- `Released` — the exact release effect completed;
- `OutcomeUnknown` — the provider cannot yet establish a terminal fact; or
- `Conflict` — the identity exists with a different request or result.

Authentication failure, throttling, transport failure and malformed response
are typed call errors, not inspection outcomes. No such error becomes
`Absent`, `Committed` or `Released`.

### Required capabilities

An adapter qualifies for version 1 only if it proves:

- immutable no-replace publication or exact idempotent adoption;
- exact effect inspection after response loss;
- streaming upload and retrieval with independent byte/digest verification;
- bounded capsule enumeration and retrieval;
- separate data/capsule retention and release receipts;
- data and capsule objects remain retained until explicit release with no TTL,
  renewal or lease-expiry path;
- provider-enforced prepaid or hard-capped account/credential authority that
  remains effective across concurrent processes and hosts; and
- stable opaque handles with positive finite encoded bounds.

Capability records are evidence scoped to an adapter binary digest,
repository configuration digest and expiry. Changing the executable or
configuration invalidates prior capability evidence before another mutation.

## Version-1 Cost and Retention Authority

Remote archival is cost-bearing twice: IC snapshots consume cycles while they
remain on the Canister, and the selected repository may charge for storage,
operations, retrieval, funding or retained references. 0.108 controls only
the remote archive tier; existing snapshot cleanup remains separately owned.

Version 1 intentionally does not automate monetary policy. Every manual
operation still has positive finite safety bounds for:

- maximum source bytes and ciphertext bytes per archive;
- maximum capsule bytes;
- maximum entries and remote effects per workflow;
- maximum retrieval bytes for pull; and
- maximum control-plane records and adapter runtime.

Provider-side authority must come from a prepaid account or credential/account
quota that the provider enforces independently across concurrent Canic
processes and hosts. An adapter assertion, local counter, observed balance,
display-only quote or workspace lock is not enforcement.

Push stages encryption first so Canic can display the exact ciphertext and
capsule byte counts. Pull displays the exact provider-reported retrieval bytes.
Release displays both exact retained objects and the provider's documented
deletion/billing semantics. The operator confirms one frozen workflow request
after those values and any provider price evidence are shown. A changed request
requires a new confirmation.

Objects have no Canic-managed expiry or renewal in version 1. A qualifying
repository retains them until explicit release. If the provider requires
retain, renew, extend-retention or lease-heartbeat effects, it does not qualify
for version 1. This closes the protocol rather than implying an operation the
protocol does not define.

If M0 cannot prove provider-enforced hard-capped authority and indefinite
retention-until-release for any real adapter, M6 remains on HOLD. Unattended
automation moves to a later design even if a provider later offers enforceable
quotes or reservations.

## Protected Configuration

Archive policy is operator configuration under the Canic workspace/state
authority, not application `canic.toml`, Fleet input or Canister state.

One repository policy binds:

- stable `RepositoryId`;
- exact adapter executable identity and non-secret configuration;
- credential-provider reference;
- key-provider and key identifier;
- disabled or manual mode;
- archive eligibility selector;
- local byte and operation safety bounds;
- provider-enforced prepaid/hard-cap evidence kind; and
- explicit-release semantics.

The exact file path and schema remain M0 decisions. Secret values are never
accepted inline. Unknown fields, zero/negative limits, unbounded collections,
duplicate repository IDs and incompatible policies fail closed.

Policy changes apply to new operations. An in-flight operation continues only
when the new policy still authorizes its exact frozen request; otherwise it
stops before the next external effect. Policy changes never release an archive.

The ordinary protected configuration is not the disaster-recovery bootstrap.
Before the first push, Canic must render and validate the independent
`ArchiveRecoveryProfileV1`. Push fails if the profile has not been exported and
its exact digest acknowledged. M0 must freeze how that acknowledgment is
recorded without making a source-host receipt necessary for recovery.

## Operation State Machines

### Common journal contract

Every journal contains:

- one immutable workflow ID and workflow kind;
- the exact repository ID, recovery-profile digest, adapter artifact digest,
  repository protocol version and configuration digest;
- the exact archive/source/capsule identities known at that phase;
- one ordered row for every remote effect;
- the frozen request bytes and domain-separated request digest for each effect;
- the distinct remote effect ID used as mutation idempotency key;
- every normalized observation and provider receipt digest;
- the current retry/reconciliation decision; and
- one terminal `Complete`, `CancelledBeforeRemoteEffect` or `OperatorReview`
  result.

For each external effect, Canic performs these durable boundaries:

1. build and validate the exact frozen request;
2. persist and fsync `IntentDurable` before invoking the adapter;
3. invoke or resume only that effect ID;
4. validate a returned control record against the frozen request;
5. persist and fsync the normalized observation and receipt before advancing;
   and
6. advance the workflow only from a matching terminal observation.

A crash after step 2 may mean the request was never sent or its response was
lost. Restart must call `inspect-effect` before deciding whether the exact
request may be retried.

### Effect reconciliation

~~~text
RequestFrozen
  -> IntentDurable
  -> AbsentObserved -------> ExactRetryAuthorized -> IntentDurable
  -> PendingObserved ------> ReconcileRequired
  -> OutcomeUnknown -------> ReconcileRequired
  -> CommittedObserved ----> ReceiptValidated
  -> ReleasedObserved -----> ReceiptValidated
  -> ConflictObserved -----> OperatorReview
  -> CallErrorRecorded ----> ReconcileRequired
~~~

- `Absent` permits retry only with the same remote effect ID and byte-identical
  frozen request.
- `Pending` and `OutcomeUnknown` permit inspection only; they do not permit a
  new effect or cleanup assumption.
- `Committed` is valid only for the exact expected put/get effect and matching
  digest, size and opaque handle.
- `Released` is valid only for the exact expected release effect and handle.
- `Conflict` is terminal operator review and never becomes adoption.
- a malformed or request-mismatched committed receipt is `Conflict`, not
  success.
- bounded retry exhaustion enters `OperatorReview`; it is not provider
  absence.

Cancellation is allowed only before the first remote `IntentDurable`. After
that boundary, the workflow must reconcile every issued effect. Removing an
already committed object is a new explicit release workflow with new effect
IDs, never cancellation of the push.

### Push workflow

~~~text
SourceAccepted
  -> SourceIdentityDurable
  -> PackageStaged
  -> SourceIdentityRevalidated
  -> CiphertextStaged
  -> ManualConfirmationDurable
  -> PutData(IntentDurable -> CommittedObserved -> ReceiptValidated)
  -> PutCapsule(IntentDurable -> CommittedObserved -> ReceiptValidated)
  -> ReceiptPublished
  -> Complete
~~~

`PutData` and `PutCapsule` use different remote effect IDs. A committed data
object without a committed capsule is an incomplete push, not an archive. The
workflow reconciles or resumes exact capsule publication. If it cannot
complete, it enters operator review; a later operator may start a separately
confirmed release workflow for the orphan data handle.

The local receipt is published only after both retained objects are inspected
and their identities match the frozen request. Ciphertext staging may then be
removed. The local backup remains untouched.

### Pull workflow

~~~text
CapsuleSelected
  -> GetCapsule(IntentDurable -> CommittedObserved -> ReceiptValidated)
  -> CapsuleAuthenticated
  -> DestinationPreflightComplete
  -> ManualConfirmationDurable
  -> GetData(IntentDurable -> CommittedObserved -> ReceiptValidated)
  -> CiphertextDurableAndVerified
  -> PackageAuthenticated
  -> LocalLayoutStaged
  -> LocalLayoutVerified
  -> LocalLayoutPublished
  -> Complete
~~~

Decryption writes only into a private no-follow staging directory. File
digests, package digest, envelope authentication, path inventory and current
backup-layout integrity must all pass before publication. Failure removes or
quarantines staging; it never publishes a partial backup.

`GetCapsule` and `GetData` have distinct effect IDs. Repeated paid retrieval is
not assumed safe: ambiguous retrieval is inspected under the same ID before a
retry. Destination filesystem capability is proved before `GetData` intent.

### Release workflow

~~~text
ReleasePlanned
  -> CapsuleAndDataHandlesAuthenticated
  -> ManualConfirmationDurable
  -> ReleaseCapsule(IntentDurable -> ReleasedObserved -> ReceiptValidated)
  -> ReleaseData(IntentDurable -> ReleasedObserved -> ReceiptValidated)
  -> TombstonePublished
  -> Complete
~~~

The capsule is released first so a newly listed archive never points at data
scheduled for release. The local journal retains the exact descriptor and data
handle until both results are terminal. Provider physical garbage collection
may occur later; reports distinguish logical release, physical deletion and
unknown deletion status.

## Version-1 Manual Command Surface

Canic adds no daemon, scheduler, after-backup hook or Canister timer in version
1. The only tentative command group is `canic backup archive`, with these leaf
commands in ASCII lexicographic order:

- `list` — enumerate and locally decrypt discoverable capsule metadata;
- `pull` — reconstruct a verified local backup directory;
- `push` — archive one complete local backup;
- `release` — release one remote archive explicitly.

Every mutating command presents exact frozen source/object identities, byte
counts, repository identity, hard-cap evidence and provider price/deletion
information, then requires explicit confirmation. A resumed journal uses its
original confirmation only when the frozen request remains byte-identical.
Otherwise it stops for a new workflow rather than widening authority.

Exact command names, arguments and JSON reports remain an implementation gate.
No help page may exceed the repository's representative-example limit.

## Retention and Deletion

Version-1 retention has one rule: a data/capsule pair remains retained until
the operator explicitly releases it. There is no TTL, renewal, automatic
retention policy, legal hold engine or multi-copy planner.

Local pruning never implies remote release. Remote release never implies local
pruning. The operator must invoke and confirm each separately.

0.108 reports the provider's actual semantics:

- `reference-released` means the logical repository handle is no longer
  retained;
- `physical-deletion-pending` means garbage collection is incomplete;
- `physically-deleted` requires positive provider evidence; and
- `deletion-unknown` requires reconciliation.

Cost is not reported as stopped until the adapter provides evidence matching
the provider's billing boundary. If release outcome is unknown, both objects
remain accounted as retained.

## Verification and Recovery Drills

Version 1 has one full verification journey: reconstruction. It retrieves
every ciphertext byte, authenticates and decrypts every chunk, verifies the
package and source identity, extracts into private staging, runs current
`BackupLayout` integrity checks and atomically publishes or discards the
result. Capsule listing and provider status are operational observations, not
verification levels.

A real restore drill is a separate explicit existing restore operation against
an authorized disposable target. Archive verification must not weaken restore
preflight, safety-snapshot or semantic-verification requirements.

Scheduled verification and cheaper partial verification levels are deferred.

## Failure and Interruption Safety

The validation matrix must cover interruption:

- before and after source acceptance;
- during every package file and encryption chunk;
- after ciphertext staging but before manual confirmation;
- before and after each provider call intent;
- after provider effect but before response receipt;
- after `Absent`, `Pending`, `OutcomeUnknown`, `Committed`, `Released` and
  `Conflict` observations but before journal advance;
- after data retention but before capsule retention;
- after both remote objects but before local receipt publication;
- during capsule discovery and authentication;
- during retrieval through the inherited bulk descriptor;
- during decryption and extraction;
- before and after local no-replace publication;
- before and after each release effect.

For every case, restart must either resume the exact operation, reconcile its
exact effect or stop with durable operator-review evidence. It may not create a
second chargeable archive, overwrite a local backup, release the last recovery
capsule or treat transport uncertainty as provider absence.

Staging names are random and journal-bound. Startup cleanup may remove only
staging that is proven unowned by an active operation and is below the exact
archive state root. It must never sweep a workspace, backup root, home
directory or global temporary directory.

## Security Requirements

- Treat every local snapshot artifact as secret application state.
- Use descriptor-relative, no-follow traversal for package inventory and
  extraction.
- Reject hard links, symlinks, devices, sockets, FIFOs, sparse-size expansion
  beyond limits and path normalization ambiguity.
- Bind package, envelope, capsule, repository, key-provider, workflow and remote
  effect IDs with domain-separated hashes.
- Compare digests in constant time where secret-dependent comparison applies.
- Zeroize raw data keys and plaintext crypto buffers through an audited
  mechanism where the language/runtime permits it.
- Create plaintext and ciphertext staging with owner-only access and explicit
  durability barriers.
- Never log archive plaintext, data keys, wrapped-key bytes, credential
  material or authority-bearing provider URLs.
- Redact Fleet, Canister and backup identities from adapter-visible metadata.
- Bound adapter execution time, output, environment, file-descriptor access
  and inherited handles.
- Pin and verify the signed adapter executable identity before every remote
  effect.
- Require the key provider and repository credentials independently for
  recovery; compromise of only the blob reference must not reveal plaintext.
- Require successful key-provider access and capsule authentication before a
  manual release can be confirmed.
- State plainly that the same-user native adapter and an external key provider
  can open unrelated paths unless a real OS sandbox is separately proved.

Client-side encryption protects confidentiality from the repository and a
leaked blob reference. It does not protect plaintext on a compromised operator
host, prevent traffic/size analysis, replace provider availability or prove
application semantic consistency.

## Observability

Human and JSON status should distinguish:

- local backup state;
- package/ciphertext staging state;
- manual confirmation identity and exact byte counts;
- provider-enforced hard-cap evidence, never local-counter authority;
- data-object and capsule retention state;
- remote discovery mode;
- last successful reconstruction journey;
- key-provider/key identifier, never key material;
- logical release, physical deletion and billing-stop evidence; and
- exact retry, uncertain outcome and operator-review state.

Reports use stable diagnostic identifiers if 0.102 has qualified by the time
0.108 is implemented. They do not embed raw provider error text as automation
or recovery authority.

24. all four manual entry points share one archive subsystem;
25. no archive-specific durable I/O primitive duplicates an existing owner;
26. Canic has no production blob package, feature, API, service DTO or backend
    dependency;
27. the 0.106 blob service, if selected, is reached only through an external
    adapter and sees ciphertext as ordinary immutable objects;
28. no live Canister performs host filesystem, key-provider or repository work;
29. package, envelope, capsule and repository protocol V1 remain exact readable
    recovery contracts in the then-current Canic release;
30. no format guessing, fallback decoder, in-place migration or mixed-version
    writer is added; and
31. blank-host and real restore-drill journeys pass.

## Open Questions

M0 must answer these before any later milestone can leave HOLD:

1. Which canonical package framing best supports multi-gigabyte snapshot
   directories, safe extraction and deterministic Linux/macOS vectors?
2. Which audited chunked AEAD construction and crypto crate meet Canic's MSRV,
   maintenance and zeroization requirements?
3. Which first production key provider gives independently recoverable
   disaster-recovery authority, and is its boundary in-process or a separately
   specified trusted process protocol?
4. Can Caffeine/Cashier enforce a prepaid or hard maximum across concurrent
   processes and hosts rather than merely report a balance or estimate?
5. Does the 0.106 tenant reference listing expose enough bounded information
   to identify capsule candidates without full data retrieval?
6. What provider event ends charging: reference release, backend deletion
   acceptance or confirmed garbage collection?
7. Which exact control encoding, schemas, limits and golden-fixture publication
   process form the sole repository protocol authority?
8. Do any required current backup journals contain absolute or host-specific
   fields, and if so how is the canonical restore-input projection made
   portable without re-serializing or weakening integrity?
9. Which exact Linux/macOS same-filesystem and no-replace directory publication
   primitives meet the crash and fsync contract?
10. Where should protected archive policy and journals live relative to the
   current workspace backup root?
11. Which archive metadata, if any, may be deliberately public to make remote
    discovery cheaper without leaking Fleet activity?

## Alternatives Considered

### Keep more IC snapshots

Useful for fast rollback, but not an independent off-machine copy. It retains
full Canister storage cost, count limits and the source Canister's operational
failure domain.

### Upload raw backup directories

Rejected. Snapshot data can contain all application state, while 0.106's first
service is public by reference.

### Make blob storage the canonical backup format

Rejected. It makes a paid external service part of capture correctness,
weakens offline restore and duplicates the maintained local layout.

### Link `blob-client` into Canic

Rejected. It violates the 0.106 hard cut and couples Canic release/feature
graphs to one object service.

### Put archive automation in a Coordinator or root

Rejected. Canisters would need key/provider credentials and would duplicate
host backup/restore policy. The native operator process is the correct trust
boundary; host automation itself is deferred beyond version 1.

### Use plaintext-content-addressed encryption for deduplication

Rejected. Deterministic ciphertext leaks backup equality and makes safe key
and nonce management harder. Cost savings do not outrank confidentiality.

### Store only the data object and keep its pointer locally

Rejected for disaster-recoverable mode. Loss of the local pointer makes the
paid ciphertext practically undiscoverable. The recovery capsule is part of
the archive contract.

### Build an in-process provider plugin ABI

Rejected for the first implementation. It creates unsafe dynamic-linking and
dependency/version coupling. A bounded external process protocol gives a
clear provider and secret boundary.

## Deferred Work

The following require later designs:

- after-backup and other unattended automation;
- automatic retention, legal holds and scheduled release;
- unattended cost authorization, provider reservations and monetary budgets;
- receipt-required degraded repositories;
- key rewrap and encryption-suite retirement;
- partial/metadata verification levels and scheduled verification;
- multi-copy retention policy;
- any later archive writer format and its non-migrating coexistence with the
  permanent V1 reader;
- multi-provider quorum and geographic redundancy;
- confidential-computing or repository-side private processing;
- application-selective or incremental snapshot archives;
- plaintext-aware deduplication;
- provider migration with continuous availability;
- a general operator secret-management framework;
- monetary chargeback across Fleets or tenants; and
- canister-controlled archive policy.

None of these may be implied by version-1 names, placeholder variants or
generic repository terminology.
