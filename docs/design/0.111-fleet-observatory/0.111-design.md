# Canic 0.111 Design: Generic Fleet Observatory

Date: 2026-08-18

## Status

- Status: accepted and scheduled after the 0.110 stateful-adoption gate. This
  planning cut authorizes no evidence or runtime mutation.
- Outcome: a supported downstream surface for one bounded, truthful local
  identity and Fleet overview served by every installed Canister.
- Flagship consumer: Prequel Wars, maintained in its own repository. Canic
  owns no game role, data, presentation theme or application endpoint.
- Predecessors: completed 0.103 role command/status consolidation, 0.107
  deployment readiness/runtime admission, 0.108 funding, 0.109
  estates/retirement and 0.110 stateful adoption.
- Repository boundary: no production or workspace dependency on Prequel Wars,
  IcyDB or another downstream application.
- Compatibility posture: one current schema-1 view/profile contract. No
  Skynet alias, theme, decoder or retained application-specific surface.

## Decision

Canic will publish a generic observatory package boundary containing:

1. passive role-local and Fleet-overview views;
2. evidence and freshness classifications;
3. one bounded HTML/JSON renderer;
4. a narrow HTTP adapter for `GET`, `HEAD` and status JSON;
5. a validated data-only presentation profile supplied by the consuming
   application; and
6. role adapters for Coordinator, root, Store and managed Components.

Prequel Wars may supply a Galactic War Room profile and its own game-local
views. Canonical Canic infrastructure never depends on that profile crate.
The supported boundary lets another downstream application provide a
different bounded profile without forking infrastructure or copying a demo
renderer.

The observatory is passive. It cannot authorize, schedule or execute Fleet,
funding, estate, retirement, adoption or application mutations.

## Why The Surface Is Generic

The former checked-in Skynet demo mixed three concerns:

- useful application-neutral view and renderer ideas;
- application role adapters and topology examples; and
- a product-specific theme and fictional role vocabulary.

Only the first concern belongs in Canic's maintained future surface. The
checked-in Skynet App and helper are removed. Historical release notes and
frozen audit evidence remain truthful records, not active design authority.

Prequel Wars replaces Skynet as the real-world proving ground because it has
stateful planet-local Components, meaningful direct ingress, application
retirement requirements and a durable multi-Subnet topology. Its game data is
not copied into Canic.

## Goals

0.111 must:

- make generic observatory views and rendering a documented supported
  downstream Rust surface;
- serve exact local identity and a bounded complete Fleet overview from every
  installed Coordinator, root, Store and admitted managed role;
- distinguish Current, Stale, Unavailable and Simulated evidence explicitly;
- use one monotonic revisioned projection instead of per-request Fleet fanout;
- preserve exact complete counts while paging or sampling detailed rows;
- expose funding, estate, retirement and adoption state without granting
  authority over it;
- keep HTML and JSON semantically identical;
- validate profile strings, labels, colours, bounds and optional sections;
- escape all untrusted text and apply strict no-store/security headers;
- remain useful and accessible on small screens and without CSS;
- prove bounded response bytes, instructions and heap growth; and
- qualify a downstream-style profile without a production downstream
  dependency.

## Non-Goals

0.111 does not:

- ship or retain Skynet roles, terminology, theme, endpoints or compatibility;
- import Prequel Wars game types, IcyDB records or application state;
- own or deploy a product static-asset Canister or emit product frontend
  environment/binding configuration;
- create a central metrics warehouse, topology database or polling Canister;
- perform Fleet-wide fanout from an HTTP request;
- expose raw Registry, Directory, funding, estate, transition or application
  records;
- add public mutation, controller bypass or application authorization;
- certify raw-gateway responses;
- make an empty module-free estate asset serve HTTP;
- infer health, readiness or application correctness from topology alone;
- add one Canic method per view, phase, role or recipient; or
- make downstream adoption evidence a prerequisite for compiling or
  publishing canonical Canic infrastructure.

## Package And Ownership Boundary

B1 freezes exact package names, but the ownership split is fixed:

| Concern | Owner |
| --- | --- |
| generic view structs and evidence/freshness enums | Canic observatory package |
| bounded renderer and HTTP adapter | Canic observatory package |
| Coordinator/root/Store/managed role adapters | owning Canic runtime/control-plane package |
| revisioned projection state and acceptance invariants | Canic model/ops/workflow |
| data-only presentation profile | downstream application or Canic test fixture |
| application-specific local sections and endpoints | downstream application |
| game/business data and policy | downstream application |

The profile may contain bounded text labels, colour tokens, navigation labels
and optional safe section metadata. It contains no callback, function pointer,
authority predicate, endpoint implementation, raw HTML, JavaScript, CSS,
database handle or runtime state accessor.

Canonical infrastructure artifacts consume only Canic-owned generic packages
and validated passive profile data. They never link a downstream application
crate.

## Evidence And Freshness

Every rendered field names one evidence class:

- `Current`: verified against the current local/revision authority;
- `Stale`: previously accepted evidence outside its freshness window;
- `Unavailable`: absent or inaccessible without inference;
- `Simulated`: explicitly fixture/demo-derived and never presented as live.

Freshness is a pure classification over observation time, accepted revision
and protected policy. Stale evidence may remain visible but cannot authorize
an effect. Missing values render unavailable rather than using an invented
default.

Each public-field conversion is allowlisted, bounded and privacy-reviewed.
Adding a field requires its source authority, evidence class, byte bound and
HTML/JSON parity test.

## Projection Protocol

The Coordinator owns one bounded Fleet overview projection:

```text
roots publish bounded exact summaries
  -> Coordinator validates and aggregates one monotonic revision
  -> Coordinator distributes the accepted projection to roots
  -> roots distribute it to sibling Stores and admitted Components
  -> Components propagate it to newly created/refreshed descendants
```

Every publication binds Fleet, source, audience, revision, content hash and
encoded size. Equal-revision/equal-content replay is idempotent;
equal-revision/different-content rejects; older content never replaces newer.
Response loss and same-release restart resume the same operation.

These are variants in the receiving role's ordinary `canic_command` and
`canic_status` surfaces. No publication, overview, freshness or propagation
phase gains a separate method. Authorization occurs before protected state is
read or mutated.

An HTTP request reads only the last accepted local projection and local role
view. It performs no inter-Canister call.

## Topology And Operational Model

The global overview contains bounded summaries for:

- Fleet, App, release set and overview revision;
- Coordinator identity and transition state;
- physical Subnets, roots and sibling Stores;
- Fleet services, Component Group deployments and placement totals;
- parent/child relationships and exact complete counts;
- root operating-funding classes and policy state;
- estate target, reserve, state counts, concurrency and transfer summaries;
- qualified versus forced retirement disposition counts;
- 0.110 transition fence, predecessor/successor and convergence state;
- incomplete durable operations by typed class/count; and
- compact diagnostic identities with safe remediation where available.

The global projection never embeds every estate Principal or application row.
Role-local status supplies cursor-bounded details and links to the authority
that owns them.

## Role-Local Detail

Every installed role uses one page structure with a prominent local identity:

- Coordinator: Fleet/release identity, roots/Stores, funding treasury,
  projection convergence and transition fence;
- root: Subnet/Store relationship, Registry/Directory summary, funding,
  estates, retirement/transfer counts and bounded local Components;
- Store: release-set/artifact summaries, storage/cycle observations and exact
  protected Store surface;
- managed Component: exact binding, deployment purpose, local children,
  authorization profile and application-supplied safe sections; and
- descendants: parent/root/Subnet binding, pool purpose, readiness and bounded
  navigation.

Empty estate assets are represented in root counts/detail only. They cannot
serve a page until code is installed and they cease to be empty.

## HTTP And JSON Contract

Every installed role exposes through its application/role HTTP adapter:

- `GET /` for HTML;
- `HEAD /` for metadata-only availability;
- `GET /api/status.json` for the same semantic snapshot; and
- bounded cursor/filter parameters only for role-owned paged local data.

Other methods return `405`; unknown paths return `404`. Responses use
`no-store`, deny framing/referrer leakage/content sniffing and load no external
resource by default. Raw gateway output states that it is not certified.

HTML and JSON are projections of one typed in-memory view. Tests reject any
semantic field, count, evidence class or freshness result that differs between
them. The schema remains version 1 and is hard-cut in place before 1.0.

## Bounds And Security

B1 freezes ceilings for projection bytes, roots, Stores, service members,
edges, local rows, samples, metrics, profile text, HTML/JSON response bytes,
render instructions and heap growth. First excess rejects or explicitly
truncates only where complete totals remain available.

Public output must not expose controllers, bearer tokens, keys, credentials,
raw protected records, backups, application user/personal data, unbounded
reject text, logs or mutation payloads. Every string is escaped and JSON uses
typed serialization. Graphs have table/list equivalents, colour is not the
only state signal, focus remains visible and reduced-motion behavior is
respected by downstream profiles.

## Prequel Wars Flagship Boundary

Prequel Wars is the intended external flagship consumer. After Canic publishes
the supported surface, its own repository may provide:

- a Galactic War Room data-only profile;
- application-owned planet, settlement and service summaries;
- role-specific safe navigation and game terminology; and
- its own multi-Subnet integration journey.

Canic qualification uses a generic repository-owned fixture with the same
profile/view boundary. It may inspect downstream requirements read-only, but
does not copy or mutate the game. Canic can close without an unpublished
downstream commit; downstream adoption is separately reported when available.

The separate
[product frontend delivery handoff idea](../ideas/product-frontend-delivery-handoff/design.md)
owns browser environment identity, generated bindings, agent/Internet Identity
configuration and externally managed static assets. The 0.111 bounded
HTML/JSON renderer neither substitutes for nor gates that product workflow.

## Completion Criteria

0.111 is complete only when:

1. generic views, renderer, HTTP adapter and profile are supported downstream
   surfaces with one owner and versioning rule;
2. every installed canonical and managed role serves exact local identity and
   the bounded Fleet overview;
3. empty module-free assets remain visible inventory but never claim HTTP;
4. all fields have an authority, evidence class, freshness rule and bound;
5. projection publication is monotonic, authenticated and exact-retry safe;
6. HTTP requests perform no Fleet-wide fanout or mutation;
7. Coordinator/root/Store artifacts depend on no application crate;
8. HTML/JSON parity, escaping, privacy, accessibility and response budgets
   pass;
9. funding, estate, retirement and adoption state remains observational only;
10. generated Candid, help, examples and active docs agree;
11. the external-consumer fixture proves the public package boundary; and
12. no active Skynet role, theme, helper, authority, compatibility path or
    workspace dependency remains.
