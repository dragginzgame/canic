## Summary

Canic topology describes deployment, lifecycle and ownership. It does not form
an Internet Computer network perimeter: every canister with public ingress can
be called directly, and neither a parent, Root, controller nor physical Subnet
intercepts that call.

0.109 establishes one logical Fleet admission perimeter without pretending
that authorization is inherited. The Coordinator owns one bounded Fleet
admission policy. Installation and same-release policy mutation project the
effective policy into every participating canister. Each protected endpoint
checks its local projection before application work, so normal ingress requires
no call to the Coordinator, Root or another policy service.

The policy supplies one Fleet-wide Principal set and may narrow it for one
Component Spec, exact Component instance or Fleet Subnet Root subtree.
Narrower policy always intersects the Fleet set; it cannot silently widen
admission. Public endpoints, infrastructure commands, trusted service calls
and application resource authorization remain separately and explicitly
classified.

Composed frameworks inside a managed canister use one synchronous adapter over
the same Canic-owned projection as Canic endpoint access expressions. This lets
Toko's direct IcyDB endpoints check the observed caller before application work
without adding another storage contract, lifecycle owner or remote lookup.

## Problem

The 0.107 runtime whitelist is secure but local:

- every managed instance of an explicitly enrolled non-Root role owns an
  independent stable record;
- `[app.whitelist]` supplies only that canister's fresh seed;
- `caller::is_whitelisted()` reads the current canister's record; and
- an endpoint is protected only when it explicitly uses that predicate.

This supports local admission evolution but does not create one Fleet policy.
Two managed roles may drift after independent mutations, and a composed
endpoint framework cannot use the Canic access-expression macro directly.
Current Toko Miner has removed Core: its singleton managed App owns browser
login plus five caller-owned IcyDB/Robot methods. Guarding only the login
method therefore cannot protect direct calls to those composed endpoints.

A parent proxy is not the default solution. The child would observe the parent
as its caller, so the real user would require another authenticated delegation
and method/target binding. It also adds latency, availability coupling and a
second application routing surface.

A remote whitelist lookup on every request is also unsuitable. It introduces
an asynchronous availability dependency, cannot protect ordinary queries with
one uniform local decision and creates a time-of-check/time-of-use boundary.

## Decision

0.109 makes these decisions:

1. One Coordinator-owned record is the canonical Fleet admission authority.
2. The protected Fleet input supplies the fresh generation-one policy; App
   configuration no longer owns `[app.whitelist]`.
3. Every participating target stores a complete bounded local projection
   binding the Fleet, generation, policy digest, target identity and effective
   Principal set.
4. Protected user ingress is authorized locally from the observed transport
   caller and active projection.
5. Every application endpoint is explicitly classified. There is no automatic
   blanket guard based on canister ancestry.
6. One Fleet rule is required. Component, instance and Root-subtree rules may
   only narrow it through set intersection.
7. A physical Subnet is placement evidence, not a security scope. The closest
   supported scope is the exact Fleet Subnet Root and its protected descendants.
8. Membership never grants policy-administration, controller, infrastructure,
   application-account or resource authority.
9. Current Coordinator controllers authorize policy mutation. Roots distribute
   policy but cannot choose or widen it.
10. Fresh managed Components receive the current projection before protected
    ingress opens.
11. Runtime mutation uses a replay-safe prepare, activate and open protocol.
    Every participant is fenced before any successor policy becomes active.
12. Once the first participant is prepared, recovery moves forward for the
    exact operation; it does not roll back through a second policy meaning.
13. Missing, corrupt, unbound, stale-generation or fenced local authority
    denies protected ingress.
14. A composed framework endpoint may use Canic's synchronous managed-runtime
    adapter, but Canic remains the sole owner of projection storage and restore.
15. The 0.107 local runtime-whitelist config, predicate, commands, status and
    independent mutation authority are removed rather than retained as a
    compatibility lane.
16. `[roles.<role>] fleet_admission = true` is the sole enrollment declaration
    for managed admission participation. Omission is a fail-closed
    non-enrollment: the role receives no projection state, init projection,
    admission command/status surface or Root convergence entry. Roots and
    built-in infrastructure cannot enroll. Endpoint classification still
    decides whether one particular method is public, Fleet-admitted or
    governed by another exact authority.

## Goals

0.109 must:

- provide one operator-visible admission policy for an exact installed Fleet;
- support Fleet, Component Spec, exact Component instance and Fleet Root
  subtree targeting;
- preserve direct authenticated user ingress without a gateway or remote
  authorization call;
- make every effective Principal projection deterministic and digest-bound;
- install current policy before the first protected application request;
- add and remove Principals under bounded exact-retry mutation;
- make removal convergence observable and fail closed during mixed progress;
- recover the same operation after Coordinator, Root, Component or host
  interruption;
- keep public, user-admitted, application-member, trusted-service and
  controller/Root access classes distinct;
- preserve caller-derived application ownership and administration checks after
  Fleet admission;
- support synchronous admission checks from a composed framework inside a
  Canic-managed canister without another lifecycle or storage owner;
- expose bounded status, plan, diagnostics and Medic convergence evidence;
- hard-cut ambiguous whitelist vocabulary and independent local authority; and
- prove direct-call denial across a multi-Root Fleet and a generic
  composed-framework managed canister before closeout.

## Non-Goals

0.109 does not:

- claim that the IC supplies a network firewall around a Fleet;
- intercept ingress at a Root, parent, controller, boundary node or physical
  Subnet;
- make every public query private;
- apply a user Principal list to Canister-to-Canister role commands or Fleet
  service calls;
- make admission imply User, Robot, account, row, object or administrator
  ownership;
- introduce a provider-specific login, wallet or frontend protocol;
- turn the 0.105 local application session into a whitelist;
- implement the deferred declarative authentication-profile token system;
- introduce a standalone admission-consumer storage, lifecycle or transition
  protocol without a current application acceptance source;
- perform a synchronous or asynchronous remote policy lookup per request;
- promise instantaneous distributed revocation before every participant has
  reached the fence barrier;
- infer policy from a caller-supplied parent, Subnet or Component identity;
- permit a narrower target rule to widen the Fleet Principal set;
- migrate pre-0.109 whitelist state or support mixed Canic releases;
- authorize 0.110 contraction or 0.111 estate implementation;
  or
- modify Toko Miner, IcyDB or another external repository.

| participant | one managed non-Root canister required to enforce a projection |
| projection | target-local complete effective admission authority derived from one canonical policy |
| protected user ingress | endpoint explicitly requiring Fleet admission before application work |

## Authority Model

### Canonical Policy

The Coordinator stores one `FleetAdmissionPolicyRecord` containing at least:

- schema version 1;
- exact `FleetKey`;
- positive monotonic generation;
- canonical ordered rules;
- complete policy digest;
- active transition identity when present; and
- the bounded retained operation/result required for exact retry.

The policy digest covers every authority-bearing field, including each
selector and Principal. Labels, rendering and observation timestamps do not
affect it.

Compiled generation one is part of the Fleet plan and Registry authority.
After fresh activation the Coordinator record is the sole mutable policy
authority. Rebuilding configuration never silently merges, adds or removes
runtime membership.

### Selectors And Narrowing

The maintained selector family is conceptually:

```rust
pub enum FleetAdmissionSelector {
    Fleet,
    ComponentSpec(ComponentSpecId),
    ComponentInstance(ComponentInstanceId),
    FleetSubnetRoot(SubnetId),
}
```

These names express semantic ownership; B1 freezes exact boundary DTO spelling.

Every policy contains exactly one Fleet rule. An effective projection starts
with that Principal set and intersects every narrower rule matching the exact
target. A narrower rule containing a Principal absent from the Fleet rule is
invalid rather than inert. Duplicate selectors, noncanonical ordering,
anonymous Principals and unknown topology identities reject before retention.

`FleetSubnetRoot` is authored with the exact Root's unique `placement_subnet`
from the same protected Fleet input and resolves through that Fleet's Root
binding and Registry. It selects that Root subtree, never arbitrary canisters
on the physical Subnet. This release is reinstall-only, so it promises no
cross-release Root-placement continuity. A raw Subnet Principal supplied by a
runtime caller is never authorization identity.

### Administration

Policy administration uses the existing Coordinator role command/status
boundary. Authorization runs before policy, revision, membership or operation
state is read. The request binds:

- exact installed Fleet and Coordinator;
- expected generation and policy digest;
- add or remove action;
- selector and Principal;
- nonzero operation identity; and
- complete successor policy digest; and
- one bounded digest and count for the exact per-Root participant catalogs
  retained in the read-only operator plan.

The protected fresh-Fleet plan binds the canonical sorted enrolled-role list
for every participating Component Spec. The mutation plan retains the complete
sorted participant binding list for every Root. Immediately before apply, the CLI re-reads the current protected
catalog and rejects a changed Root or participant set. The role-command request
uses only the aggregate catalog digest and count so it remains within the
frozen 16 KiB command envelope. Each Root derives and snapshots its complete
successor target projections from its current protected Registry mirror. The
Coordinator aggregates those Root receipts and refuses Registry publication
unless their exact catalog digests and counts reproduce the plan-bound
aggregate.

A registered Root with no enrolled target remains in that exact Root catalog
with a nonzero empty-catalog digest and count zero. It advances the same durable
aggregate prepare/activate/open receipts without a target call. A whole Fleet
with no enrolled targets may likewise rotate its policy with zero participant
effects; zero never means an omitted or unknown catalog.

Add-present and remove-absent may return typed idempotent outcomes without a
new generation. An effective mutation allocates exactly the next generation.
Membership is not administration authority. Roots and participants accept only
Coordinator-derived transition commands under their exact installed binding.

### Local Enforcement

Managed endpoints use an explicit access expression conceptually named
`caller::is_fleet_admitted()`. It reads one local projection and current fence
state. It performs no call, await, mutation, cleanup or application-data read.

The current `caller::is_whitelisted()` name and independent runtime-whitelist
surface are hard-cut. Keeping both would leave two authorities for the same
request.

Successful Fleet admission returns only the observed transport Principal. The
application must still resolve that Principal to its local User or equivalent
identity and enforce resource ownership. A client-supplied Principal, User ID
or resource owner remains untrusted.

Infrastructure endpoints keep their existing controller, Root, parent,
service-authority, role-attestation or public policy. Fleet admission does not
replace them.

## Protected Input And Compilation

The exact TOML spelling is frozen in B1, but the protected semantic shape is:

```rust
pub struct FleetAdmissionPolicyInput {
    pub fleet_principals: Vec<Principal>,
    pub rules: Vec<FleetAdmissionRuleInput>,
}

pub struct FleetAdmissionRuleInput {
    pub selector: FleetAdmissionSelectorInput,
    pub principals: Vec<Principal>,
}
```

The host compiler:

1. validates finite counts, bytes and canonical ordering;
2. resolves every selector against exact protected Fleet topology;
3. derives each participant's complete effective Principal set;
4. binds policy and projection digests into the no-effect Fleet plan;
5. verifies every protected endpoint has a participating projection;
6. includes the projections in install and activation receipts; and
7. renders public/protected endpoint counts without exposing policy members in
   ordinary logs.

The policy is per Fleet, not per App source checkout. Two Fleets of one App may
have different admission sets without rebuilding application Wasm.

## Endpoint Classification

Every maintained application endpoint belongs to one explicit class:

| Class | Required authority |
| --- | --- |
| Public | deliberate public contract only |
| Fleet admitted | active local projection contains `msg_caller()` |
| Application member | Fleet admission plus caller-derived local membership |
| Application administrator | Fleet admission, membership and application-owned role |
| Trusted service | exact Canister/Fleet-service authority, not user admission |
| Infrastructure administrator | existing controller/Root/role command authority |

Managed Canic macros publish the class in their role manifest. A composed
framework endpoint that does not use a Canic endpoint macro must call the
synchronous managed-runtime adapter before its workflow. Canic cannot prove
arbitrary foreign endpoint code honest from a declaration, so the generic
fixture and downstream adoption review must exercise direct ingress rather
than claiming artifact attachment is enforcement.

## Local Projection Contract

Each participant stores one `FleetAdmissionProjectionRecord` containing:

- schema version 1;
- exact Fleet and Coordinator binding;
- exact target selector and target identity;
- active generation and policy digest;
- canonical effective Principal set and projection digest;
- optional prepared successor projection;
- fence/open state; and
- bounded exact transition replay evidence.

The projection is complete, not a delta. Restore validates its encoding,
digests, target binding and phase synchronously before protected ingress can
open. Missing or invalid state fails closed.

Canic owns storage and restore through the managed role contract. A composed
framework receives no storage trait or lifecycle callback; it calls the same
local projection guard as Canic endpoints.

## Fresh Installation

Fresh installation follows this order:

1. compile and digest the canonical Fleet admission policy;
2. create and bind the Coordinator authority;
3. install each explicitly enrolled managed participant with its
   generation-one projection, and install omitted roles without projection
   state or admission commands;
4. collect exact target receipts;
5. commit the complete participant catalog; and
6. open protected ingress only after every required receipt is valid.

A managed participant starts without admission authority and therefore denies
protected ingress until its exact generation-one projection is installed and
opened. The controller can always replace canister code and is not modeled as
an application-admission bypass.

## Same-Release Policy Mutation

One mutation owns the following durable phases:

```text
Planned
  -> Preparing (reserve every exact Root catalog without target effects)
     -> Releasing -> CatalogChanged, when the reserved aggregate is stale
     -> fence every reserved Root, when the aggregate matches
  -> PerimeterFenced
  -> Activating
  -> Opening
  -> Converged
```

### Prepare

Each Root first derives and durably reserves its complete target catalog without
calling or fencing a target. Only after every reservation receipt reproduces
the plan-bound aggregate does the Coordinator issue the distinct fence stage.
Each Root then validates and stores the complete successor projection at every
reserved participant and atomically fences protected ingress before returning
its perimeter receipt. Until every fence receipt is accepted, some participants
may still serve the predecessor policy; status must not claim Fleet-wide
revocation.

If the reserved aggregate differs from the accepted plan, the Coordinator
enters `Releasing`, releases every pre-effect Root reservation and returns the
typed terminal `CatalogChanged` result. The active policy and Registry remain
unchanged, no target has been called or fenced, exact replay returns the same
retained result and the operator must compute a fresh plan. A reservation that
has begun target fencing cannot be released.

### Activate

After all participants are fenced, each replaces its active projection with
the exact prepared successor while remaining fenced. A response loss replays
the retained receipt. Wrong Fleet, Coordinator, target, generation, policy,
projection or operation identity rejects without mutation.

### Open

Only after every activation receipt is accepted does the Coordinator authorize
participants to open. Opening may be observed sequentially, but every opened
participant already enforces the same successor generation. Convergence is
terminal only after all open receipts are retained.

After the first prepare effect, interruption recovery advances the same exact
operation. No later request may supersede it, and no participant independently
returns to the predecessor. A permanently unavailable participant blocks
convergence until a separately authorized lifecycle operation removes it from
the Fleet; policy mutation cannot silently omit it.

Component creation, retirement, transfer, adoption and other operations that
change the participant catalog are fenced as soon as a Root durably reserves
its catalog. A race before reservation is detected by the aggregate comparison
and terminates through the pre-effect release path rather than applying a stale
plan.
A newly activated Component receives the currently converged projection before
its application ingress opens.

## Composed-Framework Adapter

Canic publishes two views of the same managed projection check:

- `caller::is_fleet_admitted()` for Canic endpoint access expressions; and
- synchronous `canic::fleet_admission::require_caller()` for an IcyDB, IC-CDK
  or other endpoint framework composed inside the same Canic-managed canister.

The synchronous facade reads `msg_caller()` itself and returns that Principal
or one typed fail-closed error before application work. It does not accept a
Principal argument, allocate stable state, register lifecycle work, schedule a
timer or perform a remote call. Both paths read the one Canic-owned projection.

The endpoint continues to observe the user's direct Principal. It does not
accept a Principal forwarded by a proxy or parent, and successful Fleet
admission does not replace application-owned membership or resource checks.

`canic::start_local!` installs no managed Fleet projection, so both admission
views fail closed in standalone-local builds. A consuming application may add
an explicit local-only branch around its own endpoint policy, but Canic does
not infer a production bypass from build locality and no local bypass is
stored in, or distributed with, Fleet authority.

## Bounds

B1 freezes these version-1 limits:

- 256 Fleet Principals;
- 32 narrower rules and 128 total Principal references across those rules;
- 4,096 registered Roots, 4,096 admission participants per Fleet and 4,096 per
  Root, with the Root count additionally constrained by the Fleet total;
- 32 participant progress rows or 128 Principal values per status page;
- at most 8,192 retained current-plus-last progress rows in either the
  Coordinator or one Root;
- memory ID 64 and 8 MiB for Coordinator admission state;
- memory ID 65 and 8 MiB for Root distribution state; and
- reused memory ID 61 and 32 KiB for one managed target's active/prepared
  projection and local replay receipt.

The conservative B1 fixture remains historical sizing evidence. Production
outer-envelope tests on the corrected contract measure a 15,069-byte
Coordinator-to-Root command and a 9,247-byte Root-to-target command, both below
the frozen 16,384-byte role-command limit. The maximum Root current-plus-last
journal, including 4,096 participants in each slot, encodes to 7,807,793 bytes
inside memory ID 65's 8 MiB allocation. B6's production current-plus-last
Coordinator fixture measures 2,055,610 encoded bytes with 8,192 Root progress
rows, and 4,096 retained Registry publication entries measure 5,565,526 bytes
in the existing 32 MiB Coordinator Registry cell. First-excess tests own the
final gate. Membership lookup performs at most eight comparisons; target
restore decodes at most 32 KiB and validates at most one active and one prepared
256-member projection synchronously.

The exact fixture and capture live under
`docs/audits/working/0.109-fleet-wide-ingress-admission/`. Raising a bound after
B1 requires a design amendment and fresh capacity proof; exceeding the command
envelope reduces a bound rather than silently adding an unreviewed paging
protocol.

DTOs remain passive. Model records end in `Record`; canonical snapshot
`export()`/`import()` naming remains reserved for complete `Data` snapshots.
Policy performs no storage, async, timer, IC or serialization work.

## Diagnostics And Observation

The no-effect plan and protected status expose:

- Fleet policy generation and digest;
- rule and Principal counts without member values by default;
- every participant and selector;
- expected, prepared, active and open projection generations/digests;
- fence and convergence phase;
- in-flight operation identity;
- bounded failure role/target/phase and compact diagnostic code; and
- the first unresolved participant in canonical order.

An explicitly authorized paged inspection may return bounded Principal pages.
Ordinary Medic and observatory surfaces report only counts, digests,
convergence and health evidence. Logs and changelogs never publish configured
Principal values.

Medic fails when a required participant is absent, unbound, fenced outside an
active transition, stale, digest-mismatched or on another generation. A public
endpoint remains public by contract and is not reported as a perimeter gap.

## Security Invariants

1. Canister ancestry never grants user admission.
2. Every protected endpoint checks locally before application work.
3. The observed transport caller is the membership key.
4. No caller supplies authoritative Fleet, target or owner identity.
5. One Coordinator record owns mutable Fleet policy.
6. A target projection is a deterministic narrowing of that policy.
7. Narrower rules cannot widen Fleet admission.
8. Physical Subnet placement is not authorization identity.
9. Membership never grants administration.
10. Infrastructure and service-call authorization remain separate.
11. Missing, corrupt, stale or fenced projection state denies.
12. No participant activates a successor before all participants are fenced.
13. No opened participant serves a predecessor after successor activation
    begins.
14. Exact retry never repeats an accepted mutation or changes its target set.
15. Participant removal cannot be hidden inside policy rotation.
16. Composed-framework endpoints use the same target-bound local projection and
    observed transport caller as Canic endpoint access expressions.
17. Admission never replaces application membership or resource ownership.
18. No compatibility whitelist path survives the hard cut.

## Testing And Qualification

Focused native tests must cover:

- canonical rule ordering, intersection and digest vectors;
- duplicate, anonymous, unknown-target and widening rejection;
- exact add/remove retry, conflict and generation exhaustion;
- local allow/deny behavior for every projection phase;
- stable capacity, restore and corrupt-record failure;
- endpoint-classification and generated-surface parity; and
- synchronous composed-framework adapter parity with the Canic endpoint
  predicate.

PocketIC coverage must include:
