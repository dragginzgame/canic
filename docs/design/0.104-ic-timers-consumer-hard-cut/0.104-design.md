# Canic 0.104 Design: Timer Ownership, Async Recovery And Synchronous Lifecycle Composition

Date: 2026-08-16
Last amended: 2026-08-18

## Status

- Status: accepted as the second scheduled application-safety prerequisite.
  The Prequel Wars review promotes the synchronous lifecycle-participant seam
  and downstream native-timer adoption evidence into this line. B1-B6 are
  accepted and B7 is authorized.
- Release boundary: reinstall only. A 0.104 installation does not decode,

## Decision

Canic owns timer consumers, never timer mechanics.

Every registration, schedule, deadline, recurrence, retry directive,
cancellation, callback-generation decision, provider handle, pending callback
command, counter and inventory entry is owned by `ic-timers`. Canic owns the
fixed jobs it needs, their callbacks, pure business rules, authoritative
domain demand, replay-safe operation identities and the durable attempt leases
needed to recover interrupted asynchronous effects.

Canic may retain an opaque native registration claim so it can reconstruct,
cancel, suspend or unregister its own declaration. Claim custody is not a
scheduler. Canic must not reproduce the state or arbitration behind that
claim.

The public application timer facade is removed. Framework lifecycle deferral
and fixed Canic jobs continue to use `ic-timers` privately. Complete shared
timer inventory remains projected into Canic runtime diagnostics.

The same release adds one compile-time, framework-neutral synchronous
lifecycle participant to canonical root and managed non-root `canic::start!`
expansions. Canic restores its invariants first, invokes the application-owned
participant before any deferred work, and remains the sole IC lifecycle export
owner. This permits a downstream application to compose Canic with IcyDB or
another synchronous runtime without adding a framework dependency to Canic.

## Audit Conclusion

The current candidate has one canonical low-level timer runtime:

- exact `ic-timers 0.6.1` is resolved once;
- production Canic has no direct `ic-cdk-timers` dependency or raw provider
  call;
- fixed Canic jobs call native `register_once`,
  `register_after_completion` and `register_watchdog`; and
- status and metrics read the shared atomic `ic-timers` inventory.

The ownership hard cut is nevertheless incomplete:

- `workflow::runtime::timer` defines Canic-local `TimerDirective` and
  `TimerRunResult` types and converts them one-for-one to provider types;
- generic `schedule`, `schedule_at` and `reconcile_at` methods repeat native
  registration capabilities;
- public `timer!` and `timer_interval!` macros introduce Canic-owned transient
  identities, opaque handles and cancellation custody for application work;
- the generic stable async-recovery record stores `Ensure`/`Reconcile` pending
  commands, watchdog-owned deadlines, timer-ownership state, retry counters and
  terminal timer state; and
- recovery explicitly stops the ordinary provider lane and transfers schedule
  authority to a Canic-owned durable watchdog lane.

The current source guard proves absence of raw CDK timer calls and freezes an
inventory of adapter call sites. It does not prove that every live scheduling
action uses a native registration capability or that Canic defines no shadow
provider state.

## Ownership Boundary

| `ic-timers` owns | Canic owns |
| --- | --- |
| callback registration and scheduling | which fixed Canic jobs exist |
| relative and absolute deadlines | stable identity and callback for each job |
| recurrence and retry directives | pure business rules selecting desired work or timing |
| callback and pending-command arbitration | callback implementation and bounded work |
| provider handles and cancellation mechanics | opaque native registration-claim custody |
| callback, claim and scheduler generations | replay-safe business operation identity |
| volatile runtime counters and process condition | domain attempt generation and lease fence |
| atomic inventory and runtime epoch | projection into Canic diagnostics |
| watchdog scheduling protocol | bounded domain work the watchdog may request |
| lifecycle reconciliation helpers | when Canic asks those helpers to reconstruct a declaration |

The similarly named generations have different authority. An `ic-timers`
callback generation fences provider delivery. A Canic async-job attempt
generation fences a fallible business continuation after an `await`. The
latter remains allowed only when no provider callback or scheduling meaning is
encoded in it.

## Goals

0.104 must:

1. freeze every production registration, schedule, cancellation, callback,
   native claim, timer result and durable recovery field;
2. remove Canic-local provider directive and run-result types from internal
   execution;
3. remove the public application timer macros, facade, transient identity
   allocator and public opaque timer handle;
4. make framework lifecycle deferral and fixed Canic owners private native
   `ic-timers` consumers;
5. retain only typed registration custody needed for lifecycle control,
   authority snapshots and owner-specific cancellation;
6. replace generic async timer recovery with explicitly domain-owned async-job
   recovery;
7. persist replay identity, active-attempt fencing and domain work demand, but
   never provider commands, handles, snapshots, generations, counters or
   copied runtime state;
8. use one native recovery watchdog to request bounded recovery work;
9. preserve exact-operation recovery after an interrupted paid or
   controller-mutating effect;
10. continue projecting the complete shared inventory into runtime status and
    metrics;
11. ship a maintained native `ic-timers` adoption guide and a minimal managed
    application fixture with distinct application and Canic owner rows;
12. add one paired compile-time `fn() -> ()` lifecycle-participant declaration
    to canonical root and managed non-root `canic::start!` expansions;
13. prove Canic restoration, participant execution and deferred-work ordering,
    including rollback and exact corrected-cause retry;
14. qualify one Canic-owned test canister that composes the seam with IcyDB and
    one shared `ic-timers` provider; and
15. replace the source guard with a semantic ownership proof.

## Non-Goals

0.104 does not:

- change `ic-timers` or add another timer provider;
- add a callback registry, scheduler trait or runtime registration protocol;
- add a Candid endpoint, CLI timer command or stable timer snapshot;
- make provider inventory durable;
- add a new recurrence or retry algorithm merely to exercise the provider;
- change root-funding policy owned by 0.107;
- change estate policy or parallel creation/reset owned by 0.108;
- preserve the removed public Rust timer surface through aliases or wrappers;
  or
- introduce cross-release state migration or mixed-version operation, which
  is owned by the scheduled 0.109 adoption line.

## Public And Internal Surface Hard Cut

The following public surface is removed completely:

- `canic::timer!`;
- `canic::timer_interval!`;
- their prelude and `canic::api::timer` re-exports;
- application `TimerApi::set`, `set_interval` and `cancel`;
- public `TimerHandle`; and
- transient application identity allocation and expired-claim cleanup.

The repository's runtime probe is the only current in-repository consumer of
the public macros. It becomes native `ic-timers` composition evidence rather
than proof of a Canic application scheduler. Downstream source breakage is an
intentional pre-1.0 hard cut; no compatibility macro remains.

The removal ships with a maintained downstream adoption guide and fixture.
They show direct native `ic-timers` registration, exact dependency alignment,
owner labels, registration custody, restart reconstruction, cancellation,
detached-registration behavior and shared inventory visibility. The guide
states plainly that provider inventory is volatile and cannot substitute for
an application's durable demand or recovery record.

The following Canic-local internal vocabulary is also removed:

- `workflow::runtime::timer::TimerDirective`;
- `workflow::runtime::timer::TimerRunResult`;
- one-for-one conversion into provider directives and completions; and
- generic wrappers whose only work is forwarding a schedule to a native
  registration.

Callbacks return `ic_timers::TimerRunResult` directly. Canic may keep boundary
DTO enums such as `TimerExecutionOutcome` for Candid/status projection, but a
DTO must not become the internal provider completion type.

`TimerError` may remain as a narrow Canic boundary when it adds a real Canic
custody, suspension or lifecycle error. It must wrap native errors without
restating native scheduling states or failure taxonomies.

## Registration Custody

Canic retains a bounded, typed set of native registration claims for:

- root issuer renewal;
- automatic cycle top-up, only for a managed profile carrying 0.103's
  config-derived `AutomaticTopup` capability;
- local intent cleanup;
- runtime-log retention;
- placement-receipt acknowledgement;
- root Canister-pool maintenance;
- the async-job recovery watchdog; and
- private lifecycle deferrals still required by canonical `canic::start!`.

The final inventory is frozen in B1 and may remove an owner whose current
domain no longer requires a timer. A central typed custody structure is
allowed when authority snapshots must enumerate all Canic claims. It may store
only native registration values and fixed identity metadata. It must not store
desired deadlines, copied registration state, recurrence state, pending
commands, counters or transient application identifiers.

Root, Coordinator, the implicit Store and a Runtime-only managed profile have
no automatic-top-up registration, callback or workflow reachability. 0.104
consumes the exact capability decision frozen by 0.103; it does not infer a
timer owner from linked cycle code.

Each scheduling action is invoked on the exact native registration capability
that owns the declaration. Lifecycle reconstruction should prefer native
`reconcile_once`, `reconcile_after_completion` and `reconcile_watchdog` where
their contract matches the fixed owner.

## Lifecycle Ordering

Canonical lifecycle ordering remains:

~~~text
enter Canic-owned init/post_upgrade export
  -> initialize the shared ic-timers runtime once
  -> restore Canic synchronous domain state
  -> construct or verify typed native registration custody
  -> derive desired schedules from authoritative domain state
  -> reconcile the native registrations
  -> schedule Canic deferred bootstrap/application hooks
  -> return
~~~

`canic::start!` stays thin. Lifecycle adapters remain synchronous and do not
`await`. User hooks continue after Canic invariants are restored through
private zero-delay native registrations. The deferred user hook is not the
synchronous lifecycle participant.

## Synchronous Lifecycle Participant

Canonical root and managed non-root expansions accept one paired declaration:

```rust
canic::start!(
    lifecycle_participant(
        init = crate::lifecycle::after_canic_init,
        post_upgrade = crate::lifecycle::after_canic_post_upgrade,
    ),
);
```

Both paths must coerce to safe `fn() -> ()`. The declaration is compile-time;
there is no registry, list, trait object, closure, string lookup, persisted
callback identity or runtime selection. The application owns any deliberate
fan-out among its synchronous reconcilers.

The exact partial order is:

```text
one Canic-owned init/post_upgrade export
  -> initialize the shared ic-timers runtime once
  -> restore Canic synchronous invariants and native claims
  -> invoke the matching application lifecycle participant exactly once
  -> schedule only state-admitted Canic bootstrap and deferred user work
  -> return
```

Managed init invokes the participant while the Component remains `Prepared`;
later activation does not repeat it. Managed post-upgrade invokes the
participant before the Active/Prepared scheduling branch, including when the
Component remains inactive. Root uses the same ordering against its own exact
restore path. `start_local!` may support the declaration as a development
surface, but `start_wasm_store!` and `start_fleet_coordinator!` do not.

Participant failure traps the enclosing lifecycle message. Canic does not
catch or downgrade it, and no later bootstrap timer or deferred hook commits.
A failed install remains empty; a failed upgrade retains the prior committed
Wasm and state. Retrying after correcting the application-owned cause reruns
the complete lifecycle message from that committed boundary.

The seam adds no Candid method, stable record, authority, readiness claim or
framework-specific production dependency. The composed Wasm retains exactly
one `init` and one `post_upgrade` export.

### Combined Canic And IcyDB Qualification

One Canic-owned test canister may use an exact test/dev IcyDB dependency to
prove the generic seam. Shipped Canic code imports no IcyDB type. The focused
proof must establish:

1. exactly one resolved `ic-timers` package identity;
2. exactly one lifecycle export pair and unchanged Candid;
3. Canic and IcyDB owner rows in the same timer inventory;
4. Canic callback progress and IcyDB recovery progress;
5. reconstruction of both owners after same-release upgrade, including while
   the managed Component remains Prepared or inactive; and
6. participant-trap rollback followed by corrected-cause retry.

## Domain-Owned Async-Job Recovery

An asynchronous Canic job may cross an `await` after recording intent or
issuing an external effect. A volatile provider callback cannot by itself
prove whether that business operation completed. Canic therefore retains a
domain recovery boundary independent of timer delivery.

The shared mechanism may retain only:

- a closed domain-job identity;
- checked last-attempt and last-operation generations;
- an optional active lease containing exact attempt, operation and expiry;
- an optional exact operation generation that must be retried; and
- the minimum receipt binding needed to prove the same business operation.

The shared mechanism must not retain:

- `Ensure` or `Reconcile` timer commands;
- provider or watchdog schedule ownership;
- a generic next timer deadline;
- an `ic-timers` handle, claim, snapshot or generation;
- recurrence or callback-pending state;
- copied provider retry streaks or terminal process condition; or
- a boolean whose meaning is that scheduling moved between two timer lanes.

When a domain requires durable retry eligibility, its owning record may store
a semantically named business fact such as an exact operation's
`retry_not_before_ns`. B1 must prove the domain owner, derivation, restart
meaning and cleanup rule. A generic timer deadline stored only because a
callback returned `RetryAfter` is prohibited.

The current private memory allocation at core ID 60 is not released authority.
0.104 either hard-cuts it to the minimal current `AsyncJobRecoveryRecord` or
removes it if owner-specific records already carry every required fact. There
is one current schema-1 meaning, no `v2`, fallback reader or migration.

## Owner Dispositions

### Root Issuer Renewal

The durable delegation batch, proof validity and next-attempt facts remain the
authoritative demand. The callback returns a native result. Lifecycle derives
the desired native deadline from current auth state. No generic recovery
deadline or copied retry counter becomes auth authority.

### Automatic Cycle Top-Up

Balance observations and protected funding policy establish demand. The exact
funding operation ID remains stable across uncertain retries. A durable active
lease rejects overlapping attempts and stale completion. Any durable retry
eligibility must belong to the funding operation, not to a timer record.

### Placement-Receipt Acknowledgement

The durable terminal-receipt index and exact operation receipts establish
demand. Empty demand leaves the retained native declaration inactive. Retry
eligibility, if persisted, belongs to the acknowledgement operation. The heap
cursor and provider counters are never promoted into stable scheduling state.

### Root Canister-Pool Maintenance

Pool records and journals establish pending creation, reset, handoff and
recovery work. Fleet activation and draining establish whether proactive
maintenance is allowed. The pool owns those business facts; `ic-timers` owns
the after-completion cadence. The control plane retains its native
`AfterCompletionRegistration` directly instead of using a public Canic timer
handle.

### Synchronous Local Jobs

Intent cleanup and log retention already derive their next exact deadline from
authoritative indexes or policy. They use native once registrations and need
no async-job recovery record.

## Recovery Watchdog

One retained native `ic-timers::WatchdogRegistration` may inspect the bounded
closed set of recovery-critical domain jobs. It may:

- detect an expired Canic business-attempt lease;
- confirm that authoritative domain demand still exists;
- claim a new attempt using the same replay-safe operation identity; and
- dispatch bounded owner-specific recovery work.

It must not:

- become an alternate deadline scheduler for healthy ordinary callbacks;
- take durable scheduling ownership away from another registration;
- merge `Ensure` and `Reconcile` requests;
- copy provider deadlines or process condition into stable state; or
- convert timeout or uncertainty into a fresh paid operation.

A late completion may commit only when its exact business-attempt token still
owns the active lease. Provider stale-callback handling remains entirely in
`ic-timers`.

## Authority Snapshots And Suspension

Snapshot admission continues to require no running Canic-owned provider claim
and no active Canic business-attempt lease. Suspension and resume use native
claim capabilities. A Canic snapshot may persist domain authority but never a
provider handle, timer snapshot or callback generation.

Resume restores domain state first, reconstructs native declarations, derives
current desired deadlines and reconciles them. A copied pre-snapshot provider
deadline is not accepted as durable authority unless the same timestamp is an
independently justified domain fact.

## Observability

Canic continues to expose neutral `CanisterTimerStatus` DTOs sourced from one
atomic `ic_timers::timer_inventory()` snapshot. Owner, subsystem, name,
registration, process condition, deadlines, runtime counters and bounded
performance observations remain provider facts projected at the public
boundary.

The optional runtime epoch may be exposed later if the status schema is
otherwise changing, but it is not required for this hard cut. Canic must not
persist or reconstruct the epoch itself.

Domain recovery status is reported separately from timer status. An active
business operation, lease expiry or exact retry receipt must not be presented
as a provider callback generation or registration condition.

## Implementation Slices

### Slice A: Ownership And Durable-Fact Inventory

- freeze the exact source and dependency baseline;
- enumerate every public/internal timer surface and production call site;
- classify every native claim as fixed custody, transient application facade
  or unnecessary wrapper;
- classify every stable recovery field as business authority, derived view or
  shadow provider state;
- freeze owner-specific domain demand and retry facts; and
- publish the exact removal and propagation map before mutation.

### Slice B: Native Provider Surface Hard Cut

- remove public timer macros, facade and transient identities;
- remove duplicate directive/result types and conversions;
- make lifecycle and fixed callbacks return native results; and
- replace forwarding wrappers with calls on exact native registrations.

### Slice C: Async-Job Recovery Hard Cut

- rename and reshape the recovery boundary around business jobs;
- delete pending timer commands, schedule ownership and copied provider state;
- preserve exact-operation retry, attempt fencing and stale-completion denial;
  and
- hard-cut or remove the unreleased memory-ID-60 record.

### Slice D: Owner Reconstruction

- migrate auth renewal, cycle top-up and placement acknowledgement to their
  authoritative domain demand;
- reconstruct native schedules from current domain state; and
- prove interruption and same-operation retry owner by owner.

### Slice E: Control Plane, Lifecycle And Snapshot Propagation

- give pool maintenance direct native claim custody;
- harden watchdog boundaries;
- preserve lifecycle ordering and snapshot suspension; and
- update the runtime probe and role-specific fixtures.

### Slice F: Downstream Timer Adoption And Lifecycle Participation

- publish the direct native `ic-timers` migration guide and managed fixture;
- add the paired compile-time lifecycle participant to canonical root and
  managed non-root `canic::start!`;
- prove exact restore/participant/deferred-work ordering and rollback; and
- reject partial, async, unsafe, argument-taking, result-returning, duplicate
  and specialized-infrastructure declarations.

### Slice G: Combined Runtime Qualification

- compose one Canic-owned test canister with an exact test/dev IcyDB revision;
- prove one provider, one lifecycle export pair and both inventory owners;
- prove inactive restoration, callback/recovery progress and same-release
  reconstruction; and
- prove participant-trap rollback and corrected-cause retry.

### Slice H: Semantic Guards And Closeout

- replace the string-count inventory with ownership guards;
- prove one resolved provider and one shared inventory;
- remove obsolete docs, examples, metrics and test vocabulary; and
- publish exact closeout evidence before downstream mutation.

## Validation Requirements

The final proof must establish:

1. the dependency graph contains exactly one `ic-timers` package ID;
2. `ic-cdk-timers` occurs only beneath `ic-timers`;
3. no Canic type implements provider scheduling, recurrence, callback
   generations or pending-command arbitration;
4. no public application timer macro, facade, transient identity or Canic
   timer handle remains;
5. every live schedule, reconcile, cancel and unregister action invokes an
   exact native registration capability;
6. every retained claim is classified as bounded Canic custody;
7. stable state contains no provider handle, snapshot, generation, counter,
   registration condition, pending timer command or generic schedule-owner
   flag;
8. every durable deadline is independently justified and named by its domain;
9. install and post-upgrade reconstruct the fixed owner set in one shared
   inventory;
10. normal callback counters advance and native retry/stop semantics remain
    truthful;
11. traps or response loss after a recovery-significant effect preserve the
    same business operation identity;
12. one expired lease permits one fenced takeover and a stale completion
    cannot clear it;
13. snapshot suspension and resume restore domain demand before native
    scheduling without copying provider state;
14. every role exposes only its declared Canic jobs plus other framework
    owners present in the shared registry; and
15. runtime status remains a projection of the atomic provider inventory;
16. the maintained guide and fixture prove native application ownership with
    no replacement Canic scheduler;
17. canonical root and managed non-root lifecycle expansions invoke one paired
    synchronous participant after Canic restore and before deferred work;
18. malformed or excluded participant declarations fail compilation and the
    resulting Wasm retains one lifecycle export pair and unchanged Candid; and
19. the combined Canic/IcyDB fixture proves one provider, both owner rows,
    same-release reconstruction, rollback and corrected-cause retry.

The semantic guard must classify each production timer module or file as:

- fixed Canic consumer;
- private lifecycle consumer;
- native registration custody;
- domain async-job recovery;
- DTO/metrics projection; or
- prohibited/unexpected scheduling authority.

A frozen count of `TimerWorkflow::` or `TimerApi::` strings is not sufficient.

## Relationship To Other Designs

### 0.103

0.103 owns the public/internal Candid consolidation and makes accepted
operations self-advancing. 0.104 begins from that completed surface, inventories
its exact timer consumers and removes shadow timer mechanics without reopening
the accepted role methods or re-exposing private phases.

### 0.102

0.102 compact diagnostics are independent. Timer interruption work later
published in `v0.103.0` is useful implementation evidence but is not a
completed ownership hard cut. The tagged baseline still contains the shadow
scheduling state identified here.

### 0.105

0.105 owns framework-neutral local application authorization. It consumes the
synchronous lifecycle seam for combined stateful applications but owns no
timer registration or lifecycle export.

### 0.106

0.106 remains evidence-only platform qualification. Its approved repository
B1 may proceed, but the final current-state and timer-ownership inventory must
reconcile with accepted 0.104 before B2 or a successor consumes it as current
evidence.

### 0.107

0.107 Coordinator-backed root funding depends directly on 0.104 because its
automatic root top-up is a recovery-critical async timer consumer. It also
retains its separate 0.106 B1 ownership and current-cost evidence gate.

### 0.108

0.108 estate implementation depends on the completed 0.104 recovery boundary,
accepted 0.106 platform qualification and completed 0.107 root funding. Estate
parallelism does not reopen timer-provider ownership.

### 0.109 And 0.110

0.109 owns the explicit stop-the-world predecessor-to-successor adoption
exception. 0.110 consumes completed estate/funding/adoption views for a generic
read-only Fleet observatory. Neither reopens timer-provider ownership.
