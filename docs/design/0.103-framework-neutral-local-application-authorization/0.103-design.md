# Canic 0.103 Design: Framework-Neutral Local Application Authorization

Date: 2026-08-13

## Status

- Status: proposed for maintainer review; no implementation is authorized.
- Release boundary: reinstall only. A 0.103 canister does not decode, import,
  migrate or adopt delegated-session state from an earlier Canic release.
- Sequence: this line follows the
  [0.102 compact diagnostic-code design](../0.102-compact-diagnostic-codes/0.102-design.md)
  and reserves 0.103 ahead of the renumbered
  [0.104 transport groundwork](../0.104-cross-subnet-data-transport-groundwork/0.104-design.md).
- Cross-repository input: the read-only IcyDB 0.226 application-scoped SQL and
  schema read-authority proposal was inspected at its 2026-08-13 design cut.
  It is evidence of a general framework-integration gap, not Canic authority
  and not a Canic dependency.
- Dependency posture: Canic must not depend on IcyDB, and IcyDB must not depend
  on Canic. A consuming application may independently use both public crates
  and owns the explicit adapter between their small decision types.
- Protocol posture: pre-1.0 hard cut. Removed session records, APIs, methods and
  documentation disappear; there is no alias, decoder, fallback or dual path.

## Summary

Canic already verifies self-contained delegated tokens locally against the
current Fleet, Canister role, subject, scope and time window. It also retains a
bounded delegated session that maps one transport caller to an authenticated
subject. Those two capabilities do not currently compose:

- the session retains no verified issuer, Fleet, role or scope authority; and
- the scoped endpoint guard obtains its delegated token from Candid argument
  zero on every call.

That is appropriate for a Canic-owned proof-bearing endpoint, but it cannot
authorize an unchanged endpoint owned by another framework. A generated SQL
query with signature `(text) -> result`, for example, cannot acquire a new
Canic token argument without changing its ABI and coupling the framework to
Canic.

0.103 adds one generic bridge:

```text
proof-bearing session establishment
  -> verified, bounded local application authority
  -> synchronous read-only scope decision for the transport caller
  -> application-owned Allow/Deny adapter
  -> framework-owned endpoint and business policy
```

The bridge is not database-specific. It supports any library or application
surface whose ABI cannot carry Canic proof material on each call: generated
queries, schema readers, metrics viewers, search endpoints, media readers or
other bounded application-defined capabilities.

## Input From IcyDB 0.226

The IcyDB proposal establishes requirements that are useful beyond IcyDB:

1. application read authority must be independent of Canister controllership;
2. a coordinator-controlled child must still admit an authenticated human
   application subject;
3. the guarded endpoint ABI must not be forced to carry a foreign token;
4. the authorization decision must be synchronous, local, bounded, fail
   closed and free of query-time inter-Canister calls;
5. SQL text, schema data, rows and continuations must remain outside the auth
   decision;
6. expiry or revocation latency must have a finite, inspectable upper bound;
7. authority must survive same-release upgrade reconstruction; and
8. the application, not either framework, must map its capability vocabulary
   across the boundary.

Canic should solve the reusable authority problem once. It should not add an
`icydb`, `sql`, `schema`, `reader` or database-specific type, configuration
field, endpoint, record, metric or diagnostic.

## Current Canic Evidence And Gap

The 0.101.53 source establishes this baseline. Batch B1 must reproduce and
measure it before runtime mutation.

| Concern | Current owner and behavior | 0.103 gap |
| --- | --- | --- |
| Token verification | `AuthOps::verify_token` verifies proof, Fleet audience, current role, local scopes and expiry without a network call | The verified authority is returned only to the immediate proof-bearing request |
| Endpoint scoped auth | `auth::authenticated(scope)` decodes the token from ingress argument zero | An unchanged foreign endpoint has no token argument |
| Delegated identity | `ResolvedAuthenticatedIdentity` separates transport caller from authenticated subject | It carries no issuer, scope, Fleet, role, expiry or authority generation |
| Delegated session | one bounded wallet-to-subject record stores issue/expiry and a bootstrap fingerprint | It discards the verified local scopes and issuer evidence needed for later authorization |
| Session lookup | active lookup scans the bounded session vector and may prune expired state | A foreign synchronous guard needs a read-only lookup with measured maximum cost |
| Session bounds | current state limits sessions and bootstrap bindings globally and per subject | Scope bytes, scopes per session, lookup cost and stable bytes are not part of the session contract |
| Metrics | native access guards and session lifecycle paths have Canic metrics | A pure foreign-framework guard must not depend on a hidden Canic mutation for correctness |
| Inspection | a caller can read its delegated subject through the runtime helper | Operators cannot inspect the complete local authority and finite expiry bound |

The current cryptographic verifier is the authority to reuse. 0.103 must not
introduce a second reader registry, whitelist, token format, signature scheme,
grant store or issuer policy.

## Decision

0.103 replaces the subject-only delegated session with a scoped local
application session established from one fully verified delegated token.

Session establishment verifies the token against the receiver's current
Fleet, role, verifier configuration, accepted proof policy and time. It then
stores only the bounded authority required for later local decisions. The
token and signature bytes are not persisted.

The public runtime facade exposes one synchronous decision:

```rust
pub struct LocalApplicationAuthorizationRequest<'a> {
    pub observed_transport_caller: Principal,
    pub required_scope: &'a ApplicationScope,
}

pub enum LocalApplicationAuthorizationDecision {
    Allow(AuthorizedApplicationSubject),
    Deny(LocalApplicationAuthorizationDenial),
}

pub struct AuthorizedApplicationSubject {
    pub subject: Principal,
    pub issuer: Principal,
    pub expires_at_ns: u64,
}
```

The names are conceptual until B1 approves the exact public surface. The
contract is normative:

- the function is synchronous and performs no `await` or inter-Canister call;
- the framework-observed caller is explicit and must equal the current IC
  transport caller before policy evaluation;
- the scope is one bounded canonical Canic application-scope identity;
- success returns only verified subject context useful to the application;
- denial is a closed machine-readable enum with no producer-owned prose;
- missing state, disabled auth, stale binding and expiry fail closed; and
- evaluation does not mutate, prune, log or schedule work.

The application adapter maps that decision to the framework it uses:

```rust
fn may_read(context: ForeignReadContext) -> ForeignDecision {
    match canic::access::application::authorize(
        context.caller,
        &MY_APPLICATION_READ_SCOPE,
    ) {
        LocalApplicationAuthorizationDecision::Allow(_) => ForeignDecision::Allow,
        LocalApplicationAuthorizationDecision::Deny(_) => ForeignDecision::Deny,
    }
}
```

This example deliberately contains no IcyDB type or scope name. Each consuming
application owns the actual adapter and its capability mapping.

## Canonical Ownership

| Owner | Responsibility |
| --- | --- |
| Canic token authority | proof verification, Fleet/role binding, scope subset, time bounds and issuer trust |
| Canic local session | bounded materialized authority, exact caller binding, expiry, generation binding, lookup and cleanup |
| Canic public facade | synchronous request/decision types and fail-closed local evaluation |
| Consuming application | declaration of application scopes and explicit mapping to framework surfaces |
| Foreign framework | endpoint generation, call ordering, public denial mapping, business safety and response bounds |
| Client | token acquisition, one explicit session-establishment call, expiry-aware renewal and caller changes |
| Host/operator | configuration inspection, capacity and expiry reporting, diagnostics and reconciliation |

Canic does not decide whether SQL is read-only, which table a caller may read,
which project a subject owns, or which framework error is returned. A foreign
framework does not decode Canic tokens, inspect Canic stable state or define
Fleet revocation.

## Scoped Application Session

The current subject-only record is replaced, not extended in parallel. The
conceptual current record is:

```rust
pub struct LocalApplicationSessionRecord {
    pub transport_caller: Principal,
    pub authenticated_subject: Principal,
    pub issuer: Principal,
    pub fleet: FleetKey,
    pub role: CanisterRole,
    pub scopes: Vec<ApplicationScope>,
    pub authority_generation: u64,
    pub issued_at_ns: u64,
    pub expires_at_ns: u64,
    pub certificate_hash: [u8; 32],
    pub bootstrap_token_fingerprint: [u8; 32],
}
```

Exact persisted fields remain a B1/B2 decision. The record must retain enough
evidence to prove that the decision is still bound to:

- the exact transport caller used to establish it;
- the verified authenticated subject;
- one verified issuer;
- the current Fleet and Canister role;
- the normalized local scope subset;
- the local verifier-authority generation; and
- the minimum token, certificate, requested-session and configured maximum
  expiry.

The record must not retain:

- encoded token, certificate or signature bytes;
- arbitrary token extension data;
- application rows, object identifiers or entitlement records;
- framework names, methods or denial prose; or
- authority for any Fleet or role other than the receiving Canister.

Scopes are sorted, deduplicated and bounded before persistence. A session
cannot gain a scope that the token verifier did not return for the receiver's
current role.

## Session Establishment And Removal

0.103 defines one standard Canic-owned establishment operation on roles that
enable local application authorization. Conceptually:

```text
canic_establish_application_session(token, requested_ttl_secs)
canic_clear_application_session()
canic_application_session_status()
```

Exact method spelling and DTOs are frozen in B1. They follow these rules:

1. the transport caller is read from ingress and cannot be supplied in the
   request;
2. anonymous and infrastructure identities are rejected;
3. the complete token is verified once against current local authority;
4. subject, issuer and local scopes are derived from verified output, never
   copied from unverified request fields;
5. effective expiry is the earliest applicable verified/configured bound;
6. token-fingerprint replay is idempotent only for the exact same active
   caller, subject and authority;
7. replacement is atomic and never temporarily widens authority;
8. capacity rejection leaves the previous session unchanged;
9. clear removes only the authenticated caller's session; and
10. status returns bounded non-secret authority metadata for that caller.

The current `set_delegated_session_subject`, `delegated_session_subject` and
their subject-only storage shape are removed. Their names are not retained as
aliases. A controller-only aggregate inspection surface may report bounded
counts and policy, but no public operation enumerates bearer principals or
token fingerprints.

## Local Authorization Algorithm

For request `(observed_transport_caller, required_scope)`, Canic:

1. reads the current IC transport caller and requires exact equality with the
   framework-observed caller;
2. rejects anonymous;
3. loads the exact session indexed by transport caller;
4. compares current time with the exclusive effective expiry;
5. compares the record's Fleet, role and authority generation with current
   protected local state;
6. validates the retained subject is still an admissible application subject;
7. performs an exact canonical-scope membership test; and
8. returns the subject context or one closed denial reason.

No step calls the parent, root, Coordinator, issuer, management Canister or a
remote policy service. No step parses endpoint payload, enters application
storage, observes foreign-framework readiness or changes session state.

Expired cleanup is a separate bounded maintenance operation. Authorization
may observe an expired record and deny it, but it never prunes during the
decision. This preserves a side-effect-free application-guard contract.

## Scope Contract

`ApplicationScope` is a bounded canonical identity, not an open diagnostic
string and not an enum owned by Canic product features.

B1 must freeze:

- allowed byte length and character grammar;
- canonical case and namespace separator;
- maximum scopes per role token grant and retained session;
- sorting, deduplication and encoded-size rules; and
- whether current broad constants such as `read` remain valid or are replaced
  by explicitly namespaced application scopes.

Canic validates and compares scope identity. The application owns meaning. A
database application may map separate application scopes to row-read and
schema-read guards, but those names live in that application configuration,
not in Canic or IcyDB.

The later
[0.106 authentication-profile design](../0.106-declarative-authentication-profiles/0.106-design.md)
must compile these same scope identities into profiles. It must consume the
0.103 session and decision contract rather than create a second tokenless
authorization store.

## Proof-Bearing And Session-Bearing Lanes

Two caller evidence shapes remain useful:

- a Canic-owned endpoint may carry a delegated token and verify it on the
  request; and
- an unchanged application/framework endpoint may use a previously
  established local session.

These are not two grant authorities. Both lower to one internal
`VerifiedApplicationAuthority` projection and one exact Fleet/role/scope
policy. The proof-bearing lane does not persist a session implicitly. The
session-bearing lane never fabricates or expands proof authority.

0.103 must remove duplicate subject-binding, scope-matching, expiry and denial
classification logic exposed by this unification. It must not retain the old
subject-only session as a compatibility lane.

## Expiry, Policy Change And Revocation

The first authority guarantee is bounded expiry, not instantaneous global
revocation.

- Caller-initiated clear is immediate on that Canister.
- Session expiry is no later than token expiry, certificate expiry, requested
  TTL and configured session maximum.
- A locally activated verifier-authority generation change invalidates every
  session bound to the previous generation immediately on that Canister.
- Issuer-policy removal without a locally activated generation change takes
  effect no later than the published maximum session lifetime.
- No documentation may call the authority instantly revocable across a Fleet
  unless measured propagation and local generation activation prove it.

B1 must decide and publish the default and maximum session TTL. It should be
substantially narrower than the broad token ceiling when sessions protect
tokenless public methods. The operator surface reports the exact maximum
staleness window.

Per-subject business entitlement remains application state. If an application
requires immediate per-resource revocation, it performs that local resource
check after Canic authenticates and scope-authorizes the subject. Canic does
not mirror that entitlement into a second grant store.

## Lifecycle And Same-Release Recovery

Session authority is restored synchronously with Canic invariants before user
hooks or deferred application work. `canic::start!` remains thin; the lifecycle
adapter restores any lookup index and validates the current authority
generation without `await`.

Same-release upgrade must preserve active current-format sessions and rebuild
derived indexes deterministically. Interrupted session establishment is
atomic: exact retry either observes the already-applied binding or applies it
once. Backup and restore use one canonical current snapshot shape.

Cross-release state is unsupported. A pre-0.103 session record is not decoded,
imported or upgraded in place.

## Bounds And Performance

B1 records current limits and selects explicit 0.103 limits for:

- active sessions per Canister;
- active sessions per authenticated subject;
- retained bootstrap replay bindings;
- scopes per session;
- scope identity and aggregate encoded bytes;
- session TTL;
- status page size; and
- cleanup work per invocation.

The authorization hot path must be `O(log G + S)` or better, where `G` is the
bounded active-session count and `S` is the bounded scopes in the selected
session. It must not scan every session, token binding, application row,
schema item or operational receipt. If the canonical snapshot remains a
vector, a derived exact-caller index is restored synchronously and cannot
become a second authority.

Measurements distinguish:

| Symbol | Measurement |
| --- | --- |
| `E` | session-establishment instructions, including cold and warm proof verification |
| `A` | local authorization instructions at 1, median and maximum admitted `G` and `S` |
| `D` | denied authorization instructions by anonymous, missing, expired, stale-generation and missing-scope reason |
| `B` | stable bytes per active session and replay binding |
| `R` | synchronous restore/index reconstruction instructions at maximum state |
| `M` | raw non-gzipped Wasm delta for the representative configured canister |

Acceptance budgets are frozen after B1 baseline review. Gzip is secondary
artifact context, never the authoritative footprint measurement.

## Diagnostics, Metrics And Inspection

The public foreign-framework decision exposes a closed denial enum. Under the
0.102 contract, any public Canic endpoint failures receive registered numeric
codes and host-owned prose. Arbitrary token, verifier or application error text
does not cross the foreign endpoint boundary.

Canic records bounded session lifecycle metrics:

- establishment started/completed/rejected;
- creation/replacement/idempotent replay;
- clear/expiry/cleanup;
- capacity rejection; and
- authority-generation invalidation.

Native Canic endpoint guards may retain bounded decision metrics. The pure
foreign-framework decision function does not mutate metrics or logs; the
framework wrapper owns aggregate allow/deny measurement for its endpoint.
Neither side records token bytes, SQL, application payloads, principals or
resource identifiers.

Self-status and controller/operator inspection report:

- enabled/disabled state;
- current Fleet, role and authority generation;
- normalized scopes for the caller's own active session;
- issuer, issue time, effective expiry and remaining lifetime;
- configured global/per-subject capacity and current aggregate counts; and
- the maximum policy-removal staleness bound.

The operator view distinguishes declared configuration, current protected
runtime binding and observed session state. It never claims that a guard path
alone answers which application subjects own which resources.

## Alternatives Rejected

### Add A Canic Token To Every Foreign Endpoint

Rejected. It changes the framework's maintained ABI, forces its generator and
clients to understand Canic, and repeats proof bytes and verification work on
every read.

### Let The Foreign Framework Store Canic Grants

Rejected. It creates a second auth authority, duplicates expiry/revocation
policy and makes the framework depend on Canic token semantics.

### Use Controllers Or A Principal Whitelist

Rejected. Controllers carry lifecycle authority, while a whitelist loses the
verified subject/Fleet/role/scope policy and becomes another grant store.

### Call A Parent Or Issuer During Authorization

Rejected. Query-time remote authority adds latency, availability coupling and
uncertain cache/revocation semantics. The current token already proves the
authority locally.

### Make Every Foreign Surface A Hand-Written Wrapper

Rejected as the standard integration. It is possible today, but forfeits the
framework's generated ABI, call ordering, diagnostics and tooling contract.
It remains a valid application choice when standard framework integration is
not needed.

### Retain Both Subject-Only And Scoped Sessions

Rejected. Two current session meanings would duplicate identity resolution and
permit accidental authorization through the weaker record. 0.103 hard-cuts to
one scoped representation.

## Complexity Gate

The justified state-space delta is one current bounded session meaning, one
closed decision and one exact-caller lookup index. The session replaces an
existing weaker record; it is not an additional grant lifecycle.

Promotion fails if implementation adds a generic policy language, dynamic
predicate registry, application entitlement table, per-framework adapter in
Canic, remote decision cache, unbounded scope/session state, second token
format or second session authority. Each batch reports source/owner delta,
duplicate flows removed, stable bytes, instructions, restore cost and raw
Wasm, plus whether the maintained structure became simpler, neutral or more
complex.

## Security Invariants

1. Application read authority never implies controller or Canister lifecycle
   authority.
2. Session establishment derives subject, issuer, Fleet, role and scopes only
   from fully verified token authority and protected local state.
3. Anonymous, missing, expired, stale and unavailable authority fails closed.
4. The framework-observed caller must equal the current IC transport caller,
   which is explicitly and exactly bound to one local session.
5. A retained scope is never broader than the verified grant for the current
   Canister role.
6. A session cannot outlive its token, certificate, requested TTL or configured
   maximum.
7. Authority evaluation performs no network call, `await`, mutation, pruning,
   payload parsing or application-storage access.
8. Current Fleet, role and authority-generation mismatch invalidates the
   session.
9. Topology and infrastructure predicates continue to consume the raw
   transport caller, never the authenticated application subject.
10. Authentication and endpoint scope do not imply resource ownership.
11. Token/signature bytes and application entitlement data are not persisted
    in the session.
12. Session state and every index, scope and cleanup operation are bounded.
13. Exact retry cannot widen or duplicate authority.
14. The public facade and storage contain no foreign-framework identity.
15. No controller bypass, whitelist fallback or `controller OR session` rule is
    implicit.
16. No compatibility decoder, alias, shim, legacy fallback or dual session
    format exists.

## Layer Ownership

The maintained dependency direction remains:

```text
endpoints -> workflow -> policy
                     +-> ops -> model
```

| Layer | 0.103 responsibility |
| --- | --- |
| `dto` | passive establishment/status boundary data only |
| `model` | current session record, capacity and snapshot invariants |
| `ops` | token-to-record conversion, exact lookup, time/config reads and storage operations |
| `policy` | pure expiry, binding, scope and replacement decisions |
| `workflow` | verify-establish, clear, cleanup and same-release retry orchestration |
| `access` | synchronous public local decision and shared verified-authority projection |
| endpoints/macros | authenticate, marshal and delegate immediately |
| facade | stable framework-neutral types and helpers |
| host/CLI | declared/observed inspection and rich diagnostic catalogue |

Policy does not read stable state, call the IC, record metrics or depend on a
DTO. Workflow does not construct or mutate records directly. Session restore
is synchronous lifecycle work, not a user hook.

## Scope

0.103 includes:

- the current-state and cost baseline;
- one bounded canonical application-scope identity;
- one verified internal application-authority projection;
- a hard-cut scoped local session record and lookup;
- standard establish, clear and self-status operations;
- one synchronous framework-neutral authorization facade;
- shared proof-bearing/session-bearing policy without duplicate grant stores;
- exact expiry and local authority-generation invalidation;
- bounded lifecycle, security, inspection and metrics evidence;
- a generic unchanged-ABI consumer fixture; and
- documentation showing an application-owned adapter without importing a
  foreign framework into Canic.

## Non-Goals

0.103 does not:

- add an IcyDB, SQL, schema, database or reader-specific contract;
- modify IcyDB or any other downstream repository;
- add a reader registry, application entitlement database or resource policy;
- add public anonymous authorization;
- pass tokens, scopes or auth blobs through a foreign endpoint ABI;
- add async or remote authorization, parent callbacks or cached remote
  decisions;
- make controllers implicit readers;
- define row-, field-, tenant-, project- or object-level access;
- replace the complete declarative authentication-profile work now assigned to
  0.106;
- preserve a pre-0.103 session record or method;
- promise instantaneous Fleet-wide revocation without measured propagation;
- add provider- or wallet-specific runtime types;
- resolve competing Canister lifecycle-macro or timer ownership between Canic
  and a foreign runtime; that composition is an independent prerequisite; or
- change foreign-framework diagnostics, readiness, parsing or business safety.

## Relationship To IcyDB 0.226

If both independent designs are implemented, a consuming application can:

1. obtain a Canic delegated token through the maintained client/auth flow;
2. call the Canic-owned session-establishment method on the target child;
3. declare separate application scopes for its SQL and schema surfaces;
4. implement two small synchronous IcyDB guards that map caller plus surface to
   Canic's local decision;
5. collapse every Canic denial to IcyDB's surface-specific policy denial; and
6. retain IcyDB's unchanged SQL/schema Candid, guard ordering, readiness and
   read-only execution rules.

Canic never imports IcyDB. IcyDB never imports Canic. The application package
is the only composition root and owns both scope constants and adapters.

Canic closeout does not require an IcyDB release. It proves the generic
contract with a local fixture whose guarded method has an unchanged payload
signature and whose adapter depends only on public Canic types. IcyDB's
cross-repository adoption and real Explorer evidence remain owned by IcyDB.
Any live combined runtime also waits for the independently owned lifecycle
composition required by IcyDB 0.225; 0.103 does not hide or duplicate that
work inside authorization.

## Relationship To Renumbered Designs

- 0.104 transport groundwork remains independent and consumes no application
  session authority.
- 0.105 Coordinator Workers remain infrastructure callers and must not be
  authenticated as application subjects.
- 0.106 declarative authentication profiles become the canonical source of
  login-time grants and must reuse the 0.103 scope/session/decision path.
- 0.107 standalone blob extraction cannot retain Canic sessions in the
  external service implicitly; any integration is an ordinary application
  adapter.
- 0.108 funding, 0.109 archives, 0.110 language-neutral guests, 0.111
  observability and 0.112 Canister estates do not gain user authority merely
  by observing a successful local application decision.

## Required Qualification

0.103 is complete only when:

1. the subject-only session record and APIs are removed without aliases;
2. one verified token establishes only its exact local Fleet/role scopes;
3. a foreign-style endpoint with unchanged payload ABI authorizes through the
   public synchronous facade;
4. the application adapter is the only place that maps scope to foreign
   surface;
5. anonymous, substituted-caller, missing, forged, expired, wrong-Fleet,
   wrong-role, missing-scope and stale-generation cases fail closed;
6. a controller receives no implicit application access;
7. the decision performs no query-time call, mutation, prune, payload parse or
   application-state read;
8. lookup and restore remain within accepted maximum-cardinality budgets;
9. exact replay and replacement do not widen authority;
10. current-format sessions reconstruct across same-release upgrade;
11. expiry/revocation latency is finite, measured and visible;
12. Canic metrics and inspection expose bounded useful state without secrets;
13. proof-bearing and session-bearing lanes share one policy and verified
    authority projection;
14. no Canic source, config, state, Candid, metric or diagnostic names IcyDB or
    a database concern;
15. no dependency from Canic to IcyDB or IcyDB to Canic exists;
16. the 0.106 profile design consumes this contract without a second session
    authority; and
17. raw non-gzipped Wasm, stable bytes, instructions, Candid and complexity
    deltas are reviewed and accepted.

## Promotion Gate

Implementation may begin only after:

1. B1 freezes the exact current source, state, Candid, scope and performance
   baseline;
2. maintainers approve scoped session materialization over the alternatives of
   changing every foreign ABI or adding a second reader registry;
3. exact public type/method names, scope bounds, cardinality, TTL and authority
   generation semantics are accepted;
4. the 0.102 diagnostic allocation path for new public failures is identified;
5. the 0.106 profile design is reconciled to reuse this one session authority;
   and
6. the maintainer explicitly authorizes mutating B2-B7.

Until then, this document and its tracker authorize design and inventory work
only. They authorize no runtime, Candid, persisted-state, package-version,
changelog-version or downstream-repository mutation.
