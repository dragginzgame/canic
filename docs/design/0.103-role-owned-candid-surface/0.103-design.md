## Decision

Canic exposes one bounded control plane per canister role. Compile-time
capabilities extend that role's command and status variants; they do not create
endpoint families.

The central invariants are:

1. roles own methods;
2. capabilities own variants;
3. callers own authority; and
4. workflows own phases.

The four Canic-owned role surfaces are:

- Fleet Subnet Root;
- Fleet Coordinator;
- Wasm Store; and
- managed application canister, whose exact protocol is determined by its
  mandatory and optional compiled capabilities.

Everything else is a caller, command variant, status variant, externally
mandated protocol, Store byte lane, application-owned method or private
workflow state.

Canic's role surface describes authorized intent and observable result, never
the private steps used to produce that result.

Commands owned by the same role and execution mode are composed as bounded
Candid variants; authority is variant-specific. A caller submits one
high-level intent. Only an intent that genuinely spans asynchronous or durable
workflow boundaries receives a replay-safe operation identity and local
operation status while Canic advances it through its internal state machine.
An atomic synchronous command returns its typed response without acquiring an
operation record, retention policy or operation-status entry. A caller never
selects or drives allocation, creation, installation, commit, directory,
runtime, membership, draining, reclamation or deletion phases.

Canic does not replace 118 methods with one cross-role universal command enum.
`RootCommand`, `CoordinatorCommand`, `StoreCommand` and `CanisterCommand` are
four separate closed protocols emitted only by their owning role. Each role
normally exposes one control update and one observation query. Update,
ordinary-query and genuinely necessary composite-query execution modes remain
distinct, and Store bytes may use narrowly justified data-plane methods.

Different caller authority is expressed by variant authorization inside the
owning role method. A controller, peer Root, Coordinator, managed child or
other admitted caller does not acquire a separate method merely because its
authority differs.

Root identity, a Cargo dependency and the availability of implementation code
do not by themselves emit every Canic endpoint. Each canister receives only
the compile-time protocol capabilities required by its declared role and
application configuration. `canic::start!` remains a thin lifecycle and
endpoint-emission bridge.

## Problem

The current facade maps much of Canic's workflow structure directly to IC
methods. Examples include separate methods for:

- Component allocation and allocation status;
- create, install and commit;
- directory preparation, runtime activation and membership activation;
- peer and child variants of the same phases;
- draining begin, quiescence, advance and final inventory;
- subtree stop preparation, stop, delete preparation, delete, membership
  removal, directory synchronization and leaf finalization;
- Fleet Registry synchronization and mirror activation plus separate status;
  and
- Store reclamation, binding finalization and deletion plus separate status.

This shape originally made each crash-safe multi-message transition directly
retryable. It also gave every transition its own static authorization macro,
payload limit, DTO pair, protocol string and focused test. Those properties
are useful, but the public method boundary is the wrong owner for them.

The consequences are material:

1. callers must understand Canic's internal state machine;
2. protocol method names become coupled to implementation phases;
3. every new phase multiplies Candid, protocol constants, generated clients,
   replay declarations, tests and documentation;
4. broad bundles make small applications inherit unrelated Fleet machinery;
5. auth and recovery review is spread across too many entry points; and
6. the actual product contract is difficult to see in a generated service.

This is architectural debt, not evidence that all current endpoints are
unauthenticated. Existing mutating methods generally enforce controller or
internal authority. The hard cut reduces the surface on which those
invariants must be maintained.

## Goals

0.103 must:

1. freeze every emitted method by role, execution mode, visibility, caller
   authority, payload bound, replay policy, workflow owner and in-repository
   caller;
2. distinguish user/operator intent, internal inter-canister protocol,
   observation and private workflow phase;
3. remove every externally driven phase whose only purpose is advancing one
   already accepted operation;
4. replace the current surface with four role-owned command/status protocols
   containing bounded named variants;
5. return a replay-safe operation receipt for asynchronous high-level intent
   and expose its observation through the owning role's status variants;
6. make accepted workflows advance and recover without callers selecting the
   next internal phase;
7. enforce variant-specific authority before command workflow dispatch or
   sensitive status access and variant-specific payload bounds before side
   effects;
8. make compile-time capabilities prune unavailable command/status variants,
   DTOs, public handlers, constants, Candid types and protocol reachability
   without adding methods; private timer-provider reachability remains 0.104's
   explicit hard cut;
9. update all Canic-owned inter-canister callers, host/CLI callers, generated
   bindings, replay manifests and fixtures in the same hard cut;
10. remove old method constants, endpoint functions, DTOs and documentation
    rather than retaining aliases; and
11. install generated-Candid count and forbidden-phase guards.

## Non-Goals

0.103 does not:

- define application-specific waveform, burn or run-control methods;
- implement the 0.104 timer-mechanics hard cut;
- change Fleet-estate policy, Coordinator funding or observatory presentation;
- add local application authorization owned by 0.105;
- create a runtime endpoint registry, callback registry or dynamically loaded
  protocol;
- combine updates and queries into one IC method;
- make one unbounded `Command`, `Request`, `Response` or byte-blob protocol;
- create a shared cross-role command or status enum;
- weaken caller, Fleet, Subnet, parent, subject or audience binding;
- preserve old methods as deprecated wrappers;
- add a `v2` product protocol or negotiate between protocol generations; or
- add cross-release upgrade, migration, adoption or mixed-version behavior.

## Execution-Mode Boundary

An IC method has one execution mode. Therefore a role may normally expose:

1. one `canic_command` update when at least one Canic-owned mutating command
   variant is compiled; and
2. one `canic_status` ordinary query containing every locally answerable
   bounded observation variant.

A role may expose one additional composite-status method only when B1 proves
that a remote query is an unavoidable part of the current protocol rather
than missing local evidence. The exception belongs to the role; it does not
create a capability family.

The preferred shape has no composite operation-status method. A mutating or
remote refresh is itself a replay-safe command; status reads locally owned
state after that command progresses.

Normative standards whose method names are externally defined, including
enabled ICRC methods, remain separately named and counted. Wasm Store byte
transport may also remain separate when its materially different payload or
response bounds cannot safely share the small control method. Every exception
is enumerated and justified in B1; convenience is not an exception.

## Role-Owned Surfaces

The Canic-owned control method names are `canic_command` and `canic_status` on
each role that emits them. B1 freezes their exact role-specific variant/type
manifest and any separately admitted exception:

| Role | Normal Canic-owned surface | Capability effect |
| --- | --- | --- |
| managed application canister | `canic_status`; optional `canic_command` only when a legitimate mutating variant exists | mandatory/optional capabilities compile status and command variants in or out |
| Fleet Subnet Root | `canic_command` and `canic_status` | provisioning, registry, topology, funding and estate capabilities add role variants |
| Fleet Coordinator | `canic_command` and `canic_status` | Registry, placement and treasury capabilities add role variants |
| Wasm Store | `canic_command`, `canic_status` and only proven byte-transport lanes | publication, GC, reclaim and deletion remain control variants; bytes may use bounded data methods |

There is no shared-runtime, root-operator, root-peer, operation-status,
funding, estate, auth, metrics or logs endpoint family. Those concepts become
variants on the owning role. In particular, a peer Root calls the destination
Root's ordinary `canic_command`; exact peer authority is a property of the
selected `RootCommand` variant.

Application-owned methods remain application-owned and are listed separately
in the generated surface report. A Fleet Subnet Root does not emit Coordinator
methods merely because `canic-control-plane` is linked.

Whenever Canic emits `canic_command` or `canic_status`, that name is reserved
for the generated role surface. `canic::build!` rejects an application-owned,
standard or manually declared method with the same name before Candid
generation. A collision is a build error, never macro-order-dependent method
replacement or ambiguous merged Candid.

The exact capability declaration syntax is a B1 decision. It must be static,
closed and validated during `canic::build!`; it may be derived from protected
application configuration and package metadata. It must not be a runtime
registry. Unknown, contradictory or role-incompatible capability declarations
fail the build.

B1 binds the exact role/capability profile and generated Candid into protected
external artifact, release-set or Directory metadata. That metadata selects
the binding before the first role call. The mandatory bounded `Overview`
variant reports the same immutable identity only for verification; it never
bootstraps decoding, negotiates a schema, gains another method or becomes
mutable runtime authority.

## Protocol Shape

Every role conceptually follows the same two-method control plane, while the
types remain role-specific:

~~~text
Fleet Subnet Root
  canic_command(RootCommand) -> Result<RootCommandResponse, Error> update
  canic_status(RootStatusRequest) -> Result<RootStatusResponse, Error> query

Fleet Coordinator
  canic_command(CoordinatorCommand)
      -> Result<CoordinatorCommandResponse, Error> update
  canic_status(CoordinatorStatusRequest)
      -> Result<CoordinatorStatusResponse, Error> query

Wasm Store
  canic_command(StoreCommand) -> Result<StoreCommandResponse, Error> update
  canic_status(StoreStatusRequest) -> Result<StoreStatusResponse, Error> query
  plus only accepted bounded byte-transport methods

managed application canister
  canic_command(CanisterCommand)
      -> Result<CanisterCommandResponse, Error> update  // omitted when empty
  canic_status(CanisterStatusRequest)
      -> Result<CanisterStatusResponse, Error> query
~~~

Each command is a named Candid variant with a named payload structure. An
atomic synchronous command returns a named bounded response. Only a command
that genuinely crosses asynchronous or durable workflow boundaries returns an
operation receipt. DTOs remain passive boundary data. There is no boundary
type alias, arbitrary map, unbounded byte field or stringly typed method
selector.

Where a role owns durable operations, operation observation is a status
variant such as
`RootStatusRequest::Operation(operation_id)`, not an operation method. Metrics,
logs, readiness, cycles, identity, directories and bounded diagnostics are
status variants unless they satisfy the endpoint-admission rule below.

The final B1 manifest must show which role variant or permitted exception
replaces each current method. A former phase name may survive as an internal
workflow function or state variant, but not as a Candid method merely to
retain the old call sequence.

## Endpoint-Admission Rule

A new Canic-owned method is forbidden unless B1 proves one of these conditions:

1. IC execution mode requires separation between update, ordinary query and a
   genuinely necessary composite query;
2. materially different transport/resource characteristics require a Store
   byte lane that cannot safely share the bounded control surface;
3. an external normative standard fixes the method name and interface; or
4. an IC-specific protocol mechanism fundamentally cannot be represented by
   the existing role method.

The following are explicitly invalid reasons for another method:

- a different caller authority;
- a different compiled capability or feature flag;
- a different command, operation, workflow or internal phase;
- a different error or producer;
- parent, child, peer or controller direction; or
- CLI, UI, test or implementation convenience.

## B1 Endpoint Disposition

Every current exported method receives exactly one disposition:

| Disposition | Required result |
| --- | --- |
| role command variant | move the high-level intent into the owning role's `canic_command` type and variant-aware dispatcher |
| role status variant | move the bounded observation into the owning role's `canic_status` request/response types |
| Store data plane | retain or replace it only under accepted byte-transport/resource evidence |
| externally mandated standard | retain the exact externally owned name/interface and identify its authority |
| application-owned | report it separately and leave its ABI under the application owner |
| private/delete | make it workflow-private or remove it and delete every public caller/constant/DTO residue |

The B1 review is not a method-grouping exercise. Each current method is
presumed `private/delete` until evidence proves that it is a role command
variant, role status variant, admitted Store byte lane, external standard or
application-owned method. Remaining capacity under a numeric ceiling is not
evidence.

There is no seventh “temporarily separate,” “internal protocol,” “peer,”
“operation,” “admin” or “diagnostic” disposition. A cross-canister method is
still classified by the receiving role; its caller authority does not own its
surface.

## High-Level Intent Rule

A Candid command is justified only when it requests a distinct authorized
outcome. It is not justified merely because the implementation crosses an
`await`, management-Canister call, timer delivery or stable transition.

A durable operation identity is justified only when the accepted command
genuinely spans asynchronous or durable workflow boundaries. A synchronous
mutation that validates, commits and responds atomically has no operation
record, operation state, cleanup/retention policy or
`StatusRequest::Operation` entry.

A top-level command variant is named for one authorized outcome. Caller class,
physical module, former endpoint family and implementation layer do not own
command taxonomy. Catch-all selectors such as `Admin`, `Peer`, `Internal`,
`Workflow` or `Legacy` may not contain the former method tree. A peer-related
word is admissible only when it names the actual outcome, never as a bucket for
commands distinguished solely by peer authority.

Examples:

| Current shape | 0.103 disposition |
| --- | --- |
| allocate -> create -> install -> commit -> directory -> runtime -> membership | one provision command variant and one operation-status variant |
| begin draining -> quiesce -> finalize inventory -> delete -> remove membership | one remove command variant and one operation-status variant |
| prepare subtree stop -> stop -> prepare delete -> delete -> synchronize -> finalize | one subtree-removal command variant and one operation-status variant |
| registry synchronize -> poll -> activate mirror -> poll | one synchronization intent whose status includes observed and activated revisions |
| Store reclaim -> finalize binding -> delete | one Store-removal command variant and one operation-status variant |

An explicit `Resume`, `Abort` or `RetryExact` command variant may exist when it
represents a real operator decision. It addresses an operation identity and
asks the owning reconciler to continue or stop. It never selects the next
private phase or supplies replacement authority for an uncertain effect.

## Autonomous Operation Contract

Every asynchronous high-level command has one authoritative durable operation
identity. Its owning workflow records enough state to provide:

- exact idempotent acceptance;
- conflict rejection when the same identity is paired with different
  authority or payload;
- current state, progress and terminal outcome;
- the last completed durable boundary;
- unresolved external-effect exposure where applicable;
- safe same-release interruption recovery; and
- bounded retention and cleanup.

The operation record remains domain-owned. 0.103 does not create a universal
stable workflow database and workflow may not construct or mutate records
directly. Existing model/ops boundaries are reused or hard-cut by their owner.

After acceptance, Canic runs the next eligible transition itself. It may use
the current scheduling and async-job recovery seam only as an interim
consumer. It must not add timer mechanics, copied provider state or a second
scheduler. 0.104 inventories the resulting consumers and completes the timer
ownership hard cut.

Uncertain paid or controller-mutating effects retain the existing strict rule:
no timeout, transport failure or stale observation is converted into a fresh
effect identity unless absence of the original effect is proved. Endpoint
consolidation cannot weaken exact replay, receipt or lease fencing.

## Authorization

Authorization remains endpoint-owned even when several variants share one
method. Both the command and status dispatchers:

1. decode the bounded request and selected variant;
2. derive the exact variant authority requirement;
3. read caller and protected authority inputs once;
4. reject before command workflow, sensitive state access or view projection
   when authority is absent; and
5. delegate immediately to the matching workflow or read owner.

The dispatcher is not an authorization bypass. Each B1 mapping records the
old authority predicate and the new command/status variant predicate.
Controller, exact infrastructure peer, protected operator and public
observation variants may share one role method only when dispatch makes their
distinct policy explicit and tests every cross-variant denial. A query is not
implicitly public: public readiness and protected topology, directory, log or
operation observations remain independently authorized variants.

For updates, `inspect_message` and replay classification also become variant-
aware. Ingress inspection decodes only within the method and variant bounds
and may reject early, but the update endpoint repeats authoritative caller and
protected-state validation before workflow dispatch. Replay policy is owned by
the selected command variant, not inferred only from the common method name.

Internal authority continues to bind caller, Fleet, Subnet, parent, subject
and audience wherever the current protocol requires them. Method-name
consolidation does not authorize a caller to choose a more privileged variant.

## Payload And Resource Bounds

One command method has one outer ingress ceiling. Therefore:

- ordinary command variants share a deliberately small maximum encoded size;
- each variant validates its stricter exact bound before state mutation;
- large artifact bytes use only an accepted Store data-plane method;
- response variants and status pages retain explicit item and byte limits;
- unknown tags and malformed data fail before workflow dispatch; and
- a large-payload exception cannot become a generic escape hatch for ordinary
  commands.

B1 records the current and proposed maximum for every variant. B2 adds
first-excess tests at both the method and variant boundary.

## Error Composition

0.103 consumes the completed 0.102 compact diagnostic contract. It does not
create one new public error enum for every former endpoint.

All role methods return the maintained compact `Error` boundary for failure.
Operation-specific nonfailure state belongs in the owning status-response
variant. Internally, domain owners retain finite typed causes where recovery
or policy needs them and explicitly project qualifying failures to the compact
diagnostic identity. Error composition must reduce endpoint-specific
vocabulary, not replace method proliferation with error-type proliferation.

## Compile-Time Emission

`canic::start!` stays thin. It may invoke generated endpoint-emission macros,
but it does not inspect dynamic capability state, authorize commands or run
orchestration.

The build output supplies a closed role/capability manifest. The role selects
its method surface. Mandatory and optional capabilities then compile exact
command/status variants into or out of that role's types and dispatch.

Pruning must remove unavailable:

- command and status variants;
- boundary DTOs and referenced Candid types;
- dispatcher branches and protocol constants;
- public handler and endpoint-reachable workflow paths; and
- implementation code where the isolated Canister build permits it.

Private timer registration, callback and recovery-dispatch pruning is not an
endpoint-emission concern. 0.103 freezes the exact capability input and keeps
an unconfigured top-up owner inert; 0.104 owns removing that private code path.

A Cargo feature makes implementation code available; it is not sufficient
authority to export methods or variants. In particular,
`features = ["control-plane"]` must not force a non-Root canister to expose
Root variants, and an inert managed canister must not retain auth,
child-management or storage variants it did not compile.

The mandatory `Runtime` capability owns only universally available local
observations: current cycle balance and its local balance history, readiness,
protected identity, basic runtime state and the bounded diagnostics admitted by
the B1 matrix. Automatic refill, top-up events, treasury interaction, funding
policy, funding history, alerts and funding automation remain behind their
explicit capabilities or owning Root/Coordinator role. They may not become
universally reachable merely because they concern cycles.

Generated Candid, protocol constants and host bindings derive from the same
accepted role/capability manifest or are checked bidirectionally against it. A
method or variant cannot exist only in a macro, only in a constant list or only
in a caller.

## Profile-Specific Binding Bootstrap

0.103 uses external manifest selection, not a common discovery call, to
bootstrap profile-specific Candid bindings. The authoritative build/release
artifact identity binds:

- the exact Canic release identity;
- the role;
- the ordered compiled capability set;
- the generated Candid SHA-256; and
- the resulting protocol-profile digest.

The host and CLI select the exact full binding for that profile from accepted
build, release-set or Directory metadata before the first role call. A static
inter-canister caller may use the smaller generated request/response fragment
for the one variant it owns, but only after protected target metadata proves
that the exact profile includes that variant. The fragment is generated from
the same manifest and request/response correlation table; it is not a generic
superset or fallback decoder. `Overview` reports the same immutable role,
capability and profile identity for post-selection verification; it is not a
schema-negotiation or bootstrap mechanism.

Missing or mismatched profile evidence fails before the call. Trial decoding,
fallback bindings, dynamic method probing and runtime protocol negotiation are
forbidden. B1 evidence must map every maintained host, CLI and inter-canister
caller to this pre-call selection authority, and B2/B3 must bind generated
bindings and artifact metadata to the same manifest-exact profile.

## Quantitative Surface Contract

The accepted nonstandard Canic-owned design ceilings are:

- a managed application canister emits at most two methods: one status query
  and an update only when at least one command variant exists;
- a Fleet Subnet Root emits exactly one command update and one status query;
- a Fleet Coordinator emits exactly one command update and one status query;
- any of those roles may emit one additional composite-status query only after
  the endpoint-admission proof, for an absolute maximum of three;
- a Wasm Store starts with exactly one command update and one status query;
  every third or later method requires independent endpoint-admission and
  transport/resource evidence, with six as the absolute design ceiling across
  control, composite and byte-transport methods; and
- zero Candid methods exist solely to distinguish capability, caller,
  operation, direction or private workflow phase.

Externally mandated standard methods and application-owned methods are outside
these architectural ceilings because Canic does not own their names. They are
still counted, classified and reported next to the Canic-owned total.

These are ceilings, not targets. The Store's six-method bound is an emergency
ceiling, not an allowance or a pool of spare slots. B1 begins from command plus
status and justifies every additional byte lane independently; an unused slot
confers no future admission authority. B1 should produce a smaller manifest
where the contract permits it. It may not silently raise a ceiling; inability
to fit the required protocol blocks implementation and requires an explicit
design amendment.

Generated checks count methods from the final Candid service, not source-text
matches. They report, per exact role/capability profile:

- Canic-owned, externally mandated and application-owned method counts;
- command-request, command-response, status-request and status-response variant
  counts;
- synchronous command kinds and durable asynchronous operation kinds;
- former methods eliminated rather than translated;
- the former methods merged into each retained high-level intent;
- maximum variant-selector nesting depth;
- Candid service bytes and referenced type count;
- protocol constants; and
- representative Wasm size.

There is no arbitrary variant ceiling: semantic outcomes determine the closed
variant set. The report exists to reject a disguised one-variant-per-phase or
nested former-family migration even when the method count is two.

## Client And Caller Hard Cut

Every in-repository caller moves in the same release line:

- `canic-core` and `canic-control-plane` inter-canister calls;
- host install, activation, recovery and observation paths;
- `canic-cli` commands and rendered help;
- Wasm Store and Fleet Coordinator callers;
- application fixtures and PocketIC canisters;
- replay-policy endpoint manifests;
- Candid fixtures and generated Rust bindings; and
- source, package and release-integrity guards.

CLI commands may remain task-oriented. Several CLI commands can submit
different variants to one role command; Candid consolidation does not require
one opaque CLI command.

Old protocol strings, constants, functions and DTOs are deleted. There is no
deprecated method, forwarding wrapper, fallback call, dual client or feature
flag that restores the prior surface.

No receiving protocol changes without its maintained callers in the same
bounded batch. B4 changes the Root/Coordinator services together with every
Root/Coordinator caller, exact binding, protocol constant, replay row and
affected fixture. B5 does the same for managed and Store services. B6 closes
cross-cutting presentation, documentation and residue; it is not the first
migration of any B4/B5 caller. A batch may remain an unreleased implementation
sequence while those edits are assembled, but no temporary dual surface or
noncompiling handoff is an accepted checkpoint.

## Acceptance Criteria

0.103 is complete only when:

1. B1 records every current method and every caller with no unclassified row;
2. every current endpoint has exactly one disposition: role command variant,
   role status variant, Store data plane, externally mandated standard,
   application-owned or private/delete;
