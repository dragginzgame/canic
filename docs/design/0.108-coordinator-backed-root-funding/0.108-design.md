## Summary

0.108 gives every active Fleet Subnet Root one automatic cycles-safety owner.
When a root falls below its configured normal threshold, it requests an exact
grant from its Fleet Coordinator. The Coordinator authenticates the calling
root against the current Fleet Registry, applies immutable per-root policy,
Fleet-wide budget and Coordinator operating-reserve constraints, then calls
that same root with the approved cycles attached.

The root accepts the cycles only for its exact durable pending operation. An
exact retry after response loss accepts zero additional cycles and returns the
committed receipt. The Coordinator therefore never repeats an uncertain value
transfer blindly.

Each root may additionally carry an optional, lower-threshold automatic ICP
refill policy. That fallback converts ICP already held by the root into cycles
for the same root only after the Coordinator path has returned an exact
terminal no-grant result. It never races an unresolved Coordinator transfer.

The hierarchy becomes:

~~~text
operator-owned external treasury
            |
            | direct top-up / Coordinator creation funding
            v
Fleet Coordinator cycles treasury
            |
            | replay-safe attached-cycles grant
            v
Fleet Subnet Root
            |
            | existing parent-funded request_cycles flow
            v
Components and Component descendants

optional emergency path per root:

root-owned ICP -> ICP Ledger -> CMC -> cycles for that same root
~~~

Direct operator top-up remains the final recovery path for a frozen root, a
frozen Coordinator or any intentionally disabled automatic policy.

Automatic funding is deliberately sparse and finite. It may bridge a small
number of low-balance incidents, but it is not a perpetual balance keeper.
Every installed policy generation has non-renewing grant-count and cycle caps;
once either cap is exhausted, only a conscious operator action may restore
headroom.

## Problem

At design acceptance, the root funding surface was incomplete and internally
contradictory.

Fresh installation was sound: every root received exact independent
`root_creation_funding`. After installation, however:

- the ordinary automatic top-up timer explicitly excludes roots;
- Components and descendants may request cycles from their parent, so roots
  can fund the complete application hierarchy while having no automatic
  parent of their own;
- the Coordinator does not currently fund roots;
- `canic cycles topup <fleet> root <amount>` was the only working replenishment
  path for the then-current singular-root catalog shape;
- `canic cycles convert <fleet> --icp-e8s <amount>` and the controller-guarded
  singular-root endpoint still existed; but
- the non-configurable implicit root record hardcodes `icp_refill = None`, so
  the live conversion workflow rejects every ordinary installed root as not
  configured.

That last shape was architectural sediment. The generic `IcpRefillPolicy`
field and its test-only renderer survived after physical roots moved out of
application configuration. 0.108 makes the maintained root-owned
behavior reachable through protected installation authority or removes the
old generic configuration surface; it does not preserve both.

The current prepaid empty-Canister pool does not solve root operating
funding. Its IC-mainnet creation path spends cycles already present in the
root's Cycles Ledger account. It does not move cycles into the root's
operating balance. The ICP Ledger, Cycles Minting Canister and Cycles Ledger
remain three distinct authorities and balances.

The reoriented
[0.111 bounded multi-Fleet estate design](../0.111-bounded-multi-fleet-estates/0.111-design.md)
retains that separation deliberately. A bounded reusable estate requires
creation fees plus retained asset balances. Those cycles belong to an explicit
pool budget in the root's Cycles Ledger account; a routine
Coordinator operating grant must never be diverted into that budget merely
because the same root owns both workflows.

## Decision

0.108 adopts a Coordinator-first, root-local-emergency model.

1. Every planned root has one required Coordinator funding policy.
2. Every Coordinator has one required Fleet-wide root-funding treasury
   policy.
3. The root samples its own operating balance locally and pushes a request
   only when the normal threshold is reached.
4. The Coordinator is the sole routine funding authority for roots.
5. The Coordinator transfers cycles through a replay-safe inter-Canister call
   to the authenticated requesting root; the request cannot name a target.
6. A root may have one optional ICP-refill policy and an optional automatic
   emergency subpolicy.
7. Automatic ICP conversion is lower priority and lower threshold than the
   Coordinator request.
8. An unresolved Coordinator grant blocks ICP fallback for that operation.
9. Manual direct cycles top-up remains available regardless of automatic
   policy.
10. The Coordinator remains externally funded in 0.108. Automatic
    Coordinator ICP conversion is a separate design decision.

## Goals

0.108 must:

- close the root's missing parent-funding link without making the Coordinator
  a Component parent;
- keep target, Fleet, root, caller and Registry bindings explicit;
- preserve one automatic cycles timer owner per root;
- bound every Coordinator grant by immutable root policy, a Fleet-wide window
  and a Coordinator operating reserve;
- make exact retry safe before and after every attached-cycles effect;
- make manual root ICP conversion reachable through protected root policy;
- permit optional automatic root ICP conversion without racing Coordinator
  funding;
- expose enough status and metrics for operators to distinguish treasury,
  policy, transport, rate and ICP-balance failures;
- preserve direct top-up as break-glass recovery; and
- prove the real value-transfer and fallback paths with PocketIC.

## Non-Goals

0.108 does not:

- make the Coordinator a root, Component parent or application router;
- let a root request cycles for another root or arbitrary Principal;
- let a caller choose funding policy, target, Coordinator or CMC recipient;
- add Coordinator Workers or a generic funding-provider abstraction;
- implement automatic Coordinator ICP conversion;
- use the Cycles Ledger pool account as implicit root operating funding;
- fund a reusable Canister estate or deposit Coordinator grants into the
  root's Cycles Ledger account;
- change Component or descendant `topup = {}` behavior;
- infer production thresholds from the current non-root 10T/5T defaults;
- poll every root from the Coordinator;
- perform ICP fallback after an unknown transfer result;
- adopt an old installation, migrate old refill records or support
  mixed-version operation;
- add a Fleet-input schema version greater than one; or
- put physical root policy in `canic.toml`.

## Terminology

| Term | Meaning |
| --- | --- |
| operating balance | cycles held directly by a Canister and burned for execution, storage and calls |
| Coordinator treasury | the Coordinator's operating cycles balance from which exact root grants are attached |
| normal threshold | root balance at or below which the root opens a Coordinator funding operation |
| target balance | balance the root attempts to approach through one exact grant or refill |
| emergency threshold | lower root balance at or below which a terminally unavailable Coordinator path may permit automatic ICP refill |
| accounting window | fixed epoch-anchored interval selected when a durable reservation is created |
| funding profile | protected assertion that resolved infrastructure occupies one physical Subnet or crosses Subnet boundaries, with corresponding minimum baselines |
| funding policy generation | exact positive monotonic funding-policy revision; its non-renewing usage never resets, while a controller-reviewed rotation may install one separately bounded successor generation |
| policy rotation fence | durable Coordinator and Root state that stops new grants and automatic refill until every affected participant has converged or the exact operation resumes |
| successful grant event | first exact Root acceptance recorded by the durable Root receipt; the immutable event anchors cooldown |
| funding fence | one authoritative Draining transition after which no new grant or refill may begin |
| root funding operation | one durable root-to-Coordinator request and its exact grant/no-grant result |
| root acceptance receipt | durable root evidence that one exact Coordinator grant was accepted once |
| ICP refill | transfer of root-held ICP to the CMC top-up account and notification that mints cycles for that same root |
| uncertain grant | a Coordinator-to-root value-transfer call whose terminal acceptance receipt is not yet known |

The configuration and public output use `refill`, not `burn`, because the
operator intent is replenishing a root. Documentation may explain that the
CMC burns the transferred ICP as part of minting cycles.

## Authority Model

| Concern | Sole authority |
| --- | --- |
| Fleet and Coordinator identity | immutable Fleet install plan and Coordinator authority |
| root identity and lifecycle | current Fleet Registry entry |
| global treasury budget and reserve | current Coordinator Registry funding-policy generation |
| per-root request threshold, target, cooldown and budget | current Registry-issued root funding-policy generation mirrored by the exact Root |
| funding policy rotation | Coordinator durable operation, authenticated controller command and exact affected-Root receipts |
| current root operating balance | exact root local observation |
| grant target | authenticated calling root; never a request field |
| Coordinator grant intent and budget ledger | Coordinator stable state |
| acceptance of attached cycles | exact target root stable state |
| root-held ICP source and refill policy | exact root protected policy |
| ICP conversion rate and fee | configured canonical system Canisters and their live responses |
| reusable-estate creation balance | exact root Cycles Ledger account under the separately approved 0.111 estate policy |
| Component/descendant funding | existing exact parent authority |
| direct emergency top-up | operator-selected external identity |

The root is trusted to report its locally observed balance because it is the
exact registered Fleet infrastructure artifact and the Coordinator still
caps every request independently. A reported balance grants no topology or
target authority.

## Protected Fleet Input

0.108 extends the strict operator-owned Fleet input. The spelling and semantics
below are frozen by this amendment; implementation may tighten validation but
must not silently rename, default or weaken these protected fields.

~~~toml
schema_version = 1
funding_profile = "preview_multi_subnet"

[coordinator.subnet]
kind = "explicit"
subnet = "<coordinator-subnet-principal>"

[coordinator.creation_funding]
kind = "cycles"
cycles = "140T"

[coordinator.root_funding]
minimum_reserve_cycles = "80T"
window_secs = 7776000
maximum_cycles = "30T"
maximum_automatic_grants = 2
maximum_automatic_cycles = "60T"

[[fleet_subnet_roots]]
placement_subnet = "<workload-subnet-principal>"

[fleet_subnet_roots.root_funding]
request_threshold = "10T"
target_balance = "30T"
cooldown_secs = 2592000
window_secs = 7776000
maximum_cycles = "30T"
maximum_automatic_grants = 2
maximum_automatic_cycles = "60T"

[fleet_subnet_roots.root_creation_funding]
kind = "cycles"
cycles = "30T"

[fleet_subnet_roots.wasm_store_creation_funding]
kind = "cycles"
cycles = "10T"
~~~

This is the recommended bounded `preview_multi_subnet` staging profile for one
Root on a standard 13-node charging Subnet and one Coordinator on another
standard 13-node charging Subnet. The Coordinator's 140T consists of its 80T
protected reserve plus the complete 60T lifetime automatic grant cap. Root and
Wasm Store creation add 30T and 10T, so initial Fleet creation funding is 180T
before the three exact Cycles Ledger creation fees. The existing 5T Core
allocation comes from the Root's 30T and is not an additional creation amount.
Automatic ICP refill is absent. Exact values remain
operator-visible protected input so a parser, Canister or later release cannot
silently change treasury authority.

### Sparse Funding Profiles

The host classifies the resolved physical topology before any paid effect:

- `single_subnet` means the Coordinator and every Root occupy one exact
  physical Subnet; and
- `preview_multi_subnet` and `multi_subnet` both require at least one Root on a
  different physical Subnet from the Coordinator. The preview lane is the
  bounded staging envelope; `multi_subnet` retains the high-reserve
  professional-Fleet minima.

The submitted `funding_profile` must match that physical classification. The
Fleet-input scaffold materializes the following standard-13-node baselines;
the strict loader still rejects omitted amounts or caps.

| Protected value | `single_subnet` | `preview_multi_subnet` | `multi_subnet` |
| --- | ---: | ---: | ---: |
| Coordinator creation funding | `100T` | reserve + Fleet lifetime cap (`140T` recommended) | `2000T + 2000T * root_count` |
| Coordinator minimum reserve | `30T` | `80T` | `2000T` |
| Root creation funding, each | `30T` | `30T` | `1000T` |
| Wasm Store creation funding, each | `10T` | `10T` | `200T` |
| Root request threshold, each | `10T` | `10T` | `250T` |
| Root target balance, each | `30T` | `30T` | `1000T` |
| Root successful-grant cooldown | 30 days | 30 days | 30 days |
| Root/Fleet accounting window | 90 days | 90 days | 90 days |
| Root window maximum | `30T` | `30T` | `1000T` |
| Fleet window maximum | `30T` | `30T * root_count` | `1000T * root_count` |
| Root non-renewing automatic cap | 4 grants / `120T` | 2 grants / `60T` recommended | 4 grants / `4000T` |
| Fleet non-renewing automatic cap | 4 grants / `120T` | 2 grants / `60T` recommended | `4 * root_count` grants / `4000T * root_count` |

Preview Coordinator creation funding covers its protected reserve plus its
complete configured Fleet lifetime cap. The recommended two-grant cap produces
140T Coordinator funding and a 180T total creation amount before fees. A
reviewed one-grant 30T lifetime cap lowers those figures to 110T and 150T. The
remaining finite automatic authority is usable only if the operator later
tops up the Coordinator directly; Canic does not silently replenish that
treasury.

The single-Subnet and preview multi-Subnet 10T/30T pair is intentionally
affordable: the 10T threshold is about 237 times the measured 42.2B-cycle Root
request/recovery floor while leaving 20T between threshold and target for
ordinary operation and initial Canister work. The multi-Subnet 250T/1P pair
remains an intentionally large professional-Fleet option. At the threshold,
the affordable and professional profiles transfer at least 20T and 750T
respectively. Each window maximum is smaller than twice that minimum grant, so
one Root cannot receive
two automatic grants in one 90-day window. The 30-day cooldown also prevents
back-to-back grants across a window boundary. Four successful grants or the
corresponding non-renewing cycle cap permanently exhausts that installed
policy generation; a rolling window reset never restores those caps. No timer,
window rollover, restart, direct top-up, policy reapplication or mutable
configuration endpoint resets exhausted authority. A fresh reinstall may
create a new policy generation. Within the same release, the sole exception is
an explicit controller-reviewed CANIC-019 rotation: it installs exactly one
digest-bound successor generation, retains cumulative predecessor usage and
never makes an old operation identity fresh.

An operator may raise balances, reserve, cooldowns or windows and may lower
the finite grant counts. A raised target may raise the corresponding finite
cycle cap, but never the four-grant ceiling.
The loader rejects a lower target/threshold gap, a shorter cooldown/window, a
window capable of two threshold-triggered grants, or more than four automatic
grants per Root in one installed policy generation. A Fleet whose measured
burn or child-funding exposure needs more frequent replenishment must raise
the target and treasury instead of shortening the interval. Direct top-up
remains the explicit escape hatch.

The defaults preserve approximate runway across larger charging Subnets by
scaling the affected Coordinator, Root or Wasm Store's creation funding and
the affected operating role's reserve, threshold, target and derived budgets
by:

~~~text
max(1, current_registry_node_count / 13)
~~~

and rounding upward to the next 10T. The scaffold writes the resulting exact
integers into the protected input and the finalized plan; neither the loader
nor runtime recomputes them later. This follows the IC rule that execution,
storage and messaging costs scale with Subnet node count. The operator must
still size above these baselines when measured burn requires it. See the
[official Subnet type](https://docs.internetcomputer.org/references/subnet-types/)
and [cycle-cost](https://docs.internetcomputer.org/references/cycle-costs/)
references.

`canic scaffold fleet-input` is the funding-only authoring surface. Given
exact IC Subnet IDs, it resolves the current Coordinator and Root node counts
from Canic's validated Registry catalog; cache-only lookup is the default and
an explicit flag may refresh missing or invalid evidence. Explicit node counts
remain a fully offline fallback. Both modes show every scaling, rounding, cap,
subtotal, per-creation fee and maximum-debit formula and emit exact integer
TOML. The command never reads an identity or balance and cannot claim install
admission. The complete merged Fleet input must still pass live `canic deploy
plan` admission.

### Operator Funding Observation

Fleet input owns one top-level `operator = "<principal>"` authority. It does
not own an account string, balance, evidence source or observation timestamps.
Planning and installation require the active ICP CLI identity to equal that
canonical non-anonymous Principal, derive the Cycles Ledger account, and query
its live cycles balance. Infrastructure creation is cycle-only; an authored
ICP creation amount rejects before profile admission because this release owns
no rate, margin or conversion authority. That possible automation remains the
deferred
[operator funding conversion authority idea](../ideas/operator-funding-conversion-authority/design.md).

The canonical plan digest binds the operator Principal and derived account but
excludes the volatile balance, source and timestamps. Sufficiency still gates
plan compilation. Maximum operator debit includes every configured creation
amount and one exact Cycles Ledger creation fee for each host-created
Coordinator, Root and Store. Installation repeats the observation immediately
before the first effect. This keeps an external top-up from invalidating an
otherwise identical approved plan while a changed identity, account or fee-
incomplete balance fails closed.

### Fiduciary Placement Is Explicit

0.108 hard-cuts the existing `kind = "recommended"` Coordinator selector
because it silently resolves to the Fiduciary Subnet. It is rejected rather
than reinterpreted. Coordinator placement must use an exact `profile` or
`explicit` selector. Any Coordinator or Root placement that the trusted
IC-mainnet catalog resolves to `subnet_specialization = fiduciary` additionally
requires this adjacent protected-input field:

~~~toml
[coordinator.subnet]
kind = "profile"
profile = "fiduciary"
acknowledge_fiduciary_cost = true

[[fleet_subnet_roots]]
placement_subnet = "<fiduciary-subnet-principal>"
acknowledge_fiduciary_cost = true
~~~

The acknowledgement is per placement, absent by default and binds to the
resolved Subnet plus catalog digest. Missing or false acknowledgement rejects
a Fiduciary placement. A true acknowledgement on a non-Fiduciary placement is
also rejected so copied or stale configuration cannot misdescribe the plan.
No default or recommendation selects a Fiduciary Subnet.

Before plan confirmation and again before the first paid effect, every
acknowledged Fiduciary placement emits a prominent warning containing the
exact role, Subnet Principal, current Registry node count, node-count cost
multiplier, materialized creation funding and maximum automatic exposure. The
warning remains present after acknowledgement; the boolean supplies authority,
not silence. The finalized plan retains the acknowledgement and evidence for
offline audit. At the currently documented 34 nodes, ordinary costs are about
`34 / 13`, or 2.6 times, the standard application-Subnet baseline; the design
never hard-codes 34 as permanent topology.

### Coordinator Policy

`coordinator.root_funding` is required when the Fleet contains roots. It
contains:

- `minimum_reserve_cycles`: balance the Coordinator must retain after the
  complete reserved call cost and grant;
- `window_secs`: positive Fleet-wide accounting window; and
- `maximum_cycles`: maximum total successful root grants in that window;
- `maximum_automatic_grants`: non-renewing successful-grant count for this
  exact installed policy generation; and
- `maximum_automatic_cycles`: non-renewing successful-grant amount for this
  exact installed policy generation.

The Coordinator does not grant a partial amount merely to consume the
remaining budget. It either reserves the exact requested grant and required
call cost or returns a typed terminal no-grant result.

### Per-Root Coordinator Policy

`fleet_subnet_roots.root_funding` is required for every root and contains:

- `request_threshold`: inclusive balance threshold for opening a request;
- `target_balance`: desired post-grant balance;
- `cooldown_secs`: minimum interval between successful grants;
- `window_secs`: positive per-root accounting window; and
- `maximum_cycles`: maximum successful grants for that root in the window;
- `maximum_automatic_grants`: non-renewing successful-grant count for the
  exact installed policy generation; and
- `maximum_automatic_cycles`: non-renewing successful-grant amount for the
  exact installed policy generation.

The requested amount is:

~~~text
target_balance - observed_balance
~~~

using checked arithmetic. A balance already at or above the target produces
no request. The Coordinator verifies the request against its retained root
policy and rejects zero, overflowed, over-target or over-budget values.

### Accounting Windows and Cooldown

Fleet, per-root and ICP budgets use deterministic fixed windows anchored to
the Unix epoch:

~~~text
window_index = now_secs / window_secs
window_start_secs = window_index * window_secs
~~~

Each durable grant reservation records the independently derived Fleet and
per-root window starts at reservation creation. Completion converts that
exact reservation into spent usage in those same windows, even when the call
or recovery crosses a boundary. It never moves the grant into the window in
which a callback happens to complete. A definite no-effect rejection releases
the exact reservation from its original windows; uncertainty retains it.

The Root acceptance receipt records one immutable `accepted_at_ns` for the
fresh successful acceptance. Exact replay returns that same event time. The
per-root cooldown begins at that successful-grant event, never at the time of
a later replay, callback or Coordinator recovery.

The Coordinator and Root separately retain non-renewing automatic count and
cycle usage beside the rolling windows. Successful completion charges both;
replay charges neither again. Window rollover never resets non-renewing usage.
Exhaustion is a typed terminal no-grant result and does not unlock automatic
ICP fallback.

### Root ICP Policy

`fleet_subnet_roots.icp_refill` is optional. Presence enables controller-
requested manual root self-refill and supplies:

- the maximum ICP amount for one call;
- a positive cumulative window and maximum ICP spend in that window;
- an ICP balance floor retained after amount plus ledger fee; and
- an optional minimum ICP/XDR rate gate.

The existing local/custom ledger and CMC overrides may remain only inside this
root-owned policy. IC system-Canister overrides require the explicit current
safety flag and remain rejected by default.

`fleet_subnet_roots.icp_refill.automatic` is optional. Its presence enables
automatic emergency refill. There is no redundant `enabled` or
`auto_burn_icp` boolean. It contains:

- `emergency_threshold`: the lower inclusive balance threshold; and
- `target_balance`: the post-conversion target used to derive the requested
  ICP amount from the current CMC rate;
- `maximum_automatic_refills`: a positive, non-renewing count no greater than
  four; and
- `maximum_automatic_refill_e8s`: a positive, non-renewing automatic ICP-spend
  cap.

Manual conversion remains available when `icp_refill` is present but
`automatic` is absent. Automatic ICP refill is absent from both default
profiles. A rolling ICP window never restores the non-renewing automatic caps.

### Validation

Strict Fleet-input validation rejects:

- an absent or topology-mismatched `funding_profile`;
- an absent, anonymous or non-canonical top-level `operator` Principal, and
  every removed self-declared operator-evidence field;
- the removed `kind = "recommended"` Coordinator selector;
- a Fiduciary Coordinator or Root placement without exact adjacent
  `acknowledge_fiduciary_cost = true`;
- `acknowledge_fiduciary_cost = true` for a placement the trusted catalog does
  not classify as Fiduciary;
- a Fleet with roots but no Coordinator funding policy;
- a root without `root_funding`;
- zero thresholds, targets, windows, cooldowns or budgets;
- a root threshold, target gap, cooldown or window below its topology
  profile's baseline;
- a per-root window maximum that can admit two minimum threshold-triggered
  grants;
- zero, inconsistent or more-than-four per-root non-renewing automatic grant
  caps;
- Fleet non-renewing caps larger than the sum of admitted per-root caps or too
  small to admit the largest root's one valid grant;
- `target_balance <= request_threshold`;
- a per-root `maximum_cycles` smaller than that root's `target_balance`, which
  is the largest valid grant after a zero-balance observation;
- a Fleet-wide `maximum_cycles` smaller than the largest root
  `target_balance`, which would make that root's largest valid grant
  impossible;
- `minimum_reserve_cycles` too small for the measured implementation floor;
- `request_threshold` below the measured Root Coordinator-request/retry
  execution and recovery floor;
- automatic ICP policy without the parent `icp_refill` policy;
- `emergency_threshold >= request_threshold`;
- `emergency_threshold` below the measured automatic-refill execution and
  recovery floor;
- automatic `target_balance <= request_threshold`;
- automatic `target_balance > root_funding.target_balance`;
- automatic ICP policy without positive, at-most-four non-renewing refill
  count and spend caps;
- zero ICP caps or windows;
- `maximum_refill_e8s < max_refill_e8s_per_call`;
- a refill amount that cannot retain the configured ICP balance floor plus
  the observed ledger fee;
- unsafe IC system-Canister overrides;
- unknown fields or old generic `topup.icp_refill` fields; and
- any root-funding or root-refill field in `canic.toml`.

The singular `root` CLI target and Fleet-only conversion target are not
retained as compatibility aliases. A multi-root Fleet must select one exact
registered root Principal for every manual refill or direct root top-up.

The 2026-08-21 M0/M1 PocketIC 15.0.0 measurements freeze these policy floors
for the pinned `ic-cdk 0.20.2` implementation:

- Root Coordinator-request/retry floor: `42,200,000,000` cycles; and
- automatic ICP-refill execution/recovery floor: `42,200,000,000` cycles.

The first combines the final `canic_command` call reservation for the
conservative 16 KiB encoded-command bound with the observed fresh/retry Root
execution. The second combines the maximum exact
ledger/CMC call reservation with fee, decimals, rate, transfer-response-loss,
duplicate-transfer recovery, notify-response-loss, notify replay and terminal
completion execution. Both round upward to the next 100M cycles. The final
bounded command call reserves `42,118,809,000` cycles and still rounds to the
frozen `42,200,000,000` request/retry floor. The final M2 command DTO's encoded
maximum fits the 16 KiB bound; lowering either floor requires an equal or
stronger PocketIC proof.

Creation funding remains separate. Before activation, the host must report
whether observed Coordinator and root balances provide enough headroom to
start their configured safety protocols. Fresh-Fleet infrastructure creation
uses exact cycle amounts only; the pre-effect operator maximum additionally
includes the exact per-create Cycles Ledger fees.

## Immutable Propagation

The host compiles the topology profile, exact materialized values,
non-renewing caps and placement-cost acknowledgements into the immutable Fleet
install plan before any paid effect. Funding policy hashes cover the profile,
all rolling and non-renewing limits and their exact values.

Coordinator policy flows through:

~~~text
Fleet input
  -> immutable install plan
  -> Coordinator init payload
  -> Coordinator stable authority
~~~

Per-root policy flows through:

~~~text
Fleet input
  -> immutable root plan
  -> FleetSubnetRootBinding / root init authority
  -> root stable authority
  -> Fleet Registry root entry
  -> Coordinator canonical Registry state
~~~

The Coordinator and root therefore validate the same policy from independent
protected copies. A mismatch blocks activation or funding; it is never
resolved by trusting the request payload.

Fiduciary acknowledgement and trusted catalog evidence remain host-side plan
authority; they do not grant a Canister a generic placement or catalog-query
capability.

Root policy is not compiled into the shared root Wasm. One qualified root
artifact may serve several roots with different protected funding policy.

## Root Funding State Machine

One root owns at most one nonterminal Coordinator funding operation.

~~~text
Observed
  -> CoordinatorRequested
  -> GrantPrepared
  -> GrantAccepted
  -> Completed

terminal no-effect branch:

CoordinatorRequested
  -> NoGrant
  -> EmergencyEligible | Completed

uncertain branch:

GrantPrepared
  -> ReconcileGrant
  -> GrantAccepted | RecoveryRequired
~~~

Conceptual root state contains:

~~~rust
pub struct RootFundingOperationRecord {
    pub operation_id: [u8; 32],
    pub operation_sequence: u64,
    pub expected_registry: FleetRegistryVersion,
    pub coordinator: Principal,
    pub observed_balance: u128,
    pub requested_cycles: u128,
    pub policy_hash: [u8; 32],
    pub phase: RootFundingPhaseRecord,
    pub opened_at_ns: u64,
    pub updated_at_ns: u64,
}
~~~

The exact operation ID is persisted before the outbound Coordinator call.
Restart, timer retry and a lost final response reuse that ID and immutable
payload. The sequence is monotonically increasing per root and is part of the
operation-ID derivation. The Coordinator admits only the exact next sequence;
this makes old-operation replay rejectable without an unbounded receipt
history.

`NoGrant` must distinguish:

- root cooldown active;
- root window exhausted;
- Fleet window exhausted;
- root non-renewing automatic cap exhausted;
- Fleet non-renewing automatic cap exhausted;
- Coordinator reserve unavailable;
- funding administratively disabled;
- stale Registry or ineligible root; and
- invalid request.

Only explicitly classified treasury-unavailable results may make the same
root operation emergency-eligible. Invalid authority, stale policy, disabled
funding and unresolved effects fail closed rather than spending ICP.

## Coordinator Funding State

The Coordinator owns:

- one immutable global root-funding policy;
- one runtime controller kill switch;
- current Fleet-wide window usage;
- per-root window and cooldown usage;
- Fleet-wide and per-root non-renewing automatic usage;
- one current/nonterminal grant intent per root;
- one exact last terminal result and sequence per root; and
- cost-reservation evidence for each attached-cycles call.

Conceptual grant authority is:

~~~rust
pub struct CoordinatorRootGrantRecord {
    pub operation_id: [u8; 32],
    pub operation_sequence: u64,
    pub fleet_subnet_root: Principal,
    pub registry: FleetRegistryVersion,
    pub observed_balance: u128,
    pub granted_cycles: u128,
    pub policy_hash: [u8; 32],
    pub phase: CoordinatorRootGrantPhaseRecord,
    pub prepared_at_ns: u64,
    pub completed_at_ns: Option<u64>,
}
~~~

Window accounting reserves the grant before the external call. A definite
callee rejection releases the reservation. An uncertain result retains the
reservation until exact replay obtains the root acceptance receipt. A
successful receipt converts the reservation into spent budget exactly once.

Receipt retention is deliberately not a collection or reclamation protocol.
Each registered root has one bounded slot containing its current/nonterminal
intent and one exact last terminal result. The root cannot open sequence N+1
until it has received N's terminal result. Arrival of valid N+1 therefore
acknowledges N and permits the Coordinator to replace N as the retained last
result. Exact retry of N remains available until that point. A stale or
non-successor sequence fails before reservation. No replay horizon, purge
timer or separate cross-Canister acknowledgement is introduced unless M0 or
a later implementation counterexample proves this bounded shape insufficient
and the maintainer accepts the smallest amendment.

## Authenticated Grant Protocol

The root calls one public Coordinator update with a passive request similar
to:

~~~rust
pub struct FleetRootFundingRequest {
    pub operation_id: [u8; 32],
    pub operation_sequence: u64,
    pub expected_registry: FleetRegistryVersion,
    pub observed_balance: u128,
    pub requested_cycles: u128,
    pub policy_hash: [u8; 32],
}
~~~

The request has no Fleet, Coordinator, root or target Principal. The
Coordinator derives all of them from its own authority and the transport
caller.

Authorization requires:

1. caller is non-anonymous and not the Coordinator;
2. caller matches exactly one current Fleet Registry root entry;
3. root status is `Active` or an explicitly funding-eligible `Draining`
   state;
4. requested Registry authority, epoch, revision and content hash are current;
5. policy hash matches the immutable root entry;
6. request amount equals the protected target calculation;
7. no competing operation exists for the root;
8. root and Fleet windows admit the complete amount;
9. cooldown admits a new successful grant;
10. the Coordinator kill switch is enabled; and
11. current Coordinator balance covers grant, complete call reservation and
    `minimum_reserve_cycles`.

`Joining`, `Removed`, unknown and conflicting roots are never funded. A
Draining root remains eligible only while it owns live teardown work and
before its terminal cycle-reclamation handoff. The final deletion protocol
continues to move excess cycles back to the Coordinator and must fence new
funding first.

## Attached-Cycles Acceptance

The Coordinator does not use an unobservable raw management `deposit_cycles`
effect for routine grants. It calls a dedicated root update with the exact
grant attached from the Coordinator's operating balance.

The root acceptance request contains the operation ID, exact policy/Registry
binding and granted amount. On a fresh call, the root:

1. authenticates `msg_caller()` as its exact protected Coordinator;
2. finds the matching durable root funding operation;
3. verifies phase, Registry, policy hash and exact expected amount;
4. verifies exactly that amount is available on the incoming call;
5. verifies its current balance remains at or below the protected normal
   request threshold;
6. accepts exactly that amount;
7. commits the acceptance receipt in the same replicated message; and
8. returns the receipt.

The live-balance comparison prevents a direct external top-up that relieves
the low-balance condition during the operation from being followed by a stale
automatic grant. Balance movement that remains within the protected
low-balance range, including unrelated call-cost refunds, preserves the need
for the exact bounded grant. Ordinary burn while the request is in flight also
leaves the grant valid. M0 must confirm that the selected balance API excludes
unaccepted incoming-call cycles before this check is implemented. The current
M0 PocketIC probe records `canister_cycle_balance()` immediately before and
after exact acceptance and observes an increase of exactly the accepted
principal, so the pre-acceptance observation excludes it.

On exact replay after the receipt exists, the root accepts zero additional
cycles and returns the existing receipt. Unaccepted attached cycles are
refunded to the Coordinator. This matches the IC call model: a canister may
attach cycles to an inter-Canister call, the callee explicitly accepts them,
and unaccepted excess returns to the caller. See the official
[inter-Canister call guidance](https://docs.internetcomputer.org/guides/canister-calls/inter-canister-calls/).

The acceptance update performs no `await` between validation, cycle
acceptance and receipt persistence. A trap cannot leave an accepted grant
without its matching durable receipt. M0 must invoke a deliberate Root trap
after exact acceptance and receipt persistence and prove that the replicated
message commits neither the receipt nor the accepted principal. That proof is
distinct from caller-side response loss after the Root message has committed.

The Coordinator persists its intent before the call. If its callback or final
response is lost, it repeats the same attached-cycles call. A root that
already accepted the first call accepts zero on replay and returns the exact
receipt, so the Coordinator can finish without a second transfer.

M0 therefore has two separately named atomicity cases:

1. Root accepts X, persists the receipt and deliberately traps before reply:
   the Root retains neither X nor the receipt and the Coordinator receives the
   unaccepted/refunded principal back after call failure.
2. Root accepts X, persists and returns the receipt, then the Coordinator
   continuation traps: exact retry attaches X again, the Root accepts zero,
   the attached principal is refunded and the same receipt completes the
   Coordinator intent.

## Root Timer Ownership

0.108 consumes the completed 0.104 boundary and retains one
`cycles:topup` consumer for each root through a native `ic-timers`
registration. It does not add a Canic scheduler or a second ICP timer.

On activation and same-release restart, the owner:

1. restores or validates any nonterminal funding or ICP-refill operation;
2. records the local cycle sample;
3. resumes the exact operation before considering a new one;
4. otherwise schedules from the normal threshold; and
5. after any terminal outcome, resamples before selecting its next deadline.

The root timer first runs the Coordinator path. It may select automatic ICP
refill only when all of the following hold:

- automatic ICP policy is present;
- the current balance is at or below `emergency_threshold`;
- the matching Coordinator operation has a terminal zero-transfer outcome
  classified as treasury unavailable;
- no Coordinator grant, ICP refill or deletion cycle handoff is unresolved;
- the root cycles-funding kill switch permits spending; and
- the root is in a funding-eligible lifecycle state.

Transport error, timeout, callback loss, Coordinator restart or an uncertain
root acceptance is not a terminal zero-transfer result. The timer retries the
same operation with bounded backoff and cannot begin ICP conversion.

Only non-root runtimes continue using the existing parent `request_cycles`
path. Selection remains role-exact rather than reviving a generic root
fallback inside child funding.

## Automatic ICP Refill

The automatic path reuses the maintained root-owned ICP Ledger and CMC
adapters, durable operation journal, exchange-rate gate and exact same-root
source/target binding. It adds an internal timer entrypoint; it does not fake a
controller caller, synthesize ingress or dispatch a public command variant
from a timer.

The root derives the cycle deficit with checked arithmetic:

~~~text
cycle_deficit = automatic.target_balance - current_cycle_balance
~~~

After querying the current CMC ICP/XDR rate, it derives the minimum ICP e8s
needed to cover that deficit, rounding upward. The operation is admitted only
when the resulting amount:

- is nonzero;
- is no greater than `max_refill_e8s_per_call`;
- fits the remaining cumulative ICP window;
- leaves `minimum_icp_balance_e8s` plus the exact observed ledger fee; and
- satisfies the optional minimum conversion-rate gate.

If the amount required to reach the target exceeds a cap, 0.108 does not
silently drain the maximum. It returns a typed policy exhaustion result and
alerts the operator. A later design may permit explicitly configured partial
refill, but it is not the 0.108 default.

The root transfers its own ICP to the CMC account subaccount derived for that
same root, persists the ledger block index, calls the CMC notification and
persists the terminal cycles result. The source and target Principals are
never request fields. The official platform flow is ICP Ledger transfer
followed by CMC notification; see the
[system Canister reference](https://docs.internetcomputer.org/references/system-canisters/).

The default ICP Ledger account is the automatic source. Manual
`canic cycles convert` may retain its explicit source-subaccount option, but
automatic policy does not search or sweep arbitrary subaccounts.

## Manual Refill and Direct Top-Up

The explicit controller operation becomes:

~~~text
canic cycles convert <fleet> <root-principal> --icp-e8s <amount>
~~~

In 0.108 it resolves the Fleet through its exact Coordinator, verifies that
the selected Principal is one current non-`Removed` Fleet Subnet Root, and
reads that root's protected `icp_refill` policy instead of the unreachable
generic `CanisterConfig.icp_refill` field. Manual and automatic operations
share:

- one active-operation exclusion;
- per-call and cumulative ICP caps;
- source/target binding;
- rate gate;
- durable transfer/notification replay; and
- metrics and operator status.

Manual operation IDs continue to support exact CLI retry. Automatic operation
IDs come from a durable root trigger record and are never regenerated while
an operation is resumable.

`canic cycles topup` remains the independent recovery mechanism. 0.108 extends
installed Fleet target resolution so both infrastructure roles are explicit:

~~~text
canic cycles topup <fleet> coordinator <amount>
canic cycles topup <fleet> <root-principal> <amount>
~~~

A root Principal must be a member of the selected Fleet's last authenticated
installed deployment truth; the command does not become an arbitrary-target
escape hatch. Both the unique
`coordinator` role and root membership resolve from authenticated host-side
installed-Fleet deployment truth retained before the recovery command:

- the canonical-network Fleet catalog row selects exact Fleet ID, release
  build and Coordinator Principal; and
- the digest-bound Fleet install plan plus canonical per-placement root
  install journals select the exact created Root Principals.

Every source is bounded, no-follow, canonically decoded and cross-validated
before selection. The command may use a live read only as optional
corroboration; it never requires a successful call to the selected target,
and a dead Coordinator is not needed to resolve its own Principal or a
retained root Principal. Missing, invalid or contradictory host authority
fails closed. Direct top-up is the required recovery for a frozen
infrastructure Canister. An operator who
deliberately needs a raw arbitrary Principal continues to use the upstream ICP
CLI under its maintained rules. Official ICP guidance confirms that any caller
may top up a Canister; see
[cycles management](https://docs.internetcomputer.org/guides/canister-management/cycles-management/).

## Policy and Failure Semantics

| Observation | Coordinator action | Root action |
| --- | --- | --- |
| balance above normal threshold | none | schedule next observation |
| balance at or below normal threshold, policy admits | reserve and attach exact grant | accept once, persist receipt, resample |
| successful grant response lost | replay exact grant call | accept zero, return prior receipt |
| root/Fleet budget exhausted | terminal no-grant | wait or enter emergency path only below emergency threshold |
| root/Fleet non-renewing cap exhausted | terminal no-grant | stop automatic funding, alert and require direct operator action |
| Coordinator reserve unavailable | terminal no-grant | alert; optional emergency path below threshold |
| cooldown active | terminal retry time, no grant | resample and wait; do not spend ICP immediately |
| stale Registry or policy | reject | stop funding owner as invariant failure |
| Coordinator transport/callback uncertain | retain in-flight grant | retry exact operation; forbid ICP fallback |
| automatic rate gate denied | no Coordinator mutation | retain ICP, back off and alert |
| insufficient root ICP | no conversion | alert and require Coordinator/operator funding |
| root frozen | cannot request or convert | operator direct top-up |
| Coordinator frozen | cannot grant | operator direct Coordinator top-up; root fallback only if its prior result is known safe |

Expected resource exhaustion uses bounded retry or the lower emergency path.
Authority, state contradiction, arithmetic overflow, receipt mismatch and
policy drift are invariant failures and stop automatic mutation.

## Funding Kill Switches

The Coordinator owns a controller-only runtime root-funding kill switch. When
disabled it:

- starts no new grant;
- preserves and reconciles any already prepared effect; and
- returns a typed disabled result after nonterminal work is safe.

Each root's existing cycles-funding runtime state also gates automatic
Coordinator requests and automatic ICP spend. Disabling it does not erase
pending records or block controller diagnostics, exact reconciliation or
direct external top-up.

Kill switches are operational state, not configuration booleans and not a
replacement for immutable limits.

## Lifecycle Rules

### Fresh Install

The host:

1. validates and freezes all funding policy in the install plan;
2. creates and installs the Coordinator with explicit creation funding;
3. creates and installs every root with explicit creation funding;
4. propagates exact policies through Coordinator and root init authority;
5. verifies Registry/root policy equality during join and activation; and
6. starts root funding timers only after the root becomes `Active`.

Prepared roots expose only the accepted activation/bootstrap status and
command variants. No funding timer or funding command variant becomes
operational early.

### Same-Release Restart

Init and post-upgrade adapters restore synchronously and schedule async work.
They do not await a funding or ICP operation. A zero-delay timer resumes the
one durable operation after invariants are restored.

Same-release restart restores and resumes the exact retained operation. Root
upgrade/snapshot admission rejects while either a funding request or ICP refill
is resumable; Coordinator snapshot admission likewise rejects a current grant.
This keeps the callback-loss protocol intact without creating a second replay
owner. Cross-release upgrade from 0.108.0 is intentionally unsupported by the
pre-1.0 reinstall-only boundary.

### Draining and Removal

Draining policy must keep enough cycles available to finish Component and
Store teardown. Lifecycle owns one authoritative funding-fence transition:

~~~text
Active
  -> funding eligible

Draining before funding fence with exact unfinished funded teardown work
  -> funding eligible

Draining at or after funding fence
  -> funding ineligible

Removed
  -> funding ineligible
~~~

Funding and deletion workflows consume that state; neither independently
infers eligibility from a loose collection of deletion observations.

Before terminal cycle reclamation:

- the root funding timer is stopped;
- no new grant or ICP operation may begin;
- every in-flight grant/refill is terminal; and
- lifecycle records the single funding fence before terminal reclamation.

The maintained deletion path then transfers reclaimable root cycles back to
the exact Coordinator while retaining its execution reserve. `Removed` roots
cannot request, receive or automatically mint cycles.

## Replay and Recovery Invariants

1. Operation identity is durable before every outbound value-transfer call.
2. Root caller and grant target are the same exact Principal.
3. Coordinator policy, root policy and Registry identity are hash-bound.
4. A root has at most one nonterminal Coordinator funding operation.
5. A Coordinator has at most one nonterminal grant per root.
6. Fresh root acceptance consumes exactly the expected attached amount.
7. Replayed root acceptance consumes zero and returns the prior receipt.
8. Window reservation precedes the grant call.
9. Successful budget spend commits exactly once from the root receipt.
10. An uncertain grant cannot release its reservation, start another grant or
    authorize ICP fallback.
11. Manual and automatic ICP refill cannot overlap.
12. Ledger transfer and CMC notification retain the existing exact operation
    identity and immutable request binding.
13. One current plus one last terminal result per root is sufficient because
    the exact next monotonic sequence acknowledges and replaces its
    predecessor; old or skipped sequences reject before effects.
14. A fresh successful grant or automatic ICP refill charges its exact
    non-renewing count and amount once; replay charges neither again.
15. Restart, fixed-window rollover and timer rescheduling never reset
    non-renewing usage.
16. Restart never creates a new operation merely because the prior callback
    was lost.
17. A policy generation is positive and increases by exactly one only through
    one accepted controller-reviewed rotation plan.
18. Rotation retains predecessor usage as cumulative history, resets only the
    new generation's finite counters and never reinterprets an old operation
    ID or sequence as fresh work.
19. Every affected Root and the Coordinator remain funding-fenced from first
    preparation until the exact new Registry generation and Root receipts are
    durably consistent.
20. A stale plan digest, predecessor generation, Registry version, topology
    evidence or participant set rejects before policy mutation.

Same-release interruption recovery is mandatory. Cross-release migration,
rollback and mixed-version recovery are prohibited.

## Stable State and Candid

0.108 is a reinstall-only stable-state hard cut.

The implementation allocates explicit role-owned records for:

- Coordinator global/per-root funding ledger plus one current and one last
  terminal grant result per root;
- root current/last funding operation and acceptance result; and
- the corrected root-owned ICP policy and any automatic-trigger evidence not
  already represented by the refill journal.

The Coordinator funding owner also retains at most one current and one last
terminal policy-rotation operation. The current operation binds the accepted
plan digest, exact predecessor generation and Registry version, complete
bounded affected-Root policy set, topology evidence, retained usage and
monotonic per-Root progress. The existing Root funding owner retains its one
matching prepared/active rotation state; no second Root journal, policy cache
or timer owner is introduced. Terminal history is cumulative and compact:
only current-generation counters, all-predecessor totals and one terminal
rotation receipt are retained.

Rotation is a same-release runtime operation, not cross-release adoption. It
does not change the reinstall-only 0.108 release boundary. On interruption,
the durable rotation fence makes a mixed generation unavailable for new
funding while exact replay converges the same operation. No rollback or
mixed-version protocol is provided.

No record is stored in application memory IDs. The Coordinator ledger owns
memory ID 62, a 32 MiB encoded bound and at most 4,096 Root slots. The Root
request/acceptance journal owns memory ID 63 and a 32 KiB encoded bound. The
existing Root-owned ICP journal remains at memory ID 39 with a 4 KiB maximum
per record and a lifetime limit of 4,096 operation identities. That journal
does not evict terminal identities: once full, creation of a new refill fails
closed while exact retained-operation replay remains available. These owners,
IDs and bounds are published by the state contract and role allocation
catalog.

The public Candid delta adds no method. It is limited to:

- a root-authenticated funding-request variant in `CoordinatorCommand`;
- a Coordinator-authenticated grant-acceptance variant in `RootCommand`;
- bounded funding and operation variants in `CoordinatorStatusRequest` and
  `RootStatusRequest` for diagnosis; and
- corrected manual-refill policy command and status variants on the Root.

The B9 amendment additionally adds controller-authenticated Coordinator
policy-rotation plan/apply variants, exact Coordinator-to-Root prepare/activate
variants and protected rotation status. These extend the maintained `v1`
contract by hard cut; they do not create a second product protocol generation.

The grant-acceptance command variant is publicly callable only at the
transport layer. The Root `canic_command` dispatcher authenticates the exact
protected Coordinator and exact pending operation before accepting any cycles.
No anonymous, controller-selected or arbitrary Canister target is admitted.
Controller kill switches are Root/Coordinator command variants, not admin
methods.

The Root and Coordinator `canic_status` dispatchers likewise derive authority
from the selected status variant before reading funding state. Public overview
cannot select protected treasury, refill-policy, receipt or operation views;
sharing the method name does not share observation authority.

Generated Candid, checked-in role DID files, variant-level protocol constants,
replay policy and payload bounds must advance together. Removed generic refill
configuration and any obsolete endpoint/type names are hard-cut rather than
deprecated.

## Layering and Ownership

The implementation follows the maintained dependency graph: endpoints call
workflow; workflow may call policy and ops independently; ops may call model.
Policy never calls ops.

### `canic-core`

- passive funding/ICP DTOs and protected policy shapes;
- pure threshold, target, budget, reserve and fallback decisions;
- root cycle observation/timer orchestration;
- corrected root-owned ICP-refill workflow and journal;
- exact attached-cycle acceptance primitives and metrics; and
- role/state allocation contracts shared by the facade and control plane.

### `canic-control-plane`

- Coordinator funding workflow and stable ledger;
- Fleet Registry caller and lifecycle authorization;
- Coordinator-to-root attached-cycles call orchestration;
- root lifecycle integration where protected root authority is owned; and
- draining/removal funding fences.

### `canic`

- thin Root/Coordinator role methods and variant dispatch;
- compile-time role surface wiring; and
- no funding policy or state decisions.

### `canic-host`

- strict Fleet-input parsing and validation;
- immutable install-plan propagation;
- Coordinator/root init payload construction;
- activation-time funding readiness evidence; and
- no runtime treasury mutation.

### `canic-cli`

- installed Coordinator and root target resolution;
- manual ICP conversion and exact retry UX;
- funding policy/status rendering; and
- direct operator top-up commands.

Policy code receives named immutable inputs and returns decisions only. It
does not read balances, Registries, stable state or clocks and performs no
async call.

Implementation encodes the exact registered-Root-to-its-one-Coordinator
protocol directly. It must not introduce generic `FundingProvider`,
`TreasuryRecipient`, `TransferProvider`, `GenericBudgetWindow` or generic
reconciled-payment abstractions. A pre-existing narrow primitive may be reused
only when its authority and recovery contract already match exactly. The
deferred Coordinator Worker and arbitrary infrastructure funding remain out of
scope.

## Metrics and Operator Surface

At minimum, metrics distinguish:

- root balance samples and threshold state;
- Coordinator request scheduled, accepted, denied, retrying and uncertain;
- requested and granted cycles;
- per-root and Fleet rolling-window plus non-renewing usage;
- Coordinator available balance and protected reserve;
- root acceptance fresh versus replay;
- fallback eligibility and suppression reason;
- manual versus automatic ICP refill;
- ICP amount, ledger fee, rate gate and cycles received; and
- terminal policy, treasury, transport, ledger, CMC and invariant failures.

Cardinality is bounded by registered root Principal and finite status/reason
labels. Operation IDs do not become metric labels.

`canic cycles` diagnostic output should show, for infrastructure Canisters:

- current balance and burn/runway observations;
- normal and emergency thresholds;
- last Coordinator grant amount/time/result;
- current root/Fleet budget usage;
- remaining non-renewing automatic grant/cycle exposure;
- resolved Subnet node count, cost multiplier and any retained Fiduciary
  acknowledgement;
- pending or recovery-required operation;
- automatic ICP policy presence and last outcome; and
- the exact direct top-up command for recovery.

When 0.111 is implemented, the same operator view must render the root's
operating balance, Coordinator grant exposure and pool Cycles Ledger balance
as three separately labelled values. It must not add them into one apparent
available balance or imply that a successful operating grant funds pending
estate creation.

Secrets are never rendered. ICP subaccounts, when explicitly requested by an
operator, follow the existing redaction and pending-operation rules.

## Security Properties

0.108 must prove:

- a foreign Canister cannot obtain Coordinator cycles;
- one registered root cannot name or fund another root;
- singular-root CLI aliases cannot silently select one root from a multi-root
  Fleet;
- a stale, Joining or Removed root cannot obtain a grant;
- root-reported balance cannot bypass amount, window, cooldown or reserve
  limits;
- no rolling-window reset can restore exhausted automatic grant, cycle or ICP
  authority;
- no timer, elapsed-time transition, restart, restore or repeated policy
  application can create a successor funding generation;
- a stale or concurrent rotation cannot partially authorize a Root, discard
  predecessor usage or make an old operation identity fresh;
- interruption may leave durable records at different rotation phases only
  while the funding fence rejects all new work; it cannot expose a silently
  mixed active generation;
- no default, recommendation or unacknowledged explicit selector can place
  Fleet infrastructure on the Fiduciary Subnet;
- the Coordinator cannot attach more than the root's exact pending amount;
- a root cannot accept the same grant twice;
- response loss cannot cause duplicate Coordinator or ICP spending;
- an uncertain Coordinator effect cannot unlock ICP fallback;
- automatic refill cannot select another ICP source owner or cycles target;
- system-Canister overrides fail closed on IC;
- controller kill switches cannot erase reconciliation evidence; and
- direct top-up remains outside Canister liveness and controller dependence.

The Coordinator is a high-value cycles treasury. Its own creation funding,
controller policy, snapshot fencing, backup evidence and operating reserve
must reflect that role. 0.108 does not claim that automatic funding removes
the need for external balance alerts.

The root pushes directly to the Coordinator, and the Coordinator owns the
value-transfer journal; no
[Coordinator Worker](../ideas/coordinator-workers/design.md) exists
implicitly. Authentication profiles and standalone blob extraction likewise
grant no funding authority.

### 0.109

0.109 replaces the independently managed runtime whitelist with one Fleet-
wide ingress-admission authority and complete role-local projections. Root
funding remains infrastructure-authorized and does not become ordinary
Fleet-member ingress merely because the admission policy is shared.

### 0.111

0.111 may create a bounded reusable root-local physical Canister estate. Its
creation calls spend a separately pre-funded root Cycles Ledger account.
0.108 keeps the root responsive while that work runs, exposes the distinct
balance classes and preserves manual emergency top-up; it does not become the
estate treasury or silently deposit operating grants into the pool account.
Any later automatic Coordinator-to-pool funding path needs an explicit shared
amendment with its own value-transfer journal, immutable budget and
interruption proof.

## Implementation Milestones

## Test Matrix

### Pure Policy

- threshold equality and above/below behavior;
- target subtraction and overflow;
- fixed epoch-anchored root/Fleet windows, cross-boundary reservation
  completion and acceptance-event cooldown;
- one-grant-per-window profile arithmetic and non-renewing cap exhaustion;
- standard-13-node baseline scaling and 10T rounding without overflow;
- Coordinator reserve and exact call-cost inclusion;
- emergency threshold ordering;
- fallback eligibility by terminal reason;
- ICP e8s ceiling division and rounding;
- per-call/window/floor/rate rejection; and
- lifecycle eligibility.

### Stable and Replay

- fresh grant intent and receipt;
- duplicate root request;
- competing request rejection;
- restart before attached call;
- restart after root acceptance but before Coordinator receipt;
- lost Coordinator response and exact root retry;
- zero-accept replay with attached-cycle refund;
- window reservation rollback after definite rejection;
- uncertain reservation retention;
- exact retry, stale/skip rejection and next-sequence replacement for one
  current plus one last result;
- restart and snapshot preservation of non-renewing automatic usage;
- manual/automatic refill exclusion;
- exact funding-policy rotation replay before preparation, after Coordinator
  Registry publication and after one or more Root activations;
- cumulative predecessor usage preservation and new-generation-only counter
  reset;
- stale predecessor, stale digest, changed topology, concurrent rotation and
  old grant-operation rejection; and
- snapshot restore refusal or reconciliation according to the frozen state
  contract.

### Authorization

- anonymous and foreign caller rejection;
- root substitution;
- stale Registry revision/content;
- removed `recommended` selector, missing/mismatched Fiduciary acknowledgement
  and catalog-digest drift;
- mismatched policy hash;
- Joining, Removed and ineligible Draining roots;
- forged amount or observed balance outside policy;
- foreign Coordinator at root acceptance;
- acceptance without pending operation; and
- manual refill by non-controller;
- root-principal selection outside the current Fleet Registry; and
- singular `root` or omitted-root manual targets.

### PocketIC

- installed Coordinator funds one real active root exactly once;
- two roots consume independent limits and one Fleet-wide budget;
- Coordinator reserve prevents an otherwise valid grant;
- response loss converges without a second transfer;
- one Root cannot receive two automatic grants in one 90-day default window;
- rolling-window rollover never restores an exhausted non-renewing cap;
- a terminal no-grant plus emergency balance runs one root ICP conversion;
- an uncertain grant suppresses ICP conversion;
- insufficient ICP and rate-gate denial spend nothing;
- a refilled root continues existing Component funding; and
- a frozen or stopped automatic path recovers through direct operator top-up;
- an exhausted Root retains application state while an explicit rotation
  installs one bounded successor and permits only the next monotonic funding
  operation.

Host-side focused evidence covers topology-profile classification, exact
materialization for single-Subnet, preview multi-Subnet and professional
multi-Subnet Fleets, node-count scaling, removed `recommended` input and both
directions of Fiduciary acknowledgement mismatch without performing a paid
network effect.

Canister creation, inter-Canister value transfer and ICP/CMC behavior use
PocketIC. Production `cfg(test)` behavior must not fabricate management or
ledger success.

## Completion Gate

0.108 is complete only when:

1. every root has explicit protected Coordinator funding policy;
2. the Coordinator has explicit Fleet-wide budget and operating reserve;
3. roots push low-balance requests without Coordinator polling;
4. target identity is always the authenticated caller;
5. attached cycles are accepted once under a durable root receipt;
6. every uncertain grant is reconciled by exact replay, never blind retry;
7. root and Fleet budgets commit exactly once;
8. automatic ICP fallback uses a lower threshold and only a terminal no-grant
   outcome;
9. manual ICP conversion is reachable only through protected root policy;
10. no generic or `canic.toml` root-refill configuration remains;
11. Component/descendant parent funding is behaviorally unchanged;
12. Coordinator/root direct top-up works as break-glass recovery;
13. draining and deletion cannot race new funding;
14. Root/Coordinator status variants deny every public/operator/peer crossing
    before protected funding state is read;
15. state, Candid, metrics, CLI and runbooks agree;
16. focused and PocketIC qualification passes;
17. all three funding-profile scaffolds materialize the frozen baselines and
    reject continuous-top-up configurations;
18. no automatic count/cycle/ICP authority renews on window rollover;
19. Fiduciary placement is impossible without exact per-placement
    acknowledgement and a retained high-cost warning;
20. the closeout audit finds no alias, compatibility decoder, automatic
    unknown-effect fallback, arbitrary-target escape hatch or implicit estate
    funding path;
21. a no-effect rotation plan reports exact predecessor authority, retained
    usage, topology evidence, successor exposure and funding source;
22. rotation apply is controller-only, digest-bound, replay-safe and remains
    funding-fenced until the Coordinator and every affected Root expose the
    same successor generation; and
23. generation rotation never renews by time, discards historical use,
    mutates application policy, forces a profile transition or makes an old
    operation identity fresh.

## Resolved Implementation Decisions

The 0.108.1 implementation resolves the former implementation gates as
follows:

1. the role surfaces use Coordinator `RequestRootFunding` and
   `SetRootFunding`, Root `AcceptFunding` and `RefillCycles`, and protected
   Coordinator/Root `Funding` status variants beneath the existing role
   methods;
2. the exact stable owners and bounds are memory ID 62/32 MiB/4,096 Roots,
   memory ID 63/32 KiB and memory ID 39/4 KiB per refill record/4,096 lifetime
   refill identities;
3. only Coordinator reserve, Fleet-window and Root-window terminal no-grants
   may authorize emergency ICP fallback; uncertainty, cooldown, disabled
   policy, authority mismatch, ineligibility and exhausted non-renewing caps
   cannot;
4. deterministic adapter tests retain local stubs, while value-transfer
   qualification uses PocketIC 15's built-in production ICP Ledger and CMC;
   and
5. restart resumes retained same-release work, while snapshots/upgrades fail
   closed until grant/refill work is non-resumable. Cross-release adoption is
   outside 0.108's reinstall-only contract; and
6. the accepted CANIC-019 amendment permits only explicit same-release
   successor funding generations. It uses one Coordinator rotation owner and
   each Root's existing funding owner, fences all automatic effects during
   convergence and retains cumulative predecessor usage.

These decisions do not change the Coordinator-first authority, lower emergency
threshold, exact-caller target, intent-before-effect or
no-fallback-on-uncertainty invariants.
