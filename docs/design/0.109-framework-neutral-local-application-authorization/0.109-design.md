# Canic 0.109 Design: Framework-Neutral Local Application Authorization

**Date:** 2026-08-13
**Last amended:** 2026-08-16

## Status

- **Classification:** accepted and scheduled as 0.109, the first line after the
  0.103-0.108 reserve-Fleet critical path.
- **Review status:** peer-review lifetime, client-access, predecessor,
  lifecycle-composition and revocation feedback are retained. This scheduling
  cut authorizes no evidence or runtime implementation.
- **Release boundary:** reinstall only. A 0.109 installation starts from fresh
  current-schema state and does not decode, import, migrate or adopt pre-0.109
  delegated-session state.
- **Sequence:** this line follows accepted 0.108 closeout. It is a scheduled
  successor, not another dependency of the reserve-Fleet critical path.
- **Predecessor gate:** B1 must inventory the exact released 0.108 source and
  may begin only after its closeout and explicit maintainer promotion. No
  mutating 0.109 batch begins before the resulting B1 contract is accepted.
- **Protocol posture:** pre-1.0 hard cut. Removed records, APIs, methods and documentation disappear; there is no alias, fallback, legacy decoder, dual write or dual authorization path.
- **Dependency posture:** this is a Canic-only design. Canic does not depend on IcyDB or any other application framework. No external framework release, repository, type, lifecycle macro or test suite gates 0.109. A consuming application may independently depend on Canic and another framework and may adapt their public contracts in application-owned code.
- **Authority posture:** local application authorization is separate from Canister controllership. Neither controllers nor Fleet infrastructure receive an implicit application-access bypass.

## Decision

Canic will replace its subject-only delegated session with one bounded, caller-bound, scope-bearing local application session derived from a fully verified delegated token.

The session lets an unchanged application endpoint make a synchronous local decision:

```text
observed transport caller + required application scope
    -> Allow(authenticated application subject) | Deny(reason)
```

The access adapter reads `msg_caller` and current IC time exactly once, loads one bounded protected snapshot and delegates to pure policy. The policy performs no IC API read, await, inter-Canister call, state mutation, cleanup, logging, payload parsing or application-data access. This is suitable for an application-owned guard in front of an endpoint whose existing ABI cannot carry a Canic token on every request.

This is not a reader registry or a second grant system. The delegated-token verifier remains the sole authority for issuer trust, Fleet audience, target role, authenticated subject, granted scopes and proof freshness. Protected local role policy separately authorizes the lifetime of the session created from that verified proof. The establishment proof remains valid for at most 60 seconds; the resulting caller-bound session may remain valid for at most 30 minutes and never widens the verified scope set.

Proof expiry and session expiry are deliberately different clocks. Proof expiry limits when new local authority may be established and how long replay evidence must remain live. It does not terminate an already-committed local session. Session expiry limits how long that retained local authority may be used and is independently bounded by protected configuration, the request and the 30-minute hard ceiling.

## Problem

Retained Canic 0.101.53 evidence records two relevant capabilities that B1
must confirm against the exact released 0.108 predecessor:

- a proof-bearing Canic endpoint can verify a delegated token locally against the current Fleet, role, subject, scopes and time; and
- a bounded delegated session can map a transport caller to an authenticated subject.

In that baseline, they do not compose:

- the subject-only session does not retain verified issuer, Fleet, role, scope, authority-generation or strict-expiry evidence; and
- the maintained scoped guard obtains its delegated token from Candid argument zero on every call.

The proof-bearing lane is correct for Canic-owned endpoints. It cannot authorize an unchanged endpoint whose ABI is owned by an application or another library. Adding a Canic token argument would change that endpoint's contract and couple its owner to Canic.

Using controllership instead is wrong in both directions:

- it gives a reader install, upgrade, stop and delete authority; and
- a managed Component may be controlled only by Fleet infrastructure, leaving no human application caller able to use a controller-gated read surface.

0.109 closes the reusable Canic gap without adding framework-specific policy.

## Goals

0.109 must:

- separate application authorization from controller and infrastructure authority;
- reuse the existing delegated-token verifier and existing Fleet/role/scope policy;
- replace the weaker subject-only session rather than add a parallel session meaning;
- bind retained authority to the exact transport caller, authenticated subject, issuer, Fleet, role, scope subset, authority generation and strict expiry;
- expose one synchronous, local, bounded and side-effect-free authorization decision;
- preserve an unchanged application endpoint ABI;
- fail closed when configuration, session state or current protected authority is absent, expired or inconsistent;
- make establishment, replacement, clear, expiry and policy staleness finite and inspectable;
- allow separate application scopes for surfaces with different sensitivity;
- make active local authority auditable through Canic's protected operator-inspection path;
- separate short proof freshness from a configurable practical session lifetime without weakening caller, scope or generation binding;
- support proof acquisition by browser and non-browser clients through the same authenticated IC ingress contract;
- preserve same-release upgrade reconstruction and bounded cleanup; and
- prove instruction, stable-memory and raw-Wasm costs before promotion.

## Non-Goals

0.109 does not:

- add an IcyDB, SQL, schema, database, reader or framework-specific type, field, endpoint, metric or diagnostic;
- modify or gate any downstream repository;
- add a principal whitelist, reader registry, entitlement database or second grant store;
- make any application endpoint public or anonymous;
- make controllers implicit application readers;
- pass a token, scope or Canic authorization blob through a foreign endpoint ABI;
- define row-, field-, tenant-, project-, object- or statement-level policy;
- authorize application mutation merely because a scope check succeeds;
- call a parent, Fleet Subnet Root, Fleet Coordinator, issuer, management Canister or remote policy service during authorization;
- add a generic policy language, dynamic predicate registry, callback registry or remote-decision cache;
- promise instantaneous Fleet-wide revocation without locally activated evidence;
- preserve pre-0.109 session state or methods;
- solve lifecycle-macro composition with an unrelated runtime; that work is
  assigned to the independent
  [synchronous lifecycle-composition idea](../ideas/framework-neutral-synchronous-lifecycle-composition/design.md); or
- replace the broader unnumbered
  [declarative authentication-profile idea](../ideas/declarative-authentication-profiles/design.md).

## Caller, Subject And Presenter Binding

The transport caller and authenticated application subject are deliberately distinct identities:

- `transport_caller` is the principal sending the establishment request and every later guarded request;
- `authenticated_subject` is the delegated application subject and equals the verified token claim `subject`; and
- raw controller, topology, parent, root, Fleet and infrastructure checks continue to use `transport_caller`, never `authenticated_subject`.

0.109 does not define `transport_caller == authenticated_subject`. A wallet or other admitted presenter may act for a different application subject because the one current proof protocol cryptographically binds the presenter, subject and proof together.

The 0.109 `DelegatedTokenClaims` contract hard-cuts in one required signed field:

```rust
pub struct DelegatedTokenClaims {
    pub presenter: Principal,
    // The remaining current 0.109 claims fields, including `subject`.
}
```

The presenter contract is normative:

- token preparation derives `presenter` from the authenticated ingress caller; no request field may nominate or override it;
- canonical claims encoding and the claims hash include `presenter`, so the issuer proof signs the exact presenter and subject together;
- token retrieval remains bound to the same authenticated preparation caller;
- verification returns both the signed `presenter` and signed `subject` in the one verified-authority projection;
- every proof-bearing and session-establishment boundary requires signed `presenter == msg_caller` before using `subject` as authenticated application identity;
- the old direct-path `subject == msg_caller` rule is removed rather than retained as a second identity meaning;
- the runtime caller is not merely a cache-key input; cache identity and every positive-cache hit remain subordinate to the signed-presenter check; and
- a token without `presenter` is an unsupported pre-0.109 shape and is never decoded, imported, upgraded, aliased or accepted.

An unbound bearer proof is never accepted merely because it is presented first. First successful presentation atomically consumes an already presenter-bound verified proof identity and records the exact `(proof_fingerprint, transport_caller, authenticated_subject)` binding; it does not manufacture missing delegation authority. When different callers present the same proof, only its signed presenter may satisfy authorization, regardless of arrival order. Replay state prevents the consumed proof from later being rebound. There is no parallel bearer, relay or subject-equals-caller compatibility lane.

## Explicit Enablement And Surface Discovery

Local application authorization is opt-in for each managed application-
canister role. Fleet Subnet Root, Fleet Coordinator and Wasm Store do not host
application-owned guarded endpoints and cannot enable this capability.

The role must explicitly enable both:

- the existing `delegated_token_verifier = true` capability; and
- the new local-application-authorization capability.

The exact configuration location and spelling are frozen in B1 using the repository's current configuration conventions. The semantic rules are fixed:

- enabling local application authorization without delegated-token verification is a host/configuration error;
- an enabled role declares positive `default_session_ttl_secs` and `maximum_session_ttl_secs` values under the same protected capability configuration;
- the configured default must not exceed the configured maximum, and the configured maximum must not exceed 1,800 seconds;
- omission of the local-application-authorization capability means disabled,
  never allow;
- disabled roles compile no application-session command or status variant;
- enabled roles add exactly the variants defined below to their existing
  managed-canister role protocol and add no method identity;
- the Rust authorization facade returns `Disabled` if called in a role where the capability is not enabled;
- configuration cannot name a framework, method, table or application resource; and
- runtime environment variables or mutable unprotected state cannot enable the capability.

Variant presence in the current Candid distinguishes “capability not compiled”
from a denial returned by an installed capability. Enabling the first mutating
Canic capability may cause the managed role's fixed optional `canic_command`
method to be emitted, but the capability does not own or name another method.
Within an installed surface, compact diagnostic codes distinguish malformed
proof, invalid authority, resource exhaustion and other establishment
failures. The Rust-only local decision distinguishes its closed denial reasons
without exporting Canic detail through another framework automatically.

## Public Canic Contract

### Managed-Role Command And Status Variants

An enabled managed role compiles these variants into its role-owned protocol:

```candid
type ApplicationScope = text;
type ApplicationSessionRequest = record {
  delegated_token : DelegatedToken;
  requested_scopes : vec ApplicationScope;
  requested_ttl_secs : opt nat64;
};
type ApplicationSessionView = record {
  authenticated_subject : principal;
  issuer : principal;
  scopes : vec ApplicationScope;
  established_at_ns : nat64;
  expires_at_ns : nat64;
  authority_generation : nat64;
};
type InactiveApplicationSession = variant {
  Missing;
  Expired : record { expired_at_ns : nat64 };
  StaleFleet;
  StaleRole;
  StaleGeneration : record {
    session_generation : nat64;
    current_generation : nat64;
  };
  InadmissibleSubject;
};
type ApplicationSessionStatus = variant {
  Active : ApplicationSessionView;
  Inactive : InactiveApplicationSession;
};
type ApplicationSessionCommand = variant {
  Establish : ApplicationSessionRequest;
  Clear;
};
type ApplicationSessionCommandResponse = variant {
  Established : ApplicationSessionView;
  Cleared;
};

type CanisterCommand = variant {
  // Other compiled managed-role command variants.
  ApplicationSession : ApplicationSessionCommand;
};
type CanisterCommandResponse = variant {
  // Other compiled managed-role response variants.
  ApplicationSession : ApplicationSessionCommandResponse;
};
type CanisterStatusRequest = variant {
  // Other compiled managed-role status variants.
  ApplicationSession;
};
type CanisterStatusResponse = variant {
  // Other compiled managed-role status responses.
  ApplicationSession : ApplicationSessionStatus;
};

canic_command :
  (CanisterCommand) -> (variant { Ok : CanisterCommandResponse; Err : Error });
canic_status :
  (CanisterStatusRequest) ->
  (variant { Ok : CanisterStatusResponse; Err : Error }) query;
```

`DelegatedToken` is the one current 0.109 Canic type and its claims contain the required signed `presenter : principal` field defined above. The pre-0.109 token shape is removed completely. `Error` uses the current compact numeric record descended from 0.102; B4 does not implement against a provisional diagnostic shape. The generated Rust DTO names follow these Candid names unless B1 proves an existing canonical naming rule that requires a mechanical adjustment before B2. No downstream design owns these names or fields.

The establishment payload deliberately contains no separate unsigned caller,
subject, issuer, Fleet, role, generation or expiry timestamp supplied as
authority. The IC supplies the observed transport caller; the signed token
supplies its presenter and subject; the verifier and protected local state
derive every other authoritative value.

`requested_scopes` narrows verified delegated authority. `requested_ttl_secs` narrows the separately configured local-session ceiling:

- `requested_scopes` must be non-empty and a subset of the token's verified local scopes;
- unsorted requested scopes are accepted and sorted once at the boundary;
- exact duplicate requested scopes are rejected rather than silently deduplicated;
- no empty list means “all scopes”;
- an ungranted requested scope rejects the complete establishment request;
- `requested_ttl_secs` must be nonzero when present and must not exceed the role's protected configured maximum or the 1,800-second hard ceiling;
- proof remaining lifetime does not clamp session lifetime, but the proof must be currently valid and eligible when a new session is committed; and
- invalid requests leave any existing session unchanged.

### Rust-Only Authorization Facade

The public facade exposes one synchronous local decision equivalent to:

```rust
pub struct LocalApplicationAuthorizationRequest<'a> {
    pub observed_transport_caller: Principal,
    pub required_scope: ApplicationScopeRef<'a>,
}
pub enum LocalApplicationAuthorizationDecision {
    Allow(AuthorizedApplicationSubject),
    Deny(LocalApplicationAuthorizationDenial),
}
pub struct AuthorizedApplicationSubject {
    pub subject: Principal,
    pub expires_at_ns: u64,
}
pub enum LocalApplicationAuthorizationDenial {
    Disabled,
    CallerMismatch,
    Anonymous,
    MissingSession,
    Expired,
    StaleAuthority,
    InadmissibleSubject,
    MissingScope,
    AuthorityUnavailable,
}
```

B1 freezes the exact module path and derives. The semantics and denial partition above are normative.

The facade/access boundary:

- reads the actual IC transport caller and current time exactly once;
- compares it with `observed_transport_caller` before session lookup;
- loads one bounded protected-authority snapshot and one canonical session record through ops;
- passes caller, time, required scope, protected snapshot and record to pure policy;
- accepts one already-validated borrowed `ApplicationScopeRef`, never an unchecked `&str`;
- returns only the authenticated subject and strict session expiry on success;
- contains no Candid or Serde obligation unless a current Canic facade convention independently requires one;
- has no success variant that means controller, infrastructure caller or anonymous; and
- does not expose issuer, Fleet internals, proof fingerprints or diagnostic prose to the guarded endpoint.

The explicit caller comparison prevents an adapter from authorizing one principal while the surrounding framework serves another.

Policy never calls `msg_caller`, time, stable storage or another IC API itself.

## Canonical Scope Contract

0.109 does not describe its proposed grammar as the predecessor contract. The retained 0.101.53 evidence admits a different character set, has no equivalent 64-byte rule and permits 32 scopes in one role grant. B1 must refresh that evidence against 0.108. The following is an intentional 0.109 hard cut, subject to B1 inventory and maintainer acceptance before B2.

One model module declares the owned `ApplicationScope`, its borrowed validated form and every bound. The tuple/string field is private. Ops, policy, access, DTO and facade code import or re-export those types; none redeclares them.

The 0.109 canonical scope grammar is:

- 1 to 64 ASCII bytes;
- colon-separated non-empty namespace segments;
- each segment starts with `[a-z0-9]` and thereafter contains only `[a-z0-9_-]`;
- no `.`, whitespace, uppercase, Unicode, empty segment or trailing separator;
- exact byte equality with no case folding or Unicode normalization;
- at most 32 scopes in a verified role grant, preserving the current grant ceiling unless B1 approves a lower hard cut;
- at most 16 requested and retained scopes in one local application session;
- at most 1,024 aggregate scope bytes in one session; and
- sorted canonical storage with binary-search membership.

Ordering has no authority meaning. Boundary sequences may arrive unsorted and are sorted once. Exact duplicates are rejected before signing or persistence; they are not silently deduplicated. Signed/certified canonical material must already commit to the sorted unique representation required by its current owner.

Application code constructs a static validated scope through one facade re-export of a domain-owned compile-time helper, conceptually:

```rust
pub const SQL_READ: ApplicationScopeRef<'static> =
    canic::application_scope!("my_app:sql_read");
```

The helper validates the same grammar at compile time and creates no runtime registry. Dynamic host/configuration input uses the domain type's one checked parser. There is no public unchecked constructor and no first-call lazy initialization in a query guard.

Application scope issuance reuses the current delegated grant owner:

- role configuration explicitly declares which canonical application scopes that role may receive;
- public proof/token preparation may request only scopes declared for the target role and admitted by current issuer policy;
- certificate/token construction sorts and commits the exact granted scope set;
- local verification reconstructs that same set; and
- session establishment may retain only the caller-requested subset.

This is an extension of the existing role-grant authority, not a second allowlist. A free-form client string does not create an issuable scope. B1 must inventory the current login-only preparation path and freeze its hard-cut replacement so application-specific scopes can be admitted explicitly without aliases or a parallel preparation API; the owning authorized mutating batch applies that cut.

Application code owns scope meaning. Names should be application-namespaced and capability-specific. Separate surfaces with materially different sensitivity use separate scopes. Broad historical scopes such as `read` survive only if B1 proves they are intentional current authority; otherwise they are removed by the hard cut rather than aliased.

## One Verified Authority Projection

Proof-bearing and session-bearing lanes remain two evidence transports, not two grant authorities.

The model owner declares one internal `VerifiedApplicationAuthority` value. Ops converts the current verifier's successful runtime material into it; access and policy never reconstruct it independently. It contains only the verified values needed by common policy:

- signed presenter, already proven equal to the transport caller;
- authenticated subject;
- issuer;
- current Fleet binding;
- current role binding;
- canonical granted local scopes;
- authority generation;
- verified proof issue/not-before/expiry bounds; and
- the existing proof identity needed by replay policy.

A Canic-owned proof-bearing endpoint consumes that projection immediately. Session establishment uses a currently valid eligible proof to mint one protected local session whose scopes are an exact requested subset and whose lifetime is bounded by protected local-session configuration. Proof validity authorizes the establishment event; it is not reused as the session-expiry clock. The session-bearing lane can never fabricate, union, extend or delegate scope authority.

Facade code may re-export public domain types but does not own their declaration.

0.109 removes duplicate caller/subject binding, scope matching, expiry and denial classification exposed by this convergence. The old subject-only session does not remain as a fallback identity lane.

## Canonical Session And Replay State

The authoritative active record is conceptually:

```rust
pub struct LocalApplicationSessionRecord {
    transport_caller: Principal,
    authenticated_subject: Principal,
    issuer: Principal,
    fleet: FleetKey,
    role: CanisterRole,
    scopes: Vec<ApplicationScope>,
    authority_generation: u64,
    established_at_ns: u64,
    expires_at_ns: u64,
    proof_fingerprint: [u8; 32],
    establishment_request_hash: [u8; 32],
}
```

The exact private encoding is frozen after B1. A field may be replaced by a smaller canonical binding only if all authorization and audit invariants remain mechanically provable. The record does not retain:

- encoded proof, certificate or signature bytes;
- arbitrary proof extensions;
- certificate hashes that are not consulted by current policy;
- framework, endpoint, method or resource identity;
- application rows, object identifiers or entitlement state;
- diagnostic prose; or
- authority for another Fleet or role.

Replay state is authoritative only for proof-consumption semantics. It is not a grant. A bounded replay record contains the proof fingerprint, bound caller/subject, authority generation and strict removal time needed to prevent reuse or resurrection. Every successfully consumed proof remains recorded through its own verified proof expiry, even after its session expires, is replaced, is cleared or its authority generation becomes stale.

Application-session establishment accepts only a proof whose complete verified lifetime is at most 60 seconds. “Complete verified lifetime” means `expires_at - issued_at` under the one current proof contract, not merely the proof's remaining lifetime when presented. If that lifetime cannot be proven from signed/certified material, establishment denies. The ordinary delegated-token ceiling may remain longer for proof-bearing endpoints, but such a long-lived proof is ineligible for this tokenless-session bridge. Tombstones therefore remain live for no more than 60 seconds from proof issue time, making their capacity a bounded burst limit rather than a 30-minute-session accumulator.

The protected local-session capability is the authority that permits a verified proof to create a longer-lived local session. A proof must be valid at the first successful commit, but its later expiry does not invalidate that committed session and does not advance session expiry. The session remains bound to the exact caller, subject, issuer, Fleet, role, scope subset and authority generation and is independently limited by protected configuration and the 1,800-second hard ceiling.

Heap lookup indexes and subject-count indexes are derived state. They are rebuilt from canonical records, never serialized as independent authority and never consulted without the corresponding canonical record.

## Establishment, Replacement, Replay And Clear

Session establishment follows this exact order:

1. read the transport caller from IC ingress;
2. reject anonymous;
3. require the protected local-application-authorization and delegated-verifier capabilities;
4. validate and bound the requested scope set and TTL before expensive work;
5. compute the canonical proof fingerprint and establishment-request hash without treating decoded claims as authority;
6. derive the current Fleet, role, authority generation and session-TTL policy from protected local state;
7. return an existing byte-exact receipt only when the same caller, proof and request still select the exact active, unexpired, current-generation session, without extending it, even when the proof has since expired; reject a conflicting reuse before proof verification;
8. for a nonterminal request, verify the complete token through the one current verifier, require it to be currently valid and require its complete verified lifetime to be at most 60 seconds;
9. require signed `token.claims.presenter` to equal the transport caller and signed `token.claims.subject` to equal the authenticated application subject;
10. require every requested scope to be in the verified local scope set;
11. calculate strict effective session expiry;
12. evaluate replacement and capacity policy without mutating state;
13. atomically commit the active session and required replay record; and
14. return the canonical current view.

Effective session expiry is exclusive. The selected TTL is
`requested_ttl_secs` when present and the protected configured default when
omitted. It must be positive and no greater than both the protected configured
maximum and `MAX_LOCAL_APPLICATION_SESSION_TTL`. Expiry is exactly
`established_at + selected_ttl`.

Arithmetic is checked. An already-expired or zero-duration result is rejected. The configured default may be lower than the hard ceiling but never higher.

The hard maximum accepted application-session proof lifetime is 60 seconds.
The hard maximum local application-session lifetime is independently 1,800
seconds. The boundary accepts an otherwise valid 60-second proof and permits a
protected configured session maximum of exactly 1,800 seconds. Roles may choose
lower protected defaults or maxima. Changing either hard maximum requires a
design amendment; B1 cannot silently lower one to fit an implementation.

Replay and replacement semantics are:

- exact replay of the same proof by the same caller with the same requested scopes and TTL is idempotent only while the exact session remains active, unexpired and current-generation; its durable request hash returns that session without extending expiry even after proof expiry;
- the same proof with different scopes, TTL, caller or subject is rejected and cannot replace authority;
- presentation of the same proof by a different caller is denied by presenter binding and remains a replay conflict even when no active session remains;
- the same proof can never extend a session or recreate a cleared session;
- a different currently valid proof for the same caller atomically replaces the old session with exactly the newly requested verified subset and newly selected bounded TTL; scopes are replaced, never unioned;
- replacement retains the old proof's replay tombstone until that proof expires, so a caller cannot roll back to earlier or broader authority;
- invalid proof, invalid narrowing request or capacity rejection leaves the old session unchanged;
- replacement that causes no net global growth is evaluated against the post-replacement per-subject counts; and
- interrupted exact retry observes either the old complete state or the new complete state, never a partial record.

`ApplicationSessionCommand::Clear` is caller-scoped and idempotent. It rejects
an anonymous caller, then removes the calling principal's retained session
record whether that record is active, expired or stale. No record returns
success. Clear retains every consumed proof fingerprint as a bounded tombstone
until that proof's strict expiry, so it cannot be reversed with the same proof.
A fresh valid proof may establish a new session.

Authority-generation change invalidates active sessions but does not erase, re-key or make reusable a live proof fingerprint. A fresh proof under the current generation is required.

`CanisterStatusRequest::ApplicationSession` is read-only. It returns `Active`
only when the caller's record currently passes caller, time, Fleet, role,
generation and subject-admissibility checks. A physically retained invalid
record uses the first matching classification in this exact precedence:

- missing or already cleaned -> `Missing`;
- strict time failure -> `Expired`;
- Fleet mismatch -> `StaleFleet`;
- role mismatch -> `StaleRole`;
- generation mismatch -> `StaleGeneration`;
- subject no longer admissible -> `InadmissibleSubject`; and
- protected-authority read failure -> compact Canic error.

It never prunes or repairs state.

The managed-role `canic_status` dispatcher authenticates this caller-scoped
variant before reading a session record. The protected paginated operator view
is a separate managed-role status variant with Fleet/operator inspection
authority, not a session-specific method; selecting it never inherits the
caller-self authority of `ApplicationSession`.

Cleanup removes expired active records and replay tombstones in bounded work. Authorization itself never performs cleanup.

## Local Authorization Algorithm

Authorization has a value-acquisition boundary followed by pure policy.

The access adapter:

1. reads actual `msg_caller` and current IC time exactly once;
2. receives the application/framework-observed caller and validated required scope;
3. loads one bounded protected-authority snapshot through ops; and
4. loads at most one canonical session record through the exact-caller index.

It then calls pure policy with those values. Policy applies this fixed denial precedence:

1. actual caller is anonymous -> `Anonymous`;
2. actual caller differs from observed caller -> `CallerMismatch`;
3. local application authorization is disabled -> `Disabled`;
4. protected authority is unavailable -> `AuthorityUnavailable`;
5. no exact canonical record exists -> `MissingSession`;
6. current time is not strictly before expiry -> `Expired`;
7. Fleet, role or authority generation differs -> `StaleAuthority`;
8. authenticated subject is no longer admissible -> `InadmissibleSubject`;
9. required scope is absent -> `MissingScope`; and
10. otherwise -> `Allow`.

The access adapter may read `msg_caller`, time and bounded Canic-owned state. Neither access nor policy performs an inter-Canister call or await. Policy performs no IC API read. No authorization step mutates, prunes, logs, schedules work, reads application state, parses endpoint payload or observes another framework's readiness.

The authorization hot path is `O(log G + log S)` or better, where `G` is the bounded active-session count and `S` is the bounded sorted scope count in the selected session. It does not scale with application rows, schemas, indexes, receipts, logs or endpoint argument length.

## Controllers, Infrastructure And Application Subjects

Controller and topology authority remain separate from application identity:

- a controller does not pass local application authorization unless it independently establishes a valid scoped session;
- a Fleet Coordinator, Fleet Subnet Root, Component parent or managed child relationship does not imply an application session;
- topology and infrastructure guards continue to consume the raw transport caller, never the authenticated application subject returned here; and
- application resource ownership continues to consume application-owned state after Canic authentication.

0.109 does not infer “human” or “Canister” from principal text. It reuses the current typed subject-admissibility and infrastructure-authority rules. B1 must inventory any string or principal-shape heuristic and freeze its removal by the owning authorized mutating batch. If current Canic cannot prove the distinction for a given path, that path fails closed rather than guessing.

## Expiry, Policy Change And Revocation

The revocation contract is local and bounded:

- caller clear is immediate on that Canister and the consumed proof cannot resurrect the session;
- strict session expiry is no later than 1,800 seconds after establishment and never later than the selected protected/requested session bound;
- proof expiry prevents a new establishment but does not invalidate or extend an already-committed session;
- a locally activated authority-generation change invalidates every session from an earlier generation immediately on that Canister;
- verifier disablement or unavailable protected authority denies immediately;
- accepted-issuer or granted-application-scope removal advances the local authority generation and denies existing sessions from the prior generation; and
- without a locally activated generation change or immediate-denial condition, a previously established session remains usable only until its already-fixed strict expiry.

Authority generation is one durable monotonic Canic-owned value or an existing equivalent current owner. Every locally activated change classified as generation-advancing below must change that binding before ingress is admitted; immediate-denial inputs are re-evaluated on the hot path. B1 must identify the existing owner; B2 must consolidate rather than introduce a second generation counter.

B1 must confirm this complete transition table against the current authority owners. The listed 0.109 behavior is normative:

| Locally activated change | Existing-session behavior |
| --- | --- |
| Verifier disabled | Deny immediately without waiting for cleanup |
| Fleet binding changes | Advance generation; prior-generation sessions deny |
| Role binding changes | Advance generation; prior-generation sessions deny |
| Accepted issuer removed | Advance generation; prior-generation sessions deny |
| Granted application scope removed | Advance generation; prior-generation sessions deny, even when unrelated scopes remain |
| Default session TTL changes | Apply to future establishment only; do not advance generation |
| Maximum session TTL reduced | Advance generation; prior-generation sessions deny rather than remain grandfathered |
| Subject-admissibility changes | Re-evaluate current protected admissibility and deny immediately |

Increasing the configured maximum session TTL affects future establishment only and remains bounded by the 1,800-second hard ceiling. Any additional current input that can change whether a retained session is valid must be added to this table during B1 and assigned an explicit future-only, immediate-denial or generation-advancing disposition before B2.

Documentation must not call this instant Fleet-wide revocation. The operator surface reports the exact local generation and maximum remaining staleness. Per-resource entitlement requiring immediate revocation stays in application-owned state and is checked after Canic returns Allow.

## Stable State, Lifecycle And Recovery

0.109 has one current persisted format. Pre-0.109 bytes are unsupported because the release boundary is reinstall only.

For the current format:

- active sessions and replay tombstones have one canonical encoding;
- derived indexes are not independent persisted authority;
- restore validates bounds, uniqueness, canonical scopes, caller keys, generation and time arithmetic;
- corrupt or over-limit authority state fails closed and cannot be partially admitted;
- the exact-caller and subject-count indexes are rebuilt synchronously before ingress or deferred application work;
- expired records may remain physically present after restore but are unusable immediately and are removed only by bounded cleanup;
- the cleanup timer/operation is registered through the existing Canic timer owner;
- same-release upgrade preserves current-format active sessions and tombstones;
- backup and restore use the same canonical snapshot model; and
- interrupted establishment is recovered as an atomic old-or-new outcome.

`canic::start!` remains the Canic lifecycle owner. This idea restores only
Canic-owned authority. Its optional user block is deferred and is not a
synchronous lifecycle-participant seam. The authorization contracts compose
at the function level. Runtime composition with another lifecycle-owning
framework additionally requires the separately qualified
[synchronous lifecycle-composition idea](../ideas/framework-neutral-synchronous-lifecycle-composition/design.md).
That seam is authorization-independent work outside this idea, and no
combined runtime qualification may be claimed until it exists and proves
single-owner lifecycle ordering.

Release-set activation must not expose a mixture of pre-0.109 and 0.109 Canic session semantics within one maintained Fleet release. Existing release-set identity and activation authority enforce the reinstall boundary; no versioned session protocol or dual decoder is added.

These are promotion ceilings, not capacity targets:

| --- | --- |
| Active sessions per Canister | 2,048 |
| Active sessions per authenticated subject | 128 |
| Retained replay fingerprints per Canister | 4,096 |
| Retained replay fingerprints per subject | 256 |
| Canonical scopes per session | 16 |
| One canonical scope | 64 bytes |
| Aggregate scope bytes per session | 1,024 bytes |
| One encoded active-session record | 2,048 bytes |
| Canonical stable active-session and replay state at maximum admission | 8 MiB |
| Reconstructed heap indexes at maximum admission | 4 MiB |
| Expired entries removed by one cleanup invocation | 128 |
| Accepted application-session proof lifetime | 60 seconds |
| Configured default local application-session lifetime | 1 to 1,800 seconds |
| Configured maximum local application-session lifetime | configured default to 1,800 seconds |
| Hard maximum local application-session lifetime | 1,800 seconds |
| Local authorization at maximum admitted state | 1,000,000 IC instructions |
| Raw non-gzipped Wasm growth over the accepted predecessor | 256 KiB |

B1 records the current values and may propose lower non-lifetime resource limits. The 60-second proof and 1,800-second session hard ceilings are already frozen; changing either requires a design amendment. B2 freezes the remaining constants. Admission validates encoded and aggregate sizes before commit. Fresh growth over capacity returns a typed resource-exhausted diagnostic and leaves existing state unchanged. Replacing an existing caller's session does not require a spare global slot but must satisfy every post-replacement bound. B1 also proves that active-session capacity is adequate for the configured 30-minute ceiling independently of replay-tombstone capacity.

No live replay tombstone is evicted to admit renewal. Because an eligible proof lives for at most 60 seconds, B1 must prove that the maximum admitted proof-issuance burst in any rolling 60-second window is no greater than 256 per subject and 4,096 per Canister, or lower those upstream issuance limits. Normal renewal cannot accumulate tombstones across a 24-hour token lifetime because such a token is ineligible for session establishment.

Measurements distinguish:

| Symbol | Measurement |
| --- | --- |
| E | establishment instructions, including cold and warm proof verification |
| A | allowed local authorization at 1, median and maximum admitted G and S |
| D | denial instructions for each closed denial reason |
| B | stable bytes per active session and replay record |
| H | reconstructed heap-index bytes at maximum admitted state |
| R | synchronous restore/index reconstruction at maximum state |

Raw canonical release Wasm is authoritative. Builder-produced gzip is secondary context.

## Diagnostics, Metrics And Auditability

Public Canic endpoint failures use the exact compact diagnostic registry released by 0.102. Establishment must allocate distinct current codes for at least:

- capability disabled or unavailable;
- malformed or non-canonical requested scope;
- requested scope not granted;
- invalid, expired, wrong-audience, wrong-role or caller-mismatched proof, subject to the existing security projection policy;
- replay conflict;
- invalid TTL; and
- capacity exhaustion.

Sensitive verifier detail retains its internal numeric diagnostic and maps to a safe public code. No arbitrary verifier, token or application prose crosses the public boundary.

The Rust-only denial enum is not automatically serialized by a consuming endpoint. An application adapter normally collapses every denial to its own surface-specific denial. Canic never dictates that foreign diagnostic.

Bounded metrics cover:

- establishment started, completed and rejected;
- create, replacement and idempotent replay;
- clear, strict-expiry observation and cleanup;
- replay conflict and capacity rejection; and
- authority-generation invalidation.

The pure authorization function does not mutate metrics. A Canic-owned endpoint wrapper or consuming application may record aggregate allow/deny counts outside the decision. Metrics and logs never label token bytes, proof fingerprints, SQL/payload content, transport callers, authenticated subjects, scopes or resource identifiers.

Audit answers three different questions without conflating them:

- What can be established? Protected operator inspection reports enabled state, accepted issuer policy, current Fleet, role, authority generation, scope grammar, proof-lifetime ceiling and configured default/maximum session lifetimes.
- What is active now? A bounded paginated operator view, protected by Canic's existing Fleet/operator inspection authority rather than raw controllership alone, reports each active caller, authenticated subject, issuer, canonical scopes, establishment time, strict expiry and generation. It omits proof fingerprints and proof bytes.
- What resources may the subject use? Canic does not answer this; the consuming application owns it.

The caller's application-session status variant reports only that caller's
current session view. Anonymous receives no session information. Operator
inspection distinguishes declared configuration, protected runtime binding
and observed current sessions, and marks expired-but-not-yet-cleaned records
as inactive.

## Framework-Neutral Proof Acquisition

“Client obtains a proof” is a maintained protocol boundary, not an assumption
that the client runs in a browser or uses a wallet UI.

- proof preparation, retrieval and establishment use ordinary authenticated IC
  ingress and are callable by any conforming agent implementation;
- the principal authenticated on the preparation call becomes the signed
  presenter and the same principal must retrieve the proof, establish each
  session and make later guarded calls;
- a desktop tool may use a PEM-backed or other agent-supported identity, but
  Canic never reads, receives, copies or persists the private key;
- no browser wallet callback, browser storage, framework relay or anonymous
  bearer download is part of the authority contract;
- one eligible Fleet/role proof may establish one local session on each
  compatible target Canister as the same presenter; replay and active-session
  state remain independent on every target Canister; and
- clients may perform those target-local establishment updates concurrently,
  but one target's success is never evidence that another target committed.

B1 must freeze the exact current preparation/retrieval command variants, caller binding,
response-loss retry behavior and client inputs, then prove proof acquisition
through the current verifier boundary with a non-browser fixture using a native
agent identity. It freezes the intended target-local establishment inputs but
does not claim an unimplemented 0.109 session command variant. B7 proves the
complete multi-target establishment journey after that variant exists. If the
maintained issuer path cannot serve the B1 fixture without browser-specific
authority, B2 is blocked. Canic may document or provide a client helper for the
maintained protocol; it may not make a framework or wallet library part of
runtime authorization.

## Framework-Neutral Adapter Contract

A consuming application may adapt Canic's decision to any synchronous two-way guard:

```rust
fn may_use_surface(context: ApplicationGuardContext) -> ApplicationGuardDecision {
    match canic::access::application::authorize(
        LocalApplicationAuthorizationRequest {
            observed_transport_caller: context.caller,
            required_scope: MY_APPLICATION_SCOPE,
        },
    ) {
        LocalApplicationAuthorizationDecision::Allow(_) => {
            ApplicationGuardDecision::Allow
        }
        LocalApplicationAuthorizationDecision::Deny(_) => {
            ApplicationGuardDecision::Deny
        }
    }
}
```

The names outside canic::access::application are placeholders owned by the consuming application. Canic production code, configuration, state, Candid, metrics and diagnostics contain no foreign-framework identity.

The adapter must be synchronous, bounded and fail closed. It must not convert a denial into controller fallback, perform a remote lookup or expose Canic's internal denial detail through the guarded surface. The consuming application owns any later subject-to-resource decision.

## Non-Normative Motivating Integration

An independently developed framework may choose to expose an application-supplied guard for unchanged application endpoints. An application that independently uses that framework and Canic could:

1. obtain a Canic delegated proof;
2. establish a bounded session on the target Canister with explicit application endpoint scope subsets;
3. call the framework's unchanged endpoint as the same transport principal; and
4. map Canic Allow/Deny to the framework's own guard decision.

This example is explanatory only:

- Canic does not import, name or release-gate on that framework;
- that framework does not need Canic to implement or test an application guard;
- Canic qualification uses a generic local consumer fixture, not the framework repository;
- the framework can qualify its guard with a trivial application predicate;
- combined end-to-end evidence belongs to the consuming application; and
- neither framework's release is a prerequisite for the other's promotion.

## Non-Normative Downstream Allowlist Baseline

The generic Canic adapter is not the only valid implementation of an
application framework's synchronous guard. A framework-neutral database guard
also needs a framework-neutral simple deployment answer. For IcyDB, the
recommended downstream contract is its maintained bounded static-principal
guard, called by an application-owned one-line function-pointer adapter:

```rust
fn authorize(context: icydb::ReadAuthorizationContext) -> icydb::ReadAuthorizationDecision {
    icydb::guards::allowlist(context, READERS)
}
```

`READERS` is the application-owned bounded principal slice. This example does
not imply separate Canic scope meaning for statements that share one downstream
endpoint; the consuming application maps its own endpoint scopes.

That downstream allowlist:

- lets a plain IcyDB Canister authorize an Explorer or other client without
  adopting Canic;
- admits only explicitly configured principals, denies anonymous callers and
  does not add controllers implicitly;
- remains application/framework authority and creates no Canic principal
  whitelist, grant store or controller bypass;
- can coexist with an application-owned Canic adapter because the framework
  consumes a generic synchronous allow/deny decision; and
- is qualified and released by IcyDB, not by Canic.

The immediate Explorer unblock is therefore the independently planned IcyDB
guard work, not Canic 0.109. Canic 0.109 supplies the stronger Fleet/role/scope
option for applications that choose it. This coordination note does not add an
IcyDB dependency, authorize mutation of the IcyDB repository or make an IcyDB
artifact a Canic promotion gate.

## Security Invariants

- Application authorization never implies controller, install, stop, delete, upgrade, topology or infrastructure authority.
- Controllers and infrastructure callers receive no implicit application-access bypass.
- Omitted, disabled, missing, expired, stale, corrupt or unavailable authority fails closed.
- Session establishment uses the one current delegated-token verifier.
- The signed token presenter equals the actual transport caller and the signed token subject is the authenticated application subject; the two principals need not be equal.
- Requested scopes may only narrow verified delegated scope authority.
- Requested TTL may only narrow the protected configured local-session maximum.
- An empty requested scope set never means all scopes.
- The actual IC caller must equal the adapter-observed caller and the session's exact bound caller.
- An establishment proof has a maximum complete lifetime of 60 seconds and must be valid at first commit.
- A committed local session has an independent maximum lifetime of 1,800 seconds and never outlives its protected configured/requested session bound; later proof expiry neither invalidates nor extends it.
- Exact replay never extends expiry, changes scopes or recreates a cleared session.
- Replacement is atomic and replaces scopes; it never unions them.
- Access reads caller, time and bounded Canic state once; pure policy performs no IC API read. Neither performs an inter-Canister call, await, mutation, prune, log, timer, payload parse or application-state read.
- Fleet, role or authority-generation mismatch invalidates the session.
- Topology and infrastructure policy always consumes raw transport identity, never the returned application subject.
- Authentication and scope authorization do not imply application resource ownership.
- Proof/signature bytes, arbitrary extensions and application entitlement data are not persisted.
- Every record, index, scope collection, page and cleanup operation is bounded.
- Derived indexes cannot become independent authority.
- No public or operator surface exposes proof fingerprints.
- A token without the signed presenter field is unsupported and no legacy decoder or fallback binding exists.
- Proof acquisition is available through browser-neutral authenticated IC ingress; browser-wallet-only authority blocks promotion.
- No controller fallback, principal whitelist, compatibility decoder, legacy alias, shim or dual session format exists.
- Canic production owners contain no foreign-framework-specific contract.

## Alternatives Rejected

### Add A Canic Token To Every Application Endpoint

Rejected. It changes the endpoint ABI, couples its owner and clients to Canic and repeats proof transfer and verification on every request.

### Keep Controller Authorization

Rejected. Controller authority is excessive for a reader and may be held only by Fleet infrastructure.

### Add A Principal Reader Set

Rejected. It becomes a second grant lifecycle, loses authenticated-subject semantics and duplicates expiry, revocation and audit policy.

### Let Another Framework Store Canic Grants

Rejected. It makes that framework interpret Canic tokens and creates competing authority.

### Call A Parent Or Issuer During Every Decision

Rejected. It adds latency, availability coupling and cache/revocation ambiguity to the endpoint hot path.

### Store Every Verified Token Scope Automatically

Rejected. A valid broad token must not silently become a broad tokenless session. Establishment requires an explicit non-empty requested subset.

### Renew With The Same Proof

Rejected. Reusing a proof to move session expiry would defeat the configured maximum staleness bound. Renewal requires a fresh proof. Byte-exact retry of an already-committed active session remains idempotent but returns the original expiry and is not renewal.

### Retain Subject-Only And Scoped Sessions

Rejected. Two current session meanings duplicate identity resolution and permit accidental authorization through the weaker record.

### Add Resource-Level Policy To Canic

Rejected. Canic owns identity and coarse application scopes; the application owns its resources and entitlements.

### Make A Particular Framework A Qualification Dependency

Rejected. A generic consumer fixture proves the Canic contract. Cross-framework evidence is useful integration evidence but cannot authorize or block a Canic release.

## Complexity Gate

The justified state-space delta is:

- one current bounded session meaning replacing the weaker subject-only meaning;
- one bounded replay/tombstone owner preserving existing proof-consumption guarantees;
- one exact-caller derived lookup;
- one synchronous closed decision; and
- one protected bounded audit view.

Promotion fails if implementation adds a second verifier, token format, grant store, session representation, authority generation, framework adapter, policy language, dynamic registry, application entitlement table, remote cache, unbounded state or compatibility path.

Every batch reports files/line delta, semantic owners, states added and removed, duplicate paths removed, stable bytes, instructions, restore cost and raw Wasm, plus whether the maintained structure became simpler, stayed neutral or became more complex.

## Acceptance Criteria

0.109 is complete when:

1. the subject-only delegated session record and its APIs are removed without aliases or fallback;
2. each role must explicitly enable local application authorization in addition to delegated-token verification;
3. enabled managed roles add exactly establish/clear command variants and one
   application-session status variant, disabled roles add none, infrastructure
   roles cannot enable them and no session-specific method exists;
4. establishment stores only a non-empty explicit subset of fully verified local scopes;
5. token preparation derives a required signed presenter from its authenticated ingress caller, verification requires that presenter to equal the current transport caller, and the separately signed subject becomes the authenticated application subject;
6. the active session is bound to exact caller, subject, issuer, Fleet, role, authority generation and strict expiry;
7. proofs accepted for session establishment have a complete verified lifetime no greater than 60 seconds;
8. protected role configuration freezes positive default and maximum session TTLs, accepts a configured maximum of exactly 1,800 seconds, rejects larger values, and permits an already-committed session to outlive its establishment proof without outliving that local bound;
9. exact replay of an active byte-exact receipt remains available after proof expiry but cannot extend expiry, alter scope or resurrect a cleared session;
10. replacement is atomic and never unions authority;
11. clear rejects anonymous, removes the caller's retained active, expired or stale session record, remains idempotent when no record exists and never removes a live replay tombstone;
12. one synchronous facade authorizes an unchanged-ABI generic consumer endpoint;
