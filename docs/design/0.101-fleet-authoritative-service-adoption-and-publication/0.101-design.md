# Canic 0.101 Design: Fleet-Authoritative Service Adoption and Publication

Date: 2026-07-25

## Status

- Status: proposed.
- Scope: adoption or provisioning of singleton Fleet-authoritative services
  inside ordinary Canister Trees, followed by canonical Fleet publication.
- Design amendment accepted 2026-07-25: the Fleet Coordinator is not part of
  a Canister Tree and never becomes the local owner, parent or controller of a
  service Canister.
- Dependency: the
  [0.100 multi-Subnet Fleet design](../0.100-multi-subnet-fleet-coordinator-and-registry-synchronization/0.100-design.md)
  must be implemented and qualified first.
- Compatibility posture: pre-1.0 current schema only. The superseded
  Coordinator-owned service-lifecycle protocol and its transfer records are
  not compatibility surfaces.

## Thesis

0.100 answers which Tree Groups and Canister Trees exist. 0.101 makes a
bounded set of Tree-owned services discoverable as the canonical
Fleet-authoritative service set.

For each role selected by `[services.fleet.targets]`, 0.101:

1. resolves the configured singleton Tree Group to one exact active
   Canister Tree;
2. proves that the role is declared by that Tree's exact Tree Spec;
3. adopts one existing matching service in that Tree or asks its Tree Root to
   provision the missing service;
4. leaves local Registry, lifecycle, management and controller authority with
   that Tree Root; and
5. publishes the complete `(role, TreeId, canister_id)` set atomically through
   the Fleet Coordinator's Registry and the derived Fleet Directory.

The Coordinator owns Fleet-wide publication. A Tree Root owns its Tree-local
lifecycle. The service Canister owns its application data. These are distinct
authorities and none is a “super root”.

## Release Boundary

| Release | Responsibility |
| --- | --- |
| 0.99 | One-Tree App/Fleet identity and the existing service candidates |
| 0.100 | Coordinator Subnet, Fleet Coordinator, Tree Specs, Tree Groups, Canister Trees, Tree lifecycle, Registry synchronization and an empty `authority_services` field |
| 0.101 | Service-target activation inside selected Trees and complete Fleet publication |
| Later | Relocation, replacement, writable-primary replication, promotion, failover and application-data synchronization |

0.101 does not reopen Tree placement, Tree scaling or Coordinator placement.
It consumes the exact committed 0.100 Registry and App declaration.

## Terminology

### Fleet-authoritative service

One singleton service role that the Fleet publishes as its canonical writable
or otherwise unique service endpoint. “Authoritative” describes the
Fleet-wide binding, not ownership by the Fleet Coordinator.

### Service target

The `[services.fleet.targets]` mapping from a service role to one
`TreeGroupId`. The target group must be singleton and resolve to exactly one
active Tree.

### Service Tree

The ordinary Canister Tree selected by a service target. It has a normal
`TreeId`, Tree Root, Tree Spec, local Registry and physical `SubnetId`. A
Primary Data Tree is a common service Tree, not a special topology class.

### Adoption

Publishing an already installed matching service from its existing target
Tree. Adoption preserves the Canister principal, application data, local
Registry row and Tree Root authority. It performs no relocation or controller
transfer.

### Provisioning

Asking the selected Tree Root to create and install a missing service through
the existing Tree-local lifecycle on that Tree's recorded physical Subnet.

### Publication

One atomic Fleet Registry revision containing the complete declared service
set. Publication makes a binding canonical for Fleet discovery; it does not
make the Coordinator a Canister controller or local Registry owner.

## Goals

0.101 must:

1. activate only explicitly declared Fleet service targets;
2. resolve the complete target set before any mutation;
3. preserve every selected Tree's identity, placement and Tree Root;
4. adopt an existing eligible service without moving it or changing its data;
5. provision a missing service only through its exact Tree Root;
6. prevent duplicate service roles or principals across live and removed Tree
   evidence;
7. publish no partial service set;
8. retain `TreeId` in both Registry and Directory service bindings;
9. make every operation restart-safe and exactly replayable; and
10. keep ordinary Canisters free of Coordinator and deployment workflows.

## Non-Goals

0.101 does not implement:

- service relocation between Trees or Subnets;
- service replacement or principal rotation;
- writable-primary replication, replica promotion or failover;
- IcyDB snapshots, change streams or application-data synchronization;
- application user/project/shard routing;
- automatic Tree scaling or placement;
- Coordinator election, replacement or relocation;
- a Coordinator-owned local service registry;
- controller transfer from a Tree Root to the Coordinator;
- root-to-root consensus or distributed transactions;
- health-, latency- or freshness-based service routing; or
- direct Coordinator calls from ordinary managed Canisters.

## Configuration Contract

The 0.100 App configuration is the sole declaration:

~~~toml
[tree_specs.primary_data]

[tree_specs.primary_data.canisters.root]
kind = "root"

[tree_specs.primary_data.canisters.users_db]
kind = "service"

[tree_specs.primary_data.canisters.projects_db]
kind = "service"

[tree_specs.primary_data.canisters.billing_db]
kind = "service"

[tree_specs.primary_data.canisters.identity_db]
kind = "service"

[tree_groups.primary_data]
tree_spec = "primary_data"
initial_trees = 1
maximum_trees = 1

[services.fleet.targets]
users_db = "primary_data"
projects_db = "primary_data"
billing_db = "primary_data"
identity_db = "primary_data"
~~~

Each mapping value is a `TreeGroupId`, not a Subnet, Tree Spec or Tree
principal. The committed Fleet Registry resolves it through:

~~~text
CanisterRole
  -> TreeGroupId
  -> one Active TreeId
  -> one Tree Root and physical SubnetId
~~~

0.101 reuses the exact 0.100 declaration stored in protected Coordinator
state:

~~~rust
pub struct FleetServiceTargetDeclaration {
    pub fleet: FleetBinding,
    pub targets: Vec<FleetServiceTargetBinding>,
}

pub struct FleetServiceTargetBinding {
    pub role: CanisterRole,
    pub group: TreeGroupId,
}
~~~

The exact stored bytes and hash are the runtime declaration authority. App
configuration may be recompiled for diagnostics, but 0.101 rejects any
difference and never activates from a later file reread.

Configuration validation requires:

- at most `MAX_FLEET_AUTHORITY_SERVICES` selected roles;
- every selected role is package-declared and eligible as a singleton Fleet
  service;
- every selected role occurs exactly once in the Tree Spec referenced by its
  target group;
- the selected role occurs in no other Tree Spec;
- the target group has `initial_trees = maximum_trees = 1`;
- the target group has exactly one `Active` Tree when activation starts;
- no selected role is a scaling or multi-instance role; and
- canonical role and group identities are unique and bounded.

An empty target map is valid. It commits no activation work and leaves the
already empty `authority_services` vector current.

For an existing 0.99 Fleet, 0.100 compiles selected roles and their preserved
candidates into the singleton `default` Tree Group. 0.101 does not silently
retarget those services to a newly declared Primary Data Tree.

## Authority and Ownership

The steady-state authority split is:

| Scope | Authority |
| --- | --- |
| Fleet binding and publication | Fleet Coordinator |
| Tree Group and Tree lifecycle | Fleet Coordinator |
| Tree-local service row and lifecycle | Selected Tree Root |
| Canister management and controller policy | Selected Tree Root under the Tree Spec |
| Service application data | Service Canister and application protocol |
| Read-only consumer discovery | Fleet Directory derived by each Tree Root |

The Coordinator:

- has no `TreeId`, `TreeGroupId`, `TreeSpecId` or `tree_root_pid`;
- is never inserted into `FleetRegistry.trees`;
- never creates a service Canister directly;
- never receives service-parent or Tree-Root authority;
- never becomes a controller merely because it publishes a binding; and
- cannot mutate a Tree-local Registry.

The selected Tree Root:

- owns the exact local Registry row;
- performs adoption preparation or provisioning;
- verifies the installed module, protected binding and controller policy;
- fences duplicate creation for the selected role while activation is
  pending; and
- retains the same authority after Fleet publication.

Controller policy is compiled into the target Tree Spec. The exact expected
controller set is verified before publication. 0.101 does not inject the
Coordinator into that set and does not use controller status as an
alternative authorization channel.

## Coordinator and Service-Tree Placement

The Coordinator Subnet identifies only where the Fleet Coordinator runs. It
does not select the service Tree.

A singleton Primary Data Tree may be explicitly placed on the same Fiduciary
Subnet as the Coordinator when a unique writable source of truth benefits
from the larger committee. This is an operator-visible resilience trade-off,
not a topology merge:

- the Coordinator and Tree keep independent identities and authorities;
- the Tree follows ordinary join, drain and removal lifecycle;
- both share Subnet capacity, cost and outage domain; and
- deleting or draining the Tree does not move the Coordinator.

A data-heavy Primary Data Tree may instead be placed on another explicitly
selected application Subnet. Its publication contract is identical. 0.101
never infers service placement from Coordinator placement.

Read-only replicas belong to separate Tree Specs and Tree Groups on other
Subnets. They are not selected by `[services.fleet.targets]` as equivalent
writable authorities. Their data feed, lag, promotion and application routing
remain later work.

## Current Data Model

0.101 populates the exact 0.100 Registry schema:

~~~rust
pub struct FleetRegistry {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub tree_groups: Vec<FleetTreeGroup>,
    pub trees: Vec<FleetTreeEntry>,
    pub authority_services: Vec<FleetAuthorityServiceBinding>,
}

pub struct FleetAuthorityServiceBinding {
    pub role: CanisterRole,
    pub tree: TreeId,
    pub canister_id: Principal,
}
~~~

`tree_groups` and `trees` are copied unchanged from the exact base Registry.
`authority_services` contains committed public bindings only. It never
contains plans, candidates, preparation state or provisioning receipts.

Bindings are canonically ordered by raw role bytes. Duplicate roles and
duplicate Canister principals are rejected. Each referenced Tree must be
`Active`, belong to the declared singleton target group and carry the exact
compiled Tree Spec hash.

The enclosing `FleetRegistryAuthority` remains the sole Fleet, Coordinator,
Coordinator Subnet and authority-epoch binding. Per-service records do not
duplicate those fields.

## Resolved Target and Activation Plan

The host resolves the protected declaration against the exact 0.100 Registry
into:

~~~rust
pub struct FleetServiceTarget {
    pub role: CanisterRole,
    pub group: TreeGroupId,
    pub tree: TreeId,
    pub tree_root: Principal,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub subnet: SubnetId,
    pub package_identity: PackageIdentity,
    pub module_hash: [u8; 32],
    pub install_arguments_hash: [u8; 32],
    pub controller_policy_hash: [u8; 32],
}

pub struct FleetServiceActivationPlan {
    pub activation_id: [u8; 32],
    pub base_registry: FleetRegistryVersion,
    pub declaration_hash: [u8; 32],
    pub targets: Vec<FleetServicePlanEntry>,
}

pub struct FleetServicePlanEntry {
    pub target: FleetServiceTarget,
    pub kind: FleetServicePlanKind,
}

pub enum FleetServicePlanKind {
    Adopt {
        canister_id: Principal,
        local_registry_row_hash: [u8; 32],
    },
    Provision,
}
~~~

Planning is complete and read-only. Before persisting the plan, the
host/Coordinator:

1. verifies the protected declaration bytes/hash, exact Fleet binding and
   current Registry version;
2. resolves every target group to one active Tree;
3. obtains authenticated complete local inventories from every `Joining`,
   `Active` and `Draining` Tree Root;
4. includes every 0.100 qualified removed-Tree final inventory;
5. fails on any unqualified removed Tree because absence cannot be proved;
6. finds every live or possibly live occurrence of each selected role;
7. chooses `Adopt` only for exactly one matching candidate in the selected
   Tree;
8. chooses `Provision` only when no candidate exists anywhere; and
9. verifies package, module, protected binding, controller and placement
   evidence as far as the platform exposes it.

A candidate in another Tree is a typed target conflict, even if that Tree is
on the same physical Subnet. 0.101 does not relocate it. More than one
candidate is ambiguous. A non-decommissioned selected role in removed-Tree
evidence blocks both adoption and provisioning.

The plan is sorted by role, bounded and hashed from exact canonical bytes. The
same protected declaration and base Registry produce one exact plan.
Declaration or Registry drift before execution invalidates it.

## Tree-Local Publication State

The Tree Root adds publication state to the existing local managed-service
row; it does not replace local ownership:

~~~rust
pub enum TreeServicePublicationState {
    Local,
    Preparing {
        activation_id: [u8; 32],
        target_hash: [u8; 32],
    },
    FleetPublished {
        activation_id: [u8; 32],
        registry_version: FleetRegistryVersion,
        binding_hash: [u8; 32],
    },
}
~~~

`Preparing` fences Canic-managed duplicate creation, removal, role
reassignment and controller-policy changes for that local role. It does not
release the row, stop application traffic or make the Coordinator its owner.

The service Canister stores or verifies its existing protected:

~~~rust
pub struct FleetServiceRuntimeBinding {
    pub fleet: FleetBinding,
    pub tree: TreeId,
    pub tree_root: Principal,
    pub role: CanisterRole,
    pub canister_id: Principal,
}
~~~

The binding deliberately contains no “Coordinator as parent” field.
Coordinator identity and Registry revision belong to publication evidence,
not the service's local hierarchy.

## Activation Protocol

The durable activation journal is:

~~~text
Planned
  -> RootsPrepared
  -> ServicesReady
  -> RegistryPublished
  -> DirectoryConverging
  -> Complete
~~~

Only one activation may execute for a Fleet authority epoch. Tree lifecycle
mutation that could change target resolution is fenced from `Planned` through
`RegistryPublished`; Registry synchronization remains available.

### 1. Persist `Planned`

The Coordinator verifies the exact canonical plan, base Registry, authority
epoch and declaration hash before it stores the plan. No Tree or service
mutation occurs before this point.

### 2. Prepare each target Tree Root

For each target, the Coordinator calls the exact recorded Tree Root with the
same activation ID and target bytes. The root verifies:

- authenticated caller is the Fleet Coordinator;
- its protected Fleet, Tree, group, Tree Spec hash and placement agree;
- the role belongs to its installed Tree Spec;
- the expected base Registry is its current verified mirror;
- no different activation or publication already claims the role; and
- the requested `Adopt` or `Provision` kind matches its local inventory.

The root persists `Preparing` before acknowledging. Exact retries return the
same receipt. A conflicting request fails without mutation.

### 3. Adopt or provision inside the Tree

For `Adopt`, the root:

1. loads the exact existing local Registry row;
2. verifies principal, role, package/module, protected runtime binding,
   controller policy and local row hash;
3. preserves the principal, data and local ownership; and
4. returns a canonical ready receipt.

For `Provision`, the root:

1. journals one exact create request bound to the activation, Tree and role;
2. creates the Canister through its existing Tree-local allocation path on
   the Tree's recorded physical Subnet;
3. records the returned principal before any further management call;
4. installs the exact qualified Wasm and protected runtime binding;
5. commits one normal local Registry row;
6. verifies module and controller evidence; and
7. returns a canonical ready receipt.

An unknown create outcome is never repeated without recovering the exact
principal from durable Tree-local evidence. Install and controller
reconciliation use the existing idempotent or observation-backed paths.

### 4. Verify the complete ready set

The Coordinator accepts a ready receipt only from the target's exact Tree Root
and only when all authority, plan, Tree, role, principal, module, local-row and
controller hashes agree. It retains one bounded receipt per role.

`ServicesReady` is committed only when:

- every declared role has exactly one ready binding;
- the bindings exactly equal the target plan;
- every referenced Tree remains the same active Tree;
- no two roles use the same principal; and
- the base Registry is still current.

### 5. Publish once

The Coordinator creates one new Fleet Registry snapshot:

- `tree_groups` unchanged;
- `trees` unchanged; and
- `authority_services` equal to the complete sorted ready set.

It advances the revision with checked arithmetic, publishes the canonical
snapshot atomically and records `RegistryPublished`. There is no intermediate
Registry containing a partial service set.

An empty declaration is already complete when the base Registry has an empty
`authority_services` vector. A non-empty published set is immutable in 0.101;
replacement or removal requires a later design.

### 6. Confirm Tree-local publication

Each target Tree Root eventually observes the exact Registry through the
normal 0.100 synchronization path, verifies its binding, and advances
`Preparing -> FleetPublished`. Losing this acknowledgement does not undo the
canonical Registry. Exact retry or mirror observation converges.

The Coordinator does not wait for every ordinary Canister to receive the
Directory before the Registry becomes canonical. `DirectoryConverging`
tracks normal root mirror and local-cascade progress. `Complete` means every
eligible Tree Root has activated the exact Registry revision and initiated or
finished its recoverable local cascade according to the 0.100 contract.

## Fleet Directory Projection

0.101 uses the exact 0.100 Directory shape:

~~~rust
pub struct FleetDirectory {
    pub provenance: DirectoryProvenance,
    pub groups: Vec<FleetDirectoryGroup>,
    pub entries: Vec<FleetDirectoryService>,
    pub trees: Vec<FleetDirectoryTree>,
}

pub struct FleetDirectoryService {
    pub role: CanisterRole,
    pub tree: TreeId,
    pub canister_id: Principal,
}
~~~

For one verified Registry snapshot:

~~~text
authority_services -> entries
tree_groups         -> groups
trees               -> trees
~~~

The projection preserves every service's owning `TreeId`. It does not imply
that the service belongs to the Coordinator or Coordinator Subnet. Ordinary
Canisters learn the complete projection only through their own Tree Root's
existing local cascade and never call the Coordinator directly.

`entries`, `groups`, `trees`, Registry revision and Registry content hash are
identical across roots for the same revision. `source_root` and
`synchronized_at` remain truthful root-local provenance as defined by 0.100.

## Recovery and Idempotency

0.101 performs no ownership transfer. Recovery is therefore monotonic but
simpler:

- before `Planned`, no state exists;
- after `Planned`, restart loads the exact plan or fails on drift;
- after a root prepares, it returns the same preparation state for the same
  activation;
- after provisioning records a principal, recovery observes and resumes that
  principal rather than creating another;
- after `ServicesReady`, publication recomputes and verifies the exact
  complete binding set;
- after an unknown publication result, the Coordinator reads its current
  manifest and reconciles by revision, hash and activation ID;
- after `RegistryPublished`, the Registry remains canonical even if a target
  root has not yet marked `FleetPublished`; and
- Directory convergence resumes through the existing 0.100 mirror/cascade
  journal.

Before Registry publication, an authorized abort may clear only preparations
that provably created no new local service. A provisioned service with a known
principal is retained and the same activation resumes; it is not deleted or
silently orphaned. After publication, rollback is forbidden.

Missing evidence never permits blind repetition of create, install,
controller or publication operations. Every retry uses the exact persisted
request and validates the observed result.

## Bounds and Canonical Encoding

0.101 retains all 0.100 Tree, Registry and target-declaration bounds and adds
activation-evidence bounds:

~~~rust
const MAX_FLEET_AUTHORITY_SERVICES: usize = 32;
const MAX_FLEET_SERVICE_TARGET_DECLARATION_BYTES: usize = 8_192;
const MAX_FLEET_SERVICE_ACTIVATION_PLAN_BYTES: usize = 16_384;
const MAX_RETAINED_SERVICE_EVIDENCE_BYTES_PER_ROLE: usize = 65_536;
const MAX_RETAINED_SERVICE_RECEIPT_BYTES_PER_ROLE: usize = 32_768;
const MAX_SINGLE_SERVICE_RECEIPT_BYTES: usize = 4_096;
~~~

Targets, plan entries, ready receipts and public bindings are ordered by raw
`CanisterRole` bytes. Controller principals are ordered by raw principal
bytes. Duplicate logical keys reject before hashing.

The protected target declaration bytes are a fixed array containing:

~~~text
FleetBinding
[
  role,
  target_group
]
~~~

The activation plan adds the activation ID, exact base Registry version and
each target's resolved Tree, Tree Root, Tree Spec, spec hash, Subnet, package,
module, install-argument and controller-policy hashes. Each sorted target then
uses `0 = Adopt` with principal/local-row hash or `1 = Provision`.

Every hash covers the exact canonical bytes transferred or persisted:

~~~text
SHA-256(
  domain_separator
  || u64_be(canonical_byte_length)
  || exact_canonical_bytes
)
~~~

The domain separators are:

~~~text
canic:fleet-service-target-declaration\0
canic:fleet-service-activation-plan\0
canic:fleet-service-root-preparation\0
canic:fleet-service-ready\0
canic:fleet-service-publication-binding\0
~~~

Registry revision arithmetic is checked. Overflow returns
`RevisionExhausted` without mutation. 0.101 never changes the authority epoch.

## Authorization

- The host may compile plans but cannot substitute display text or local files
  for committed Registry and root evidence.
- Only the Fleet Coordinator may persist the activation plan and publish the
  Fleet Registry.
- Only the exact recorded target Tree Root may return preparation and ready
  receipts for its Tree.
- A Tree Root accepts activation work only from the protected Fleet
  Coordinator at the current authority epoch.
- Only the Tree Root's existing local lifecycle authority may create, install
  or register the service.
- Controllers do not gain Registry mutation authority.
- Ordinary Canisters consume Directory state and have no 0.101 control-plane
  endpoint.

Every call and receipt binds the exact Fleet, authority epoch, activation ID,
Tree, Tree Root, role, expected module and base Registry version. Caller,
subject and audience checks remain explicit.

## Stable State, Upgrade and Backup

The upgrade order is:

1. upgrade all Tree Roots and selected service candidates to understand the
   current target-preparation contract;
2. verify their exact 0.100 Registry mirrors and local inventories;
3. upgrade the Coordinator to accept the 0.101 plan and publish non-empty
   `authority_services`; and
4. start activation only after every target reports readiness for the same
   current schema.

An older root seeing a Registry with non-empty `authority_services` would be
unsafe because it cannot derive the current Directory service shape. The
Coordinator therefore cannot publish until all eligible roots required for
Fleet Directory convergence attest the 0.101 schema.

Coordinator backup includes:

- the exact declaration and activation plan;
- every target and ready receipt;
- current Registry manifest and canonical snapshot;
- activation journal and Directory convergence progress; and
- the inherited 0.100 removed-Tree evidence.

Tree Root backup includes:

- local Registry and service publication state;
- create/install/controller receipts for provisioned services;
- protected Tree and service runtime bindings; and
- current Registry mirror and cascade progress.

A restored Coordinator cannot lower the current authority epoch or Registry
revision. A restored Tree Root cannot clear `Preparing` or `FleetPublished`
without matching canonical evidence. Backup possession grants no new
authority.

## Wasm Role Boundary

The host/CLI owns:

- App configuration compilation;
- complete inventory collection and plan construction;
- release artifact and module-hash selection;
- deployment journalling and operator recovery; and
- placement and Wasm-size reporting.

The Fleet Coordinator Wasm owns:

- canonical plan admission;
- authenticated preparation/ready receipt collection;
- complete-set validation;
- atomic Fleet Registry publication; and
- activation recovery state.

The Tree Root Wasm owns:

- target verification;
- local publication fences;
- existing-service qualification;
- same-Tree provisioning and controller reconciliation; and
- Registry mirror and Directory cascade.

An ordinary service Wasm owns only its protected Fleet/Tree/role binding and
application behavior. It does not retain plan compilation, Tree lifecycle,
Coordinator Registry mutation or deployment-journal workflows.

Closeout records raw and compressed release-Wasm size for ordinary,
Tree-Root, Coordinator and service archetypes. Size changes must be attributed
to the owning role rather than explained only by aggregate workspace growth.

## Invariants

1. The Fleet Coordinator is not a member of any Canister Tree.
2. Every published service is owned locally by exactly one active Tree.
3. Every service target resolves through one singleton Tree Group to one
   active `TreeId`.
4. Coordinator Subnet placement never substitutes for service Tree
   placement.
5. The Coordinator owns publication, not the service's local Registry,
   hierarchy, controllers or application data.
6. Adoption preserves principal, data, local Registry row and Tree Root
   authority.
7. Provisioning runs only through the target Tree Root on its recorded Subnet.
8. A selected role has at most one live or possibly live candidate across all
   active and removed Tree evidence.
9. A non-decommissioned candidate in the wrong Tree blocks activation.
10. `tree_groups` and `trees` do not change during service publication.
11. No partial service set is canonical or cascaded.
12. The published role set equals `[services.fleet.targets]` exactly.
13. Every public binding carries role, owning Tree and Canister principal.
14. Every Directory entry is derived from the same Registry binding without
    dropping `TreeId`.
15. A service Tree co-located with the Coordinator remains an ordinary,
    independently removable Tree.
16. Writable primaries and read replicas are different roles/specs/groups.
17. Unknown management outcomes never justify creating another Canister.
18. A published binding is immutable in 0.101.
19. Old backup state cannot lower Registry revision or resurrect a competing
    activation.
20. Ordinary Canisters never call the Fleet Coordinator.

## Typed Failures

At minimum, preserve distinct failures for:

- invalid, duplicate or ineligible service target;
- missing target Tree Spec role;
- non-singleton target group;
- missing, multiple or non-active target Trees;
- base Registry or authority-epoch mismatch;
- Tree, group, Tree Spec hash, root or placement mismatch;
- unqualified removed Tree;
- candidate absent where adoption was required;
- candidate in the wrong Tree;
- ambiguous or duplicate candidate;
- package, module, install-argument or controller-policy mismatch;
- protected Fleet/Tree/service binding mismatch;
- activation conflict or declaration drift;
- preparation or ready-receipt mismatch;
- unknown creation outcome without a recoverable principal;
- duplicate public role or Canister principal;
- partial publication attempt;
- Registry revision exhaustion;
- snapshot/hash/canonical-order mismatch; and
- backup or restore monotonicity violation.

Failures are typed state and evidence errors. Tests assert the typed result or
observable state, not rendered error strings.

## Observability

Bounded controller/operator status reports:

- activation ID and phase;
- exact base/current Registry version;
- declaration and plan hashes;
- one row per target with group, Tree, root, Subnet and Adopt/Provision kind;
- prepared/ready/published state per role;
- retained principal for every provision attempt;
- current mirror and Directory convergence counts;
- last typed failure and retry time; and
- raw/compressed Wasm size by role archetype.

Reports distinguish `Coordinator Subnet` from each service Tree's `SubnetId`.
Co-location is shown explicitly and never summarized as ownership.

## Implementation Slices

### Slice 1 - Contracts and target compilation

- Hard-cut configuration to `[services.fleet.targets]`.
- Load only the protected 0.100 declaration bytes/hash and reject config drift.
- Add `TreeId` to Registry and Directory service bindings.
- Compile and validate singleton group targets.
- Freeze canonical encodings, hashes and bounds.

### Slice 2 - Tree Root preparation

- Add Tree-local `Preparing` and `FleetPublished` state.
- Add authenticated idempotent prepare/status endpoints.
- Qualify existing candidates without moving or releasing them.
- Fence duplicate Tree-local role creation during activation.

### Slice 3 - Complete planning

- Collect current live and removed Tree inventories.
- Resolve every target to exact Adopt or Provision work.
- Persist one complete bounded plan and Fleet lifecycle fence.
- Reject ambiguity, wrong-Tree candidates and unqualified removal.

### Slice 4 - Tree-local provisioning

- Reuse the existing Tree Root allocation/install path.
- Journal principal-returning create operations before continuation.
- Verify runtime binding, module and controller policy.
- Commit a normal local Registry row and ready receipt.

### Slice 5 - Atomic publication

- Verify the complete ready set.
- Publish one checked Registry revision.
- Derive Tree-bearing Directory entries.
- Confirm target-root `FleetPublished` state.

### Slice 6 - Recovery and qualification

- Resume every durable boundary.
- Prove exact idempotency for unknown responses.
- Qualify current-schema upgrade and restore monotonicity.
- Record per-role Wasm-size and focused PocketIC evidence.

## Required Validation

### Configuration and planning

- accept the Primary Data Tree example with four target roles;
- reject a target role absent from the target Tree Spec;
- reject the same target role in another Tree Spec;
- reject a target group whose maximum exceeds one;
- reject zero or two active Trees in the target group;
- accept several target roles in one singleton service Tree;
- compile an existing 0.99 candidate to the extracted `default` Tree; and
- reject a source-config target map that differs from the protected 0.100
  declaration;
- prove default workload placement does not choose the Coordinator Subnet.

### Placement and ownership

- place a Primary Data Tree on the Coordinator Subnet and prove it keeps a
  distinct Tree ID, root, Registry and lifecycle;
- place the same Tree Spec on another Subnet with identical publication
  semantics;
- prove the Coordinator has no Tree identity or local service row;
- prove adoption leaves controllers, local Registry and principal unchanged;
- prove provisioning is initiated by the target Tree Root; and
- prove draining a co-located service Tree does not alter the Coordinator.

### Candidate qualification

- adopt exactly one matching candidate in the selected Tree;
- provision only when complete inventory proves no candidate exists;
- reject a candidate in another active or draining Tree;
- reject multiple candidates, including co-located Trees;
- reject a possibly live candidate from qualified removed-Tree evidence; and
- reject unqualified removed-Tree evidence without treating it as empty.

### Publication and Directory

- publish all four example bindings in one Registry revision;
- retain `(role, TreeId, canister_id)` exactly in Registry and Directory;
- reject partial, duplicate-role and duplicate-principal publication;
- prove `tree_groups` and `trees` bytes remain unchanged;
- prove every Tree Root derives the same entries from the same revision;
- prove ordinary Canisters learn entries only through their Tree Root; and
- prove no Coordinator parent/controller relationship is created.

### Recovery

- restart after every activation-journal transition;
- reconcile a lost root preparation or ready response;
- reconcile a create response lost after principal persistence;
- reject blind create retry when no principal can be recovered;
- reconcile publication success with a lost response;
- resume Directory convergence after publication; and
- reject a restored state that lowers authority epoch or Registry revision.

### Replica boundary and Wasm roles

- reject configuring the same writable role as horizontally equivalent
  targets;
- accept separately declared replica Tree Specs/Groups without publishing
  them as the writable primary;
- prove no data replication, promotion or failover behavior is implied;
- attribute raw/compressed Wasm changes to the host, Coordinator, Tree Root and
  service roles; and
- prove unrelated ordinary Canisters retain no 0.101 workflows.

## Completion Criteria

0.101 is complete when:

1. `[services.fleet.targets]` is the sole Fleet service declaration.
2. The protected 0.100 declaration, not mutable source configuration, is the
   activation authority.
3. Every target resolves to one exact active Tree in a singleton Tree Group.
4. Existing services are adopted in place without ownership or controller
   transfer.
5. Missing services are provisioned only through their target Tree Root.
6. Complete live and removed Tree evidence prevents duplicates.
7. The Coordinator publishes one complete service set atomically.
8. Every Registry and Directory service entry includes its owning `TreeId`.
9. The Coordinator remains outside all Canister Trees and service hierarchies.
10. Co-locating a Primary Data Tree with the Coordinator is explicit and
   changes no logical authority.
11. A service Tree on another Subnet behaves identically.
12. Writable-primary replication and promotion remain unimplemented and
    separately modelled.
13. Every durable boundary has focused restart and idempotency proof.
14. Restore cannot lower canonical authority or publication state.
15. Per-role Wasm evidence proves control-plane logic is not retained by
    unrelated ordinary Canisters.
16. Closeout finds no Coordinator-owned local service registry, ownership
    transfer machinery or superseded distinguished-Subnet terminology.

## Expected Follow-On

0.101 deliberately stops at one canonical writable binding per selected role.
A later replication design may define:

- a replica-specific Tree Spec and Tree Group;
- snapshot or change-stream transport;
- lag and completeness evidence;
- read routing;
- promotion and old-primary fencing; and
- recovery when the primary Tree or Subnet is unavailable.

Those replicas are not equivalent members of the primary service target. The
Primary Data Tree remains the unique published writable authority until a
later protocol safely changes that fact.

The
[0.103 cross-Subnet data transport groundwork](../0.103-cross-subnet-data-transport-groundwork/0.103-design.md)
may supply bounded call and route evidence for later Canister-to-Canister
transport. It is not required for client-directed routing: clients can call
the published principal directly and present Fleet-scoped chain-key-backed
credentials for local verification.
