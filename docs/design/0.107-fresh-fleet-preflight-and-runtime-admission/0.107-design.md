## Problem

The first downstream installation attempt exposed three related readiness
gaps:

| Feedback | Current limitation | 0.107 outcome |
| --- | --- | --- |
| CANIC-009 | installation discovers an anonymous, locked or wrong effective ICP identity only after expensive build preparation | exact non-anonymous Fleet-operator identity admission before release-build allocation or Wasm preparation |
| CANIC-011 | `caller::is_whitelisted()` reads only the compile-time App configuration | bounded, durable and auditable runtime admission administered by an owning Root or controller |
| CANIC-012 | `canic deploy plan` is not target- and Fleet-input-complete, and the top-level environment is not forwarded to its leaf | one effect-free fresh-Fleet preflight compiled from the same authoritative inputs as installation |
| CANIC-013 | a live NNS Subnet Catalog inconsistency loses important provenance while being wrapped for the operator | structured version, assurance, source, cache, subject, retry and pre-effect diagnostics |

These are one release line because they meet at the same safety boundary. An
operator must know that a fresh Fleet is admissible before building or
installing it, and the installed application must retain an explicit way to
change its local caller admission without recompiling the Wasm.

## Decision

0.107 makes five hard-cut decisions:

1. `canic deploy plan` becomes the canonical effect-free fresh-Fleet
   preflight and accepts the same App, Fleet, environment, Fleet input and
   build profile that installation consumes.
2. explicit plan refresh and fresh installation may acquire missing or invalid
   mainnet catalog evidence, but compile the authoritative decision from its
   stable validated snapshot authority so acquisition does not perturb digest
   parity.
3. Installation and planning call one pure plan compiler. The canonical plan
   digest is recorded by installation, so equal authoritative inputs and
   observations produce the same identity.
4. live Subnet Catalog failures retain structured collection provenance and
   explicitly state whether any build, local-state or IC mutation began;
5. the checked-in whitelist seeds a fresh installation exactly once. A
   bounded stable runtime record is authoritative after restoration.

No part of this decision weakens NNS Registry validation or turns planning
into a best-effort forecast.

## Goals

0.107 must:

- forward the top-level environment to the direct `deploy plan` leaf and
  reject disagreement between global, internal and resolved target identity;
- require protected Fleet input for a fresh-Fleet plan under the same rules as
  `canic install`;
- resolve placement, admissions, pool shape, funding requirements, expected
  Canister count, maximum debit and operator balance before build preparation;
- keep planning read-only with respect to deployment state and IC update calls;
- let an explicit cold-cache mode acquire live Registry evidence and publish
  only Canic's private catalog cache;
- let installation acquire the same evidence when its cache is missing or
  invalid, then compile from stable validated snapshot authority;
- require the effective non-anonymous ICP CLI identity to equal the Fleet-input
  operator before release-build allocation or Wasm preparation;
- reuse the exact install-plan compiler, canonical encoding and digest;
- persist the plan digest and relevant catalog evidence in install receipts;
- fail closed on missing, stale, inconsistent or insufficient evidence;
- preserve the exact Registry version when the upstream collector exposes it;
- classify diagnostics without guessing that a live inconsistency is
  transient;
- seed runtime whitelist authority on a fresh install and persist exact
  add/remove results, revision and digest;
- authenticate whitelist administration through existing role-owned command
  and status surfaces; and
- prove unauthorized, capacity, exact-retry, interruption and restoration
  behavior.

## Non-Goals

0.107 does not:

- bypass Registry invariants, synthesize missing subnets or route around an
  invalid catalog;
- fall back to Dashboard data, a stale cache or a lower assurance source;
- execute installation, build Wasm, create Canisters, write local deployment
  state or reserve funds during `deploy plan`; the explicit catalog-acquisition
  mode may write only the private `.canic/ic-query` cache;
- adopt an existing Fleet or introduce rolling or mixed-version operation;
- make application sessions from 0.105 into a whitelist or grant store;
- add a general entitlement database, user login protocol or application-
  specific authorization model;
- let a whitelisted caller administer the whitelist merely by being present;
- merge later changes to compiled App configuration into restored runtime
  authority;
- add a second-generation product schema, legacy decoder, alias or fallback;
  or
- modify Toko or another downstream repository.

## Authority Model

### Deployment Inputs

The following named authority is hashed and compared as one unit:

| Field | Authority |
| --- | --- |
| App | exact source App identity and canonical App configuration |
| Fleet | exact operator-selected Fleet identity |
| environment | canonical network selected by the top-level CLI and ICP project configuration |
| Fleet input | canonical protected Fleet-input bytes and schema-1 digest |
| build profile | exact selected Canister build profile |
| release source | exact workspace or release-build identity already owned by installation |
| catalog | validated Registry version, catalog digest, assurance and source endpoints when available |
| operator | exact principal and account used for admission and balance evidence; installation requires the effective ICP identity to equal this principal before builds |

A mismatch is a blocker, not a warning. The CLI may render multiple spellings,
but the plan compiler accepts only the canonical named structure.

### Runtime Admission

The runtime whitelist has three distinct authorities:

- the App configuration supplies the initial set only during fresh bootstrap;
- the owning Root and current Canister controllers authorize administrative
  commands through the existing role boundary; and
- the Canister-local stable record is the sole membership authority after
  bootstrap and restoration.

Membership never confers administrative authority. Root/controller authority
never silently confers application access; a controller that must use a
whitelist-protected application endpoint is added explicitly.

B1 must freeze the exact Root/controller predicate for each managed role and
prove that it does not create a policy-to-ops dependency inversion.

## Fresh-Fleet Plan Contract

The maintained operator shape is:

```text
canic deploy plan <fleet> --app <app> --fleet-input <path> [--refresh-catalog]
```

The existing global environment and build-profile inputs remain valid. B1 may
refine option spelling only when it keeps every functional command and help
surface in ASCII lexicographic order. Without `--refresh-catalog`, planning
uses existing validated catalog evidence and never contacts the IC. On an IC
target, the explicit flag selects the existing `RefreshMissingOrInvalid`
acquisition policy: public NNS Registry query calls may update the private
`.canic/ic-query` cache, but no IC update call or deployment mutation is
permitted. Direct planning compiles from the stable snapshot authority returned
by that validated load. Installation performs its existing exact recompilation
through a second cache-only read, but both decisions use the same stable
snapshot authority, so cache path, collection time, transient disposition and
the flag itself do not create a plan/install digest mismatch.

### Pure Compilation

One host-owned function compiles a canonical `DeploymentPlanV1` from already
loaded, validated named inputs. It must not:

- read ambient process state;
- resolve a second environment;
- write the Fleet Catalog, receipts, caches or output files;
- invoke a build;
- activate an ICP environment; or
- perform an IC update call.

Input loading and live catalog collection occur before the pure compiler and
retain their own typed errors. Text/JSON rendering and optional explicit
`--out` persistence occur after compilation. Writing an operator-requested
new output file is report delivery, not plan authority, and must retain the
existing create-new/no-follow safety rules.

### Required Evidence

The plan report must make these facts machine-readable and render them
concisely in text:

- canonical App, Fleet, environment, network and build profile;
- Fleet-input source, schema and digest;
- operator principal and funding account;
- canonical catalog Registry version, digest, assurance and source endpoints
  when available;
- separate report-only catalog cache path, collection time and acquisition
  disposition;
- selected subnet and the placement/admission result for every required role;
- expected role, root and pool Canister counts;
- per-category funding requirements and maximum possible debit;
- observed operator balance, observation source/time and sufficient/
  insufficient result;
- release/build identity and expected artifact inventory;
- ordered blockers, warnings and assumptions;
- canonical plan digest; and
- a `no_effects_started` fact covering builds, deployment-state workspace
  writes and IC update mutation. Catalog-cache acquisition is represented by
  separate report provenance instead.

Unknown evidence required for a fresh install is a blocker. A plan must not
convert missing funding, placement or catalog evidence into a successful
assumption merely because the Fleet does not yet exist.

### Digest And Installation Binding

The plan digest covers the canonical plan payload, not text formatting, file
paths, timestamps used only for display or diagnostic prose. Every fact that
can change an installation decision is inside the payload.

Installation must call the same compiler after loading the same authority.
Before build preparation it:

1. rejects any plan blocker;
2. prints the canonical plan digest and maximum debit;
3. binds its durable install session to that digest; and
4. records the digest in completion, rejection and resume evidence.

If a live observation changes between an earlier plan and installation, the
new digest is intentionally different. The operator can require the expected
digest using the accepted B1 option or input binding; installation fails
before effects on disagreement. B1 freezes the smallest CLI spelling that
works with current install-session and deployment-truth surfaces.

## Subnet Catalog Diagnostics

The current collector resolves the subnet list, complete authoritative
`canister_ranges_*` family and subnet records at one pinned Registry version.
It reads legacy `routing_table` only when the pinned modern family is genuinely
empty and never falls back after a modern-family error. 0.107 preserves that
strictness.

### Structured Failure

A collection or validation failure carries, when known:

| Field | Meaning |
| --- | --- |
| network | canonical network requested |
| endpoint | exact source endpoint without secret material |
| assurance | certified/uncertified classification already defined upstream |
| registry_version | exact version used for the internally consistent read |
| cache_disposition | bypassed, absent, rejected, refreshed or used |
| subject | offending subnet, principal, routing range or record kind |
| category/code | stable upstream and Canic diagnostic classification |
| retry | retryable, non-retryable or unknown with a reason |
| effects | build, local mutation and IC mutation all false for this boundary |

Canic renders “live catalog inconsistency” unless the typed source proves a
more specific category. It must not call the condition transient solely
because a later Registry version might repair it.

### Upstream Gate

If the current `ic-query` public error loses the Registry version or offending
subject while wrapping validation, B1 records the exact missing fields and
the smallest upstream API change. Canic may land independent target and plan
work, but CANIC-013 is incomplete until a published/committed dependency can
preserve every field claimed by the final report. No string parsing or forked
collector is allowed as a substitute.

## Runtime Whitelist Contract

### Stable Record

The current product contract remains schema version 1. The authoritative
record contains at least:

- a sorted unique bounded principal set;
- an exact monotonically increasing revision;
- a canonical membership digest; and
- the last accepted operation identity/result required for interruption-safe
  exact retry.

B1 freezes the hard maximum principal count and operation-retention bound from
measured stable-memory and Candid limits. A request that would exceed the
limit fails without mutation. No unbounded list, scan history or audit log is
stored.

### Bootstrap And Restoration

On a fresh 0.107 install, synchronous Canic restoration creates the stable
record from the validated compiled seed before deferred hooks run. Duplicate
seed principals collapse under canonical ordering. Missing configuration
creates an empty record and whitelist checks fail closed.

On same-release restart or upgrade, restoration reads the existing stable
record. It never reseeds, merges or deletes membership based on the compiled
configuration. Corrupt or unsupported state traps/fails restoration under the
normal model invariant rather than silently returning to the seed.

This is same-release interruption recovery, not cross-release migration.

### Commands And Status

Whitelist administration adds bounded variants beneath the existing managed
Canister role command/status envelopes. It does not add a universal public
method. The exact variant names are frozen in B1 and must cover:

- add one principal with expected revision and operation identity;
- remove one principal with expected revision and operation identity; and
- return one bounded membership page plus revision and digest.

Add-present and remove-absent are successful idempotent outcomes and do not
advance the revision. A new effective mutation advances it exactly once. An
exact operation replay returns the retained result; a conflicting reuse is
rejected. Authorization occurs at the endpoint before membership, revision or
operation state is read.

### Access Evaluation

`caller::is_whitelisted()` keeps its public predicate meaning but delegates to
runtime whitelist ops instead of configuration ops. The access policy remains
pure in shape: endpoint/macro access evaluation reads a named view/result and
does not mutate storage. Application-session authorization remains separate.

## Layering And Ownership

| Concern | Owner |
| --- | --- |
| CLI arguments, help, text/JSON rendering | `canic-cli` |
| Fleet-input loading, plan compilation, install binding and receipts | `canic-host` |
| NNS catalog collection types | released `ic-query` dependency |
| Canic catalog classification and propagation | `canic-host` |
| whitelist stable record and invariants | `canic-core::model` |
| deterministic membership and record conversion | `canic-core::ops` |
| authorization decisions and capacity policy | `canic-core::policy` |
| command/retry orchestration | `canic-core::workflow` |
| role command/status DTOs and immediate authentication | existing endpoint/facade boundary |

DTOs remain passive. Workflow does not construct or mutate records. Policy
does not call ops or storage.

## Failure And Recovery Invariants

- Plan failure occurs before build preparation, deployment-state mutation or
  IC update mutation and says so in structured output. An explicitly requested
  catalog refresh may already have updated only the private catalog cache.
- An environment mismatch fails before catalog refresh.
- An invalid Fleet input fails before balance or live catalog work where the
  ordering can be deterministic.
- Installation resolves the effective ICP identity after exact plan
  recompilation but before release-build allocation or Wasm preparation. It
  rejects anonymous, unusable and Fleet-operator-mismatched identities; later
  controller observations remain required at the effect boundary.
- An insufficient balance fails before build preparation and installation.
- A catalog refresh never replaces stronger accepted evidence with weaker
  evidence.
- An interrupted whitelist command is either absent or replayable to the one
  accepted result; it cannot apply twice.
- Revision conflict, operation conflict, unauthorized caller and capacity
  excess leave membership and digest unchanged.
- Removal takes effect for the next access evaluation and survives
  restoration.
- No fallback to compiled seed occurs after stable authority exists.

## Acceptance Criteria

0.107 is complete only when:

1. the direct `deploy plan` leaf receives and reports the canonical selected
   environment;
2. a fresh-Fleet plan consumes the exact Fleet input required by install;
3. a fresh checkout can explicitly acquire authoritative live mainnet catalog
   evidence without a build, deployment mutation or IC update call;
4. installation can acquire the same missing or invalid evidence while keeping
   its digest equal to the preceding authoritative plan;
5. installation rejects anonymous, unusable or Fleet-operator-mismatched ICP
   identities before release-build allocation or Wasm preparation;
6. invalid placement, catalog or funding evidence blocks before build and IC
   effects;
7. plan and install produce the same digest for the same authoritative facts,
   and expected-digest disagreement is rejected;
8. catalog inconsistency output preserves all upstream-known provenance and
   never labels unknown retryability as transient;
9. a freshly seeded whitelist can be changed through authorized bounded
   runtime commands without rebuilding;
10. unauthorized, capacity, conflict, interruption, exact-retry, removal and
   restoration evidence passes;
11. application sessions and compiled whitelist authority remain separate;
12. active documentation and generated surfaces contain no superseded command,
   schema or schedule residue; and
13. one read-only downstream Toko rerun confirms CANIC-009, CANIC-011,
    CANIC-012 and CANIC-013 are closed or records an exact external blocker.
