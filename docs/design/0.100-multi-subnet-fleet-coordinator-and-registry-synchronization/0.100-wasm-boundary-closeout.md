# Canic 0.100 Infrastructure Wasm Boundary Audit

Date: 2026-08-03

## Verdict

`PASS` for the code and artifact boundary. Released 0.100.98 removes the
root-embedded Store artifact and implements independent host installation plus
root-observed adoption. Open 0.100.99 removes the final root-triggered Store
build side effect and records the post-extraction artifacts below. Overall
0.100 closeout still waits for the maintainer-owned disposable real-network
root-deletion proof described in the implementation status.

This measurement is based on immutable `v0.100.98`
(`94119c39c725383aa7f2ffd5e5f4ee9154ee91a2`) plus the open 0.100.99
build-boundary hard cut. No package version, deployment, Canister state or
sibling repository was changed by the measurement.

## Method

All three release artifacts were produced through the host
`build_artifact` entrypoint with `ICP_ENVIRONMENT=local`, offline locked Cargo,
the `release` Canister profile and the test App's maintained configuration.
That is the same artifact authority used by the recurring Wasm audit; no
direct Cargo Wasm, pre-shrink or reconstructed gzip path was used.

The run used:

- `rustc 1.97.1 (8bab26f4f 2026-07-14)`;
- `ic-wasm 0.11.0`; and
- `twiggy 0.8.0`.

`gzip -t` passed for every compressed artifact, and decoding each gzip
reproduced the exact raw-Wasm SHA-256 digest. `ic-wasm info` parsed every raw
artifact and reported an embedded public Candid metadata section with the
same byte length as its emitted `.did` file.

## Authority Result

| Boundary | Sole behavior authority | Measured evidence |
| --- | --- | --- |
| Fleet Registry membership and root-row lifecycle | Fleet Coordinator | Registry query, acknowledgement, activation, draining, removal and Coordinator deletion-execution receipts occur only here |
| Component trees and local Canister assets | Fleet Subnet Root | Component allocation, child creation, Directory convergence, subtree removal, root-local draining/deletion preparation, pool and Store administration occur only here |
| Artifact bytes and local garbage collection | Wasm Store | Catalog, chunk publication/read, manifest staging and Store GC endpoints occur only here |
| Build package and artifact identity | Host artifact builder | one dispatch maps built-in Coordinator/Store and admitted root roles to one output carrying package, paths and transforms |
| Installation evidence | Host installation plan and journal | complete for Coordinator, root and sibling Store, including separate funding, same-Subnet creation, reciprocal installation and a root-observed sole-controller adoption receipt |

Shared init, inspection, timer, readiness, cycle and infrastructure activation
surfaces are runtime protocol plumbing. The root's Store overview/publication
methods control its separate Store Canister; they do not read or mutate the
Store's catalog locally. Generic `post_upgrade` hooks remain shared lifecycle
scaffolding, but 0.100 defines no cross-release upgrade, migration, import,
mixed-version or rollback path and the install flow remains reinstall-only.

## Removed Duplication

- Install preparation no longer invokes the Coordinator-specific builder
  outside the canonical artifact dispatcher.
- The Fleet Subnet Root package is taken from its qualified build output, not
  looked up again through the complete-build target collection.
- Coordinator and Wasm Store builders now emit the same canonical artifact
  output type as admitted role builds, including transform evidence.
- Cargo provenance rejects a qualified output whose package identity differs
  from the selected package manifest.
- Application-union file qualification preserves the build output's package
  identity instead of copying it from the target, making the existing
  output/target comparison effective.
- The facade root-control-plane feature no longer repeats the Store feature
  already implied by root authority. Rebuilding afterward produced identical
  root and Store raw/gzip hashes.

The root-embedded Store bytes, root-triggered Store build and post-root
artifact-residue qualifier are not retained. Installation preparation invokes
the canonical Store builder explicitly and consumes its output independently;
root and Store artifacts relate only through protected manifest/hash identity.

## Post-Extraction Result

Implementation and measurement now prove:

- independent root and Store build outputs with no root data segment carrying
  Store Wasm bytes;
- one immutable plan and recoverable host journal for separate root and Store
  funding, same-Subnet creation and installation;
- reciprocal root/Store init bindings and exact live module verification;
- a root-observed Store controller set containing only that root plus the
  host-verified terminal adoption receipt;
- root publication through the imported Store binding with no root-owned
  create/install or replacement path;
- focused interruption coverage for Store creation, install and controller
  handoff;
- exact replacement raw/gzip/hash, Candid and retained-size measurements for
  all three infrastructure artifacts; and
- a root-only build with the prior Store artifact moved aside that leaves the
  Store path absent while reproducing the measured root bytes exactly,
  followed by an explicit Store build that reproduces its measured bytes.

## Stale-Path Result

Maintained source under `crates/`, `apps/`, `canisters/` and `scripts/`
contains no surviving:

- `TreeSpecId`, `TreeGroupId`, `TreeId`, Tree binding, Registry or Directory;
- logical `SubnetSlotId`;
- role-based `SubnetRegistry` or `SubnetDirectory`;
- old Fleet/Tree root-principal field;
- shared pre-split `DirectoryProvenance`;
- nested Component declaration or nested lifecycle authority; or
- arbitrary artifact fallback.

Current `FleetDirectoryProvenance` and `ComponentDirectoryProvenance` are the
intentional split owners. Ordinary source-path variables and backup source-root
Canister fields are unrelated to removed topology provenance.
The deterministic generated-wrapper path used when a packaged downstream has
no direct Store package is part of the same validated build-source resolver;
it does not select prebuilt or caller-supplied artifact bytes.

Historical changelogs, archives and this design's dated implementation record
retain old terminology as development evidence; they are not maintained
runtime or configuration surfaces.
