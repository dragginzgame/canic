# Canic 0.100 Design: Multi-Subnet Fleet Coordinator and Registry Synchronization

Date: 2026-07-25

## Status

- Status: proposed.
- Release boundary: reinstall only.
- Dependency: the
  [0.99 App/Fleet hard cut](../0.99-app-fleet-identity-and-terminology-hard-cut/0.99-design.md)
  defines the terms and identities reused by this design.
- Scope: Fleet coordination, heterogeneous Canister Trees, Tree lifecycle,
  Registry synchronization and local Directory projection.
- Compatibility posture: none. A 0.100 Fleet starts from empty 0.100 state.

0.100 does not read or transform a 0.99 installation. It has no extraction
step, one-member seed, authority transfer, source-root fence, cross-release
journal, mixed-version mode or prior-release recovery path. Existing Fleets
are reinstalled.

## Thesis

A Fleet may contain several independently scaled Canister Trees with different
local topologies. One separately placed Fleet Coordinator owns the complete
Fleet-wide Tree Registry. Each Tree Root owns only its Tree-local Registry,
mirrors the Fleet Registry and cascades a read-only Fleet Directory to the
Canisters in that Tree.

~~~text
Fleet Coordinator
  owns FleetRegistry
       |
       | authenticated, bounded snapshot synchronization
       v
Tree Root
  owns Tree-local SubnetRegistry
  stores FleetRegistryMirror
       |
       | existing Tree-local cascade
       v
ordinary managed Canisters
  consume FleetDirectory
~~~

The Coordinator is not a Tree member, root-of-roots, application router or
controller of Tree-local Canisters.

## Terminology

| Term | Meaning |
| --- | --- |
| Fleet Coordinator | The sole Fleet Registry writer |
| Coordinator Subnet | Physical IC Subnet hosting the Coordinator |
| Tree Spec | App-declared permitted rooted topology |
| Tree Group | Fleet-scoped collection of Trees using one Tree Spec |
| Canister Tree | One concrete rooted hierarchy on one physical Subnet |
| Tree Root | Local lifecycle and Registry owner for one Tree |
| TreeId | Fleet-scoped logical identity of one Tree |
| SubnetId | Physical placement metadata; never Tree identity |
| Fleet Registry | Complete Coordinator-owned Tree lifecycle state |
| Fleet Registry Mirror | Complete read-only Registry copy at a Tree Root |
| Fleet Directory | Consumer projection cascaded inside a Tree |

Several Trees may use the same physical `SubnetId`. Co-location does not merge
their identities, Registries, roots or lifecycle.

`default`, when used, is an application workload name. It does not select the
Coordinator Subnet.

## Release Installation Boundary

A fresh 0.100 installation proceeds in this order:

1. compile and freeze the App's Tree Specs and Tree Groups;
2. resolve and journal the Coordinator placement;
3. allocate and journal every initial `TreeId` and exact placement;
4. create and install the Fleet Coordinator with its protected binding;
5. create the genesis Fleet Registry from empty state;
6. create and install every fresh Tree Root behind the runtime `Prepared`
   fence with its protected Tree binding;
7. register each Tree through `Joining`, synchronize the exact snapshot and
   accept the recorded root's acknowledgement;
8. commit every required initial Tree as Registry `Active`;
9. synchronize every initial root to the final all-active Registry version and
   atomically activate its matching Directory;
10. activate each Tree Root's runtime only after that final synchronization;
11. verify exact runtime `Active` evidence and final mirror/Directory agreement
    for every required initial Tree; and
12. publish the Fleet catalog row only after that complete evidence is durable.

The installation journal owns same-release interruption recovery. It never
refers to a 0.99 root, catalog, Registry, stable state or Canister.

Registry lifecycle and runtime lifecycle are different state machines.
`ManagedTreeStatus::Active` means the Tree is eligible in Fleet topology; it
does not by itself open the Tree Root's ordinary endpoints or start timers.
The existing runtime `Prepared` fence admits only the exact bootstrap,
synchronization, acknowledgement, activation-status and activation operations
needed by fresh installation.

A Tree Spec is a permitted topology, not an instruction to instantiate every
declared role during 0.100 installation. The initial 0.100 Tree inventory
contains its Tree Root. Later Tree-local lifecycle operations may create
permitted descendants, and 0.101 explicitly provisions declared
Fleet-authoritative services. Merely naming another role in a Tree Spec never
creates it.

## Goals

0.100 must:

1. establish exactly one Fleet Registry writer;
2. represent heterogeneous Tree Specs and independently scaled Tree Groups;
3. separate logical Tree identity from physical Subnet placement;
4. make Tree join, activation, drain and removal explicit;
5. authenticate every Coordinator/Tree Root control-plane call;
6. synchronize complete bounded Registry snapshots;
7. activate a mirror and its derived Directory atomically;
8. preserve Tree-local lifecycle ownership at each Tree Root;
9. remain deterministic across interruption and exact retry; and
10. keep ordinary Canisters out of Fleet control-plane workflows.

## Non-Goals

0.100 does not implement:

- any prior-release transition;
- service-Canister adoption;
- Fleet-authoritative service activation or publication;
- application routing, sharding decisions or data replication;
- automatic metric-driven Tree scaling;
- Coordinator election, relocation or replacement;
- Tree relocation or `TreeId` reuse;
- distributed consensus between roots;
- a second Fleet Registry writer; or
- compatibility aliases, decoders or fallback state.

## Authority Map

| Concern | Sole owner |
| --- | --- |
| App topology declaration | checked-in App configuration |
| fresh installation progress | host installation journal |
| Coordinator placement | finalized deployment evidence |
| Fleet Tree lifecycle | Fleet Coordinator Registry |
| Tree-local Canister lifecycle | that Tree Root's local Registry |
| root copy of Fleet state | Fleet Registry Mirror |
| ordinary-Canister topology view | Fleet Directory |
| application routing | application code, outside this design |

A mirror, Directory, host report, status file or controller assertion never
becomes Fleet Registry authority.

## Coordinator and Tree Placement

Coordinator placement is independent of App topology and Tree placement:

~~~rust
pub enum CoordinatorSubnetSelector {
    Recommended,
    Profile(SubnetProfileId),
    Explicit(SubnetId),
}

pub struct FleetCoordinatorBinding {
    pub fleet: FleetBinding,
    pub coordinator_subnet: SubnetId,
    pub coordinator: Principal,
}
~~~

The selector is host deployment input, not App configuration or runtime
protocol state. On the public IC, `Recommended` resolves through trusted
network metadata to the Fiduciary Subnet. A named eligible profile or explicit
`SubnetId` may override it. Resolution records the exact resulting Subnet and
evidence in the finalized deployment plan before creation. An unavailable,
ineligible or ambiguous target fails rather than falling back to a random
application Subnet.

Initial Tree placement is also finalized deployment input:

~~~rust
pub struct PlannedTreePlacement {
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub subnet: SubnetId,
}
~~~

Every initial Tree has one exact journalled placement before its root is
created. `SubnetId` may repeat, allowing several Trees from the same or
different groups to be co-located. A service or high-value data Tree may also
share the Coordinator Subnet. Co-location changes capacity, cost and outage
trade-offs only; it never changes Tree identity or authority.

The Tree Root and every Canic-managed descendant of one Tree must be created
on, or independently observed on, that Tree's exact placement Subnet. A
contradictory descendant placement fails before local Registry commitment and
becomes explicit recovery work; it never silently turns one Tree into a
cross-Subnet hierarchy.

App configuration declares logical topology and scaling limits. It contains no
physical placement. Host planning must expose and finalize enough placement
input to support one user-focused Tree, many project-focused Trees, deliberate
co-location and distinct Subnets without encoding application routing policy.

## Configuration

0.100 hard-cuts topology configuration to explicit Tree Specs and Tree Groups:

~~~toml
[tree_specs.users]

[tree_specs.users.canisters.root]
kind = "root"

[tree_specs.users.canisters.user_hub]
kind = "service"

[tree_specs.users.canisters.user_shard]
kind = "shard"

[tree_specs.projects]

[tree_specs.projects.canisters.root]
kind = "root"

[tree_specs.projects.canisters.project_instance]
kind = "instance"

[tree_groups.users]
tree_spec = "users"
initial_trees = 1
maximum_trees = 1

[tree_groups.projects]
tree_spec = "projects"
initial_trees = 20
maximum_trees = 150
~~~

Rules:

- every Tree Spec contains exactly one root role;
- every Tree Group references one existing Tree Spec;
- `initial_trees` and `maximum_trees` are nonzero and
  `initial_trees <= maximum_trees`;
- the sum of group maxima fits the Fleet bound;
- source config contains no concrete `TreeId`, root principal or physical
  `SubnetId`; and
- removed 0.99 topology keys, including `[services.fleet].roles`, do not
  parse.

Fleet service targets are not a 0.100 configuration surface. A fresh 0.101
installation introduces and validates that declaration with its service
publication schema.

## Tree Identity and Spec Binding

`TreeSpecId` and `TreeGroupId` are distinct bounded identifiers. `TreeId` is
32 random bytes allocated and durably journalled before root creation. Its
complete identity is `(FleetKey, TreeId)`.

A Tree Spec hash covers the canonical permitted role/package topology and
binding-relevant configuration. It excludes:

- concrete principals;
- physical placement;
- local Registry rows;
- application data; and
- Tree Group scale policy.

Each Tree registration repeats its exact group and Spec hash. A missing group,
wrong hash or full group fails before the Registry changes.

The protected root bootstrap is:

~~~rust
pub struct FleetRegistryBootstrap {
    pub authority: FleetRegistryAuthority,
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub placement_subnet: SubnetId,
    pub tree_root: Principal,
}
~~~

Every ordinary managed Canister retains the same immutable Fleet, Tree,
Tree-Root, group, Spec-hash and placement identity required to reject
cross-Tree cascade or local-lifecycle traffic. The Coordinator has only
`FleetCoordinatorBinding`; it never receives `FleetRegistryBootstrap`.

## Registry Model

The canonical model is:

~~~rust
pub struct FleetRegistry {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub tree_groups: Vec<FleetTreeGroup>,
    pub trees: Vec<FleetTreeEntry>,
}

pub struct FleetRegistryAuthority {
    pub binding: FleetCoordinatorBinding,
    pub epoch: u64,
}

pub struct FleetTreeGroup {
    pub group: TreeGroupId,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub initial_trees: u16,
    pub maximum_trees: u16,
}

pub struct FleetTreeEntry {
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub spec_hash: [u8; 32],
    pub subnet: SubnetId,
    pub tree_root: Principal,
    pub status: ManagedTreeStatus,
}

pub enum ManagedTreeStatus {
    Joining,
    Active,
    Draining,
    Removed,
}
~~~

Groups and Trees use canonical ascending order. Snapshot hashes never depend
on insertion order.

The content hash is stored in a manifest outside the hashed snapshot:

~~~rust
pub struct FleetRegistryManifest {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub byte_length: u64,
    pub content_hash: [u8; 32],
}

pub struct FleetRegistryVersion {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub content_hash: [u8; 32],
}
~~~

`FleetRegistryVersion` is the exact compact identity used by mirrors,
acknowledgements, journals and later service/transport protocols. It is not an
application-data revision.

## Registry Commit

Every Registry mutation:

1. loads the current canonical snapshot;
2. validates the complete requested transition;
3. constructs and deterministically encodes the next snapshot;
4. checks entry and byte limits;
5. writes and durably confirms the complete snapshot;
6. atomically publishes its manifest as current; and
7. returns the new exact version.

The head never references absent or incomplete bytes. No mutation is inferred
from a returned command status alone.

Genesis uses authority epoch 1 and Registry revision 1. It contains every
compiled Tree Group and zero Trees. Tree joins advance the revision.

## Authority Epoch and Restore Fence

The authority epoch binds Registry history to one exact Coordinator. 0.100
records it but does not implement Coordinator replacement.

Mirrors accept only the protected Coordinator, Fleet binding and epoch:

- a lower epoch is stale;
- another Coordinator at the same epoch is contradictory;
- an unexpected higher epoch requires a future explicit design; and
- no mirror may promote itself.

A restored Coordinator backup cannot resume mutation at the same epoch unless
the latest committed Registry version is independently proven. 0.100 defines
no such proof, so an ambiguous restore remains read-only and fail-closed.
This is a restore safety rule inside 0.100, not a cross-release transition.

## Snapshot Synchronization

0.100 synchronizes complete snapshots, not deltas or an event log.

The Coordinator exposes authenticated inter-Canister update calls for:

- the current Registry manifest; and
- exact snapshot bytes for one manifest.

A Tree Root:

1. reads the current head;
2. fetches bytes only when its local version differs;
3. checks byte length before decoding;
4. verifies the content hash;
5. validates Fleet, Coordinator, epoch, revision, groups and Tree rows;
6. persists a candidate mirror;
7. derives the Directory from those exact bytes;
8. atomically activates mirror and Directory; and
9. cascades that Directory inside its Tree.

Interrupted candidate state never becomes active. A newer head discovered
during fetch discards the superseded candidate and restarts within bounded
retry policy.

The default steady-state poll interval is five minutes. Failures use bounded
backoff from 15 seconds to 15 minutes. Configuration may select 60 seconds to
one hour. Polling stops for removed Trees.

## Tree Registration

Registration is:

~~~text
absent → Joining → Active
~~~

### Joining

The Coordinator validates:

- authenticated administrative authority;
- a journalled unused `TreeId`;
- known Tree Group;
- exact Tree Spec hash;
- group capacity;
- exact placement `SubnetId`;
- exact Tree Root principal; and
- absence of conflicting principal or Tree identity.

It then publishes one `Joining` revision.

### Acknowledgement

The recorded Tree Root must:

1. fetch the snapshot containing its exact `Joining` row;
2. persist and activate the exact mirror;
3. derive and activate the matching Directory; and
4. acknowledge the exact Registry version and content hash.

Only that root may acknowledge. A valid acknowledgement publishes the next
revision with the Tree `Active`. Exact retry returns the existing result.

Failed joins may become `Removed`; their `TreeId` is never reused.

## Draining and Removal

Removal is:

~~~text
Active → Draining → Removed
~~~

`Draining` excludes the Tree from new placement while retaining explicit
lookup and domain-owned evacuation.

Before ordinary removal, the Tree Root:

1. durably fences new Canic-managed creation and local Registry mutation;
2. exports its bounded final managed-Canister inventory;
3. binds that inventory to the exact Tree and Registry version; and
4. sends authenticated qualification evidence to the Coordinator.

The Coordinator stores that evidence before publishing `Removed`. If the root
is unavailable, emergency removal stores an explicit unqualified tombstone
rather than inventing an empty inventory.

Removal does not delete or stop Canisters, change controllers or erase local
state. Those are separate explicit deployment operations. A removed root
cannot synchronize or regain Fleet lifecycle authority. Tombstones are not
compacted and `TreeId`s are not reused in 0.100.

## Local Directory Projection

Each active mirror produces one Fleet Directory containing:

- exact authority and Registry provenance;
- all Tree Group projections;
- all Tree lifecycle projections.

`source_root` and activation time remain truthful local provenance. Group,
Tree, revision and content-hash data are identical for every root activated at
the same Registry version.

The exact 0.100 consumer shape is:

~~~rust
pub struct FleetDirectory {
    pub provenance: DirectoryProvenance,
    pub groups: Vec<FleetDirectoryGroup>,
    pub trees: Vec<FleetDirectoryTree>,
}

pub struct DirectoryProvenance {
    pub authority: FleetRegistryAuthority,
    pub source_root: Principal,
    pub registry_revision: u64,
    pub registry_content_hash: [u8; 32],
    pub synchronized_at: Timestamp,
}

pub struct FleetDirectoryGroup {
    pub group: TreeGroupId,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub initial_trees: u16,
    pub maximum_trees: u16,
}

pub struct FleetDirectoryTree {
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub spec_hash: [u8; 32],
    pub subnet: SubnetId,
    pub tree_root: Principal,
    pub status: ManagedTreeStatus,
}
~~~

0.100 has no service-entry field. Fresh 0.101 installation hard-cuts this
shape to add its complete service projection.

The existing Tree-local cascade distributes this Directory. Every request and
stored child binding carries exact `TreeId` and Tree Root identity, so
co-located Trees cannot accept each other's children.

Ordinary Canisters never fetch the Registry directly from the Coordinator.

## Consumer Boundary

The maintained topology API may expose:

- Fleet Registry authority;
- Coordinator and Coordinator Subnet;
- one Tree or Tree Group;
- active Trees, optionally filtered by group;
- Trees placed on a physical Subnet;
- the local Tree and group; and
- exact Directory provenance.

These are topology candidates, not application routing answers. Canic does not
map a user, project or other domain key to a Canister.

Missing state, unknown identity, inactive status, Spec mismatch, Fleet
mismatch, authority mismatch and corrupt projection return typed failures.

## Authorization

The Coordinator uses the Fleet-scoped trust boundary installed with the fresh
Fleet. It does not create a second administrator list or token audience.

Every control-plane endpoint binds:

- caller principal;
- Fleet;
- authority epoch;
- Tree identity when applicable;
- expected Registry revision/hash; and
- operation identity for mutations.

Controllers do not gain Tree synchronization access merely by being
controllers.

## Failure and Recovery

For every external effect, durable intent precedes invocation. After an
uncertain outcome, restart observes authoritative state before retrying.

Same-release recovery must be:

- single-writer;
- monotonic;
- identity-bound;
- bounded in attempts and retained evidence;
- deterministic for exact retry; and
- fail-closed for contradictory or unknowable state.

Completed operations return their recorded result without repeating external
work. Retryable transport failure never rewinds committed Registry state.

## Role and Dependency Boundary

| Owner | Responsibility |
| --- | --- |
| Host/CLI | compile config, choose explicit placement, journal creation and drive installation |
| Fleet Coordinator Wasm | own Registry, Tree lifecycle and bounded synchronization |
| Tree Root Wasm | own local Registry, mirror Fleet state and cascade Directory |
| Ordinary Canister Wasm | retain exact identity and consume local Directory |

Host planning code must not enter Wasm. Coordinator lifecycle code must not
enter ordinary Canisters. Tree-local child management must not enter the
Coordinator.

Qualification records raw and compressed Wasm sizes for an ordinary Canister,
Tree Root and Fleet Coordinator and attributes role-specific growth.

## Stable-State Rules

- New durable records use the current schema only.
- One allocation has one named owner.
- The Registry snapshot and current manifest have one atomic activation
  direction.
- Candidate mirror state cannot be read as active.
- Tree-local Registry and Fleet Registry are separate authorities.
- Removed-tree fences survive restart.
- Unknown enum tags, malformed bytes, invalid ordering and over-limit values
  fail closed.
- No reader recognizes 0.99 state as 0.100 state.
- No release-transition state or compatibility decoder exists.

## Implementation Slices

### Slice 1 — Freeze current authorities

- map existing Registry, Directory, cascade and lifecycle code;
- freeze Tree types, bounds and role-package boundaries; and
- prove no 0.99 transition path is required.

### Slice 2 — Fresh Coordinator installation

- compile Tree Specs and Groups;
- resolve and journal independent Coordinator and initial Tree placements;
- install the Coordinator from empty state; and
- commit the genesis Registry.

### Slice 3 — Registry and Tree lifecycle

- implement canonical snapshot commits;
- implement Joining, Active, Draining and Removed;
- install initial Tree Roots behind the runtime `Prepared` fence;
- enforce capacity, identity and tombstone rules; and
- retain removal qualification.

### Slice 4 — Mirror and Directory

- implement head/snapshot synchronization;
- atomically activate verified mirror and Directory;
- cascade Tree-locally; and
- expose bounded consumer topology.

### Slice 5 — Recovery and closeout

- qualify interruption and exact retry;
- activate initial runtimes only after final topology synchronization and
  publish the terminal Fleet catalog only after complete evidence;
- qualify restore fencing;
- measure Wasm boundaries; and
- remove stale or duplicate authority.

## Required Validation

Tests must prove:

- a fresh empty-state installation creates one Coordinator authority;
- no 0.99 state, endpoint or artifact is read;
- `Recommended` Coordinator placement resolves to trusted Fiduciary metadata,
  while named and explicit eligible overrides remain independent of Tree
  placement;
- initial placement supports distinct Subnets and deliberate repeated
  `SubnetId` without merging Tree identity;
- several Tree Groups may use different Specs and limits;
- several Trees may share one physical Subnet without identity crossover;
- a managed descendant observed outside its Tree's placement Subnet rejects
  before local Registry commitment;
- `TreeId` is allocated before creation and never reused;
- wrong Fleet, epoch, group, Spec, root, Subnet, revision or hash rejects;
- group capacity is enforced before Registry mutation;
- snapshot publication never exposes incomplete bytes;
- corrupt, oversized, stale and superseded snapshots fail closed;
- mirror and Directory activate atomically;
- exact acknowledgement and completed mutations are idempotent;
- interruption before and after every durable transition resumes safely;
- Registry `Active` never bypasses the runtime `Prepared` fence;
- no initial Tree Root activates before the final all-active Registry and
  matching Directory are synchronized;
- no Fleet catalog row appears before every required root has exact runtime
  `Active` and final mirror/Directory evidence;
- Coordinator downtime preserves explicitly stale read-only topology;
- removal retains qualified evidence or an explicit unqualified tombstone;
- ordinary Canisters cannot mutate or directly synchronize Fleet state;
- role-specific Wasms do not link unrelated orchestration.

PocketIC or a disposable environment must exercise a real Coordinator and at
least two independently identified Trees, including a cross-Subnet path where
the harness supports it.

## Completion Criteria

0.100 is complete when:

1. a fresh installation creates the sole Fleet Coordinator and Registry;
2. every initial Tree becomes Active through the canonical join protocol;
3. every initial Tree Root remains runtime `Prepared` until it has the final
   all-active Registry and matching Directory;
4. the terminal Fleet catalog row is published only after exact runtime
   activation and topology agreement;
5. Tree Roots mirror one exact Registry and cascade one Directory;
6. Tree-local and Fleet-wide authority remain separate;
7. all recovery is same-release, monotonic and fail-closed;
8. no 0.99 extraction, handoff, fencing, import or mixed-version path exists;
   and
9. current APIs, tests, examples and documentation describe only this model.

inside its selected Tree and publishes the complete set through the
