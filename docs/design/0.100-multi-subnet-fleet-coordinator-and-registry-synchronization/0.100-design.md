# Canic 0.100 Design: Multi-Subnet Fleet Coordinator and Registry Synchronization

Date: 2026-07-25

## Status

- Status: proposed.
- Scope: multi-subnet coordination, heterogeneous Canister Tree topology and
  Tree lifecycle only.
- Design amendment accepted 2026-07-25: a Fleet may contain independently
  scaled Tree Groups with different Tree Specs. Canister Trees in one group
  share an allowed role/policy topology but retain different concrete
  Canisters and application data. Multiple Trees may be placed on the same
  physical IC Subnet.
- Implementation begins with a repository pass to map the canonical
  authorities in this document onto the current root, subnet-state, cascade
  and durable-workflow code.
- This is a hard-cut design. It must not introduce a second competing subnet
  registry, compatibility facade or parallel propagation path.
- Dependency: the [0.99 App/Fleet identity and terminology hard cut](../0.99-app-fleet-identity-and-terminology-hard-cut/0.99-design.md)
  must be complete before any 0.100 implementation begins.
- Compatibility posture: pre-1.0 current schema only. There is no schema tag,
  old-name mapping layer or multi-schema decoder.

## Terminology and 0.99 Transition

0.100 introduces the final topology terms. The 0.99 `SubnetSlotId`,
`subnets.default` and `fleet_root_pid` surfaces remain valid only as
one-Tree input to the 0.100 hard cut:

- `FleetCoordinator` is the separately placed Canister that owns Fleet-wide
  Tree Group and Tree lifecycle state. It is not a root-of-roots.
- `Authority Subnet` is the resolved physical IC Subnet where the Coordinator
  is hosted. It is not the default workload Subnet and is not itself a
  Canister Tree.
- `Tree Spec` is an App declaration of one permitted rooted Canister topology.
  `TreeSpecId` identifies it in App configuration.
- `Tree Group` is a Fleet-scoped horizontally scaled collection of Canister
  Trees that use one exact Tree Spec. `TreeGroupId` identifies the collection.
- `Canister Tree` is one concrete rooted Canister hierarchy, identified by
  `TreeId` and placed entirely on one physical IC Subnet.
- `Tree Root` is the one root Canister and local authority for a Canister Tree.
  It owns that Tree's local `SubnetRegistry`; it is not an authority over the
  physical IC Subnet or over other Trees placed there.
- `SubnetId` is only physical placement identity. It is not a Tree, Tree
  Group, Tree Spec or Fleet lifecycle key, and it may appear in more than one
  Tree entry.
- `FleetRegistry` is the complete Fleet-Coordinator-owned Tree Group and
  Canister Tree lifecycle authority.
- `FleetRegistryMirror` is the complete read-only copy held by each Tree Root.
- `FleetDirectory` is the consumer-shaped projection cascaded from a Tree Root
  to the other Canisters in that Tree.
- `FleetBinding { fleet: FleetKey, app: AppId }` is the immutable runtime
  identity established by 0.99.

`Authority Subnet` is the canonical replacement for the former `Prime Subnet`
term. The distinguished-subnet concept remains: every Fleet has one Subnet
selected to host its Fleet Coordinator. Fiduciary is the recommended fresh
live-Fleet placement policy, not the domain name of that concept.

A Registry is the complete authoritative record set within its scope. A
Directory is a derived, read-only, consumer-shaped projection carrying
Registry provenance. `Index` is not public topology vocabulary.

The 0.99 stable Canister identity, fresh-install activation receipt and
current one-root state are prerequisites. 0.100 consumes them once, allocates
the first `TreeId`, compiles installed `subnets.default` into the canonical
`default` Tree Spec and `default` Tree Group, and publishes only the new
current model. It adds no 0.99 alias, decoder or dual terminology.

## Summary

Canic currently manages one rooted Canister topology inside an individual
Subnet: the root owns the authoritative local state and distributes it to the
other Canisters.

What is missing is the layer above that:

Which Canister Trees exist, which Tree Group and Tree Spec govern each, where
each Tree is placed, and which Canister coordinates Fleet-wide topology?

Install one `FleetCoordinator` on the Authority Subnet and give it one
Fleet-wide `FleetRegistry`.

For a fresh public-IC Fleet, an omitted Authority Subnet selector resolves to
the recommended Fiduciary Subnet; a named profile or explicit `SubnetId` may
override it. For an existing 0.99 Fleet, 0.100 independently observes the
physical Subnet containing the current root and uses it as the Authority
Subnet. Every Tree Root keeps a durable Registry mirror. Only the Fleet
Coordinator and Tree Roots communicate across Subnets for topology
synchronization; ordinary Canisters receive topology through their Tree
Root's existing same-Subnet state cascade.

~~~text
Authority Subnet
  Fleet Coordinator
  owns authoritative FleetRegistry
        |
        | infrequent inter-subnet synchronization
        v
each Tree Root
  stores a complete FleetRegistryMirror
  owns its Tree-local SubnetRegistry
        |
        | existing same-subnet cascade
        v
local canisters
  store consumer-shaped Fleet Tree topology
~~~

0.100 does not adopt, create, move or publish Fleet-authoritative service
Canisters. It establishes the one current Fleet Registry schema with an empty
`authority_services` field so 0.101 can publish the complete set without a
schema change. Authority-service operations belong to 0.101. Existing
root-local creation, attachment, sharding and scaling remain available inside
the exact permitted Tree Spec; 0.100 makes those paths Tree-aware rather
than introducing a second local installer. Roles selected by
`[services.fleet]` are the exception: they are reserved for 0.101 authority
scope and are not created or replicated as fresh Tree-local roles.

Canister Trees are not necessarily homogeneous Fleet replicas. An App may
define, for example, one `users` Tree Group and one `projects` Tree Group. The
first may contain one Tree running user-signup and user-shard roles, while the
second begins with twenty Trees running project-instance, asset and ledger
roles. Trees in the `projects` group share the same permitted Tree Spec but
contain different project Canisters and data.

0.100 compiles those App declarations into immutable Tree Specs and Tree Group
definitions, binds every Tree registration to one exact group/spec/hash, and
exposes the result through the Fleet Directory. It does not choose an
application's user/project routing key, replicate application data or make
concrete Tree inventories identical.

## Problem

Per-subnet topology is insufficient once one Canic fleet spans several subnets.

Without one canonical Fleet Registry:

- roots cannot reliably discover other managed Trees;
- Canisters may need a hard-coded Fleet Coordinator principal;
- different roots can disagree about Fleet topology;
- deployment cannot prove whether a Tree is eligible for user, project or
  another workload family;
- a root can join without proving which App topology template it runs;
- adding or removing a Tree has no authoritative lifecycle;
- later placement policies such as `one_per_active_tree` cannot be evaluated;
- application code may perform unnecessary inter-subnet discovery calls;
- there is no consistent answer to “which Canister owns Fleet Tree lifecycle?”

Later authority-service adoption and replica designs depend on these Tree
facts already existing. Therefore multi-subnet Fleet Registry management must
come first.

## Tree Spec, Tree Group and Canister Tree

The three placement concepts are deliberately separate:

| Concept | Scope | Meaning |
| --- | --- | --- |
| Tree Spec | App configuration | One named permitted rooted topology, identified by `TreeSpecId` |
| Tree Group | Fleet topology | One horizontally scaled collection, identified by `TreeGroupId`, that references one exact Tree Spec |
| Canister Tree | Runtime topology | One concrete hierarchy, identified by `TreeId`, with one Tree Root and one placement `SubnetId` |

A Tree Spec has no resolved platform identity, Tree ID or root principal. It
declares the root template plus the application roles, packages, local
creation policies and topology permitted for that workload family. A Tree
Group references one exact Tree Spec and adds Fleet-local horizontal-scaling
policy. A Canister Tree instantiates that group/spec as concrete Canisters on
one physical IC Subnet.

Multiple Canister Trees may belong to the same group. They share the same Tree
Spec hash but need not have identical `SubnetRegistry` rows,
Canister principals, shard assignments, application data or current local
capacity. Different groups may declare disjoint role sets and topology. A
`users` Tree and a `projects` Tree are therefore both Fleet Trees without
being replicas of one another.

`TreeId` and Tree Root principal are the runtime uniqueness boundaries.
`SubnetId` is placement metadata and may repeat: the same physical IC Subnet
may host multiple Trees from the same or different Tree Groups, as well as the
Fleet Coordinator. Co-located Trees remain separate hierarchies with separate
roots, registries, identities and lifecycle rows. They deliberately share the
physical Subnet's capacity, scheduling and outage domain; Canic never presents
co-location as redundancy or merges Trees because their placement matches.

The 0.99 `subnets.default` declaration compiles into the `default` Tree Spec
and a first Tree Group during existing-Fleet extraction. That hard cut does
not make `default` the Authority Subnet. In fresh configuration, a declared
default Tree Spec remains only the application's default workload topology.
Authority placement is a separate Fleet deployment decision. A default Tree
may be placed on the Authority Subnet, another Tree's Subnet or a distinct
Subnet without changing any authority relationship.

The 0.99 `fleet_root_pid` field is likewise transitional one-Tree
terminology. During 0.100 activation, ordinary managed Canisters hard-cut that
relationship to `tree_root_pid`, identifying their exact Tree Root.
The separate Coordinator principal comes only from
`FleetCoordinatorBinding`. No `authority_root`, `member_root` or root-of-roots
identity is introduced, and no compatibility field preserves
`fleet_root_pid` after the coordinated 0.100 activation.

## Existing Authority Preserved

0.100 introduces a global authority without replacing local subnet authority.

| State | Authority | Meaning |
| --- | --- | --- |
| Tree-local registry | Tree Root | Canisters, roles and topology for one Canister Tree |
| Fleet Registry | Separately placed Fleet Coordinator | Tree Group definitions plus managed Canister Trees, their roots and lifecycle |

The exact existing type may no longer be named `SubnetState`. Implementation
must locate and reuse the current canonical local topology and cascade
authorities.

The two state families must remain semantically distinct:

- local topology changes are owned by the Tree Root;
- Fleet Tree lifecycle changes are owned only by the Fleet Coordinator;
- a Tree Root may mirror the Registry but may not mutate it; and
- an ordinary Canister may consume the Fleet Directory projection but may not
  synchronize topology directly with the Fleet Coordinator.

Physical co-location does not merge logical ownership. Any number of bounded,
explicitly planned Trees and the Fleet Coordinator may occupy the same
physical Subnet while owning disjoint state and Canister sets. “One root per
Canister Tree” refers to that Tree's root; it does not count the Coordinator
or another co-located Tree Root. 0.100 neither transfers existing local
registry rows to the Coordinator nor creates application-service rows in a
Coordinator-owned scope.

### Fleet Registry Access Contract

0.100 creates the first `canic_fleet_registry` boundary. It derives the
genesis row from the immutable 0.99 `FleetBinding`, the qualified
`OneTreeFleetSeed` and the surviving root-owned local `SubnetRegistry`.
0.99 exposes no Fleet Registry, Registry writer or Registry endpoint to
supersede:

- on the Fleet Coordinator, controller-gated `canic_fleet_registry` is the
  complete administrative/read projection of the authoritative Registry;
- Tree Roots expose their complete copy only as a controller-gated
  `canic_fleet_registry_mirror` diagnostic/backup projection, never as
  canonical authority;
- authenticated root synchronization uses the bounded
  `canic_fleet_registry_head` and `canic_fleet_registry_snapshot` endpoints;
- ordinary Canisters and public topology consumers receive only
  `FleetDirectory`; and
- Coordinator backup captures the binding, manifest, complete immutable
  snapshot and protected removed-tree qualification evidence, but a backup
  file or restored mirror does not acquire mutation authority.

Host access, controller visibility and backup possession are read/recovery
capabilities; none make the host, a mirror or a backup the canonical writer.
Same-epoch restore of Coordinator mutation authority is constrained separately
below.

## Authority Subnet Selection and Installation

0.100 introduces and resolves the Authority Subnet selector:

~~~rust
pub enum AuthoritySubnetSelector {
    Recommended,
    Profile(SubnetProfileId),
    Explicit(SubnetId),
}

pub struct FleetCoordinatorBinding {
    pub fleet: FleetBinding,
    pub authority_subnet: SubnetId,
    pub coordinator: Principal,
}
~~~

The selector is host deployment input for a fresh Fleet. `canic.toml` does not
choose the Authority Subnet, and runtime code never interprets a profile name.
For fresh installation, `canic deploy plan` exposes mutually exclusive
`--authority-subnet-profile <profile>` and
`--authority-subnet <principal>` options. Omitting both produces
`Recommended`.

The placement policy is:

| Fleet path | Authority Subnet rule |
| --- | --- |
| Fresh public-IC live Fleet | Resolve `Recommended` to the current network `fiduciary` profile |
| Fresh Fleet on another live network | Resolve its configured recommended authority profile or fail planning |
| Fresh PocketIC/local/test Fleet | Use the Authority Subnet supplied by the harness |
| Fresh Fleet with developer override | Resolve the exact named profile or explicit `SubnetId` |
| Existing 0.99 Fleet | Use the sole existing Tree's physical `SubnetId` as independently observed by 0.100; reject profile and explicit overrides |
| Later relocation | Outside 0.100; requires an epoch-advancing recovery design |

The Fiduciary subnet is suitable as the recommended live placement because it
is an application subnet open to user Canister creation and uses a larger
committee than standard application subnets. The stronger fault threshold is
valuable for small, authoritative Fleet metadata. Its higher cycle multiplier
is an explicit tradeoff for a fresh Fleet's Coordinator, not for ordinary
workloads. The Fiduciary Subnet does not give a Canister special system
privileges, free execution or a second writer. Coordinator authority still
comes from the protected `FleetCoordinatorBinding` and single-writer protocol.

Named profiles are open network metadata, not a protocol enum. The public IC
currently documents Fiduciary and European choices; a Swiss or other future
profile becomes selectable only when the chosen network's trusted metadata
actually advertises an eligible Subnet. The design does not reserve or
hard-code speculative names.

The fresh-Fleet installation workflow:

1. Resolve `Recommended`, `Profile` or `Explicit` against trusted metadata
   for the exact `CanonicalNetworkId`.
2. Verify as a best-effort preflight that the resolved Subnet exists, accepts
   arbitrary user Canister creation and currently appears usable.
3. Persist the selector, exact resolved `SubnetId`, metadata evidence and
   resolution time in the deployment plan.
4. Create the Fleet Coordinator explicitly on that Subnet. The management
   Canister result is the authoritative capacity and eligibility outcome;
   planning metadata is not a capacity proof.
5. Install it with the immutable `FleetBinding`, authority Subnet and initial
   authority epoch.
6. Persist `FleetCoordinatorBinding` in the host receipt, Coordinator and
   every Tree Root's protected bootstrap state.

An unavailable, ineligible or ambiguous recommended target fails planning. A
creation rejection fails installation with the exact typed platform cause.
Canic never silently selects a random application Subnet. The developer can
rerun fresh planning with a named profile or explicit Subnet. System subnets
are ineligible because they do not accept arbitrary user Canister creation.

Changing deployment configuration after installation cannot move or replace
the authority. Authority relocation must fence old history by advancing the
authority epoch through a later explicit recovery design.

## Existing-Fleet Seed

0.100 consumes one exact seed from the qualified 0.99 one-root state:

~~~rust
pub struct OneTreeFleetSeed {
    pub fleet: FleetBinding,
    pub tree_root: Principal,
    pub local_registry_content_hash: [u8; 32],
}

pub struct ExistingTreePlacement {
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub subnet: SubnetId,
    pub tree_root: Principal,
}
~~~

The 0.99 root and completed fresh-install receipt agree on the Fleet and sole
current root; the upgraded root recomputes and verifies the local Registry
hash. 0.99 does not persist a physical IC `SubnetId`, `TreeId`, `TreeGroupId`
or `TreeSpecId`, so its receipt is not required to attest values it does not
own.

The pre-upgrade seed is obtained only from 0.99-compatible evidence: the exact
Active `canic_fleet_activation_status` binding, the current `canic_env`
root facts, the unchanged `canic_subnet_registry` projection and the completed
`FleetInstallActivationJournal` plus Fleet catalog receipt. No new endpoint is
assumed to exist on an older Wasm.

Before mutation, the 0.100 host/harness:

1. compiles installed `subnets.default` into the first `TreeSpecId` and exact
   `spec_hash`;
2. emits `TreeSpecId("default")` and `TreeGroupId("default")`, then allocates
   and journals the first random `TreeId`;
3. resolves the root's physical `SubnetId` through trusted network/harness
   observation, independently of the 0.99 receipt;
4. requires a second observation to agree before Coordinator creation; and
5. journals the complete `ExistingTreePlacement` and local Registry hash.

The observed Subnet becomes the Authority Subnet for this extraction. The
Coordinator is then created through the root's same-Subnet creation authority,
and a final observation after handoff must still agree. Missing, ambiguous,
changed or untrusted placement evidence blocks extraction. An existing-Fleet
override is rejected. This preserves the placement needed for 0.101 adoption
without pretending that 0.99 already stored physical Subnet identity.

## 0.99-to-0.100 Coordinator Handoff

The sole 0.99 root begins as the authority for its immutable one-Tree seed
and local Registry facts. It has no Fleet Registry and cannot mutate Fleet
Tree lifecycle. 0.100 consumes and permanently fences that seed-attestation
authority while creating Fleet topology authority in the separately
installed Coordinator through one durable handoff:

~~~text
LegacyActive
  → CoordinatorPrepared
  → SourceQuiesced
  → SourceFenced
  → CoordinatorCommitted
  → MirrorActivated
~~~

These are durable workflow states, not inferred host observations:

- `CoordinatorPrepared` binds the exact seed, Coordinator principal, Authority
  Subnet, authority epoch and Fleet-scoped trust bootstrap. It exposes neither
  a current Registry manifest nor mutation authority.
- `SourceQuiesced` records that the old root has stopped seed attestation and
  Tree-topology publication while retaining authority to write its final
  fence. It does not reinterpret or move retained local Registry services.
- `SourceFenced` is persisted by the old root before acknowledgement. It binds
  a unique handoff ID, seed hash, Coordinator principal and epoch. Once
  persisted, the old seed-attestation authority can never be re-enabled at
  that epoch.
- `CoordinatorCommitted` requires authenticated source-fence evidence from the
  exact old root. Only then may the Coordinator publish the genesis Registry
  manifest and accept Tree lifecycle mutation.
- `MirrorActivated` records that the former source root has activated the
  exact committed Registry as its mirror and completed the Tree-topology
  cascade.

The irreversible fence evidence is:

~~~rust
pub struct SourceFenceEvidence {
    pub handoff_id: [u8; 32],
    pub fleet: FleetBinding,
    pub source_root: Principal,
    pub coordinator: FleetCoordinatorBinding,
    pub authority_epoch: u64,
    pub seed_hash: [u8; 32],
}
~~~

After persisting `SourceFenced`, the source root calls the prepared
Coordinator's handoff-commit update endpoint itself. The Coordinator requires
`caller == source_root` and an exact match with its prepared handoff. A
host-relayed record without the authenticated source call is not fence
evidence. An unknown call outcome is retried by the fenced source with the
same handoff ID.

For an existing Fleet:

1. Validate and journal the exact `OneTreeFleetSeed`,
   `ExistingTreePlacement` and repeated trusted Subnet observation.
2. Create the Coordinator through the current root's same-Subnet creation
   workflow and record its principal before installation proceeds. Do not
   invoke the fresh-Fleet selector.
3. Install the Coordinator with the protected `FleetBinding`, genesis epoch,
   prepared one-Tree Registry and Fleet-scoped trust bootstrap. Verify
   `CoordinatorPrepared`.
4. Upgrade the existing root to the 0.100 handoff/mirror-capable Wasm with the
   exact seed and protected `FleetRegistryBootstrap`. The install atomically
   enters `SourceQuiesced`, preserves the local `SubnetRegistry`, exposes no
   Fleet Registry writer or active mirror and stops seed attestation/Tree
   topology publication.
5. Persist `SourceFenced` in the old root and deliver its authenticated fence
   evidence to the prepared Coordinator.
6. Verify the exact fence evidence and commit the genesis Registry containing
   the existing Tree as `Active`; publish its first current manifest.
7. Activate `FleetRegistryMirror` in the already upgraded root from the exact
   committed manifest; it never gains canonical Registry mutation.
8. Pull the exact committed snapshot, cascade Tree topology locally, persist
   `MirrorActivated`, verify the Coordinator, mirror and host receipt agree,
   verify that the bound local Registry content hash and rows are unchanged,
   re-observe the root and Coordinator on the exact Authority Subnet, and then
   remove quiescence.

The current root's temporary authority to attest the exact one-Tree seed
disappears after `SourceFenced`; installing the 0.100 source-handoff state is
not itself fence evidence. While `SourceQuiesced` it exposes only transition
diagnostics and the authenticated fence operation. After `MirrorActivated` it
exposes only `canic_fleet_registry_mirror`. The new Fleet Coordinator creates
and exclusively exposes the first current `canic_fleet_registry` authority.

The host journal coordinates retries but is not an authority. Before
`SourceFenced`, recovery may abandon the prepared Coordinator and retain the
seed-attestation authority through an explicit rollback inside the already
installed 0.100 root Wasm. That rollback proves the exact seed/local Registry,
re-enters `LegacyActive` behavior and abandons the prepared Coordinator; it
does not reinstall 0.99, decode an old schema or expose a compatibility path.
After `SourceFenced`, rollback is forbidden: recovery must resume preparation
or commitment of the same Coordinator principal. An availability gap is
acceptable; overlapping seed-attestation and Registry-mutation authorities are
not. Unknown create, install, fence-delivery or commit outcomes are reconciled
by exact handoff-ID status reads and idempotent retries, never by creating a
replacement Coordinator.

Fresh 0.100 deployment installs the Fleet Coordinator first, commits a
Tree-empty genesis Registry containing the exact Tree Groups and then joins
Canister Trees through the normal `Joining` lifecycle.

## Goals

0.100 must provide:

1. One authoritative Fleet Registry of declared Tree Groups and managed
   Canister Trees.
2. A stable `TreeId` and unique Tree Root for each managed Canister Tree,
   independent of physical placement.
3. A separately placed Fleet Coordinator with a protected Authority Subnet and
   Canister binding.
4. App-declared Tree Specs and heterogeneous Tree Groups with bounded
   horizontal scaling.
5. Exact Tree, group, spec and spec-hash binding for every lifecycle.
6. Explicit registration, activation, draining and removal lifecycles.
7. Durable synchronization from the Fleet Coordinator to every Canister Tree
   Root.
8. Atomic activation of complete Registry snapshots.
9. Same-subnet propagation through the existing root cascade.
10. Local APIs for inspecting authority, group, Tree and placement topology.
11. Fleet-bound provenance and freshness information.
12. Failure-safe operation while the Fleet Coordinator is temporarily
    unavailable.
13. A bounded inter-subnet control-plane call pattern.
14. Durable qualified final inventory and root-local fencing for ordinary
    Tree removal, with explicit unqualified evidence for emergency removal.

## Core Invariants

The implementation must preserve these invariants:

1. For each Fleet and authority epoch, exactly one committed authority
   descriptor value identifies the Authority Subnet and Fleet Coordinator.
2. Every protected or published copy for that Fleet and epoch agrees exactly
   with the committed descriptor value and immutable `FleetBinding`.
3. Every snapshot, manifest, version, acknowledgement, mirror record,
   projection and hash preimage binds the same `FleetBinding`.
4. The Authority Subnet is Coordinator placement, not an ordinary
   `FleetTreeEntry`; its binding cannot be joined, drained or removed through
   the Tree lifecycle. Trees placed on that same physical Subnet remain
   ordinary independent entries.
5. Every Registry contains the exact canonical Tree Group definitions
   compiled for that Fleet, and every Tree references one present group and
   repeats its exact protected Tree Spec hash.
6. Different groups may use different Tree Specs; Trees of one group share
   the spec but not their concrete local inventory or data.
7. Every `TreeId` appears exactly once among retained Registry entries.
   `SubnetId` may repeat across entries and is never a uniqueness key.
8. Every Tree Root principal appears in at most one retained Tree
   row, including `Removed`; root-principal reuse requires a later explicit
   tombstone-compaction design. Every ordinary managed Canister has one exact
   protected Tree/Tree-Root binding; co-located roots cannot cascade into or
   mutate each other's local registries.
9. Only the Fleet Coordinator can commit a new Registry revision.
10. Registry revisions increase monotonically within an authority epoch.
11. A revision identifies exactly one canonical content hash within one
   `FleetBinding` and authority epoch.
12. Evidence from another network, Fleet or App never compares equal or
    activates, even when epoch, revision and entries match.
13. A mirror never activates a partial or unverified snapshot.
14. A mirror never replaces a newer Registry with an older one.
15. A mirror never promotes itself because the Fleet Coordinator is
    unreachable.
16. Ordinary Canisters never need an inter-Subnet call to read Fleet Directory
    state.
17. `Joining`, `Draining` and `Removed` Trees are not treated as normal
    active placement targets.
18. Group eligibility is enforced before Canic-managed creation, attachment
    or placement; application routing remains application-owned.
19. Registry removal does not falsely claim that the removed root Canister
    has been stopped or deleted.
20. Co-location never changes authority: a Tree on the Authority Subnet is
    still governed by its Tree Root, and a Coordinator on a Tree's Subnet does
    not govern that Tree's local Registry.
21. At steady state, every registry-managed Canister has exactly one committed
    registry owner. A future epoch-bound movement handoff may stage source and
    destination records, but two registries are never committed owners for the
    same ownership epoch.
22. Every `Removed` Tree has exactly one Coordinator-retained
    `Qualified` or `Unqualified` removal record; absence is invalid.
23. A qualified removal binds the exact authority, Tree, group and spec hash,
    Fleet Registry version, final local Registry hash, complete
    bounded inventory and authenticated root-local fence.
24. An unqualified removal never implies an empty Tree and cannot be used as
    duplicate-absence evidence.
25. A persisted removed-tree fence never permits Canic-managed creation,
    attachment, placement or local-registry mutation to resume at the same
    authority epoch.
26. `authority_services` is present in every current Registry snapshot and is
    empty throughout 0.100.
27. A `[services.fleet]` role is absent from every fresh Tree Spec.
    An already-installed 0.99 candidate may remain locally only as
    adoption-only evidence and cannot be created or replicated into another
    Tree.

## Data Model

~~~rust
pub struct FleetRegistry {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub tree_groups: Vec<FleetTreeGroup>,
    pub trees: Vec<FleetTreeEntry>,
    pub authority_services: Vec<FleetAuthorityServiceBinding>,
}

pub struct FleetRegistryAuthority {
    pub binding: FleetCoordinatorBinding,
    pub epoch: u64,
}

pub struct FleetTreeGroup {
    pub group: TreeGroupId,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub initial_trees: u16,
    pub maximum_trees: u16,
}

pub struct FleetTreeEntry {
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub spec_hash: [u8; 32],
    pub subnet: SubnetId,
    pub tree_root: Principal,
    pub status: ManagedTreeStatus,
}

pub enum ManagedTreeStatus {
    Joining,
    Active,
    Draining,
    Removed,
}

pub struct FleetAuthorityServiceBinding {
    pub role: CanisterRole,
    pub canister_id: Principal,
}
~~~

Tree Groups use ascending canonical `TreeGroupId`; Tree entries use ascending
canonical `TreeId`. Hashing, equality and publication never
depend on insertion order.

`TreeSpecId` and `TreeGroupId` are distinct bounded identities. The spec names
an App topology declaration; the group names a Fleet collection and references
one spec. Multiple groups may reference the same spec while retaining
different scaling policy. `TreeId` is allocated and durably journalled before
root creation. None is inferred from `SubnetId`, root principal or display
text.

`TreeSpecId` and `TreeGroupId` are non-empty canonical UTF-8 strings with the
current 64-byte identifier bound, but they are different concrete types and
never decode as `SubnetSlotId`. `TreeId` is exactly 32 cryptographically random
bytes, generated and durably journalled before creation and collision-checked
within the Fleet. Its complete logical identity is `(FleetKey, TreeId)`.

`spec_hash` covers the canonical Tree Spec declaration:
allowed Tree-local role/package identities, local topology and creation
policies and binding-relevant configuration. Tree Group identity and
`initial_trees`/`maximum_trees` belong to the group declaration and its
Registry row, not the Tree Spec hash. Selected `[services.fleet]` roles are
excluded. The hash does not cover concrete Canister principals, local Registry
rows, preserved adoption-only candidates, shard assignments, application data
or physical placement.

The host retains the bounded canonical declaration bytes and hashes:

~~~text
SHA-256(
  "canic:tree-spec\0"
  || u64_be(canonical_tree_spec_length)
  || exact_canonical_tree_spec_bytes
)
~~~

Those fixed-array bytes contain, in order, the `FleetBinding`,
`TreeSpecId` and existing canonical topology/config digest. A root receives
those exact bytes before installation,
independently reproduces the hash and persists them as protected group
configuration. The public Registry group row stores the spec identity, policy
counts and hash rather than duplicating the complete local App configuration.

`initial_trees` is the fresh-deployment target compiled into the group plan;
it does not promise perpetual availability. `maximum_trees` is the hard
admission limit for `Joining`, `Active` and `Draining` Trees of that group.
Both values must be nonzero, `initial_trees <= maximum_trees`, and the sum
of all group maxima must fit `MAX_MANAGED_TREES`. 0.100 performs explicit
registration and does not implement metric-driven automatic scaling.

Every Tree repeats the Tree Spec hash so its registration,
bootstrap, acknowledgement, removal evidence and consumer projection remain
self-binding. A missing group, wrong spec hash or group at its maximum fails
before a new `Joining` revision is committed.

`authority_services` is part of the sole current snapshot schema and canonical
encoding from the first 0.100 Registry. It is empty throughout 0.100.
`FleetAuthorityServiceBinding` intentionally stores only the service role and
principal: the exact `FleetBinding`, Coordinator, Authority Subnet and
authority epoch are stored once in `FleetRegistry.authority`. 0.101 may
populate the field only with a complete committed declared set; it does not
replace this type or add another Fleet binding to the public Registry.

The content hash is publication metadata rather than a self-referential field
inside the hashed Registry snapshot:

~~~rust
pub struct FleetRegistryManifest {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub byte_length: u64,
    pub content_hash: [u8; 32],
}
~~~

A complete Registry identity is therefore:

~~~rust
pub struct FleetRegistryVersion {
    pub authority: FleetRegistryAuthority,
    pub revision: u64,
    pub content_hash: [u8; 32],
}
~~~

The exact encoding and hash construction are frozen below. Otherwise identical
Registries for different Authority Subnets or Coordinators, canonical networks
or Fleets of the same App produce different evidence. Two environment profiles
that resolve to the same canonical public IC network do not create different
Registry evidence merely because their labels differ.

## Authority Epoch

The authority epoch fences Registry history belonging to different Fleet
Coordinators within one immutable `FleetBinding`.

0.100 records the epoch but does not implement automatic authority relocation
or replacement.

Every Tree Root is provisioned with a protected bootstrap descriptor:

~~~rust
pub struct FleetRegistryBootstrap {
    pub authority: FleetRegistryAuthority,
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub placement_subnet: SubnetId,
    pub tree_root: Principal,
}
~~~

A mirror accepts snapshots only from the configured Fleet Coordinator
and only for the configured authority descriptor and exact protected
`FleetBinding`.

Within 0.100:

- a lower epoch is rejected as stale;
- a different Authority Subnet or Coordinator at the same epoch is rejected;
- an unexpected higher epoch is rejected pending an explicit recovery operation;
- no root derives authority from availability or majority; and
- no mirror can promote itself.

A later design may define a protected authority-relocation workflow that
advances the epoch. Merely including the epoch in 0.100 avoids publishing an
unfenceable format.

## Same-Epoch Restore and Rollback

A matching `FleetBinding`, Coordinator principal and authority epoch do not
prove that a restored Coordinator snapshot is current. Reactivating revision 8
after any Tree observed revision 12 could fork or reuse committed history.

0.100 therefore permits a Coordinator backup to restore only read-only
diagnostic and recovery state. It does not reactivate Registry mutation
authority at the same epoch. Same-epoch reactivation would require independent
proof that the restored `FleetRegistryVersion` equals the latest committed
version; 0.100 defines no such proof authority.

When latest-version equality cannot be proven, restore remains fenced and
fails closed pending a later epoch-advancing recovery procedure. A Tree
mirror, host journal, controller assertion or offline backup is not sufficient
on its own. Ordinary canister upgrade with intact monotonic stable state is not
treated as backup restoration.

## Bootstrap Truth

Configuration provides only the minimum facts needed to join the Fleet:

- the immutable Fleet binding;
- the exact Tree, Tree Group and Tree Spec identities;
- the protected Tree Spec hash;
- the expected physical placement Subnet;
- the expected Tree Root principal;
- the Authority Subnet;
- the Fleet Coordinator principal; and
- the expected authority epoch.

It must not contain a second complete list of managed Trees.

These facts are deployment/install input persisted in protected host and root
state. The Tree Spec, group and hash originate in the host's canonical
compilation of `canic.toml`, but a root never reparses that file or treats it
as runtime authority. The runtime `FleetRegistry` becomes the only authority
for Fleet Tree lifecycle and canonical group definitions.

Canic must not claim it has cryptographically discovered which subnet hosts a
root if the Internet Computer does not expose that fact to the canister. The
`(tree, subnet, tree_root)` relationship comes from the trusted
deployment/harness placement authority and is verified as far as the platform
permits. Tree identity never derives from placement.

## Tree Group Configuration and Deployment

0.100 hard-cuts App topology configuration to explicit Tree Spec and Tree
Group namespaces:

~~~toml
[tree_specs.user]

[tree_specs.user.canisters.root]
kind = "root"

[tree_specs.user.canisters.user_hub]
kind = "service"

[tree_specs.user.canisters.user_shard]
kind = "shard"

[tree_specs.project]

[tree_specs.project.canisters.root]
kind = "root"

[tree_specs.project.canisters.project_instance]
kind = "instance"

[tree_specs.project.canisters.project_asset]
kind = "instance"

[tree_specs.project.canisters.project_ledger]
kind = "instance"

[tree_groups.users]
tree_spec = "user"
initial_trees = 1
maximum_trees = 1

[tree_groups.projects]
tree_spec = "project"
initial_trees = 20
maximum_trees = 150
~~~

`tree_specs.<id>` declares the permitted local shape.
`tree_groups.<id>` gives a Fleet collection its own identity, references one
Tree Spec and declares initial/maximum Tree counts. Configuration does not
contain physical `SubnetId`s, `TreeId`s, Tree Root principals or concrete
application routing bindings. Multiple groups may reference one spec.

Every Tree Spec declares exactly one `root` topology role. The global
`[roles.root]` declaration remains the single package authority, while each
concrete Tree instantiates one Tree Root from it. 0.100
therefore hard-cuts the 0.99 “exactly one root attachment globally” validation
to “exactly one root attachment per Tree Spec and one concrete Tree Root per
Canister Tree.” The root is Tree infrastructure, not an application routing
target, and its binding-relevant spec configuration is covered by the Tree
Spec hash.

Fresh 0.100 configuration requires at least one Tree Spec and one Tree Group,
but neither must be named `default`. If `default` is declared, it remains only
the application's fallback workload topology/group. Existing 0.99 extraction
compiles installed `subnets.default` into the initial Tree Spec and Tree Group.
Neither rule selects the Authority Subnet.

The 0.100 config hard cut also separates Fleet-authoritative roles from Tree
Specs. A role selected by `[services.fleet]` remains globally
package-declared but is rejected under
`[tree_specs.<id>.canisters.<role>]` for a fresh 0.100 Fleet. Fresh Trees
therefore cannot auto-create a service that 0.101 must provision on the
Authority Subnet. Existing 0.99 extraction preserves any already-installed
selected-role row and Canister as an adoption-only candidate, but excludes
that role from the compiled Tree Spec and fences new Tree-local
creation or replication. 0.101 either adopts that exact qualified candidate
when it is co-located with the Authority Subnet or provisions the missing
service there.

Fresh deployment planning:

1. Canonically compile every Tree Spec, spec hash and Tree Group.
2. Validate nonzero initial/maximum counts, unique Tree Spec and group keys,
   exact group-to-spec references, role eligibility and aggregate bounds.
3. Allocate and journal one stable `TreeId` for each planned Tree.
4. Resolve one physical `SubnetId` for each Tree from explicit deployment
   input or a trusted harness/network placement authority. Subnet IDs may
   repeat across Trees and may equal the Authority Subnet.
5. Journal every `(TreeId, TreeGroupId, TreeSpecId, spec hash, SubnetId,
   expected Tree Root principal)` before root creation or installation.
6. Create each Tree Root explicitly on its recorded Subnet and install it with
   the exact protected `FleetRegistryBootstrap` and Tree Spec.
7. Register and activate every Tree through the normal group-bound
   `Joining` lifecycle.
8. Qualify fresh deployment only after every planned initial Tree is `Active`
   with the exact Tree/group/spec/root/placement binding.

For public-IC live deployment, Canic does not invent a health-based or random
Tree selector. The operator or a separately qualified network placement
authority supplies the exact Tree targets. Co-location is an ordinary explicit
placement result, not an exception: a one-Subnet harness can qualify several
independent Trees and Tree Groups, while a multi-Subnet harness additionally
qualifies cross-Subnet synchronization and distinct placement.

Co-location is useful for local/PocketIC qualification, small low-utilization
Trees, phased rollout and existing-Fleet extraction. It is not horizontal
capacity or fault isolation. A live deployment plan must show every repeated
`SubnetId` explicitly and report that the affected Trees share capacity and
Subnet failure; Canic never co-locates them silently.

After initial deployment, scaling is explicit. An authorized registration may
add another Tree to a group below `maximum_trees`; removal follows the
normal lifecycle. 0.100 does not monitor application capacity, choose a group
from traffic, create Trees automatically or define application routing.
In this example the `users` group is deliberately pinned to one Tree even if
that Subnet approaches capacity, while the `projects` group can grow from
twenty to 150. A project Tree is never substituted for the full user Tree.

The canonical Tree Spec and group sets, each spec hash and each maximum are
immutable after genesis in 0.100. Adding a group, changing its local topology
template or raising its maximum is an App/Fleet deployment evolution that must
be designed with the same release, root-upgrade and recovery evidence; it is
not smuggled through ordinary Tree registration. Removing a group is
likewise outside 0.100.

The Coordinator stores only the canonical compiled group definitions and live
Tree lifecycle. It does not duplicate every Tree's local Registry. Each Tree
Root validates Canic-managed creation and attachment against its protected
Tree Spec, so a `project_instance` cannot be created in a `users` Tree merely
because both belong to the same Fleet or share a physical Subnet.

## Fleet Coordinator Registry Publication

The Fleet Coordinator stores the authoritative Fleet Registry as an immutable,
revisioned snapshot. It does not own any Tree's local Canister registry and
0.100 transfers no local Canister rows to it.

A Registry mutation must:

1. Load the current canonical Registry.
2. Validate the requested transition.
3. Construct the complete next snapshot.
4. Serialize it deterministically.
5. Enforce entry-count and byte-size limits.
6. Calculate its content hash.
7. Durably store the complete snapshot.
8. Atomically make its manifest current.

`canic_fleet_registry_head` must never expose a manifest whose snapshot is
absent or incomplete.

~~~rust
async fn canic_fleet_registry_head(
) -> Result<FleetRegistryManifest, FleetRegistryError>;

async fn canic_fleet_registry_snapshot(
    version: FleetRegistryVersion,
) -> Result<Vec<u8>, FleetRegistryError>;
~~~

Both synchronization endpoints are authenticated inter-Canister **update**
calls. They are logically read-only, but 0.100 does not use query or composite
query transport for cross-Subnet synchronization.

## Canonical Snapshot Protocol

0.100 uses complete Registry snapshots, not deltas or an event log.

The protocol constants are:

~~~rust
const GENESIS_AUTHORITY_EPOCH: u64 = 1;
const GENESIS_REGISTRY_REVISION: u64 = 1;
const MAX_TREE_GROUPS: usize = 64;
const MAX_TREE_SPEC_BYTES: usize = 65_536;
const MAX_MANAGED_TREES: usize = 256;
const MAX_FLEET_REGISTRY_SNAPSHOT_BYTES: usize = 131_072;
const MAX_REMOVED_TREE_INVENTORY_ENTRIES: usize = 4_096;
const MAX_REMOVED_TREE_INVENTORY_BYTES: usize = 1_048_576;

const MIN_POLL_INTERVAL_SECONDS: u64 = 60;
const DEFAULT_POLL_INTERVAL_SECONDS: u64 = 300;
const MAX_POLL_INTERVAL_SECONDS: u64 = 3_600;
const INITIAL_RETRY_BACKOFF_SECONDS: u64 = 15;
const MAX_RETRY_BACKOFF_SECONDS: u64 = 900;
const MAX_SUPERSEDED_RETRIES_PER_PASS: u8 = 3;
~~~

The genesis Registry is revision 1 in authority epoch 1. For a fresh Fleet it
contains every compiled Tree Group and no Tree rows before planned roots
join. After a successful 0.99 extraction it contains the canonical `default`
group and the sole existing Tree as `Active`. `authority_services` is empty
on both paths. Revision increment uses checked arithmetic. An attempt to
advance `u64::MAX` fails before mutation with
`RevisionExhausted`; it never wraps, resets or silently advances the epoch.

Snapshot bytes use deterministic CBOR under RFC 8949 deterministic-encoding
rules. Records are encoded as fixed arrays in the field order shown in this
document; integers use their shortest form; principals and digests are byte
strings; vectors are definite-length; and maps, text keys, floats and
indefinite-length items are forbidden. `ManagedTreeStatus` encodes as the
unsigned values `0 = Joining`, `1 = Active`, `2 = Draining` and `3 = Removed`.
Identity types retained from 0.99 use their frozen raw byte representations;
`TreeId` uses its exact 32 bytes, and `TreeSpecId`/`TreeGroupId` use their
exact canonical UTF-8 bytes. No identity encodes through display text. Tree
Groups are sorted by canonical raw
`TreeGroupId` bytes before encoding. Trees are sorted by canonical raw
`TreeId` bytes before encoding. Authority-service bindings are sorted by
canonical raw role bytes before encoding; 0.100 rejects a non-empty vector
because service activation belongs to 0.101. `MAX_TREE_GROUPS` counts every
canonical group definition. The Tree-Spec byte limit applies independently to
each protected canonical Tree Spec before its hash is admitted.
`MAX_MANAGED_TREES` counts every retained Tree row, including `Removed`
tombstones.

The hash is calculated over the exact bytes returned by
`canic_fleet_registry_snapshot`, not over a separately reconstructed logical
preimage:

~~~text
SHA-256(
  "canic:fleet-registry\0"
  || u64_be(snapshot_byte_length)
  || exact_canonical_snapshot_bytes
)
~~~

The snapshot bytes themselves contain the complete authority descriptor,
revision, Tree Group vector, Tree vector and authority-service vector. A
mutation exceeding an applicable count or byte bound fails before
authoritative state changes.

Chunk transfer is excluded from 0.100. If a Fleet Registry ever becomes too
large for one bounded response, that should be justified by observed use
before adding a generic transfer protocol.

### Snapshot Retention and Head Races

The Coordinator retains only:

- the current committed snapshot and manifest; and
- one non-public staging slot needed to replace them durably.

After a new manifest commits, the previous snapshot is no longer retrievable
and its storage is reclaimed. `canic_fleet_registry_snapshot(version)` returns
typed `VersionSuperseded` unless `version` exactly equals the current
`FleetRegistryVersion`. A root receiving that result restarts from the head
request. One synchronization pass follows at most
`MAX_SUPERSEDED_RETRIES_PER_PASS` such races before recording a retryable
failure and entering bounded backoff.

A join acknowledgement must normally reference the current committed version.
If the Registry advanced first, the Coordinator returns `RegistryAdvanced`
and the joining root synchronizes again. The idempotent exception is a
repeated acknowledgement after that exact root is already recorded as
`Active`; it returns the existing committed Active result even when the
original acknowledgement response was lost.

## Mirror Synchronization

Every Tree Root owns one durable synchronization state:

~~~rust
pub struct FleetRegistryMirrorState {
    pub authority: FleetRegistryAuthority,
    pub active: Option<FleetRegistryVersion>,
    pub last_polled_at: Option<Timestamp>,
    pub last_confirmed_current_at: Option<Timestamp>,
    pub synchronized_at: Option<Timestamp>,
    pub consecutive_failures: u32,
    pub next_poll_at: Option<Timestamp>,
    pub last_failure: Option<FleetRegistrySyncFailure>,
}
~~~

A timer-driven synchronization pass performs:

1. Record the polling attempt and call the configured Fleet Coordinator for
   `canic_fleet_registry_head`.
2. Validate the full Fleet binding and authority descriptor.
3. If the exact version is already active, durably set
   `last_confirmed_current_at`, clear the last failure, reset retry backoff and
   return without cascading.
4. Reject an older epoch or revision.
5. Reject the same epoch and revision with a different hash.
6. Fetch the complete snapshot when behind.
7. On `VersionSuperseded`, restart from the bounded head step.
8. Verify its exact length and hash before decoding.
9. Decode and validate every Registry invariant.
10. Durably stage the snapshot.
11. Atomically activate the mirror and derived Fleet Directory, setting both
    `synchronized_at` and `last_confirmed_current_at`.
12. Enqueue or resume the existing same-subnet Tree-topology cascade.
13. Clear failure state, reset backoff and record synchronization success.

Revision gaps are permitted because every publication is a complete snapshot.
A mirror can move directly from revision 4 to revision 12.

Polling configuration is clamped to the constants above. Retry backoff doubles
from the initial value to the maximum and resets after either a confirmed
current head or snapshot activation. There is one polling actor per Tree Root,
not one per ordinary Canister. Durable timers and work resume through the
existing Canic machinery.

## Interruption and Uncertain Outcomes

All inter-subnet synchronization calls in 0.100 are observational and safe to repeat.

Local activation and cascade must also be idempotent.

If interruption occurs:

- before snapshot activation, the previous Registry remains active;
- after activation but before the success receipt, restart detects the
  already-active `FleetRegistryVersion`;
- during local cascade, the active root Registry remains valid and cascade
  resumes through its existing durable progress; and
- after receiving a response whose local receipt was not persisted, the root
  repeats the head or snapshot request.

No pending state may be reset merely because the previous process tree became quiescent.

## Canister Tree Registration

Registration is Fleet-Coordinator-authorized and phased.

~~~text
Absent → Joining → Active → Draining → Removed
             └──────────────────────→ Removed
~~~

### Create Joining Entry

An authorized Fleet administrator registers:

- one new stable `TreeId`;
- its Tree Group and exact Tree Spec hash;
- its physical placement `SubnetId`; and
- its expected Tree Root principal;

The Fleet Coordinator validates Tree/root uniqueness, group existence, exact
spec-hash equality and group Tree capacity before publishing a new Registry
revision with the entry in `Joining`. It does not require `SubnetId`
uniqueness.

A `Joining` Tree:

- is visible for bootstrap and diagnostics;
- is not returned by normal `active_trees`;
- is not eligible for placement; and
- cannot be treated as a service destination.

### Join Acknowledgement

The joining root:

- starts with its protected bootstrap descriptor;
- pulls the authoritative Fleet Registry;
- verifies that it contains its expected
  `(tree, group, spec_hash, subnet, tree_root)` entry;
- verifies that its locally installed canonical Tree Spec hashes to
  the same value;
- activates that snapshot locally; and
- calls the Fleet Coordinator with an idempotent join acknowledgement.

~~~rust
async fn acknowledge_tree_join(
    applied: FleetRegistryVersion,
) -> Result<JoinStatus, FleetRegistryError>;
~~~

The Fleet Coordinator verifies:

- the caller is the Tree Root principal recorded in the `Joining`
  entry;
- the acknowledged Fleet binding exactly matches protected authority state;
- the acknowledged group and spec hash match the `Joining` entry and
  canonical Registry group;
- the reported authority epoch matches;
- the acknowledged revision and hash were published by the Fleet Coordinator;
  and
- the acknowledged snapshot contained that joining entry.

A valid acknowledgement transitions the Tree to `Active` and publishes the
next revision.

Repeating an acknowledgement after activation returns the existing active result.

### Cancel Failed Join

An authorized Fleet administrator may transition `Joining → Removed` when a
join cannot complete. Cancellation publishes a new Registry revision and
retains the normal removed tombstone. It does not delete, stop or repurpose the
root Canister. A live joining root follows the normal final-inventory and
root-local-fence qualification below. If the root never became callable or an
emergency cancellation cannot obtain that evidence, the Coordinator records
the tombstone as removal-unqualified rather than inventing an empty Tree.
Reusing that `TreeId` remains outside 0.100; its `SubnetId` was never reserved
to this Tree.

### Synchronization Caller Access

The Coordinator authenticates `canic_fleet_registry_head` and
`canic_fleet_registry_snapshot` by caller principal and current Registry
status:

- the root recorded for a `Joining`, `Active` or `Draining` Tree may
  synchronize;
- a `Removed` root, an unknown caller and a principal recorded for another
  Tree are rejected;
- a controller does not gain synchronization access merely by being a
  controller; and
- controller-gated administrative Registry reads remain a separate recovery
  capability.

## Draining and Removal

Removal is also phased:

~~~text
Active → Draining → Removed
~~~

### Draining

Draining means:

- do not choose the Tree for new placement;
- retain it for explicit lookup and evacuation;
- retain its root identity; and
- allow existing workloads to be managed according to their domain policy.

The Registry does not decide when application evacuation has finished. An
authorized administrative action starts removal qualification. The normal
transition to `Removed` commits only after the Coordinator retains the
authenticated final inventory and fence evidence described below; emergency
removal records an explicit unqualified tombstone.

### Removed

Removed means:

- exclude the Tree from normal active resolution;
- reject it as a new placement target;
- preserve a tombstone preventing stale state from looking like a new
  registration; and
- reject Fleet-management authority from that root where Registry lifecycle
  access is required.

A removed entry is not immediately deleted from the Registry.

0.100 does not permit reusing a removed `TreeId` as a fresh
registration. Replacement or tombstone compaction requires a later explicit
design.

Registry removal does not stop the root Canister, change controllers or erase
local state. Those are deployment operations outside the Registry. A removed
but still-running root may retain stale local knowledge, but active Fleet
Trees no longer recognize it as active.

Every Canister Tree, including one physically co-located with the Authority
Subnet, follows the same lifecycle and may be drained or removed. Removing a
co-located Tree entry does not move the Fleet Coordinator or remove the
Authority Subnet from the Fleet descriptor. Coordinator relocation is a
separate operation outside 0.100.

### Removed-Tree Qualification

Removal must not erase the evidence later needed to prove that no possibly
live managed Canister conflicts with a Fleet-authoritative service.

Before an ordinary `Joining`, `Active` or `Draining` Tree becomes
`Removed`, the Coordinator requests one final inventory at an exact current
Fleet Registry version. The Tree Root atomically:

1. freezes Canic-managed creation, attachment, placement and local-registry
   mutation for that Tree and authority epoch;
2. exports its complete bounded committed local managed-Canister inventory;
3. persists the final local Registry content hash, canonical inventory bytes
   and inventory hash;
4. persists the removal fence before acknowledging it; and
5. calls the Coordinator's dedicated removal-qualification update endpoint
   itself.

The operational evidence shapes are:

~~~rust
pub struct RemovedTreeIdentity {
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub spec_hash: [u8; 32],
    pub subnet: SubnetId,
    pub tree_root: Principal,
}

pub struct FinalManagedCanisterRecord {
    pub canister_id: Principal,
    pub role: CanisterRole,
    pub disposition: FinalManagedCanisterDisposition,
}

pub enum FinalManagedCanisterDisposition {
    Managed,
    Released {
        ownership_epoch: u64,
        receipt_hash: [u8; 32],
    },
    Decommissioned {
        receipt_hash: [u8; 32],
    },
}

pub struct FinalTreeInventory {
    pub authority: FleetRegistryAuthority,
    pub tree: RemovedTreeIdentity,
    pub base_registry_version: FleetRegistryVersion,
    pub local_registry_content_hash: [u8; 32],
    pub canisters: Vec<FinalManagedCanisterRecord>,
}

pub struct RemovedTreeFence {
    pub authority: FleetRegistryAuthority,
    pub tree: RemovedTreeIdentity,
    pub removal_id: [u8; 32],
    pub base_registry_version: FleetRegistryVersion,
    pub local_registry_content_hash: [u8; 32],
    pub final_inventory_hash: [u8; 32],
}

pub struct RemovedTreeFenceReceipt {
    pub fence: RemovedTreeFence,
    pub fence_hash: [u8; 32],
    pub persisted_at: Timestamp,
}

pub enum RemovedTreeQualification {
    Qualified {
        inventory: FinalTreeInventory,
        fence_receipt: RemovedTreeFenceReceipt,
    },
    Unqualified {
        authority: FleetRegistryAuthority,
        tree: RemovedTreeIdentity,
        removal_id: [u8; 32],
        last_registry_version: FleetRegistryVersion,
        reason: RemovalUnqualifiedReason,
    },
}
~~~

`FinalTreeInventory.authority` is the one stored Fleet binding hierarchy;
the evidence does not add a second Fleet identity field. Its Tree identity,
Tree Group, Tree Spec hash, placement, Fleet Registry revision and local
Registry hash are exact. The canonical inventory includes every committed
local managed-Canister row, including released ownership tombstones. Any
record whose disposition is not `Decommissioned` identifies a Canister that
may still exist and must not be silently treated as absent.

The inventory is limited to
`MAX_REMOVED_TREE_INVENTORY_ENTRIES` records and
`MAX_REMOVED_TREE_INVENTORY_BYTES` deterministic-CBOR bytes. Records are
ordered by raw Canister principal bytes, then raw role bytes. The inventory
is a fixed array in `FinalTreeInventory` field order, every record is a
fixed array in `FinalManagedCanisterRecord` field order, and dispositions
encode as `0 = Managed`, `1 = Released` and `2 = Decommissioned`.
`Released` payload fields retain their shown order. The inventory hash is:

~~~text
SHA-256(
  "canic:removed-tree-inventory\0"
  || u64_be(inventory_byte_length)
  || exact_canonical_inventory_bytes
)
~~~

`removal_id` is 32 cryptographically random bytes generated and durably stored
by the Coordinator before it requests qualification. The root's canonical
fence bytes are a fixed array in `RemovedTreeFence` field order. Its
`fence_hash` is:

~~~text
SHA-256(
  "canic:removed-tree-fence\0"
  || u64_be(fence_byte_length)
  || exact_canonical_fence_bytes
)
~~~

The receipt is the fixed array `[fence, fence_hash, persisted_at]`. The root
persists that receipt before returning it through the authenticated
inter-Canister update call. The Coordinator records the authenticated caller,
exact receipt and inventory as one qualification; display projections or a
host assertion cannot substitute for those bytes.

For ordinary removal, the Coordinator accepts qualification only when `caller`
equals the exact recorded root, the Tree is still `Joining`, `Active` or
`Draining`, every authority/Tree/version/hash field matches and the
root-local fence receipt authenticates the same bytes. It durably stores the
complete qualified evidence before publishing the `Removed` Registry revision.
Once the root persists the fence, restart cannot re-enable Canic-managed
creation, attachment, placement or registry mutation at that authority epoch.
Read-only diagnostics and the idempotent exact qualification call may remain
available.

If emergency removal must complete while the root cannot provide this
evidence, the Coordinator may publish `Removed` only after durably storing an
`Unqualified` record. It retains the Tree tombstone, last Registry version,
removal ID and typed reason. It does not invent an empty inventory. A later
exact recovery may replace `Unqualified` with `Qualified`, but the root is not
required to remain live or callable forever and ordinary synchronization
access is not restored. That recovery uses only the dedicated qualification
endpoint, requires `caller` to equal the tombstoned root and must match the
exact stored authority, Tree, removal ID and last Registry version. It
cannot change Tree lifecycle status, regain Fleet-management authority or submit
an inventory that was not durably fenced at the root.

Qualification state is protected Coordinator operational state, not a public
Fleet Registry field. It is retained for the lifetime of the Tree tombstone
unless a later explicit compaction design proves it safe to remove.

## Local Propagation

A root must not create a new direct global channel to every Canister.

After activating a Registry revision, the root uses the existing local
topology/state cascade to distribute the relevant Fleet Directory to:

- existing managed Canisters; and
- Canisters joining or being created later.

“Local” is Tree-local, not merely Subnet-local. Every cascade request and
stored child binding carries the exact `TreeId` and Tree Root. A Tree Root
must reject a Canister bound to another co-located Tree even though both
principals execute on the same physical Subnet.

0.100 evolves the one canonical `FleetDirectory` envelope introduced in 0.99;
it does not add a second companion projection:

~~~rust
pub struct FleetDirectory {
    pub provenance: DirectoryProvenance,
    pub groups: Vec<FleetDirectoryGroup>,
    pub entries: Vec<DirectoryEntryInput>,
    pub trees: Vec<FleetDirectoryTree>,
}

pub struct DirectoryProvenance {
    pub authority: FleetRegistryAuthority,
    pub source_root: Principal,
    pub registry_revision: u64,
    pub registry_content_hash: [u8; 32],
    pub synchronized_at: Timestamp,
}

pub struct FleetDirectoryGroup {
    pub group: TreeGroupId,
    pub tree_spec: TreeSpecId,
    pub spec_hash: [u8; 32],
    pub initial_trees: u16,
    pub maximum_trees: u16,
}

pub struct FleetDirectoryTree {
    pub tree: TreeId,
    pub group: TreeGroupId,
    pub spec_hash: [u8; 32],
    pub subnet: SubnetId,
    pub tree_root: Principal,
    pub status: ManagedTreeStatus,
}
~~~

`groups` is the complete consumer-shaped projection of the canonical Tree
Group definitions. `trees` is the complete consumer-shaped Tree projection
derived from the active verified `FleetRegistryMirror`. Together they let
consumers and application routing code restrict selection to eligible active
groups without fetching App configuration. `entries` is the existing service
lookup field, but it is empty throughout 0.100 because `authority_services` is
empty. 0.100 does not reinterpret a local service as Fleet authority or delete
it from its Tree-local registry. 0.101 populates `entries` only from the
complete committed `authority_services` set.

The existing `fleet_directory` cascade field carries this exact shape as a
deliberate pre-1.0 wire cut. No companion Tree lifecycle or service Directory is
introduced.

The semantic rules are fixed:

- each Tree Root's active verified mirror is the Directory source;
- ordinary Canisters never fetch the Registry from the Fleet Coordinator;
- projection does not give ordinary Canisters mutation authority;
- group definitions and Tree rows are projected from the same exact Registry
  revision and activate atomically;
- `entries`, `groups`, `trees`, Registry revision and Registry content hash
  are identical across roots at that revision, while `source_root` and
  `synchronized_at` remain truthful root-local provenance;
- group metadata is topology and placement eligibility, not an application
  routing decision or authorization grant;
- new Canisters receive the latest locally active Fleet Directory;
- interrupted distribution resumes rather than starting a second cascade; and
- `synchronized_at` records the instant the root atomically activates both the
  verified Registry mirror and its derived Fleet Directory for that exact
  revision.

An up-to-date head confirmation updates root-local operational state but does
not change `synchronized_at` or recascade the Directory. The value is not the
Coordinator publication time, last poll time or cascade-completion time.
Consequently, cascaded provenance makes no claim about current Coordinator
reachability.

maintain their own durable placement bindings and route clients directly to
the selected Canister. Fleet-scoped chain-key-backed authentication may then
verify locally without making Directory lookup an authorization dependency.

- missing Fleet Directory state;
- unknown Tree Group;
- unknown Tree;
- Tree/group/spec mismatch;
- non-active Tree where active status is required;
- Fleet binding mismatch;
- authority mismatch; and
- corrupt projected state.

## Application Routing and Inter-Subnet Boundary

0.100 separates its control plane from the application data plane.

The Canic control plane performs bounded, infrequent inter-Subnet calls only
between the Fleet Coordinator and Tree Roots for Registry head,
snapshot, join and removal workflows. Ordinary Canisters read the locally
cascaded Fleet Directory.

An application may avoid routine inter-Canister cross-Subnet calls by:

1. maintaining an application-owned binding from a user, project or other
   domain key to one concrete Canister;
2. returning that target to the client or ingress router;
3. sending the authenticated request directly to the target Canister; and
4. verifying Fleet-scoped chain-key-backed credentials locally on that
   destination Subnet.

Canic group metadata supplies eligible topology and proves which workload
family a Tree runs. It does not own the domain-key binding, choose a shard,
make a multi-Subnet transaction atomic or imply that chain-key authentication
solves routing. Any workflow that requires state from two Subnets must still
define its own idempotency, receipt and consistency boundary.

## Freshness and Authority Subnet Downtime

If the Fleet Coordinator is temporarily unreachable:

- each Tree Root retains its last complete Fleet Registry;
- existing local topology continues operating;
- ordinary Canisters keep their last distributed Fleet Directory;
- local Fleet Directory lookups remain available with stale provenance;
- synchronization retries with bounded backoff;
- Tree registration, activation, draining and removal are unavailable; and
- no mirror becomes authoritative.

Canic exposes root-local time since the last poll and last confirmed current
head. The cascaded Directory exposes only `synchronized_at`, the atomic
mirror-and-Directory activation time for its exact revision. Neither a mirror
nor the Directory claims a stale Registry is fresh, and no mirror promotes
itself.

Callers that require fresh Fleet Tree lifecycle may apply an explicit maximum-age
policy. Generic Directory lookup does not silently reject stale state unless
the operation specifically requires freshness.

## Fleet-Scoped Authorization Transfer

The Coordinator derives administration authority from the 0.99 Fleet-scoped
trust boundary. It does not create a new controller list, administrator list
or Coordinator-specific token audience.

`CoordinatorPrepared` installs one canonical trust bootstrap exported by the
0.99 source root while that root is still the trusted Fleet authority. The
bootstrap contains:

- the exact protected `FleetBinding`;
- the current Fleet-scoped issuer verification material and proof chain;
- the Fleet-administration subject/policy projection needed for Tree lifecycle
  mutation;
- the current revocation, replay and proof-floor state required by the 0.99
  verifier; and
- the handoff ID, source root and canonical content hash binding that material
  to this extraction.

The Coordinator verifies the proof chain and rejects any audience other than
the exact `FleetKey` in its protected binding. It persists the bootstrap before
reporting `CoordinatorPrepared`. A lost preparation receipt is reconciled by
an authenticated status read keyed by handoff ID and content hash; a retry
with different trust material is rejected.

After `CoordinatorCommitted`, Fleet Registry administration uses the same
Fleet-scoped delegated-token verification and policy authority established by
0.99. Controller capability permits install, upgrade and explicitly documented
recovery operations, but controller status alone does not authorize Registry
mutation. Tree Roots expose no canonical Registry mutation endpoint.

Join acknowledgement additionally requires the caller to equal the recorded
`Joining` root. Head and snapshot calls use the lifecycle access rules above.
Every administrative request, root call and acknowledgement binds the exact
protected `FleetRegistryAuthority`; a snapshot's internal authority claim is
never sufficient.

## Validation Rules

A Fleet Registry snapshot is valid only when:

- its full `FleetBinding` exactly matches protected bootstrap state;
- the authority epoch, Authority Subnet and Fleet Coordinator principal match
  protected bootstrap state;
- its revision is at least `GENESIS_REGISTRY_REVISION`;
- Tree Group definitions are non-empty, canonically ordered and bounded;
- Tree Group IDs are unique and every group references one valid Tree Spec;
- each group has a valid Tree Spec hash and nonzero Tree bounds with
  `initial_trees <= maximum_trees`;
- Tree entries are canonically ordered;
- `TreeId`s are unique;
- every Tree references one present group and repeats its exact spec hash;
- `SubnetId` may repeat without changing Tree identity;
- each group's `Joining`, `Active` and `Draining` Tree count fits its declared
  maximum;
- Tree Root principals are unique across all retained Tree rows;
- `authority_services` is present and empty;
- every status value is recognized;
- all identities pass existing canonical validation;
- serialized size and Tree count are within the frozen bounds; and
- the content hash matches the received bytes.

The same `(FleetRegistryAuthority, revision)` arriving with a different hash
is not a routine retry failure. It is authority equivocation or corruption
and must be surfaced as a terminal synchronization failure requiring
investigation.

A different `FleetRegistryAuthority` is always rejected before revision
comparison. Matching revision and content from another canonical network,
Fleet, App, Authority Subnet or Fleet Coordinator is not an idempotent retry.

Coordinator removal state is valid only when every `Removed` Tree has one
matching qualification record. Qualified evidence must pass its independent
authority, group/configuration, Tree, version, ordering, size,
inventory-hash and root-fence receipt checks. An unqualified record must
retain its exact typed reason and must never be projected as an empty
inventory.

## Observability

Each Tree Root should expose:

- protected Fleet binding;
- protected Tree, Tree Group, Tree Spec and spec hash;
- physical placement Subnet and Tree Root;
- local active Registry version;
- configured authority descriptor;
- `last_polled_at`;
- `last_confirmed_current_at`;
- `synchronized_at`;
- consecutive failures;
- next retry time;
- last typed failure;
- local cascade progress for the active revision; and
- whether its own Tree is `Joining`, `Active`, `Draining` or `Removed`.

The Coordinator's bounded administrative projection also exposes, for every
removed tombstone, whether it is `Qualified` or `Unqualified`, its removal ID,
base Registry version, final inventory count/hash when qualified and typed
unqualified reason otherwise. The complete inventory remains protected
operational evidence rather than a public Directory or Fleet Registry field.

Metrics should include:

- successful and failed head checks;
- downloaded snapshot count and bytes;
- rejected stale revisions;
- hash or invariant failures;
- synchronization interruption and resume;
- Registry activation duration;
- cascade completion age;
- qualified and unqualified removal counts;
- final-inventory and root-fence qualification failures;
- current Registry revision; and
- per-group `Joining`, `Active`, `Draining` and `Removed` counts; and
- time since last confirmed current head.

Failures must remain typed through internal ownership. Human-readable strings
are projections, not the stored error authority.

## Stable-State and Schema Rules

The implementation must identify:

- the canonical stable owner of the authoritative Fleet Registry;
- the host compilation owner for App Tree Specs and the Coordinator's sole
  runtime owner of their canonical Tree Group definitions;
- the old root's durable handoff/fence owner and the Coordinator's preparation
  and commitment owner;
- the canonical stable owner of each mirror;
- the Coordinator's protected owner of qualified and unqualified
  removed-tree evidence and the root's irreversible removal fence;
- the current stable owner of local cascade progress; and
- whether the Fleet Coordinator and mirrors use the same stored snapshot type.

There must not be:

- two stored canonical Tree or Tree Group lists;
- an App configuration reader on each root competing with the protected Tree
  Spec installed for that Tree;
- a configuration list continually dual-written with the runtime Registry;
- both mutable row state and an independently authoritative published snapshot; or
- legacy and new Registry readers running in parallel.

The Coordinator stores one current snapshot/manifest pair plus one staging
slot. The source root stores its irreversible fence independently. The host
journal records progress and receipts but cannot synthesize source-fence
evidence, removed-tree qualification, Coordinator commitment or a newer
Registry version. Qualified inventories and unqualified tombstones are retained
for the lifetime of their Tree tombstones.

If an existing global-subnet concept already exists, 0.100 must migrate or
replace it as a hard cut rather than wrapping it indefinitely.

Stable snapshots, manifests, mirror state, cascade progress and provenance have
one current shape with the full `FleetRegistryAuthority`. Any migration
required for deployed Canisters must be explicit, bounded and tested through
upgrade. After activation there is no schema tag, old decoder or fallback
reader; pre-1.0 internal structures are replaced directly.

### Synchronization

- A mirror with no Registry bootstraps from the Fleet Coordinator.
- An up-to-date mirror persists `last_confirmed_current_at`, clears failure
  state, resets backoff and does not cascade.
- A mirror skips directly across multiple revisions.
- requesting a snapshot superseded after the head read returns
  `VersionSuperseded` and restarts from head;
- more than three superseded races in one pass enter bounded retry;
- only the current committed snapshot is retrievable;
- committing a new snapshot reclaims the previous snapshot after durable
  manifest replacement;
- An older revision cannot replace a newer revision.
- The same revision and hash is an idempotent no-op.
- The same revision with a different hash fails terminally.
- A corrupted or truncated snapshot never activates.
- A snapshot with a different Fleet binding leaves the previous snapshot
  active.
- An authority descriptor mismatch is rejected.
- Unexpected lower and higher authority epochs fail closed.
- `last_polled_at`, `last_confirmed_current_at` and `synchronized_at` advance
  only for their declared events.

### Handoff, Interruption and Recovery

- interruption in `LegacyActive` leaves the 0.99 root authoritative for its
  exact one-Tree seed and local `SubnetRegistry`; no Fleet Registry exists;
- `CoordinatorPrepared` exposes neither a current manifest nor mutation
  authority;
- interruption in `SourceQuiesced` resumes or explicitly rolls back before
  fencing without downgrading the root Wasm or changing the seed;
- the source persists `SourceFenced` before acknowledging it;
- Coordinator commitment rejects host-only or wrong-source fence evidence;
- after `SourceFenced`, recovery resumes with the same Coordinator principal
  and never restores the old seed-attestation authority;
- an unknown Coordinator commit outcome reconciles by handoff ID without
  creating another Coordinator;
- at no durable boundary can the Fleet Coordinator accept Registry mutation
  while the Tree Root can still commit or attest a different handoff
  seed;
- loss of availability between fence and commitment is recoverable and does
  not weaken the single-writer rule;
- Interruption before durable snapshot staging retains the old Registry.
- Interruption after staging but before activation retains the old Registry.
- Interruption after activation but before receipt reconciles as complete.
- Upgrade during polling resumes safely.
- Upgrade during local cascade resumes from durable progress.
- Repeated timeouts do not discard the last valid Registry.
- Fleet Coordinator downtime never promotes a mirror.

### Authorization and Restore

- the Coordinator rejects trust material for another Fleet, audience, source
  root, handoff ID or content hash;
- loss of the trust-install receipt reconciles to the same prepared state;
- controllers cannot call Fleet Registry mutation without Fleet-scoped
  authorization;
- a stale same-epoch Coordinator backup may restore read-only recovery state
  but cannot reactivate mutation authority;
- mirror state, a host journal or controller assertion alone cannot prove that
  a restored revision is latest.

### Local Distribution

- Existing Canisters receive empty service `entries` and the complete
  `groups` plus group-aware `trees` projections without changing
  Tree-local Registry ownership.
- group-filtered lookup returns only active Trees of the requested group;
- different groups may expose disjoint permitted roles and different concrete
  local inventories;
- application user/project bindings remain outside the Fleet Registry and
  Directory;
- A newly created Canister receives the root’s current revision.
- No ordinary Canister performs an inter-Subnet Registry call.
- Partial cascade is observable and recoverable.
- Directory provenance carries `synchronized_at`, not a publication, poll or
  cascade-completion time.
- A successful unchanged head poll does not recascade the Directory.

- IcyDB snapshot, change-stream or application-data replication;
- application-owned user/project/shard routing bindings;
- traffic-, health- or capacity-driven automatic Tree Group scaling;
- automatic choice of public-IC placement Subnets;
- automatic Tree-replica or `one_per_active_tree` provisioning;
- health-, latency- or freshness-based service routing;
- automatic Fleet Coordinator election, replacement or relocation;
- root-to-root consensus;
- multi-writer Registry mutation;
- root-to-root mesh synchronization;
- Registry deltas or change-data capture;
- chunked artifact transfer;
- generic distributed transactions;
- proof that two application databases contain identical data;
- subnet health or “best available subnet” selection; or
- physical removal of a subnet, root or canisters.

## Hard-Cut Completion Criteria

0.100 is complete when:

1. The separately placed Fleet Coordinator is the only canonical writer
   of Tree Group definitions and Tree lifecycle.
2. Every authoritative and mirrored record and every evidence hash binds the
   exact canonical network, Fleet and App through `FleetBinding`.
3. An omitted fresh public-IC Authority selector resolves to the dynamic
   Fiduciary profile, fresh tests use their harness Subnet, developer
   overrides are validated and no failure falls back to a random Subnet.
4. The Authority Subnet is Coordinator placement bound outside ordinary Tree
   rows; co-located Trees retain independent identity and lifecycle.
5. Existing 0.99 Fleets use the sole observed Canister Tree without an
   override, the exact one-Tree seed remains bound through extraction and
   no local Registry row moves or changes ownership.
6. The durable handoff permits zero writers temporarily but never two
   committed writers, and recovery after the source fence uses the same
   Coordinator principal.
7. Every Tree Root durably mirrors a verified complete current Fleet
   Registry and proves its exact Tree/group/spec/hash/placement binding.
8. Registry group/Tree changes propagate through the `groups` and
   group-aware `trees` fields of the exact current Fleet Directory while
   service `entries` remain empty.
9. Inter-Subnet topology synchronization is limited to the Fleet Coordinator
   and Tree Roots, bounded and infrequent.
10. Registration, activation, failed-join cancellation, draining and removal
    are explicit and tested.
11. Every removed Tree has durable qualified final inventory and root-fence
    evidence or an explicit unqualified tombstone that cannot prove absence.
12. Removed-Tree evidence remains usable after the root becomes permanently
    unavailable.
13. Every maintained distinguished-subnet surface uses Authority Subnet
    terminology; `Prime Subnet` appears only when identifying the removed
    name.
14. No unexplained competing Tree/group list or privileged-Tree authority
    remains.
15. The snapshot protocol has one exact encoding, hash, retention rule,
    bounded race recovery and checked revision sequence.
16. Every snapshot uses the one current schema with canonical
    `tree_groups`, group-bound `trees`, an empty `authority_services` field
    and one Fleet binding beneath `authority`.
17. Fleet-scoped trust transfers without creating a controller-derived or
    Coordinator-local administrator authority.
18. Coordinator restore cannot roll back same-epoch mutation authority.
19. Heterogeneous `users` plus horizontally scaled `projects` qualification
    proves group-specific topology without identical local inventories and
    proves that physical `SubnetId` may repeat.
20. Fresh Trees never instantiate `[services.fleet]` roles; an extracted
    0.99 candidate remains adoption-only and is never replicated.
21. Upgrade and interruption tests prove every durable boundary.

## Expected Follow-On

With 0.100 complete, 0.101 can safely adopt and provision Fleet-authoritative
services:

~~~text
0.100
  “Which Canister Trees and Tree Groups exist, which Tree Roots own them,
   where are they placed, and which Fleet Coordinator owns lifecycle?”

0.101 authority services
  “How are existing mutable services adopted without changing
   their principals or data, how are fresh services provisioned,
   how does registry ownership move, and what is published
   through the Fleet Directory?”

0.103 transport groundwork
  “Can Canic classify, bound, measure and safely attempt a call
   that may cross Subnets?”

Later database transport
  “How does one authoritative service distribute
   application-owned data to its mirrors?”
~~~

0.101 compiles the service-owned `[services.fleet].roles` declaration,
qualifies singleton eligibility, adopts in place or provisions missing
services, transfers registry ownership and publishes the canonical Directory.
Relocation of an existing mutable authority to another physical Subnet remains
separate from adoption in place.

The
[0.103 cross-Subnet data transport groundwork](../0.103-cross-subnet-data-transport-groundwork/0.103-design.md)
adds route evidence, cross-Subnet-safe call bounds and measurement without
defining database snapshots, logs, replicas or application-data semantics.
It is not a prerequisite for the client-directed application path in this
design: a client may route directly to its bound user or project Canister and
that Canister may verify Fleet-scoped chain-key-backed credentials locally.
0.103 is needed only where a Canister workflow itself performs a cross-Subnet
call.
