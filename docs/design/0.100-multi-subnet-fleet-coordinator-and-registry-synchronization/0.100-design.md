# Canic 0.100 Design: Fleet Subnet Roots, Flat Components and Fleet Registry Synchronization

Date: 2026-07-29

## Status

- Status: implementation in progress.
- Release boundary: reinstall only.
- Dependency: the
  [0.99 App/Fleet hard cut](../0.99-app-fleet-identity-and-terminology-hard-cut/0.99-design.md)
  defines the App, Fleet and network identities reused by this design.
- Scope: Fleet coordination, one Fleet Subnet Root per occupied physical
  Subnet, flat Component Specs, root-local Component lifecycle,
  bounded peer-Component provisioning,
  qualified Canic infrastructure installation, topology-admitted Wasm Store
  construction, Fleet Registry synchronization, distinct Fleet/Component
  Directory projection and read-only version-bound physical-Subnet/provider
  observation.
- Compatibility posture: none. A 0.100 Fleet starts from empty current state.

0.100 does not read or transform a 0.99 installation or an earlier 0.100
installation. It has no extraction step, authority transfer, cross-release
journal, mixed-version mode, compatibility decoder or prior-release recovery
path. Existing Fleets are reinstalled.

## Thesis

A Fleet may use several physical Subnets. Every occupied workload Subnet has
exactly one Fleet-scoped Fleet Subnet Root. That root is the sole lifecycle
authority above every multi-level Component tree on the Subnet, maintains one
Fleet Registry Mirror and operates one local Wasm Store built from the flat
potential-Wasm catalogs of the Component Specs admitted to that root.

A Component instance is the independently admitted and quota-bounded partition
below a Fleet Subnet Root. Its Component Canister is a direct child of the
root and the root manages every descendant in that Component's dynamic
parent-child tree. Any exact registered Component or Component Child may ask
the root to create one of the Component Spec's potential child roles beneath
itself. The requester records real parentage, while the root remains the sole
controller, installer, cycles funder, Registry owner and lifecycle executor.
A Component may also request creation of an admitted peer Component through an
exact bounded provisioning grant. That request records causation only: the
selected Fleet Subnet Root remains the new Component's direct parent,
controller, Registry owner and lifecycle executor.

~~~text
Fleet Coordinator
  owns FleetRegistry
       |
       | authenticated, bounded snapshot synchronization
       v
Fleet Subnet Root for Fleet A @ Subnet X
  owns one FleetRegistryMirror and FleetDirectory
  owns one topology-admitted Wasm Store and active release set
  owns ComponentRegistry[ComponentInstanceId] and platform effects
       |
       +-- Component users_hub
       |       +-- Component Child user_shard
       |       +-- Component Child user_shard
       |
       +-- Component app
       |
       +-- Component project_hub
               +-- Component Child project_instance
                       +-- Component Child project_ledger
                       +-- Component Child project_machine [on demand]
~~~

The Coordinator is not a Component, application router or controller of
Component Children. Toko's Project Hub retains a
`project_id -> ComponentChildBinding` index after it asks its root to create
the Project Instance as its direct child. The Project Instance may then ask
that same root to create its Ledger, Machine and other admitted children. All
of them remain on the same physical Subnet and in the same Component tree.

Physical co-location is intentional. Components and Component Children that
communicate frequently may share a Fleet Subnet Root and avoid cross-Subnet
traffic. Sharing a root reduces control-plane Canisters, synchronization,
publication and provisioning fanout; it does not make the root an
application-data proxy.

## Shared Physical Subnets

Fleet Subnet Root uniqueness is scoped by both Fleet and physical Subnet:

~~~text
exactly one Fleet Subnet Root per (FleetKey, SubnetId)
~~~

Several Fleets may use the same physical Subnet. If Fleet A and Fleet B both
occupy Subnet X, each has its own Fleet Subnet Root on Subnet X:

~~~text
Subnet X
  +-- Fleet Subnet Root for Fleet A
  +-- Fleet Subnet Root for Fleet B
  +-- unrelated Canisters owned by other users
~~~

Those roots share only the IC placement and failure domain. They do not share
Fleet authority, Registry state, Component admission, Wasm Store contents,
release sets, cycles, limits, journals or controller authority. Every
control-plane request binds the exact Fleet as well as the root.

Root limits are Fleet-local ceilings, not reservations of physical Subnet
capacity. Deployment planning may consider observed Subnet headroom, but
another Fleet or unrelated user may consume that headroom later.

## Rooted Multi-Level Component Tree Invariant

Canic runtime parentage has one infrastructure root and arbitrary dynamic
depth bounded by finite Component and root canister ceilings:

~~~text
Fleet Subnet Root -> Component -> Component Child -> Component Child -> ...
~~~

The Component declaration remains flat: it lists the Component role and every
potential descendant role/Wasm once, without encoding a static hierarchy.
Concrete parent-child edges exist only when the root journals and creates an
instance. The following remain invalid:

- a Component whose parent is another Component;
- a Component declared as another Component's child;
- nested or included Component Spec declarations;
- a child role or raw Wasm absent from the owning Component Spec's flat
  potential-Wasm catalog;
- a parent outside the exact Component tree or physical Subnet;
- delegated controller, Registry, Wasm Store or lifecycle authority; or
- interpreting a Component Provisioning Grant as a parent edge.

Each child binding records its immediate parent. That parent may request
further children, but every effect still goes through the Fleet Subnet Root.
A Component Provisioning Grant remains a separate non-parent authorization
edge for creating another top-level peer Component.

`service` is reserved for Fleet publication vocabulary in 0.101. A Fleet

ordinary.

`default`, when used, is an application workload name. It does not select the
Coordinator Subnet or a physical workload Subnet.

## Tree Identity Hard Cut

The intermediate Tree layer has no remaining authority in this architecture.
A Component instance is already the lifecycle, quota, Registry and Directory
partition, so retaining another logical container would duplicate identity
without owning an effect.

The following current-schema cuts are exact:

| Superseded surface | Sole 0.100 destination |
| --- | --- |
| `TreeSpecId` | `ComponentSpecId` with one direct Component role and one flat potential descendant-role catalog |
| `TreeGroupId` | removed; a Component Spec carries its Fleet ceiling and each root carries its immutable local allocation. The later `ComponentGroupSpecId` identifies only a 0.101 compile-time deployment composition and never a root, partition or runtime parent |
| `TreeId` | removed; a concrete Component uses `ComponentInstanceId`. The later `ComponentGroupPlacementId` identifies one orchestration copy only and is never a Canister, workload partition, Registry owner or runtime parent |
| `TreeBinding` | removed; Component identity is complete in `ComponentBinding` |
| `TreeRegistry` | `ComponentRegistry`, partitioned by `ComponentInstanceId` |
| `TreeDirectory` | `ComponentDirectory` |
| `canic app role attach --tree-spec` | `canic app role attach --component-spec`; no alias |
| per-Tree root role | removed; the Fleet Subnet Root is outside Component Specs |
| `SubnetSlotId` and `subnet_slot` | removed; Component declaration uses `ComponentSpecId`, concrete identity uses `ComponentInstanceId`, and placement uses `SubnetId` |
| Fleet Root, `fleet_root_pid` and `is_fleet_root` | Fleet Subnet Root, `fleet_subnet_root`/`fleet_subnet_root_pid` and `is_fleet_subnet_root` |
| `SubnetRegistry` | root-owned, `ComponentInstanceId`-partitioned `ComponentRegistry` |
| `SubnetDirectory` | `ComponentDirectory` |
| per-logical-partition release manifest | root-specific `FleetSubnetRootReleaseSetManifest` projected from one Fleet-wide build |
| one-partition service-shaped `FleetDirectory` | Fleet Registry-derived root projection, extended with service bindings by 0.101 |
| shared `DirectoryProvenance` | split into `FleetDirectoryProvenance` and `ComponentDirectoryProvenance` |
| Fleet Directory `source_root` | `FleetDirectoryProvenance.source_fleet_subnet_root` |

These are hard replacements, not aliases. A current runtime, Candid surface,
durable owner, DTO, endpoint, test or active document must not retain Tree
identity or the earlier one-root-per-Tree model. Historical changelog entries
remain unchanged as a record of development.

## Release Installation Boundary

A fresh 0.100 installation proceeds in this order:

1. compile and freeze the App's complete Component Specs and Component
   Topology;
2. allocate one `ReleaseBuildId`, build the exact Canic infrastructure
   artifacts and the separate union of admitted Component and Component Child
   Wasms once, then freeze both manifests and their final artifact evidence;
3. resolve and journal Coordinator placement and creation funding;
4. resolve every required workload Subnet and create exactly one Fleet Subnet
   Root placement and funding plan for each distinct
   `(FleetKey, SubnetId)`;
5. distribute each Component Spec's Fleet-wide instance ceiling into
   immutable root-local Component admissions;
6. freeze each root's admissions, configured limits and exact Fleet Subnet
   Root Release-Set Manifest projected from the Fleet-wide artifact union;
7. host-create and install the Fleet Coordinator directly from the exact
   infrastructure-manifest entry and protected binding;
8. create the genesis Fleet Registry from empty state;
9. create and install every Fleet Subnet Root behind the runtime `Prepared`
   fence, bootstrap its implicit local Wasm Store and publish only the
   artifacts admitted by its Component Topology and active release set;
10. register every Fleet Subnet Root through `Joining`, synchronize the exact
    snapshot and accept that root's acknowledgement;
11. commit every required root as Fleet Registry `Active`;
12. synchronize every root to the final all-active Fleet Registry version and
    atomically activate its matching Fleet Directory;
13. seal each root's empty 0.100 initial Component inventory and activate its
    runtime only after the local Wasm Store, final mirror and Fleet Directory
    agree;
14. verify exact runtime `Active` and final topology evidence for every
    required root; and
15. publish the Coordinator-anchored Fleet catalog row only after that
    complete evidence is durable.

The installation journal owns same-release interruption recovery. It never
refers to prior-release Registry state, stable state or Canisters.

The 0.100 install plan contains Component admission ceilings, not initial
Component counts. A fresh 0.100 install therefore must not reinterpret an
admission such as `project_hub = 10` as ten creation requests. It seals an
empty initial inventory, activates the root, and then admits ordinary
administrator or grant-authorized Component creation through the active-root
lifecycle. Fresh 0.101 installation adds a separate exact Component Group
placement plan and may materialize that nonempty inventory while roots remain
`Prepared`.

Initial Coordinator progress is the monotonic sequence `Planned`,
`CreationInFlight`, `Created`, `InstallInFlight`, `Installed`, `Verified`.
The exact Fleet install plan, complete Component Topology, infrastructure
manifest entry, funding and expected module hash are durable before creation.
The creation command streams its principal result into a separate durable
no-follow result file. A restart may recover that principal and observe the
Canister, but an in-flight creation with no recoverable principal fails closed
instead of issuing a second paid creation. An in-flight install similarly
advances only by observing the exact expected module hash; absence or an
unknown module never triggers a blind second install.

`Verified` additionally requires controller-authenticated live queries for
the complete Fleet Registry, its manifest and its version to equal genesis
recomputed from the journalled protected authority and Component Topology.
No Fleet Subnet Root creation may begin before that live verification.

Every planned Fleet Subnet Root then owns an independent monotonic
`Planned`, `CreationInFlight`, `Created`, `InstallInFlight`, `Installed`,
`Verified`, `StoreStaging`, `StoreStaged`, `StoreBootstrapInFlight`,
`StoreBootstrapped`, `StoreVerified`, `RegistryJoinInFlight`,
`RegistryJoined`, `RegistryJoinVerified`, `RegistrySyncInFlight`,
`RegistrySynchronized`, `RegistrySyncVerified` journal in canonical plan
order. Its immutable authority includes the exact Fleet and Coordinator
binding, physical placement Subnet, Component admissions, root-local limits,
initial release set, infrastructure artifact, creation funding and expected
module hash.
`Verified` requires the live module hash, empty runtime `Prepared` status and
controller-authenticated protected root authority to match that journal. All
roots must reach `Verified`, and their complete observed binding set must
satisfy Fleet-wide topology invariants, before any local Store effect or
Registry registration begins.

The host then chunk-stages each root's canonical release-set manifest and
compressed application artifacts through that root's controller-only
`Prepared` surface. The root reconstructs the exact manifest bytes, verifies
their protected digest, build, topology, admission, role/package and Store-byte
authority, creates exactly one implicit local Store and publishes the complete
deduplicated role catalog. `StoreVerified` requires a separate composite query
to reproduce the same root, Store, release-set and ordered catalog evidence.
An exact retry may restage identical bytes or re-enter an in-flight bootstrap,
but it must reuse the same Store and cannot admit an extra catalog row. Store
verification does not itself imply Registry `Joining`, synchronization or
activation.

After every Store is independently verified, the host registers roots through
the Coordinator in canonical plan order. Before each mutation it reconstructs
and checks the exact live Registry prefix, journals a request bound to the
expected Registry version and planned `Joining` row, then independently checks
the returned row and next live snapshot, manifest and version. The Coordinator
validates the complete next snapshot and atomically commits it with a durable
response receipt. Exact retry returns that original response even after later
roots advance the live Registry revision; reused Subnet or root identity with
different authority fails closed. Installation reaches
`RegistryJoinVerified` only when the complete all-`Joining` Registry equals
locally recomputed authority.

The host then journals that exact all-`Joining` version and the exact request
needed to reverify the local Store. Each root independently revalidates its
Store, fetches the complete current snapshot through a caller-authenticated
Coordinator update, validates the Registry, manifest, version and its exact
protected row, then durably stages the candidate before acknowledging it. The
Coordinator accepts an acknowledgement only while the complete non-empty root
set remains `Joining`, commits the exact `(root, version)` receipt in canonical
root order and returns the same receipt on exact retry. The root stores that
receipt beside the candidate. `RegistrySyncVerified` requires a separate
root composite query plus the Coordinator's complete acknowledgement
inventory to reproduce the same root set and version.

The all-`Joining` candidate remains private preparation state. The Coordinator
atomically commits the complete acknowledged root set as `Active` through one
response-idempotent transition, and the host independently verifies the final
Registry, manifest and version. Each root then reverifies its Store, fetches
and validates that exact all-`Active` snapshot, derives its Fleet Directory
and atomically replaces the private candidate with one active
mirror/Directory record. A separate root status query reproduces the durable
active evidence before installation proceeds. This does not change runtime
state; runtime activation remains a later journalled boundary.

Fleet Registry lifecycle and runtime lifecycle are different state machines.
An `Active` Fleet Subnet Root is eligible in Fleet topology; that status does
not by itself open the root's ordinary endpoints or start timers. The runtime
`Prepared` fence admits only the exact bootstrap, synchronization,
acknowledgement, Wasm publication, activation-status and activation operations
needed by fresh installation.

0.100 creates no empty logical workload partitions. A
`ComponentInstanceId` exists only when a concrete Component creation
operation durably allocates it. After installation, authenticated Fleet
administration may create admitted ordinary Components, and an exact
same-root Component may use a compiled grant to request an admitted peer.
0.101 extends the fresh-install barrier to provision declared Component Group
placements and publish their typed Fleet-service member sets before terminal
activation, then uses that publication to authenticate grant-checked
cross-root requesters.

## Canic Infrastructure Artifacts and Installation Ownership

Canic infrastructure Wasms are a separate qualified artifact family from
application Component and Component Child Wasms:

~~~rust
pub enum CanicInfrastructureRole {
    FleetCoordinator,
    FleetSubnetRoot,
    WasmStore,
}

pub struct CanicInfrastructureArtifactManifest {
    pub release_build_id: ReleaseBuildId,
    pub entries: Vec<CanicInfrastructureArtifactEntry>,
}
~~~

The manifest contains exactly one entry for each role above. Each entry binds
the exact Cargo package, qualified build identity, raw and compressed byte
lengths and hashes. Missing, duplicate, cross-build or unqualified entries
fail before any Canister creation. Infrastructure entries never enter a
root's application release set or local Wasm Store Catalog.

Installation ownership is explicit:

- the host creates and installs the Fleet Coordinator directly from the exact
  `FleetCoordinator` entry;
- the host creates and installs each Fleet Subnet Root directly from the exact
  `FleetSubnetRoot` entry; and
- each installed root creates its own implicit local Wasm Store and installs
  only the exact `WasmStore` artifact carried by, and verified against, its
  protected bootstrap evidence.

The Coordinator is therefore not installed by a root, Component or Wasm
Store, and it does not belong to a Component hierarchy. The local Wasm Store
bootstrap is the only one of these three installations delegated to a Fleet
Subnet Root.

## Goals

0.100 must:

1. establish exactly one Fleet Registry writer;
2. establish exactly one Fleet Subnet Root for each occupied
   `(FleetKey, SubnetId)`;
3. allow several Fleets to occupy the same physical Subnet without sharing
   authority;
4. represent heterogeneous, independently scalable Component Specs;
5. allow several Component Specs and instances to share one Fleet Subnet Root;
6. preserve multi-level dynamic parentage inside each Component tree while
   retaining one root lifecycle authority;
7. qualify and install Canic infrastructure separately from application
   artifacts;
8. construct each local Wasm Store from only its admitted Component Specs and
   their children;
9. separate Component identity from physical Subnet placement;
10. make root and Component lifecycle explicit;
11. authenticate every Coordinator/root and Component/root control-plane call;
12. synchronize complete bounded Fleet Registry snapshots once per root;
13. activate a Fleet Registry Mirror and Fleet Directory atomically;
14. preserve independent Component Registry and Component Directory authority
    per `ComponentInstanceId`;
15. remain deterministic across interruption and exact retry;
16. allow every exact registered tree node to request admitted direct-child
    effects without becoming a controller or lifecycle executor;
17. permit a Component to request an admitted peer Component without creating
    nested lifecycle authority; and
18. derive each root's complete potential-Wasm set from its admitted flat
    Component catalogs before any dynamic child creation; and
19. establish one version-bound host observation of Subnet kind, node count
    and node-provider membership before any later Cloud Engine placement
    policy consumes those facts.

## Non-Goals

0.100 does not implement:

- any prior-release transition;
- Component or child adoption;
- nested Components, nested Component declarations or delegated lifecycle
  execution;
- unbounded peer provisioning or requester-selected lifecycle ownership;
- arbitrary Wasm upload or artifact selection by a Component;
- Component Group provisioning, Fleet-service member publication or grouped
  runtime activation;
- cross-root publication of ordinary Component requester identity; 0.101 uses
  exact Fleet-service membership for that purpose;
- application routing, sharding decisions or data replication;
- automatic metric-driven Component placement or scaling;
- automatic ICP exchange-rate lookup or creation-funding optimization;
- automatic Subnet-utilization discovery or capacity reservation;
- automatic node-provider selection, scoring, contracting or replacement;
- treating cached node-provider names or reward accounts as placement
  authority;
- making a Cloud Engine eligible merely because read-only topology
  observation classifies it;
- Coordinator election, relocation or replacement;
- Fleet Subnet Root replacement or a second root for one Fleet on one Subnet;
- Component relocation, principal replacement or
  `ComponentInstanceId` reuse;
- distributed consensus between roots;
- a second Fleet Registry writer; or
- compatibility aliases, decoders or fallback state.

## Physical Subnet Kind and Topology Evidence

Canic preserves the IC's four physical-Subnet execution kinds:

~~~rust
pub enum SubnetKind {
    Application,
    CloudEngine,
    System,
    Unknown,
}
~~~

The host consumes this vocabulary directly from `ic-query`; it does not map
`Application` and `System` into an umbrella kind. Network scope is called `IC
mainnet` and is never a `SubnetKind`. A later runtime/protected representation
must retain these exact variant names and meanings through one canonical
conversion rather than introduce a narrower management classification.

`SubnetSpecialization::{None, Fiduciary, European, Unknown}` is a separate
catalog axis with its own provenance. Specialization is not execution kind,
placement eligibility, creation-funding policy or provider topology.
`Unknown` kind remains valid observational evidence but cannot authorize
placement. Application/System eligibility and funding remain separate facts.

The protected placement target is a named pair:

~~~rust
pub struct SubnetPlacement {
    pub subnet: SubnetId,
    pub kind: SubnetKind,
}
~~~

A later reinstall-only protected-placement cut may replace the existing bare
Coordinator, root and Component `SubnetId` fields with `SubnetPlacement`.
That cut must update the Fleet install plan, Coordinator/root/Component
bindings, Fleet Registry rows, Mirrors, Fleet Directory rows, installation
journals and operator inventory atomically. The first slice defined here is
read-only and does not change current Candid, stable state, Fleet Registry
encoding or Cloud Engine eligibility.

### Version-Bound Subnet Topology Snapshot

The first host-side Canic projection is:

~~~rust
pub struct SubnetTopologySnapshot {
    pub provenance: SubnetTopologyProvenance,
    pub subnets: Vec<SubnetMetadata>,
}

pub struct SubnetTopologyProvenance {
    pub canonical_network_id: CanonicalNetworkId,
    pub registry_canister_id: Principal,
    pub registry_version: u64,
    pub fetched_at: String,
    pub source_endpoint: String,
    pub fetched_by: String,
}

pub struct SubnetMetadata {
    pub subnet: SubnetId,
    pub kind: SubnetKind,
    pub node_count: u32,
    pub node_providers: Vec<SubnetNodeProvider>,
}

pub struct SubnetNodeProvider {
    pub node_provider: Principal,
    pub node_count: u32,
}
~~~

This is a host observation, not App configuration, runtime protocol state,
Fleet Registry authority or physical-capacity reservation. Rows are ordered
by `SubnetId`; provider rows are ordered by principal. Subnets and providers
are unique, every provider row has a positive node count, and each Subnet's
provider counts sum exactly to its node count. Every assigned node must join
to one node operator and provider at the same registry version. Missing or
contradictory relation data rejects qualification rather than inventing an
owner.

Provider principal and per-Subnet membership count are topology evidence.
Optional provider names, governance registration state, reward accounts,
capacity summaries, data-center labels and regions are enrichment. They may
appear in read-only reports but do not enter the canonical placement pair or
authorize a policy decision unless a later design explicitly promotes an
exact versioned field.

### `ic-query` Source and Shared Cache

`ic-query` owns the raw registry/governance query, cache model and topology
join. Its current typed reports already expose:

- Subnet principal and raw kind;
- node principal, Subnet, node operator, node provider and data center;
- registered provider principal plus optional name, node count and reward
  account; and
- aggregate provider/operator capacity and topology health.

The dependency now exposes that boundary as
`ic_query::nns::topology::NnsSubnetTopologyReport`, with canonical Subnet rows
and per-Subnet provider counts joined at one exact registry version.
`ic-query`, not Canic, owns the concrete report schema, refresh lock and cache
path.

Canic passes the exact ICP project root and network to typed `ic-query` Rust
APIs. Direct `ic-query` commands and Canic therefore share the dependency's
current `.icq` cache namespace. Canic must not parse `.icq` JSON directly,
construct dependency-private cache paths, shadow those files under `.canic`
or implement a second refresh lock. The maintained dependency boundary
provides:

- `load_cached_nns_subnet_topology` for a cache-only read;
- `refresh_nns_subnet_topology` for an explicit live refresh;
- `load_or_refresh_missing_nns_subnet_topology` for absence-only refresh;
- `load_or_refresh_stale_nns_subnet_topology` for caller-policy refresh; and
- `nns_subnet_topology_freshness` for a side-effect-free freshness
  projection.

The current component caches are independently published and an existing
cache is not refreshed merely because a read occurs. Consequently:

- a read-only report may consume cached data only while exposing its
  `fetched_at`, registry version and stale status;
- absence may use the dependency's ordinary read-through refresh;
- an authority-producing first installation must obtain one explicit fresh,
  version-bound topology snapshot before publishing a plan;
- separately cached Subnet, node, operator or provider reports may be joined
  only when their network, registry Canister and registry version agree;
- version skew triggers one bounded refresh/retry or a typed failure;
- an exact install retry uses its already published immutable plan and
  evidence rather than re-resolving mutable `.icq` state; and
- no Canister runtime reads host cache files or invokes `ic-query`.

The joined report is atomically cached at the dependency-owned
`.icq/subnet-topology/<network>/report.json` path under one sibling refresh
lock. Canic discovers the concrete path only through
`nns_subnet_topology_cache_path` and otherwise treats it as opaque.

### Staged Adoption

The first Canic implementation slice is deliberately observational. With the
joined `ic-query` report and cache lifecycle available, Canic must:

1. consume the report through one `canic-host` adapter;
2. preserve the report's exact `SubnetKind` and validate canonical provider
   membership;
3. expose source provenance and freshness in read-only evidence; and
4. qualify the mapping and invariants against live IC mainnet Registry data.

It does not remove the current Cloud Engine installation rejection or
root-auth signer safety check. Before a protected `SubnetPlacement` cut may
make Cloud Engines eligible, a follow-on design must resolve:

- Coordinator, Fleet Subnet Root, Store, Component and Worker eligibility;
- Cloud Engine creation, installation and funding ownership;
- root-issued authentication/signing policy;
- cross-Subnet cycle-bearing and unbounded-wait calls plus any NNS-managed
  Subnet proxy;
- provider-diversity, jurisdiction, capacity and freshness policy; and
- topology change detection, operator reconciliation and fail-closed runtime
  behavior.

### Creation Funding

Trusted network metadata must classify whether each host-created initial
Canister can use ordinary cycles-funded creation or requires CMC-backed

amount for the Coordinator and every initial Fleet Subnet Root before any

blindly repeated.

document, unsafe file, topology drift or artifact-union drift fails closed.

Spec must be admitted by at least one planned root. For each Spec, the sum of
admission ceilings across the Fleet's roots must be positive and must not
exceed the Spec's Fleet-wide ceiling. Unallocated capacity is unavailable in
0.100; admissions do not expand live.

The root, its implicit Wasm Store, every Component and every Component Child
must be created on, or independently observed on, the root's exact physical
Subnet. Contradictory placement fails before Component Registry commitment.

Root and admission limits are Fleet-local policy ceilings, not a measurement
or reservation of shared Subnet capacity. When a root reaches a limit, a new
Component instance must use another already-admitted eligible root or fail
with a typed limit error. Canic does not create a second Fleet Subnet Root for
the same Fleet and Subnet.

App configuration declares logical topology plus Fleet, per-Component and
per-Component-Child scale and cycles-funding limits. Root limits cap aggregate
actual usage across admitted Components; they do not enlarge a Component
allowance. Host planning may express affinity between chatty Components and
anti-affinity where physical failure separation matters. App configuration
contains no physical placement.

## Configuration

One Component Spec declares exactly one direct Component role and a flat
catalog of every role/Wasm that may occur at any depth beneath it. The catalog
does not declare concrete parent edges:


Rules:

- every Component Spec declares exactly one `component_role`;
- that role is always a Component directly below a Fleet Subnet Root;
- a Component role occurs in exactly one Component Spec;
- a Component Spec may declare zero or more potential child roles;
- every role that may occur anywhere below the Component appears once in that
  flat catalog, regardless of runtime depth;
- a child table cannot contain another Component or child table because
  concrete hierarchy is runtime Registry state, not configuration;
- `spawn_grants.<parent-role>.<child-role>` is a flat capability graph, not a
  nested runtime declaration: both roles remain declared once and every
  concrete parent edge still comes only from root-owned Registry state;
- every potential child role has at least one incoming spawn grant, every
  grant has a positive `maximum_instances_per_parent`, and a Singleton target
  has a per-parent maximum of exactly one;
- a parent role may be the Component role or any role in the same child
  catalog; role-graph recursion is permitted because concrete Registry
  parentage is always a finite acyclic tree bounded by aggregate quotas;
- any exact registered Component or child may request only a direct child
  covered by its exact parent-role/child-role grant, subject to the grant,
  Component-tree and root ceilings;
- scaling, sharding and index pools may be configured on the Component or on
  a descendant-manager role, may target only child roles declared by the same
  Component Spec, and require a matching spawn grant from that manager role;
- a pool maximum cannot exceed its matching spawn grant;
- ownership comes only from the concrete root-journalled parent binding and
  cannot change when pool policy changes;
- the same package-backed role may be a top-level Component role in one Spec
  and a potential child role in another Spec;
- `kind = "root"`, `kind = "service"` and `kind = "component"` do not parse;
  the Component role is the one explicit `component_role`;
- `owner_component` does not parse because the containing Component Spec is
  the sole structural owner;
- `wasm_store` is implicit root infrastructure and cannot be configured as a
  Component or child;
- no Component Spec includes or nests another Component Spec;
- a `provisions.<component-spec>` table key is the sole target
  `ComponentSpecId` and is a non-parent authorization reference to that exact
  existing Spec; no second target name or alias is accepted;
- every grant has a positive
  `maximum_instances_per_requester_per_root`; duplicate targets,
  self-targets and grant cycles reject, and a grant never adds target
  admission or artifact capacity;
- grants are Spec-level: every exact instance of the requester Spec has the
  same bounded permission; an App requiring a narrower provisioner class uses
  a distinct requester Component Spec;
- `maximum_instances` is positive and the sum of Spec maxima does not exceed
  the 4,096-Component-instance Fleet bound;
- every Component has explicit aggregate descendant, Registry-byte and
  cycles-funding limits; omitted values compile to finite documented defaults;
- omitted Component limits default to 20,000 descendants and 16 MiB of
  canonical Registry state;
- one Spec has at most 256 distinct child roles, 4,096 spawn grants and 256
  outbound peer-Component grants, and the complete canonical Component
  Topology is at most 2 MiB;
- source config contains no concrete `ComponentInstanceId`, root principal or
  physical `SubnetId`;
- maintained role attachment selects `--component-spec <component-spec>`; and
- removed Subnet Slot, Tree Spec, Tree Group, Tree identity and per-Tree root
  forms do not parse.

Fleet service targets are not a 0.100 configuration surface. A fresh 0.101
installation introduces those declarations and restricts every Fleet-service
member to an admitted Component Spec.

## Component Topology

The canonical admission model carries no static hierarchy. Each Component
Spec contains one flat potential child-role catalog. Concrete recursive
parentage lives in root-owned Component Registry records, while provisioning
grants remain separate from child ownership:

~~~rust
pub struct ComponentTopology {
    pub component_specs: Vec<ComponentSpec>,
    pub provisioning_grants: Vec<ComponentProvisioningGrant>,
}

pub struct ComponentSpec {
    pub component_spec: ComponentSpecId,
    pub spec_hash: [u8; 32],
    pub component_role: CanisterRole,
    pub maximum_fleet_instances: u32,
    pub limits: ComponentLimits,
    pub children: Vec<ComponentChildSpec>,
    pub spawn_grants: Vec<ComponentSpawnGrant>,
}

pub struct ComponentLimits {
    pub maximum_descendants: u32,
    pub maximum_registry_bytes: u64,
    pub cycles_funding: CyclesFundingBudget,
}

pub struct ComponentChildSpec {
    pub role: CanisterRole,
    pub kind: ComponentChildKind,
    pub cycles_funding: ComponentChildFundingPolicy,
}

pub struct ComponentSpawnGrant {
    pub parent_role: CanisterRole,
    pub child_role: CanisterRole,
    pub maximum_instances_per_parent: u32,
}

pub struct ComponentProvisioningGrant {
    pub requester_component_spec: ComponentSpecId,
    pub target_component_spec: ComponentSpecId,
    pub maximum_instances_per_requester_per_root: u32,
}

pub struct ComponentChildFundingPolicy {
    pub max_per_request: Cycles,
    pub max_per_child: Cycles,
    pub cooldown_secs: u64,
}

pub enum ComponentChildKind {
    Singleton,
    Replica,
    Shard,
    Instance,
}
~~~

`ComponentChildKind::Replica` classifies a potential managed role inside one
Component tree. It is not the 0.101 Fleet-service Replica purpose. A
cross-Subnet service Replica is another direct Component instance of the same
Component Spec under a different Fleet Subnet Root.

Component Specs use canonical `ComponentSpecId` order. Potential child roles
use raw role order. Spawn grants use canonical `(parent_role, child_role)`
order. Provisioning grants use canonical
`(requester_component_spec, target_component_spec)` order. The bounded
canonical encoding is domain-separated and length-prefixed. Each root receives
the exact Component Spec projection selected by its `component_admissions`
plus every incoming provisioning grant whose target Spec it admits; that
topology projection alone produces its `ComponentTopologyDigest`. An incoming
grant carries requester Spec identity and authorization limits but does not
pull the requester artifact into that root's release set. The canonically
encoded admissions remain a separate protected capacity authority.

Spawn grants and pool configuration are included in the corresponding
Component Spec hash. A spawn grant is authorization policy; it is not a
concrete parent edge or source of child ownership.

The amended canonical encoder uses maintained schema version `1`, unsigned big-endian
integers and `u64` byte/count prefixes. Spec hashes use domain
`canic/component-spec/v1`; topology digests use
`canic/component-topology/v1`. Before 1.0, an incompatible shape hard-replaces
the maintained v1 encoding; version numbers are never advanced to preserve
superseded state. This reinstall-only design has no prior-shape decoder or
mixed-version path. The Spec ID is encoded by the topology and
admission bindings, not by the reusable Spec-content hash. A Spec hash covers
the exact Component and potential child role/package declarations, spawn
grants, aggregate Component-tree limits, initial cycles, top-up and
cycles-funding policy, scaling/sharding/index pools and
auth/standards/diagnostics/metrics policy.
Empty optional pool tables normalize to an empty pool set. The topology digest
encodes every selected Spec ID, Spec hash, Component role, Fleet ceiling,
compiled limits, potential child-role entry, spawn grant and incoming
provisioning grant in canonical order. Peer-Component grant policy is
topology-level authorization and does not alter either endpoint Spec's
reusable content hash.

Configuration-only deserializers do not cross into the compiled topology.
`ComponentChildFundingPolicy` is the passive compiled equivalent of
`CyclesFundingPolicyConfig`, which keeps the protected Candid model independent
of TOML shorthand parsing.

Root and Component limits are explicit compiled quotas. Funding budgets have
a positive bounded window and amount. They sit above each Component Child's
per-request, per-child and cooldown policy, so a valid child request must pass
every applicable level without treating physical Subnet headroom as an
allocation. A Component's aggregate `maximum_descendants` bounds the entire
dynamic tree above the independent spawn-grant ceilings applied under each
immediate parent.

The Component Topology is the sole topology admission authority:

- a root may create a Component only from an admitted Component Spec;
- a root may create at most the admitted number of instances for that Spec;
- every Component role resolves to exactly one Component Spec;
- an exact registered requester may request only a target named by its
  compiled provisioning grant;
- the selected root enforces both the target Spec admission and the grant's
  per-requester/root ceiling;
- a grant records no parent, controller, Registry owner or child edge;
- any exact registered Component-tree principal may request a direct child
  only when its registered parent role and the requested child role match one
  exact compiled spawn grant;
- every child request binds the exact immediate parent and Component tree;
- a request cannot supply a replacement package, Wasm hash or raw Wasm;
- missing, orphaned or duplicated catalog roles, incomplete or invalid spawn
  grants, and invalid, duplicate, self-referential or cyclic peer-Component
  grants fail during configuration validation; and
- a root's Component Topology and admissions are immutable for that
  installation.

Raw configuration is parsed into a temporary validation shape. Protected
bindings, bootstrap input, Registry rows, Directory entries and durable
runtime state use only the flat compiled catalog plus concrete parent-bound
instances. A `ComponentChildBinding.parent_canister_id` may identify the
Component or another registered child in the same Component tree. It can
never identify another Component, root, Coordinator or foreign Fleet.

The same child role may appear in more than one Component Spec only when it
resolves to the same exact package and qualified artifact. Authorization and
ownership remain scoped by Component Spec, Component instance and principal.

### Registry, Directory and Placement Index terminology

These names are deliberately non-interchangeable:

- a **Registry** is root-owned authoritative lifecycle and parentage state;
- a **Directory** is a read-only, versioned discovery projection derived from
  an exact Registry commitment; and
- a **Placement Index** is application-owned keyed placement state such as
  `project_id -> ProjectInstance`.

Scaling, sharding and indexing are placement strategies. A Placement Index may
use the root child-creation surface to resolve or create an admitted instance,
but an index entry is not Registry evidence, is not a Directory entry and
grants no lifecycle authority. `binding` remains reserved for protected
identity values such as `ComponentBinding`; keyed placement is never called a
Directory or Placement Binding in the current surface.

## Topology-Admitted Release Set and Wasm Store

Every Fleet Subnet Root operates one implicit local `wasm_store`. It is
infrastructure owned by that root:

- it is not a Component;
- it has no `ComponentInstanceId`;
- it is absent from Component Registries and Component Directories;
- it is not a Fleet-authoritative service; and
- Components and Component Children cannot publish to it.

The host builds each qualified application artifact once per
`ReleaseBuildId`, separately from the Canic Infrastructure Artifact Manifest,
then projects one exact Fleet Subnet Root release set for each root:

1. compile the complete Component Topology;
2. resolve every Component and Component Child role to one checked-in role
   declaration and exact Cargo package;
3. reject missing packages, conflicting role/package mappings, orphan
   artifacts and roles outside the Component Topology;
4. build the deduplicated Fleet-wide Component/Component-Child artifact union
   under one exact `ReleaseBuildId`;
5. verify raw and compressed Wasm hashes plus qualified build identity once;
6. project each root's admitted Component Specs from that already-built union;
7. construct one canonical `FleetSubnetRootReleaseSetManifest` containing
   exactly the projected artifacts;
8. record its `ReleaseSetDigest` as that root's initial active release set in
   finalized deployment evidence and the Fleet Registry; and
9. bootstrap the generic store runtime and publish exactly that release set
   before the root becomes runtime `Active`.

~~~rust
pub struct ApplicationArtifactUnion {
    pub release_build_id: ReleaseBuildId,
    pub fleet_component_topology_digest: ComponentTopologyDigest,
    pub entries: Vec<ApplicationArtifactEntry>,
}

pub struct FleetSubnetRootReleaseSetManifest {
    pub release_build_id: ReleaseBuildId,
    pub component_topology_digest: ComponentTopologyDigest,
    pub entries: Vec<FleetSubnetRootReleaseSetEntry>,
}

pub struct FleetSubnetRootReleaseSetEntry {
    pub component_spec: ComponentSpecId,
    pub kind: ApplicationReleaseSetEntryKind,
    pub artifact: ApplicationArtifactEntry,
}
~~~

The union digest is explicitly Fleet-wide. The digest in each projected
manifest is root-local and must equal the canonical projection of that root's
immutable admissions. Pre-build targets bind the accepted role, resolved
Cargo package and raw/gzip output paths; qualified build outputs must match
those targets exactly before their bytes can enter the union.

The host immutably persists the canonical union at
`.canic/release-builds/<release-build-id>/application-artifact-union.json`
before release-build finalization. An exact retry may recover the same bytes
before or after finalization. Conflicting bytes, a union missing at
finalization, noncanonical encoding, release-build mismatch or topology drift
fail closed.

The generic `canic-wasm-store` runtime may be byte-identical across roots.
Each deployed Wasm Store Catalog and release-set projection is root-specific
and contains only the Component/Component-Child closure admitted by that
root.

Admission of a Component Spec always carries its complete flat potential-Wasm
catalog, regardless of which concrete parent-child edges will later exist. A
root admitted for `project_hub` therefore stores the exact `project_hub`,
`project_instance`, `project_ledger` and `project_machine` Wasms once before
activation. Creating one Ledger per Project Instance and a Machine for only
one project in one hundred selects from that already-admitted vocabulary; it
does not upload, discover or duplicate a Wasm at request time.

If two topology entries use the same exact artifact, the store may deduplicate
bytes. Authorization remains represented for every exact Component Spec and
potential child-role entry; byte deduplication never broadens admission.

The root resolves lifecycle Wasm only by protected
`(ComponentSpecId, role, ReleaseBuildId)` context from its active release set.
A Component can request an admitted child role but cannot choose the artifact.
Publication of an undeclared role, a different build, an incomplete topology
closure or a release-set manifest exceeding the root's Wasm Store limit fails
before root activation.

The immutable Component Topology answers what may exist. Component admissions
answer how many instances of each Spec that root may create. The active
release set answers which exact qualified build supplies those roles. The Wasm
Store Catalog proves what is currently published. None may substitute for
another.

The topology digest and admissions are protected root-binding facts. The
active release set is versioned Fleet Registry and root runtime state, not
permanent root identity.

0.100 defines neither live topology/admission expansion nor an active
release-set transition. Accepting a new Component Spec or child role,
increasing an admission, or activating a different release set requires a
fresh installation under this release's reinstall-only boundary. Separating
the state shapes does not introduce an upgrade path.

## Component Identity and Protected Bindings

`ComponentSpecId` is a bounded declaration identifier. It contains 1–40 bytes
using only ASCII letters, numbers, `-` or `_`.

`ComponentInstanceId` is 32 bytes allocated and durably journalled by the
Fleet Subnet Root before Component creation. Its derivation is
domain-separated over the exact Fleet, root principal and a root-owned durable
allocation sequence. Its canonical boundary text is exactly 64 lowercase
hexadecimal characters. Its complete identity is
`(FleetKey, ComponentInstanceId)`; embedding the unique root principal in the
derivation domain-separates allocations from different roots. Any duplicate,
allocation-sequence exhaustion or rollback fails before creation.

This ID is not another logical container. It identifies the concrete
Component creation operation before a Canister principal exists, distinguishes
several instances of the same role and lets response-loss recovery return the
same binding. It has no children beyond those owned by that Component and no
independent placement or lifecycle policy.

A Component Spec hash covers:

- its exact Component role;
- every potential child role, kind and per-parent cardinality;
- role/package identity;
- Fleet, Component and child limits plus cycles-funding policy;
- permitted sharding and binding-relevant configuration; and
- the flat declaration/recursive runtime-tree authority split.

It excludes concrete principals, physical placement, Component Registry rows,
application data, root-local admission allocation and active release identity.

The protected bindings are:

~~~rust

pub struct ComponentBinding {
    pub authority: FleetRegistryAuthority,
    pub component: ComponentInstanceId,
~~~

Every Component retains one immutable `ComponentBinding`. Every Component
Child retains one immutable `ComponentChildBinding` naming its Component tree,
immediate parent, role and principal. The parent may be the Component or
another registered child in that same tree. The root validates the parent
record before mutation, so the binding rejects cross-Fleet, cross-root,
cross-Spec, cross-Component and cross-Subnet parentage even when several
Fleets or Components share one physical Subnet.

The Fleet Subnet Root receives only its root binding and initial active
release set. It is not itself a Component. The Coordinator has only
`FleetCoordinatorBinding`; it receives neither root nor Component binding.

No current protected identity carries a logical Subnet Slot, Tree Spec, Tree
Group, Tree ID or per-Tree root.

Component Specs and roots use canonical ascending order. Snapshot hashes never

admission ceilings are immutable. The sum of all root admissions for one Spec
cannot exceed the Fleet declaration. A root's active release set is explicit
Registry state and must agree with the root runtime and Wasm Store Catalog;
0.100 defines no transition that changes it.

The Fleet Registry does not inventory ordinary Component instances. Their
identity, effects and membership are root-local Component Registry authority.
The Coordinator therefore manages one root per occupied Fleet/Subnet pair,
not every ordinary Component. 0.101 adds only typed Fleet-service mode/member
bindings to the Registry.

## Operator Fleet Subnet Inventory

0.100 closeout adds:

~~~text
canic info subnets <fleet> [--json]
~~~

This is a live, read-only inventory of physical Subnets occupied by the
selected Fleet. It does not claim to enumerate every Canister owned by other
Fleets or operators on those physical Subnets.

The command resolves the Fleet Coordinator from the terminal
canonical-network Fleet catalog row, queries its current Fleet Registry, then
queries one compact controller-only Canister summary from every non-`Removed`
Fleet Subnet Root. The terminal Fleet catalog is Coordinator-anchored; the
single-root `root_principal` catalog shape is hard-cut, with no decoder,
explicit-principal or legacy-root fallback. Its maintained discovery row is:

authority. One canonical-network lock serializes publication; exact same-
Fleet retry returns the durable row, while reuse of a Fleet name, Fleet ID or
Coordinator under contradictory authority fails closed.

The sole writer is behind terminal validation. It recomputes the current
Coordinator Registry manifest and version, matches the complete immutable
root plan to all-`Active` Registry rows and requires one exact active compact
summary for every planned root. The host must not call this boundary until
the existing Component/root runtime journey can supply that complete
evidence. A terminal catalog row therefore cannot be used as an intermediate
installation checkpoint.

Each root summary binds the exact Fleet Registry authority, placement
`SubnetId`, Fleet Subnet Root principal and acknowledged Registry version. It
reports checked counts for:

- root-local infrastructure: the Fleet Subnet Root and its Wasm Store; and
- every top-level Component and Component descendant whose Canister principal
  is known-created and whose deletion is not durably confirmed.

The maintained root query contract is v1:

the runtime parent-child hierarchy is flat.

The summary is derived from bounded root-owned counters and indexes. The CLI
must not download every Component Registry member merely to calculate the
count. The CLI adds the Coordinator itself to its physical Subnet, then
groups a co-located Coordinator and Fleet Subnet Root into one row. Rows are
ordered canonically by physical `SubnetId`.

or runtime-fenced Canisters that still exist. It excludes unresolved creation
reservations without a principal, deletion-confirmed Canisters, `Removed`
root tombstones, non-Canic Canisters and every other Fleet's independently
owned Canisters.

The Component Registry increments its known-created counter atomically with
the first durable recording of a returned Canister principal. Exact retry
cannot increment it again. A later removal workflow may decrement only after
durable deletion confirmation; stopping, runtime fencing, an install failure
or an unresolved deletion attempt does not decrement it. The counter must
remain within the protected root-managed capacity and the Registry's
allocation/descendant accounting or the summary fails closed.

Default text output contains `SUBNET`, `ROOT`, `STATUS` and `CANISTERS`, plus
an exact Fleet total. JSON output is schema-versioned and additionally keeps
the Coordinator principal, Registry revision, root-local infrastructure and
Component counts, and the exact per-Subnet total as separate numeric fields.

## Fleet Registry Commit

Every Fleet Registry mutation:

1. loads the current canonical snapshot;
2. validates the complete requested transition;
3. constructs and deterministically encodes the next snapshot;
4. checks Spec, root, admission and byte limits;
5. writes and durably confirms the complete snapshot;
6. atomically publishes its manifest as current; and
7. returns the new exact version.

The head never references absent or incomplete bytes. No mutation is inferred
from a returned command status alone.

Genesis uses authority epoch 1 and Fleet Registry revision 1. It contains
every compiled Component Spec and zero roots. Root joins advance the revision.

## Authority Epoch and Restore Fence

The authority epoch binds Fleet Registry history to one exact Coordinator.
0.100 records it but does not implement Coordinator replacement.

Mirrors accept only the protected Coordinator, Fleet binding and epoch:

- a lower epoch is stale;
- another Coordinator at the same epoch is contradictory;
- an unexpected higher epoch requires a future explicit design; and
- no root or Component may promote itself.

A restored Coordinator backup cannot resume mutation at the same epoch unless
the latest committed Fleet Registry version is independently proven. 0.100
defines no such proof, so an ambiguous restore remains read-only and
fail-closed.

## Snapshot Synchronization

0.100 synchronizes complete snapshots, not deltas or an event log.

The Coordinator exposes an authenticated inter-Canister update returning the
complete current Fleet Registry, manifest and exact version to a current
non-`Removed` root. Canonical Registry validation bounds the response and
binds the manifest/version before a candidate can commit.

During fresh-install preparation, each Fleet Subnet Root:

1. revalidates its exact local Wasm Store evidence;
2. fetches the current all-`Joining` snapshot;
3. validates Fleet, Coordinator, epoch, revision, Component Specs and roots;
4. verifies the manifest, content hash and host-expected exact version;
5. verifies its exact `Joining` row, admissions, topology digest, release set
   and limits;
6. durably persists a private candidate;
7. acknowledges that exact version to the Coordinator only after the
   candidate commit; and
8. durably records the returned exact acknowledgement.

After the Coordinator later commits the required roots `Active`, each root
fetches and validates the final snapshot, derives its Fleet Directory and
atomically activates the matching Fleet Registry Mirror and Directory. All
Component instances on one root share that active mirror and Fleet Directory.
Interrupted candidate state never becomes active.

The default steady-state poll interval is five minutes. Failures use bounded
backoff from 15 seconds to 15 minutes. Configuration may select 60 seconds to
one hour. Polling stops for removed roots.

## Fleet Subnet Root Registration

Root registration is:

~~~text
absent -> Joining -> Active -> Draining -> Removed
~~~

The Coordinator validates authenticated administrative authority, exact
journalled placement and principal, one root for the Fleet/Subnet pair, exact
Component admissions and Component Topology digest, active release set,
positive bounded limits and absence of conflicting identity.

The recorded root must durably stage the snapshot containing its exact
`Joining` row and acknowledge that exact Fleet Registry version. It must also
prove that its protected binding agrees with the registered topology,
admissions and limits and that its local Wasm Store Catalog agrees with the
registered active release set before becoming `Active`. The staged
all-`Joining` candidate is not activated as the public mirror or Directory.

Exact retry returns the existing result. A failed root join may become
`Removed`; the root principal is never rebound inside 0.100.

## Component and Component Child Lifecycle

### Component creation

An authenticated Fleet administrator, or an exact Component acting under a
compiled Component Provisioning Grant, may request creation of an admitted
Component on one Fleet Registry-`Active`, runtime-`Active` Fleet Subnet Root.
The Coordinator workflow defined by 0.101 may use the same lifecycle while the
root is runtime `Prepared`, but only through that release's explicit
publication barrier. A Component-originated 0.100 request is accepted only
when that same root can verify the requester from its own Component Registry;
0.101 defines cross-root verification through published Fleet-service
membership.

The request binds the exact Component Spec, operation identity and
provisioning origin. It does not supply a `ComponentInstanceId`, principal,
controller or artifact. An administrator origin records the authenticated
administrator. A Component origin records the exact requester
`ComponentBinding` and matching grant as causal evidence, not as a parent
binding.

The root:

1. validates its protected binding, permitted runtime state and Fleet Registry
   Mirror;
2. authenticates the administrator or exact requester Component and, for a
   Component origin, verifies the incoming grant and its
   per-requester/root ceiling;
3. resolves the exact target Component Spec from its Component Topology;
4. checks the Spec admission, Fleet-wide compiled ceiling, root limits and
   current root-local instance count;
5. rejects a competing or contradictory operation;
6. durably reserves the next allocation sequence and derives one
   `ComponentInstanceId`;
7. resolves the exact Component and complete potential-Wasm catalog from its
   active release set in the local Wasm Store;
8. records effect intent before Canister creation;
9. creates and installs the Component on the root's Subnet behind the runtime
   `Prepared` fence;
10. reconciles every uncertain effect before retry;
11. creates the Component Registry partition and commits the exact Component
    row;
12. derives and sends exact Fleet and Component Directories;
13. activates the Component only after matching provenance is observed; and
14. returns an idempotent root receipt containing the exact provisioning
    origin.

The request cannot contain raw Wasm or select another artifact. Exact retry of
the same operation returns the same Component identity, principal and receipt.
The root receipt and committed Component Registry rows are the sole
platform-effect truth; Component-local desired state or a successful call
response cannot replace them.

Ordinary Component creation does not mutate the Fleet Registry and does not
make the Component a Fleet-service member.

### Peer Component provisioning

A Component Provisioning Grant permits one exact requester Spec to cause one
exact target Spec to be created. It does not permit the requester to choose a
different Spec, artifact, build, identity, principal, controller or lifecycle
parent. The target root must already admit the target Spec and contain its
complete active-release-set closure. The effective capacity is the
intersection of the grant ceiling, target Spec admission and aggregate root
limits; a grant creates no capacity of its own.

On the requester's own root, the root authenticates the exact caller against
its local Component Registry. A target on another root requires an
independently authenticated requester projection; merely presenting a foreign
`ComponentBinding` is insufficient. 0.101 uses a current Fleet-service member
binding for that cross-root proof and then invokes this same creation
lifecycle. The target remains an ordinary direct Component of the selected
root.

The target root stores the provisioning origin in its operation and receipt
so exact retry and per-requester/root accounting remain deterministic. It does
not expose the origin as `parent`, copy it into `ComponentBinding`, put the
created Component in the requester's Component Directory or let the requester
manage the created Component's tree.

The grant ceiling counts in-progress reservations plus committed non-Removed
target Components with that exact requester origin on that root. Exact retry
counts once. A qualified administrative removal may release concurrent grant
capacity, but its tombstone and provisioning origin remain durable and no
`ComponentInstanceId` is reused.

### Multi-level Component Child creation and management

Any exact registered Component or Component Child may request one direct child
inside its own Component tree. Every request binds:

- Fleet and authority epoch;
- Fleet Subnet Root and exact `ComponentBinding`;
- exact immediate parent principal and current parent Registry row;
- child role;
- operation identity;
- expected Component Registry version; and
- requested bounded lifecycle effect.

The root verifies that the caller is the exact registered immediate parent,
that the parent belongs to the same Component tree, that the Registry row's
parent role and requested child role match one exact compiled spawn grant,
that the requested role is present in the Spec's flat potential-Wasm catalog
and that the per-parent grant, Component-descendant and root limits permit the
effect. A role's presence in the catalog alone is never authorization.

Before any await, the root durably binds the operation to the exact parent,
child role, active release set and expected Component Registry head, then
atomically reserves the parent-role count, Component descendant capacity and
aggregate root capacity. Exact retry returns that original reservation and
does not charge capacity twice. A reservation is not yet a Registry member:
it does not advance the Component head or Directory. Successful child commit
later transfers the count from reserved to committed and advances the
Component Registry/Directory authority.

The root journals and executes creation, cycles funding, installation, start,
stop and deletion through its canonical platform lifecycle. It
resolves installation artifacts from its active release set. Cycles funding
may target only an exact registered Component Child and is checked against the
compiled per-child policy plus Component and root aggregate limits before
mutation.

New children remain runtime `Prepared` until the root commits the Registry
row with its immutable `parent_canister_id`, derives the new Component
Directory head, sends the child its exact protected binding plus current Fleet
and Component Directory provenance, and observes matching provenance. The root
does not rebroadcast a 20,000-entry snapshot to every member after each
mutation. It then activates the child and records its idempotent receipt. Once
active, that child may use the same surface to create only the direct children
covered by grants from its registered role.

Each parent owns its application policy and domain allocation decisions. The
root owns platform effects, effect recovery and every authoritative Component
Registry row. No parent may target another Component tree, create a top-level
Component as a child, choose raw Wasm or delegate the root's lifecycle
authority. A valid peer-Component request uses the separate grant-checked root
surface above and still grants no lifecycle authority over the result.

Child-subtree removal is a root-journalled post-order operation. The root
first fences new mutations for the subtree, then removes or retains leaves
before their parents, commits each transition idempotently and removes the
target parent only after no live Registry row references it. Interruption
resumes from the durable traversal cursor; it never leaves a committed child
whose immediate parent is absent.

For each selected leaf, the root first freezes the exact leaf, immediate
parent and protected root controller before a management call. Stop execution
then requires the live Canister to retain exactly that sole controller and the
payload module hash resolved through the active root-local Store. An already
stopped leaf is adopted, a `Stopping` leaf is not stopped twice, and a fresh
status read after either call success or error is the only authority that may
commit the durable stopped receipt.

Deletion next freezes that complete stopped receipt as the exact destructive
effect authority. A target already independently observed absent is adopted.
A present target must still be stopped under the same sole root controller and
Store-backed module before the call; a fresh typed status observation after
either call success or error is the only authority that may commit the durable
deleted receipt. Registry membership removal and Directory publication remain
later independent transitions, so deletion never silently changes logical
membership or releases capacity.

### Controller topology

The Fleet Subnet Root is the required Canic lifecycle controller and executor
for every Component and Component Child it manages. A Component is not
installed as controller of its Component Children and cannot bypass the root's
admission, limits, journal or artifact selection through a Canic API.

Any separately declared deployment-recovery controller is explicit protected
installation policy. Controller status alone grants no Coordinator,
Component, Registry, Directory or Wasm Store authority.

`ComponentRegistryMember` is the protected boundary projection. Stable
storage is normalized: the full `ComponentBinding`, provisioning origin and
release-set identity occur once in `ComponentRegistryPartitionRecord`; child
rows store only child-specific fields. The root reconstructs
`ComponentChildBinding` at the boundary. It never stores a complete
`ComponentBinding` in every descendant row.

The primary stable key begins with `ComponentInstanceId` and then the member
discriminator and principal. A separate bounded head exists for each
Component instance. The same collection maintains compact indexes for:

- principal to exact Component/member record;
- `(ComponentInstanceId, parent_canister_id, role, canister_id)` child
  traversal;
- active `(ComponentInstanceId, parent_canister_id, role)` counts for
  spawn-grant enforcement; and
- durable `(ComponentInstanceId, operation_id)` lifecycle work.

This preserves independent revisions and avoids full-partition scans or a
separate stable-memory structure for every possible Component.
`maximum_registry_bytes` charges the canonical partition record, member rows,
index keys/values, retained operation records and tombstones. The root updates
`encoded_bytes` by checked deltas before mutation and fails closed if either
the Component limit or aggregate root Registry limit would be exceeded.

The `ComponentChild` variant carries its tree's `ComponentBinding` and exact
immediate `parent_canister_id`. The parent edge grants only the right to
request admitted direct-child effects through the root; it does not grant
controller, Registry or platform-effect authority. A
`ComponentProvisioningOrigin::Component` is retained for peer-Component audit,
exact retry and grant accounting only and is never interpreted as parentage.

### Directory distribution

The root derives each Component Directory from its exact Component Registry.
It distributes compact Directory provenance directly and serves bounded,
filtered pages from its local indexes. A child commitment prepares the new
child, synchronizes the owning top-level Component and also synchronizes the
exact immediate parent when that parent is a distinct Component Child. These
are the nodes whose global or direct-child discovery view changed. The root
does not materialize a full descendant vector or fan one revision out to
every unrelated child after each mutation. Components do not relay
control-plane Directory authority in 0.100. A future relay would require a
separately designed root-verifiable envelope.

An unrelated active descendant may therefore retain an older valid current
head until it is directly affected. When it later creates a child, the root
may advance it monotonically from that older head to the exact current
revision without replaying intermediate revisions. The immutable Directory
under which it originally activated remains separate and unchanged. This
keeps each child creation to one preparation plus at most two active-member
synchronizations instead of making a 20,000-descendant Component tree an
O(n²) inter-Canister call pattern.

An affected active member satisfies the barrier when independent status shows
the committed authority or a strictly later valid authority that covers it.
The response reports stable coverage evidence for the required authority
rather than mislabelling a later observed head as the member's exact current
status. The root revalidates the requesting parent after all calls and commits
the child Directory receipt last.

For each newly installed node, the root sends one
`ComponentRuntimeDirectoryAuthority` containing the exact active Fleet
Directory and owning Component Directory head. The Component allocation
commit freezes a domain-separated hash of that authority before distribution.
The target retains the complete authority and hash in its existing protected
Fleet activation record and advances only from `AwaitingDirectory` to
`DirectoryPrepared`. An exact retry is response-idempotent; after an uncertain
call the root queries the target, compares the complete retained authority and
hash, independently queries it again and only then records its fixed-size
terminal Directory-prepared receipt.

Directory preparation does not make the Component or root runtime `Active`.
Activation is a separate transition and may occur only from matching retained
Directory evidence. Conflicting target evidence cannot be replaced.

The target's separate `ComponentRuntimeActivationRequest` names only its
protected install operation and exact retained Directory-authority hash. One
atomic target-local transition consumes the prepared application init
arguments, retains the full original activation Directory and hash separately
from its current Directory, records the original activation timestamp and
advances the shared runtime fence to `Active`. It does not invent the retired
cascade or credential evidence. Exact retry returns the original receipt and
never reschedules the application hook.

The root queries before invoking this transition, reconciles an uncertain
response through the same status surface, independently queries the target
again and only then records its fixed-size terminal runtime receipt.
For a Component Child, the public internal root endpoint authenticates the
exact registered immediate parent before the first query and revalidates that
parent after every awaited call before committing the receipt. This
transition preserves the original prepared partition and leaves child
membership absent.
Application Components expose this Directory-bound activation surface instead
of the generic non-root topology-cascade, credential-generation and Fleet
activation mutations. The implicit Wasm Store retains its separately composed
legacy activation surface until that infrastructure lifecycle is replaced.

Runtime activation and Registry membership activation are distinct durable
facts. The first runtime transition remains bound to the immutable prepared
Directory revision. A subsequent root-local transition advances the
Component Registry partition from `Prepared` to `Active`, derives a new
revision-bound Component Directory and synchronizes that current authority to
the already-active target. This ordering preserves the exact response of the
original Directory-preparation operation while preventing an `Active`
Registry row from claiming a target that has not activated. Root runtime
activation requires both receipts and convergence on the current active
Directory.

The root commitment likewise retains the original prepared partition head,
encoded-byte evidence and Directory synchronization observation. Later
partition revisions therefore cannot change the response of commit,
Directory-preparation or runtime-activation retries; those operations
reconstruct their original evidence while current Registry and Directory
queries continue to expose the latest revision.

The first top-level membership transition is one atomic root-local mutation.
It changes the exact partition from revision-one `Prepared` to revision-two
`Active`, recomputes its canonical content hash, replaces exact Registry-byte
accounting and retains a separate immutable membership receipt. The receipt
binds the active Directory hash, derivation observation and stable footprint;
its final bit is committed only after independent target convergence.

Each later child-membership transition likewise changes exactly one normalized
child row from `Prepared` to `Active` and advances the owning partition by one
revision. Its descendant-status digest is an O(1), domain-separated transition
from the previous digest and exact child identity; the root neither walks nor
synchronizes unrelated descendants. The child-specific receipt freezes the
resulting Registry head, descendant digest, reserved and committed counts,
encoded bytes, Directory observation and authority hash. Exact retry can
therefore reconstruct the original response after a later reservation or
child mutation advances current authority. A later valid target Directory may
prove that the original synchronization is covered, but the retry response is
normalized to the frozen membership authority. The fixed-size terminal bit is
committed only after independent target observation and requesting-parent
revalidation.

The target accepts that current Directory only while its runtime is already
`Active`. It requires the exact protected install operation, the same owning
Component and source root, a strictly later Component Registry revision, a
later synchronization observation and non-regressing Fleet Registry
authority. An exact repeated authority is idempotent; a strictly later
revision may skip irrelevant intermediate heads. Updating the current
Directory never replaces the full original activation Directory. Exact
retries of current synchronization return the converged authority, while
exact retries of preparation and activation still return their original
revision-one responses.

Root activation seals the exact ordered set of allocation operations that
exist at the initial activation boundary. The root rejects sealing while any
operation is nonterminal, while Registry counters or bytes differ from the
complete set, or while any Component lacks committed Registry authority,
terminal Directory/runtime/membership receipts and an `Active` current
partition. A domain-separated inventory hash binds every prepared and active
Registry head, Directory receipt, immutable binding and release-set identity
to the protected Fleet activation operation.

Sealing is a one-way pre-activation boundary. A `Prepared` root admits exact
retries of existing operations but no new allocation reservation after the
seal. Immediately before the root transition, it revalidates the sealed
inventory and independently queries every Component runtime for its exact
active current Directory, then records aggregate convergence. Root runtime
activation commits next and a separate terminal receipt is written before
bootstrap may mark the root ready. An interrupted exact retry reconciles an
already-active root into that terminal receipt. Later dynamic allocations are
again admitted once the root is `Active`; they never rewrite the frozen
initial-inventory evidence.

## Component Draining and Removal

Component lifecycle membership is root-local:

~~~text
Active -> Draining -> Removed
~~~

`Draining` excludes new child creation while retaining lookup and
domain-owned evacuation.

Before ordinary removal, the Fleet Subnet Root:

1. durably fences new mutation for that Component;
2. obtains Component-specific quiescence evidence;
3. walks the retained parent indexes in deterministic post-order and
   explicitly stops, deletes or retains each descendant according to the
   requested qualified operation;
4. exports the bounded final Component Registry inventory;
5. binds that inventory to the exact Component and root state; and
6. records the final idempotent receipt.

Removal from local membership is not inferred from an unreachable Canister.
An emergency removal retains an explicit unqualified tombstone rather than
inventing empty inventory or claiming the Canister stopped.

A removed `ComponentInstanceId` is never reused. Component relocation,
principal replacement and adoption require later designs.

Every Component created through 0.100 is ordinary. A fresh 0.101 installation
adds protected group-placement and Fleet-service references; its ordinary
removal endpoint must reject a grouped Component while any such reference or
in-progress group operation remains. The 0.100 removal workflow cannot be
reinterpreted as 0.101 group scale-in.

## Root Draining and Removal

A Fleet Subnet Root may enter `Draining`, after which it accepts no new
Component creation.

Ordinary root removal requires every Component Registry partition to be
quiescent or removed, the local Wasm Store to be quiescent and an exact final
root inventory digest. Emergency root removal stores an explicit unqualified
tombstone for the root and its remaining Component inventory.

Removal does not claim that the physical Subnet or every managed Canister has
stopped. Other Fleets' roots on the same Subnet are unaffected.

A fresh follow-on design that binds group placements or Fleet services to a
root must prevent that root from entering `Draining` or `Removed` while those
references remain. Controller status, an unreachable Canister or a Subnet
failure observation cannot bypass that fence.

~~~rust
    pub directory: ComponentDirectoryHead,
    pub entries: Vec<ComponentDirectoryChildEntry>,
    pub next_cursor: Option<ComponentDirectoryPageCursor>,
}

pub struct ComponentDirectoryPageCursor(pub Vec<u8>);

pub struct ComponentDirectoryChildEntry {
    pub binding: ComponentChildBinding,
    pub kind: ComponentChildKind,
    pub installed_artifact_hash: [u8; 32],
    pub status: ComponentLifecycleStatus,
}

    pub component: ComponentBinding,
    pub source_fleet_subnet_root: Principal,
    pub component_registry_revision: u64,
    pub component_registry_content_hash: [u8; 32],
    pub synchronized_at: Timestamp,

~~~

`FleetDirectoryProvenance` and `ComponentDirectoryProvenance` are not aliases
and cannot substitute for each other. One Component's revision never
invalidates another Component Directory merely because they share a root.

`ComponentDirectoryPageCursor` is opaque, bounded to 2 KiB and bound to the exact
Component, Registry revision, content hash, filter and last canonical key. A
cursor from another revision or query fails as stale rather than silently
mixing snapshots. `limit` is positive and at most 100; it bounds canonical
Registry rows examined as well as returned entries. A sparse role or status
filter may therefore return fewer entries, including an empty page, together
with a continuation. Complete enumeration follows that continuation until it
is absent, and no endpoint returns an unbounded descendant vector.

Component Directory children use canonical
`(parent_canister_id, role, canister_id)` order. The owner Component is
represented once in provenance. Parent links reconstruct the complete
multi-level tree without making a child a Directory authority. Every entry
validates exact Fleet, Fleet Subnet Root, Component Spec, Component and parent
ownership, so co-located Components or Fleets cannot accept each other's
state.

Managed Canisters never fetch the Fleet Registry directly from the
Coordinator. They receive Directory heads from their root and query only the
bounded Component Directory views their application policy needs. The page
endpoint authenticates the caller against the root's exact active normalized
membership before accepting the requested head and filters, so a registered
top-level Component or descendant can inspect its own complete multi-level
tree but cannot select a co-located Component or Fleet.

## Consumer Boundary

The maintained topology API may expose:

- Coordinator and Coordinator Subnet;
- Fleet Subnet Roots and their physical Subnets;
- the local Component Spec, Component instance and root;
- exact Fleet or Component Directory provenance; and
- admitted child roles for the local Component; and
- exact peer Component Specs granted to the local Component.

These are topology candidates, not application routing answers. The optional
Placement Index workflow may maintain an application-local domain-key mapping,
but that mapping is separate from Directory discovery and Registry authority.

Missing state, unknown identity, inactive status, Spec mismatch, Component
mismatch, Fleet mismatch, root mismatch, authority mismatch and corrupt
projection return typed failures.

## Authorization

The Coordinator uses the Fleet-scoped trust boundary installed with the fresh
Fleet. It does not create a second administrator list or token audience.

Every Coordinator/root control-plane endpoint binds caller principal, Fleet,
authority epoch, root, expected Fleet Registry revision/hash and operation
identity.

Every Component-tree/root lifecycle endpoint additionally binds the exact
caller and immediate parent principal, Component instance, Spec, requested
catalog role, expected Component Registry revision/hash and effect identity.

Every peer-Component provisioning endpoint additionally binds the exact
requester identity, requester Spec, target Spec, matching grant, target root,
operation identity and expected target-root topology/admission state. A local
0.100 root accepts only a requester proven by its own Component Registry. A
foreign Component binding or controller assertion has no authority; 0.101
adds the exact published cross-root requester proof.

Controllers do not gain synchronization or Component authority merely by
being controllers. Component Children may request their own admitted direct
children but have no root lifecycle-execution authority. A root belonging to
another Fleet on the same Subnet has no authority in this Fleet.

Root-signed role-attestation issuance is available only after the Fleet Subnet
Root is `Active`. Prepare resolves the caller to one exact active Component or
Component Child in the root-owned Component Registry and requires the request
subject, catalog role and physical Subnet to match that protected row.
Retrieval revalidates current active membership and remains keyed to the same
caller and prepared payload hash. Neither ambient runtime configuration,
controller status nor the removed `SubnetRegistry` is role-attestation
authority.

## Failure and Recovery

For every external effect, durable intent precedes invocation. After an
uncertain outcome, restart observes authoritative state before retrying.

Same-release recovery must be single-writer, monotonic, identity-bound,
bounded in attempts and retained evidence, deterministic for exact retry and
fail-closed for contradictory or unknowable state.

Completed operations return their recorded result without repeating external
work. Retryable transport failure never rewinds committed Registry state.

A restored Fleet Subnet Root cannot allocate a new Component identity unless
its latest durable allocation sequence and every active Component Registry
head are proven. Ambiguous restored state remains mutation-fenced rather than
risk reusing a `ComponentInstanceId`.

A root outage pauses lifecycle effects and Directory refresh for its managed
Components. Already-active Components and Component Children continue from
their last authenticated active Directories unless application policy
requires fresher state. Root absence is not interpreted as proof that the
physical Subnet or every managed Canister is stopped.

Root mutation scheduling is partitioned by `ComponentInstanceId`; there is no
root-wide Component Registry mutex. Each partition serializes its short
Registry compare-and-commit sections by expected revision, while durable
reservations allow independent platform calls on separate branches to remain
in flight concurrently. Per-parent/role counts are reserved atomically before
an await. One Component's failed or incomplete operation cannot hold another
Component's lifecycle journal or Registry lock, and a slow branch does not
block an unrelated branch except at that Component's bounded commit fence.
Root-wide managed-Canister, Registry-byte, Store-byte and cycles budgets still
use checked aggregate reservations. Scheduling, in-flight work and retained
journals are bounded globally and per Component.

Failure of one Fleet's root does not mutate another Fleet's root merely
because both occupy the same Subnet.

## Follow-On

0.101 is another fresh installation. It adds bounded composable
`ComponentGroupSpec` declarations that flatten completely before planning;
they do not reintroduce Tree identity or runtime nesting. The same Component
Spec may be materialized repeatedly on one or several admitted roots with
typed Ordinary, Authority, Replica or PoolMember purpose. Every concrete group

`AuthorityReplica` publishes one same-Spec Authority plus zero or more

Target-level member density/spread is independent of deployment placement, so
an installation may enforce anti-affinity or explicitly permit co-location.

consistency. 0.101 provisions initial placements and permits explicit
monotonic scale-out with exact never-reused placement IDs and
placement-to-root assignments.

Root. The root resolves every Wasm from its exact active release set in the
topology-admitted Store. 0.101 does not preserve service Canisters from 0.100,
expand admissions during scale-out, implement group scale-in through the
ordinary Component/root removal paths or implement application-data
synchronization. It also uses published Fleet-service membership to let an
exact Component Provisioning Grant cross root boundaries without routing
high-cardinality Component creation through the Coordinator.
