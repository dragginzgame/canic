# Canic 0.105 Design: Fleet Estate Platform Qualification

Date: 2026-08-15

## Status

- Status: direction approved; repository-only B1 evidence and qualification
  harness work may begin. B2 live-network measurements require a separate,
  exact maintainer authorization before any external effect.
- Implementation posture: evidence only. This line introduces no production
  pool policy, stable record, Candid method, CLI command, timer owner or
  canister runtime behavior.
- Sequence: this line follows the 0.104 synchronous lifecycle-composition
  design and precedes the renumbered 0.106 transport groundwork. It is the
  mandatory platform predecessor of the full 0.114 Fleet-estate design.
- Release posture: an implementation slice or completed qualification report
  is not itself a package release. Cargo versions remain maintainer-owned.
- Repository scope: Canic only. No sibling or downstream repository is
  modified by this work.
- Compatibility posture: no compatibility surface is introduced. The
  qualification observes one exact current Canic and IC contract; it does not
  adopt, decode or migrate pool state across releases.

## Decision

Canic will qualify the risky external facts needed by a 1,000-Canister reserve
Fleet now, without pulling the complete estate state machine and operator
surface forward.

This line extracts the former 0.114 M0 into one independent evidence
authority. It answers whether the current platform can safely support the
future design and freezes the measured inputs needed for implementation. The
full 0.114 design remains responsible for indexed estate state, parallel
production lanes, reserve-Fleet composition, cross-Fleet transfer, claim
funding and the final 10/100/1,000 proof.

The qualification has two effect boundaries:

1. repository and local evidence may be implemented under this approved
   design; and
2. disposable remote-network or IC-mainnet effects require a later explicit
   authorization naming the network, identity, asset ceiling, cycle ceiling
   and terminal asset disposition.

Approving this design does not authorize Canister creation, cycle transfer,
controller mutation or deletion on an external network.

## Why This Work Moves Forward

Canic already owns the essential small-pool safety primitives:

- one root-owned physical-Canister ledger;
- exact-Subnet Cycles Ledger creation;
- intent-before-effect and bounded replay behavior;
- controller, module, balance and Subnet observation;
- claim, reset, recycle and root-draining handoff; and
- bounded status pagination.

The current pool is nevertheless an elastic `Ready` buffer rather than a
fixed estate. It admits only one pending creation record, processes one reset
candidate per maintenance pass, wakes on a 30-second maintenance interval and
derives hot counts through complete inventory exports. Configuring
`minimum_size = 1000` would therefore be an unqualified serialized workaround,
not the maintained reserve-Fleet contract.

The highest-risk unknowns are platform behavior, cost, safe balances,
throughput and the current state that must be replaced. They are useful to
resolve early and do not require the production hard cut.

## Goals

0.105 must:

1. prove whether an explicitly placed Fleet Subnet Root with zero application
   Components can install and activate without a dummy role;
2. freeze the current Cycles Ledger creation, deduplication, fee, `TooOld`,
   exact-Subnet and uncertain-result contract;
3. measure creation and reset behavior at bounded lane counts of 1, 8, 16 and
   32 in qualified disposable environments;
4. perform only the smallest separately approved IC-mainnet sample needed to
   confirm that the disposable result is directionally valid;
5. measure safe empty-standby balance and later claim/install headroom;
6. freeze the controller-transition and same-Subnet routing observations on
   which 0.114 can rely;
7. inventory current stable-memory identities, encoded maxima, complete scans,
   replay ceilings and timer ownership;
8. publish exact duration, rate, cost, failure and uncertainty evidence;
9. recommend bounded production defaults without implementing them; and
10. leave one reviewable qualification report that 0.114 must consume.

## Non-Goals

0.105 does not:

- create a 1,000-Canister Fleet;
- add `owned_target`, `owned_maximum`, `ready_reserve` or estate configuration;
- change `minimum_size`, `maximum_size` or current pool semantics;
- add parallel production creation or reset lanes;
- add pause, resume, target or concurrency administration;
- add a production reserve App or dummy Component;
- implement cross-Fleet transfer or a controller saga;
- fund a root or its Cycles Ledger account automatically;
- add a stable record, storage migration or compatibility decoder;
- change Candid, generated clients, public DTOs or CLI help;
- claim that Canister identities reserve shared Subnet compute, memory or
  storage;
- infer mainnet safety from PocketIC alone; or
- modify IcyDB, Toko or another downstream repository.

If qualification requires a production contract change to proceed, the batch
stops and records the blocker. That change belongs to an explicitly promoted
implementation design, not hidden M0 scope.

## Qualification Baseline

Every evidence run records:

- immutable Canic commit and package version;
- clean or exactly enumerated source state;
- Rust toolchain and ICP CLI identity;
- exact Cycles Ledger and management method surface;
- network, Subnet and observation date;
- resolved caller Principal without its local identity alias;
- relevant Canister Principals;
- requested concurrency and asset count;
- starting and ending cycle balances; and
- whether the run was simulated, local, disposable remote or IC mainnet.

Results from different networks remain separately labelled. PocketIC proves
state-machine behavior; it does not prove IC throughput, current fees or
Subnet capacity. A remote test network may measure real asynchronous behavior
but is not silently relabelled as IC-mainnet evidence.

## Q1: Empty-Topology Fleet Proof

The host proof builds one ordinary Fleet plan containing:

~~~text
one Fleet Coordinator
  + one explicitly placed Fleet Subnet Root
  + one sibling Wasm Store
  + zero application Components
  + zero dummy roles
~~~

The proof must establish:

- strict Fleet input accepts the exact empty application topology;
- root and Store placement and creation funding remain explicit;
- the install plan contains no invented Component admission or placement;
- the root reaches the ordinary `Prepared` and `Active` barriers;
- the Coordinator publishes a terminal catalog with exact infrastructure
  counts and zero workload Components; and
- exact retry after an interrupted same-release install resumes the same plan.

The proof first uses host fixtures and PocketIC. A disposable remote install is
optional and separately authorized. If the current installer rejects a valid
empty topology, 0.105 records the exact failed invariant and the later 0.114
reserve-Fleet batch owns the correction.

No checked-in production reserve App is added in this line. A bounded test
fixture may express the empty App shape without becoming a maintained product
profile.

## Q2: Cycles Ledger Creation Contract

The qualification freezes the exact current behavior of concurrent
Cycles-Ledger Canister creation:

- request fields included in duplicate identity;
- `created_at_time` precision and accepted window;
- exact Ledger fee and creation amount accounting;
- successful duplicate response behavior;
- definite rejection behavior;
- `TooOld` behavior before and after an uncertain result;
- response loss after a paid effect;
- whether an exact result can be recovered without opening another paid slot;
- exact requested Subnet placement; and
- observed controller set of the resulting Canister.

Each lane has a unique canonical operation identity. A retry reuses the exact
request. No harness converts `TooOld`, timeout or transport uncertainty into a
fresh paid request unless the platform evidence proves the original effect
did not occur.

The report separates:

- creation cycles consumed;
- Ledger fees consumed;
- cycles retained in the new Canister;
- unresolved reserved exposure; and
- root/harness execution cost.

## Q3: Creation And Reset Throughput

Measure one-lane behavior first, followed by bounded 8-, 16- and 32-lane
cohorts. Creation and reset are measured independently and as one complete
create-to-Ready journey.

For each cohort record:

- admitted, started, completed, rejected and unresolved operations;
- wall-clock completion time;
- completions per minute;
- median and tail latency from the observed sample;
- lane saturation and effective concurrency;
- throttling, queueing and replica rejection;
- instructions and stable-memory access where observable;
- cycles consumed, retained and reserved;
- recovery after response loss or interrupted scheduling; and
- whether one slow lane blocks independent lanes.

The harness must be completion-driven. A timer may recover abandoned work but
must not manufacture throughput by blindly reissuing paid calls.

The 8/16/32 cohorts are not proposed defaults. The accepted report selects the
smallest useful default and a conservative immutable maximum from evidence.
An unsupported lane count is rejected rather than rounded or silently
serialized.

## Q4: Standby And Claim Balance

Measure balances as distinct concerns:

1. the minimum retained balance at which an empty, root-controlled and
   uninstalled asset can safely remain `Ready`;
2. reset and observation burn;
3. the balance required to claim, install and activate a representative
   workload with explicit headroom; and
4. an informational high-balance observation threshold.

The report may recommend:

- `standby_minimum_cycles`;
- `claim_threshold_cycles`;
- `claim_top_up_cycles`; and
- `overfunded_observation_cycles`.

They remain dated recommendations, not 0.105 runtime constants. No maximum
accepted balance or autonomous sweep is introduced.

The representative workload and Wasm are named exactly. Results from a tiny
fixture are not generalized to every App without an explicit headroom rule.

## Q5: Controller And Same-Subnet Observation

Using bounded test assets, freeze the platform facts needed by later transfer:

~~~text
created asset:
    [owning root]

reset Ready asset:
    [owning root], no installed module

qualified controller transition:
    [source root]
      -> [source root, destination root]
      -> [destination root]
~~~

This is a platform proof, not the 0.114 durable transfer protocol. It must
record:

- which current controller may issue each management call;
- the observed controller set after every call;
- module-hash and stopped/running observations;
- exact source and destination root Principals;
- source and destination physical Subnet evidence;
- behavior when routing evidence is missing, stale or contradictory; and
- interruption points which require forward convergence rather than rollback.

Controller status alone never establishes Fleet, App, root or Component
authority. Same-Subnet placement alone grants no transfer permission.

## Q6: Current State And Scan Inventory

Before 0.114 selects new stable allocations, 0.105 inventories:

- every current physical-asset record and state;
- current creation, reset, claim, recycle and handoff records;
- exact stable-memory IDs and owner modules;
- encoded record sizes and configured or structural maxima;
- the receipt-backed intent and resource-identity ceilings touched by creation;
- full inventory exports and scans in maintenance, claim, capacity, summary
  and status paths;
- current derived counts and missing durable counters/indexes;
- the single pending-creation owner;
- reset selection and ordering;
- the 30-second maintenance timer and non-overlap lease; and
- restart and snapshot reconstruction owners.

The inventory classifies each item as retained authority, replaced authority,
derived view or temporary evidence. It does not allocate the future stable IDs
or mutate current records.

## Evidence Bundle And Report

Working evidence lives under:

~~~text
docs/audits/working/0.105-fleet-estate-platform-qualification/
~~~

The bundle remains within the ordinary eight-file governance ceiling. It
contains one compact index and consolidated evidence rather than one file per
run, lane or source module.

The terminal qualification report includes:

- pass, fail or unresolved verdict for Q1-Q6;
- recommended creation and reset default/maximum parallelism;
- measured standby and claim funding values;
- exact current-state/stable-allocation constraints;
- measured cost and duration for the bounded cohorts;
- a modelled, explicitly non-promissory 10/100/1,000 estimate;
- the smallest safe later IC-mainnet qualification procedure;
- every blocker assigned to its future 0.114 batch; and
- exact evidence freshness and revalidation conditions.

The report does not claim 1,000-asset qualification. Only the 0.114 closeout
may make that claim after the real 10/100/1,000 journeys.

## External-Effect Authorization

Before any remote or IC-mainnet effect, a separate maintainer authorization
must freeze:

1. exact network and physical Subnet;
2. exact caller Principal and controlled root;
3. maximum new Canister count;
4. maximum total cycles transferred or consumed;
5. maximum concurrent lanes;
6. test start/stop and abort conditions;
7. terminal controller set and asset disposition; and
8. whether assets are retained, transferred or explicitly deleted later.

Identity aliases, seed phrases, passwords and other secrets never enter the
plan, logs, receipts or report. Deletion is a separate destructive action and
is not implied by permission to create test assets.

## Implementation Slices

### Slice A: Repository Inventory And Harness

- freeze the immutable baseline;
- inventory current state, scans and external call ownership;
- add bounded host/test harnesses without production endpoints;
- prove empty topology through host fixtures and PocketIC; and
- exercise concurrent lane decisions, exact retry and interruption locally.

### Slice B: Disposable Platform Qualification

- run the bounded cohorts on an approved disposable environment;
- capture Ledger, controller, routing, balance and throughput evidence;
- reconcile every created Principal and paid request; and
- reduce the evidence to proposed mainnet bounds.

### Slice C: Explicit Small Mainnet Confirmation

- stop until the external-effect authorization is recorded;
- run only the approved count/concurrency/budget;
- compare the result with disposable evidence without relabelling either;
- reconcile every asset and terminal controller set; and
- publish the accepted qualification report.

These are evidence slices, not package versions or production protocol
generations.

## Release-Batch Plan

| Batch | Outcome | Owner | Included evidence | Validation | Status |
| --- | --- | --- | --- | --- | --- |
| B1 | Reproducible repository/local qualification boundary | host planning, test harness and current pool inventory | immutable baseline, Q1/Q6, local lane/retry/controller proofs and exact external plan | focused host, control-plane and PocketIC checks; no external effects | Approved to begin |
| B2 | Dated platform qualification and accepted handoff to 0.114 | qualification harness and audit report | Q2-Q5 disposable measurements, separately approved minimal mainnet confirmation, cost/balance recommendations and complete reconciliation | bounded run-specific checks plus maintainer evidence review | Blocked on B1 and explicit external authorization |

This line intentionally has two release batches rather than the usual six to
ten. It is a bounded evidence-only predecessor, introduces no maintained
runtime surface and is separated at the external-effect authorization
boundary. Manufacturing additional patch-sized batches would not improve
reviewability. Neither batch independently requires a package release.

## Validation Requirements

Repository validation is targeted to the harness and evidence changed. It
must include:

- strict empty-topology plan acceptance and nearest invalid topology;
- exact same-release interrupted install recovery;
- lane-capacity equality and first-excess rejection;
- duplicate request equality and conflicting-retry rejection;
- definite failure, uncertain result and response-loss recovery;
- checked aggregate count and cycle arithmetic;
- one slow lane not serializing independent local lanes;
- controller/routing contradictions failing closed;
- bounded report pagination; and
- source guards proving no production endpoint, stable record, Candid or CLI
  surface entered 0.105.

External evidence is validated against its frozen run plan. A successful call
without complete cost, Principal, Subnet and terminal-controller reconciliation
is an invalid run.

## Freshness And Revalidation

Semantic evidence remains usable only while the observed Cycles Ledger and
management contracts are unchanged. Throughput, fees, balances and capacity
are dated measurements rather than timeless constants.

Before 0.114 mutating work freezes production defaults, it must compare the
current platform with the 0.105 report. A changed method contract, fee,
deduplication window, routing authority, controller behavior or materially
different platform environment triggers the smallest affected remeasurement.
Unchanged semantic proofs are not repeated merely because design numbering
advanced.

## Relationship To Other Designs

### 0.102

Compact diagnostics are independent. Qualification failures remain typed
current failures; 0.105 allocates no future estate diagnostic code.

### 0.103 And 0.104

Application authorization and synchronous lifecycle composition neither gate
nor gain authority from this evidence line. Their peer-reviewed identities
remain unchanged. Evidence batches may proceed independently.

### 0.106 Through 0.113

These renumbered provisional designs retain their order and implementation
status. Transport, Workers, authentication profiles, blob extraction, root
funding, snapshot archives, language-neutral guests and the observatory do not
become part of the qualification harness.

### 0.114

0.114 is the sole production owner of Fleet Subnet Canister estates and
reusable reserve Fleets. Its former M0 is replaced by this accepted predecessor
report. No mutating 0.114 batch begins until 0.105 B2 is accepted or a
maintainer explicitly amends that predecessor gate.

## Acceptance Criteria

0.105 is complete only when:

1. one immutable current baseline is reproducible;
2. an empty-topology explicit root and sibling Store reach terminal Fleet
   activation without a dummy Component, or an exact later-owner blocker is
   accepted;
3. current Cycles Ledger duplicate, fee, `TooOld`, uncertainty and exact-Subnet
   behavior is frozen;
4. 1/8/16/32 creation and reset cohorts have bounded disposable evidence;
5. the separately authorized mainnet confirmation stays within its exact
   count, concurrency and cycle ceilings;
6. every created Principal, paid operation and final controller set is
   reconciled;
7. standby, claim/install and overfunded-observation recommendations are dated
   and workload-qualified;
8. controller transition and same-Subnet routing observations are explicit;
9. current stable IDs, encoded maxima, receipt ceilings and full scans are
   complete;
10. proposed defaults distinguish evidence from examples and promises;
11. the final report models but does not claim 1,000-asset readiness;
12. no production pool policy, runtime state, Candid, CLI or timer behavior
    changed;
13. no sibling repository changed;
14. no external effect occurred without its separate exact authorization; and
15. 0.114 names the accepted report as its mandatory predecessor.

## Promotion Gate

B1 may begin under this design. B2 repository preparation may proceed, but no
remote effect begins until the maintainer approves the exact external run
plan. 0.105 completion authorizes no production estate implementation by
itself.

After the qualification report is accepted, 0.114 may request promotion of
its first mutating batch. That review must use the actual observed limits and
must not silently preserve illustrative values from the estate design.
