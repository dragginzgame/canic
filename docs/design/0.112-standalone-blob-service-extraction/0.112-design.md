## Ownership and build boundary

`ic-blob-storage` owns content identity, upload manifests, references, tenant
policy, provider interaction and accounting. Its standalone entrypoint and client
tools have no Canic dependency. The sibling checkout is read-only context.

Canic owns `integrations/blob-service`, a main-workspace member that depends
on the published service library and the Canic facade. It owns only endpoint,
platform and lifecycle composition. Its catalog, lockfile and release version
are owned by the main workspace; the two application consumers remain separate.
The catalog selects published Blob Storage/contracts, sharing the selected Memory
and Timers runtime with Canic. The adapter is part of the published Canic family.
The [composition guide](../../features/blob-storage/README.md) owns the maintained
adoption boundary; the current handoff records exact qualification selections.
Independent upstream ownership does not require an independent adapter workspace.

The adapter is a reusable library with optional placement. `mount!` adds endpoints
and host-selected memory grants to an existing application. The application
composes synchronous lifecycle functions and blob metric rows with its own
participants and sole sampler. `canister!` assembles those same parts into a
dedicated shell. Both retain one Canic lifecycle and Candid export; neither
requires a direct service dependency in the consumer. Build scripts and package
metadata select the consuming App's exact configuration and role.
The example consumer is a separate workspace under the adapter, with no direct
service-library dependency. The library re-exports upstream DTOs for installation
and calls instead of defining parallel contracts. Host admission permits helpers
to share the role's exact public Canic facade, while still rejecting additional
Canic/memory/timer identities, undeclared feature activation and alternate paths to
protected internals. The adapter itself carries no App metadata or build script.

The adapter uses ordinary Canic managed endpoints and Fleet guards. Explicit
rejection mode preserves the provider's plain certificate reply. Service-specific
authority remains enforced by the shared service workflows; controllers do not
become tenant operators. Certificate issuance commits synchronously without an
intervening await. Query/update decoding has raw-byte, work, skip, type and header
bounds. The owning lifecycle macro bounds the outer envelope before restoration;
the participant bounds the nested configuration.

Canic owns the sole default `ic-memory` runtime. The adapter declares seventeen
service grants in its application-owned range before bootstrap, then opens those
committed grants synchronously. It must never bootstrap a second runtime.
Restoration opens the shared service fenced. Platform-version observation and
independent current-instance proof preserve the library's recovery contract.
Older-snapshot activation and cross-release migration are unsupported.

## Production application initialization

A Component Spec with `application_init_required = true` holds the allocated
Component before installation. Both example consumers require it. Root owns
allocation and the protected Canic envelope; the application owns encoding its
nested installation contract after observing the exact allocated Principal.

Controller-visible pool claims identify the target and member operation; Root
operation status exposes those member allocations only to controllers, including
Component Group allocations.

The controller supplies `RootCommand::BindComponentInitialization` with the
existing member allocation operation ID, exact target Principal and 1–16,384
opaque application bytes. Host's `component_initialization::encode_command`
checks bounds and encodes that production command without importing blob DTOs.
Root validates its retained allocation and topology, charges registry capacity,
and atomically retains the binding before any install effect. First binding is
permitted only in the allocated/created phase. Exact replay is effect-free;
changed bytes or target cannot replace a retained binding.

The install intent binds the hash of target plus exact application bytes.
Ordinary and Component Group installation share this path and deliver those
retained bytes after the framework-owned envelope. Root restart, missing replies
and the existing management-install reconciliation retain the same operation;
a different application initializer never repairs or replaces an issued intent.
The application producer must retain its prepared command and reconcile Root's
operation status before retrying. The controller authenticates at the Root
endpoint; no application override or copied blob adapter is involved.

This changes the current configuration hash, Root wire contract and stable
allocation record through a pre-1.0 hard cut. Earlier releases require clean
reinstall; there is no predecessor reader or migration. Same-release interruption
recovery remains required. The synthetic Component fixture's post-allocation
callback separately qualifies application composition and is not production
Root delivery evidence.
