# Upstream Ownership and Standalone Blob Extraction

## Duplication-removal plan — 2026-10-13

The maintainer requested this plan and its in-repository implementation after
the extraction audit. Extend the existing 0.112 integration outcome; do not
allocate a patch per slice. The goal is one executable owner for reusable
mechanics, with the superseded implementation and generic tests removed when
the production caller adopts that owner. Dependency selection, declaration
moves and fewer local lines alone do not establish faster builds or smaller Wasm.

### Ownership

| Concern | Upstream owner | Canic retains |
| --- | --- | --- |
| Backup filesystem and command custody, transfer steps | IC Backup | Fleet membership/controllers, original effect authority, application consistency, terminal qualification and CLI |
| Input evidence, Cargo dependency discovery and cache transactions | IC Build | Generated-input recipe, source exclusion/admission, exact finalized-release qualification and operator diagnostics |
| Certificate/witness and ledger-block evidence | IC Query, using Agent verification | Exact mint intent/account/memo/amount binding, spending authority and paid-result reconciliation |
| Anonymous replica query envelope and response codec | IC Agent | ICP environment/origin selection, HTTP policy and readiness Candid projection |
| Canonical auth protocol and scope/grant rules | IC Auth/protocol types | Fleet/role projection, caller binding, issuance policy and committed replay/session state |

Retain Core/Control Plane lifecycle, provisioning, registry and cycle-conservation
workflows. Retain Canic fixtures proving those product contracts. IC Metrics
continues owning arithmetic, while Canic owns performance sampling/attribution.
Do not move a product workflow upstream merely because it is large.

### Coherent batches

**B1 — Backup custody convergence.** Consume published journal exclusion directly
(the concurrent adoption already does this). Replace layout/reference and command
custody only as one complete original-journal/command integration: persist exact
command custody before dispatch, retain bounded process execution, independently
qualify terminal journal bytes, and hold every quiescence guard through durable
reference release. Remove local generic lock/reference owners and their generic
tests. Keep product interruption, uncertain-command, lost-publication-response,
original-authority and effect-free terminal replay cases. A reconstructed inode,
empty command list or all-completed projection is not terminal evidence.
Subsequent capture/restore workflow adoption follows the same original authority,
never a second journal permitting the same effect. Owning issue: Canic #513.

**B2 — Build-input convergence.** Consume IC Build 0.2.2's published standalone
input-evidence and depfile API. Its concurrent adoption is recorded in the current
handoff; do not reintroduce its removed private scanner or snapshot owner.
Canic supplies its generated-export names, selected roots/exclusions,
tools and environment. Replace generic file inventory, framing/hash, depfile
parsing and before/after mutation checks together. Preserve external inputs,
disappearing inventories and refusal of newly discovered inputs. Retain
CompleteBuildReuse release admission and operator lock diagnostics. Qualify cold
build/reuse, changed source/tool/environment/features, malformed evidence and
retained outputs through the real caller. Owning issues: Canic #530, Build #12.

**B3 — Read-only transport and evidence convergence.** First replace Canic's
anonymous query CBOR owner with the already-selected IC Agent while retaining
anonymous HTTP, selected origin, no proxies/redirects, bounded elapsed time and
typed rejection/transport failures. Remove the old codec and generic codec tests;
retain real HTTP boundary tests and readiness projection. Separately qualify a
bounded typed IC Query certificate/tip/block API before deleting local receipt
decoders. Keep ledger evidence validation separate from Canic mint decisions.
No certificate budget or typed failure may be lost to save lines.

**B4 — Auth protocol convergence.** Reuse existing upstream passive types where
Fleet/role semantics agree; retain projections where they do not. Adopt published
shared scope/grant validation (Auth #50) before deleting its local owner. Verify
canonical hashes, Candid/Serde structure, invalid-role ordering and zero issuance
on refusal. Remove redundant generic tests while keeping Canic authority cases.
Owning issue: Canic #491.

## Ownership and build boundary

`ic-blob-storage` owns content identity, upload manifests, references, tenant
policy, provider interaction and accounting. Its standalone entrypoint and client
tools have no Canic dependency. The sibling checkout is read-only context.

Canic owns `integrations/blob-service`, a main-workspace member that depends
on the published service library and the Canic facade. It owns only endpoint,
platform and lifecycle composition. Its catalog, lockfile and release version
are owned by the main workspace; the two application consumers remain separate.
The catalog selects published Blob 0.22, sharing the selected Memory
0.35 and Timers runtime with Canic. The adapter is unpublished.
Independent upstream ownership does not require an independent adapter workspace.

The adapter is a reusable library with optional placement. `mount!` adds endpoints
and host-selected memory grants to an existing application. The application
composes synchronous lifecycle functions and blob metric rows with its own
participants and sole sampler. `canister!` assembles those same parts into a
dedicated shell. Both retain one Canic lifecycle and Candid export; neither
requires a direct service dependency in the consumer. Build scripts and package
metadata select the consuming App's exact configuration and role.
The example consumer is a separate workspace under the adapter, with no direct
service-library dependency. The library re-exports upstream DTOs for installation
and calls instead of defining parallel contracts. Host admission permits helpers
to share the role's exact public Canic facade, while still rejecting additional
Canic/memory/timer identities, undeclared feature activation and alternate paths to
protected internals. The adapter itself carries no App metadata or build script.

The adapter uses ordinary Canic managed endpoints and Fleet guards. Explicit
rejection mode preserves the provider's plain certificate reply. Service-specific
authority remains enforced by the shared service workflows; controllers do not
become tenant operators. Certificate issuance commits synchronously without an
intervening await. Query/update decoding has raw-byte, work, skip, type and header
bounds. The owning lifecycle macro bounds the outer envelope before restoration;
the participant bounds the nested configuration.

Canic owns the sole default `ic-memory` runtime. The adapter declares seventeen
service grants in its application-owned range before bootstrap, then opens those
committed grants synchronously. It must never bootstrap a second runtime.
Restoration opens the shared service fenced. Platform-version observation and
independent current-instance proof preserve the library's recovery contract.
Older-snapshot activation and cross-release migration are unsupported.

## Production application initialization

A Component Spec with `application_init_required = true` holds the allocated
Component before installation. Both example consumers require it. Root owns
allocation and the protected Canic envelope; the application owns encoding its
nested installation contract after observing the exact allocated Principal.

Controller-visible pool claims identify the target and member operation; Root
operation status exposes those member allocations only to controllers, including
Component Group allocations.

The controller supplies `RootCommand::BindComponentInitialization` with the
existing member allocation operation ID, exact target Principal and 1–16,384
opaque application bytes. Host's `component_initialization::encode_command`
checks bounds and encodes that production command without importing blob DTOs.
Root validates its retained allocation and topology, charges registry capacity,
and atomically retains the binding before any install effect. First binding is
permitted only in the allocated/created phase. Exact replay is effect-free;
changed bytes or target cannot replace a retained binding.

The install intent binds the hash of target plus exact application bytes.
Ordinary and Component Group installation share this path and deliver those
retained bytes after the framework-owned envelope. Root restart, missing replies
and the existing management-install reconciliation retain the same operation;
a different application initializer never repairs or replaces an issued intent.
The application producer must retain its prepared command and reconcile Root's
operation status before retrying. The controller authenticates at the Root
endpoint; no application override or copied blob adapter is involved.

This changes the current configuration hash, Root wire contract and stable
allocation record through a pre-1.0 hard cut. Earlier releases require clean
reinstall; there is no predecessor reader or migration. Same-release interruption
recovery remains required. The synthetic Component fixture's post-allocation
callback separately qualifies application composition and is not production
Root delivery evidence.

## Removal and operator behavior

Remove the embedded blob/billing features, DTOs, macros, storage records,
provider client, stable IDs 55–58, CLI command group and Medic option. Remove their
standalone probes, protocol pins, main-workspace PocketIC suite and release gate.
Retain generic feature resolution, descriptor integrity, bounded endpoints,
lifecycle and authorization tests using current Canic-owned fixtures.

The independent service CLI owns blob operations. Its status command does not
implement Canic's former `--check-ready` exit contract. Direct provider funding
has no qualified replacement command in the selected standalone service. These
are explicit removed operator surfaces, not reasons to retain obsolete code.

The source cut does not delete any canister, reset stable state, upload content or
spend cycles. Existing providers may retain liability after logical release. Keep
observed obligations and their evidence until separately reviewed retirement can
account for them; source removal is not physical deletion or billing cessation.
