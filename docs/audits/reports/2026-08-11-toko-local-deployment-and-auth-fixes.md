# Toko local deployment and internal authorization fixes

Date: 2026-08-11  
Canic base: `v0.101.43` (`c190a54aa`)  
Working state: local, dirty, uncommitted, unstaged  
Changelog placement: `Unreleased` after `v0.101.43`

## Purpose

This report records the complete Canic change set produced while diagnosing
Toko's fresh local deployment and login failures. It also records the
downstream Toko integration that motivated the final Canic API additions.

The reconciled worktree contains unstaged changes only. The complete pre-pull
state remains recoverable in
`stash@{0}: codex-pre-v0.101.43-reconcile-2026-08-11`; review `git diff HEAD`
before committing or splitting the work into pull requests.

## Executive summary

Four distinct problems were found:

1. Root Store status re-read and re-hashed every staged application Wasm
   payload. Toko's full release set made the query exceed the IC's five-billion
   instruction limit.
2. A top-level `--icp <path>` selection was lost inside fresh-install
   orchestration. Nested work silently returned to the `icp` binary found on
   `PATH`.
3. managed Component environments stored the Fleet Subnet Root Canister
   principal as `subnet_pid`, rather than the physical placement Subnet from
   the Component Registry binding.
4. Toko attempted to retrieve a certified role-attestation proof from Root by
   making an inter-Canister call to a query method. That execution context has
   no root data certificate, so the design could not work even after correcting
   the Subnet identity.

The resulting fixes are deliberately separate:

- Root Store bootstrap still performs full staged-payload validation, while
  status verifies bounded approved metadata and the exact live Store catalog.
- The selected ICP executable is now an explicit install input carried to
  every raw ICP command.
- Component and Component Child runtime environments use their Registry-bound
  physical placement Subnet.
- Root applications can resolve exact active Component Registry membership,
  and downstream applications can implement async endpoint access predicates
  through Canic's public facade.

Canic's existing role-attestation feature was not removed. Toko stopped using
its certified-query retrieval path for automatic Canister-to-Canister updates.

## Observed failure sequence

### 1. The wrong ICP CLI was selected

The first local start failed with:

```text
found: icp 1.1.0
required: icp-cli >=1.2.0, <2.0.0
```

Toko could select a newer executable at the outer command boundary, but the
fresh-install path reconstructed several nested commands with the literal
program name `icp`. That made execution depend on `PATH` again.

This was not merely a help-text or parsing defect. The executable identity had
to survive all the way through network readiness, creation, installation,
verification, Root Store bootstrap, Registry activation, Component
provisioning and Fleet catalog closeout.

### 2. Root Store status exhausted query instructions

The next material failure was:

```text
canic_root_store_bootstrap_status
Canister exceeded the limit of 5000000000 instructions
```

Bootstrap correctly validated staged chunks and payload hashes before Store
publication. Status then repeated that expensive validation while checking the
postcondition. With Toko's multi-Canister release set, this made a nominal
status query scale with the total compressed Wasm bytes.

### 3. Role attestation used the wrong Subnet identity

After installation progressed, login first failed with a role-attestation
Subnet mismatch. The request contained the Root Canister principal where the
Registry expected the physical placement Subnet principal.

The managed runtime environment had populated both of these fields from the
Root principal:

```text
fleet_subnet_root_pid = root Canister principal
subnet_pid            = root Canister principal  # incorrect
```

The correct identity is:

```text
fleet_subnet_root_pid = root Canister principal
subnet_pid            = Component binding placement_subnet
```

### 4. Certified proof retrieval was impossible in that call context

Once the Subnet mismatch was corrected, login reached the next failure:

```text
[RootDataCertificateUnavailable]
root data certificate unavailable for role-attestation proof retrieval
```

Toko's helper performed this sequence from a managed application Canister:

```text
Component update
  -> Root canic_prepare_role_attestation update
  -> Root canic_get_role_attestation query
```

`canic_get_role_attestation` assembles a Canister-signature proof and therefore
requires `data_certificate()`. A query invoked through this inter-Canister
update chain does not receive a data certificate. Retrying, reinstalling,
changing the Subnet value or moving the same code to another helper cannot
make that certificate appear.

The correct Toko path is direct active-membership authorization through Root's
current Component Registry, enforced as an async endpoint access predicate.

## Change batch A: bounded Root Store status

File:

- `crates/canic-control-plane/src/workflow/bootstrap/root_store/mod.rs`

### What changed

The staged release lookup was split into two operations:

- `exact_staged_manifest_metadata` validates the exact approved manifest
  authority for every role: template identity, role, version, payload hash,
  payload size, chunking mode, approval state and accepted Store binding.
- `exact_staged_manifests` calls that metadata operation and additionally runs
  `TemplateChunkedOps::validate_staged_release` for every payload.

`bootstrap` continues to call `exact_staged_manifests`, so the mutation gate
still validates every staged chunk and complete payload before publication.

`status` now calls `exact_staged_manifest_metadata`, then compares it with the
single live Store catalog and the raw module hashes protected by the release
set.

### Why

Status is a postcondition check after the release set has passed the full
bootstrap integrity boundary. Re-reading every staged payload during status
made query work proportional to artifact bytes without strengthening the live
catalog comparison.

### Security and correctness boundary

This does not weaken bootstrap admission:

- canonical release-set bytes and digest are still checked;
- the admitted topology projection is still reproduced;
- artifact metadata and size ceilings are still checked;
- bootstrap still verifies staged chunks and payload hashes;
- status still requires exact approved metadata and the exact live Store
  catalog.

The intentional change is only that status does not repeat full staged-payload
decoding and hashing after publication.

## Change batch C: correct managed runtime Subnet identity

File:

- `crates/canic-core/src/workflow/env/mod.rs`

### What changed

For both `ManagedCanisterBinding::Component` and
`ManagedCanisterBinding::ComponentChild`, `Env.subnet_pid` now comes from the
binding's `placement_subnet`.

`fleet_subnet_root_pid` and `root_pid` remain the Root Canister principal.

### Why

A Root Canister principal and an IC Subnet principal are different authority
identities. Role-attestation admission compares the claimed Subnet with the
physical placement retained by the Component Registry. Supplying the Root
principal made a valid Component appear to be on a different Subnet.

This is a real Canic identity bug independently of Toko's later certificate
retrieval problem.

## Change batch D: active Component lookup and async access facade

Files:

- `crates/canic-control-plane/src/api/component_auth/mod.rs`
- `crates/canic/Cargo.toml`
- `crates/canic/src/access/mod.rs`
- `Cargo.lock`

### What changed

`ComponentAuthApi` now exposes:

```rust
pub fn active_component_member(
    subject: Principal,
) -> Result<ManagedCanisterBinding, Error>
```

It delegates to the existing Component Registry workflow, which requires an
active Fleet Subnet Root and exact active membership. The existing
caller-specific attestation path now reuses this method.

The public `canic::access` facade now exports:

- `AccessContext`;
- `AsyncAccessPredicate`;
- the `async_trait` attribute.

The `canic` package therefore adds its existing workspace `async-trait`
dependency, reflected in `Cargo.lock`.

### Why

An application Root needs to answer a narrow question for guarded internal
calls: "Is this exact principal currently an active managed Component, and
what immutable binding does it hold?"

The authoritative workflow already existed, but the application-facing API did
not expose it. Similarly, Canic endpoint macros accepted custom async
predicates, but downstream crates could not implement that contract through
the supported facade.

This change exposes the existing authority; it does not create another
Component Registry or duplicate its validation logic.

### What Canic does not add

Canic does not add a generic public network endpoint that reveals arbitrary
members. The downstream Root chooses whether to expose a narrowly guarded
application endpoint and remains responsible for its caller policy.

## Downstream Toko integration

These changes live in the Toko repository and are not part of the Canic diff,
but they explain why batch D exists.

### Authorization flow

```text
original Component A
  -> protected system endpoint on Component B
       -> B's async access predicate calls Toko Root with subject A
            -> Root first proves B is an active Component Registry member
            -> Root resolves A's exact active binding and returns its role
       -> B admits only configured roles
       -> endpoint body runs
```

Important properties:

- the subject comes from `AccessContext::transport_caller`, not a payload role
  supplied by A;
- authorization happens before the endpoint body;
- Root unavailability or missing membership fails closed;
- no certified query proof is requested from an inter-Canister update;
- no unrestricted public system endpoint was introduced.

### Root endpoints and delegation provisioning

Toko Root now provides a guarded `toko_active_component_role(subject)` update.
Only an active managed Component can call it.

`toko_provision_issuer_delegation(issuer_pid)` no longer accepts a caller-
supplied attestation or Fleet key. Root derives and verifies the authority:

- a non-controller caller must be an active `user_hub`;
- the issuer must be an active `user_shard`;
- caller and issuer must belong to the same Fleet;
- a controller may invoke the operation, but the issuer must still be an
  active `user_shard`, and the Fleet audience is derived from that binding.

This is stricter than trusting a supplied Fleet field.

### Guarded Toko surfaces

| Receiver | Accepted active caller role | Additional binding |
| --- | --- | --- |
| `user_hub` system user/project endpoints | `project_hub`, `project_instance` | existing local-build and controller allowances retained |
| `project_registry.refresh_project` | `project_instance` | non-controller transport caller must equal the supplied project principal |
| `project_instance.system_get_registry_snapshot` | `project_registry` | role checked before snapshot construction |
| `discovery_shard.add_project` | `project_instance` | transport caller must equal the supplied project principal |
| internal IcyDB metrics endpoints | `user_shard` | admin proxy also validates the target is an active allowlisted metrics role |
| Root issuer provisioning | `user_hub` or controller | issuer is active `user_shard`; Fleet identity must agree |

### Service discovery correction

Toko's runtime helper previously searched `canic_canister_children`. Current
top-level Components are root-owned pool workloads represented by committed
Component Directory bindings, not legacy generic Root children.

The helper now consumes Toko Root's `toko_platform_canisters` projection. This
is required for `user_hub` and `project_registry` resolution independently of
the authorization fix.

## Security considerations

### Endpoint admission remains authoritative

The application check is an `AsyncAccessPredicate`, not a convention inside
business logic. If the Root lookup fails, returns a disallowed role or finds an
inactive principal, Canic rejects before entering the endpoint body.

### No caller-provided role is trusted

Receivers send Root the IC transport caller principal they observed. Root
derives the role and Fleet authority from its current Component Registry.

### Revocation timing

The decision reflects Root's active Registry state at lookup time. As with any
cross-Canister authorization call, a later Registry mutation can occur before
the receiver resumes. Workflows that require Root-serialized revocation at the
exact mutation commit point should execute that mutation under Root ownership
rather than relying on a remote admission lookup.

### Availability and cost

Guarded calls now include a Root round trip. This adds latency and cycles, but
it is bounded and fails closed. Admin metrics can perform two lookups: one to
validate the requested metrics target and one at the target to validate the
`user_shard` proxy.

### Scope is local to one Root

The lookup resolves the current Root's Component Registry. It is not a
cross-root or cross-Fleet peer-authentication protocol. A future cross-root
surface must use the dedicated Fleet-service peer authority model rather than
assuming this lookup spans Roots.

### Role-directory visibility

An active Component can ask the application Root for another principal's role
through Toko's narrow endpoint. Component roles are topology metadata, not
secrets. If that assumption changes, the endpoint should return only a boolean
decision for a declared policy rather than the role string.

## Items investigated but not changed here

### eCryptfs durable create-new fallback

The unsupported `renameat2(RENAME_NOREPLACE)` behavior on eCryptfs was already
fixed upstream before this local batch. The current `v0.101.43` base includes
the fallback first published in `0.101.33` and present in later releases. There
is no local diff to `crates/canic-host/src/durable_io/mod.rs` for this issue.

### Empty prepaid Root pool

The local wrapper observed zero Ready Canisters, provisioned the configured
pool and resumed the install journal. That was expected recovery behavior and
did not require a Canic code change in this batch.

### Missing frontend Root Canister ID

`VITE_ROOT_CANISTER_ID` is a downstream artifact/environment synchronization
issue. It is generated only after a successful local install and requires the
frontend dev process to restart. No Canic runtime change was made for it.

### Role-attestation protocol

The certified role-attestation API remains in Canic for execution contexts
that can retrieve and verify certified query material. This batch does not
redesign that protocol or claim that certified query results are available to
ordinary inter-Canister updates.
